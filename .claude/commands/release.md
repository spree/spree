---
description: Cut a Spree release end to end — audit, version bump, release notes, pull request, tags and the GitHub release.
---

Cut the Spree release named in the arguments: `6.0.2`, `6.1.0` or a
prerelease such as `6.1.0.rc1` (gem spelling). With no argument, propose the
next patch of `Spree::VERSION` and confirm it.

Version: $ARGUMENTS

Releases are published by `.github/workflows/release.yml` from tags pushed on a
commit already on `main`; `.changeset/README.md` has the mechanics. This command
wraps them with the review a release needs. Run the phases in order. Phase 5
needs the pull request merged, so the command usually stops after phase 4 and
is run again to publish.

Work on a branch named `chore/release-<version>` with the workspace installed
(`node_modules` present), never on `main`.

## 1. Audit what ships

Run `git fetch origin --tags` first. The last Spree tag is `git describe
--tags --abbrev=0 --match 'v*' origin/main` and its date is `git log -1
--format=%cI <tag>`. List the commits since it with `git log --format='%h %an
%s' <tag>..origin/main`. A commit merged through a pull request ends in
`(#1234)`; fetch all of those in one call, `gh pr list --state merged --base
main --search "merged:>=<tag date>" --limit 200 --json
number,title,author,body`, and keep the numbers the log names. A commit with
no number was pushed straight to `main`: it stays in the list with its author
and is linked by commit instead. Strip CodeRabbit and "Generated by" trailers
from the bodies. These feed the release notes in phase 3.

Then check the diff since the tag for anything that does not fit the release
type, and list each item for the user before bumping:

- **Migrations**: new files under `spree/*/db/migrate/`, and any edit to a
  migration that has already shipped (apps that ran it will not run it again).
- **Gemspec and `package.json` dependency changes**: a major bump or a removed
  runtime dependency breaks apps that relied on it. `bundle update
  --conservative` cannot follow a dependency major.
- **Public API and component changes** marked as `patch` in `.changeset/`:
  removed props, renamed fields, anything a plugin or SDK user could call.
- **Generated artifacts left behind**: a serializer change without its
  `docs/api-reference/*.yaml` regeneration, SDK types out of date.
- **Open pull requests by the user** that are green and could ride along.

A patch release carries only patch changesets for the packages in the
`fixed` group. If one of those names `minor` or `major`, either downgrade it
with the user's agreement (6.0.1 did this) or stop and propose a minor release
instead. `@spree/cli` and `create-spree-app` keep their own versions, so their
changesets may name any bump.

Decide the tool releases: `@spree/cli` and `create-spree-app` ship only when
`git log <their last tag>..origin/main -- packages/<dir>` names a change to
what the package publishes (its source, binaries, templates or dependencies;
not tests, lint or repository files), where the tag is `git describe --tags
--abbrev=0 --match '@spree/cli@*' origin/main` (or `create-spree-app@*`).
Every such change needs a changeset; add one if a commit forgot it. A tool
with no such change keeps its version and gets no tag.

Confirm CI is green on `origin/main` HEAD: `gh run list --branch main --limit 6`.

## 2. Bump

1. Set `Spree::VERSION` in `spree/core/lib/spree/core/version.rb`.
2. `GITHUB_TOKEN=$(gh auth token) pnpm version:packages` — the changelog
   writer needs the token to link pull requests. Never run plain
   `changeset version`.
3. Read every `packages/*/CHANGELOG.md` entry it wrote. A changeset shared by
   several packages lands word for word in each; rewrite an entry that describes
   another package (the CLI's entry must talk about the CLI). The entry for a
   package with no changes of its own is "Released with Spree <version>, with no
   changes of its own."
4. Verify: `node scripts/publish-packages.mjs verify v<version>` and, for each
   tool that moved, `verify @spree/cli@<version>` or
   `verify create-spree-app@<version>`. `pnpm install --frozen-lockfile
   --offline` must still pass; a version bump never changes the lockfile.
5. For a minor or major release, add the entry to `docs/changelog.mdx` (the
   6.0.0 release commit shows the shape) and make sure the upgrade guide under
   `docs/developer/upgrades/` exists. Patch releases skip this.
6. Commit as `Released Spree <version>`. The body says which tools moved and
   which stayed, and why. Amend the fixes from the reviews that run before the
   pull request opens into it; once it is open, `/open-pr` pushes each round
   as its own commit and the pull request is squash-merged.

## 3. Write the release notes

Write `tmp/release-notes-<version>.md` in the repository (`tmp` is ignored by
git) in exactly this shape. It becomes the GitHub release body, and the
dashboard's notifications panel renders that body in every merchant's admin, so
keep it plain GitHub markdown.

````markdown
# Spree <version>

<Two or three sentences: what kind of release this is and the three or four things a merchant or developer will notice.>

```bash
npx spree upgrade
```

---

## ✨ New features

- **<Feature in a few words>.** <One or two sentences on what it does for the merchant or developer.> [#1234](https://github.com/spree/spree/pull/1234)

## 🧭 Admin dashboard improvements

- **<Improvement>.** <Sentence.> [#1234](https://github.com/spree/spree/pull/1234)

## 🐛 Bug fixes

- <What works now, as a plain sentence; no bold lead.> [#1234](https://github.com/spree/spree/pull/1234) by @handle

## ⬆️ Upgrading from <previous minor>

- <Fixes and steps for stores still coming from the previous minor.> [#1234](https://github.com/spree/spree/pull/1234)

## 🛠 Developer experience

- <Dependency changes, removed gems or packages, CLI and template changes, with what an app owner must do.> [#1234](https://github.com/spree/spree/pull/1234)

## 📚 Documentation

- <Guide rewrites and new pages.> [#1234](https://github.com/spree/spree/pull/1234) by @handle

---

## 📦 Package versions

| Package | Version |
| --- | --- |
| Spree gems | `<version>` |
| `@spree/sdk`, `@spree/admin-sdk`, `@spree/seller-sdk`, `@spree/core` | `<npm version>` |
| `@spree/dashboard`, `@spree/dashboard-core`, `@spree/dashboard-ui`, `@spree/seller-dashboard` | `<npm version>` |
| `@spree/cli` | `<version>` |
| `create-spree-app` | `<version>` (unchanged) |

**Full Changelog:** https://github.com/spree/spree/compare/v<previous>...v<version>
````

Rules:

- Keep only the sections that have entries, in this order. "Upgrading from"
  appears when a change fixes the upgrade path from the previous minor.
- One bullet per pull request, or one bullet for a group of pull requests that
  make one change (list every number). Every bullet links its pull request.
- Write for the reader of the section: merchants in features, dashboard and
  bug fixes; developers in upgrading, developer experience and documentation.
  Say what works now, not what was broken or how it was fixed. No class names,
  file paths or internal terms in the merchant sections.
- Credit every author other than the person cutting the release with
  `by @handle` after the link.
- Breaking or action-needed items (a dependency major, a removed gem, a removed
  prop, a rake task to re-run) go in "Developer experience" or "Upgrading from"
  with the action spelled out.
- Internal work (test helpers, CI, repository tooling nobody installs) is left
  out.
- The npm spelling of a prerelease is `6.1.0-rc.1`; the table shows it.

Show the notes to the user in the final report of this phase.

## 4. Open the pull request

Run `/open-pr`. The pull request description is the release summary (which
tools moved and that the tags and GitHub release follow the merge), a `---`
line, then the notes from phase 3 verbatim. A release pull request is the
exception to the short-description rule: reviewers review the notes there, and
phase 5 reads them back from it. Only collaborators can edit a pull request
description, so never post the notes as a comment, which anyone can write.
Stop when `/open-pr` reports: the merge needs a human review.

## 5. Publish (after the merge)

Run from a checkout of `main` at the merge commit (`git pull`). Check
`Spree::VERSION` is the target and the tag does not exist yet.

1. Tag the merge commit and push, three tags at most in one push (GitHub starts
   no workflow beyond that):

   ```bash
   git tag v<version> && git tag '@spree/cli@<version>'   # only tools that moved
   git push origin v<version> '@spree/cli@<version>'
   ```

2. Watch the release workflow: `gh run list --workflow release.yml --limit 3`,
   then `gh run watch <id>`. Every job skips versions already on its registry,
   so a failed run is re-run with `gh run rerun <id> --failed`, never with a
   new tag.

3. Create the GitHub release from the notes once the gems and packages are on
   their registries. Take the notes from the pull request description, from
   the `# Spree <version>` heading to the end:

   ```bash
   gh pr view <n> --repo spree/spree --json body --jq .body | tr -d '\r' | sed -n '/^# Spree <version>$/,$p' > tmp/release-notes-<version>.md
   ```

   The `tr` matters: a description edited on github.com comes back with CRLF
   line endings, and the heading match would otherwise find nothing.

   Show the file to the user and wait for their go-ahead before publishing:
   the body reaches every admin's notifications panel, so a wrong or tampered
   body is a security problem, not a typo.

   ```bash
   gh release create v<version> --title v<version> --notes-file tmp/release-notes-<version>.md --latest
   ```

   `--latest` only when this is the newest stable release; a patch for an older
   minor takes `--latest=false`. A prerelease takes `--prerelease` and not
   `--latest`.

4. Confirm the exact version, not the latest one (a prerelease publishes under
   npm's `beta` tag and RubyGems hides prereleases by default):
   `gem info spree_core --remote --prerelease -v <version>`,
   `npm view @spree/sdk@<npm version> version`, and the dashboard's
   notification panel on a store running the new version names the release.

## Final report

The pull request or release URL, the audit items the user accepted or
deferred, the tool versions released or kept, and the follow-ups the audit
produced (regenerated docs, a changeset a commit forgot, an upgrade note).
