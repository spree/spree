# Preferences Stored as JSON

**Status:** Design finalized — open questions settled 2026-10-01, nothing built
**Target:** Spree 6.0
**Depends on:** nothing. Follows the precedent of the metadata consolidation (`20260809120001_consolidate_metadata_columns.rb`)
**Author:** Damian + Claude
**Last updated:** 2026-10-01
**Tracking:** Linear V-3730 · GitHub spree/spree#14786

## Summary

Every model's `preferences` column is a YAML document, written by one line in `Spree::Preferences::Preferable` (`serialize :preferences, type: Hash, coder: YAML`). This plan moves them to a JSON column (`jsonb` on PostgreSQL, `json` on MySQL and SQLite) in 6.0, converting the stored data during the 6.0 upgrade. Reasons: loading YAML is an attack surface Rails has to fence with `yaml_column_permitted_classes`; that list is application configuration Spree has to inject and every Rails upgrade touches; YAML columns cannot be queried or indexed; and two tables built in 6.0 already declare `preferences` as JSON but, through the shared coder, hold a YAML document wrapped in a JSON string — so they look queryable and are not. 6.0 is a clean-break release and already carries a data-converting migration of the same shape, which makes it the right release for this.

## Key Decisions (do not deviate without discussion)

1. **One JSON coder replaces YAML in `Preferable`.** It writes a plain JSON object with string keys and loads it as a `HashWithIndifferentAccess`, so `preferences[:amount]`, `fetch(:amount)` and the generated `preferred_*` readers keep working unchanged.
2. **The declared type casts on read as well as on write.** The `preferred_*` reader passes the stored value through the same `convert_preference_value` the writer already uses, so a decimal read from JSON comes back as a `BigDecimal`, exactly as it did from YAML. The preference declarations are the schema; no second schema is introduced.
3. **Symbols are not stored.** Keys become strings; symbol values become strings. Code comparing preference values to symbols must compare strings.
4. **The conversion runs inside the 6.0 migration, not in an upgrade task.** `spree:upgrade` runs its manifest *after* `db:migrate` (see `upgrade.rake` and the CLI's `upgrade` command), so a backfill scheduled there would find the YAML column already replaced. This is the reasoning `ConsolidateMetadataColumns` recorded for the same problem. The proposal's "add a column, backfill with a task, swap later" order does not work with Spree's upgrade runner.
5. **The migration never uses models.** It reads rows with `select_all`, parses with `YAML.safe_load` and an explicit permitted-class list, and writes with `exec_update`. A model would load through whichever coder the current code declares, which is the thing being changed.
6. **No batching or background job.** Every table in the inventory is configuration-sized (one row per calculator, rule, gateway, store, import). The append-only log table the proposal anticipated no longer exists.
7. **A row still holding YAML fails when it is read, not at boot** (decided 2026-10-01). `JsonCoder.load` raises `Spree::Preferences::LegacyYamlError` naming the model's table and the task that fixes it (a coder sees the value, not the record, so the row is found by the task), and the `spree:upgrade:preferences_json` task reports any leftovers. A boot check was rejected: boot also happens where there is no database (asset builds) and before the converting migration has run, so it would block the very migration that repairs the data, and it would cost a query per table on every start. Accepted trade-off: a missed row breaks the requests that touch that record rather than the whole application, so the failure is loud but local.
8. **Decimals are stored as exact strings** (decided 2026-10-01): `{"amount": "9.99"}`, which is what `BigDecimal#as_json` produces and what the API already returns. A JSON number was rejected because Ruby and JavaScript parse it as a float before the read cast can restore it. Accepted trade-off: a numeric comparison in SQL needs an explicit cast (`(preferences->>'amount')::numeric`).
9. **Tiered calculators store tiers as a list, not a hash with number keys** (decided 2026-10-01). `Spree::Calculator::TieredPercent` and `TieredFlatRate` change `preference :tiers, :hash` to `preference :tiers, :array` of `{ "threshold", "rate" }` (`"amount"` for flat rate) objects, sorted by threshold. JSON object keys are always strings, so the hash shape could only survive with a hidden cast; a list reads naturally in JSON and TypeScript. This changes the `tiers` value these calculators show through the Admin API, which is a breaking change listed in the upgrade guide. The migration converts the shape.
10. **Encryption is out of scope** (decided 2026-10-01). Gateway secrets in payment method preferences stay as unencrypted as they are today; this plan changes the storage format only. Encrypting them gets its own plan. See the constraint below about keeping that option open.

## Design Details

### Coder

```ruby
# spree/core/lib/spree/core/preferences/json_coder.rb
module Spree::Preferences
  # One instance per model (`coder: JsonCoder.new(table_name)`), so the
  # error can name the table.
  class JsonCoder
    def initialize(table_name)
      @table_name = table_name
    end

    def dump(hash)
      hash.nil? ? nil : hash.to_h.deep_stringify_keys.as_json
    end

    def load(value)
      raise LegacyYamlError, @table_name if value.is_a?(String)

      (value || {}).with_indifferent_access
    end
  end
end
```

`as_json` turns `BigDecimal` into its exact string (`"9.99"`), `Date` into ISO 8601 and symbols into strings, so `dump` never hands the adapter a Ruby-only type. Rails' JSON column type has already decoded the value before `load` sees it, on every adapter, so a string reaching `load` can only be a leftover YAML document.

### Reads cast through the declared type

```ruby
define_method preference_getter_method(name) do
  stored = (preferences || {}).fetch(name) { return default.call }
  convert_preference_value(stored, type, nullable: nullable)
end
```

`convert_preference_value` is idempotent for every type it handles, so casting on read changes nothing for values written in this process.

### Places that assume symbol keys

Three raw reads (`provision_defaults.rb`, `promotion/rules/country.rb` twice) keep working through indifferent access. Two places compare key sets and need a stringify: `Spree::Base`'s `after_initialize` backfill (`default_preferences.except(*preferences.keys)` would otherwise see every default as missing and dirty every record on load) and `Preferable#preference_change`.

### Migration

One migration, `ConvertPreferencesToJson`, for every table in the inventory:

1. For each table that has a `preferences` column whose values are YAML: add `preferences_json` (`jsonb` if the adapter has it, else `json`), convert each row, drop `preferences`, rename `preferences_json` to `preferences`.
2. For the two tables already typed JSON: rewrite each row whose value is a string in place.
3. Convert `spree_preferences.value` the same way.

Conversion per row: `YAML.safe_load(text, permitted_classes: [Symbol, BigDecimal, Date, Time, ActiveSupport::TimeWithZone, ActiveSupport::TimeZone, ActiveSupport::HashWithIndifferentAccess], aliases: true)` — the list Spree's engine already permits, plus `Date` — then `JsonCoder.dump`. Tables are discovered from the schema (any table with a `preferences` column), as the metadata migration does, so an application's own `Preferable` table converts too.

A row that does not parse — typically an old `!ruby/hash-with-ivars:ActionController::Parameters` dump, which the current code already cannot load — stops the migration with the table name and row id, rather than being converted to `{}`.

### Tiered calculators

```ruby
# Before: { 100.0 => 10.0, 250.0 => 15.0 }
preference :tiers, :array, default: []
# After:  [{ "threshold" => "100.0", "rate" => "10.0" }, { "threshold" => "250.0", "rate" => "15.0" }]
```

`compute` picks the last tier whose threshold the amount reaches. Validation checks that each entry has a positive threshold and, for the percent calculator, a rate from 0 to 100, and that thresholds are unique. The migration converts the hash for rows whose `type` is either calculator, keeping the decimal-string rule above.

### Afterwards

`yaml_column_permitted_classes` injection is removed from `Spree::Core::Engine` and from the dummy app generator. The comments in `preferable.rb` and `base.rb` that explain YAML behaviour go with it.

## Migration Path

1. Change the tiered calculators to the list shape (code and specs).
2. Add `JsonCoder` and `LegacyYamlError`; switch `Preferable` to it; cast on read; stringify the two key-set comparisons; delete the dead `serialize` on `Spree::Address`.
3. Add the `ConvertPreferencesToJson` migration, including the tiers reshaping, with a reversible `down` (JSON back to YAML restores every value through the declared types; tiers convert back to the hash).
4. Add the `spree:upgrade:preferences_json` safety-net task to the 5.6→6.0 manifest: it reports and converts any row still holding YAML, for schemas changed out of band.
5. Remove the YAML permitted-classes configuration.
6. Document the change in `docs/developer/upgrades/5.6-to-6.0.mdx` and update `docs/developer/customization/model-preferences.mdx` (keys are strings in the raw hash; values come back typed through the `preferred_*` readers), and the tiers example in `docs/developer/core-concepts/promotions.mdx`.
7. Specs: a coder round trip for every declared type, the migration on each adapter, the existing preference specs passing unchanged, and the tiered calculator specs moved to the list shape.

## Constraints on Current Work

- **New `preferences` columns are JSON.** Use the `t.respond_to?(:jsonb)` guard from the root CLAUDE.md. Do not add another `text` preferences column.
- **Read preferences through `preferred_*` or `get_preference`, not the raw hash.** The raw hash is where YAML and JSON differ; the readers hide it.
- **Do not store symbols, `BigDecimal` or `Time` objects in a preference you expect back unchanged** without a declared type that casts it.
- **Keep `:password` preferences as single string values.** A later encryption plan will encrypt them value by value inside the JSON, so other keys stay queryable. Do not nest secrets inside `:hash` or `:array` preferences, where they could not be found and encrypted.
- **No number keys in `:hash` preferences.** JSON turns them into strings. Use a list of objects, as the tiered calculators now do.
- **Do not query `preferences` in SQL until this lands.** On the two JSON-typed tables the value is a YAML string today and any JSON operator silently matches nothing.
