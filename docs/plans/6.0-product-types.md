# ProductType (Prototype → ProductType)

**Status:** Draft
**Target:** Spree 6.0
**Depends on:** Custom Fields system (Metafields, shipped 5.4; 6.0 vocabulary per `5.4-6.0-custom-fields-rename.md`), `6.0-store-scoped-custom-field-definitions.md` (definitions become store-owned — the joins here validate same-store). Coordinates with: `6.0-replace-taxons-with-categories.md` (this plan ships **before** the Taxon→Category table rename; the `class_name` flip happens in that plan's wave). Consumed by: `6.0-fulfillment-and-delivery.md` (`fulfillment_types` replaces ShippingCategory — that plan cannot ship before this one).
**Author:** Damian + Claude
**Last updated:** 2026-07-27

## Summary

Rename and extend the existing `Spree::Prototype` model into `Spree::ProductType` — a persistent, schema-defining, **store-owned** association on Product. Today Prototype is a fire-and-forget creation template (it *replaces* the product's option types and taxons at creation, then has no ongoing relationship — and since the legacy admin's prototype UI was already deleted, prototypes are currently uncreatable outside the console). ProductType becomes a **live template** that defines what option types, categories, and custom field definitions a product has, driving dashboard form generation and enabling type-aware filtering.

ProductType acts as an **authoritative template** for option types: changes to a type's option types propagate to all products of that type. Products may add extra option types beyond what the type provides, but cannot remove type-defined ones. This ensures catalog consistency (all "T-Shirts" share Color and Size) while allowing per-product flexibility (one T-shirt can add "Sleeve Length").

This closes Spree's biggest functional gap in catalog modeling, while building on existing infrastructure rather than starting from scratch.

## Problem

1. **No product schema enforcement.** All Spree products share the same shape. A merchant selling T-shirts and laptops has no way to say "T-shirts must have Size and Color; laptops must have RAM and Storage" without custom code.

2. **No admin form generation from type.** The dashboard shows the same fields for every product. Modern platforms auto-generate product editing forms based on ProductType — adding an attribute to a type instantly updates the form for all products of that type.

3. **Prototype is wasted infrastructure — more than previously stated.** The model, join tables (`spree_option_type_prototypes`, `spree_prototype_taxons`), and creation-time callback exist, but there is **no admin UI and no API endpoint for prototypes at all today** (verified: zero controllers/views/routes; only a dead locale key). The only living consumers are the `attr_accessor :prototype_id` + `add_associations_from_prototype` callback (`product.rb:137, 485, 868-873`), a factory, and a dangling v2 serializer registration.

4. **Custom fields are unstructured per product.** Any definition can be attached to any product. There's no way to declare "products of this type should have these custom fields."

## Key Decisions (do not deviate without discussion)

- **Rename only, no new table.** `Spree::Prototype` → `Spree::ProductType`, `spree_prototypes` → `spree_product_types`. Existing join tables renamed accordingly. No data loss.
- **All new surface is born with custom-field vocabulary** (the born-correct principle every other 6.0 plan follows). The new join is `Spree::ProductTypeCustomFieldDefinition` / `spree_product_type_custom_field_definitions` / `custom_field_definition_id`, associating via the `Spree::CustomFieldDefinition` constant (the 5.5 alias makes this work today, pre-rename). API keys are `custom_field_definitions`; prefixed IDs are the real ones (`cfdef_`). Naming the join against `MetafieldDefinition` would create a legacy-named model in the same release that deletes that constant.
- **ProductType is store-owned** (`belongs_to :store`, `Spree::SingleStoreResource`), matching Product (single-owner since 5.5), Category (6.0), and CustomFieldDefinition (`6.0-store-scoped-custom-field-definitions.md`). A global type joining store-scoped definitions/categories onto store-owned products would be a cross-tenant surface. Joins validate same-store; the Admin API scopes through `current_store.product_types`. Backfill: existing prototypes → `Store.default`.
- **Persistent `belongs_to`.** Product gets a `product_type` reference (nullable — existing products don't require a type), via `add_reference` (PK-type agnostic; no hardcoded `:bigint`). The `attr_accessor :prototype_id` + fire-and-forget callback is replaced by a real association. **Behavior change, stated plainly:** today's callback *replaces* the product's option types/taxons by assignment; the new sync is **additive**. API input takes prefixed IDs (`pt_…`), resolved via `find_by_prefix_id`.
- **ProductType defines OptionTypes, Categories, and CustomFieldDefinitions.** Three M2M associations, carried over or added via join tables.
- **ProductType is a live template for option types.** Adding an option type to the type adds it to all its products; removing one removes it from products (with safety checks). Products can add extra option types but cannot remove type-defined ones — "additive override": the type is the floor, not the ceiling.
- **The custom-field join carries `required` and `sort_order`.** `spree_product_type_custom_field_definitions` determines which definitions a type uses, whether they're required, and display order. This is the schema enforcement layer.
- **Prefix ID: `pt_`.** Replaces `proto_`.
- **No shared value pools in this phase.** Custom-field values remain per-resource strings. Faceted filtering via shared pools stays in Open Questions.
- **ProductType is optional.** Products without a type work exactly as today. Type enforcement is additive, not breaking.
- **ProductType is immutable on product after creation — and deletion honors the same invariant.** Changing a product's type would invalidate its custom-field values, so type changes are blocked at the model level once custom fields are assigned; `has_many :products, dependent: :restrict_with_error` blocks deleting a type that products still use (deletion *is* a type change to nil — the previous `dependent: :nullify` contradicted this decision and would have bypassed the guard via `update_all`). One-time exception: the 6.0 data migrations may assign an initial type to products that have none (see fulfillment-types addendum); immutability applies from then on.
- **ProductType carries `fulfillment_types`** (addendum 2026-07-27, required by `6.0-fulfillment-and-delivery.md`) — see "Fulfillment types" under Design Details. **This plan's Phase 1 owns the column** (previously orphaned: neither plan's migration created it, which would have silently broken digital checkout eligibility — `attribute` on a missing column is a virtual attribute that persists nothing).
- **`name` is translatable** — `TRANSLATABLE_FIELDS = %i[name]` + Mobility `translates` + a `spree_product_type_translations` table + registration in `Spree.translatable_resources`, so ProductType appears in the `5.5-6.0-resource-translations-api.md` discovery and batch endpoints. (The `include Spree::TranslatableResource` alone is not enough — verified against Product/Taxon.)

## Design Details

### Models

```ruby
# Renamed from Spree::Prototype
class Spree::ProductType < Spree.base_class
  has_prefix_id :pt

  include Spree::Metadata
  include Spree::Metafields            # becomes Spree::HasCustomFields in the rename wave
  include Spree::TranslatableResource
  include Spree::SingleStoreResource

  TRANSLATABLE_FIELDS = %i[name].freeze
  translates(*TRANSLATABLE_FIELDS, column_fallback: Spree.mobility_column_fallback)

  belongs_to :store, class_name: 'Spree::Store'

  # Existing (renamed join tables)
  has_many :option_type_product_types, class_name: 'Spree::OptionTypeProductType', dependent: :destroy
  has_many :option_types, through: :option_type_product_types

  has_many :product_type_categories, class_name: 'Spree::ProductTypeCategory', dependent: :destroy
  has_many :categories, through: :product_type_categories  # class_name flips Taxon→Category in the categories rename wave

  # New
  has_many :product_type_custom_field_definitions, class_name: 'Spree::ProductTypeCustomFieldDefinition',
           dependent: :destroy
  has_many :custom_field_definitions, through: :product_type_custom_field_definitions

  # restrict, not nullify — deletion honors the immutability invariant and keeps products_count honest
  has_many :products, class_name: 'Spree::Product', dependent: :restrict_with_error

  validates :name, presence: true, uniqueness: { scope: spree_base_uniqueness_scope }
  validates :store, presence: true, unless: -> { Spree::Config[:disable_store_presence_validation] }
  validates :fulfillment_types, presence: true

  attribute :fulfillment_types, default: ['shipping']   # model-level default; column has none (CLAUDE.md rule)

  self.whitelisted_ransackable_attributes = %w[name]
  self.whitelisted_ransackable_associations = %w[option_types]

  def digital? = fulfillment_types == ['digital']
  def requires_shipping? = fulfillment_types.include?('shipping')
end
```

ProductType must also be registered in `Spree.metafields.enabled_resources` (its own `include Spree::Metafields` is rejected by the definition `resource_type` validation otherwise) and in `Spree.translatable_resources`.

```ruby
# Renamed from Spree::OptionTypePrototype
class Spree::OptionTypeProductType < Spree.base_class
  belongs_to :option_type, class_name: 'Spree::OptionType'
  belongs_to :product_type, class_name: 'Spree::ProductType'

  validates :product_type, :option_type, presence: true
  validates :product_type_id, uniqueness: { scope: :option_type_id }

  # Live template: propagate to all products of this type
  after_create :add_option_type_to_products
  after_destroy :remove_option_type_from_products

  private

  def add_option_type_to_products
    product_type.products.find_each do |product|
      product.option_types << option_type unless product.option_types.include?(option_type)
    end
  end

  # Remove from products — only if no variants use values from it
  def remove_option_type_from_products
    product_type.products.find_each do |product|
      has_variants_using = product.variants.joins(:option_values)
                                  .where(spree_option_values: { option_type_id: option_type.id })
                                  .exists?
      next if has_variants_using

      product.option_types.delete(option_type)
    end
  end
end
```

### Product changes

```ruby
class Spree::Product < Spree.base_class
  belongs_to :product_type, class_name: 'Spree::ProductType', optional: true,
             counter_cache: :products_count

  # Remove: attr_accessor :prototype_id + add_associations_from_prototype
  # (also remove :prototype_id from Spree::PermittedAttributes.product_attributes)
  after_create :sync_associations_from_product_type

  validate :required_custom_fields_present, if: :active?
  validate :type_option_types_present, if: :product_type

  def type_option_type?(option_type)
    product_type&.option_types&.include?(option_type)
  end

  def extra_option_types
    return option_types unless product_type

    option_types - product_type.option_types
  end

  private

  # ADDITIVE — deliberately unlike today's prototype callback, which REPLACES
  # option_types/taxons by assignment (product.rb:870-871)
  def sync_associations_from_product_type
    return unless product_type

    product_type.option_types.each { |ot| option_types << ot unless option_types.include?(ot) }
    product_type.categories.each { |cat| taxons << cat unless taxons.include?(cat) }
  end

  def type_option_types_present
    (product_type.option_types - option_types).each do |ot|
      errors.add(:option_types, "cannot remove type-defined option type: #{ot.name}")
    end
  end

  def required_custom_fields_present
    return unless product_type

    product_type.product_type_custom_field_definitions.required.each do |join|
      unless has_custom_field?(join.custom_field_definition)
        errors.add(:base, "Missing required custom field: #{join.custom_field_definition.name}")
      end
    end
  end
end
```

### Admin surface (React dashboard — no Rails admin in 6.0)

Admin API + `@spree/admin-sdk` `productTypes` resource + dashboard pages (list under products settings, edit page with option-type picker, category picker, and a sortable custom-field-definitions editor with `required` toggles — dnd-kit reorder per house convention, i18n keys in all locale files, `<Can>` gating).

Product form behavior:
1. Type-defined option types render locked (cannot remove); extra option types removable.
2. Custom-field form fields render in `sort_order`, grouped by namespace, with required indicators; required fields validated before activation.
3. Creating a product: optional ProductType selector; selecting a type attaches its option types and categories (live — not a copy).

ProductType editing:
1. Adding an option type propagates to all products of the type.
2. Removing one is blocked per-product where variants use its values.
3. The UI shows affected product counts before destructive changes — **including deletion**, which is refused while products use the type (reassign first).

### Fulfillment types (addendum 2026-07-27)

`ShippingCategory` is dropped in 6.0 (`6.0-fulfillment-and-delivery.md`); its only real job — "which delivery methods may serve this product?" — moves here:

- `fulfillment_types` JSON column on `spree_product_types` (**created in this plan's Phase 1**, jsonb-guarded, nullable — the `['shipping']` default is model-level), e.g. `["shipping"]`, `["digital"]`, `["shipping", "pickup", "local_delivery"]`.
- **Products without a ProductType default to `['shipping']`** — the reconciliation between optional ProductType and today's effectively-mandatory ShippingCategory (every product presence-validates one, with auto-assignment).
- The fulfillment plan's data migration creates/assigns types **only where the category carried signal** — products in a digital shipping category get a `Digital` ProductType (`fulfillment_types: ['digital']`). This is the sanctioned one-time initial assignment; it doesn't violate immutability, which governs *changes* after a type is set.
- `Product#digital?` re-implements on top of this (today it's a four-hop chain through ShippingCategory → shipping-method scope → calculator class). `Product#fulfillment_types` is **net-new** surface — no such method exists today.
- Delivery-method eligibility semantics (matching against `DeliveryMethod#fulfillment_type`, per-product exclusions) are owned by `6.0-fulfillment-and-delivery.md`, not this plan.

## Migration Path

### Phase 1: Rename + schema

```ruby
class RenamePrototypesToProductTypes < ActiveRecord::Migration[7.2]
  def change
    rename_table :spree_prototypes, :spree_product_types
    rename_table :spree_option_type_prototypes, :spree_option_type_product_types
    rename_table :spree_prototype_taxons, :spree_product_type_categories

    rename_column :spree_option_type_product_types, :prototype_id, :product_type_id
    rename_column :spree_product_type_categories, :prototype_id, :product_type_id
    rename_column :spree_product_type_categories, :taxon_id, :category_id

    add_reference :spree_products, :product_type, index: true        # PK-type agnostic
    add_reference :spree_product_types, :store, index: true

    # fulfillment_types — owned here (see addendum); nullable, no DB default
    if connection.adapter_name.downcase.include?('postgresql')
      add_column :spree_product_types, :fulfillment_types, :jsonb
    else
      add_column :spree_product_types, :fulfillment_types, :json
    end

    add_column :spree_product_types, :products_count, :integer

    # match the model's uniqueness validation (the option-type join already has one)
    remove_index :spree_product_type_categories, [:product_type_id, :category_id]
    add_index :spree_product_type_categories, [:product_type_id, :category_id], unique: true

    create_table :spree_product_type_translations do |t|
      t.string :name
      t.string :locale, null: false
      t.references :product_type, null: false
      t.timestamps
    end
    add_index :spree_product_type_translations, [:product_type_id, :locale], unique: true
  end
end
```

## Constraints on Current Work

- **Do not remove Prototype yet.** It will be renamed, not deleted. Don't add features to it either.
- **Do not add `prototype_id` as a persisted column.** The rename adds `product_type_id` instead.
- **All new code around this feature uses custom-field vocabulary** (`custom_field_definition`, `has_custom_field?`, `cfdef_`) — never metafield naming (see `5.4-6.0-custom-fields-rename.md` constraints).
- **New CustomFieldDefinitions should be resource_type-aware** (`resource_type: 'Spree::Product'` for product-intended definitions).
- **Don't create a separate Attribute/Property system.** Everything builds on custom fields. No new EAV tables.
- **Don't build Product ↔ OptionType management that bypasses ProductType.** Type-defined option types are locked; only extras are freely managed.

## Resolved Questions

1. **Immutability is enforced at the model level, including deletion** (2026-07-27, closing former Open Question 3): type changes are blocked once custom fields are assigned; `dependent: :restrict_with_error` blocks deletion while products use the type; migrations get the one-time initial-assignment exception.
2. **ProductType is store-owned** (2026-07-27): global types joining store-scoped definitions/categories onto store-owned products would be cross-tenant; same-store validations on both joins; Admin API scoped via `current_store`.
3. **Born-correct custom-field naming** (2026-07-27): the join model/table/FK/API surface use custom-field vocabulary from birth; the 5.5 constant alias makes this implementable before the 6.0 rename wave.
4. **This plan owns the `fulfillment_types` column** (2026-07-27): previously orphaned between this plan and the fulfillment plan; now in Phase 1.

## Open Questions

1. **Shared value pools for faceted filtering.** Custom-field values are per-resource strings today; efficient faceted navigation ("count products by Color = Red") needs shared value rows for choice-type fields. Future phase here, or separate plan?
2. **Variant-level definitions on ProductType.** Should `ProductTypeCustomFieldDefinition` carry a `level` column (`:product` / `:variant`)? OptionTypes already own variant identity; variant-level custom fields would be descriptive metadata. Defer or include?
3. **Store API filtering by ProductType.** Should `GET /api/v3/store/products?filter[product_type_id]=pt_xxx` be first-class? Useful for type-specific browse pages.
4. **Option type removal UX.** When removal is blocked per-product (variants use its values), should the Admin API return the blocked-product list for resolution, or hard-block until variants are cleaned up?
