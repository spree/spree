## Summary

Rename and extend the existing `Spree::Prototype` model into `Spree::ProductType` — a persistent, schema-defining, **store-owned** association on Product. Today Prototype is a fire-and-forget creation template (it *replaces* the product's option types and taxons at creation, then has no ongoing relationship — and since the legacy admin's prototype UI was already deleted, prototypes are currently uncreatable outside the console). ProductType becomes a **creation-time template with live-by-reference schema** (semantics revised 2026-08-06, replacing the earlier "live template" design):

- **Live by reference (no sync, no copies):** the custom-field form the dashboard renders (including which fields are marked required) and `fulfillment_types` delivery eligibility are read from the type *at use time*. Editing the type's custom-field definitions updates every product form on next load with zero product rows touched.
- **Seeded at attach time (additive, one-shot):** option types and categories are materialized state (join rows that variants and navigation hang off), so the type seeds them additively when a product is created with the type or a type is assigned later. Editing a type **never mutates existing products**; the only path from a type edit to existing products is the explicit, previewed, additive-only **"Apply to existing products"** action.

This is the Shopify-shaped behavior (category changes affect nothing retroactively, and a type's `required` flag is guidance rather than a save-time rule) with Saleor's schema value (type-driven forms), and it closes Spree's biggest functional gap in catalog modeling while building on existing infrastructure rather than starting from scratch.

## Implementation status (verified 2026-08-05; semantics rescoped 2026-08-06)

**Shipped:** Phase 1 (the `Spree::ProductType` model, both join models, `fulfillment_types` with registry-backed validation, `Product#product_type` + `#fulfillment_types` + `#digital?`), Phase 3 (admin API controller, Store + Admin serializers — the base `V3::ProductTypeSerializer` exists only as the admin serializer's parent class per house convention; it is not wired to any store endpoint), and most of Phase 4 (dashboard settings page, product-types table, `product_type_id` on the product form).

**Phase 2 as rescoped — shipped 2026-08-06:**

1. **Seeding trigger fixed** — `sync_associations_from_product_type` now also runs `after_update, if: :saved_change_to_product_type_id?`, so assigning a type to an existing product and reassigning both seed (detach is a no-op). Presence guards query the join tables rather than the cached associations, which are stale when pending variants insert option-type joins in the same save.
2. **`ProductTypeCustomFieldDefinition`** — table + model with `required`/`sort_order`, `required`/`ordered` scopes, per-type uniqueness, and a validation that the definition's `resource_type` is `Spree::Product`. **No `Spree::CustomFieldDefinition` constant exists in Ruby** (the 5.5 alias this plan assumed is API-layer only), so the association carries custom-field vocabulary while `class_name` points at `Spree::MetafieldDefinition`.
3. **`required` is advisory — no server-side enforcement** (revised 2026-08-06, see Key Decisions). The join keeps the flag and the dashboard marks the field; nothing rejects a blank value.
4. **`ProductTypes::ApplyToProducts`** + `ApplyToProductsJob` + `POST /api/v3/admin/product_types/:id/apply_to_products` (202 with `products_count`). Batched, additive, idempotent. Both halves bulk-insert, and the counter caches, branch counts and reindexing that `insert_all` skips settle once per run rather than per category per batch. The job runs on **ActiveJob Continuations** (`Spree::Imports::ProcessJob` is the reference): the cursor is the last product id applied, so a deploy or timeout mid-backfill resumes there instead of restarting a catalog-sized run.
5. **Admin write surface** — `option_type_ids`, `category_ids` and the nested `custom_field_definitions` replace-set are permitted; the serializer returns association ids as prefixed ids (read/write symmetry). Category ids are re-scoped to `current_store` before assignment (OptionType is global — nothing to scope there).
6. **Dashboard** — the type sheet edits option types, categories and the dnd-kit-sortable custom-field list with per-row `required` toggles, carries the "changes apply to new products" note, and offers the confirmed apply action. The product form renders custom fields from its type via a new `definitionIds` prop on `FormBackedCustomFieldsProvider` (omitted ⇒ all definitions, so typeless products are unchanged). Keys added to all six locales.
7. **No immutability guard** — the superseded 2026-07-27 model-level block was never shipped and was not added; specs cover detach/reassign being additive and non-destructive.

Also shipped alongside: an integration spec for the whole resource (product types were entirely absent from the API reference), the `productTypes.applyToProducts` SDK method with expanded params, a sequenced `product_type` factory name (the static name collided whenever a spec built two types in one store), and `Spree::Store#product_types` — the inverse association was missing even though ProductType is store-owned.

**Sample data showcases the feature (2026-08-06).** `spree:load_sample_data` previously put all 37 demo products in one `Default` type, which demonstrated nothing. The CSV's `product_type` column now names six types derived from what the catalog actually contains — Kitchen Appliance, Air Treatment, Garment Care, Vacuum Cleaner, Hair Styling, Grooming — and `db/sample_data/product_types.rb` gives each its own schema: all six require wattage/voltage/warranty, Grooming also requires runtime (every trimmer and shaver is cordless), and capacity/room coverage/runtime/connectivity/noise level are optional where they apply. A field is required only where every product of that type actually carries it — room coverage is optional on Air Treatment because fans move air rather than treating a room. Categories are linked afterwards by `product_type_categories.rb`, since the import is what creates them. The `Default` and `Digital` types stay — they are seeds, not sample data.

**ShippingCategory is fully retired from behavior (2026-08-05).** `ProductType#fulfillment_types` is the sole delivery-eligibility input — `Stock::Package#eligible_delivery_methods` reads it and nothing consults the category for routing. The CSV `shipping_category` column was cut outright rather than bridged (see `6.0-fulfillment-and-delivery.md`); `Product#shipping_category` survives only as a deprecated association, dropping with the table in 6.1. The removal is unreleased but stays (2026-08-06 decision) — see the fulfillment plan's "named delivery groups" note for the if-needed 6.1 successor to profile-style grouping.

## Problem

1. **No product schema enforcement.** All Spree products share the same shape. A merchant selling T-shirts and laptops has no way to say "T-shirts must have Size and Color; laptops must have RAM and Storage" without custom code.

2. **No admin form generation from type.** The dashboard shows the same fields for every product. Modern platforms auto-generate product editing forms based on ProductType — adding an attribute to a type instantly updates the form for all products of that type.

3. **Prototype is wasted infrastructure — more than previously stated.** The model, join tables (`spree_option_type_prototypes`, `spree_prototype_taxons`), and creation-time callback exist, but there is **no admin UI and no API endpoint for prototypes at all today** (verified: zero controllers/views/routes; only a dead locale key). The only living consumers are the `attr_accessor :prototype_id` + `add_associations_from_prototype` callback (`product.rb:137, 485, 868-873`), a factory, and a dangling v2 serializer registration.

4. **Custom fields are unstructured per product.** Any definition can be attached to any product. There's no way to declare "products of this type should have these custom fields."

## Key Decisions (do not deviate without discussion)

- **Rename only, no new table.** `Spree::Prototype` → `Spree::ProductType`, `spree_prototypes` → `spree_product_types`. Existing join tables renamed accordingly. No data loss.
- **All new surface is born with custom-field vocabulary** (the born-correct principle every other 6.0 plan follows). The new join is `Spree::ProductTypeCustomFieldDefinition` / `spree_product_type_custom_field_definitions` / `custom_field_definition_id`, associating via the `Spree::CustomFieldDefinition` constant (the 5.5 alias makes this work today, pre-rename). API keys are `custom_field_definitions`; prefixed IDs are the real ones (`cfdef_`). Naming the join against `MetafieldDefinition` would create a legacy-named model in the same release that deletes that constant.
- **ProductType is store-owned** (`belongs_to :store`, `Spree::SingleStoreResource`), matching Product (single-owner since 5.5), Category (6.0), and CustomFieldDefinition (`6.0-store-scoped-custom-field-definitions.md`). A global type joining store-scoped definitions/categories onto store-owned products would be a cross-tenant surface. Joins validate same-store; the Admin API scopes through `current_store.product_types`. Backfill: existing prototypes → `Store.default`.
- **Persistent `belongs_to`.** Product gets a `product_type` reference (nullable — existing products don't require a type), via `add_reference` (PK-type agnostic; no hardcoded `:bigint`). The `attr_accessor :prototype_id` + fire-and-forget callback is replaced by a real association. **Behavior change, stated plainly:** today's callback *replaces* the product's option types/taxons by assignment; the new seeding is **additive**. API input takes prefixed IDs (`pt_…`), resolved via `find_by_prefix_id`.
- **ProductType defines OptionTypes, Categories, and CustomFieldDefinitions.** Three M2M associations, carried over or added via join tables.
- **Creation-time template, not a live sync** (2026-08-06, reversing the 2026-07-27 "live template" decision after competitor review — Saleor is the only platform with live propagation, and only because attributes there have no existence outside the type; Shopify deliberately made category changes affect nothing retroactively). Two regimes by data nature:
  - **Live by reference:** custom-field form generation, required-field validation, and `fulfillment_types` read the type at use time — they need no propagation to be "live".
  - **Seeded additively at attach:** option types and categories are copied (additively) when a product gets the type — at creation or a later assignment. Editing a type never mutates existing products; there are **no propagation callbacks** on the join models, no locked option types, and no provenance tracking to maintain. Products manage their option types freely after seeding; the type is a template, not a contract.
  - **Explicit apply action:** `ProductTypes::ApplyToProducts` (additive-only, idempotent, background job, previewed with the affected count) is the sole sanctioned path from a type edit to existing products — a deliberate bulk edit the merchant asks for by name, categorically different from a standing invariant mutating products as a side effect.
- **The custom-field join carries `required` and `sort_order`.** `spree_product_type_custom_field_definitions` determines which definitions a type uses, whether they're required, and display order. This is the schema enforcement layer. **No `level` column** — variant-level definitions are deferred to 6.1 (2026-08-06); option types already own variant identity, and the column would be speculative schema.
- **`required` is advisory, never enforced server-side** (2026-08-06, reversing the earlier "enforced at activation" decision). The flag stays on the join, ships in the API, is editable in the type editor, and renders as a marker on the product form — but no validation rejects a blank value. **Why the reversal:** Spree writes a product and its custom fields in *two* steps (the CSV importer saves at `product_variant.rb:88` and attaches at `:93`; API clients can do the same), so any save-time rule fights the write model. Three successive attempts at a trigger — activation-only, excluding creation, including creation — each either broke the importer or left a hole (a product created active never changes status again, so it would stay permanently non-compliant). **Competitor check:** Shopify has no required flag on metafield definitions at all; Medusa and Vendure have no type-driven required concept. Only Saleor enforces, and it can because attributes exist *solely* through the type and ride the product mutation atomically — neither is true in Spree, where any definition can attach to any product. A dashboard-side nudge on the activation action can be added later without touching the model.
- **Prefix ID: `pt_`.** Replaces `proto_`.
- **No shared value pools — ever, for custom fields** (2026-08-06, closing the former open question). Custom-field values remain per-resource strings. The split of roles, stated precisely: **predicate** search/sort/filter on those strings already ships storefront-side (5.6 — per-definition `searchable?`/`sortable?` flags, `SearchProvider::MetafieldSchema`, `with_metafield_filters` with Ransack-style predicates, in both Database and Meilisearch providers) and continues unchanged. **Faceted navigation over canonical values with counts** ("Color: Red (42)") is the OptionType/OptionValue role — value rows already shared, translatable, disjunctive facet counting shipped in 5.4 — and a value pool on custom fields would duplicate it. If demand for product-level descriptive facets emerges (the Vendure Facet / Saleor non-variant-attribute case), that is a new dedicated plan, not a custom-fields extension.
- **ProductType is optional.** Products without a type work exactly as today. Type enforcement is additive, not breaking.
- **A product's type is changeable: explicit detach and reassign are allowed** (2026-08-06, reversing the 2026-07-27 hard-immutability decision — which was never shipped). Both are per-product, non-destructive operations: detach (type → nil) removes nothing — custom-field values survive as unstructured values, option types and categories stay; reassign is detach + attach — the new type's option types/categories seed additively, and its required fields are marked on the form but never enforced. Nothing in the system ever changes a product's type automatically. Deletion still honors the safe path: `has_many :products, dependent: :restrict_with_error` blocks deleting a type that products still use (reassign first). One-time exception: the 6.0 data migrations may assign an initial type to products that have none (see fulfillment-types addendum).
- **ProductType is a back-office concept — no Store API exposure at all** (2026-08-06). Storefront navigation and filtering use categories and collections only. No store endpoint, no `expand=product_type`, no store filter param. The base `V3::ProductTypeSerializer` exists solely as the admin serializer's parent class (house convention).
- **ProductType carries `fulfillment_types`** (addendum 2026-07-27, required by `6.0-fulfillment-and-delivery.md`) — see "Fulfillment types" under Design Details. **This plan's Phase 1 owns the column** (previously orphaned: neither plan's migration created it, which would have silently broken digital checkout eligibility — `attribute` on a missing column is a virtual attribute that persists nothing).
- **`name` is translatable** — `TRANSLATABLE_FIELDS = %i[name]` + Mobility `translates` + a `spree_product_type_translations` table + registration in `Spree.translatable_resources`, so ProductType appears in the `5.5-6.0-resource-translations-api.md` discovery and batch endpoints. (The `include Spree::TranslatableResource` alone is not enough — verified against Product/Taxon.)

### Models

```ruby
# Renamed from Spree::Prototype
class Spree::ProductType < Spree.base_class
  has_prefix_id :pt

  include Spree::Metadata
  include Spree::Metafields            # becomes Spree::HasCustomFields in the rename wave
  include Spree::TranslatableResource
  include Spree::SingleStoreResource

  TRANSLATABLE_FIELDS = %i[name].freeze
  translates(*TRANSLATABLE_FIELDS, column_fallback: Spree.mobility_column_fallback)

  belongs_to :store, class_name: 'Spree::Store'

  # Existing (renamed join tables)
  has_many :option_type_product_types, class_name: 'Spree::OptionTypeProductType', dependent: :destroy
  has_many :option_types, through: :option_type_product_types

  has_many :product_type_categories, class_name: 'Spree::ProductTypeCategory', dependent: :destroy
  has_many :categories, through: :product_type_categories  # class_name flips Taxon→Category in the categories rename wave

  # New
  has_many :product_type_custom_field_definitions, class_name: 'Spree::ProductTypeCustomFieldDefinition',
           dependent: :destroy
  has_many :custom_field_definitions, through: :product_type_custom_field_definitions

  # restrict, not nullify — a type in use cannot be deleted (reassign products first);
  # also keeps products_count honest
  has_many :products, class_name: 'Spree::Product', dependent: :restrict_with_error

  validates :name, presence: true, uniqueness: { scope: spree_base_uniqueness_scope }
  validates :store, presence: true
  validates :fulfillment_types, presence: true

  attribute :fulfillment_types, default: ['shipping']   # model-level default; column has none (CLAUDE.md rule)

  self.whitelisted_ransackable_attributes = %w[name]
  self.whitelisted_ransackable_associations = %w[option_types]

  def digital? = fulfillment_types == ['digital']
  def requires_shipping? = fulfillment_types.include?('shipping')
end
```

### Product changes

```ruby
class Spree::Product < Spree.base_class
  belongs_to :product_type, class_name: 'Spree::ProductType', optional: true,
             counter_cache: :products_count

  # Remove: attr_accessor :prototype_id + add_associations_from_prototype
  # (also remove :prototype_id from Spree::PermittedAttributes.product_attributes)

  # Seeds fire on create AND on any later assignment or reassignment —
  # detach (nil) is a no-op, reassign seeds the new type additively.
  after_create :sync_associations_from_product_type
  after_update :sync_associations_from_product_type, if: :saved_change_to_product_type_id?

  # No required-field validation — `required` is advisory (see Key Decisions).

  private

  # ADDITIVE — deliberately unlike the legacy prototype callback, which REPLACED
  # option_types/taxons by assignment. Never removes anything; a product that
  # already has the option type or category is untouched.
  # Presence guards hit the join tables, not the cached associations — those go
  # stale when pending variants insert option-type joins in the same save.
  def sync_associations_from_product_type
    return unless product_type

    product_type.option_types.each do |ot|
      option_types << ot unless product_option_types.exists?(option_type_id: ot.id)
    end
    product_type.categories.each do |cat|
      categories << cat unless product_categories.exists?(category_id: cat.id)
    end
  end

end
```

There is **no** `type_option_types_present` validation, no `type_option_type?`/`extra_option_types` helpers, and no locked rows — all artifacts of the superseded live-template design. After seeding, a product's option types are its own.

### Apply to existing products

`Spree::ProductTypes::ApplyToProducts` (Tier 1 service per `6.0-service-workflows.md`) is the ONLY path by which a type edit reaches existing products. Additive and idempotent: safe to re-run, never removes anything, never touches variants or option values. It batches with `find_in_batches`, bulk-inserts the missing option-type joins (continuing each product's own `acts_as_list` position sequence), and delegates the category half to `Categories::AddProducts` — that service owns the counter-cache, position and search-index bookkeeping that a raw `insert_all` would silently skip. Returns the count of products changed.

Invoked from the Admin API via a background job (`ProductTypes::ApplyToProductsJob`, `Spree.queues.products`), which includes `ActiveJob::Continuable` and walks products in id order with the last applied id as its cursor — a large catalog survives a deploy mid-run. The dashboard confirms with the type's `products_count` before enqueueing. Adding an option type to a product is safe by construction: existing variants simply have no values for it yet — no validation starts failing.

### Admin API

```
GET    /api/v3/admin/product_types
POST   /api/v3/admin/product_types
GET    /api/v3/admin/product_types/:id
PATCH  /api/v3/admin/product_types/:id
DELETE /api/v3/admin/product_types/:id                    # 422 while products still use the type (restrict_with_error)
POST   /api/v3/admin/product_types/:id/apply_to_products  # 202; additive-only background job
```

Scoped through `current_store.product_types`. Response shape (flat, real prefixed IDs — OptionType is `opt_`, definitions are `cfdef_`):

```json
{
  "id": "pt_k5nR8xLq",
  "name": "T-Shirt",
  "fulfillment_types": ["shipping"],
  "option_type_ids": ["opt_abc", "opt_def"],
  "category_ids": ["ctg_xyz"],
  "custom_field_definitions": [
    { "id": "cfdef_123", "key": "material", "namespace": "product", "required": true, "sort_order": 0 },
    { "id": "cfdef_456", "key": "care_instructions", "namespace": "product", "required": false, "sort_order": 1 }
  ],
  "products_count": 142
}
```

`products_count` is a real counter-cache column (added in Phase 1), not a per-row query. Writes use a nested replace-set payload mirroring the option-values-on-OptionType precedent — read and write field names match, and replace-set semantics are safe here because they edit the template only (no propagation):

```json
PATCH /api/v3/admin/product_types/:id
{ "custom_field_definitions": [ { "id": "cfdef_123", "required": true, "sort_order": 0 } ] }
```

`apply_to_products` responds `202` with `{ "products_count": <n> }` so the client can message the scope of the job it just confirmed.

### Store API

None (2026-08-06). ProductType is a back-office concept; storefront navigation and filtering use categories and collections only. No endpoint, no expand, no filter param. The base `V3::ProductTypeSerializer` exists solely as the parent class of `Admin::ProductTypeSerializer` (house convention: admin extends store-namespace base) and is not wired to any store surface.

### Admin surface (React dashboard — no Rails admin in 6.0)

Admin API + `@spree/admin-sdk` `productTypes` resource + dashboard pages (list under products settings, edit page with option-type picker, category picker, and a sortable custom-field-definitions editor with `required` toggles — dnd-kit reorder per house convention, i18n keys in all locale files, `<Can>` gating).

Product form behavior:
1. Option types and categories seeded by the type render like any others — nothing is locked; the merchant may remove or add freely after seeding.
2. Custom-field form fields render from the type's **current** definition list in `sort_order`, grouped by namespace, with a marker on the ones the type calls required (advisory — no save is blocked).
3. Creating a product: optional ProductType selector; selecting a type seeds its option types and categories additively. Changing or clearing the type later is allowed (explicit, non-destructive; the form re-renders custom fields from the new type).

ProductType editing:
1. The edit page states plainly that changes affect **new products only** (plus the custom-field form/validation, which are live by reference).
2. "Apply to existing products" is a separate explicit action with a confirm dialog showing `products_count` ("This adds this type's missing option types and categories to 1,204 products. Nothing is removed."), then enqueues the job.
3. Deletion is refused while products use the type (reassign first); the UI shows `products_count` on the delete confirm.

### Fulfillment types (addendum 2026-07-27)

`ShippingCategory` is dropped in 6.0 (`6.0-fulfillment-and-delivery.md`); its only real job — "which delivery methods may serve this product?" — moves here:

- `fulfillment_types` JSON column on `spree_product_types` (**created in this plan's Phase 1**, jsonb-guarded, nullable — the `['shipping']` default is model-level), e.g. `["shipping"]`, `["digital"]`, `["shipping", "pickup"]` (6.0 built-in tokens: shipping/pickup/digital — decisions.md 2026-08-06).
- **Products without a ProductType default to `['shipping']`** — the reconciliation between optional ProductType and today's effectively-mandatory ShippingCategory (every product presence-validates one, with auto-assignment).
- The fulfillment plan's data migration creates/assigns types **only where the category carried signal** — products in a digital shipping category get a `Digital` ProductType (`fulfillment_types: ['digital']`). This is the sanctioned one-time initial assignment.
- `Product#digital?` re-implements on top of this (today it's a four-hop chain through ShippingCategory → shipping-method scope → calculator class). `Product#fulfillment_types` is **net-new** surface — no such method exists today.
- Delivery-method eligibility semantics (matching against `DeliveryMethod#fulfillment_type`, per-product exclusions) are owned by `6.0-fulfillment-and-delivery.md`, not this plan.
- **Granularity (clarified 2026-08-06): product-level is not a regression.** Spree never had a variant-level shipping category — `spree_variants` has no `shipping_category_id` (verified back through the consolidated 4.3 schema); `Variant#shipping_category` was a pure delegation to the product. (Solidus is the fork that added a real variant-level column.) Mixed physical/digital within one product (hardcover + ebook) is a **pre-existing gap**, shared with Saleor, that Shopify/BigCommerce close at the variant level. The reserved relief valve, 6.1-if-needed: a nullable per-product (or per-variant) `fulfillment_types` override with the type as default — `Product#fulfillment_types`' reading chain already ends in a fallback, so the override slots in without breaking anything. Do not build it speculatively.

## Migration Path

### Phase 1: Rename + schema

```ruby
class RenamePrototypesToProductTypes < ActiveRecord::Migration[7.2]
  def change
    rename_table :spree_prototypes, :spree_product_types
    rename_table :spree_option_type_prototypes, :spree_option_type_product_types
    rename_table :spree_prototype_taxons, :spree_product_type_categories

    rename_column :spree_option_type_product_types, :prototype_id, :product_type_id
```

## Constraints on Current Work

- **Do not remove Prototype yet.** It will be renamed, not deleted. Don't add features to it either.
- **Do not add `prototype_id` as a persisted column.** The rename adds `product_type_id` instead.
- **All new code around this feature uses custom-field vocabulary** (`custom_field_definition`, `has_custom_field?`, `cfdef_`) — never metafield naming (see `5.4-6.0-custom-fields-rename.md` constraints).
- **New CustomFieldDefinitions should be resource_type-aware** (`resource_type: 'Spree::Product'` for product-intended definitions).
- **Don't create a separate Attribute/Property system.** Everything builds on custom fields. No new EAV tables.
- **Editing a ProductType must never mutate existing products** except through the explicit `ApplyToProducts` action (additive-only, previewed, background job). No propagation callbacks on the join models — ever.
- **Never enforce `required` server-side.** The flag drives a dashboard marker only. Spree writes a product and its custom fields in two steps, so a save-time rule fights the write model — see the Key Decision for the three trigger variants that each failed. A dashboard-side nudge is fine; a model validation is not.
- **No Store API exposure of ProductType** — no endpoint, no expand, no filter. Storefronts see categories and collections only.

## Resolved Questions

1. ~~**Immutability is enforced at the model level, including deletion** (2026-07-27)~~ — **superseded 2026-08-06** (see 5). Deletion handling survives: `dependent: :restrict_with_error` blocks deletion while products use the type; migrations keep the one-time initial-assignment exception.
2. **ProductType is store-owned** (2026-07-27): global types joining store-scoped definitions/categories onto store-owned products would be cross-tenant; same-store validations on both joins; Admin API scoped via `current_store`.
3. **Born-correct custom-field naming** (2026-07-27): the join model/table/FK/API surface use custom-field vocabulary from birth; the 5.5 constant alias makes this implementable before the 6.0 rename wave.
4. **This plan owns the `fulfillment_types` column** (2026-07-27): previously orphaned between this plan and the fulfillment plan; now in Phase 1.
5. **Creation-time template semantics; type changes allowed** (2026-08-06, competitor review vs Saleor/Shopify/Medusa/Vendure): the type seeds option types/categories additively at attach and is live-by-reference for custom fields and fulfillment; editing a type never mutates existing products; the explicit `ApplyToProducts` action (shipping in 6.0 Phase 2) is the sole bulk path; per-product detach and reassign are explicit, non-destructive operations. This dissolves the former open question on option-type removal UX — removing an option type from a type no longer touches any product, so there is nothing to block or report.
6. **Variant-level custom-field definitions deferred to 6.1** (2026-08-06): no `level` column in the 6.0 join — option types own variant identity, and speculative schema is against house rules. Unblocked by: concrete demand for templated variant metadata (revisit with the 6.1 catalog work).
7. **No Store API exposure** (2026-08-06): ProductType is back-office vocabulary; storefront filtering/browse pages use categories and collections. The formerly planned `expand=product_type` on store products was never implemented and is cancelled.
8. **No shared value pools for custom fields** (2026-08-06, closing the last open question): the question conflated two roles that are both already served. Predicate search/sort/filter on custom-field strings shipped in 5.6 (`SearchProvider::MetafieldSchema` + `with_metafield_filters`, storefront included) and stays string-based; faceted navigation over canonical values with counts is the OptionType/OptionValue role (disjunctive faceting shipped 5.4). Custom fields stay unstructured per-resource strings. Product-level descriptive facets (Vendure Facet / Saleor non-variant attributes), if ever demanded, get their own plan.
