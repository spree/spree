# Self-Service Returns Portal

**Status:** In Progress — building every phase for 6.1: order payload, returnable flag, Store API surface, emails, storefront portal and docs
**Target:** Spree 6.1
**Depends on:** `6.0-returns-exchanges-claims.md` (Return, Exchange and Claim models, workflows, Store API returns and claims), `6.0-shipping-labels-and-deliveries.md` (return labels owned by the return, customer label download), `5.4-6.0-eu-legal-compliance.md` (per-market `withdrawal_period_days`, `Order#withdrawal_period_ends_at`), `6.0-store-policies.md` (the return policy page)
**Author:** Damian + Claude
**Last updated:** 2026-11-03
**Tracking:** Linear V-3622 · GitHub spree/spree#14402

## Summary

Let a customer return or exchange what they bought without writing to
support, from the order page in the Next.js storefront, in a way that holds
up under the EU Consumer Rights Directive (2011/83/EU). The 6.0 Store API
already opens and lists returns and claims, tracks the withdrawal deadline
per market and streams a prepaid label to the customer, but a storefront
cannot build the flow on it today: the order payload never names the
fulfillment items the create endpoint requires, nothing tells the customer
what is still returnable or whether the window is open, the reason
vocabulary has no customer-facing endpoint, exchanges have no Store API
route, and the only return email is the refund confirmation, where the
Directive wants an acknowledgement the moment the request lands. This plan
closes those gaps on the API, ships the portal UI in the storefront on top of
the Store SDK, and records the compliance rules the UI leans on.

## Key Decisions (do not deviate without discussion)

- **The portal lives on the existing order page, not a separate app.** A
  "Return or exchange items" action on `/account/orders/:id` (and on the
  guest order page reached from the confirmation email) opens a stepper on
  the same route. Returns are a view of the order, and the order page
  already has the customer's identity, the parcels and the items. No new
  Store API audience, no new auth.
- **Returns are against shipped units.** `POST …/returns` keeps taking
  `fulfillment_item_id` (decision 2026-08-07): a return is of something that
  travelled, and partial fulfillments make the line item the wrong grain. The
  fix is to expose the id, not to change the contract. The fulfillment
  serializer's `items` array keeps one row per line item (the dashboard reads
  that grain) and gains `returnable_quantity`, `non_returnable_reason` and a
  nested `units` array, each unit carrying its `fulfillment_item_id`,
  `quantity`, `returnable_quantity` and `non_returnable_reason`
  (as built, 2026-11-03).
- **Eligibility is previewed through the same hook that enforces it.** The
  storefront must say "window closed on 14 Oct" before the customer picks
  items, and it must say exactly what the create call would say. A
  `Returns::Eligibility` read runs the `returns.create.validate` handlers
  with `created_by: nil` and no writes, and the order payload carries the
  verdict as `returns_eligibility: { eligible, errors: [{ code, message }],
  return_window_ends_at, withdrawal_period_ends_at }`. No
  second rule set, no duplicated window maths in TypeScript. On the order
  payload rather than a separate endpoint (2026-11-03): the order page
  decides whether to show the button on first render, and item-level rules
  still answer on the create call, whose 422 the stepper shows as it is.
- **Non-returnable goods are a flag on the catalogue, frozen onto the
  order; there is no rule model (2026-11-03).** `Spree::Product#returnable`
  (boolean, default true) and `Spree::Variant#returnable` (nullable, nil
  defers to the product, resolved by `Variant#returnable?` the way
  `resolved_delivery_profile` and `tax_category` defer) say whether a unit
  may come back. At completion the cart copier writes `variant.returnable?`
  onto `LineItem#returnable`, and the validator reads the line item, never
  the live catalogue: the terms the customer bought under are the ones that
  apply, so marking a product final sale later cannot strip a right already
  granted, and a legal exemption (sealed hygiene goods, personalised or
  perishable goods, CRD Art. 16) is stated where the merchant already
  describes the product. A market survey (2026-11-03, references below)
  settled the shape: Adobe Commerce's per-product `Enable RMA` with a store
  default, Happy Returns' and Loop's product tags, Salesforce Commerce
  Cloud's and BigCommerce's custom fields all model the exclusion as a
  product attribute; only Shopify has policy objects, and those are
  per-market window rules read-only through its API, which Spree already has
  as `Market#return_window_days` and `withdrawal_period_days`. Shopify's
  final-sale exclusions are product or collection lists set in the admin.
  Medusa derives eligibility from quantities alone; Saleor and Vendure have
  nothing. A `ReturnRule` table would only earn its place for category-level
  exclusions, restocking fees or customer-group windows, which no merchant
  has asked for; the hook carries those until they do.
- **Core still ships no return policy engine.** Reaffirming the 6.0
  constraint with one amendment: `returnable` is the only policy column, and
  there is still no window, restocking fee or rule table on Store, Market,
  Product or the return models beyond the two market preferences that exist.
  Core registers two more handlers on `returns.create.validate` and
  `exchanges.create.validate` beside the window validator:
  `Returns::ReturnableValidator` (the frozen line item flag) and
  `Returns::DigitalContentValidator` (digital fulfillments, Art. 16(m)).
  Both are advisory for staff like the window, and a store unregisters any
  of them or registers its own handler for category exclusions,
  customer-group windows or anything else. The hook contract does not
  change, and the eligibility preview below runs the same chain, so a custom
  handler's verdict reaches the storefront without further work.
- **Reasons become customer-facing, read-only.** `GET /store/return_reasons`
  and `GET /store/claim_reasons` list the store's active reasons. The 6.0
  "back-office vocabulary" reading stopped holding once the create endpoints
  accepted `reason_id` from customers. Same shape as the seller endpoints:
  active rows only, `id` and `name`, no create or update.
- **Exchanges reach the Store API in this release**, as the 6.0 plan
  promised: `GET`/`POST /store/orders/:order_id/exchanges`, items
  `[{ fulfillment_item_id, new_variant_id, quantity }]`, through
  `Spree.exchange_create_workflow` with `created_by: nil`. The replacement
  must be a variant of the same product as the unit coming back
  (2026-11-03). A swap of
  size or colour is what customers mean by an exchange, and it keeps the
  price difference at zero in the common case, since the portal has no way to
  take a payment and core puts a positive difference on the order as a fee
  for the merchant to collect (decision 2026-10-01).
- **A customer can withdraw a request they opened, while it is still
  `requested`.** `PATCH …/returns/:id/cancel` and `…/exchanges/:id/cancel` on
  the Store API call the existing cancel workflows, guarded by status. Once
  the merchant has approved and possibly bought a label, cancelling is theirs.
- **Acknowledge every request by email.** CRD Art. 11(3): a withdrawal
  submitted through the trader's website is acknowledged without delay on a
  durable medium. `spree_emails` gains `ReturnMailer#requested_email` and
  `ExchangeMailer#requested_email`, sent on `return.requested` and
  `exchange.requested`, listing the items, the reason, what happens next and
  the link back to the order page. Editable like the other templates.
- **Refunds go back the way the money came, and the customer does not choose
  otherwise at request time.** CRD Art. 13(1) requires the same means of
  payment unless the consumer expressly agrees to another. `Returns::Refund`
  already defaults to `original_payment`; the portal offers no store-credit
  option. A store that wants to offer credit as an incentive does it in the
  dashboard with the customer's consent recorded in `memo`, or in its own
  handler. Nothing in the API accepts a refund method from a customer.
- **Guest access rides the order token, with an emailed link for customers
  who lost it.** The returns portal is reachable for guests from the
  confirmation email and the order-placed page, both of which carry the order
  token. A "Find my order" form takes an order number and email and always
  answers "if that order exists we have emailed you a link", sending a signed
  link to the order's address. No endpoint ever confirms or denies that a
  number and email match (2026-11-03; a direct lookup answering with the
  token would confirm which email placed an order, and a portal with no
  guest form sends every lost-email customer to support).
- **Auto-approval is a handler, not a preference.** Within the withdrawal
  period the merchant has no legal discretion to refuse, so a store may want
  requests approved on arrival. Core ships no `auto_approve` flag (same
  constraint as policy columns). The plan documents a
  `returns.create.after_create` handler that calls `Returns::Approve` when
  `order.within_withdrawal_period?`, and `spree_enterprise` may ship it as a
  setting.
- **The portal is the model withdrawal form.** Annex I(B) of the Directive
  gives a model form; a trader may offer an online form instead and must then
  acknowledge receipt. The stepper collects the same facts (which goods,
  ordered and received on which dates, the consumer's name and address, the
  date) and the acknowledgement email restates them. The return policy page
  (`policies/return-policy`) stays the place for the merchant's own wording;
  the portal links to it and never paraphrases it.

## Implementation Notes (2026-11-03)

Built as designed, with these differences:

- Per-unit verdicts run the `validate` hook chain once per unit with that
  unit as the only item (`Spree::Workflow.check_hook`), so a store's own
  item-level handler names its own `non_returnable_reason` code.
- `ReturnableValidator` also refuses customer returns of units that have not
  shipped (`not_shipped`); staff are unaffected.
- Exchanges have no label endpoint: `Spree::Exchange` owns no shipping
  labels, so `label_available` and tracking are on returns only.
- Return and exchange events embed the order, reason and lines
  (`event_serializer_params`), so a storefront sending its own emails can
  acknowledge a request from the webhook alone. `order.lookup_requested`
  carries the order token and is credential-gated (`write_orders`).
- The Next.js storefront's acknowledgement email links to the account order
  page and to "Find your order" with the number filled in, because the return
  webhook carries no order token. Its approval email is not built; Spree
  Emails sends one.
- Guest order pages set `referrer: no-referrer` because the address carries
  the order token.
- Returnability is opt-in: `returns_eligibility` and the per-unit fields are
  serialized only with the `returnability` serializer param, which the Store
  order show endpoint sets. Admin, email and webhook payloads never pay for
  the hook runs, and staff never see a customer-only verdict.
- `memo` stays staff-only on the Store API: staff cancellation reasons are
  appended to the same column. The acknowledgement emails render it, since at
  request time it holds only the customer's note.
- "Find my order" matches in a background job (`Spree::Orders::LookupJob`),
  so a match and a miss take the same time to answer.
- Customer withdrawal passes `only_from: %w[requested]` to the cancel
  workflow, which re-checks the status under a row lock, so a merchant
  approving at the same moment wins.
- Exchange replacement units are judged by their own variant
  (`FulfillmentItem#returnable?`), not the original line they ride on.

## Design Details

### Store API

#### Order payload additions

```ruby
# FulfillmentSerializer — items are shipped units, so the unit id travels
attribute :items do |fulfillment|
  fulfillment.fulfillment_items.includes(:line_item, :variant).filter_map do |unit|
    next unless unit.line_item
    {
      fulfillment_item_id: unit.prefixed_id,
      item_id: unit.line_item.prefixed_id,
      variant_id: unit.variant.prefixed_id,
      quantity: unit.quantity,
      returnable_quantity: returnable_quantity_for(unit),  # Returns::ReturnableQuantity
      non_returnable_reason: non_returnable_reason_for(unit) # nil | 'already_returned' | 'not_returnable' | 'digital_content'
    }
  end
end
```

The manifest grouping that merges units of one variant and line item goes
away for this attribute: the customer picks units, so the array lists units.
A parcel with a split unit (one line item shipped as two fulfillment items in
the same box) shows two rows; the UI groups them by variant for display and
sends each id. `non_returnable_reason` names why a unit shows zero, the way
Shopify's `NonReturnableLineItem.quantityDetails` does, so the UI can say
"final sale" rather than only greying the row out; `returnable_quantity` is
zero whenever the line item is not returnable or the fulfillment is digital.

```ruby
# OrderSerializer — the verdict the create call would give, before it is made
typelize returns_eligibility: 'ReturnsEligibility'
attribute :returns_eligibility do |order|
  Spree::Returns::Eligibility.new(order).to_h
end
# => { eligible: true, errors: [], return_window_ends_at: '2026-11-20T…',
#      withdrawal_period_ends_at: '2026-11-14T…' }
```

`Spree::Returns::Eligibility` instantiates `Returns::Create` with the order,
no items and `created_by: nil`, runs only the `validate` hooks, and collects
`workflow.errors`. Nothing is written and no event is published. It is
exposed on the order and used by the digital-content and window validators'
specs as the single place a storefront reads eligibility from. The
`Spree::Workflow` base gains a `dry_run_hooks(:validate)` helper for this;
the exchange flow reuses it.

`return_window_ends_at` is the market window (`return_window_days` from
completion) and `withdrawal_period_ends_at` is the statutory deadline already
on the order. Both reach the UI so it can show the statutory date as the
promise and the merchant window as the goodwill extension.

#### Catalogue flag and its snapshot

```ruby
add_column :spree_products,   :returnable, :boolean, default: true, null: false
add_column :spree_variants,   :returnable, :boolean                    # nil = product
add_column :spree_line_items, :returnable, :boolean, default: true, null: false

# Spree::Variant
def returnable?
  return product.returnable if returnable.nil?
  returnable
end

# Carts::Complete, through Spree.cart_copiers — once per completion
line_item.update_column(:returnable, cart_line_item.variant.returnable?)

# Spree::Returns::ReturnableValidator, registered on returns.create.validate
# and exchanges.create.validate beside EligibilityValidator
def call(workflow)
  return if workflow.created_by.present?
  blocked = workflow.items.reject { |item| item[:fulfillment_item].line_item.returnable? }
  return if blocked.empty?

  workflow.errors.add(:base, :not_returnable,
                      message: I18n.t('spree.return_errors.not_returnable',
                                      items: blocked.map { |i| i[:fulfillment_item].variant.name }.to_sentence))
  workflow.reject!
end
```

Draft orders built in the dashboard copy the flag the same way through the
copier the quoting copy already runs. Orders completed before the column
exists read `true`, which is what they were sold as.

The flag is exposed everywhere the customer meets the product so the
exemption is stated before purchase, as the Directive requires:
`returnable` on the Store `ProductSerializer` (resolved from the product),
`VariantSerializer` (resolved) and `LineItemSerializer` (the frozen value,
on carts from the variant and on orders from the column). The Admin product
and variant forms get a "Returnable" toggle, variants defaulting to
"Same as product". The Admin and Seller line item serializers carry the
frozen value too, so staff see why a customer was refused.

#### New routes

```
GET    /api/v3/store/return_reasons                       # active, read-only
GET    /api/v3/store/claim_reasons

GET    /api/v3/store/orders/:order_id/exchanges
GET    /api/v3/store/orders/:order_id/exchanges/:id
POST   /api/v3/store/orders/:order_id/exchanges
PATCH  /api/v3/store/orders/:order_id/exchanges/:id/cancel   # while requested

PATCH  /api/v3/store/orders/:order_id/returns/:id/cancel     # while requested

POST   /api/v3/store/order_lookups                           # guest "find my order"
```

`Store::ReasonsController` mirrors `Seller::ReasonsController`: store
scope, `.active`, index only, serialized by the existing
`ReturnReasonSerializer` and `ClaimReasonSerializer`. The admin audience is
untouched.

`Store::Orders::ExchangesController` is `ReturnsController` with the
exchange workflow and serializer, plus the same-product check:

```ruby
request_params 'CreateExchangeParams', action: :create do |body|
  body.attribute :items, :array, required: true do |item|
    item.attribute :fulfillment_item_id, :id, required: true
    item.attribute :new_variant_id, :id, required: true,
      description: 'A variant of the same product as the unit coming back.'
    item.attribute :quantity, :integer, required: true
  end
  body.attribute :reason_id, :id
  body.attribute :memo, :string
end
```

The replacement variant is looked up through the store's purchasable
variants of the unit's product, so a variant from another product or a
non-purchasable one answers 422 `invalid_replacement` and nothing else is
disclosed. Stock is checked by the exchange workflow as it is for staff.

Cancel actions call `Spree.return_cancel_workflow` and
`Spree.exchange_cancel_workflow` with no reason and refuse (422
`not_requested`) when the record has left `requested` (as built: 422 with the `not_cancelable` message). The cancel workflow
already refunds a live prepaid label, so a request the merchant approved and
labelled is not cancellable here on purpose.

#### Return and exchange serializers

The customer-facing `ReturnSerializer` and `ExchangeSerializer` gain:

- `label_available: boolean` — whether `active_shipping_label` exists, so
  the UI shows "Download your label" without probing for a 404. The label
  row itself stays unserialized (its cost and provider ids are merchant data).
- `tracking` and `tracking_url` of the inbound delivery, from the return's
  latest `Spree::Delivery`, nullable.
- `cancelable: boolean` — `status == 'requested'`, so the UI never offers a
  cancel the API will refuse.

`created_at` stays off: the serializer rule in `spree/AGENTS.md` holds, and
the status timestamps already tell the story.

#### Guest order lookup

```ruby
# POST /api/v3/store/order_lookups   { number: 'R123456789', email: 'a@b.c' }
# → 202 always, body { "status": "sent" }
```

The server verifies the pair: it looks for a completed order of this store
whose `number` and `email` both match (case-insensitive on the email). On a
match, `OrderMailer#lookup_email` sends a link to the storefront order page
carrying the order token (`store.storefront_url + /orders/:id?token=`), the
same link the confirmation email carries, to the order's own address. The
inbox is the proof of identity: only someone who can read it can open the
order. On no match nothing is sent.

Either way the response is the same 202, and the storefront says "if we
found an order for these details, we have emailed you a link". The check
happens, but its answer travels through the inbox rather than the HTTP
response: order numbers are sequential and printed on parcels, so a 404 on
mismatch would let anyone holding a number try addresses until the server
confirmed which one placed the order. Same reasoning as password reset
forms. Rate limited like registration, so a known address cannot be flooded
with lookup emails. The accepted cost is that a mistyped email gives no
error, only no email; the confirmation copy tells the customer to check
spam and to use the address they ordered with. The storefront's "Find my
order" page is the only caller.

#### Emails

| Template | Event | To | Content |
| --- | --- | --- | --- |
| `return_mailer/requested_email` | `return.requested` | order email | Acknowledgement: items and quantities, reason, order and delivery dates, the customer's name and address, what happens next, link to the order page, link to the return policy |

| `return_mailer/approved_email` | `return.approved` | order email | Where to send the goods (stock location address), label download link when `label_available`, deadline to ship (14 days from the request, CRD Art. 14(1)) |
| `exchange_mailer/approved_email` | `exchange.approved` | order email | Same |

subscribers follow `ReturnEmailSubscriber`: skipped when the store does not

#### Compliance rules core enforces or exposes

| Directive rule | Where it lives | Portal behaviour |
| --- | --- | --- |
| 14-day withdrawal from receipt of the last parcel (Art. 9) | `Order#withdrawal_period_ends_at`, per market | Shown on the order page and in the stepper; eligibility is still the merchant window, which must be at least as long |
| Acknowledge a web withdrawal (Art. 11(3)) | `requested_email` | Sent on every request |
| Refund within 14 days of notice, may wait for goods or proof of sending (Art. 13) | `Returns::Refund`, merchant action | Stepper copy states the deadline; the dashboard's returns list shows days since request (dashboard follow-up, not this plan) |
| Same means of payment (Art. 13(1)) | `refund_method` default | No customer-facing choice |
| Consumer bears direct return cost unless the trader agrees (Art. 14(1)) | Prepaid label is the trader agreeing | Stepper shows "prepaid label" only when the merchant bought one; otherwise names the return address and says shipping is at the customer's cost unless the policy says otherwise |
| Digital content exemption (Art. 16(m)) | `Returns::DigitalContentValidator` | Digital units are listed as not returnable with the reason |
| Sealed, personalised, perishable goods (Art. 16) | `Product#returnable` / `Variant#returnable`, frozen on the line item, `Returns::ReturnableValidator` | Stated on the product page and in the cart before purchase; the unit shows as final sale in the stepper |
| Anything else a store rules on | Store `validate` handler | The UI shows whatever error the hook gives, in the preview and on create |

### Storefront

Routes under `src/app/[country]/[locale]/(storefront)/`:

- `account/(authenticated)/orders/[id]` — the existing page gains a "Return
  or exchange" button when `returns_eligibility.eligible` and any unit has
  `returnable_quantity > 0`, and a "Returns & exchanges" section listing the
  order's returns and exchanges with status, refund total, inbound tracking,
  label download and cancel while `cancelable`.
- `account/(authenticated)/orders/[id]/return` — the stepper, four steps:
  1. **Items**: parcels and their units, each with a quantity picker capped
     at `returnable_quantity`; units with zero are shown disabled with the
     reason (already returned, digital content). Per item: return or exchange.
     An exchange shows the same product's other purchasable variants.
  2. **Reason**: one of the store's return reasons and an optional note.
  3. **Review**: the items, the refund estimate per line (from the order's
     line prices; the server figure comes back on the created record), the
     statutory and merchant deadlines, the return policy link, and a
     consent-free statement of how the refund is made.
  4. **Done**: the return number, "we have emailed you a confirmation", what
     to do next, and a label download when one exists.
  Items picked as exchanges and items picked as returns go out as two
  requests, one exchange and one return, and the done step lists both.
- `orders/[id]` (guest, token in the URL, already used by the confirmation
  email) — same components, no account chrome.
- `orders/find` — the "Find my order" form posting to `order_lookups`.

Data access follows `lib/data/orders.ts`: server actions wrapping the Store
SDK (`orders.returns.create`, `orders.exchanges.create`, `returnReasons.list`,
`orderLookups.create`), `withAuthRefresh` for the account surface and the
cart-token options for guests. All copy goes through `messages/*.json`.

The money shown before the server answers is `display_` strings from the
payload, never arithmetic in the client (`6.0-money-correctness.md`).

### SDK

`@spree/sdk` gains `returnReasons.list`, `claimReasons.list`,
`orders.exchanges.{list,get,create,cancel,labelPath}`,
`orders.returns.cancel`, `orderLookups.create`, and the regenerated types:
`Fulfillment.items[]` with the two new fields, `Order.returns_eligibility`,
`Exchange`, `ExchangeLineItem`, `ReturnsEligibility`.

### Dashboard

No new screens. The returns and exchanges lists already show
customer-opened records (`created_by` nil). One follow-up worth its own
small change: a "requested N days ago" column so the 14-day refund clock is
visible to staff.

### Testing

- Request specs for every new Store endpoint, including: another customer's
  order is 404, a non-`requested` cancel is 422, a replacement from another
  product is 422, lookup answers 202 for a miss and sends nothing, digital
  units are rejected for customers and accepted for staff.
- Serializer specs: `fulfillment_item_id` and `returnable_quantity` on a
  partly returned order, `returns_eligibility` outside the window.
- Email specs for the four new templates and their subscribers.
- Storefront Playwright, in `storefront/e2e`: a signed-in customer returns
  one of two units and sees the request on the order page; an exchange for
  another size; a guest reaches the portal from the order-placed page; the
  window-closed state shows no button. Backed by the e2e seed that creates
  a shipped and delivered order.

## Migration Path

1. **Order payload** — `fulfillment_item_id`, `returnable_quantity` and
   `non_returnable_reason` on fulfillment items, `returns_eligibility` on the
   order, `Spree::Returns::Eligibility` and the workflow dry-run helper.
   Regenerate SDK types. This alone unblocks any storefront and ships first,
   as its own pull request.
2. **Returnable flag** — the three columns, `Variant#returnable?`, the cart
   copier, `ReturnableValidator` and `DigitalContentValidator` registered in
   the engine, serializer fields on Store, Admin and Seller, the dashboard
   toggles, Admin API write support, MCP tool attributes. Its own pull
   request with a schema review.
3. **Store API surface** — reasons endpoints, exchanges controller and
   routes, cancel actions, serializer additions, guest order lookup. SDK
   methods. OpenAPI and Store API docs.
4. **Emails** — the four templates, subscribers, samples and editable
   registry entries. Upgrade guide note that stores with their own return
   emails should check for duplicates.
5. **Storefront** — the stepper, the order page section, guest pages,
   messages, Playwright specs. Lands in `spree/storefront` after the SDK
   release that carries step 3.
6. **Docs** — "Customer self-service" in `returns-exchanges-claims.mdx`
   rewritten around the portal; a new "EU returns compliance" guide listing
   the table above and the handler examples (exemptions, auto-approval).

One migration (step 2), additive with defaults. Every API change is
additive; nothing is deprecated.

## Constraints on Current Work

- **Do not add `fulfillment_item_id` to the line item serializer** or
  anywhere other than the fulfillment's `items` array. A unit belongs to a
  parcel, and listing it elsewhere would give two ids for one thing.
- **No eligibility logic in TypeScript.** The storefront reads
  `returns_eligibility` and `returnable_quantity`; it never computes a window
  or compares dates from `completed_at`. If the UI needs a new verdict, the
  verdict is added to the eligibility read.
- **`returnable` is the only policy column.** Carried over from 6.0 with
  that one amendment: no window, fee, rule table or category flag on Store,
  Market, Product, Category or the return models. A rule that cannot be
  stated as "this product is returnable or not" is a `validate` handler.
- **Read the frozen flag, never the live one, after completion.** Return
  and exchange code reads `line_item.returnable`; the variant's value is for
  carts, product pages and the copier only.
- **Register eligibility rules on the hook, nowhere else.** A new core rule
  is a handler class beside `EligibilityValidator`, so a store can
  unregister it, and so the preview and the create call cannot disagree.
- **Customer-facing serializers stay customer-facing.** `memo` is the
  customer's; `created_by`, label cost, provider ids, `received_quantity`
  before the count, and staff notes stay out. Check `spree/AGENTS.md`
  serializer rules before adding a field.
- **Nothing on the Store API accepts a refund method.** Art. 13(1) is the
  reason; a store wanting store-credit incentives records consent itself.
- **The lookup endpoint never discloses a match.** Any change to it keeps
  the single 202 response.

## Open Questions

None. The four questions the draft raised (guest entry point, exemptions
beyond digital content, eligibility preview shape, exchange replacement
scope) and the two the exemption answer opened (rule model or flag, live or
frozen flag) were settled on 2026-11-03 and are recorded under Key
Decisions.

Deferred, with what would reopen it: a `ReturnRule` table for category-level
exclusions, restocking fees or customer-group windows, if merchants ask for
one; until then those are `validate` handlers. Customer self-cancellation of
an unshipped order, which is withdrawal before delivery, belongs to
`5.5-6.0-order-cancellation-and-approval.md`.
