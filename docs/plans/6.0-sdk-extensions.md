# SDK Extensions

**Status:** In Progress — building all three phases for the next 6.0 patch release: `client.extend` on the Store, Admin and Seller clients; extensions' OpenAPI documents and response types; and `spree sdk generate`, which writes an extension's whole client from them
**Target:** Spree 6.0.x (the SDK packages' next patch release)
**Depends on:** `6.0-agent-tools-from-openapi.md` (extensions ship an `openapi/*.yaml` of their own endpoints, which Phase 2 reads)
**Author:** Damian Legawiec (design driven with Claude)
**Last updated:** 2026-11-04
**Tracking:** Linear V-3780 · GitHub —

## Summary

A Spree extension that adds API endpoints can ship a typed client for them that
plugs into the SDKs developers already use. Today the only way to call an
extension's endpoint is `client.request<T>(method, path)`, with types the
developer writes by hand. With this plan the extension publishes an npm package
of SDK extensions, generated from the extension with `spree sdk generate`, and
an app adds it to its client:

```ts
import { createClient } from '@spree/sdk'
import { extendStoreClient } from 'my-quotes-extension'

const client = extendStoreClient(createClient({ baseUrl, publishableKey }))

await client.quotes.create({ note: 'Bulk pricing?' }) // typed
client.products.list()                                // unchanged
```

The extension calls its endpoints through the client's own request function, so
it uses the same sign-in, store, locale, currency and retries as the built-in
resources. Its types come from the extension's own OpenAPI document, generated
the same way the SDKs generate theirs.

## Key Decisions (do not deviate without discussion)

- **`extend` returns a new client (2026-11-04).** `client.extend(ext)` returns
  an object built on the client (as `createClient` already builds the client on
  `StoreClient`), with the extension's namespace added. The original is
  unchanged. There is no global registry and no TypeScript module augmentation:
  each client's type says which extensions it has, and an app that installs
  nothing sees exactly today's types.
- **An extension adds namespaces, never changes built-ins (2026-11-04).**
  `extend` refuses a name the client already answers (`orders`, `request`, an
  extension added twice). Wrapping or replacing `client.orders` is out of scope.
- **Extensions are per API (2026-11-04).** `defineStoreExtension`,
  `defineAdminExtension` and `defineSellerExtension` mark which API an extension
  calls, and each client accepts only its own, in its type and at runtime. A
  store extension on an admin client would send its paths to `/api/v3/admin`.
- **Extensions are plain objects (2026-11-04).** `{ api, name, build }`, checked
  by shape, not `instanceof`. `@spree/sdk-core` is inlined into each SDK's
  bundle, so an extension package and the app can hold separate copies of it.
- **`build` receives a context object, not a bare function (2026-11-04).**
  `build({ request })` lets the context grow (uploads, list param helpers)
  without breaking existing extensions.
- **The helpers live in `@spree/sdk-core` and are re-exported by each SDK
  (2026-11-04).** `sdk-core` stays private. An extension package imports
  `defineStoreExtension` from `@spree/sdk` (and so on) and lists the SDKs it
  extends as peer dependencies.
- **Types are generated, not hand-written (2026-11-04).** An extension already
  generates `openapi/admin.yaml` from its rswag specs (`6.0-agent-tools-from-openapi.md`).
  Phase 2 makes the generators the SDKs use for request bodies and list filters
  read that document.
- **The client is generated too (2026-11-04).** Every method a package would
  write by hand repeats an operation in the document: its path, verb, body
  and response. Phase 3 writes one extension per resource from the document,
  so a package has no hand-written client to drift from its API. Defining an
  extension by hand stays for an endpoint the document does not describe.
- **One command, no settings (2026-11-04).** `spree sdk generate` runs the
  extension's rake tasks and writes everything, reading the extension's
  location from the package's `package.json`. The rake task finds the engine
  (or app) whose root is the current folder, so nothing is configured twice.
- **Core's Typelizer setup stays as it is (2026-11-04).** Moving core's writers
  out of its always-on initializer would spare `SdkTypes` two lines (clearing
  those writers, switching the enum source for its run), at the cost of
  changing how every Spree SDK type is generated. Not worth it.

## Design Details

### Defining an extension

```ts
import { defineAdminExtension, type PaginatedResponse } from '@spree/admin-sdk'
import type { Quote, QuoteSendParams } from './types'

export const adminQuotes = defineAdminExtension('quotes', ({ request }) => ({
  list: (params?: Record<string, unknown>) =>
    request<PaginatedResponse<Quote>>('GET', '/quotes', { params }),
  get: (id: string) => request<Quote>('GET', `/quotes/${id}`),
  send: (id: string, body: QuoteSendParams) =>
    request<Quote>('PATCH', `/quotes/${id}/send`, { body }),
}))
```

`request` is the client's own (`client.request`): paths are relative to the
client's API base (`/api/v3/store`, `/api/v3/admin`, `/api/v3/seller`).
`build` runs once, when the extension is added.

### Adding one

```ts
interface Extension<Api extends 'store' | 'admin' | 'seller', Name extends string, Namespace> {
  readonly api: Api
  readonly name: Name
  readonly build: (context: ExtensionContext) => Namespace
}

// on each client
extend<Name extends string, Namespace>(
  extension: Extension<'admin', Name, Namespace>,
): this & { readonly [K in Name]: Namespace }
```

- Chains: `createClient(...).extend(quotes).extend(loyalty)`.
- The extended client delegates to the original, so `setToken`, `setStore`,
  `setLocale` and `onUnauthorized` on either one affect both, and an
  extension's calls follow later sign-ins.
- Errors: an extension for another API, a name the client already has, or an
  object that is not an extension throw a `TypeError` naming the extension.

### Phase 2: types from an extension's documents

**Documents.** `Spree::Api::TestingSupport::Openapi.configure` writes the
extension's `openapi/admin.yaml` and, with `store_title:`, an
`openapi/store.yaml` with the Store API's security schemes; a Store API spec
names it with `openapi_spec: 'openapi/store.yaml'`. `filter_parameters_for`
moves from core's spec support into the testing support
(`Spree::Api::TestingSupport::FilterParameters`) and is extended into an
extension's request specs, so its list endpoints publish the same filter
tables core's do.

**Types.** `spree sdk types` in `@spree/cli` (which already bundles `sdk-core`,
as `spree filters types` does) writes, per document:

```bash
spree sdk types   # openapi/{store,admin,seller}.yaml → src/types/<api>/
```

- `src/types/<api>/params/`: one file per request body type and an index,
  from the same renderer as the SDKs' `generate:params`.
- `src/types/<api>/filters.ts`, when the document lists filters, from the same
  renderer as `generate:filters`.

Both import their building blocks (code lists such as `CurrencyCode`, the
filter types) from the SDK the document's API belongs to, since `sdk-core` is
private. The API is read from the document's file name. Both are rewritten
from scratch on each run, so an endpoint that went away takes its types with
it.

**Response types.** `Spree::Api::SdkTypes` runs Typelizer in the extension's
test app (`rake spree:sdk:serializer_types`, defined for every extension by
`extension_rake` and for apps by spree_api; it finds the engine, or the app,
whose root is the current folder, and writes to `OUT`):

- It replaces the writers `spree_api` configures for Spree's own SDKs, which
  would write core's types into the installed gem, with one writer per API
  for the serializers defined under the engine's `app/serializers`, sorted by
  namespace as core's are.
- Every generated file imports what it references from `<api>/spree.ts`,
  which re-exports the SDK's types and the package's own, so a nested core
  record (`Order`) is the SDK's type, not a copy. A name the package shares
  with the SDK is a type error there, not a silent override.
- Named value lists are defined in the package, open unless closed, instead
  of being re-exported from the private `@spree/sdk-core`.
- It uses core's Alba type mapping and `interface` output, shared with
  `Spree::Api::TypelizerGeneration`, and named type exports, so the files
  compile with or without `verbatimModuleSyntax`.

### Phase 3: generated clients

`spree sdk generate`, run in the package:

```json
{ "name": "my-quotes-extension", "spree": { "extension": "../my_extension" } }
```

1. Runs `bundle exec rake spree:openapi:generate spree:sdk:serializer_types
   OUT=…` in the extension, outside the CLI's own bundle (`--no-backend` skips
   it and uses the committed files).
2. Writes, per API the extension documents, `src/generated/<api>/`:
   `client.ts`, `params/` and `filters.ts`, beside the `types/` and `spree.ts`
   the rake task wrote. An API no longer documented loses its files.
3. `--check` writes into a temporary folder and fails when it differs from
   the committed one, for CI.

`client.ts` (`renderExtensionSource` in `sdk-core`) has one
`define<Api>Extension` per resource (the path's first segment), and an
`extend<Api>Client` that adds them all:

- Method names follow the SDKs': `list` (a `GET` on the collection with
  filters or `page`), `get`, `create`, `update`, `delete`; an action is its
  segment camel-cased (`PATCH /quotes/{id}/send` → `quotes.send`); deeper
  paths are the verb and the nested resource (`listItems`). An `operationId`
  names a method instead, and two operations that would make one method are
  refused.
- Arguments: path parameters in order, then the body (`params`, required when
  the document says so), list params typed by the operation's filters, or
  `{ expand }` for a read; then `options`.
- The response is the `200`/`201` schema the document declares, or else the
  package's type named after the resource (`quotes` → `Quote`), or `unknown`.
- Each method's doc comment is the operation's summary and description.
- An extension's `build` gets `listParams` and `readParams` beside `request`,
  so generated and hand-written lists build their query as the SDKs' do.

`spree generate api_resource` declares `request_params` on the controllers it
writes and adds an Admin integration spec, so a new resource is documented,
and has request types and a generated client, from its first commit.

## Migration Path

1. **Phase 1:** the extension helpers in `sdk-core`, re-exported by `@spree/sdk`,
   `@spree/admin-sdk` and `@spree/seller-sdk`; `extend` on the three clients;
   tests, and a "Shipping a client for an extension" section on the Store and Admin SDK Custom Endpoints pages.
2. **Phase 2:** the store document and filter documentation for extensions,
   `spree sdk types`, `rake spree:sdk:serializer_types`, and the docs: the CLI
   reference, "Generating the extension's types" on the SDK pages, and the
   store document on the custom tools page.
3. **Phase 3:** `renderExtensionSource`, `spree sdk generate` (replacing
   `spree sdk types`, never released), the zero-config task, `api_resource`
   documenting what it scaffolds, and one end-to-end section, "From an
   endpoint to agent tools and an SDK client", on the API customization page.
4. Built-in resources are unaffected. `client.request` stays the way to call a
   single endpoint without a package.

## Constraints on Current Work

- `client.request` stays public on every client; extensions build on it.
- New SDK resources are built into the SDKs as today. `extend` is for packages
  outside this repository, not a way to split the SDKs.
- An extension package lists the SDKs it extends as peer dependencies, never as
  dependencies, so the app's single client is the one extended.
