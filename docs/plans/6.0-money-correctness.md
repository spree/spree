# Money Correctness

**Status:** In Progress — building PR A (floats out); A2 (gateway amounts), B (wire contract) and C (precision) follow
**Target:** Spree 6.0
**Depends on:** `5.5-client-side-money-normalization.md` (canonical decimal-string contract), `6.0-6.1-split-adjustments.md` (typed `spree_tax_lines` / `spree_discounts` / `spree_fees` — landed, so they are in scope), `6.0-json-preferences.md` (decimal preferences are exact strings), `6.0-payment-gateways-monorepo.md` (Stripe lives in the monorepo; Adyen and PayPal Checkout are separate gems patched in the same release)
**Author:** Damian + Claude
**Last updated:** 2026-10-09
**Tracking:** Linear V-3738 · GitHub spree/spree#14848

## Summary

Spree stores money in decimal columns, but four things still make amounts wrong or ambiguous before 6.0. Some money paths pass through floats (`.to_f` in Ruby, `parseFloat` in the dashboard), which cannot hold most decimal amounts exactly and are only rescued by a rounding step that happens to follow. The API does not agree with itself on what a money field looks like: most fields are strings, a few are JSON numbers, and the strings are not normalized (`"10.0"`, never `"10.00"`). Payment gateways receive a bare integer in hundredths of the currency, which is the right unit only for two-decimal currencies, while Stripe sessions use ISO minor units — and Stripe's own units are neither (ISK, HUF, TWD carry special rules). And the columns are `decimal(10, 2)`, which cannot hold a Kuwaiti dinar's third decimal, a sub-cent B2B unit price, or a large Vietnamese dong order. This plan removes floats from money paths in Ruby and TypeScript and writes the rule into `CLAUDE.md`, hands gateways an amount with its currency and lets each adapter convert to its provider's unit, makes every money field on the wire a decimal string written to a published per-currency exponent, and widens the money columns to `decimal(19, 4)`. It ships as four pull requests: A (floats out), A2 (gateway amounts), B (wire contract), C (precision).

## Key Decisions (do not deviate without discussion)

All decided 2026-10-08; the ones marked *review* were changed or added after the design review that day.

- **Decimal strings, not integer minor units.** Money stays a canonical decimal string on the wire (`5.5-client-side-money-normalization.md`). No integer minor-unit field appears in the API; the integer `amount_in_cents` / `compare_at_amount_in_cents` fields leave the Price and PriceHistory serializers.
- **BigDecimal end to end, Ruby and TypeScript.** Money is never a `Float` / JS `number` between parsing and persisting or between reading and comparing. Stated as a rule in `CLAUDE.md` ("Money").
- **The currency exponent is ISO 4217, from one Spree-owned file** (*review*). `spree/core/config/currency_exponents.json` holds the ISO 4217 minor-unit table, pinned to a dated list. Ruby registers it over the Money gem at boot, so `Spree::Money::Rounding.precision`, `Money#cents` and `Money#format` agree; `@spree/sdk-core` imports the same file; `CurrencySerializer` exposes it as `decimal_places`. Where the Money gem differs today (HUF 0 → 2, MGA and MRU 1 → 2) Spree follows ISO. Why: the exponent is now part of the contract (`"100.5"` JPY is a 422), so a client must be able to read it, and the TypeScript side must use exactly the same table. Accepted trade-off: Spree stops rounding HUF to whole forints; stored HUF values are already at two decimals and do not change. Upgrade-guide entry.
- **Gateways receive a `Spree::Money`, not an integer** (*review*; supersedes "gateways receive true minor units" from the first pass). Core passes amount and currency; each adapter converts to its provider's unit. Stripe's adapter owns Stripe's rules (zero-decimal list, ISK sent in a two-decimal representation divisible by 100, HUF and TWD whole-amount rules). Why: no single integer unit is right for every provider, and this gives the TypeScript rewrite a gateway interface whose unit does not depend on the currency.
- **Old gateways keep today's behaviour for one release** (*review*). A gateway opts in with `self.accepts_money_amounts = true`. Core keeps passing the integer in hundredths, exactly as today, to any gateway that has not opted in, with a deprecation warning; the bridge is removed in 6.1. Stripe (monorepo), `spree_adyen` and `spree_paypal_checkout` opt in in the same release. Shipped alone as PR A2, so reverting it restores today's behaviour.
- **Two precisions on write** (*review*). Unit-price fields — `price` and `compare_at_amount` on prices (base and price-list prices, which carry price breaks), `price` on line items, `cost_price`, `unit_cost` — accept up to 4 decimals (`"0.0125"` USD). Every other money field — totals, payments, refunds, captures, adjustments, discounts, fees, tax lines, gift cards, store credit, payouts — accepts at most the currency's exponent. Line amounts are `price × quantity` rounded to the exponent when persisted. Why: B2B unit pricing and price breaks ship in 6.0 and need sub-cent unit prices; money that changes hands never has sub-minor-unit amounts.
- **Writes are strict strings.** The Admin and Seller APIs parse money with `BigDecimal(str)` and reject a JSON number, a non-canonical string (`"1,99"`, `"1e3"`, `" 5"`, `"+5"`), or an over-precise string (by the rule above) with 422 `invalid_money_format`, naming the field. Top-level fields and the money keys inside `preferences`. Supersedes "JSON numbers are also accepted" in `monetary-amounts.mdx` and the 5.5 plan's "lenient now" leaning. Accepted trade-off: breaking for integrators sending numbers.
- **Canonical read format.** A money field is a string matching `^-?\d+(\.\d+)?$`. Exponent fields carry exactly the currency's decimal places (`"10.00"`, `"1.500"`, `"100"`). Unit-price fields carry at least the exponent and at most 4, with zeros beyond the exponent stripped (`"19.99"`, `"0.0125"`, `"19.9950"` → `"19.995"`). `display_*` companions are unchanged.
- **Rates and percentages are canonical decimal strings** (*review*: canonical form and naming rule added). No fixed exponent, trailing zeros and a trailing `.` stripped (`decimal(8,5)` `0.23000` → `"0.23"`, `23.00` → `"23"`), top-level and inside `preferences`. Naming rule, enforced by the contract spec: a name ending `_percent` or `_percentage` is 0–100; a name that is `rate` or ends `_rate` is a fraction (0.23). A field may not be named like money (`amount`, `value`) when it holds a rate. So the Admin tax rate's `amount` (fraction) becomes `rate` and `amount_percentage` becomes `rate_percent`, with model aliases per the read/write-symmetry rule. Discount `value` is the one documented exception: money or percent by its `value_type`.
- **Round only at boundaries; the rounding mode is a parameter** (*review*). Intermediate math keeps full precision. `Spree::Money::Rounding.to_currency(amount, currency, mode: :half_up)` is called when a total or line amount is persisted, when a gateway adapter converts, and when an amount is serialized. Tax providers own their rounding (per line or per invoice, and the mode); the internal provider keeps per-line half-up.
- **Columns become `decimal(19, 4)`.** Every money column, including the typed adjustment tables. Rate and percentage columns keep their current scale. Widening changes no stored value.
- **The column migration is idempotent and has a documented online path** (*review*). It skips a column already at `(19, 4)`, so an install that widened large tables ahead of the upgrade (shadow column plus backfill) runs it as a no-op for those. Default path: one migration in the 6.0 upgrade window, accepting the table rewrite under lock.
- **Wrong capture events are reported, not repaired.** `spree:money:audit_capture_events` lists payments in non-two-decimal currencies whose capture events disagree with the corrected value, and writes nothing. Spree never rewrites money on completed orders.
- **The rule lives in `CLAUDE.md`, not in a lint tool** (decided 2026-10-09; supersedes the first pass's RuboCop cop and Biome twin). A cop was built and then dropped: the repository runs no RuboCop, and a name-matching rule needs an allowlist that is mostly noise. `CLAUDE.md` "Money" states it for people and agents alike.
- **Open carts in zero- and three-decimal currencies change on their next recalculation.** Accepted trade-off: a yen total can move by under one yen mid-checkout. Completed orders are frozen and do not change.
- **Spree stops parsing numbers by locale** (decided 2026-10-09; supersedes the 5.5 plan's "`LocalizedNumber` is not removed" and this plan's first-pass "out of scope"). The model setters that re-parsed strings with `Spree::LocalizedNumber` under the request locale are removed, and Rails' decimal type reads the value as sent. Why: the legacy admin they served is gone, and under a store whose language writes a comma decimal they misread the dashboard's canonical `"49.50"` as 4950 and grew an untouched `"99.0"` tenfold on every save (a reported bug). `Spree::LocalizedNumber.parse` stays one release as a deprecated method nothing in Spree calls, and is removed in 6.1. The variant's `cost_price`/`weight`/`width`/`height`/`depth` writers keep ignoring a blank value. Ships in PR A.
- **The dashboard shows and reads money in the admin's own number format** (decided 2026-10-09, following Shopify; supersedes the 5.5 plan's "currency's market locale"). `useMoneyLocale()` returns the dashboard language; every money field formats and normalizes through it, whatever the currency or market. Why: a store can have several markets with one currency and different conventions (EUR in Germany and Ireland), so the market-based format depended on which market loaded first; the person typing knows their own convention, and the old reason against it, server re-parsing, is gone. Accepted trade-off: a German-speaking admin of a US store sees `1234,56` for dollars. Ships in PR A.
- **PR A applies the ISO table to Spree's own rounding only; registering it over the Money gem moves to A2** (decided 2026-10-09). Registering changes `Money#cents` for HUF, which Stripe payment sessions read, and A2 is the only PR that may change what a gateway receives.

### Gateway amounts

Today `payment_method.authorize/purchase/capture/credit` receive `Spree::Money#amount_in_cents`, the amount in hundredths for every currency (1000 JPY → `100000`; 1.505 KWD → `151`), while Stripe sessions use `Money#cents`, the ISO minor unit (1000 JPY → `1000`). The capture event then reads the hundredths value back as minor units: a 1000 JPY capture records 100,000 JPY, a 1.500 KWD capture records 0.150 KWD. `Payment#captured_amount` sums those events and the capture flow resizes the payment from that sum, so the error can reach the payment's own amount.

The two capture callers do not even agree with each other: an admin capture passes hundredths, a capture on dispatch passes the currency's minor unit, and the workflow records both the same way. No fix to the recording alone is right for both, so PR A only removes the float and keeps every unit as it was; PR A2 fixes the recording with the interface, when the workflow receives a `Spree::Money`:

```ruby
class Spree::Gateway
  class_attribute :accepts_money_amounts, default: false
end

# core, one place (Spree::Payment#gateway_amount):
amount = payment_method.accepts_money_amounts ? money : legacy_hundredths(money)

class SpreeStripe::Gateway < Spree::Gateway
  self.accepts_money_amounts = true

  def capture(money, payment_intent_id, options = {})
    Stripe::PaymentIntent.capture(payment_intent_id, { amount_to_capture: stripe_units(money) }, opts)
  end
end
```

`stripe_units` lives in the Stripe gem and is also what payment sessions use, so a session and its capture always agree. `spree_adyen` (Adyen minor units, its own currency table) and `spree_paypal_checkout` (PayPal decimal strings) opt in in releases cut alongside 6.0. The store credit gateway opts in and reads `money.amount` directly.

### Strict parsing at the API boundary

`Spree::Money::Rounding.parse_canonical(value, currency, unit_price: false)` returns a `BigDecimal` for a `String` matching `^-?\d+(\.\d+)?$` with at most the currency's decimal places (4 with `unit_price: true`), and `nil` for `nil`. Anything else raises `Spree::Money::InvalidFormat`, which the v3 base controller renders as 422 with code `invalid_money_format` and the field in `details`. Rates use `parse_canonical_decimal(value)`: same shape, no decimal limit beyond the column's. Admin and Seller controllers validate every declared money and rate field, including the money and percentage keys of `preferences`, before assignment, so a model setter only ever sees a canonical string. The Store API takes no client amounts (5.5 audit) and is unchanged.

### Wire contract

`BaseSerializer.money_attributes` is the only way to declare a money field, with the currency read from the record:

```ruby
money_attributes :total, :item_total                          # currency from object.currency
money_attributes :amount, :compare_at_amount, unit_price: true
money_attributes :cost_price, currency: :cost_currency, unit_price: true
money_attributes :minimum_payout_amount, currency: ->(store) { store.default_currency }
rate_attributes  :rate, :rate_percent                         # canonical decimal, zeros stripped
```

Both format through `Spree::Money::Rounding.format(amount, currency, unit_price:)` / `format_decimal`, keep `hide_prices`, and type the field `string | null`. `CurrencySerializer` gains `decimal_places`.

The contract spec loads every v3 serializer (Store, Admin, Seller), builds each resource from its factory in USD, KWD and JPY, and asserts: every `money_attributes` field matches `^-?\d+(\.\d+)?$` with exactly the currency's decimal places (or within exponent..4 for unit prices); every `rate_attributes` field has no trailing zeros; no attribute whose name matches the money pattern is declared any other way; no rate is named like money; `_percent`/`_percentage` fields fall in 0–100 and `rate`/`_rate` fields in 0–1 on the factory data.

Known non-conforming fields today: `cart.order_minimum_amount` / `order_minimum_shortfall` (numbers), admin store `preferred_default_minimum_payout_amount` / `preferred_default_commission_tax_rate` (numbers), admin tax rate `amount` (fraction named like money) and `amount_percentage` (number), product filter price range `min`/`max` (numbers), report money metrics (numbers), `price.amount_in_cents` / `compare_at_amount_in_cents` / `price_history.amount_in_cents` (removed). Every other money field is already a string, but unnormalized.

### TypeScript money

`@spree/sdk-core` gains a small decimal helper over strings, built on the same `currency_exponents.json`: `compareMoney(a, b)`, `sumMoney(values, currency)`, `isZeroMoney(value)`, `decimalPlaces(currency)`. It works on scaled `bigint`s internally and returns canonical strings, so no money value passes through a JS `number`. The dashboard's money sites move onto it; display keeps `Intl.NumberFormat` on the `display_*` fields or on the string. Both `monetary-amounts.mdx` pages replace `parseFloat` with the helper.

### Precision migration

One migration, `ChangeMoneyColumnsToDecimal194`, changes every money column below to `decimal(19, 4)`, keeping each column's `null` and `default`, and **skips any column already at `(19, 4)`**. Its `down` restores each original type. Values do not change: every stored `decimal(10,2)` / `(8,2)` / `(12,4)` value is exactly representable.

Columns (from `server/db/schema.rb` at `4ca24b8`): `spree_adjustments.amount`; all `*_total`, `cost`, `price`, `cost_price`, `pre_tax_amount`, `amount*`, `refund_amount`, `tax_amount`, `unit_cost`, `revenue`, `settled_amount`, `minimum_payout_amount`, `min_amount`/`max_amount`, `markup_flat` columns on carts, orders, line items, fulfillments, payments, payment splits, payment sessions, payment capture events, refunds, reimbursements and reimbursement credits, return / claim / exchange line items, return items, prices and price histories, gift cards and batches, store credits and events (today `8,2`), tax lines, discounts (`amount`; `value` is percent-or-amount and widens with it), fees, commission lines and rate values, seller payouts and transfers, sellers, catalog order minimums, delivery methods and their services, delivery rates (today `8,2`), shipping labels, purchase order items, stock movements, variants (`cost_price`), products and products-stores (`revenue`), Stripe payment intents. Extension tables (`spree_paypal_checkout_orders`) are listed in the upgrade guide for their gem to follow. Not changed: `tax_rates.amount`, `tax_lines.rate`, `commission_*.rate`/`tax_rate`/`commission_tax_rate`/`value`, `price_adjustment_*percentage`, `markup_percent`, dimensions, weights, coordinates, focal points.

Cost: a scale change rewrites the table under an exclusive lock on PostgreSQL, and every `ALTER` rewrites on MySQL. The upgrade guide documents the default (run it in the upgrade window) and an online path for large installs: add a `(19,4)` shadow column, backfill in batches, swap names in one short transaction for `spree_orders`, `spree_line_items` and `spree_adjustments`; the migration then finds those columns already widened and skips them.

### Value-changing cases

None changes a stored value of an existing two-decimal order.

1. **Capture events in zero- and three-decimal currencies** are recorded correctly from PR A2. Old rows are reported by `spree:money:audit_capture_events`, never rewritten.
2. **What opted-in gateways receive** changes for every currency's representation (a `Spree::Money` instead of an integer); the amount charged changes only where it was wrong (JPY captures at Stripe). Un-opted gateways see no change until 6.1.
3. **Open carts in zero- and three-decimal currencies** recalculate with exponent rounding (`123.40` JPY → `123`). Accepted.
4. **Promotion and manual discount distribution in JPY/KWD** splits in whole yen / thousandths of a dinar on new orders.
5. **HUF** stops rounding to whole forints (ISO 4217 says two decimals).
6. **CSV exports and reports** print canonical strings instead of floats.
7. **Every money string on the wire** is written to its exponent (`"10.0"` → `"10.00"`, JPY `"1000.0"` → `"1000"`); rates lose trailing zeros; the tax rate fields are renamed.

## Migration Path

**PR A — floats out.** No wire, schema or gateway-interface change.
1. Add `currency_exponents.json` and read it in `Spree::Money::Rounding`; add `parse_canonical`, `parse_canonical_decimal`, `format`, `format_decimal`, and a `mode:` parameter on `to_currency`.
2. Fix every **money** row of the Ruby inventory and the hard-coded hundredths. Capture events and dispatch captures keep their units (fixed in A2), without the float.
3. Remove the locale-parsing model setters and deprecate `Spree::LocalizedNumber`; the dashboard formats money in the admin's own language (`useMoneyLocale`), with end-to-end tests for English and German admins and for a store whose market writes a comma decimal.
4. Add `spree:money:audit_capture_events` (report only).
5. Add the "Money" rule to `CLAUDE.md`.
6. Rounding conformance specs that do not depend on column width.
7. Upgrade guide: HUF exponent, open-cart rounding, the audit task, `LocalizedNumber` deprecation.

**PR A2 — gateway amounts.** Revertible on its own.
1. Register `currency_exponents.json` over the Money gem; `Spree::Gateway.accepts_money_amounts`, the hundredths bridge with its deprecation warning, `Spree::Payment#gateway_amount`.
2. The capture workflow takes a `Spree::Money` from every caller and records it as is, which fixes yen and dinar capture records.
3. Stripe adapter opts in with `stripe_units` (zero-decimal list, ISK, HUF, TWD rules), used by sessions and by capture/refund; store credit gateway opts in.
4. Patch and release `spree_adyen` and `spree_paypal_checkout` alongside 6.0.
5. Upgrade guide and changelog: the extension API change and the 6.1 removal of the bridge.

**PR B — wire contract (breaking).**
1. `money_attributes` (exponent and unit-price formats) and `rate_attributes`; convert the non-conforming fields; rename the tax rate fields with model aliases; remove the `*_in_cents` fields; `decimal_places` on currencies.
2. Strict `invalid_money_format` parsing on Admin and Seller writes, including `preferences`.
3. Contract spec over every v3 serializer.
4. Regenerate Typelizer types and Zod schemas for `sdk`, `admin-sdk`, `seller-sdk`; regenerate `docs/api-reference/*.yaml` through rswag.
5. `@spree/sdk-core` decimal helper; move the dashboard and seller panel money sites onto it.
6. Both `monetary-amounts.mdx` pages (remove "JSON numbers are also accepted", "percentage keys stay numbers" and `parseFloat`; document `invalid_money_format`, `decimal_places`, unit-price precision and the rate naming rule), `docs/developer/upgrades/5.6-to-6.0.mdx`, `docs/changelog.mdx`, a changeset for the SDKs.

**PR C — precision.**

## Constraints on Current Work

- **No float on a money path, in Ruby or TypeScript.** Parse with `parse_canonical`, compute in `BigDecimal` (or the sdk-core helper), never `* 100`, never `.round(2)` — round with `to_currency(amount, currency)`.
- **Exponents come from `currency_exponents.json`**, never from a hard-coded 2 or straight from the Money gem's defaults.
- **Declare money fields with `money_attributes`** (with `unit_price: true` for unit prices) **and rates with `rate_attributes`.** Never a plain `attribute`, never `.to_f`, never typed `:number`.
- **Name rates by the rule**: `_percent`/`_percentage` is 0–100, `rate`/`_rate` is a fraction, and a rate is never named like money.
- **New gateways set `accepts_money_amounts = true`** and convert `Spree::Money` to their provider's unit in the adapter.
- **New money columns are `decimal(19, 4)`**, `null: false, default: 0` where required. Rates are `decimal(8, 5)`.
- **Do not round in intermediate math** — only when persisting, in a gateway adapter, or when serializing. Tax providers choose their own rounding.
- **Money writes are strict.** A new Admin or Seller endpoint taking an amount parses it with `parse_canonical(value, currency)`; never `.to_d`, `BigDecimal(x.to_s)` on a raw param, or `LocalizedNumber`.
- **No locale parsing on the server.** A model setter never re-parses a number by locale; localized input is normalized by the client.
