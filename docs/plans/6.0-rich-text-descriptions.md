# Rich Text Descriptions

**Status:** Phases 1–2 partially shipped in 5.4 (`RichTextHelper` + Product serializer split ✓ — PR #13811); **sanitizer retargeted to 5.6** (never shipped, live XSS surface — decisions.md 2026-07-27); ActionText removal pending in 6.0
**Target:** Spree 5.4 (serializer split ✓) + **5.6 (sanitization — permissive allowlist)** + 6.0 (allowlist tightened to Tiptap set; ActionText removal — **entirely**, dependency included)
**Depends on:** `6.0-admin-spa.md` (Tiptap is the only editor at 6.0 — no legacy admin), `6.0-replace-taxons-with-categories.md` (sequencing: Phase 3 runs **before** the `spree_taxons` table rename; that plan owns the translation-table renames), `5.4-6.0-custom-fields-rename.md` (`CustomFields::RichText` value storage migrates here), `5.4-metafield-translations.md`, `5.5-6.0-resource-translations-api.md` (translated HTML flows through the same sanitizer)
**Author:** Damian + Claude
**Last updated:** 2026-07-27

## Summary

Standardize how rich text (product descriptions, category descriptions, policy bodies, custom-field rich text, internal notes) is stored and served. Move off ActionText as a storage backend in favor of sanitized plain HTML text columns, since the 6.0 admin uses Tiptap (not Trix). Unify the API shape: every rich text field reads as `field` (plain text) + `field_html` (HTML), and **writes as `field_html`** (read/write symmetry).

**Scope expansion vs the original draft (2026-07-27 review):** ActionText is removed *entirely* at 6.0 — including `CustomFields::RichText` values and Order/User internal notes, which the original draft deferred. Both deferrals collapsed under scrutiny: the dashboard already writes Tiptap HTML into rich-text custom fields **today** (through ActionText's Trix allowlist — the exact bug this plan exists to fix), and at 6.0 the SPA's internal-note editor is the *only* editor, so "stays on ActionText for the Rails admin" describes a UI that no longer exists. With those two migrated, nothing in core uses ActionText and the dependency is dropped.

## Problem

Rich text storage is inconsistent across models (state at HEAD, 2026-07-27):

| Model | Storage | Translation | API output |
|-------|---------|-------------|------------|
| Product | `text` column | Mobility (table backend) | `description` (plain) + `description_html` ✓ shipped 5.4 — **but unsanitized** |
| Taxon | ActionText | Mobility (action_text backend) | `description` + `description_html` (reading ActionText objects) |
| Policy | ActionText | Mobility (action_text backend) | `body` + `body_html` (reading ActionText objects) |
| CustomFields::RichText | ActionText (`has_rich_text :value`, ignores its own `value` column) | per `5.4-metafield-translations.md` | serialized via `value.body` |
| Order#internal_note | ActionText | none | Admin API: **plain text only** (`internal_note`) |
| User internal_note | ActionText | none | Admin API: **HTML only** (`internal_note_html`) — inconsistent with Order |

1. **ActionText is a Trix companion, not a generic HTML store.** It sanitizes against Trix's allowlist, which strips valid Tiptap output; it wraps content in `<div class="trix-content">` and uses `<action-text-attachment>` tags. The dashboard's Tiptap editor already writes custom-field rich text through this today — silent corruption in production, not a future risk.
2. **No sanitization exists anywhere on the shipped path.** Admin API `:description` writes are stored raw and served as `description_html` to storefronts. The concern/sanitizer classes in the original draft (`SanitizableRichText`, `RichTextSanitizer`) were never implemented — verified repo-wide.
3. **Inconsistent shapes.** The two internal-note serializers ship opposite conventions (plain-only vs html-only); write params accept HTML under plain field names.

## Key Decisions (do not deviate without discussion)

- **Store HTML in text columns.** Tiptap produces HTML via `editor.getHTML()`. No ActionText, no Tiptap JSON — HTML is universally consumable (storefronts, emails, search, feeds, mobile); the admin is the only writer.
- **ActionText is dropped entirely at 6.0 — code in 6.0, tables in 6.1.** All five users migrate in 6.0 (Taxon, Policy, CustomFields::RichText, Order#internal_note, User internal_note), and 6.0 removes the runtime surface: the `mobility-actiontext` gemspec dependency, the `has_rich_text`/`backend: :action_text` declarations, and the model-generator template line. The `action_text_rich_texts` **tables** are dropped in 6.1 with the other legacy-table drops (data is copied out in 6.0; the tables linger one release as the rollback path — the same convention `spree_adjustments` follows). Nokogiri (already used by the shipped helper, but only a transitive dependency) is declared in `spree_core.gemspec`.
- **Read/write symmetry (the v3 non-negotiable):** reads are `field` (plain) + `field_html` (HTML); **writes accept `field_html`**, never HTML-in-the-plain-field — the original draft's "accept HTML in the `description` param" meant a client PATCHing `description: "<p>x</p>"` read back `description: "x"`. The **model owns the bridge** (the OptionType#label pattern): `description_html=` sanitizes and writes the underlying column, paired with the existing reader. Writes to the plain field on rich-text models are rejected (422), not silently stripped.
- **Sanitize on write, allowlist scoped to what the editor emits.** The dashboard's Tiptap is StarterKit + Link (bold/italic/strike, lists, blockquote, code/pre, headings, links). The allowlist matches that — **no `style`, no `class`** (resolving the original draft's own open question flagging them as attack vectors), no tables/img/figure/span/div until the editor gains them (each future extension widens the allowlist deliberately). Server-side via `Rails::HTML5::SafeListSanitizer` (rails-html-sanitizer ≥ 1.6, present).
- **Plain text extraction via the shipped `Spree::RichTextHelper`** (`app/helpers/spree/rich_text_helper.rb`) — it deliberately maps block boundaries and `<br>` to newlines; the original draft's `.text.squish` would glue Tiptap's whitespace-free blocks together. Serializers standardize on it.
- **Internal notes standardize on the same shape**: both Admin serializers expose `internal_note` (plain) + `internal_note_html`; controllers permit `internal_note_html`. Text columns on `spree_orders`/`spree_users`, no translations.
- **Rake tasks never hardcode table names** (`Spree::Taxon.table_name` etc.) — Phase 3 must survive shipping before *or* after the `spree_taxons → spree_categories` rename, though the intended order is before.
- **Models with plain-text-only descriptions keep simple text columns** (Promotion, PaymentMethod, Store, PriceList, CustomerGroup) — no `_html` variant.

## Design Details

### Storage + translations

All rich text fields are `text` columns on the model's own table, translated via the Mobility **table** backend. Current-code forms (the original draft's snippets were stale):

```ruby
class Spree::Taxon < Spree.base_class
  TRANSLATABLE_FIELDS = %i[name pretty_name description permalink].freeze
  RICH_TEXT_TRANSLATABLE_FIELDS = %i[description].freeze
  translates(*TRANSLATABLE_FIELDS, column_fallback: Spree.mobility_column_fallback)
  # Removed: translates :description, backend: :action_text   (taxon.rb:164)
end
# Policy: same shape with body (RICH_TEXT_TRANSLATABLE_FIELDS = %i[body]); Product already correct.
```

`RICH_TEXT_TRANSLATABLE_FIELDS` stays — it drives the SPA translation matrix's rich-text editor (`translatable_rich_text_fields`).

### Sanitization

```ruby
module Spree
  class RichTextSanitizer
    # Matches the dashboard Tiptap editor (StarterKit + Link). Widen ONLY when the editor gains a node type.
    ALLOWED_TAGS = %w[h1 h2 h3 h4 h5 h6 p br hr ul ol li a strong em u s del sub sup blockquote pre code].freeze
    ALLOWED_ATTRIBUTES = %w[href target rel].freeze   # no style, no class — resolved 2026-07-27

    def self.sanitize(html)
      Rails::HTML5::SafeListSanitizer.new.sanitize(html, tags: ALLOWED_TAGS, attributes: ALLOWED_ATTRIBUTES)
    end
  end
end

module Spree
  module SanitizableRichText   # concern: sanitizes_rich_text :description — before_save allowlist pass
  end
end
```

Applied to every rich-text writer path — which includes CSV import (`import_schemas/products.rb` maps `description` raw; the `before_save` hook covers it) and the translations batch endpoint.

### Write bridge (per model)

```ruby
class Spree::Product < Spree.base_class
  include Spree::SanitizableRichText
  sanitizes_rich_text :description

  def description_html = description.to_s
  def description_html=(value) = self.description = value   # sanitized by the concern on save
end
```

Controllers permit `:description_html` (products, categories), `:body_html` (policies), `:internal_note_html` (orders, customers) — and stop permitting HTML under the plain names.

### Serializers

Product shipped in 5.4 (`product_serializer.rb:48-56`) and is the reference. Category/Policy switch from reading ActionText objects (`.to_plain_text` / `.body.to_s`) to `RichTextHelper.to_plain_text(record.description)` + `record.description.to_s`. Both internal-note serializers converge on `internal_note` + `internal_note_html` (today Order ships plain-only, Customer ships html-only — both wrong against this plan's own convention).

### Consumers of raw HTML (all routed through the helper/sanitizer in Phase 5)

- **Meilisearch indexing** (`search_provider/product_presenter.rb:52`) indexes raw HTML — tag names become searchable tokens; switch to `RichTextHelper.to_plain_text`.
- **Google data feed** (`data_feeds/google_presenter.rb:68`) emits raw HTML into `g:description` against Google's plain-text guidance — same fix.
- **CSV export** (`csv/product_variant_presenter.rb:88` — `description&.html_safe`) — export the HTML but drop the spurious `html_safe`.
- Emails render no descriptions (verified) — no work.

### Translations surface (deliberate, documented divergence)

The `5.5-6.0-resource-translations-api.md` matrix keys stay model-attribute-based: `{ "fr" => { "description" => "<p>…</p>" } }` with the field's `type: 'html'` hint — HTML in both directions, symmetric *within* that surface. The resource-level pair remains `description`/`description_html`. Translated HTML passes through the same sanitizer on write.

## Migration Path

### Phase 1 (remainder): Sanitizer — **ships in 5.6.2** (implemented 2026-07-28), it closes a live hole ✳

Implemented and registered as the `sanitize_rich_text` step in the 5.5→5.6 upgrade manifest, so `spree:upgrade` runs it automatically — both for 5.5 upgraders and for existing 5.6.x installs re-walking the manifest on the patch bump (every step is idempotent by contract). Upgrade guide: `docs/developer/upgrades/5.5-to-5.6.mdx` (incl. the iframe allowlist warning). Decided 2026-07-27: don't wait for 6.0.

**Severity (corrected 2026-07-28).** This is defense-in-depth and 6.0 preparation, **not** a live-XSS fix. `spree_multi_vendor` already ships `Spree::SanitizeConcern`, applied to Product as `sanitize :description, :meta_description, if: -> { vendor_id.present? }`, so today's lower-trust writers (Enterprise vendors) are already covered — by a *stricter* scrubber than this one (`PruneScrubber` with `tags_to_prune = %w[script style]` drops those element bodies entirely; `SafeListSanitizer` keeps their inner text). Every remaining core writer is privileged (admin JWT, `write_products` keys, CSV import).

The real driver is **`6.0-multi-vendor-marketplace.md`**: it moves vendors into core, bringing lower-trust writers to a core write path with no sanitization of its own. Shipping in 5.6.2 gets the primitive in place, exercised, and its allowlist tuned by merchants a full release before core vendors arrive. Two design notes follow from the Enterprise implementation: sanitize-on-**write** is the durable form (Enterprise derives `sanitized_description` at read time, so the stored value stays raw and only call sites that remember the `sanitized_*` prefix are protected), and `PruneScrubber`-style body-pruning for `script`/`style` is worth adopting when core absorbs the vendor path — Enterprise's stricter behavior should be the 6.0 target, not a regression.

The 5.6 cut deliberately differs from the 6.0 end-state in two ways:

- **Permissive-but-safe allowlist** — legacy content was written with TinyMCE (spans, divs, inline styles, tables, images) and real descriptions embed video `iframe`s; the 6.0 Tiptap-scoped list would corrupt that on next save. 5.6 ships Rails safe-list defaults + tables/img (kills `script`, event handlers, `javascript:` URLs; Loofah scrubs `style` contents). `iframe` stripped by default, re-permittable via the class-level configurable allowlist (`RichTextSanitizer.allowed_tags`/`allowed_attributes` in an initializer). **6.0 tightens to the Tiptap-emitted set** (Key Decisions above).
- **No write-contract change** — the `description_html=` bridge and plain-param rejection are 6.0 breaking scope; 5.6 keeps the `:description` param and sanitizes it.

Contents: `RichTextSanitizer` + `SanitizableRichText` applied to Product (covers Admin API writes and CSV import via `before_save`); the `spree:sanitize_rich_text` rake task for **existing** `spree_products.description` rows + translation rows — idempotent and loud, run through the operator-invoked `spree:upgrade` flow (never as a migration side effect: a patch release must not mutate merchant data outside an explicit upgrade run); `nokogiri` + `rails-html-sanitizer` declared in `spree_core.gemspec` and required in `lib/spree/core.rb`.

## Constraints on Current Work

- **No new `has_rich_text` or `backend: :action_text` declarations.** New rich text = text column + `SanitizableRichText`.
- **New rich-text serializers return `field` + `field_html`; writes accept `field_html`.** Never HTML under a plain field name.
- **Do not store Tiptap JSON.**
- **Don't widen the sanitizer allowlist ahead of the editor.** Editor gains a node type → allowlist widens in the same PR.
- **Rake tasks use `Model.table_name`** — never literal table names (CLAUDE.md rule; the categories rename may land on either side).

## Resolved Questions

1. **`style`/`class` stripped entirely** (2026-07-27, closing the original open question): the shipped Tiptap editor (StarterKit + Link) emits neither; the original allowlist admitted attack surface (CSS overlays, class collisions) for markup no writer produces. Text-align classes get allowlisted if/when the editor gains the extension.
2. **Write contract is `field_html`** (2026-07-27): read/write symmetry per the v3 rule; model-owned bridge; plain-field HTML writes rejected.
3. **ActionText is fully dropped, not reduced** (2026-07-27): custom-field rich text and internal notes migrate too — the dashboard already Tiptaps both surfaces (custom fields today, internal notes at 6.0 when the SPA is the only admin), and keeping ActionText for them preserves the exact Trix-corruption bug this plan exists to fix.
4. **Sequencing with the categories rename** (2026-07-27): Phase 3 before the table rename by intent, table-name-agnostic by construction. The categories plan drops its `backend: :action_text` line (fixed) and owns the translation-table renames.

## Open Questions

- **Image handling.** Tiptap image nodes produce `<img src="...">` — uploaded to Active Storage with URLs rewritten, or external URLs allowed? Intersects `5.4-6.0-product-media-system.md` and the SPA media manager; the sanitizer excludes `img` until this is decided.
