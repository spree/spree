# Collections Merchandising Parity

**Status:** In Progress — Migration Path steps 1–7 (publishing, correctness fixes, Collection promotion rule, rule types, mixed membership, image alt, storefront) on `feat/collections-merchandising`
**Target:** Spree 6.1
**Depends on:** Collections (shipped in 6.0, `6.0-replace-taxons-with-categories.md`), Channels/ProductPublication (shipped, `6.0-channels-catalogs-b2b.md`), Product Market Availability (`6.1-product-market-availability.md`), Product Types (shipped), Custom Field Definitions (shipped)
**Author:** Damian + Claude
**Last updated:** 2026-11-05 (implementation decisions)
**Tracking:** Linear V-3782 · GitHub spree/spree#15120

## Summary

Collections shipped in 6.0 as a flat, translatable, SEO-ready merchandising
grouping with manual or rule-based membership, eight sort orders, and a Store
API that the Next.js storefront now builds collection pages, header search and
home-page shelves on. Measured against what merchants expect from a
modern commerce platform's collections, the gaps a merchant hits on day one are: a collection is
public the moment it is saved (no draft, schedule or per-channel publishing);
a promotion cannot target a collection; automatic membership has three rule
types where merchants expect conditions on price, stock, category, title,
type, seller and custom fields with range and prefix comparisons; manual
picks and rules cannot be mixed, and nothing can be excluded; and two
correctness issues — the `Sale` rule reads only the store's default currency,
and a renamed collection's old permalink 404s through the Store API even though
FriendlyId history records it. This plan closes those gaps in 6.1 by reusing
machinery Spree already has (ProductPublication's shape, the Category promotion
rule's shape, CustomFieldDefinition, ProductType, Seller), and explicitly
leaves variant-scoped collections, app-shareable rule sources and theme
template suffixes out.

## Key Decisions (do not deviate without discussion)

- **Build on existing Spree shapes.** Publication copies
  `ProductPublication`; the promotion rule copies `Promotion::Rules::Category`;
  new rule types are STI subclasses registered in
  `config.spree.collection_rules`. No separate rule-source object graph — that
  shape only pays off for app-shareable sources and sub-collections, both
  out of scope.
- **Membership stays materialized.** `spree_product_collections` remains the
  single read path (listing, search index, promotions). New rule types and the
  inclusion/exclusion lists all feed `RegenerateProducts`; nothing evaluates
  rules at read time.
- **Collections publish to every active channel by default; existing
  collections are backfilled the same way** (2026-11-05, interactive review).
  Zero behavior change on upgrade, and API clients that create collections
  keep getting live ones. "Every active channel" means the channels active
  when the collection is created (or when the upgrade backfill runs). A
  channel created or reactivated later starts with no collections, the same
  as with products: the merchant adds them from the channel, through
  `Channel#add_collections` (a copy of `#add_products`). Both the upgrade
  backfill (a rake task, see Migration Path) and the new
  `Spree.collection_create_workflow` write publications with `insert_all`
  (one statement per collection batch, not a `create!` per channel). *Accepted trade-off:*
  a half-built collection is live until the merchant unchecks
  its channels or sets a future `published_at`; the dashboard's Publishing
  card makes that visible on the create form.
- **Price and Sale rules evaluate in one named currency; membership stays one
  set per collection** (2026-11-05). A rule's nullable `currency` defaults to
  the store's default currency. *Accepted trade-off:* "Under $50" is $50 in
  that currency for every market; a merchant who wants per-market price bands
  creates one collection per market (and publishes each to the matching
  channel). Per-currency materialization was rejected: it multiplies the
  membership table and forces a currency onto every read path.
- **No sub-collections** (2026-11-05). Hierarchy is what categories are for
  (`category` rule with `include_descendants`, §2); mixed rules + manual
  inclusions + exclusions (§3) covers the "combine" cases collections need.
- **The Collection promotion rule does eligibility + item targeting only**
  (2026-11-05), the same shape as the Category rule. *Accepted trade-off:* no
  "buy from collection A, get collection B discounted" — that needs a
  buy-X-get-Y action, which is a separate promotions plan if wanted.
- **Market availability is not re-implemented here.** A product hidden in a
  market by `6.1-product-market-availability.md` is hidden inside every
  collection by that plan's read-path intersection. This plan only fixes
  collection-owned logic (the `Sale` rule's currency).
- **One pull request, committed by layer** (2026-11-05, implementation).
  The steps share the membership table, the collection model and the
  dashboard form, so reviewing them apart would mean reviewing intermediate
  shapes that never ship; commits split by layer (core, API, SDK, dashboard,
  docs) instead of by step. The storefront change (step 7) is a separate
  pull request on `spree/storefront`, opened in the same run.
- **`spree_product_collections.source` stays nullable in 6.1; NOT NULL ships
  in 6.2** (2026-11-05, implementation). A NOT NULL migration in 6.1 would fail
  `db:migrate` on any install that has not yet run the
  `spree:collections:backfill_membership_sources` upgrade step, which breaks
  the migrate-then-upgrade order. In 6.1 the model requires a `source` and
  every writer names one. *Accepted trade-off:* the database does not enforce
  it for one release.
- **Publications are written two ways** (2026-11-05, implementation). The
  nested `publications` resource serves API clients and agents; the
  collection payload also takes a `publications` set (the product's
  `product_publications` shape) so the dashboard's create form saves the
  merchant's channel choice in one request. Omitting it on create publishes
  on every active channel.
- **A product's `collection_ids` means hand-picked collections** (2026-11-05,
  implementation). The Admin API reads and writes the same set, so a form
  that posts back what it read never turns rule memberships into hand-picks.
- **`automatic` is accepted and ignored on write, and marked deprecated**
  (2026-11-05, implementation). The flag is derived from whether the
  collection has rules. *Accepted trade-off:* sending `automatic: false` no
  longer deletes or disables a collection's rules; a client removes rules by
  sending `rules: []`.

## Design Details

### 1. Collection publishing (per channel, with a window)

New `Spree::CollectionPublication` (`cpub_`), mirroring `ProductPublication`:
`collection_id`, `channel_id`, nullable `published_at` / `unpublished_at`,
unique on the pair, `published` scope with the same window semantics.
`Channel has_many :collection_publications`; `Collection has_many
:publications` + `published_on?(channel)`. `Channel.add_collections` /
`#add_collections` / `#remove_collections` copy the product methods of the
same names (upsert, optional window); they are how a new channel gets
collections, since nothing publishes onto a channel when it is created.

- **Store API:** `CollectionsController#scope` joins to publications on
  `Spree::Current.channel` with the `published` scope — list, show and search
  alike. An unpublished collection is a 404 (the storefront's proxy check
  already turns that into a real 404).
- **Admin API:** `publications` as a nested RESTful resource on the
  collection (`index/create/update/destroy`), declared with `request_params`
  and covered by rswag specs — which also makes them agent tools
  (`6.0-agent-tools-from-openapi.md`). Webhook events `collection.published` /
  `collection.unpublished`, payloads from the Store serializer.
- **Dashboard:** a "Publishing" card on the collection form (channel
  checkboxes + optional schedule), same component as the product card.
- **Defaults:** a new `Spree.collection_create_workflow` (the Admin API
  controller overrides `create_workflow`; CSV import and sample data call it
  too — today they all build the record directly) publishes to every active channel of the store, and the migration backfills every existing collection the same
  way — both via `Spree::CollectionPublication.insert_all` (see Key
  Decisions). Setting a future `published_at` is how a merchant stages a
  collection before launch.

### 2. More automatic rule types and relations

New STI subclasses of `Spree::CollectionRule`, registered in
`config.spree.collection_rules`. Each declares the match policies it accepts
(`self.match_policies`) so validation and the dashboard offer only meaningful
relations; `MATCH_POLICIES` grows to add `greater_than`, `less_than`,
`starts_with`, `ends_with`.

| Rule (`api_type`) | `value` | Policies | Notes |
|---|---|---|---|
| `category` | category id; `include_descendants` preference | equals / not_equals | Optionally matches subcategories |
| `product_type` | product type id | equals / not_equals | |
| `price` | decimal amount | greater_than / less_than | Evaluated per currency — see below |
| `in_stock` | — | equals (in stock) / not_equals | Any variant with `can_supply?`; refreshed on stock change |
| `title` | string | equals / contains / starts_with / ends_with / negations | Translated name in the store's default locale |
| `seller` | seller id | equals / not_equals | Marketplace stores |
| `custom_field` | definition id + value | per field type (text: contains…, number/date: greater/less) | Only definitions with a new `collection_condition` flag, alongside the existing `searchable`/`sortable` flags |

**Currency-sensitive rules (`price`, `sale`).** Membership is materialized
per collection, not per currency. A rule evaluates against the store's
default currency **unless** the rule names a `currency` (new nullable column
on `spree_collection_rules`). This keeps one membership set and makes the
multi-currency case explicit instead of silently wrong (Key Decisions).

**Regeneration triggers.** `in_stock` and `price` change outside product
saves, so `Products::AutoMatchCollectionsJob` is also enqueued from stock
item and price changes — debounced per product, and only when the store has
an automatic collection using that rule type
(`Collection.automatic.joins(:rules).where(rules: { type: … })`).

### 3. Mixed membership: rules + manual inclusions + exclusions

Replace the `automatic` either/or with three inputs that `RegenerateProducts`
unions:

- **Rules** (as today, `rules_match_policy` all/any).
- **Manual inclusions** — `spree_product_collections.source` = `manual`
  (new string column, `null: false`, **no default**; rule-derived rows
  written as `rule`). Every writer names the source, bulk `insert_all` in
  `RegenerateProducts` included, so a forgotten argument fails instead of
  turning rule rows into hand-picked ones.
- **Manual exclusions** — new `spree_collection_exclusions`
  (`collection_id`, `product_id`, unique) removed from the rule result.

The pair stays unique, so a product has one membership row and one
`source`. Precedence:

- **Manual wins over rule.** Regeneration deletes only `rule` rows the rules
  no longer match and inserts `rule` rows only for products with no row; it
  never touches a `manual` row. Adding a product that is already a `rule`
  member flips the row to `manual` and keeps its position.
- **Removing a manual inclusion** deletes the row and enqueues regeneration;
  if the rules still match, the product comes back as a `rule` row at the
  end of the manual order. To keep it out, the merchant excludes it.
- **Exclusion wins over both.** Excluding deletes the row whatever its
  source. Adding an excluded product by hand deletes the exclusion first,
  since adding is the later, explicit act; removing an exclusion enqueues
  regeneration, which brings the product back if the rules match.

`automatic` stays as a derived/compat flag (`rules.exists?`) for one release
so existing API clients and `Collection.automatic` scopes keep working, then
is deprecated. Positions are shared across sources so a manual sort order
covers rule-derived and hand-picked products alike.

### 4. Promotion rule: Collection

`Spree::Promotion::Rules::Collection` (`api_type` `collection`), a copy of
the Category rule's shape: `has_many :promotion_rule_collections`
(new join `spree_promotion_rule_collections`), `match_policy` any/all,
store-scoped id assignment, `eligible?(order)` against the order's products'
`collection_ids`, and `actionable?(line_item)` so item-level actions discount
only collection members. Reads the materialized membership — no rule
evaluation at checkout.

### 5. Historic permalinks resolve through the Store API

`CollectionsController#find_resource` falls back to FriendlyId history
(`friendly_id_slugs`, already populated) when the current-permalink lookup
misses, and returns the collection; the response's `permalink` is the
current one, so a storefront compares and 301s. Same change for categories
in the same PR (they share the history table and the gap).

### 6. Image alt text

Expose `image_alt` / `square_image_alt` on the Store and Admin serializers,
read from the media-library `Spree::Media#alt` record that the attachment is
placed from (`HasLibraryMedia`). Translatable through Media's existing
translations; no new column on collections.

### 7. Market and count correctness

- `CollectionRules::Sale` uses the rule's `currency` (§2) instead of
  `store.default_currency`.
- `products_count` stays "members of the collection" and is documented as
  such in the Store API schema; the market-correct count is the listing
  endpoint's `meta.count`, which inherits product market availability.

## Migration Path

1. **Publishing** — migration for `spree_collection_publications` (schema
   only); `spree:collections:backfill_publications`, a rake task that puts
   every collection on every active channel with `insert_all` and is
   registered as a step in a new `upgrades/6_0_to_6_1/manifest.yml`
   (data transformations go in rake tasks, `spree/AGENTS.md`);
   `Spree.collection_create_workflow`; `Channel#add_collections`; Store API
   scope; Admin API + webhooks; dashboard card; SDK types regenerated. The
   workflow, the backfill and the Store API scope ship in one release, so no
   install ever has collections without publications while the scope
   filters on them.
2. **Correctness fixes** — historic permalink resolution (collections +
   categories); `Sale` currency; Store API schema note on `products_count`.
   Independent; can land first.
3. **Promotion rule** — join table, rule, Admin API (rule types endpoint
   lists it), dashboard rule editor.
4. **Rule types + relations** — `match_policies` per type, new policies,
   `currency` column, the seven rule classes, regeneration triggers,
   `collection_condition` flag on `CustomFieldDefinition`, dashboard rule
   builder.
5. **Mixed membership** — `source` column (added nullable; the
   `spree:collections:backfill_membership_sources` upgrade step sets
   existing rows on automatic collections → `rule`, else `manual`; a later
   migration makes it `null: false` once the step has run), exclusions table,
   `RegenerateProducts` rewrite, `automatic` becomes derived + deprecated.
6. **Image alt** — serializers + SDK.
7. **Storefront** (`spree/storefront`) — redirect on permalink mismatch,
   use `image_alt`, nothing else required (publishing is enforced server-side).

## Constraints on Current Work

- New Store API reads of collections must go through
  `CollectionsController#scope` (or a shared `Collections::ForContext`), never
  `store.collections` directly — once publishing lands, a bypass leaks
  unpublished collections.
- Don't add new readers of `Collection#automatic` as a stored mode; treat it
  as "has rules".
- Until publishing lands (Migration Path step 1), code that creates
  collections keeps calling `Collection.create` directly; there is no
  workflow yet and nothing filters on publications. From step 1 on, writes
  that create collections (API, imports, seeds, upgrade tasks) go through
  `Spree.collection_create_workflow` or write publications themselves — a
  collection with no publication is invisible on every storefront. Step 1
  ships the workflow, the backfill and the scope together, so there is no
  release where collections can be created without publications.
- Code that writes `spree_product_collections` rows names their `source`
  (`manual` or `rule`), including bulk `insert_all` calls; a missing source
  is a bug even while the column is nullable.
- New collection rule types must declare `match_policies` and register in
  `config.spree.collection_rules`; don't extend `MATCH_POLICIES` handling with
  per-type `case` statements in shared code.

## Open Questions

None open. The four draft questions (publishing defaults, currency-sensitive
rules, sub-collections, promotion targeting depth) were settled on 2026-11-05
and are recorded under Key Decisions. Review on the plan PR settled the rest
the same day: later channels start empty (Key Decisions), manual membership
wins over rules and exclusions win over both (§3), and both backfills are
upgrade rake tasks (Migration Path).
