# TypeScript Models

**Status:** Draft — design finalized, nothing built
**Target:** Spree 6.2
**Depends on:** `6.0-money-correctness.md` (money is never a float), `6.0-typed-webhook-events.md` (the event catalog names the models that publish events)
**Author:** Damian Legawiec (design driven with Claude)
**Last updated:** 2026-11-16
**Tracking:** Linear — · GitHub —

## Summary

Server-side TypeScript can read Spree's data only through the Admin API today: a network call and one of Puma's request threads for every read. This plan adds a server package, `@spree/server`, whose first content is `@spree/server/db`: Drizzle models of Spree's tables, generated from the Rails models, with a read-only connection. They cover the models that publish events and the records read next to them, not every table. The first consumer is TypeScript subscribers (`6.2-typescript-subscribers.md`). The models are also the first piece of the TypeScript-native next major, which keeps most of today's tables.

## Key Decisions (do not deviate without discussion)

- **Read-only in 6.x (2026-11-14).** The validations, callbacks and workflows that keep the data consistent are Ruby, so a row written from TypeScript would skip all of them without an error. The connection is opened read-only and a write through it fails. Writes go through the Admin API.
- **Generated from the Rails models, not from the database (2026-11-16).** A rake task, `spree:db_models:generate`, reads the Rails models and writes the TypeScript, the way `typelizer:generate` already writes the SDK types. Reading the tables with Drizzle's own tool was rejected: it sees tables and columns only, and what makes the models safe to use lives in Ruby — associations, soft deletes, id prefixes, class names, encrypted attributes. Hand-written models were rejected: they are out of date after the next migration and nothing detects it. Accepted cost: a generator to write and keep working in Ruby.
- **The package is `@spree/server`, and the models are `@spree/server/db` (2026-11-16).** This reverses the 2026-11-13 statement that no general server package is created in 6.x. One server package was chosen over a separate `@spree/db` so a handler's imports do not move in the next major, when services join the models. Accepted cost: the name and top-level shape of the next major's server package are fixed now, before that major is designed.
- **`@spree/core` stays browser-safe.** `@spree/server` depends on `@spree/core`, never the other way round, and is never imported by code that runs in a browser.
- **camelCase in TypeScript, snake_case in the database (2026-11-16).** Fields are named the way TypeScript code usually names them, and Drizzle maps them to the column names, as its documentation describes: tables are declared with the `snakeCase` builder. Accepted cost: a handler works with two vocabularies. The event payload and the API say `completed_at`; the model says `completedAt`.
- **Drizzle 1.0 (2026-11-16).** The `snakeCase` builder and the relations API this plan uses exist only in Drizzle 1.0, which is a release candidate today (`1.0.0-rc.5`); the stable line (`0.45`) has neither in this form. Accepted cost: the work starts on a release candidate, pinned to an exact version. If 1.0 is still a candidate at the 6.2 freeze, the preview ships on the pinned candidate. Falling back to the stable line was considered and rejected: its casing and relations are declared differently, so the generator's output would have to be written twice.
- **Only what subscribers use (2026-11-14).** About 55 models publish events, out of more than 400. Models are generated for those and for a hand-kept list of the records read next to them. Accepted cost: a handler that needs another table waits for it to be added to the list.
- **Unstable until the next major settles its schema.** The models follow the schema of the Spree release they ship with and may change in a minor release. Because they are generated and typed, a schema change shows up as a type error when a project builds, not as a failure at run time.
- **The package versions with the Spree gems.** The models match one schema, so `@spree/server` is released with the gems and a project keeps both on the same release.
- **Ruby class names never reach TypeScript.** Columns that store a class name are read and filtered by the short name the API uses.
- **Encrypted attributes are left out.** A generated model has no field for a column Rails encrypts, so ciphertext is never handed to a handler.

## Design Details

### What a developer sees

```ts
import { createReadOnlyDb, decodeId } from '@spree/server/db'

const db = createReadOnlyDb()

const order = await db.query.orders.findFirst({
  where: { id: decodeId('ord_k5nR8xLqAb') },
  with: { lineItems: true },
})

order.completedAt // camelCase here, completed_at in the database
order.total       // '129.9900': a string, never a number
```

In a subscriber the handler receives `db` ready-made; `createReadOnlyDb` is for scripts, such as a first full sync of existing records.

### What the generator writes

```ts
// packages/server/src/db/generated/orders.ts — generated, do not edit
import { bigint, numeric, snakeCase, timestamp, varchar } from 'drizzle-orm/pg-core'

export const orders = snakeCase.table('spree_orders', {
  id: bigint({ mode: 'number' }).primaryKey(),
  number: varchar(),
  total: numeric({ precision: 19, scale: 4 }),
  completedAt: timestamp(),
  // …
})
```

The table keeps its real name (`spree_orders`); the export drops the prefix (`orders`). Relations are written with `defineRelations` in a generated file of their own. The example shows the shape, not final output.

### Which models

The generator takes a list kept in `spree_core`:

- every model the event catalog names as publishing an event, taken from the catalog so the list cannot fall behind it;
- a hand-kept list of neighbours: the records a handler reads next to those, such as line items, variants, customers and addresses;
- the translation tables of the models above (see below).

A relation is generated only when both ends are in the list. An association that points outside the list stays a plain foreign-key column.

### What the generator handles that a table reader cannot

| Rails fact | Count today | What the model does |
| --- | --- | --- |
| Prefixed ids (`ord_…`), encoded from the integer id | 149 models | `decodeId` and `encodeId`, with the prefix of each covered model generated |
| Soft-deleted rows | 41 models | A handler must not get deleted rows by accident; the mechanism is an open question |
| Class names stored in polymorphic and type columns | 31 associations, 22 type columns | A column type that converts to and from the API's short name, from a generated map |
| Encrypted attributes | 5 | The field is left out |
| Translated attributes kept in translation tables | 8 tables | The translation table is a model with a `translations` relation; a translated name is read from there, not from the main table |
| Money and rate columns (`decimal`) | — | A string in TypeScript, never a number |

The id decoder uses the same encoding as Ruby (Sqids, minimum length 10). A test decodes ids that Ruby encoded, so the two cannot drift apart unnoticed.

### Column types

| Rails | TypeScript |
| --- | --- |
| `bigint` id and foreign keys | `number` |
| `string`, `text` | `string` |
| `decimal` | `string` |
| `integer`, `float` | `number` |
| `boolean` | `boolean` |
| `datetime` | `Date` |
| `date` | `string` |
| `json`, `jsonb` | `unknown` |

### The connection

`createReadOnlyDb()` uses the database settings Rails uses: `DATABASE_URL` in production; `DATABASE_HOST`, `DATABASE_USERNAME`, `DATABASE_PORT` and `DATABASE_NAME` in development. It opens the connection in Postgres's read-only mode, which guards against accidents and is not a security boundary. The pool is small, two connections by default, so each replica adds little to the database's connection count. The driver is plain JavaScript, so the package bundles into one file, as the subscribers build requires.

### Keeping the models in step with Rails

- The generated files are committed. A check in CI runs the generator and fails when the committed output differs.
- A second check loads the Rails schema into Postgres and reads every generated model and relation once, so a wrong column name fails in CI.
- `spree upgrade` already moves a project's gems and npm packages to one release; `@spree/server` joins that set.

### The next major

In 6.x Rails owns the schema and the models follow it. In the TypeScript-native major the direction turns round: the Drizzle models become the source of the schema and gain writes, and the generator is retired. Handler code that reads through `@spree/server/db` keeps its imports. This is the intent, not a promise: the models stay labelled unstable until that major's schema is settled.

## Migration Path

1. **Package:** `packages/server` with the `db` entry, a lint rule that stops browser packages importing it, and release wiring so it versions with the gems.
2. **Generator in `spree_core`:** the model list, columns and types, relations inside the list, the id prefixes, the class-name map, encrypted attributes left out. RSpec for the generator.
3. **Runtime pieces:** the id decoder with fixtures encoded by Ruby, the class-name column type, the read-only connection. A prototype here settles how soft-deleted rows are filtered.
4. **CI:** the stale-output check and the read-every-model check against a migrated Postgres.
5. **First consumer:** `db` in the subscriber handler context (`6.2-typescript-subscribers.md`).
6. **Docs:** a section in the TypeScript subscribers guide, carrying the unstable label and the two-vocabularies note.

## Constraints on Current Work

- `@spree/core` stays browser-safe. Server-side TypeScript goes in `@spree/server`, which is never imported by the dashboards, the SDKs or a storefront.
- No write path through the models in 6.x.
- Generated files are never edited by hand. Once the generator exists, a migration that changes a covered table ships with regenerated models.
- A table subscribers should read is added to the generator's list, not hand-written as a Drizzle table in `@spree/server`.
- A `decimal` column is never a `number` in TypeScript.
- Ruby class names stay out of the values the models expose.

## Open Questions

None block the start of the work. All are deferred, each with what settles it.

- **How soft-deleted rows are filtered.** The requirement is fixed: a handler does not get deleted rows by accident, and can ask for them on purpose. Whether the read-only `db` can apply that to every query, or the package ships a filter a handler adds, depends on what Drizzle's query API allows. Settled by: the prototype in step 3.
- **Read-only mode behind a connection pooler, and encrypted connections.** A pooler in transaction mode may refuse the setting that makes a connection read-only, and the Node driver does not treat a connection string's encryption settings the way Rails' driver does. Settled by: a test against a managed database and a pooler before the preview.
- **Custom fields and other one-to-many polymorphic links.** Custom field values sit in one table shared by every model. Whether they are a generated relation or a query a handler writes is undecided. Settled by: step 2, once the relation generator exists.
- **Models for a project's own tables and for extensions.** Not in the first version; a project can declare its own Drizzle tables and query them with the same `db`. Settled by: what preview users ask for.
- **Allowed values of status columns as TypeScript unions.** Plain `string` at first. Settled by: preview feedback.
