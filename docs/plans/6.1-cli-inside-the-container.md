# CLI Inside the Container

**Status:** Draft — design finalized, nothing built
**Target:** Spree 6.1
**Depends on:** `6.0-backend-agnostic-cli.md` (neutral command names, the backend adapter), `6.1-spree-base-image.md` (the image the CLI ships in; needed for step 2 only)
**Author:** Damian Legawiec (design driven with Claude)
**Last updated:** 2026-11-16
**Tracking:** Linear — · GitHub —

## Summary

A developer learns the `spree` CLI on their machine and then has to switch to `bin/rails` on production, because the CLI only knows how to reach an app through Docker Compose. Upgrades show it most: `spree upgrade` locally, `bin/rails spree:upgrade` on the server. This plan lets the CLI run its operations commands directly when it is already inside the app, and ships the CLI in the base image, so `spree migrate`, `spree task`, `spree upgrade` and `spree console` mean the same thing in both places. Reaching a remote machine from a laptop is not part of it.

## Key Decisions (do not deviate without discussion)

- **One CLI, two ways to run a command (2026-11-16).** `backend.ts` already says what each command runs; only Docker Compose says where. A second runner executes the same backend command directly in the current environment. A Ruby `bin/spree` with the same command names was rejected: it is a second implementation of the same commands, and it would drift.
- **Only the operations commands work inside the container (2026-11-16).** `migrate`, `migrate:status`, `migrate:rollback`, `task`, `upgrade`, `console`, `seed` and `exec`. Every other command stops with one line saying it needs the project's source and belongs on the developer's machine. Offering every command that can technically run was rejected: `generate` would write files into an image that is thrown away on the next deploy. Accepted cost: eight commands are tested in two ways of running.
- **The image says so, the CLI does not guess (2026-11-16).** The base image sets `SPREE_CLI_RUNNER=direct`, and the CLI runs commands directly when it is set. Detecting it from the folder was rejected: a wrong guess runs a command against the wrong place. Accepted cost: an image that is not built on the base has to set the variable itself.
- **The CLI is baked into the base image (2026-11-16).** The runtime image carries the CLI for its Spree line and the weekly rebuild refreshes it. Installing the project's exact version during the project build was rejected: it slows every build, and a bare starter clone has no version to read. Accepted cost: the CLI in the image can be a patch or a minor version away from the one on a developer's laptop, so a direct command must keep working across the versions of one line.
- **`spree upgrade` inside the container runs only the post-deploy steps.** On a developer's machine it also moves gems, packages and project files; inside an image those are already built in. The same word covers both halves of one upgrade.
- **`spree migrate` inside the container applies migrations and copies none.** On a developer's machine it first copies new migrations from the gems into the project. Inside an image that copy would be lost on the next deploy and would leave the database ahead of the repository.
- **`spree` for operations joins the image contract.** The base image promises that these eight commands work inside it. Whatever later runs commands in a container, a hosted control plane included, can call them without knowing what the backend is, and a later Spree major can change the backend without changing the commands.
- **Remote access is out of scope.** Running `spree migrate` on a laptop against a production machine, signing in to a hosted account, and how a self-hoster reaches their own machines are a separate design that is not settled.
- **Delivered in two pull requests (2026-11-16).** The CLI change needs no image and starts now. Putting the CLI into the image follows once the base image has merged. Accepted cost: both touch CLI files the base image pull request also changes, so whichever merges second resolves a conflict.

## Design Details

### What changes for a developer

| Where | Today | With this plan |
| --- | --- | --- |
| Their machine | `spree upgrade` | `spree upgrade` |
| Production, after the deploy | `bin/rails spree:upgrade` | `spree upgrade` |
| Production, a one-off task | `bin/rails spree:search:reindex` | `spree task search:reindex` |
| Production, a console | `bin/rails console` | `spree console` |

Production already applies migrations on boot: the image's entrypoint prepares the database before the server starts. `spree migrate` inside the container is for the cases where someone needs to run it by hand.

### How the CLI decides

```
SPREE_CLI_RUNNER=direct  ->  run the backend command here, in the working directory
anything else            ->  find the project's docker-compose.yml and run through it (today's behaviour)
```

The project context already has a `mode`, and `docker` is its only value today. This plan adds `direct`. In direct mode the CLI does not look for a compose file.

### What each command does in direct mode

| Command | Runs |
| --- | --- |
| `spree migrate` | Pending migrations already in the image. No copy from the gems. |
| `spree migrate:status`, `spree migrate:rollback` | As on a developer's machine |
| `spree task <name>` | The Spree task, as on a developer's machine |
| `spree upgrade` | The post-deploy upgrade steps only, with the same `--plan`, `--step` and `--to` flags |
| `spree console` | The backend's console |
| `spree seed` | The seeds |
| `spree exec <command>` | The command, unchanged |
| Everything else | Stops: "This command needs the project's source. Run it on your machine." |

Prompts already fall back to non-interactive behaviour when there is no terminal, so a command run by a deploy script does not hang.

### In the image

- The base image's runtime stage installs `@spree/cli` for its line and puts `spree` on the path. The package is about 2 MB with five small dependencies.
- The CLI version range moves into `docker/base/lines.json`, next to the Ruby and Node versions of each line.
- The base image sets `SPREE_CLI_RUNNER=direct`. The build variant inherits it, so `spree` also runs directly inside an ejected project's development container.
- The base image workflow gains two checks: `spree --version` runs in the runtime image, and `spree migrate:status` succeeds inside the booted stock image. The second proves direct mode against a real app and database on every rebuild.
- An image that is not built on the base installs the CLI with npm and sets the variable. The Docker guide says how.

## Migration Path

1. **CLI, its own pull request, starting now:** a runner that either goes through Docker Compose or runs directly; the `direct` mode and the variable; the eight commands; the refusal for the rest; the two differences for `upgrade` and `migrate`. Tests for both modes.
2. **Image, after the base image pull request merges:** the runtime image ships the CLI and sets the variable; `lines.json` carries the CLI range; the two workflow checks.
3. **Docs:** a "Running commands in production" section in the Docker guide; the upgrade guides say `spree upgrade` for the post-deploy step; the guide for images not built on the base.

## Constraints on Current Work

- Every backend invocation stays in `packages/cli/src/backend.ts`. A command file never builds a Rails command itself.
- A command file does not call Docker Compose directly for a backend command; it goes through the runner, so the command works in both modes or refuses in one.
- A new CLI command states whether it works in direct mode. The default is that it does not.
- A direct-mode command keeps working across every CLI version of one Spree line, because the image and the laptop can be on different versions.
- Nothing in direct mode writes files that only exist until the next deploy.

## Open Questions

None block the work. Deferred:

- **Reaching a remote machine from a laptop.** Targets, sign-in and transports. Unblocked by: the design of the hosted offering.
- **Telling a developer their image's CLI is older than their laptop's.** Whether a direct command should warn. Unblocked by: seeing whether the difference causes confusion once images are in use.
- **A database console and logs inside the container.** The runtime image has no `psql`, and logs belong to the platform. Unblocked by: a request for them.
