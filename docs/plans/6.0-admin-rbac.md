# Admin RBAC and Permission Management

**Status:** Design Finalized
**Target:** Spree 6.0
**Depends on:** `5.5-admin-api-key-scopes.md` (shipped), `6.0-admin-api.md`, `6.0-admin-spa.md`, `6.0-platform-auth.md` (Customer/Staff split)
**Author:** Damian (from spree/spree#14164 by @caspianlwoods)
**Last updated:** 2026-08-07

## Summary

Merchants should be able to create staff roles and edit their permissions from the
dashboard, without writing Ruby in an initializer. This plan replaces the
permission-set system with **one grant model**: a flat catalog of
`read_<resource>` / `write_<resource>` keys — the same vocabulary secret API keys
already use ([5.5-admin-api-key-scopes.md](5.5-admin-api-key-scopes.md)). **Roles
are pure data**: keys live on the role row, edited in the dashboard, via the Admin
API, or seeded with plain ActiveRecord — there is no code-managed role concept and
no runtime merge. Code defines the *vocabulary* (catalog registrations, including
extensions'); data defines the roles. One catalog powers the role editor, the
API-key scope picker, `/me`, endpoint enforcement, and authorization-failure
diagnostics.

The system is **staff-only**. The storefront has no roles: customer authorization
is ownership (scope-fetching: `current_user.addresses`, cart tokens) plus a fixed
internal baseline — not something a merchant edits. B2B company accounts (multiple
users per company, buyer/approver roles, hierarchies, spend limits) are a separate
future Enterprise system with its own vocabulary and are explicitly out of scope
here; sharing a registry with them would poison the meaning of every key
(`write_orders` means "manage the store's orders" to staff and "place my company's
orders" to a purchaser — those must never be the same token).

Much of what issue #14164 asks for already exists and only needs to be surfaced:
store-scoped role assignments work end to end (`Spree::RoleUser` + per-store
resolution in `Spree::Ability` + the staff API), `RoleGrantGuard` already blocks
privilege-escalating grants, and `/me` already feeds the dashboard's permission
mirror. What is genuinely new: the catalog registry, a `permissions` column on
`Spree::Role`, role CRUD in the Admin API, model-level protection of the admin
role, unified key-based enforcement for both admin principals, and the dashboard
pages.

## Key Decisions (do not deviate without discussion)

### The grant model

- **The permission catalog is the API-key scope vocabulary.** Grantable units are
  `read_<resource>` / `write_<resource>` keys, exactly the tokens in
  `Spree::ApiKey::SCOPES`. No parallel `orders.read` dot-grammar — the scope
  tokens shipped in 5.5 and are public API. The UI shows translated labels, not
  raw keys.
- **Resource granularity, not action granularity** — reaffirming the 5.5 scopes
  decision. No `cancel_orders` / `approve_orders` keys. The motivating example
  ("customer service reads orders but cannot refund") already falls out of
  resource granularity because `payments`, `refunds`, `gift_cards`, and
  `store_credits` are separate resources from `orders`.
- **Permission sets are deleted at 6.0 — with no compatibility bridge
  (2026-08-07).** This is a deliberate exception to the "every 6.0 rename keeps
  a one-release bridge" convention: it is a system removal, not a rename, and a
  behavior-preserving shim would have to carry the runtime-union machinery the
  removal exists to kill. Old initializers fail loudly at boot (`NameError` on
  the deleted set constants; `Spree.permissions.assign` raises with an
  upgrade-guide pointer — a tripwire, not a bridge). Migration is genuinely
  trivial: delete the initializer lines, recreate the role in the editor.
  Fail-closed is the right failure mode for permissions — nothing boots with
  staff silently over- or under-privileged. Custom rules that mixed
  record-level conditions into sets migrate to
  `Spree::Dependencies.ability_class` — replacing the ability class outright
  is the remaining low-level escape hatch (2026-08-08: `register_ability` was
  dropped too; the catalog plus a full class swap is the whole surface). (Two earlier same-day drafts — sets kept as "bundles" over the
  catalog, then a one-release `assign` bridge with an import task — were both
  rejected as complexity serving only back-compat comfort in the breaking
  window.)
- **Roles are pure data — there is no code-managed role concept (2026-08-07).**
  No `Spree.permissions.grant`, no runtime merge, no union semantics, no
  "granted in code" locked rows: the editor is WYSIWYG and the row is the whole
  truth. "Roles as code" is served by seeds
  (`Spree::Role.find_or_create_by!(name: 'support').update!(permissions: [...])`
  is plain ActiveRecord) or by the Admin API with a secret key. Extensions
  register catalog resources — never roles. This matches the entire field:
  Saleor (permission groups via dashboard/GraphQL only), Vendure (roles are DB
  entities; code defines only the permission catalog and optional initial
  seeds), Medusa (no OSS RBAC at all), Shopify/commercetools (UI/API only).
- **Role permissions are a JSON array of concrete keys on `spree_roles`,**
  mirroring `Spree::ApiKey#scopes` storage exactly (native JSON column,
  `attribute` default `[]`, known-key validation). No join table, no stored
  aliases (`read_all` / `write_all` stay API-key conveniences; the editor offers
  select-all client-side).
- **Locked roles use a `mutable` column — the NamedType pattern applied to
  roles (2026-08-07).** The admin role seeds with `mutable: false` (plus a
  belt-and-braces guard on the `admin` name); a host that needs a
  compliance-locked role sets `mutable: false` from seeds or console and the
  editor renders it read-only. This covers the one legitimate thing the code
  path used to provide — roles staff cannot edit — without a second grant
  source.

### Scope of the system

- **Staff-only (2026-08-07).** The catalog, the editor, `Spree.permissions`, and
  role resolution apply to admin-user principals only. `Spree::Ability` resolves
  roles solely for `Spree.admin_user_class` principals; customer principals get
  the storefront baseline directly — which also drops a per-request `role_users`
  query for logged-in customers and aligns with the platform-auth Customer/Staff
  split (a customer holding the admin role stops being a concept at 6.0).
- **The Store API does not use CanCanCan at all (2026-08-08, superseding the
  2026-08-07 "internal baseline" decision).** `Spree::Ability` is staff-only;
  an ability built for a customer principal has no rules. Storefront
  authorization is ownership, enforced two ways: **scope-fetching** (every
  account controller reads through `current_user` — addresses, cards, gift
  cards, store credits, wishlists — and catalog endpoints read the store's
  public data with no per-record check), and **`Spree::Storefront::AccessPolicy`**
  for the checks a scope cannot express: cart/order access proven by JWT
  ownership OR a guest token. The policy is swappable via
  `Spree::Dependencies.storefront_access_policy_class`; denials raise
  `Spree::Storefront::AccessDenied`, rendered as the same 403 payload as
  CanCan's. The generic `authorize_resource!`/`authorize_parent!` hooks and
  the `accessible_by` collection filter moved from the shared v3
  `ResourceController` down to the Admin branch — the shared base carries
  no authorization framework.
- **B2B company accounts extend the storefront through seams, not controller
  decoration (2026-08-08).** The Enterprise B2B module
  (`6.1-channels-catalogs-b2b.md`: Company → CompanyLocation →
  CompanyContact, buyer/approver/viewer contact roles, approvals, spending
  limits) needs exactly three kinds of authority change, and each has an
  open-source injection point already in place:
  1. **Access widening** ("an approver sees every purchase of their company
     location") — subclass `Spree::Storefront::AccessPolicy`, override
     `scope`/`readable?`/`writable?`, register via
     `Spree::Dependencies.storefront_access_policy_class`. Relational scoping
     is the natural shape here; a rule engine is not — CanCanCan's
     `accessible_by` cannot translate block rules (the token checks) to SQL,
     which is why the old ability needed `authorize!` calls on top of scopes
     in the first place.
  2. **Action vetoes** ("orders over the spending limit need approval") —
     checkout workflow `validate` hooks (`carts.complete.validate`), shipped
     with `6.0-service-workflows.md`. These are order-state policies, not
     access rules; they never fit an ability cleanly.
  3. **Catalog visibility** (per-location catalogs/price lists) — data
     scoping through the products-for-context seam, per the 2026-08-07
     decision below.
  Enterprise implements policy subclasses and hook handlers; open source owns
  the seams. No CanCanCan and no controller decoration on the storefront —
  matching Medusa/Saleor/Vendure, none of which ship a storefront rule
  engine, and Shopify B2B, whose company-contact permissions are fixed roles
  resolved server-side.
- **B2B company roles are out of scope and must stay a separate system
  (2026-08-07).** Company-account permissions (buyer/approver, location roles,
  hierarchies, spend limits, order approvals) are ownership-scoped and
  workflow-shaped — what the flat catalog deliberately cannot express — and they
  are an Enterprise feature. Industry precedent is unanimous on separation:
  commercetools Business Unit associate roles, Shopify B2B company-contact
  permissions, and Medusa's B2B employee/spend-limit models are all distinct from
  staff RBAC. The polymorphic seams (`RoleUser#user`, `RoleUser#resource`) stay
  as-is and uncommitted — Enterprise may reuse the storage or ship its own
  models; this plan promises nothing.
- **Catalog/product visibility per customer group or company is data scoping,
  never a permission key.** "Can see catalog B" is a property of what the
  storefront query returns (channels/catalogs work, `6.1-channels-catalogs-b2b.md`),
  not of an authorization registry. Non-goal here, recorded so nobody models it
  as one later.

### Enforcement

- **The key gate is the primary check for both admin principals (2026-08-07).**
  `ScopedAuthorization` generalizes: every admin request resolves a principal key
  set — a JWT staffer's expanded role keys, a secret key's scopes — and checks
  `<read|write>_<scoped_resource>` against it. The per-controller
  `scoped_resource` declaration becomes the enforcement contract for everyone,
  which is what actually fixes the issue's "menus, API and CanCanCan drift apart"
  complaint. This supersedes the 5.5 constraint "don't add scope checks to
  JWT-authenticated paths" (noted there).
- **CanCanCan is demoted to internal plumbing, not dropped (2026-08-07).** Keys
  compile to CanCanCan rules behind the gate, because three things still need it:
  the storefront baseline's record-level rules, host ability-class swaps,
  and sixty-odd admin controllers plus the SPA mirror that speak
  `authorize!`/rules today — rewriting the enforcement layer and the grant model
  in one release doubles the risk. Nothing public configures CanCanCan anymore.
  Removing the gem from the admin path becomes a mechanical 6.1+ cleanup option,
  not a 6.0 goal.
- **Role protection lives on the model, not in the ability layer.** Rename,
  permission changes, and destroy are blocked by `Spree::Role` guards keyed off
  `mutable` (plus the `admin`-name guard), following the 2026-08-05 NamedType
  decision — ability rules don't fire for secret-key principals, so protection
  must live where every path hits it.
- **A role in use cannot be deleted.** `can_be_deleted?` is false while
  `role_users` or pending invitations reference the role. Reassign staff first.
- **Role CRUD gets the same escalation guard as role assignment.** Creating or
  updating a role may only grant keys the caller effectively holds (expanded:
  `write_x` implies `read_x` before comparison). `RoleGrantGuard` switches its
  comparison from permission-set classes to expanded key sets; secret-key callers
  are bounded by their own scopes — the anti-amplification rule API keys already
  have.
- **403 diagnostics reuse the scope declaration.** `handle_access_denied` adds
  `details: { required_permission: "<read|write>_<scoped_resource>" }` — the JWT
  twin of the shipped `details.required_scope`. Development logs additionally
  include the caller's roles and effective keys.

### Interactively settled 2026-08-07

- **`staff` splits out of the `settings` scope.** New `read_staff` /
  `write_staff` pair covers `/admin_users`, `/invitations`, `/roles` and the
  AdminUser/Invitation/Role/RoleUser subjects; those controllers re-scope from
  `settings` to `staff`. Team management is the escalation path and must be
  grantable separately from store configuration. **Accepted trade-off:** secret
  keys minted with `settings` before 6.0 lose the staff endpoints — Developer
  Preview breakage, called out in the release notes.
- **`Spree::ApiKey::SCOPES` derives from the catalog.** Key validation,
  `ScopedAuthorization`, and the OpenAPI scope docs read the registry; an
  extension registering a resource gets the role-editor row and mintable
  `read_x`/`write_x` scopes in one step. **Accepted trade-off:** the scope list
  is boot-dynamic — auditing "what can keys do" means consulting the running
  catalog (`/permissions`), not a frozen constant.
- **The role editor is a settings sheet** (revised 2026-08-08). The original
  call was a full page for the matrix and a members sidebar; in review the
  consistency argument won — every other settings resource (tax categories,
  payment methods, API keys) edits in a `?edit=<id>` / `?new=1` sheet, and a
  roles page that navigated away was the odd one out. The members sidebar is
  dropped with it: the row already shows a member count and Staff owns
  assignment. One sheet serves create, duplicate and edit.
- **No seeded roles; the create flow offers client-side templates.** "Order
  manager" / "Merchandiser" / "Support" presets pre-fill the matrix; nothing
  lands in the DB until saved. **Accepted trade-off:** templates are
  dashboard-only — headless/API consumers start from the bare protected `admin`
  role.

### Already true, kept deliberately

- **Store-scoped role assignment ships as-is; no new scoping model.** Per-store
  roles already work (`RoleUser` + ability + staff API). Vendor-scoped
  assignments arrive with `6.0-multi-vendor-marketplace.md` through the same
  polymorphic `resource`.
- **`/me` keeps the CanCanCan rules dump and adds `permission_keys`.** The SPA's
  `can(action, subject)` API stays stable — the catalog knows which resource owns
  each subject, so dashboard-core resolves subject → key internally; the rules
  dump remains for record-level hints while any remain.

## Design Details

### Permission catalog

A registry on `Spree.permissions` (the existing `PermissionConfiguration`
object), populated by core at boot and open to extensions:

```ruby
# core registration (engine initializer)
Spree.permissions.register_resource(:orders, group: :orders, subjects: -> {
  [Spree::Order, Spree::LineItem, Spree::TaxLine, Spree::Discount, Spree::Fee,
   Spree::Return, Spree::Exchange, Spree::Claim]
})

# an extension — one call yields the role-editor row AND mintable key scopes
Spree.permissions.register_resource(:reviews, group: :catalog, subjects: -> {
  [SpreeReviews::Review]
})
```

Each registration yields two catalog entries — `read_<resource>` (compiles to
`can [:read, :admin], subject` per subject) and `write_<resource>`
(`can :manage, subject`) — unless `write: false` (dashboard). Subjects are
lambdas for load-order safety. Labels and descriptions resolve through `Spree.t`
(`spree.permissions.<key>.{label,description}`), so backend extensions localize
without touching the SPA.

Core registers one entry per resource of the current scope vocabulary:

| Resource | Group | Subjects (canonical) |
|---|---|---|
| `orders` | Orders | Order, LineItem, TaxLine, Discount, Fee, Return, Exchange, Claim |
| `payments` | Orders | Payment |
| `fulfillments` | Orders | Fulfillment |
| `refunds` | Orders | Refund |
| `gift_cards` | Orders | GiftCard, GiftCardBatch |
| `store_credits` | Orders | StoreCredit |
| `products` | Catalog | Product, ProductType, Variant, OptionType, OptionValue, Price, PriceList, PriceRule, Asset, ProductPublication |
| `categories` | Catalog | Category, Taxonomy, ProductCategory |
| `collections` | Catalog | Collection, ProductCollection, CollectionRule |
| `stock` | Catalog | StockItem, StockLocation, StockMovement, StockTransfer, StockReservation |
| `promotions` | Marketing | Promotion, PromotionRule, PromotionAction, PromotionCategory, CouponCode |
| `customers` | Customers | `Spree.customer_class`, Address, CreditCard, CustomerGroup |
| `settings` | Settings | Store, PaymentMethod, DeliveryMethod, DeliveryZone, Market, Channel, TaxCategory, TaxRate, reasons, MetafieldDefinition, Policy, AllowedOrigin, OrderRoutingRule, … (today's ConfigurationManagement list minus webhooks) |
| `webhooks` | Settings | WebhookEndpoint, WebhookDelivery |
| `api_keys` | Access | ApiKey |
| `staff` *(new at 6.0)* | Access | `Spree.admin_user_class`, Invitation, Role, RoleUser |
| `dashboard` (read-only) | Analytics | `:dashboard` |

Notes:

- Today `AdminUser` and `Invitation` subjects are grantable only through
  SuperUser's `manage :all`. The `staff` entry closes that gap so a "Store
  manager" custom role can manage the team without full admin.
- `Spree::ApiKey::SCOPES` becomes catalog-derived: known-scope validation,
  `ScopedAuthorization`, and OpenAPI docs enumerate
  `Spree.permissions.catalog.keys` plus the `read_all`/`write_all` aliases. Keys
  minted under a vocabulary that later shrinks stay revocable (the existing
  `scopes_enforceable?` guard covers this).
- Catalog entries are pure Axis A: flat capability grants, no block conditions,
  no domain-invariant `cannot` rules (see `decisions.md` 2026-08-05). The
  `allow_cancel?` / `can_be_deleted?` block rules currently inside
  `OrderManagement`/`SuperUser` move to model/workflow guards as part of this
  work (guard + spec first, then drop the ability condition).

### Roles are data

```ruby
# the only "roles as code" story — plain ActiveRecord in db/seeds.rb (or the Admin API):
Spree::Role.find_or_create_by!(name: 'support')
  .update!(permissions: %w[read_orders read_customers], description: 'Read-only support')
```

`Spree::Role` gains:

```ruby
add_column :spree_roles, :description, :string
add_column :spree_roles, :permissions, <jsonb|json>, default: [], null: false
add_column :spree_roles, :mutable, :boolean, default: true, null: false
```

- `attribute :permissions, default: []` + normalizing setter — the exact
  `ApiKey#scopes` pattern.
- Validation: every key must be a concrete catalog key (no aliases).
- Guards keyed off `mutable` (NamedType pattern): name, permissions, and
  destroy are blocked while `mutable` is false. The `admin` role seeds with
  `mutable: false` and additionally can never be renamed or deleted by name
  guard. `can_be_deleted?` also requires no `role_users` and no pending
  invitations.
- The `admin` role reports the full catalog as its permissions (display); other
  roles report exactly their stored keys — there is no computed merge.

`Spree.permissions` ends up doing exactly one thing: catalog registration.
`assign` raises with an upgrade-guide pointer (tripwire for 5.x initializers);
there is no `grant`, no bridge, no union.

The storefront leaves CanCanCan entirely: customer/guest requests are
authorized by ownership-scoped queries plus `Spree::Storefront::AccessPolicy`
(cart/order token checks, order-listing scope), swappable through
`Spree::Dependencies.storefront_access_policy_class`. Role resolution
(`determine_role_names` + key activation from the role rows) runs only for
admin-user principals. The `admin` role activates the full catalog; its former
safety rules are model guards by then.

`Spree::Dependencies.ability_class` — swapping the whole ability class — is the
remaining low-level escape hatch for host rules that don't fit keys ("support
sees only their region's orders") and the migration target for custom
permission sets that mixed record-level conditions into grants.

### Admin API

```text
GET    /api/v3/admin/permissions        # catalog discovery
GET    /api/v3/admin/roles              # existing
GET    /api/v3/admin/roles/:id          # existing
POST   /api/v3/admin/roles              # new
PATCH  /api/v3/admin/roles/:id          # new
DELETE /api/v3/admin/roles/:id          # new
```

- **`/permissions`** returns the catalog:
  `[{ key, resource, kind, group, label, description }]`. Authenticated,
  `skip_scope_check!` (vocabulary, not data — same class as `/tags`), localized,
  HTTP-cacheable per boot. Replaces the dashboard's hardcoded `SCOPE_GROUPS`
  array and its "keep in sync with the server" comment.
- **Roles CRUD** on the existing controller (re-scoped to `staff`):
  `permitted_params` are `name`, `description`, `permissions: []` (read/write
  symmetry with the serializer). Create/update run the key-set escalation check;
  destroy surfaces the model-guard errors as 422.
- **Serializer** grows `description`, `permissions`, `mutable` (boolean — false
  renders read-only in the editor), `users_count` (assignments on the current
  store).
- **`/me`** adds `permission_keys` (expanded effective keys for the current
  store) alongside the existing rules dump.
- **Enforcement:** the generalized key gate checks every admin request's
  principal key set against `<read|write>_<scoped_resource>`; CanCanCan runs
  behind it (compiled from the same keys), so
  `authorize!`/`accessible_by` in controllers keep working unchanged during 6.0.
- **403 diagnostics:** `details.required_permission` from the `scoped_resource`
  declaration; development logs include roles + effective keys.

### Dashboard

- **Subject constants:** add `Role: 'Spree::Role'` to `dashboard-core`'s
  `lib/permissions.ts`. `can(action, subject)` keeps its signature; dashboard-core
  resolves subject → owning resource key via the catalog.
- **Navigation:** `settings.roles` in the `team` group (position 150, between
  Staff and API keys), gated by `subject: Subject.Role`.
- **Roles list** (`/settings/roles`): name, description, permission summary (the
  `ScopeList` badge treatment: "Full access" for admin, first N keys + overflow),
  members count, lock icon on immutable roles. Row actions: edit,
  duplicate (opens the new-role page pre-filled), delete (confirm; disabled with
  tooltip while `can_be_deleted?` is false).
- **Role editor** (a sheet on the same page, driven by `?edit=<id>` / `?new=1`,
  with `?from=<id>` for duplicate): name, description, then the permission
  matrix grouped by catalog group — read/write checkboxes per resource
  (read-only resources render read alone). "Read only" / "Full access" /
  "Clear" presets. Immutable roles (`mutable: false`) and callers without
  update authority get a read-only sheet with no Save. Keys outside the
  caller's own grant render disabled (the API would reject them — don't offer
  them). Creating opens with template buttons — Order manager / Merchandiser /
  Support — pre-filling the matrix client-side; templates are dashboard
  constants, never DB rows.
- **Shared picker:** the matrix extracts as
  `components/spree/permission-picker.tsx`, driven by `usePermissionCatalog()`
  (GET `/permissions`, store-keyed query). The API-keys page's `ScopePicker`
  becomes a consumer and drops its hardcoded list.
- **PermissionProvider:** refetch `/me` when the active store changes — rules
  and keys are store-scoped. Expose `permissionKeys`.
- **Staff page polish:** role badges get a permission-summary tooltip; the edit
  sheet links to the roles page ("Manage roles").
- **i18n:** all new keys in all six locales (en, de, fr, pl, ar, zh-CN) in both
  `dashboard` and `dashboard-core` as appropriate. Core key labels translate
  client-side; unknown (extension) keys fall back to the server-provided
  localized label.
- **E2E:** `e2e/roles.spec.ts` — create a role with a permission subset, assign
  it, verify the editor round-trip and the guard (non-admin cannot grant beyond
  own keys).

### SDK and type generation

`admin-sdk` gains `roles.create/update/delete` and `permissions.list`; the `Role`
type grows the new attributes. Standard pipeline (typelizer → zod → rswag →
OpenAPI regen); rswag integration specs follow the settings resources' pattern.

## Migration Path

Phase 1 — backend (core + api):

1. Catalog registry + core resource registrations (including `staff`);
   `PermissionSets::*` deleted outright; `assign` raises with the upgrade-guide
   pointer; the install generator's initializer template drops its permission
   lines **in the same change** (the template references the deleted constants).
2. Storefront baseline internalized in `Spree::Ability`; role resolution gated
   to admin-user principals; DB-key activation; Axis A/B extraction
   (`Order#cancel/destroy` guards, `Spree::Role` protection guards) — guard +
   spec first, ability rule removal after.
3. `spree_roles` migration (`description`, `permissions`, `mutable`) + model
   guards + known-key validation; admin role seeded `mutable: false`.
4. `Spree::ApiKey::SCOPES` re-pointed at the catalog; `admin_users` /
   `invitations` / `roles` controllers re-scoped `settings` → `staff`;
   `ScopedAuthorization` generalized to JWT principals (release-note both
   Developer Preview breakages).
5. Roles CRUD + `/permissions` endpoint + `/me.permission_keys`;
   `RoleGrantGuard` key-set comparison; 403 `required_permission` enrichment.
6. Typegen + admin-sdk resources + rswag/OpenAPI.

Phase 2 — dashboard:

7. `usePermissionCatalog` + shared `PermissionPicker`; migrate the API-keys
   scope picker onto it.
8. Roles list + editor pages (with the template picker), nav entry,
   `Subject.Role`; PermissionProvider store-change refetch; staff page polish.
9. Locales ×6; `roles.spec.ts` e2e.

Phase 3 — docs + cleanup:

10. Rewrite `docs/developer/customization/permissions.mdx` around the editor,
    the Admin API, and seeds (with an ability-class swap as the advanced
    escape hatch); write the 6.0 upgrade-guide entry (below).
11. 6.1: evaluate removing CanCanCan from the admin path (the storefront keeps
    it).

No data migration and no bridge. The upgrade-guide entry for hosts coming from
5.x: delete the permission lines from `config/initializers/spree.rb` (they
raise/`NameError` at boot otherwise) and recreate any custom roles in
Settings → Roles — or in seeds — **before deploying**: pre-existing custom role
rows come up with empty `permissions`, so their staff are locked out (fail
closed) until the matrix is filled in.

## Constraints on Current Work

- **No new permission sets, anywhere — and no compatibility shims for them.**
  New capabilities are catalog resource registrations; roles in examples/docs
  are data (editor, Admin API, or seeds). Reviewers should reject PRs adding
  `PermissionSets::` classes, `assign`/`grant`-style role config, or a bridge
  resurrecting any of it — the no-bridge removal is a recorded decision, not an
  oversight.
- **Every new admin-visible model must appear in a catalog entry.** Declaring
  `scoped_resource` (existing rule) is not enough — the models the controller
  authorizes must be in that resource's subject list, or custom roles cannot
  reach the endpoint. Reviewers should reject admin PRs that add subjects no
  entry covers.
- **Grants stay flat.** Record-level conditions belong on models/workflows
  (Axis B) or in a host ability-class swap — never in the catalog.
- **Don't remove the `cannot …, Spree::Role, name: ['admin']` ability rules**
  until the model guards land with specs (extraction order: guard first).
- **New sensitive resources get their own catalog resource** rather than riding
  `settings` — splitting later is a breaking vocabulary change.
- **Storefront authorization must not grow role dependence.** Scope-fetching
  stays the primary enforcement; nothing storefront-side may consult
  `Spree::Role` or the catalog.

## Open Questions

The design questions raised while drafting (staff scope split, editor container,
SCOPES derivation, starter roles, replace-vs-wrap, storefront/B2B boundary,
code-managed roles and the migration bridge — the last two dropped entirely) were
all resolved 2026-08-07 and live in Key Decisions. Genuinely deferred:

- **Per-action keys** (`approve_orders`-style) stay out, reaffirming the 5.5
  scopes decision. Unblocked by: a concrete merchant/partner case resource
  granularity cannot express — revisit both plans together, since the vocabulary
  is shared.
- **Store-scoped role *definitions*** (a role visible in only one store) — roles
  stay global reference data; only assignments are store-scoped. Unblocked by:
  SaaS multi-tenant demand where tenant A's custom roles must be invisible to
  tenant B.
- **Vendor-scoped assignments** — the schema already carries them: a vendor
  staffer is a `RoleUser` with `resource: vendor` (whose store binding derives
  from the vendor's store), invitations accept the same polymorphic resource,
  and the catalog keys are the same vocabulary (a vendor "Catalog manager"
  holds `write_products`). Direction settled 2026-08-08 for the marketplace
  plan to inherit:
  - **Same machinery, separate pools.** Roles gain an *audience* (staff |
    vendor). The operator defines vendor capability tiers in the same editor;
    vendors assign their people to those tiers but do not define roles
    (role names are globally unique — vendor-created roles would collide;
    per-vendor-owned pools are a later need, like per-store definitions).
  - **A vendor-grantable catalog subset.** Vendor roles draw only from
    vendor-safe resources (products, orders, fulfillments, stock, analytics —
    never `settings`, `staff`, `api_keys`); catalog resources carry the
    marker, the editor filters the grid by audience, and assignment /
    invitation guards pair audience with resource type.
  - **The vendor boundary is tenancy, not new keys** (Axis A/B): vendor-panel
    endpoints scope-fetch through `current_vendor` exactly as admin endpoints
    scope through `current_store`. The store-admin half of that boundary is
    **already enforced** — `Spree::Ability#staff_roles` and
    `RoleGrantGuard#caller_roles` match on `resource_type: 'Spree::Store'`, not
    `store_id` alone, so a vendor-resourced assignment (which binds to the
    vendor's store) confers nothing in the store admin. Regression specs cover
    it, including an `admin`-named vendor role. The marketplace plan adds the
    vendor-side ability that reads those assignments.

  Surface and enforcement ship with `6.0-multi-vendor-marketplace.md`, not
  here.
- **Audit trail for role/permission changes** — rides a future admin audit-log
  feature; not blocking the editor.
- **CanCanCan-free admin path** — becomes possible once nothing public speaks
  it; evaluate in 6.1.
