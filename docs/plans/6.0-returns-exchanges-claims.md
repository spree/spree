# Returns, Exchanges & Claims as First-Class Entities

**Status:** Draft
**Target:** Spree 6.0
**Depends on:** Fulfillment & Delivery rework (6.0-fulfillment-and-delivery.md), Split Adjustments (6.0-split-adjustments.md), Normalize state→status (6.0-normalize-state-to-status.md), Service Workflows (6.0-service-workflows.md)
**Successor:** 6.1-order-change-substrate.md — the mutation half of these flows moves onto the shared OrderChange substrate in 6.1 (additive; the models and statuses below do not change)
**Author:** Damian + Claude
**Last updated:** 2026-08-02

## Summary

Replace the deeply nested return/reimbursement chain (ReturnAuthorization → ReturnItem → CustomerReturn → Reimbursement → ReimbursementType → Refund/Exchange) with three first-class entities that directly model the business operations:

- **Return** — customer sends items back, gets a refund
- **Exchange** — customer sends items back, gets different items
- **Claim** — customer reports a problem (damaged, missing, wrong item), may keep the original

Each is a top-level model on Order with its own line items, status, and resolution. No more 6-model-deep nesting. No more exchanges-as-a-reimbursement-type hack.

## Problem

### 1. Six models for a simple return

Today's flow: `ReturnAuthorization` → `ReturnItem` → `CustomerReturn` → `Reimbursement` → `ReimbursementType` → `Refund`. A merchant processing a return touches 6 interconnected models. Each has its own state machine. The mental model is impossible for new developers.

### 2. Exchanges are not a first-class concept

An exchange is modeled as a `ReturnItem` with an `exchange_variant_id`, processed through `ReimbursementType::Exchange`. There's no `Exchange` model — you can't query "all exchanges this month" or "exchanges pending fulfillment" without digging through ReturnItems that happen to have an exchange_variant set.

### 3. Claims don't exist

If a customer receives a damaged item, there's no way to model "we're sending a replacement without requiring the original back." Today merchants either create a manual order or hack it through the return flow (create a return authorization, immediately mark as received, create an exchange). There's no `Claim` entity.

### 4. CustomerReturn is confusing

`CustomerReturn` represents "physical receipt of returned items at the warehouse." It's the bridge between ReturnAuthorization (permission) and Reimbursement (money). But it duplicates validation logic from ReturnItem, has no state machine, and its `order` method derives the order from return_items → inventory_units — not a direct association.

### 5. ReimbursementType STI is over-engineered

Four STI subtypes (Credit, Exchange, OriginalPayment, StoreCredit) that each implement `self.reimburse`. The Exchange subtype delegates to `Spree::Exchange`. The OriginalPayment subtype delegates to `Refund`. The indirection adds complexity without flexibility — the actual reimbursement logic lives in `Refund` and `Exchange`, not in the type classes.

## Current State

| Model | Purpose | State machine? | Lines |
|---|---|---|---|
| ReturnAuthorization | Permission to return | Yes (authorized → canceled) | ~110 |
| ReturnItem | Individual item in a return | Yes (reception_status + acceptance_status) | ~290 |
| CustomerReturn | Physical receipt at warehouse | No | ~95 |
| Reimbursement | Money-back execution | Yes (pending → reimbursed/errored) | ~170 |
| ReimbursementType | STI: how to reimburse | No (strategy class) | ~20 + 4 subtypes |
| Refund | Actual payment reversal | No (after_create: perform!) | ~140 |

## Key Decisions (do not deviate without discussion)

- **Three first-class models:** `Return`, `Exchange`, `Claim`. Each belongs directly to Order.
- **Each has its own line items:** `ReturnItem`, `ExchangeItem`, `ClaimItem`. No shared polymorphic item model — each type has different fields.
- **No state machines. Workflows own every transition.** Each entity carries a
  plain `status` string column with an inclusion validation. Moving a return to
  `received` is `Spree::Returns::Receive.call(...)`, not `return.receive!`. See
  "Why workflows, not state machines" below — this is the load-bearing decision
  in this plan and it is not negotiable.
- **Statuses are configuration, not constants.** `Spree::HasStatus` holds them
  in a `class_attribute` with an additive `add_status`, so a merchant can slot
  in an `inspecting` step without reopening core. Additive only — core
  workflows guard on core statuses, so removal is not offered.
- **No business logic in model callbacks.** Restocking, refunding and creating
  replacement fulfillments are named workflow steps. Nothing happens as a side
  effect of a save.
- **Refund stays.** `Spree::Refund` is the payment-level reversal — it stays as-is. Returns and Claims link to Refunds when money needs to go back.
- **Drop:** `CustomerReturn`, `Reimbursement`, `ReimbursementType` (all four subtypes), `ReturnAuthorization`. Their functionality is absorbed into the three new models.
- **ReturnItem is reused** (renamed from the current model, simplified). ExchangeItem and ClaimItem are new.

## Why workflows, not state machines

An earlier draft of this plan gave each entity a `state_machine :status` block
with the real work hanging off transition callbacks —
`after_transition to: :received, do: :restock_items`,
`after_transition to: :refunded, do: :process_refund`. That is the pattern
6.0 is systematically removing, and it is worth stating plainly why, because
these three models are the last place it would have been reintroduced.

**It hides money movement inside a save.** `process_refund` called from
`after_transition` runs inside the transaction that saves the status column. A
refund is a gateway call. Gateway I/O inside a database transaction is the
exact failure the `Carts::Complete` three-phase design exists to prevent: the
connection is held open across a network round trip, and a timeout leaves the
database and the payment processor disagreeing about reality.

**Transitions cannot take arguments.** `return.receive!` has nowhere to put
"who received it", "which items actually arrived", "two of the three are not
resellable". Every real return is partial. Callback-driven transitions push
that state into instance variables set before the bang method, which is how
the current ReturnAuthorization → CustomerReturn → Reimbursement chain became
unreadable.

**There is no compensation story.** If restocking succeeds and the refund
fails, a state machine has already committed the status change. `Spree::Workflow`
arms `on_flow_failure:` undo steps when the surrounding transaction commits and
unwinds them in reverse.

**Guards are invisible at the call site.** `allow_cancel?` living inside a
transition guard means a caller discovers the rejection as a raised
`StateMachines::InvalidTransition` rather than a `Result` it can inspect.

**The layered-state-machine problem is what we set out to kill.** The stated
purpose of this plan is escaping six interlocking state machines. Replacing six
with three is an improvement in degree, not in kind. Replacing them with
explicit workflows is the actual fix.

The order-level precedent already shipped: `Spree::Orders::Cancel` and
`Spree::Orders::Resume` absorbed what `Order#after_cancel` and `#after_resume`
buried, and the order state machine itself is gone in 6.0
(`6.0-cart-order-split.md`). Returns, exchanges and claims follow the same rule.
`state_machines-activerecord` stays a dependency for legacy models during the
6.0 window; **new models do not get state machines.**

### Status as a plain column

`Spree::HasStatus` ships in core (`app/models/concerns/spree/has_status.rb`)
as the house replacement for state machines. Values live in a
`class_attribute`, not a frozen constant, so extensions can add statuses
without reopening core:

```ruby
module Spree::HasStatus
  extend ActiveSupport::Concern

  class_methods do
    # Declares the valid values and generates predicates + scopes only — no
    # events, no transitions, no callbacks. Transitions belong to workflows.
    def has_status(*values, default:)
      class_attribute :statuses, default: values.map(&:to_s)
      class_attribute :default_status, default: default.to_s

      validates :status, inclusion: { in: -> (record) { record.class.statuses } }

      values.each { |value| define_status_methods(value) }
    end

    # Additive only — core statuses can't be removed (see below).
    def add_status(value, after: nil)
      return if statuses.include?(value.to_s)

      index = after ? statuses.index(after.to_s)&.+(1) : statuses.size
      self.statuses = statuses.dup.insert(index || statuses.size, value.to_s)
      define_status_methods(value)
    end

    private

    def define_status_methods(value)
      define_method("#{value}?") { status == value.to_s }
      scope value, -> { where(status: value.to_s) }
    end
  end
end
```

The default is applied by the creating workflow, never as a database default
(CLAUDE.md: no default values in migrations).

**Why additive only.** `Returns::Refund` guards on `return.received?`. If an
extension could replace the status list and drop `received`, that guard would
silently never pass — returns would stop working with no error at the point of
removal. Adding a status is safe; removing a core one is not, so the API only
offers the safe half.

A custom status needs a custom workflow to move records into it — `add_status`
deliberately takes no `from:`/`to:` graph, since validating transitions
centrally would be a state machine by another name.

```ruby
# Extension: an inspection step between receipt and refund
Spree::Return.add_status(:inspecting, after: :received)

module MyStore
  class Returns::Inspect < Spree::Workflow
    hooks :after_inspect

    def perform(return_record:, inspector:)
      super
      step :ensure_inspectable
      ApplicationRecord.transaction do
        step :mark_inspecting
        run_hooks :after_inspect
      end
      success(return_record.reload)
    end
  end
end
```

## Design Details

### Return

A customer returns items and gets a refund (to original payment, store credit, or gift card).

```ruby
class Spree::Return < Spree.base_class
  has_prefix_id :ret

  include Spree::Core::NumberGenerator.new(prefix: 'RET', length: 9)
  include Spree::NumberIdentifier
  include Spree::Metafields
  include Spree::Metadata

  publishes_lifecycle_events

  belongs_to :order, class_name: 'Spree::Order', inverse_of: :returns
  belongs_to :stock_location, class_name: 'Spree::StockLocation'
  belongs_to :reason, class_name: 'Spree::ReturnReason', optional: true
  # Staff only. Customer-initiated (Store API) records leave this nil —
  # the requester is always order.customer, so no second FK is needed.
  belongs_to :created_by, class_name: Spree.admin_user_class.to_s, optional: true

  has_many :return_items, class_name: 'Spree::ReturnItem', dependent: :destroy, inverse_of: :return
  has_many :refunds, class_name: 'Spree::Refund', as: :originator

  include Spree::HasStatus
  has_status :requested, :approved, :received, :refunded, :canceled, default: :requested

  validates :order, :stock_location, presence: true
  validates :return_items, presence: true

  accepts_nested_attributes_for :return_items, allow_destroy: true

  # Predicates (#received?) and scopes (.received) are generated by has_status.

  # Total refund amount. A pure read — safe on the model.
  def refund_total
    return_items.sum(:pre_tax_amount)
  end
end
```

The model holds associations, validations, scopes and pure reads. Restocking
and refunding live in `Spree::Returns::Receive` and `Spree::Returns::Refund`
(below).

### ReturnItem (simplified)

```ruby
class Spree::ReturnItem < Spree.base_class
  has_prefix_id :ri

  belongs_to :return, class_name: 'Spree::Return', inverse_of: :return_items
  belongs_to :fulfillment_item, class_name: 'Spree::FulfillmentItem'  # renamed from InventoryUnit
  belongs_to :line_item, class_name: 'Spree::LineItem'
  belongs_to :variant, class_name: 'Spree::Variant'

  validates :fulfillment_item, :quantity, presence: true
  validates :quantity, numericality: { greater_than: 0 }

  attribute :pre_tax_amount, :decimal, default: 0
  attribute :resellable, :boolean, default: true
  attribute :quantity, :integer, default: 1

  before_create :set_default_pre_tax_amount

  delegate :order, to: :return

  private

  def set_default_pre_tax_amount
    self.pre_tax_amount ||= line_item.pre_tax_amount / line_item.quantity * quantity
  end
end
```

### Exchange

A customer returns items and gets different items in return (different size, different product).

```ruby
class Spree::Exchange < Spree.base_class
  has_prefix_id :exch

  include Spree::Core::NumberGenerator.new(prefix: 'EX', length: 9)
  include Spree::NumberIdentifier
  include Spree::Metafields
  include Spree::Metadata

  publishes_lifecycle_events

  belongs_to :order, class_name: 'Spree::Order', inverse_of: :exchanges
  belongs_to :stock_location, class_name: 'Spree::StockLocation'
  belongs_to :reason, class_name: 'Spree::ReturnReason', optional: true
  belongs_to :created_by, class_name: Spree.admin_user_class.to_s, optional: true

  has_many :exchange_items, class_name: 'Spree::ExchangeItem', dependent: :destroy, inverse_of: :exchange
  has_one :exchange_fulfillment, class_name: 'Spree::Fulfillment', as: :originator  # the new shipment

  # If there's a price difference, link to a refund or additional payment
  has_many :refunds, class_name: 'Spree::Refund', as: :originator

  include Spree::HasStatus
  has_status :requested, :approved, :received, :fulfilled, :canceled, default: :requested

  validates :order, :stock_location, presence: true
  validates :exchange_items, presence: true

  accepts_nested_attributes_for :exchange_items, allow_destroy: true

  # Price difference: positive = customer owes more, negative = refund due
  def price_difference
    exchange_items.sum { |ei| ei.new_variant_price - ei.original_price }
  end
end
```

Restocking and replacement-fulfillment creation live in
`Spree::Exchanges::Receive` and `Spree::Exchanges::Fulfill`. The price
difference is settled through the internal-vs-gateway branch (see "Refunding:
internal vs gateway" below) — a gateway capture or refund runs as an
`external_step` outside the transaction that writes the status; store-credit
settlement stays inside it.

### ExchangeItem

```ruby
class Spree::ExchangeItem < Spree.base_class
  has_prefix_id :ei

  belongs_to :exchange, class_name: 'Spree::Exchange', inverse_of: :exchange_items
  belongs_to :fulfillment_item, class_name: 'Spree::FulfillmentItem'  # the original item being returned
  belongs_to :line_item, class_name: 'Spree::LineItem'  # original line item

  validates :fulfillment_item, :original_variant, :new_variant, :quantity, presence: true

  attribute :resellable, :boolean, default: true

    line_item.price * quantity

    new_variant.price_in(exchange.order.currency)&.amount.to_d * quantity
  end
end
```

### Claim

A customer reports a problem — damaged, missing, or wrong item. The merchant may send a replacement, issue a refund, or both — without requiring the original item back.

```ruby
class Spree::Claim < Spree.base_class
  has_prefix_id :claim

  include Spree::Core::NumberGenerator.new(prefix: 'CLM', length: 9)
  include Spree::NumberIdentifier
  include Spree::Metafields
  include Spree::Metadata

  publishes_lifecycle_events

  # Configuration, not a frozen constant (same ruling as statuses) — a
  # merchant adds a claim type without reopening core:
  #   Spree::Claim.claim_types += ['late_delivery']
  # Types are pure labels with no per-type behaviour, so extending the
  # list needs no accompanying workflow.
  class_attribute :claim_types, default: %w[damaged missing wrong_item other]

  belongs_to :order, class_name: 'Spree::Order', inverse_of: :claims
  belongs_to :reason, class_name: 'Spree::ClaimReason', optional: true
  belongs_to :created_by, class_name: Spree.admin_user_class.to_s, optional: true

  has_many :claim_items, class_name: 'Spree::ClaimItem', dependent: :destroy, inverse_of: :claim
  has_many :refunds, class_name: 'Spree::Refund', as: :originator
  has_one :replacement_fulfillment, class_name: 'Spree::Fulfillment', as: :originator

  include Spree::HasStatus
  has_status :open, :approved, :resolved, :denied, :canceled, default: :open

  RESOLUTIONS = %w[refund replacement refund_and_replacement].freeze

  validates :order, :claim_type, presence: true
  validates :claim_items, presence: true
  validates :claim_type, inclusion: { in: -> (record) { record.class.claim_types } }
  validates :resolution, inclusion: { in: RESOLUTIONS }, allow_nil: true

  accepts_nested_attributes_for :claim_items, allow_destroy: true

  def refund_total
    claim_items.sum(:refund_amount)
  end
end
```

`Spree::Claims::Resolve` takes the resolution as an argument rather than
reading it off the record, so the caller's intent is explicit; refunds settle
through the internal-vs-gateway branch (see "Refunding: internal vs gateway").

### Refund gains polymorphic originator

```ruby
class Spree::Refund < Spree.base_class
  # Existing: belongs_to :payment
  # Add: polymorphic originator — who triggered this refund?
  belongs_to :originator, polymorphic: true, optional: true
  # originator can be: Spree::Return, Spree::Exchange, Spree::Claim, or nil (manual refund)
end
```

Note: this is the one intentional polymorphic association — Refund needs to know what triggered it, and the originator set is small and closed (3 types + nil). The performance concern from Adjustments doesn't apply here because refunds are infrequent and never bulk-queried in hot paths.

## Workflows

Every transition is a workflow in `app/workflows/spree/`. These qualify for the
workflow tier under `6.0-service-workflows.md` on all three counts: they carry
extension hooks, they perform gateway I/O that must sit outside a transaction,
and they need compensation.

### Returns

| Workflow | Arguments | Hooks | Notes |
|---|---|---|---|
| `Returns::Create` | `order:`, `items:`, `reason:`, `stock_location:`, `created_by:` | `validate`, `after_create` | `validate` is where a store rejects out-of-window returns |
| `Returns::Approve` | `return:`, `approver:`, `note:` | `after_approve` | Optionally generates the return label (`external_step` — carrier API) |
| `Returns::Receive` | `return:`, `items:`, `received_by:` | `before_restock`, `after_receive` | Partial receipt is the normal case: `items:` carries actual quantities and per-item resellable flags |
| `Returns::Refund` | `return:`, `amount:`, `refund_method:` | `before_refund`, `after_refund` | Branches on refund method (below); `on_flow_failure:` reverses the status |
| `Returns::Cancel` | `return:`, `reason:` | `after_cancel` | Restocks nothing; only valid from requested/approved |

```ruby
module Spree
  module Returns
    # Receives physically-returned items. Quantities and resellable flags come
    # from the warehouse, not from what the customer said they would send —
    # partial and damaged receipt is the normal case, not an edge case.
    class Receive < Spree::Workflow
      hooks :before_restock, :after_receive

      # @param return_record [Spree::Return]
      # @param items [Array<Hash>] `[{ return_item:, quantity:, resellable: }]`
      # @param received_by [Object, nil]
      def perform(return_record:, items:, received_by: nil)
        super

        step :ensure_receivable
        step :validate_quantities

        ApplicationRecord.transaction do
          step :record_receipt
          run_hooks :before_restock
          step :restock_resellable_items
          step :mark_received
        end

        run_hooks :after_receive
        return_record.publish_event('return.received')
        success(return_record.reload)
      end

      private

      def ensure_receivable
        failure(return_record, :not_approved) unless return_record.approved?
      end

      def restock_resellable_items
        items.each do |item|
          next unless item[:resellable]

          return_record.stock_location.restock(
            item[:return_item].variant, item[:quantity], return_record
          )
        end
      end
    end
  end
end
```

### Refunding: internal vs gateway

Not every refund is a network call. Store credit and gift cards are internal
ledger writes, so forcing them through `external_step` would push a pure
database write outside the transaction that marks the return refunded — a crash
between the two would leave a refunded return with no credit issued.
`Returns::Refund` branches:

```ruby
ApplicationRecord.transaction do
  run_hooks :before_refund               # veto point — before any money moves
  step :mark_refunded
  step :issue_internal_credit if internal_refund?
end

external_step :refund_at_gateway, on_flow_failure: :revert_refunded unless internal_refund?
```

`internal_refund?` covers store credit and gift cards. The precedent is
`Orders::Cancel#settle_payments`, which already treats gift-card-covered
payments differently from gateway payments. `Claims::Resolve` and
`Exchanges::Fulfill` use the same branch when settling money.

### Exchanges

| Workflow | Hooks | Notes |
|---|---|---|
| `Exchanges::Create` | `validate`, `after_create` | Validates replacement variants are purchasable |
| `Exchanges::Approve` | `after_approve` | |
| `Exchanges::Receive` | `before_restock`, `after_receive` | Same partial-receipt shape as returns |
| `Exchanges::Fulfill` | `before_settle`, `after_fulfill` | Creates the replacement fulfillment, then settles `price_difference` as an `external_step` |
| `Exchanges::Cancel` | `after_cancel` | |

### Claims

| Workflow | Hooks | Notes |
|---|---|---|
| `Claims::Create` | `validate`, `after_create` | Store API entry point; `validate` gates self-service claims |
| `Claims::Approve` | `after_approve` | |
| `Claims::Resolve` | `before_settle`, `after_resolve` | Takes `resolution:` explicitly; refund settles via the internal-vs-gateway branch, replacement fulfillment is in-transaction |
| `Claims::Deny` | `after_deny` | |
| `Claims::Cancel` | `after_cancel` | |

### Why `validate` hooks matter here

Return eligibility is the single most-customized rule in commerce — 30-day
windows, final-sale categories, per-customer-group policies, region-specific
consumer rights. A `validate` hook on `Returns::Create` and `Claims::Create` is
the seam that keeps those out of core. It pairs with the EU consumer-rights
withdrawal period in `5.4-6.0-eu-legal-compliance.md`.

## Migration Path

### Phase 1: Create new tables

Per CLAUDE.md migration rules: no foreign key constraints, `null: false` on
required columns, JSON columns guarded with `respond_to?(:jsonb)`. Defaults
(refined 2026-08-02): **status/string columns get no database default** — the
creating workflow sets the status; **integer and decimal columns do carry
defaults** (`quantity` 1, amounts 0), so a raw insert can never produce a null
quantity or amount. Metadata is a **single `metadata` column** — the new 6.0
tables drop the legacy public/private split (`metadata` is already the primary
API param on carts).


## Constraints on Current Work

- **Don't add new features to ReturnAuthorization, CustomerReturn, or Reimbursement.** They're being replaced.
- **Don't add new ReimbursementType subtypes.** The STI hierarchy is being dropped.
- **New return/exchange logic should be designed for the three-model pattern.** Think "Return with ReturnItems" not "ReturnAuthorization with ReturnItems through CustomerReturn."
- **Refund stays as-is.** It's the payment-level primitive. Returns, Exchanges, and Claims create Refunds when money needs to go back.
- **No state machine on any new model in this area.** Plain `status` string,
  inclusion validation, transitions through workflows. This generalizes beyond
  returns — see `6.0-service-workflows.md` → "State machines".
- **Don't persist a financial preview.** Showing an admin what a partial return
  will refund is computed in memory and discarded; the persisted preview
  substrate arrives in `6.1-order-change-substrate.md`.

## Resolved Questions

1. **Store API return initiation.** Both Store API (self-service) and Admin API. Customers can initiate returns and claims; exchanges may require admin approval depending on store config. Self-service returns are the modern standard — backoffice-only is legacy.

2. **Return shipping labels.** Yes. Return gains `generate_label` which delegates to the FulfillmentProvider interface (from 6.0-fulfillment-and-delivery.md). E.g., `return.generate_label` calls EasyPost to create a prepaid return label. The label URL is stored on the Return record. Add `return_label_url` column.

3. **Partial returns/exchanges.** No separate "case" or "ticket" model. All three entities belong to Order — `order.returns`, `order.exchanges`, `order.claims` gives the full picture. The admin UI shows a unified "Post-sale" tab on the order page listing all three chronologically. If correlation is needed (e.g., "this claim was filed because the exchange arrived damaged"), use the `metadata` JSON column.
