# Store Context & First-Run Setup

**Status:** In Progress (Phases 1–2 implemented 2026-08-13; 6.1 cleanup pending)
**Target:** Spree 6.0
**Depends on:** `6.0-platform-auth.md` (auth stack), `5.5-admin-api-key-scopes.md` (shipped), `6.0-admin-rbac.md` (role/membership model)
**Author:** Damian Legawiec + Claude
**Last updated:** 2026-08-13

## Summary

Two related gaps in the headless stack. First, **store context is resolved wrong everywhere**: the v3 API resolves every request to `Spree::Store.default` — the configured finder (`Spree::Stores::FindDefault`) accepts the request hostname and discards it, the admin SDK sends `X-Spree-Store-Id` on every request but no server code reads it, and API keys are validated *against* the already-resolved store instead of *selecting* it. The dashboard is fully multi-store in its URL structure (`/$storeId/...`, store switcher) and the backend silently ignores all of it. Second, **installation mints a dummy admin** (`spree@example.com` / `spree123`) with hardcoded credentials duplicated across three codebases, and there is no way to create an admin account or a store outside seeds and invitations. This plan makes store context explicit and credential-derived (no hostname resolution anywhere), and replaces the dummy-admin seed with a first-run setup flow: a one-time, token-guarded screen in the dashboard that creates the first admin account and names the store — the Medusa-style onboarding.

## Key Decisions (do not deviate without discussion)

- **No hostname-based store resolution in the APIs — ever.** (2026-08-13) Store context is explicit and credential-derived: the publishable key selects the store on the Store API, `X-Spree-Store-Id` (validated against role membership) selects it on the Admin API, and a secret key is bound to its store. Hostname resolution was a requirement of the server-rendered era (admin + storefront per subdomain) and is retired with it. `Spree.current_store_finder` remains as an override point, and `FindDefault` remains the single-store fallback.
- **The key selects the store; the store never validates the key.** (2026-08-13) Today's flow is inverted: `current_store` resolves first (to the default store) and the key is nulled on mismatch. New flow: authenticate the credential, then set `Spree::Current.store` from it. This implements what the auth docs already claim ("publishable key identifies the store").
- **Admin API honors `X-Spree-Store-Id`.** (2026-08-13) JWT staff sessions resolve the requested store by prefixed ID and are checked for membership against *that* store (the check exists today but runs against the default store, so the store switcher silently lies). Secret keys ignore the header for selection — the key's own `store_id` wins; a conflicting header is a 403.
- **First-run setup replaces the dummy admin.** (2026-08-13) When no admin user exists, the dashboard shows a setup screen (create admin account + name the store) instead of login, backed by one-time endpoints under `auth/`. The `Seeds::AdminUser` dummy defaults are removed: the seed only creates an admin when `ADMIN_EMAIL`/`ADMIN_PASSWORD` are explicitly set (CI, worktrees, and scripted installs keep working by passing them).
- **The setup endpoint is guarded by a one-time setup token in every environment.** (2026-08-13) The zero-admins gate alone leaves a freshly deployed instance claimable by whoever finds the URL first. The token lives on `Spree::Store` via `has_secure_token :setup_token` (amended 2026-08-13: no separate digest table — plaintext at rest matches the invitation-token posture, and only means anything while the database holds nothing but seed data). Generated at store creation, printed by the installer and reprintable by `bin/rails spree:setup:token` (`ROTATE=1` issues a fresh one), required by the setup endpoint, cleared on completion, and dead permanently once the first admin exists. Same rule in development — dev tooling seeds explicit credentials instead, so the setup flow never engages there unless you want to exercise it.
- **No general store CRUD in the OSS Admin API.** (2026-08-13) First-run setup configures the one store; creating *additional* stores is out of scope for open core (multi-store provisioning is an enterprise concern). The singular `resource :store` (`show`/`update` on `current_store`) stays as-is.
- **First-run setup adopts and renames the seeded store; it never creates one.** (2026-08-13) `Seeds::Stores` keeps creating the default store during `db:seed` (dozens of downstream seeds depend on it existing), and the setup flow renames/configures it. One code path for store creation — the seed — and setup stays a pure "claim this installation" step.
- **Admin API requests without the header keep resolving to the default store through 6.0, removed in 6.1.** (2026-08-13) The SDK always sends the header, so this only affects hand-written curl/scripts against a single-store install — where the default store is the right answer anyway. A deprecation warning logs when a JWT request omits the header; 6.1 makes it required.

## Design Details

### 1. Store API: publishable key selects the store

`Spree::Api::V3::ApiKeyAuthentication#authenticate_api_key!` changes from

```ruby
@current_api_key = current_store.api_keys.active.publishable.find_by(token: extract_api_key)
```

to a global lookup followed by context assignment:

```ruby
@current_api_key = Spree::ApiKey.active.publishable.find_by(token: extract_api_key)
# then: Spree::Current.store = @current_api_key.store
```

`current_store` in the Store API base becomes an alias for the key's store. Channel binding (`5.6-store-channel-context-and-key-binding.md`) is unaffected — the bound channel already belongs to the key's store. Guest cart tokens keep their existing store-scoped lookups, which now scope against the key-derived store.

### 2. Admin API: `X-Spree-Store-Id` header

A `StoreContext` concern in the v3 Admin base controller resolves `current_store` in this order:

1. **Secret key** → `@current_api_key.store`. If the header is also present and names a different store → 403.
2. **JWT + header** → `Spree::Store.find_by_prefix_id(header)`; unknown ID → 404. `require_store_membership!` then runs against this store (today it runs against the default store — the actual bug behind the inert store switcher).
3. **JWT, no header** → `Spree::Store.default` + deprecation log line (removed in 6.1).

`Spree::Current.store` is set from the result before any authorization runs, so every `current_store.<association>` lookup, Ransack scope, and cache key downstream is against the requested store. No dashboard changes are needed — the SDK already sends the header and the routes already carry `$storeId`. Two small SPA cleanups ride along: `_authenticated/index.tsx` drops its literal `'default'` fallback ID, and `store-provider.tsx`'s query becomes honest (the `storeId` key now actually varies the response).

### 3. First-run setup flow

**Endpoints** (unauthenticated, rate-limited like login, mounted under `auth/` so the refresh-cookie path matches — same shape as invitation acceptance):

- `GET /api/v3/admin/auth/setup` → `{ "setup_required": true | false }`. True only while zero admin users exist. Safe to expose: it leaks one boolean that is also self-evident from a fresh install.
- `POST /api/v3/admin/auth/setup` → params: `setup_token`, `email`, `password`, `first_name`, `last_name`, `store_name`, optional `currency`/`country_iso`. Guards, in order: admin count is zero; the submitted token matches the store's `setup_token` (`secure_compare`), re-checked under a lock on the store so concurrent submissions cannot both spend it. Effects, in one transaction: create the admin user, `add_user` with the `admin` role on the default store, rename/configure the store, clear the `setup_token` column. Then issue the refresh cookie + JWT exactly like `InvitationAcceptancesController` and return the admin-user payload. Any later call 404s (setup no longer required).

**Setup token mechanics.** The token is a `has_secure_token :setup_token` on `Spree::Store` — generated when the seed creates the default store, so a repeated `db:seed` reprints the same URL. `Store#setup_url` builds it on top of `Spree::Stores::DashboardUrl`, the single resolver for "where is the dashboard" now shared by the setup link, invitation emails and the SSO callback: `Spree::Config[:dashboard_url]` (env-backed, see below) → the deprecated `admin_url` → **this app's own `/dashboard` mount** when `spree_dashboard` is installed with a build to serve → the Vite dev server in development → the store's own URL.

**The chicken-and-egg problem the mount solves (2026-08-13).** The setup link is printed by `db:seed`, which runs *before* anything is serving the dashboard — and under `create-spree-app` it runs inside a container, where the host's Vite port is unknowable. Two answers, one per install path. A plain Rails app (`spree:install`, `template.rb`) links at its own `/dashboard`, which the app serves itself the moment it boots — no second process, which is why the mount outranks the Vite guess: it is a fact about the deployment rather than an assumption about the developer's setup. The CLI keeps only the **token** from the seed output and rebuilds the URL against the dashboard it is about to launch (dev server if runnable, else the API's bundled mount), since it alone knows the host-side ports.

**App configuration reads the environment (2026-08-13).** `RuntimeConfiguration.preference` takes an `env:` option, so an app-level setting can be configured from the deployment environment instead of Ruby, with precedence explicit value → env var → coded default. `dashboard_url` is the first adopter (`SPREE_DASHBOARD_URL`) because the setup link is printed by `db:seed`, before anyone can reach a console to set a preference, and every worktree and container has a different dashboard origin (worktree provisioning writes it into `server/.env`). `admin_url` is deprecated in its favour — both named the same origin, and the split was a legacy-admin artifact. The option is deliberately limited to `Spree::Config`; per-store behavior belongs in Store preferences, which one global env var cannot express. `bin/rails spree:setup:token` prints the current link (generating one for stores predating the column; `ROTATE=1` rotates). The setup endpoint compares with `secure_compare` behind the zero-admins gate and clears the token when setup completes, so the flow is dead on every install that seeds credentials explicitly. Plaintext at rest, deliberately — the same posture as invitation tokens, and the token only works while the database contains nothing but seed data.

**Dashboard.** A fifth unauthenticated route, `/setup`: reads `?token=`, calls the lookup endpoint, renders the account + store form (same form/error conventions as invitation acceptance), and on success lands in `/$storeId`. The login page checks `setup_required` and links to `/setup` when true (covering the "opened /login first" path — they'll still need the token from the install output).

### 4. Seed and tooling changes

- `Seeds::AdminUser`: dummy defaults removed. Creates an admin only when `ADMIN_EMAIL` **and** `ADMIN_PASSWORD` are both set; otherwise defers to the setup-token flow. The existing table-wide `count.zero?` guard stays (it is the same gate the setup flow uses).
- `@spree/cli` `init`: prompts for admin email/password (Medusa-style) with a `--no-admin` escape that prints the setup URL instead; deletes the hardcoded `DEFAULT_ADMIN_EMAIL`/`DEFAULT_ADMIN_PASSWORD` constants — the success card echoes whatever was actually used.
- `spree/template.rb`, `scripts/worktree/setup.sh`, e2e global setup, Docker scripts: pass `ADMIN_EMAIL`/`ADMIN_PASSWORD` explicitly (worktrees and e2e keep `spree@example.com` / `spree123` as their *explicit* choice — dev docs stay true).
- `spree:cli:create_admin` rake task: made idempotent (find-or-create by email), fails loudly when the `admin` role is missing instead of silently minting a role-less user.

### 5. Store model fixes (ride-along)

- `Spree::Store#set_default_code` currently defaults `code` to the literal `'default'`, which collides with the unique index the moment a second store is created (the enterprise provisioning path hits this immediately). Fix: derive from `parameterize(name)` with a numeric suffix on conflict; keep `'default'` only for the very first store for back-compat with tooling that references it.
- `ensure_default_exists_and_is_unique` keeps its demote-others behavior (correct for a single-default invariant) but gains a spec pinning it, since provisioning code will lean on it.

## Migration Path

1. **Phase 1 — store context.** Key-selects-store inversion in `ApiKeyAuthentication`; `StoreContext` concern in the Admin API base honoring `X-Spree-Store-Id`; membership check against the requested store; deprecation log on header-less JWT requests; SPA fallback cleanups. No client changes required — the SDK already sends everything. **Shipped 2026-08-13** (`KeyStoreContext` + `Admin::StoreContext` concerns; dashboard `setStore` moved to the `$storeId` route's `beforeLoad` so the header is set before any query fires). Two token-in-URL public endpoints resolved their store context explicitly: digital downloads derive the store from the globally unique link token (the token IS the credential), and data feeds serve the default store (slugs are only unique per store; matches the old finder's effective behavior — a store-carrying feed URL shape is future work).
2. **Phase 2 — first-run setup.** `setup_token` column on `spree_stores`, seed changes, the two `auth/setup` endpoints, the `/setup` dashboard route, CLI/template/scripts updates, `spree:setup:token` rake task. **Shipped 2026-08-13** (`has_secure_token :setup_token` on Store; `Seeds::AdminUser` env-only; `spree:cli:create_admin` made idempotent; `spree init` prompts for credentials, `spree dev` reads the remembered email; create-spree-app no longer prints dummy credentials; worktree template passes explicit credentials).
3. **6.1 cleanup.** Header becomes required for JWT Admin API requests; `FindDefault`'s ignored `url:` parameter is dropped from the finder contract.

## Constraints on Current Work

- **Never assume `current_store == Spree::Store.default`** in Admin API controllers, serializers, or jobs — after Phase 1 the requested store can be any store the caller has a role on. The existing rule (every lookup through `current_store.<association>`) is what makes this safe; violations are now cross-store leaks, not just IDOR risks.
- **No new hostname-based store logic anywhere** — don't read `request.host`/`SERVER_NAME` to pick a store, don't add URL-matching to finders.
- **Store-touching cache keys must include the store id** by construction (`cache_key_with_version` on the store, or an explicit store-id component), never a bare global key.
- **New scripts and tooling must pass `ADMIN_EMAIL`/`ADMIN_PASSWORD` explicitly** instead of relying on the dummy defaults, which are removed at 6.0.
