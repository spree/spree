# Adyen Payment Provider

**Status:** Design finalized — nothing built; open questions settled 2026-11-16
**Target:** Spree 6.0 (next patch release)
**Depends on:** `6.0-payment-gateways-monorepo.md` (the provider gem shape; this plan is its Migration Path step 2), `6.0-paypal-payment-provider.md` (the latest port, followed wherever Adyen allows), payment sessions in core, `6.0-money-correctness.md` (`accepts_money_amounts`), `6.0-json-preferences.md` (internal and `:password` preferences), `6.0-maintenance-tasks.md` (upgrade steps), `6.0-normalize-state-to-status.md` (`has_status`), `5.6-6.0-single-store-promotions-payment-methods.md` (one store per payment method)
**Author:** Łukasz Adamczyk
**Last updated:** 2026-11-16
**Tracking:** Linear V-3819 · GitHub spree/spree#15229

## Summary

Bring Adyen to Spree 6 as an optional provider gem at `spree/providers/adyen`,
publishing the existing gem name `spree_adyen` and released with Spree,
because 6.0 is out and the standalone
[`spree/spree_adyen`](https://github.com/spree/spree_adyen) gem (0.11.0, built
for 5.4–5.6, depending on `spree_admin`) does not run on it, so a merchant
taking Adyen on 5.x cannot upgrade. This is a rewrite of that gem's
payment-session half on the 6.0 contract, not a copy: it predates the
cart/order split, the single `metadata` column, money amounts,
`settle_payment!` and the rule that providers never decorate core models, and
on its payment-session path it never records the PSP reference Adyen needs to
capture, cancel or refund a payment. The first release takes payments through
Adyen's Sessions flow and Drop-in, offering every method the merchant enables
in Adyen that pays a session in one payment, honors the store's capture
setting, saves cards for signed-in customers who ask, and configures its own
webhook. Core gains two additive changes: the webhook endpoint stops dropping
the `metadata` a gateway's parser returns, and a gateway may now answer a
capture, void or refund with "accepted, the outcome follows by webhook", which
Adyen requires. That answer leaves the payment `requested` or the refund
`requested` until the webhook settles it; gateways that answer at once, such
as Stripe and PayPal, never take that path. The Next.js storefront already
renders Drop-in; the classic Rails storefront, the legacy admin, the legacy
webhook endpoint and Storefront API v2 stay behind, and the old repository
becomes a 5.x maintenance branch.

## Key Decisions (do not deviate without discussion)

1. **Ships in the next 6.0 patch release, core changes included** (decided
   2026-11-16). Adyen merchants cannot upgrade to 6.0 until the gem exists,
   and both core changes (Key Decisions 7 and 8) are additive. The new status
   columns are added empty and backfilled by a core upgrade task, and an
   empty status reads as completed until then. So a gateway that does not
   answer `requested?` sees no change in behaviour. 6.0 patches have shipped
   migrations before (6.0.1–6.0.4 added four). Waiting for 6.1 was rejected
   for that reason.
2. **Same shape as Stripe and PayPal.** Directory `spree/providers/adyen`, gem
   `spree_adyen`, `s.version = Spree.version`, exact pin on `spree_core`,
   Rails engine registering the gateway in a late `after_initialize`. The
   `spree` meta gem does not depend on it; the `spree_admin` dependency is
   dropped. Adyen's official `adyen-ruby-api-library` is pinned `~> 12.0`
   (12.0.0, 2026-08-18). It calls Checkout API v72, whose session update Key
   Decision 11 relies on (`update_session`), and its webhook HMAC check
   compares in constant time. Since 11.0 it raises typed exceptions for 400,
   422 and 5xx responses, where 10.x returned them (the 5.x gem allowed
   `>= 10.3, < 12`).
   - **The gem requires Ruby 3.3** (decided 2026-11-16):
     `s.required_ruby_version = '>= 3.3'`, while core and the other gems stay
     at `>= 3.2`. 12.0 requires 3.3, and Ruby 3.2 reached end of life on
     2026-03-31. CI runs Ruby 4.0 and releases build on 3.3, so neither
     changes. The `spree` meta gem does not depend on this gem, so core's
     floor does not move.
   - **Accepted trade-off:** a store on Ruby 3.2 moves to 3.3 before adding
     Adyen. The upgrade guide says so.
   - **Rejected: staying on 11.3**, calling v72 through
     `Adyen::Checkout.new(client, 72)` and `call_adyen_api`. It works on 3.2,
     but leaves the gem on a library line Adyen no longer develops.
3. **Every stored class name is kept**: `SpreeAdyen::Gateway`,
   `Spree::PaymentSessions::Adyen`, `Spree::PaymentSetupSessions::Adyen`, and
   the 46 `SpreeAdyen::PaymentSources::*` names 5.x wrote. These live in
   `type` columns, so an upgrading installation keeps its rows. The wire name
   stays `adyen` (`Spree::Gateway.api_type`, the storefront's mapping).
   - **Which names.** 5.x shipped 60 source files: 59 classes and an
     abstract base. Released 5.x code created sources only through its
     variant table (45 classes) and `Unknown`, so only those 46 names can be
     stored. Its other 13 classes never had a row and are not ported:
     `ApplePay` (in a pre-release test factory only), `Bcmc`, `BcmcMobile`,
     `EbankingFi`, `EftDirectdebitCa`, `EftposAustralia`, `Elo`, `Givex`,
     `GopayWallet`, `GrabpayPaylater`, `Hipercard`, `Kakaopay` and
     `KcpNaverpay`.
   - **How they are declared** (decided 2026-11-16). Each stored name is an
     explicit one-line subclass of one shared base, as Stripe declares its 9
     per-method classes, and new payments pick their class from the variant
     table (Design Details, Payment sources). In 6.0 a source class only
     names stored rows and gives the orders CSV export its display name
     (`Payment#display_source_name`, such as "Klarna"); no API or dashboard
     reads it.
   - **Rejected alternatives.**
     - Declaring the names from a list with `const_set` in the namespace file
       relies on metaprogramming and leaves the names ungreppable.
     - PayPal's shape, one class for new payments with the method in
       `metadata`, would leave two row shapes, and core's CSV display name
       would have to ask the instance.
     - Collapsing every name into one class needs an upgrade step to rewrite
       historical rows. Until it ran, loading those sources would raise
       `SubclassNotFound` and break the orders' pages.
   - **Accepted trade-off:** about 48 small files are kept for good (the 46
     names, the base and the card source). A new Adyen method shows as
     `Unknown` in the CSV until a line is added for it.
4. **Only the payment-session path is ported.** The gem implements the
   contract: `create_payment_session`, `update_payment_session`,
   `complete_payment_session`, `cancel_payment_session`,
   `create_payment_setup_session`, `complete_payment_setup_session`,
   `parse_webhook_event`, the session's settlement hooks, and the money
   verbs. Core changes for Key Decisions 7 to 9. The 5.6 → 6.0 manifest gains
   the gem's two upgrade steps and core's status backfill.
5. **Sessions flow with Drop-in; one session, one payment.** A session settles
   only when Adyen reports exactly one payment for it, authorised or pending
   (`Received` / `Pending`), for the session's amount and currency. That
   holds whether the report is the session result, a redirect's
   `/payments/details` result or an `AUTHORISATION` webhook. A report that
   fails this check settles nothing. Complete raises a `GatewayError` naming
   the problem and leaves the session open, and `parse_webhook_event` treats
   the delivery as one it does not act on. The methods on offer are the ones
   the merchant enables in Adyen's Customer Area; the gem has no per-method
   code beyond its variant table. Partial payments, where Drop-in pays one
   session with a gift card and then another method, are out of scope: core
   links a session to exactly one payment, through `response_code`. The
   storefront does not register Adyen's gift card component. A client that
   offers one anyway is unsupported: a partial payment never matches the
   session's amount, so it never settles, and the merchant handles it in
   Adyen.
6. **A session payment's `response_code` is always its Adyen session id; the
   PSP reference lives in its `metadata`.** Core links a session to its
   payment through `response_code = external_id`, and `handle_response`
   overwrites `response_code` with the authorization any gateway call returns.
   So `authorize`, `purchase`, `capture`, `void` and `cancel` return the
   session id as their authorization. `credit` returns the refund's own PSP
   reference, which core stores as the `Spree::Refund`'s `transaction_id`, not
   on the payment. The PSP reference of the authorised payment is recorded as
   `metadata['adyen_psp_reference']` at settlement; capture, void, refund and
   the dashboard link read it from there. Payments taken by 5.x's legacy
   checkout keep the PSP reference as their `response_code`, since no session
   links to them (Upgrading from the 5.x gem). On its payment-session path,
   the 5.x gem created the payment with the session id and never recorded the
   PSP reference, so its capture, cancel and refund requests sent a session
   id where Adyen expects a PSP reference. They only worked on the legacy
   webhook path, which overwrote `response_code` with the PSP reference.
7. **Core carries a gateway's webhook `metadata` through to settlement.**
   `PaymentMethod#parse_webhook_event` is documented to return
   `{ action:, payment_session:, metadata: }`, and `Payments::HandleWebhook`
   takes `metadata:` and passes it to `settle_payment!`. But the webhooks
   controller has enqueued `HandleWebhookJob` with only the payment method,
   the action and the session id since webhooks became asynchronous (#13776),
   so the metadata never arrives. The controller now passes it to the job and
   the job to the workflow. It defaults to `{}`, so jobs enqueued before the
   deploy still run, and values must be JSON-safe with string keys, which the
   contract comment will say. Stripe and PayPal return no metadata and are
   unaffected. Adyen needs it: when a buyer never comes back from a redirect,
   the `AUTHORISATION` webhook is the only place the PSP reference is
   reported, and Adyen has no call that returns it from the session id alone
   (`GET /sessions/{id}` requires the `sessionResult` only the buyer's browser
   holds). Writing the reference from inside `parse_webhook_event` was
   rejected because parsing an event must not act on it, the reasoning of
   PayPal's Key Decision 12.
8. **Captures, voids and refunds wait for Adyen's answer, and core learns how
   to wait** (decided 2026-11-16). Adyen answers every capture, cancel and
   refund request with `status: received`, a value it "will always have".
   Its docs say "Wait for the CAPTURE webhook to learn the outcome of the
   request" and "Wait for the REFUND webhook to learn the outcome of the
   refund request". Even a success can be followed, rarely and days later,
   by `CAPTURE_FAILED` or `REFUND_FAILED`. Adyen's partner integration
   checklist requires webhooks that "update other systems that are
   integrated with the payments flow". The 5.x gem waited for captures and
   voids through decorator statuses (`capture_pending`, `void_pending`;
   spree_adyen#36, V-3287) but treated refunds as done on `received`. 6.0
   forbids the decorator, so core gains the waiting state (Design Details,
   Core change: asynchronous modifications):
   - a gateway may answer with `Spree::PaymentResponse#requested?` (named
     after the status it leads to, decided 2026-11-16; `pending?` was
     rejected because a `pending` payment already means "authorized, not
     captured");
   - that leaves the payment `requested` or the refund `requested`;
   - webhook outcomes addressed to a capture, a payment or a refund complete
     or fail them, late failures included.
   
   Only a gateway that answers `requested?` takes this path. Stripe, PayPal
   and store credit never do, so their flows run as they do today. Bogus does
   only in an opt-in mode, off by default, that exists so core can test the
   path without Adyen (Design Details, Testing without Adyen); every existing
   spec and seed that uses it is unaffected. The others see new vocabulary,
   not new behaviour: a status value on payments, a status on refunds and on
   capture events, and optional webhook outcomes.
   
   Counting a capture or refund as done on `received`, which needs no core
   change, was rejected: it contradicts Adyen's guidance and the partner
   checklist, and a failed capture or refund would read as done in Spree.
   Waiting for payments only, as 5.x did, was rejected because refund
   failures would then never reach Spree. **Accepted trade-off:** a payment
   or refund whose outcome never arrives stays `requested`, with no timeout
   and no staff override. Adyen retries an undelivered webhook for up to 30
   days, and the docs tell merchants to check a long wait in Adyen.
9. **One flat `requested` status; whether a capture or a void was requested
   is derived from the payment's data** (decided 2026-11-16). `has_status`
   values are configuration that may only grow (decisions.md, "Statuses are
   configuration, not frozen constants"). `PaymentStatus` is an open list in
   the API, so clients already accept a value they do not know. So core
   declares `requested`, between `pending` and `completed`, rather than
   having the gem `add_status` it: the order roll-up and the workflows'
   guards must know what it means. A capture request writes a capture event
   in status `requested`, carrying Adyen's reference for that capture; a void
   request writes nothing. So `Payment#requested_action` answers `capture`
   when the payment is `requested` and has a requested capture event, and
   `void` otherwise. The Admin API exposes it, and the dashboard shows
   "Capture requested" or "Void requested". The webhook names which one
   finished (`CAPTURE` or `CANCELLATION`), so the outcome never needs the
   status to say it. Reusing `pending` was rejected: it already means
   "authorized, not captured", so a payment waiting on a capture would look
   uncaptured, and staff or dispatch would capture it again. Reusing
   `processing` was rejected because it means "a workflow is in flight" and
   counts as neither authorized nor captured. Split `capture_pending` /
   `void_pending` statuses, which 5.x used, were rejected: the action is
   derivable, and one value means one roll-up rule and one guard.
   - **5.x payments still waiting at upgrade are marked done** (decided
     2026-11-16). A 5.x payment in `capture_pending` becomes `completed`,
     with a capture event, and one in `void_pending` becomes `void`. Each is
     logged by payment id. They cannot wait for Adyen: 5.x acknowledged their
     outcome webhooks without acting on them, so Adyen will not send them
     again, and Adyen has no API that reads a payment's status.
   - **Accepted trade-off:** for these legacy rows only, Adyen's acceptance
     is counted as done. A rare earlier failure stays wrong until the
     merchant checks the logged ids in Adyen. Turning them into `requested`
     with a staff override was rejected: it needs a new back-office action in
     a patch release for a one-off cleanup.
10. **The store's capture setting is honored, except for methods Adyen
    captures at once** (amended 2026-11-16).
    - **Capture at checkout.** The session sends no capture flag. Adyen
      captures by its account's capture delay, immediate by default, and the
      session settles as captured.
    - **Capture on dispatch or manually.** The session sends
      `additionalData.manualCapture`, which overrides the Customer Area
      setting. It settles as authorized, and Spree captures later, waiting
      for Adyen's answer (Key Decision 8).
    - **Which one applies.** It is stored in the session's `external_data` at
      creation, so a webhook is mapped by what the session asked Adyen for,
      not by the method's setting when the webhook arrives.
    - **Methods that cannot capture later.** Some methods do not support a
      separate capture, iDEAL among them, so Adyen takes the money at once
      whatever the session asked. A payment by such a variant settles as
      captured whatever the setting, so the order reads paid, which is true.
      The variant table carries the flag. It is seeded from 5.x's own split
      for methods other than cards: 5.x listed `capture` among a source's
      `actions` for 12 of its 59 classes and left it out for the rest.
      Only its legacy admin read that, and its settlement still pended such
      payments. Cards, and the card wallets (Apple Pay, Google Pay), can be
      captured later. 5.x stored them as `Spree::CreditCard`, whose actions
      come from core and include capture; Apple Pay fell through to
      `Unknown`, which offered none, a 5.x gap. Each entry is checked against
      Adyen's per-method pages during implementation.
    - **Accepted trade-off: authorisations expire.** Adyen expires
      authorisations for the global card schemes after 28 days, and schemes
      may expire them earlier; a capture after that fails with Adyen's
      reason. Authorisations are not extended, the same as Stripe and PayPal.
    - **Accepted trade-off: the table needs upkeep.** A variant missing from
      the table settles as authorized, and its later capture fails with
      Adyen's reason.
    - **Adyen's own capture delay.** The docs tell merchants to leave it at
      immediate: with a delay there, Spree records as captured at checkout
      money Adyen takes days later.
11. **Sessions open unpayable and become payable only through Spree, so
    canceling one locally really cancels it** (amended 2026-11-16). No Adyen
    API cancels a session; it expires (one hour by default, at most 24).
    Adyen's own answer is to refund duplicate payments. Checkout v72 adds
    `payable`. A session created with `payable: false` takes no payment until
    the server sends `PATCH /sessions/{id}` with the final amount and
    `payable: true`, and after that it cannot be changed. Adyen tells
    integrations to send that call from Drop-in's `beforeSubmit` callback,
    with an amount the server holds ("Do not get the updated amount from the
    client"). So:
    - **Create** sends `payable: false`. It refuses when the cart already has
      a completed Adyen session. It cancels the cart's open Adyen sessions
      locally, with no Adyen call, before opening a new one.
    - **Update** with a different amount, while the session is not yet
      payable, changes Spree's amount only; Drop-in shows the new figure
      through its own `update`. Once the session is payable, a different
      amount raises a `GatewayError` telling the client to create a new
      session.
    - **Submit.** The storefront's `beforeSubmit` calls the update endpoint
      with `external_data.submit`. The gem makes the session payable at the
      amount Spree holds for it, never one sent with the call. It records
      `payable` in `external_data` and returns the new `session_data`, which
      the storefront hands to Drop-in's `actions.resolve`. A session that is
      no longer `pending` (canceled, completed, failed or expired) is refused
      with a `GatewayError`. A session already payable is answered with its
      stored `session_data`, so a buyer retrying after a refused card keeps
      paying the same session.
    - **Cancel**, from `cancel_payment_session` or from Create replacing a
      session, is local. For a session never made payable that is a real
      cancel: its submit is refused, so Adyen never lets it be paid. Core's
      rule that a gateway must not report as canceled a session that can
      still be paid holds for these.
    - **A method that skips `beforeSubmit` fails closed.** Adyen refuses
      payment on a session that is not payable, so such a method fails
      instead of slipping past Spree. During implementation the author
      confirms in the test account that every method Drop-in offers calls
      it, wallets and redirect methods included, and records any that do not.
    - **Setup sessions are created payable**, Adyen's default. They move no
      money, and their amount never changes.
    - **Accepted trade-off: a session canceled after the buyer pressed Pay.**
      A payable session stays payable at Adyen until it expires, one hour
      after creation. Spree still cancels it locally when the cart changes or
      the order is placed through another session. A buyer could then pay it,
      for instance by retrying a refused card in a tab left open.
      `HandleWebhook` records that payment whatever the session's status (Key
      Decision 12), the order shows more paid than owed, and the merchant
      refunds the difference. This is the one remaining exception to core's
      rule (`PaymentMethod#cancel_payment_session`'s comment, and the gateways
      plan's one-open-session constraint).
      - Leaving such sessions pending was rejected: it breaks the rule that a
        cart holds one open session per gateway, and no later call could
        cancel them.
      - Refusing a new session while one is payable was rejected: Adyen cannot
        say whether a payable session has a payment in flight, so any refused
        card would lock the cart for up to an hour.
    - **Rejected: payable sessions canceled locally on every change**, this
      decision's first version on Checkout v71. Every reload or cart change
      left a session the buyer could pay for an hour. The 5.x gem was worse:
      it never canceled sessions, and its amount update changed only Spree's
      figure, so Adyen charged the old total.
12. **Completion checks that the result belongs to the session; a session
    Spree canceled locally still settles.** A `sessionResult` is checked
    through `GET /sessions/{id}`, which Adyen binds to the session. A
    `redirectResult` is resolved through `/payments/details`, whose
    `merchantReference`, amount and currency must equal the session's before
    anything settles. The 5.x gem completed a session from any
    `redirectResult`. A refusal leaves the session open, because Adyen lets
    the buyer try again within the same session, and raises a `GatewayError`
    with Adyen's refusal reason. A session Spree canceled locally after it
    was made payable (Key Decision 11) that Adyen reports as authorised has
    its payment settled and stays `canceled`: a session completes only from
    `pending` or `processing`.
13. **Configuration runs by itself after save.** The operator types the API
    key, the merchant account, test mode and, for live, the live URL prefix.
    The merchant account is no longer taken from the credential's first
    associated account, as 5.x did, because a company-level credential
    reaches several. Adyen's partner checklist requires multi-store setups:
    "the integration you build must be able to handle multiple merchant
    accounts under one company account". This design meets that.
    - Each store's payment method names its own merchant account; with 6.1's
      payment method rules, so can several methods in one store, for example
      one per market.
    - Methods may share one company-level credential or use merchant-level
      ones. Saving checks that the method's credential reaches its merchant
      account and names a missing permission.
    - The client key and allowed origins belong to the credential, so a
      shared credential has one client key, which configuration never
      replaces, and collects every store's storefront origins.
    
    After save, a job reads the credential, generates a client key only if
    the credential has none, and adds the store's allowed origins to the
    credential (Drop-in loads only on those). It then puts the method's
    merchant-level webhook on the method's URL: it updates the one it
    created before if that points elsewhere, otherwise finds or creates one.
    It generates an HMAC key for a webhook that has none stored, keeping the
    previous key for deliveries already signed with it.
    
    **Accepted trade-off:** Adyen "strongly recommend[s]" configuring webhooks
    at company level, to avoid duplicate configurations. The gem creates one
    merchant-level webhook per payment method, as 5.x did, for two reasons.
    It is the level a merchant-level credential can reach. And each method
    has its own endpoint (its prefixed id is in the URL) and its own HMAC key.
    A merchant with several methods on one company sees one webhook per method
    in Adyen. Where two methods share a merchant account, each one's webhook
    may also carry the other's events (Adyen does not say whether it does).
    That is harmless: each method acts only on its own sessions, payments and
    refunds.
14. **Every webhook is verified; authorisations and modification outcomes are
    acted on.** The HMAC signature is checked with the library's
    `valid_webhook_hmac?`, which compares in constant time since 12.0 (11.x
    compared with `==`). It is checked against the current key and, after a
    new key was generated, the previous one. The delivery's merchant account
    and live flag must match the method. There is no development or test
    bypass, the rule of PayPal's Key Decision 10.
    - An `AUTHORISATION` with `success: true` becomes `:captured` or
      `:authorized` (Key Decision 10).
    - An `AUTHORISATION` with `success: false` is acknowledged and not acted
      on: Adyen sends one for every refused attempt, and the buyer may still
      pay the same session with another card.
    - `CAPTURE`, `CAPTURE_FAILED`, `CANCELLATION`, `REFUND`, `REFUND_FAILED`
      and `REFUNDED_REVERSED` become core's modification outcomes (Key
      Decision 8).
    - Everything else is acknowledged and not acted on.
    
    **Accepted trade-off: a pending payment Adyen later refuses.** A session
    settled on `Received` or `Pending` places the order with a pending
    payment. If the later `AUTHORISATION` says `success: false`, nothing in
    Spree changes: failing the payment of a completed session is a
    session-level outcome core does not have, and PayPal's plan left it out
    for the same reason. The merchant sees the pending payment in the
    dashboard and the refusal in Adyen. Until then the payment reads
    "authorized, not captured"; for a method that captures at checkout, Adyen
    captures it when it is authorised, and staff should not capture it by
    hand.
15. **Secrets stay out of `metadata`.** The 5.x gem kept the previous HMAC key
    in `private_metadata`. 6.0's metadata consolidation moved it into the
    payment method's `metadata`, which the Admin API returns. In 6.0 it is an
    internal `:password` preference, and an upgrade step removes it from
    `metadata`. The client key is public, since Drop-in needs it in the
    browser, so it goes to the storefront in the session's `external_data`. It
    is an internal `:password` preference written by configuration, hidden
    from the form like Stripe's webhook secrets, until 6.1's public
    preferences (decisions.md, 2026-11-02).
16. **Return URLs must be on one of the store's allowed origins.** The client
    sends `return_url` (the storefront does), and the gem accepts it only if
    `Store#allowed_origin?` matches, as core's redirect URLs already are
    (`AllowedRedirectUrl`). Otherwise session creation raises a
    `GatewayError`. There is no default: 5.x defaulted to
    `<storefront>/adyen/payment_sessions/redirect`, a Rails storefront route
    the Next.js storefront does not have, and it took any URL a client sent,
    which made Adyen's redirect an open redirect. **Accepted trade-off:**
    allowed origins are http(s) only, so a native app returns through a
    universal or app link on an allowed origin, never a custom URL scheme.
17. **Money is Adyen minor units, from Adyen's own currency table.** The
    gateway sets `accepts_money_amounts = true`. `SpreeAdyen::Amounts`, the
    twin of `SpreeStripe::Units`, converts with the decimals Adyen publishes
    per currency. An amount Adyen cannot represent raises, naming the rule,
    and a currency missing from the table is not offered
    (`available_for_order?` is false).
18. **Every money-moving request carries an idempotency key derived from
    Spree records, new for each attempt, which is what makes retries safe.**
    Adyen answers a repeated key with its first answer for 7 to 14 days. So a
    key must repeat when the previous attempt's outcome is unknown, and
    change once Adyen has answered:
    - session creation: the cart and its session count;
    - capture: the payment and the number of capture events it already has;
    - void: the payment and the number of cancel references the gem has
      recorded on it;
    - refund: the payment and the number of refund rows it had before this
      one.
    
    A capture or void Adyen refused leaves a record behind (a failed capture
    event, a recorded cancel reference), so the next attempt gets a new key.
    A call that timed out leaves none, so its retry repeats the key and gets
    Adyen's first answer. Core deletes a refund row whose credit raised
    (`destroy_uncredited_refund`), so a refund retried after a timeout
    repeats its key instead of refunding twice. Keys stay under Adyen's 64
    characters. The 5.x gem sent a fresh random key on some calls and none on
    others, which protects nothing.
    
    The client sets explicit open and read timeouts instead of the SDK's 30
    and 60 seconds. A call that times out or gets a 5xx is retried up to twice
    with backoff and the same key, as the project's third-party rule asks and
    PayPal's gem does. A money-moving call still unanswered after its retries
    raises `Spree::Core::AmbiguousGatewayError`, because its outcome is
    unknown.
19. **No circuit breaker, the same as Stripe.** **Accepted trade-off:** this
    departs from the project rule for third-party calls, and during an Adyen
    outage each checkout waits for the timeouts. Outage protection, if wanted,
    goes into core for every gateway.
20. **Line items are sent only when they add up.** Buy-now-pay-later methods
    such as Klarna need line items that sum to the amount. The presenter
    builds products, delivery, fees and discounts (store credit included) as
    lines, and sends them only when they reconcile exactly; otherwise the
    session carries the amount alone, and Adyen refuses those methods for that
    cart. The 5.x gem sent products only, which never added up once a cart had
    delivery.
21. **No request or response bodies in logs.** They carry names, emails and
    addresses. Logging is status lines only.
22. **Apple Pay's domain file is the storefront's.** Apple Pay through Adyen
    needs Adyen's domain association file at
    `/.well-known/apple-developer-merchantid-domain-association` on every
    storefront domain. A headless backend does not serve those domains, so the
    5.x upload and route are dropped and the docs tell merchants to host the
    file in the storefront. This is the same reasoning that dropped Stripe's
    domain registration.
23. **Cards are saved only with the buyer's consent** (decided 2026-11-16).
    At checkout, a signed-in customer's session sends
    `storePaymentMethodMode: askForConsent`, so Drop-in shows a "Save for my
    next payment" checkbox on card payments. Card schemes require the
    cardholder's consent to store a card. A setup session sends `enabled`,
    since the buyer opened it to save a card (decided 2026-11-16). Guests get
    no shopper reference, and nothing is stored. **Accepted trade-off:**
    fewer cards are saved at checkout, and this differs from the Stripe gem,
    which saves every card. Always saving at checkout (`enabled`, as 5.x did)
    was rejected because it stores cards without asking.
24. **A payment without a session is refused, the same as Stripe** (decided
    2026-11-16). `authorize` and `purchase` read back a session's
    authorisation; for a payment with no session they fail with a message
    saying Adyen payments are taken through a payment session. 5.x's
    card-on-file charge (`ContAuth` with the stored payment method id) was
    rejected: it is a second payment path the Stripe gem lacks, it works only
    for saved cards, and issuers may decline merchant-initiated charges.
    **Accepted trade-offs**, the same as Stripe's gem has today:
    - Staff cannot charge a saved card; the merchant takes a new payment.
    - Core cannot re-authorize the remainder of a partial capture. Adyen
      cancels what a partial capture leaves anyway, unless the merchant has
      asked Adyen to enable multiple partial captures. The remainder payment
      core splits off has no session, so its re-authorization fails.
    - So capture on dispatch takes payment for the first parcel of a
      multi-parcel order only. A later parcel dispatched while that capture
      is `requested` finds no pending payment to capture. One dispatched
      after it finds a failed remainder.
25. **Setup sessions are kept if Adyen returns the card token, and healed by
    nobody** (decided 2026-11-16).
    - **The flow.** Saving a card without a purchase opens a zero-amount
      session in the store's default currency and completes from the session
      result's stored payment method id. 5.x defaulted to USD unless the
      client passed a currency.
    - **The open risk.** Adyen's docs say a `/sessions` token arrives in the
      `recurring.token.created` webhook. The 5.x cassettes show it in a
      checkout session's result, but none records a setup session's result.
    - **The check.** During implementation the author confirms in the Adyen
      test account that a setup session's result carries the token. If it
      does not, setup sessions leave the first release
      (`setup_session_supported?` false), and cards are saved at checkout
      only.
    - **No webhook backup, as with Stripe.** Core routes webhooks only for
      payment sessions and the outcomes of Key Decision 8. The 5.x gem's
      handling inside `parse_webhook_event` acted while parsing.
    - **Accepted trade-off:** a buyer who closes the tab during a setup
      redirect gets no saved card in Spree. Adyen still stores it, and
      Drop-in shows it at the next checkout.
26. **Authorization adjustments are deferred** (decided 2026-11-16). An
    authorization adjustment changes an authorised amount later, for example
    after an order edit, through `/amountUpdates` on a payment authorised as
    a pre-authorisation. Adyen's partner checklist lists them as required.
    5.x never had them, and the first release keeps that scope. **Accepted
    trade-off:** one partner-checklist item stays unmet. An Adyen payment
    keeps the amount it was authorised for. When an order is edited
    afterwards, the order's payment status shows the difference, as for any
    gateway (decisions.md, 2026-09-25), and staff settle it. When this is
    picked up, it needs a core gateway verb that tells a gateway an
    authorised payment's amount changed; no gateway has one today. Sessions
    would then request a pre-authorisation, and the gem would answer that
    verb through `/amountUpdates`, waiting for Adyen's webhook like any other
    modification (Key Decision 8).

`SpreeAdyen::Result` is an ActiveModel value object, in the `TrackerEvent`
pattern. It is built from any of the three reports (session result,
`/payments/details`, `AUTHORISATION` webhook) and exposes the PSP reference,
result, amount, Adyen's payment method variant (its `paymentMethod` field),
card summary, expiry and stored payment method id. Settlement reads only this
object, so the synchronous and webhook paths cannot drift.

### Gateway

`SpreeAdyen::Gateway < Spree::Gateway`:

- Preferences: `api_key` (`:password`), `merchant_account` (string),
  `test_mode` (boolean, default true), `live_url_prefix` (string, required
  when not in test mode; Adyen's live Checkout endpoints still need it, the
  Management API does not). Internal ones, written by configuration and
  hidden from the form: `client_key`, `hmac_key` and `previous_hmac_key`
  (`:password`), and `webhook_id`.
- Validation on save checks that the credential reaches `merchant_account`.
  It lists the merchant accounts the credential can access through the
  Management API (`GET /merchants`). 5.x read `associatedMerchantAccounts`
  from `GET /me`, which the v3 schema does not document for that call; the
  recorded cassettes settle which call answers. A refusal names what to fix:
  an invalid key, a merchant account the credential cannot reach, or a missing
  role. The roles are API credentials read and write, and Webhooks read and
  write. Skipped in the test environment, as Stripe's `validate_secret_key`
  is.
- `logo_url` / `docs_url` for the dashboard gallery card.
- `gateway_dashboard_payment_url` links to Adyen's transaction page on
  `ca-test` or `ca-live` for `metadata['adyen_psp_reference']`; no reference
  means no link. 5.x built it from `transaction_id`, the session id on its
  payment-session path, so the link opened nothing.
- `session_required?` true. `payment_profiles_supported?` true: cards are
  saved under the customer's shopper reference (Payment sources), and core
  passes the source to `void` and `credit`, as for Stripe.
- `authorize(money, source, gateway_options)` / `purchase(...)`: called by
  core when a session-created payment moves on. Adyen already holds the
  authorisation, so they return success with the session id and make no
  call. A payment with no session fails (Key Decision 24).
- `capture(money, session_id, gateway_options)`: requests a capture of the
  payment's PSP reference and answers `requested?`. The response's
  authorization stays the session id, and its `reference` is the capture's
  own PSP reference.
- `void(session_id, source, gateway_options)`: requests a cancel of the PSP
  reference, records the cancel's reference on the payment for the next
  attempt's key (Key Decision 18), and answers `requested?`.
  `can_void?(payment)` is false for a completed payment, as in Stripe,
  because a captured payment is refunded instead.
- `credit(money, source, session_id, options)`: requests a refund of the PSP
  reference, keyed from `options[:originator]` (the `Spree::Refund`), and
  answers `requested?` with the refund's own PSP reference as the
  authorization.
- `cancel(session_id, payment, refund:)`: same as Stripe, and answers
  `requested?`. A completed payment is refunded through
  `Spree.refund_create_workflow` unless `refund: false`; anything else is
  voided.
- A payment with no PSP reference (5.x's payment-session path; see Upgrading)
  is refused by `capture`, `void` and `credit` with a `GatewayError` saying
  Adyen cannot be asked without one and naming the Customer Area.
- Adyen errors are wrapped as `Spree::Core::GatewayError` carrying Adyen's
  error code and message, never the SDK's generic text. A request Adyen
  refuses outright (a 4xx, such as an expired authorisation) fails at once,
  as with any gateway; only an accepted request waits. Timeouts follow Key
  Decision 18.

### Payment sessions

**Create.** Refuses a zero amount, a cart with a completed Adyen session, and
a `return_url` outside the store's allowed origins. Cancels the cart's open
Adyen sessions locally (Key Decision 11). Creates the session through
`SessionPresenter`:

- the amount in Adyen minor units, and the cart's currency;
- `reference` as `<cart prefixed id>-<n>`, where n counts this method's
  sessions on the cart, deleted ones included, and `merchantOrderReference` as
  the cart's prefixed id, so every attempt for a cart is found together in
  Adyen. The order number does not exist yet;
- `returnUrl`, `channel` (`Web` by default, or `iOS` / `Android` from the
  client, with the other platform's wallet blocked, as in 5.x);
- `countryCode` from the bill or ship address, else the store's default
  market country (5.x fell back to the store's default country, then `US`);
- the shopper's name and email, and the shopper reference and consent rule
  from Payment sources;
- `additionalData.manualCapture` per Key Decision 10;
- line items per Key Decision 20;
- `applicationInfo` naming Spree and the gem version, which the partner
  checklist requires and 5.x already sent;
- `expiresAt` one hour out, Adyen's default, kept explicit;
- `payable: false` (Key Decision 11). Setup sessions leave it out.

Stores the Adyen session id as `external_id` and puts in `external_data` what
the storefront and the gem need: `session_data`, `client_key`, `environment`
(`test` / `live`), `channel`, `return_url`, `reference`, `manual_capture` and
`payable`. The gem owns these keys and ignores values a client sends for them
through the create and update endpoints.

**Update.** Before the session is payable, a new amount changes Spree's
amount only, and `external_data` keys the gem does not own are merged. Once
it is payable, a different amount raises (Key Decision 11).

**Submit.** An update carrying `external_data.submit` sends
`PATCH /sessions/{id}` (the library's `update_session`) with the original
`sessionData`, the amount Spree holds in Adyen minor units, and
`payable: true`. It stores the
returned `sessionData` and `payable: true`, and responds with the session.
It refuses a session that is not `pending`, and answers a payable one from
what is stored. If a submit's answer is lost and its retry finds the session
already payable, Adyen refuses the update. The gem then raises, the
storefront opens a new session, and the old one falls under Key Decision 11's
trade-off.

**Complete.** Takes `session_result` (Drop-in's `onPaymentCompleted`) or
`external_data.redirect_result` (the buyer back from a redirect), and builds a
`Result` from `GET /sessions/{id}` or `/payments/details`.

| Adyen says | Gem does |
|---|---|
| Session `completed`, or `Authorised` | settle: captured, unless the session asked for manual capture and the variant is not one Adyen captures at once (Key Decision 10) |
| Session `paymentPending`, or `Received` / `Pending` | settle as authorized: Adyen's guidance for `Received` is to tell the shopper the order is in and wait, and the `AUTHORISATION` webhook completes it |
| `Refused`, `Cancelled`, `Error`, or a session still `active` | raise a `GatewayError` with Adyen's reason; the session stays open |
| Session `refused` (too many refused attempts) | fail the session |
| Session `expired` | expire the session |

"Settle" means: run the checks of Key Decision 5 and, for a redirect, Key
Decision 12, then call `settle_payment!(captured:, metadata: result.to_h)` and
complete the session. A failed check raises a `GatewayError` naming it and
settles nothing. Complete never completes the cart; the storefront's
cart-complete call or `HandleWebhook` does that.

**Cancel.** Local: the session is canceled with no Adyen call. That is a real
cancel for a session never made payable (Key Decision 11).

**Settlement hooks on `Spree::PaymentSessions::Adyen`.** Both paths pass the
same `Result#to_h` as `metadata`: the synchronous one from Complete, the
webhook one from `parse_webhook_event` through core (Key Decision 7).

- `payment_source_for_settlement` returns nil, because it receives nothing
  on the webhook path.
- `apply_settlement_metadata` records `adyen_psp_reference` and
  `adyen_variant` on the payment. It also attaches the payment source built
  from the result (Payment sources). It does not merge the raw report into
  `metadata`.
- `capture_reference_for_settlement`, a new core hook (Core change:
  asynchronous modifications), returns the PSP reference. When the payment
  settles as captured, it is written on the capture event core creates, so a
  late `CAPTURE_FAILED` for an automatic capture finds it.
- All three run inside the settlement lock, so this is database work only.
  `prepare_for_settlement!` keeps the default no-op: nothing needs fetching.

### Payment sources

- **A card with a stored payment method id** (the buyer saved it, Adyen
  reported `tokenization.storedPaymentMethodId`) becomes a `Spree::CreditCard`:
  the brand mapped from Adyen's variant (5.x's table, plus the wallet suffixes
  `_applepay` / `_googlepay`, which 5.x missed for Apple Pay), last four from
  `cardSummary`, expiry from `expiryDate`, the stored id as
  `gateway_payment_profile_id`, the shopper reference as
  `gateway_customer_profile_id`, the wallet in `metadata`, and the cart's
  customer.
- **A card without one** (a guest, or a buyer who did not save it) is recorded
  on `SpreeAdyen::PaymentSources::Card`, a non-reusable source with brand and
  last four in `metadata`. A `Spree::CreditCard` without a profile id needs a
  number, name and expiry Adyen does not give, and it would show among saved
  cards where choosing it fails. PayPal records guest cards the same way.
- **Every other method** (Klarna, iDEAL, BLIK, PayPal through Adyen, …)
  becomes the 5.x source class for Adyen's variant, through
  `SpreeAdyen::Variants` (`klarna_paynow` → `Klarna`, `bcmc_mobile` →
  `Bancontact`, …). A variant missing from the table uses `Unknown`. Every
  class is a one-line subclass of `SpreeAdyen::PaymentSources::Base`, which
  keeps the variant in `metadata['adyen_variant']` and takes its display name
  from the table. 5.x's per-class `actions` and `store_accessor
  :public_metadata` declarations go: nothing in 6.0 reads a source's
  `actions`, the capture split they encoded moves into the variant table
  (Key Decision 10), and 6.0 has one `metadata` column (Key Decision 3).
- Last four and expiry come from two Adyen settings the docs name: Developers
  → Additional data, which gates fields in Checkout API responses, and the
  webhook's own additional settings, which gate fields in webhooks.
- Cards are saved under shopper reference `customer_<customer id>`, the 5.x
  format, so cards saved under 5.x still appear in Drop-in: Adyen honors a
  token only with the shopper reference it was stored under. A signed-in
  customer is asked first (Key Decision 23). Guests get no shopper reference
  and nothing is stored. 5.x stored guest cards under `guest_<order number>`,
  which nobody can use again.
- Saved Adyen cards are listed among the customer's saved cards, and Drop-in
  offers them at checkout. Nothing charges one outside Drop-in (Key Decision
  24).

### Setup sessions

`create_payment_setup_session(customer:)` opens a zero-amount session with the
customer's shopper reference, `storePaymentMethodMode: enabled`, the store's
default currency and the same return-URL rule.
`complete_payment_setup_session` reads the session result. `completed` with a
stored payment method id creates the `Spree::CreditCard` and completes the
session; `completed` without one fails it, naming the token as missing. Other
statuses map as in Complete. Whether the first release keeps setup sessions at
all is settled by the check in Key Decision 25.

### Webhooks

**Verification.** Core's endpoint calls `parse_webhook_event`, which:

- parses the body (malformed → `WebhookSignatureError`);
- requires exactly one `NotificationRequestItem`, which is all JSON webhooks
  carry;
- checks `additionalData.hmacSignature` with the library's
  `Adyen::Utils::HmacValidator#valid_webhook_hmac?` (constant time), against
  `hmac_key`, then `previous_hmac_key`. The deprecated
  `valid_notification_hmac?` is not used. Each HMAC key belongs to one
  webhook;
- checks `merchantAccountCode` against the method's merchant account and
  `live` against test mode.

Any failure raises `WebhookSignatureError`, which answers 401 so Adyen
delivers again later. Adyen needs any 2xx within 10 seconds, which core's
immediate `head :ok` gives. Webhooks created before May 2024 expected an
`[accepted]` body; the configuration job only creates or updates the
method's own webhooks, so none of those is left on the method's URL.

**Events.**

| Adyen event | Result |
|---|---|
| `AUTHORISATION`, `success: true` | session `:authorized` or `:captured` by Key Decision 10's rule, with the `Result` as `metadata` |
| `AUTHORISATION`, `success: false` | not acted on (Key Decision 14) |
| `CAPTURE`, `success: true` | `:capture_succeeded` |
| `CAPTURE`, `success: false`; `CAPTURE_FAILED` | `:capture_failed`, with Adyen's `reason` |
| `CANCELLATION`, `success: true` | `:void_succeeded` |
| `CANCELLATION`, `success: false` | `:void_failed`, with Adyen's `reason` |
| `REFUND`, `success: true` | `:refund_succeeded` |
| `REFUND`, `success: false`; `REFUND_FAILED`; `REFUNDED_REVERSED` | `:refund_failed`, with Adyen's `reason` |
| everything else | not acted on |

**Which record each outcome names, and how it is found.** No JSON queries;
plain lookups only.

| Outcome | Names | Found by |
|---|---|---|
| session `:authorized` / `:captured` | the payment session | `additionalData.checkoutSessionId`, scoped to this payment method |
| `:capture_succeeded`, `:capture_failed` | the capture event | its `transaction_id`: the webhook's `pspReference`, which is the reference Adyen returned for Spree's capture request. For an automatic capture's late failure, the webhook's `originalReference`, the payment's PSP reference written at settlement. Both lookups are scoped to this method's payments |
| `:void_succeeded`, `:void_failed` | the payment | this method's `requested` payments whose `metadata['adyen_psp_reference']` equals `originalReference`, compared in Ruby; only payments waiting on Adyen are read |
| `:refund_succeeded`, `:refund_failed` | the refund | its `transaction_id`: the webhook's `pspReference`, scoped to this method's payments |

**Accepted trade-off:** Adyen's sessions-flow examples carry
`checkoutSessionId`, but its schema does not promise it. An `AUTHORISATION`
without it is not acted on, and the buyer's return to the storefront still
settles the session.

Adyen sends a default set of event codes to standard webhooks, and they cannot
be turned off; that set includes `CAPTURE_FAILED` and `REFUND_FAILED`. The
`CAPTURE` event is not sent for automatic captures, which never go through
Spree's capture request, so nothing waits for one. Captures, cancellations
and refunds made in Adyen's Customer Area are not synced into Spree, as with
Stripe and PayPal: nothing in Spree waits for them, so their outcomes find no
record.

### Configuration job

`SpreeAdyen::ConfigureJob` runs after commit on create, and when `api_key`,
`merchant_account`, `test_mode` or `live_url_prefix` change. Saves that change
only the preferences the job writes are skipped, as with Stripe's
`only_webhook_registration_changed?`. `SpreeAdyen::Configure`:

1. reads the credential (`GET /me`);
2. generates a client key if the credential has none (`POST
   /me/generateClientKey`). An existing key is kept, because generating a new
   one retires the old one after 24 hours, and other stores sharing the
   credential would then stop loading Drop-in;
3. adds each of the store's non-loopback allowed origins (`POST
   /me/allowedOrigins`), treating "already exists" as done;
4. puts the merchant-level webhook on `webhook_url`:
   - a stored `webhook_id` whose webhook points at another URL (5.x's
     `/adyen/webhooks`) has its URL changed in place. That keeps its HMAC key
     and delivers what Adyen queued for it;
   - otherwise it finds the merchant's standard webhook for `webhook_url` or
     creates one (`POST /merchants/{id}/webhooks`);
   - a webhook with no stored key gets a new HMAC key, and the current one
     moves to `previous_hmac_key`;
5. stores the client key, webhook id and keys.

Allowed origins added in Spree later reach Adyen the next time the payment
method is saved, since `Spree::AllowedOrigin` publishes nothing a provider can
subscribe to and providers never decorate core models. The docs say so.

### Core change: webhook metadata

- `Spree::Api::V3::Webhooks::PaymentsController#create` passes
  `metadata: result[:metadata] || {}` to `HandleWebhookJob`.
- `Spree::Payments::HandleWebhookJob#perform` takes `metadata: {}` and passes
  it to `Spree.payments_handle_webhook_workflow`.
- `PaymentMethod#parse_webhook_event`'s comment says metadata must be
  JSON-safe with string keys, because it crosses a job boundary.
- Specs: the controller enqueues with metadata, and the job hands it to the
  workflow, which already passes it to `settle_payment!`.

### Core change: asynchronous modifications

Opt-in by response: every branch below runs only when a gateway answers
`requested?`. A gateway that answers at once takes the code path it takes
today, and money it moved is counted as today.

**Response.** `Spree::PaymentResponse` takes `requested: true` and an optional
`reference:`, the provider's id for this capture request. `requested?` is
false by default. A refund's id travels as the authorization, as today,
because core already stores that as the refund's `transaction_id`. A capture's
cannot, because a capture's authorization becomes the payment's
`response_code`.

**Payment status.** `Spree::Payment` declares `requested` after `pending`. It
is not claimable: nothing else may start on the payment until the provider
answers. `Payment#requested_action` derives `capture` or `void` (Key Decision
9). Every flow that moves money refuses a `requested` payment with a message
saying the provider has not answered yet:

- capture, void and refund (refunds already require `completed`);
- `Orders::Cancel`, which refuses to cancel the order. Today it voids an
  incomplete payment it can void, which would release a hold Adyen is still
  capturing;
- dispatch, which captures only `pending` payments and so passes it by (Key
  Decision 24);
- settlement: `HandleWebhook` and `settle_payment!` leave a `requested`
  payment alone, so a redelivered `AUTHORISATION` never moves it.

**`Payment#cancel!`.** On a `requested?` answer, an uncaptured payment becomes
`requested`, waiting on the void. A completed payment stays `completed`, and
its refund, created `requested` by `Refunds::Create`, carries the outcome.
Today `cancel!` voids a completed payment at once, as for Stripe, which here
would leave a void payment beside a refund that may still fail. Answers that
are not `requested?` keep today's behaviour.

**Capture events.** `spree_payment_capture_events` gains `status`
(`requested` / `completed` / `failed`) and `transaction_id` (the provider's
capture reference, indexed). The capture workflow and `confirm!` set the
status explicitly. Settlement writes `transaction_id` from the session's new
`capture_reference_for_settlement` hook (nil by default), so only a gateway
that overrides it fills it in.

**Refunds.** `spree_refunds` gains `status` (`requested` / `completed` /
`failed`) and `failure_reason`, and its `transaction_id` gets an index.
`Refunds::Create` creates the row `requested` and marks it `completed` when
the gateway answers at once. A crash between the two then leaves a visible
`requested` refund, not one that looks completed with no transaction id.

**Empty statuses.** The project's rules forbid defaults on status columns and
data changes in migrations, so the columns are added empty. The core upgrade
task `backfill_settlement_statuses` sets existing capture events and refunds
to `completed`. It is a non-optional step in the 5.6 → 6.0 manifest; stores
already on 6.0 run it with `spree upgrade --step backfill_settlement_statuses`.
Until it runs, an empty status reads as completed, so no sum moves. 6.1 makes
the columns `NOT NULL`.

**Every place money is summed.** Captured and refunded money counts
completed, or empty, rows only. A balance check subtracts every refund that
has not failed, so a requested refund keeps its balance reserved and cannot be
refunded twice. That rule is applied in each place core sums them today:

- `Payment#captured_amount` and `Payment#credit_allowed`;
- `Purchase::Totals` (`payment_total`) and `Carts::RecalculateTotals`;
- `Order#refunds_total` and `#returned_items_refund_total`, which feed the
  outstanding balance;
- `Payment::CustomEvents#order_settled_in_full?`;
- `OrderGroup` and `Refunds::OrderPayments`;
- `PaymentSplit`'s refunded amount. `PaymentSplitSubscriber` writes it on
  `refund.created` today, and moves to the refund's completion;
- `Orders::UpdateStatuses`, in both the ordinary and the split-checkout
  branch.

Other gateways write only completed rows, so their sums do not move.

**Split checkouts.** Grouped dispatch records a share as captured when the
capture workflow succeeds (`settle_share(captured: true)`). A `requested?`
answer leaves the share authorized until the capture's outcome, which records
it then. A late capture failure takes back the share's captured amount and the
order's `payment_total`.

**Flows.**

| Flow | `requested?` answer | Provider says yes | Provider says no |
|---|---|---|---|
| Capture (`Payments::Capture`) | payment `requested`, a capture event `requested` with the amount and `reference`, `payment.capture_requested`; the workflow succeeds, so dispatch goes ahead, because the provider accepted | event `completed`, the remainder split as today, payment `completed`, `payment.captured` | event `failed`, payment `failed`, `payment.capture_failed` |
| Late capture failure | | | after success: event `failed`, payment `failed`, `payment.capture_failed`, order and split figures re-derived |
| Void (`Payments::Void`, `Payment#cancel!`) | payment `requested`, `payment.void_requested` | payment `void`, `payment.voided` | payment back to `pending` (the authorisation still holds), `payment.void_failed` |
| Refund (`Refunds::Create`) | refund row `requested` with `transaction_id`, `refund.requested`; the uncredited-row cleanup does not run, since money is on its way | refund `completed`, order recalculated, `payment.refunded` | refund `failed` with `failure_reason`, balance released, order recalculated, `refund.failed` |
| Late refund failure | | | after success: same as "no" |

A failed capture or void records Adyen's reason with
`Payment#add_gateway_processing_error`, core's existing place for gateway
errors on a payment. It moves out of custom fields with the rest of core's in
6.1 (decisions.md, 2026-10-06). The new events are declared like every other
webhook event (decisions.md, 2026-09-29). `payment.captured`,
`payment.voided` and `payment.refunded` publish when the provider confirms,
not at request.

**Webhook outcomes.** `parse_webhook_event` may also return
`{ action:, capture_event: | payment: | refund:, metadata: }`, with the record
each outcome names in the Webhooks section, and these actions:
`:capture_succeeded`, `:capture_failed`, `:void_succeeded`, `:void_failed`,
`:refund_succeeded` and `:refund_failed`. The controller enqueues a new job,
which runs a new workflow beside `HandleWebhook`
(`Spree.payments_handle_modification_webhook_workflow`). The workflow locks
the payment, applies the row above, and treats a repeat delivery as done: an
outcome for a record that has already moved past `requested` changes nothing,
except a late failure after success. Stripe and PayPal never return these
actions.

**API and dashboard.**

- The Admin payment serializer exposes `requested_action`.
- The capture event and refund serializers expose `status`, and refunds also
  `failure_reason`.
- `PaymentStatus` stays an open list and documents `requested`.
- The dashboard shows "Capture requested" or "Void requested" from
  `requested_action`, hides the payment's actions while it is `requested`,
  and shows a refund's status and failure reason.

**Testing without Adyen.** `Spree::Gateway::Bogus` gains a `requested` mode, a
boolean preference that is off by default, in which capture, void and credit
answer `requested?`. In that mode its `parse_webhook_event` accepts a plain
JSON outcome naming the action and the record's reference, so core specs and
the dashboard's E2E test post outcomes to core's webhook endpoint. With it
off, Bogus answers at once, as it does today.

**Migration.** One core migration adds the four columns (`status` on capture
events and refunds, `transaction_id` on capture events, `failure_reason` on
refunds) and the two `transaction_id` indexes, with no defaults, written to
run on PostgreSQL, MySQL and SQLite.

It removes the values and their two definitions, since custom fields belong to merchants |

The gem's two steps go into the 5.6 → 6.0 manifest in the patch release that
ships the gem, as PayPal's did, and for the same reason: the stores that need
them are leaving 5.x and walk exactly that manifest. Core's
`backfill_settlement_statuses` step goes there too, before them.

- `migrate_adyen_payments` walks payment rows, so it names a `task_class`,
  `SpreeAdyen::MaintenanceTasks::MigratePayments`, a `Spree::MaintenanceTask`
  with a collection (progress, resume, dry run). It tallies converted,
  marked-done and unrecoverable payments in the run's record.
- `configure_adyen_gateways` is one pass over a handful of payment methods,
  so it names a rake `task`, `spree:upgrade:configure_adyen_gateways`, run
  through core's shared `UpgradeStep` runner. It runs `SpreeAdyen::Configure`
  inline.

Both are `optional: true` and safe to run again. **Accepted trade-off**, as
for PayPal: a store already recorded as upgraded to 6.0 does not see the new
steps on the dashboard's upgrade page; it runs them with
`spree upgrade --step <id>`, and the upgrade guide says so.

### Storefront and dashboard

The dashboard needs nothing for the gateway itself: the payment method form is
generated from the preference schema, internal preferences are hidden, and the
gallery card reads `logo_url` / `docs_url`. Its changes for the waiting state
are core's (Core change: asynchronous modifications). Changes land in the
`spree/storefront` repository:

- read `client_key` and `environment` from the session's `external_data`,
  with `NEXT_PUBLIC_ADYEN_CLIENT_KEY` / `NEXT_PUBLIC_ADYEN_ENVIRONMENT` only as
  fallbacks; the `isAdyenConfigured` gate goes;
- make Drop-in's registered components one constant, written out twice today,
  without the gift card component (Key Decision 5);
- filter the saved-card list to the selected payment method. It holds every
  gateway's cards and is shown for Stripe, so a store running both would offer
  an Adyen card to Stripe. Adyen's saved cards are shown inside Drop-in;
- patch the session with the amount due after store credit, which is what a
  new session defaults to, instead of the cart total. Today every patch on a
  cart with store credit mismatches. Call Drop-in's `update` with the same
  amount so the buyer sees it. Once the session is payable, a new amount is
  refused and the existing fallback opens a new session (Key Decision 11);
- in Drop-in's `beforeSubmit`, call the session update endpoint with
  `external_data.submit` and no amount. Pass the returned `session_data` to
  `actions.resolve`, or call `actions.reject` on an error (Key Decision 11);
- on a failed completion, keep Drop-in mounted, since the session stays open
  (Key Decision 12), and create a new session only when the session is no
  longer pending.

The redirect page already passes Adyen's `sessionId` and `redirectResult` to
the complete endpoint, which finds a session by `external_id`.

## Constraints on Current Work

- No new feature work in the standalone `spree/spree_adyen` repository;
  critical 5.x fixes only.
- Don't rename `SpreeAdyen` or the session and source classes in docs,
  examples or seeds; their names are stored data.
- A session payment's `response_code` stays its Adyen session id. Code that
  needs the PSP reference reads `metadata['adyen_psp_reference']`.
- Every Adyen call that moves money carries an idempotency key derived from
  Spree records that repeats only while the previous attempt's outcome is
  unknown. A new call without one is a bug.
- Don't give this gem network protection Stripe's lacks, such as a circuit
  breaker.
- A gateway's webhook `metadata` must be JSON-safe with string keys: it now
  crosses the job boundary.
- **A gateway answers `requested?` only when the provider has accepted a
  request and will report its outcome by webhook.** It must then return that
  outcome through `parse_webhook_event`. A gateway that answers at once never
  sets it, and core code must not assume any gateway does.
- **A payment in `requested` is waiting on its provider.** Code that moves
  money refuses it, settlement leaves it alone, and code that sums money
  counts it as authorized. Captured and refunded money counts completed (or
  not yet backfilled) capture events and refunds only, while a balance check
  subtracts every refund that has not failed. New code that sums captures or
  refunds follows the same rule.
- The storefront's Drop-in components stay without gift cards until partial
  payments are designed (one session, several payments).
- Changes to the core payment-session contract are checked against Adyen as
  well as Stripe and PayPal once this lands: Adyen is the gateway whose
  sessions can be canceled only before they are payable and whose
  modifications complete asynchronously.
