# Diagnostics and Issue Reporting

**Status:** In Progress — building all three phases for 6.0.4
**Target:** Spree 6.0 (all three phases in the 6.0.4 patch release)
**Depends on:** `6.0-telemetry-and-update-check.md` (`Spree::UpdateCheck` already collects the stack fields), `6.0-admin-spa.md` (settings pages, `PageHeader`), `6.0-backend-agnostic-cli.md` (the CLI reaches Rails only through `backend.ts`)
**Author:** Damian Legawiec (design driven with Claude)
**Last updated:** 2026-11-11
**Tracking:** Linear — · GitHub —

## Summary

Bug reports from self-hosted installations arrive with no context. We can't
see the reporter's Spree version, gems, Ruby, database, OS, store setup,
markets, channels or providers, and the current `bug_report.md` asks them to
post their Gemfile.lock in a Gist, which almost nobody does. This plan adds
one anonymised diagnostics report, built in `spree_core`. Users can get it in
two ways: a Settings → System info page in the dashboard, and `spree info`
in the CLI. The dashboard and CLI can copy it as
Markdown or open a pre-filled GitHub issue form. The report includes recent
Spree errors by class and code location, without their messages. A second phase turns the existing
per-page "View as JSON" drawer into a standard that every resource page gets
for free. A third phase adds a developer inspector drawer, modelled on Stripe
Workbench, that lists the dashboard's recent API requests with their request
IDs, bodies and "copy as curl / SDK call" actions. This follows the pattern
of WordPress Site Health, Home Assistant System Information, n8n "Copy debug
info", VS Code "Report Issue" and `next info`.

## Key Decisions (do not deviate without discussion)

- **One report, built once in core.** `Spree::Diagnostics.report` returns a
  `Spree::Diagnostics::Report`. The rake task, the Admin API endpoint, the
  dashboard page and the CLI all render that same report. None of them collects fields of its own,
  except the CLI's client-side section (Node, package manager, `@spree/*`
  versions, Docker).
- **Allowlist, never denylist.** Each field is added on purpose by name.
  Settings are reported by type, and only when changed from their default:
  booleans, integers, decimals and fixed-choice strings. Free-form strings
  are never reported, whatever they hold, so a new setting holding a URL or
  a credential can't leak (2026-11-11, chosen over a per-setting
  "reportable" flag that every new setting would have to remember).
- **Store and channel names are hidden by default (2026-11-11).** Stores,
  channels and markets appear only as prefixed IDs plus their settings
  (currency, locales, number of countries, active flag). Names, URLs and
  emails never appear. Rationale: the report is pasted into a public GitHub
  issue, and prefixed IDs are enough to tell records apart in a conversation.
- **Recent errors are included as class and location only, never the
  message (2026-11-11).** Messages routinely carry customer data (emails,
  addresses, values echoed from a database row), and no regex scrubber can
  promise to catch them all in a report that ends up in a public issue.
  Accepted trade-off: "`NoMethodError` at `complete.rb:162`" is sometimes
  not enough, and maintainers will ask for the message in the issue thread,
  where the reporter decides what to paste.
- **Only public gems are named (2026-11-11).** A gem appears by name and
  version only when it is Spree's own (its homepage or source points at
  spreecommerce.org or github.com/spree) or comes from rubygems.org. Private
  `spree_*` gems and other gems built on Spree are only counted, and their
  backtrace frames become `gem/[redacted]`, like the host app's
  `app/[redacted]`.
- **Refused requests are not errors (2026-11-11).** The error log skips any
  exception Rails answers with a 4xx (`rescue_responses`), so invalid records
  and bad parameters don't crowd out real failures. An error raised in the
  host application before any Spree frame is the merchant's, even though
  Spree's middleware is further up every request's stack.
- **Exception class names are an exception to "no Ruby class names on the
  wire" (2026-11-11).** `errors[].error_class` is what a maintainer reads in
  a bug report, not a value any client branches on, so it stays a class name.
- **Errors are kept in a `Rails.cache` ring buffer (2026-11-11).** No
  migration, no write per error to the database, and nothing to prune.
  Accepted trade-off: the log is lost when the cache is cleared or the app
  restarts, and with a per-process `:memory_store` each process sees only
  its own errors. The report says so instead of pretending to be complete.
- **`spree info` is local only (2026-11-11).** It runs `bin/rails spree:info`
  in the project. Deployed installations run that rake task in their host's
  shell. Secret API keys still never see the running version, as decided in
  `6.0-telemetry-and-update-check.md`. Accepted trade-off: there is no
  one-command report for a remote production install.
- **Everything ships in a 6.0.x patch (2026-11-11).** All three phases go
  out in 6.0.4. The work is additive: a new endpoint, a rake task, a CLI
  command, dashboard pages and an optional SDK callback. Accepted trade-off:
  a feature-sized patch release, so nothing in this plan may change an
  existing response, need a migration, or break a 6.0 extension.
- **Sizes are ranges, never exact counts.** This reuses the buckets
  `Spree::UpdateCheck` already sends (`0`, `1-9`, `10-99`, …, `100k+`).
- **The same access rule as `/updates`.** The report reveals the running
  version and stack, so it answers only signed-in staff with `manage` on the
  store.
- **The dashboard shows the report before it is copied.** Users see exactly
  what they are about to share, in the same Markdown that ends up in the
  issue.
- **"View as JSON" comes from the resource, not from each page
  (2026-11-11).** About sixteen detail pages wire `jsonPreview` by hand, and
  pages such as Store settings have none. Phase 2 makes `PageHeader` derive
  the drawer from the `resource` and endpoint it is given. A page opts out
  rather than in.
- **The inspector never leaves the browser.** It records requests in memory
  for the current tab only. Nothing is persisted or sent anywhere, so it adds
  no privacy surface beyond what the admin can already see.
- **The report covers versions, stack and settings only (2026-11-11).** Store,
  Markets, Channels, Providers and Features were dropped after review: they
  made the report long and touched the merchant's setup without helping
  triage much, and an extension can still add its own section. `spree info`
  leaves out Recent errors, since its own process rarely sees the server's
  log; the dashboard keeps them. This supersedes the store, markets, channels
  and providers rows in Design Details.

## Design Details

### Phase 1 — Diagnostics report

#### `Spree::Diagnostics` (`spree_core`)

`spree/core/app/services/spree/diagnostics.rb`. The stack fields move out of
`Spree::UpdateCheck#query` into `Spree::Diagnostics::Stack`, and
`UpdateCheck` calls it, so the heartbeat and the report can't drift apart.

```ruby
report = Spree::Diagnostics.report(store: current_store) # => Spree::Diagnostics::Report
report.to_markdown                                       # => String, for issues
```

Sections, each a `Spree::Diagnostics::Section` subclass so extensions can
register their own (`Spree.diagnostics_sections << 'MyGem::DiagnosticsSection'`):

| Section | Fields |
| --- | --- |
| `platform` | Spree version, every `spree*` gem with version, installed extensions (other gems that depend on a Spree gem) |
| `runtime` | Ruby, Rails, OS and architecture, Puma/web server, `Rails.env` |
| `infrastructure` | database adapter and server version, queue adapter, cache store class, Active Storage service name (not bucket), Action Cable adapter, whether Redis is configured (not its URL) |
| `store` | store prefixed ID, default currency, supported currencies, default locale, supported locales, timezone, default country ISO, size ranges (products, variants, orders, customers, sellers) |
| `markets` | per market: prefixed ID, currency, country count, locales, default flag |
| `channels` | per channel: prefixed ID, type, active flag, market IDs |
| `providers` | payment method types, tax provider, delivery rate provider, search provider, payout provider — all by `api_type` |
| `features` | marketplace on/off, B2B on/off, dashboard mounted, emails gem, storefront detected |
| `preferences` | `Spree::Config` and store settings changed from their default, of a reportable type (see Key Decisions) |
| `errors` | recent scrubbed errors (below) |

Every field is read with a rescue that reports `"unavailable"` instead of
failing. A half-broken installation is exactly when the report is needed.

#### Recent errors

- `Spree::Diagnostics::ErrorLog` subscribes to `Rails.error` (Rails 7.1+
  error reporter). Spree workflows already report through
  `Rails.error.report(..., source: 'spree.checkout')`, and Rails reports
  unhandled controller and job errors through the same channel.
- It keeps the last 50 errors in `Rails.cache`, grouped by exception class
  and first application frame, with a count and first/last seen time.
- What it stores: exception class, `source`, up to 10 backtrace frames
  trimmed to gem-relative paths (`spree_core-6.0.4/app/...`), the request ID
  when there is one, count, and first and last seen times. The message is
  never read into the entry, so it cannot leak through the cache either.
- Frames from the host application are shown as `app/[redacted]` with no
  path, so the merchant's own code layout is not shared.
- Only errors whose `source` starts with `spree` or whose first application
  frame is inside a Spree gem are kept. A merchant's own app errors are not
  ours to collect.
- With no shared cache store (`:memory_store` across several processes), the
  section says "per-process; restart clears it", and the report still works.

#### `bin/rails spree:info`

Internal plumbing for `spree info`, with no `desc` so it stays out of
`bin/rails -T`; the CLI is the supported way to get the report from a
terminal (2026-11-12). Prints the Markdown report to standard output. Works with no server
running, which matters when the dashboard is the thing that is broken.
`FORMAT=json` prints the hash with the Markdown in it, on one line, which
is what `spree info` reads. `SHOW_NAMES=1` is deliberately not offered; there
is no flag that adds names.

#### Admin API

`GET /api/v3/admin/diagnostics` on `Spree::Api::V3::Admin::DiagnosticsController`:
singleton, `skip_scope_check!`, JWT only (a secret key gets a 404, as on
`/updates`), `authorize! :manage, current_store`. The response is the report
hash plus `markdown`, `issue_url` and `issue_prefilled`, rendered by
`Admin::DiagnosticsSerializer`, so Typelizer emits `Diagnostics` and
`@spree/admin-sdk` gets `adminClient.diagnostics.get()`. The controller adds a
"Client" section with the request's user agent. An rswag spec documents it.

**The server renders the whole report (2026-11-11).** Callers pass what only
they can see as `extra_sections` (the dashboard's browser, the CLI's
tooling), and the server returns the Markdown and the issue link with them
in. The CLI and the dashboard never edit or rebuild the Markdown, so its
format and the issue form URL live in one place. `issue_url` is pre-filled
when it fits in 6,000 characters and is the empty form otherwise
(`issue_prefilled: false`).

#### Dashboard: Settings → System info

- `settings/system-info.tsx` in `@spree/dashboard`. Admin dashboard only;
  the seller panel doesn't get it.
- Shows each section as a read-only card, then the Markdown preview.
- Actions:
  - **Copy as Markdown** — copies the report, browser included.
  - **Report an issue on GitHub** — opens the Report an issue dialog.
- The error log shows each entry's request ID, so the admin can find the
  matching line in their own logs.

#### Dashboard: Send feedback

Added 2026-11-11, because a report reachable only from a settings page was
not something an admin found when something went wrong.

- **Send feedback** in the account menu opens a dialog for every staff
  member, with three kinds:
  - **Report a bug** fills the GitHub issue form's `description`, `logs`
    and `environment` fields: the admin's message, this tab's last five
    failed Admin API requests (method, path, status, error code and request
    ID only, never bodies or query strings; can be unticked) and the
    diagnostics report when the admin can manage the store.
  - **Suggest an idea** and **Something else** open a GitHub discussion in
    the Ideas or General category, with the message and the Spree version.
- When the Admin API answers with a 5xx, an error toast offers **Report**,
  which opens the dialog on a bug report. At most one toast every 10
  seconds, since failed queries are retried.
- The developer tools drawer and System info open the dialog on a bug
  report.
- When a link would be too long, the largest part is copied to the
  clipboard and the page opens with the rest.

#### CLI: `spree info`

- Runs `spree:info` with `FORMAT=json` through `captureTask`, passing its
  own section in `SPREE_INFO_CLIENT`: Node, package manager, `@spree/*`
  package versions from the project, OS, and the Docker version.
- `spree info --json` and `spree info --issue` (opens the pre-filled issue in
  the browser, with the same clipboard fallback as the dashboard).
- `spree info` is not on the telemetry allowlist and sends nothing.

#### GitHub issue form

`.github/ISSUE_TEMPLATE/bug_report.md` becomes `bug_report.yml` with fields
for what happened, what was expected, steps to reproduce, and a required
`environment` textarea: "Paste the output of `spree info`, `bin/rails
spree:info`, or Dashboard → Settings → System info". Its `id` is
`environment`, which the pre-filled URLs depend on. `config.yml` keeps blank
issues off.

### Phase 2 — Standard "View as JSON"

Today `PageHeader` accepts `jsonPreview: { title, fetch, endpoint,
resolveLink }` and about sixteen pages build it by hand, mostly from data the
page already loaded. Pages without a `PageHeader` resource (Store settings,
Markets, Channels and others) have none.

- `PageHeader` gains `endpoint?: string`. When it is given together with
  `resource`, the drawer is wired automatically. It uses the resource itself
  as the payload (no second fetch), `spreeJsonLinkResolver` as the link
  resolver (provided through `dashboard-core` context, so `dashboard-ui`
  stays free of Spree terms), and the page title as the drawer title.
- `jsonPreview` stays for pages that need a custom fetch, such as Orders,
  which load a different shape than the header shows.
- Settings pages without a detail header (Store, Markets, Channels, Payment
  methods, Taxes) get the same "View as JSON" action through
  `SettingsPageHeader`.
- The drawer gains "Copy JSON" and "Copy as curl". Curl uses a placeholder
  token, never the real one.
- A Vitest check lists dashboard detail routes and fails when one renders a
  `PageHeader` with a `resource` but no `endpoint` and no `jsonPreview={false}`.
- The seller panel gets the same behaviour, since it uses the same
  `PageHeader`.

### Phase 3 — Developer inspector

- `sdk-core` gains an optional `onRequestComplete` callback in its client
  options, called with method, path, query, status, duration, request ID
  (from the existing `X-Request-Id` response header), request body and
  response body. Bodies are passed as references, not copied, so the cost
  when nobody listens is zero.
- `dashboard-core` always keeps the last 50 entries in memory in a
  `DeveloperInspectorProvider` and renders a bottom drawer, opened with a
  keyboard shortcut or from the user menu. There is no toggle (2026-11-11):
  a toggle meant the request behind a bug was gone by the time an admin
  turned it on. The cap keeps a tab's memory small, and nothing leaves the
  tab.
- Tabs: **Requests** (list plus detail, with "Copy as curl", "Copy as SDK
  call", "Copy response"), **Errors** (failed requests with the API error
  code and request ID), **Webhooks** (links to existing webhook deliveries),
  and **System** (the Phase 1 report).
- The `Authorization` header and any field named `password`, `token` or
  `secret` are masked in the stored entries.

## Migration Path

1. Extract `Spree::Diagnostics::Stack` from `Spree::UpdateCheck#query`, with
   `UpdateCheck` calling it. No behaviour change, covered by the existing
   specs.
2. Add `Spree::Diagnostics`, its sections, the extension registry, the
   reportable-preference flag, and `bin/rails spree:info`.
3. Add `Spree::Diagnostics::ErrorLog` and the Rails error subscriber, with a
   spec asserting that no message text and no host-app path reaches the cache.
4. Add `GET /api/v3/admin/diagnostics`, its serializer, its rswag spec, the
   Typelizer types and `adminClient.diagnostics`.
5. Convert `bug_report.md` to `bug_report.yml`.
6. Add the Settings → System info page, with a Playwright spec for copy and
   the pre-filled issue link.
7. Add `spree info` to `@spree/cli`.
8. Phase 2: `PageHeader` `endpoint`, the settings header action, copy
   actions, the Vitest coverage check, and backfill every detail and settings
   page.
9. Phase 3: the `sdk-core` callback, the inspector provider and drawer, and a
   Playwright spec.
10. Docs: a "Reporting issues" page under developer docs, linked from the
    issue form and the upgrade guide.

## Constraints on Current Work

- New detail pages pass `resource` and an endpoint to `PageHeader` (or
  `jsonPreview` today), so Phase 2 doesn't need to touch them again.
- A setting that must never appear in a bug report must not be a boolean,
  number or fixed-choice string; those are reported when changed.
- Report errors through `Rails.error.report` with a `source` starting with
  `spree.`, as checkout already does, rather than `Rails.logger.error`.
  Only errors reported this way reach the diagnostics error log.
- Don't expose the running Spree version anywhere new outside `/updates`
  and `/diagnostics`, and never to secret API keys.
- Because this ships in a patch release, don't add migrations or change
  existing serializers, `PageHeader` props or `sdk-core` signatures as part
  of this work. Everything is a new optional prop, option or endpoint.
