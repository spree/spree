# Fulfillment Profiles

**Status:** Design Finalized
**Target:** Spree 6.0
**Depends on:** `6.0-fulfillment-and-delivery.md` (shipped waves), `6.0-delivery-rate-provider.md` (dynamic carrier rates), `6.0-delivery-zones.md`, `6.0-product-types.md`
**Author:** Damian Legawiec + Claude (design sessions 2026-08-09)
**Last updated:** 2026-08-09

## Summary

`Spree::FulfillmentProfile` is the store-scoped grouping that decides how a set of products ships: which origins can fulfill them, which destination zones apply, and which delivery methods are offered. Products reference a profile directly (nil falls back to the store's default profile); carts split per profile; a package's candidate methods are exactly its profile's methods filtered by origin and destination. The model is **ShippingCategory promoted, not replaced**: the 5.x table and the product foreign key are renamed in place, so historical data migrates by rename rather than by copy.

This supersedes three earlier decisions: "fulfillment types are NOT a model", "named delivery groups are 6.1-if-needed", and live-by-reference `fulfillment_types` on ProductType. Rationale for reversing inside the 6.0 window: there is no rewrite window in 6.1; custom string types were second-class (providers declare handled types, so a custom type could not use any carrier rate provider); the origin axis (stock locations ↔ methods) did not exist for shipping methods at all; and the array-on-ProductType was the sole live-by-reference exception to the product-type template doctrine.

## The model

```
Spree::Store ─────────────────────────────── has many; exactly ONE default per store
 ▼
Spree::FulfillmentProfile                    spree_fulfillment_profiles   (prefix fp_)
 │   store_id · name · default · position    (renamed spree_shipping_categories)
 │   "General" (default) · "Oversized" · "Digital"
 │
 ├──< Spree::Product                         spree_products.fulfillment_profile_id
 │      (renamed shipping_category_id; nullable → default profile fallback)
 │      ProductType.fulfillment_profile_id = creation-time template:
 │        stamps the product at creation, never manages it afterwards
 │
 ├──< profile ↔ StockLocation join           spree_fulfillment_profile_locations
 │      which origins can fulfill this profile; no rows ⇒ every store location
 │
 ├──< Spree::DeliveryZone                    gains fulfillment_profile_id
 │      country/state/postal members unchanged
 │
 └──< Spree::DeliveryMethod
        fulfillment_profile_id  (required)
        delivery_zone_id        (nullable; must belong to the same profile;
                                 nil = no destination restriction — digital,
                                 pickup, or genuinely worldwide shipping)
        modality                (renamed fulfillment_type: shipping | pickup |
                                 digital; validated against
                                 Spree::DeliveryMethod.modalities, a
                                 class_attribute extensions append to)
        ships-from narrowing    (existing DeliveryMethodStockLocation join,
                                 optional subset of the profile's locations;
                                 empty = all; Pickup keeps its policy override)
        rate/fulfillment providers · calculator · markup · carrier services ·
        rules — unchanged from the dynamic-carrier-rates work
```

No location-group layer: named origin bundles were considered (2026-08-09) and dropped — per-method ships-from narrowing expresses the multi-origin case ("UPS from the US warehouse, DPD from the EU one") without a third entity, and a group layer can be added additively in 6.1 if merchants outgrow that.

## Runtime flow

1. **Split** — `Stock::Splitter::FulfillmentProfile` (replaces `Splitter::FulfillmentType`) partitions cart contents by each item's resolved profile.
2. **Allocate** — the Coordinator allocates a profile's items only from stock locations the profile covers (its join; empty = all).
3. **Quote** — for a package (profile, origin): candidates are the profile's methods whose ships-from set covers the origin, whose zone is nil or includes the ship address, passing the existing rule/calculator/audience filters; rate providers then fan out (multi-rate carriers untouched).
4. **Derive, never declare twice** — `Product#digital?` ⇐ its profile's methods are all digital-modality; pickupable ⇐ the profile contains a pickup method; the order requires an address ⇐ any item's profile has a method whose provider `requires_address?`.

## Key Decisions (do not deviate without discussion)

- **Profile on the Product, template on the ProductType (2026-08-09).** `fulfillment_profile_id` lives on `spree_products`; ProductType's own `fulfillment_profile_id` is stamped onto products at creation only. This restores the uniform "creation-time template" doctrine that the `fulfillment_types` array violated, and makes a product's shipping behavior inspectable on the product itself.
- **Migration by rename, not by copy (2026-08-09).** `spree_shipping_categories` → `spree_fulfillment_profiles`; `spree_products.shipping_category_id` → `fulfillment_profile_id`. 5.x products arrive assigned; the 5.x "Digital" category becomes the Digital profile. What the rename cannot express is handled by `spree:upgrade:migrate_fulfillment_profiles`: store assignment (5.x categories were global; products are single-owner since 5.5, so each profile goes to the store whose products use it, duplicated + remapped when shared — loudly logged), default-profile flagging ("Default"-named else most-used, else a created "General"), and collapsing `spree_shipping_method_categories` (m:n) into the method's single `fulfillment_profile_id` (unambiguous for one binding; default profile + LOUD warning for several). The m:n table survives to 6.1 solely as that task's source.
- **Modality is a method concern.** `fulfillment_type` on the method is renamed `modality` and means the delivery mechanics (shipping/pickup/digital). The `Spree.fulfillment_types` registry (engine config + `Spree.fulfillment_types` accessors) is deleted outright — unreleased 6.0-dev surface. The vocabulary is `Spree::DeliveryMethod.modalities` (class_attribute, default `%w[shipping pickup digital]`); provider `fulfillment_types` declarations keep their name and mean modalities.
- **`ProductType#fulfillment_types` array is removed** (column + validation) in favor of the template profile reference. Capabilities derive from the profile's methods rather than being declared on the product side.
- **Zones belong to the profile; a method belongs to at most one zone.** The `spree_delivery_method_zones` m:n join is dropped (backfilled to the first zone with a warning on multiples). A method with no zone has no destination restriction.
- **One default profile per store**, enforced like `StockLocation#default` (`ensure_one_default`); undeletable; created by a `Store` `after_create` hook and by seeds/upgrade for existing stores. Non-default profiles are deletable only when no products reference them (model-level guard, per the RBAC axis-B convention).
- **Competitor names never appear in code or comments** — grounding stays in plan documents.

## Migration Path

1. Structural migration (6.0, `[8.1]`): renames + new columns/joins as diagrammed; adds `store_id`/`default`/`position` to the renamed profiles table (nullable until the upgrade task assigns them; `null: false` tightening lands in 6.1); drops `spree_delivery_method_zones` after backfill.
2. `Spree::ShippingCategory` + `Spree::ShippingMethodCategory` classes, deprecated associations (`Product#shipping_category*`, `Variant#shipping_category*`, `DeliveryMethod#shipping_categories*`), factories, permission-catalog subject, and typelizer entry are deleted. The permission catalog gains `Spree::FulfillmentProfile`.
3. `spree:upgrade:migrate_fulfillment_profiles` in the 5.6→6.0 manifest (resumable, anonymous-AR readers for the m:n) performs the judgement work listed above.
4. 6.1: drop `spree_shipping_method_categories`, tighten profile `store_id` constraints.

## Constraints on Current Work

- New delivery features must resolve eligibility through the profile chain — never reintroduce parallel product-side capability arrays.
- Anything reading `fulfillment_type` on methods means modality now; do not overload modality for product segmentation (that is what profiles are for).
- The Store API surface for profiles is read-only derivation (product serializers may expose digital/pickupable); profile management is Admin API only.

## Open Questions

- Whether ships-from narrowing needs promotion to named origin groups (6.1, evidence-first — additive).
- Multi-currency/multi-market interplay: profiles are store-scoped; market-aware profiles deferred to the channels/markets work.
