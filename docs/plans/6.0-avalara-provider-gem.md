# Avalara AvaTax Provider Gem (`spree/providers/avalara`)

**Status:** Design Finalized
**Target:** Spree 6.0
**Depends on:** 6.0-tax-provider.md (Phases 1–5 + 7 shipped to main — this plan IS its Phase 6), 6.0-integrations-admin.md (Integration credential surface), 6.0-service-workflows.md (hooks contract)
**Author:** Łukasz + Claude
**Last updated:** 2026-09-02

## Summary

The first-party reference tax provider for Spree 6.0: a new monorepo gem at `spree/providers/avalara` implementing `Spree::TaxProvider::Base` against Avalara AvaTax — estimate during checkout, commit on completion, void on cancellation, ReturnInvoice on refunds — plus consumption of the typed inputs the 6.0 contract delivers (buyer `TaxIdentifier` → `businessIdentificationNo`, `TaxExemption` entries → entity use codes / exemption numbers) and Avalara address validation rewired onto the `carts.complete.validate` hook. The legacy `spree_avatax_official` extension cannot be ported (it hijacks Adjustments, `Calculator::DefaultTax`, order state-machine transitions and the ERB admin — all removed in 6.0); it serves as the salvage source for AvaTax API mappings and as the upgrade source for merchant data.

## Key Decisions (do not deviate without discussion)

### New monorepo gem, not an in-place rewrite (2026-08-19)

Lives at `spree/providers/avalara`, versioned with Spree, per the providers convention (CLAUDE.md providers table; decisions.md 2026-07-30 reference-providers entry). `spree_avatax_official` remains the 5.x line and is not ported; its repo gains a pointer once the gem ships.

### Naming: gem `spree_avalara`, module `SpreeAvalara` (2026-08-19, confirmed with the author)

Supersedes the `spree_tax_avalara` working name in `6.0-tax-provider.md` Phase 6. `SpreeAvalara::Integration` derives `api_type` `'avalara'` (a class named exactly `Integration` takes its shorthand from the outer module), matching `TaxLine.provider_id: 'avalara'` and the `spree.integrations.avalara.*` locale keys; no Zeitwerk inflection needed; consistent with the flat-name family (`spree_easypost`, `spree_stripe`). The Integration class is `SpreeAvalara::Integration` (easypost convention), NOT the legacy `Spree::Integrations::Avalara` — a provider gem does not plant constants in core's namespace; the upgrade task retypes existing rows.

### Estimate prices the whole owner and fails closed on a service failure (2026-08-19, amended 2026-09-02)

Avalara prices a whole document per API call, so `estimate` ignores the `items` subset for the request, always sends `owner.taxable_items`, and honors replace-all by sweeping and rewriting **all** of its own rows (`provider_id: 'avalara'` — never another provider's). A 5-minute response cache keyed on a request fingerprint absorbs the single-item call sites (`Carts::AddItem`, `UpsertItems`, `LineItem`). Unreachable Avalara **raises** (fail closed — no silent under-collection); a cart with no tax address or no items sweeps and returns (no opinion, not a failure).

**Amended 2026-09-02: a disconnected integration is not a failure.** The original decision raised for a missing or inactive integration too, and that turned an operational toggle into an outage — the integration lookup runs before the "nothing to price" guard, so a market naming Avalara with nothing connected raised out of `Carts::AddItem` and the customer could not add to their cart at all, before any address existed and long before payment. Merchants connect providers at different stages, deactivate one to rotate credentials, and activate it again; none of that may decide whether a store can sell. So every entry point — `estimate`, `commit`, `refund`, and address validation — treats "nothing connected" as no opinion: rows are swept, `pre_tax_amount` is restored, and the misconfiguration is reported through `Rails.error` rather than raised. What still fails closed is a *connected* Avalara that refuses or cannot be reached, which is the case the under-collection argument was really about. Verified live: deactivating mid-cart clears the rows, reactivating restores them, and add-to-cart never breaks.

### Treatment mapping: read Avalara's reason fields, derive only the EU split (2026-08-19)

Avalara returns the treatment cause as structured fields (`nonTaxableType` `"NexusRule"`/`"RateRule"`, `exemptReasonId`/`exemptCertId`/`exemptNo`/`entityUseCode`, `rateTypeCode` `G/S/Z/R`, `isItemTaxable`, `vatCode` — verified against the legacy gem's recorded cassettes), so `taxability_reason` is mostly a deterministic fold. Only `intra_community_supply` vs `reverse_charge` is derived from request-side facts (identifier sent, goods vs service line, ship-from/ship-to countries) — Avalara reports the zero rate but not that distinction, and core's vocabulary deliberately keeps it (different e-invoice categories, K vs AE). Raw details always ride in `TaxLine.data` for re-derivation.

**Amended 2026-09-01 after verifying against a live sandbox company.** Three `SalesOrder` quotes (US, ship-from CA) show the fold cannot rest on the fields this decision originally named:

| case | taxCalculated | exemptAmount | isItemTaxable | detail `taxType` | detail `rate` |
|---|---|---|---|---|---|
| ship-to WA, taxable goods — company has no nexus | 0.0 | 100.0 | false | `Use` | 0.0 |
| ship-to CA, taxable goods — company has nexus | 7.25 | 0.0 | true | `Sales` | 0.06 |
| ship-to CA, `NT` tax code — company has nexus | 0.0 | 100.0 | false | `Sales` | 0.06 |

Three consequences:

- **`nonTaxableType` was absent from every response**, so no predicate may depend on it. Keep reading it when Avalara sends it; never require it.
- **`exemptAmount > 0` is not evidence of a customer exemption.** The whole line lands in `exemptAmount` in both zero-tax cases above, with `entityUseCode: ""`, `exemptCertId: 0` and `exemptNo: ""`. Certificate evidence means a code we sent, or a returned `exemptCertId` / `exemptNo` — not the amount.
- **`taxType` is the registration discriminator.** `Use` is how AvaTax says the seller is not registered to collect there (the buyer owes use tax); `Sales` says the seller collects, so a zero on a `Sales` line is about product or jurisdiction rules rather than nexus. `liabilityType` reads `Seller` in all three and discriminates nothing. The detail's `rate` separates the two zero cases independently: no nexus returns rate 0, while an exempt tax code returns the jurisdiction's real rate against a fully non-taxable amount.

A use-flavoured tax type does **not** on its own mean nothing was collected. Several states — Alabama, Arizona and Tennessee among them — call what a *registered* out-of-state seller collects "seller's use tax" rather than sales tax: same money, collected by the seller, different statutory name. So row 7 requires zero rate and zero tax alongside the type, and a collected use-tax line falls through to rows 9–10 as reduced or standard rated. That holds however Avalara spells the case (`Use` versus a distinct `SellersUse`), which is why the predicate does not depend on knowing — Phase 7 records a registered-remote-seller destination to settle it.

Empty strings and zeros are how AvaTax says "absent", so predicates test `.present?` / `.to_i.positive?`, never `.nil?`. These observations are US sales/use tax from one sandbox company; the EU rows still rest on Phase 7.

### Document id lives in `order.metadata`, no ledger table (2026-08-19)

`order.metadata['avalara_transaction_id']`, per the tax-provider plan's resolved question. The legacy `SpreeAvataxOfficial::Transaction` table dies. Idempotency does not need a ledger: commit uses `create_or_adjust_transaction` keyed on `(companyCode, order.number, SalesInvoice)`, void/refund key on fixed document codes and treat already-voided/duplicate as success.

### Exemptions: the gem consumes the core seam, adds no storage (2026-08-19)

The gem takes the typed `exemptions:` input exactly as core assembles it — `Spree::Tax::ResolveExemptions` resolving the order's company's active certificates for the tax address — and translates each entry to `entityUseCode`/`exemptionNo` (document-level or per-line). **No `Dependencies` swap and no gem-owned exemption storage**: company exemptions are fully covered by core, and whether *customer-level* (no-Company) exemptions need first-class handling is an Open Question, with the suggestion that core — not the gem — should grow it. Until that resolves, individual buyers' exemptions work through Avalara's own certificate store (the treatment mapping already records exemptions Avalara applies on its own — row 2). Legacy `spree_users.vat_id` migrates to core `Spree::TaxIdentifier`; the legacy entity-use-code DB table + seeder become a frozen 17-code constant used for reason-code translation; the legacy user-level exemption columns are deliberately left in place as the future migration's source.

### Address validation enforces at `carts.complete.validate`, never `Spree.validators.addresses` (2026-08-19)

The model-level registry fires on every address save — address book, admin — with no checkout context, and would let Avalara block a customer from saving a legitimate address. The hook handler is scoped to the order's tax address, gated on the `address_validation_enabled` preference + US/CA, and **fails open on transport errors** (advisory validation must not import Avalara downtime into checkout; only `estimate` fails closed). The `Address::Validate` service stays public for storefronts wanting feedback at the address step.

### Capabilities: `unsupported_capabilities = []` (2026-08-19)

AvaTax handles US local tax, reverse charge and proportional delivery tax natively. EU OSS threshold behavior depends on the merchant's Avalara company profile configuration, not on this gem — a README note, not a false capability warning.

### Tax inclusiveness derives from the tax destination, not the browsing market (2026-08-19)

`taxIncluded` per line and `included` on rows read `Market#tax_inclusive` — the sanctioned external-provider wiring of the column whose fate `6.0-tax-provider.md` Phase 9 left open — but **resolved through the tax address, never read naively off `owner.market`**. `owner.market` is browsing context (seeded from `Spree::Current.market`, re-resolved **by currency** on a currency change, never validated against the address — the one guard, `Carts::Update#clear_shipping_address_if_outside_market`, runs only on an explicit market change and is bypassed by the currency-driven `before_validation` resolution). So the browsing market can diverge from the tax destination through mundane triggers: a currency switcher flipping the market under a fixed address, a bill-address tax destination (digital goods) never checked against markets at all, or one API request omitting the `x-spree-country` hint dropping the cart onto the default market. This is the recorded 5.x bug fixed by spree_avatax_official PR #198; shipping the 6.0 gem with the shape the 5.x gem just fixed would be a regression.

Resolution policy (PR #198's, restated for 6.0), a **single overridable module function** `SpreeAvalara.tax_inclusive?(owner)`:

1. No tax address country yet → `owner.market&.tax_inclusive` (nothing to resolve from).
2. The cart's own market covers the tax country (`market.country_codes.include?(country)`) → keep it — in the well-behaved setup (German buyer on the German market) this is a no-op identical to the naive wiring.
3. Otherwise the first store market covering the tax country → its flag.
4. No market covers it → fall back to `owner.market&.tax_inclusive`.

The resolved flag (never the raw market flag) feeds `taxIncluded`, the rows' `included`, and the estimate cache key — so an address change that flips inclusiveness busts the cache instead of serving a stale calculation. Consequence unchanged: `VatPriceCalculation` restatement is hard-gated on the Internal provider, so an Avalara market states destination prices via geo-scoped price lists (README caveat).

### The legacy order-level discount mechanism dies (2026-08-19)

6.0 distributes order-level promotions into `LineItem#taxable_basis`, so lines are sent already-discounted with `discount: 0` and `discounted: false`. No `avatax_discount_amount`, no line flagging.

### Upgrade task points blank markets at Avalara, and only blank ones (2026-08-19)

For stores with an active Avalara integration, the upgrade task sets `tax_provider` on markets whose value is **literally blank** (nil/empty — today's fallback-to-Internal state) and never rewrites a value that is already set: an explicitly chosen provider, including an explicit Internal, is preserved. Rationale: the 5.x gem was store-global, so a blank market on an upgrading Avalara merchant means "was calculating through Avalara" — leaving it blank would silently fall back to Internal, whose rate table is empty for these merchants (an under-collection window). Every change is logged per market.

### Standalone-refund parity deferred past v1 (2026-08-19, confirmed with the author)

Core 6.0 routes only `Returns::Refund` to the provider; a goodwill refund with no return is not filed with Avalara in v1 (README documents the gap). The deferred subscriber (`refund.created`, percentage refund, skipping refunds originated by the returns flow — see Deferred under Migration Path) waits for real demand — and core may yet wire standalone refunds into the provider contract, which would make a gem subscriber redundant.

### Integration

Preference set identical to legacy `Spree::Integrations::Avalara` — `account_number`, `license_key` (`:password`), `endpoint` (default sandbox `https://sandbox-rest.avatax.com`), `company_code`, `address_validation_enabled` (false), `commit_transaction_enabled` (true), `show_rate_in_label` (false) — identical names so serialized preferences survive the upgrade STI retype untouched. `integration_group = 'tax'`, `integration_name = 'Avalara AvaTax'`, `can_connect?` via `client.ping` checking `authenticated`. Class helpers `active_for(store)` / `active_for!(store)` (raises `SpreeAvalara::NotConfiguredError`). The dashboard renders the credential form from the preference schema — no admin UI code in the gem.

### Client

Wraps `AvaTax::Client` (`faraday_response: true`; open 2.0s / read 6.0s timeouts, ENV-overridable `SPREE_AVALARA_*` — deployment config, never preferences). Replaces the legacy `AvaTax::API#request` monkey-patch with wrapper-level retry (≤2 retries on connection/timeout errors — safe because every write is idempotent). Methods: `create_transaction`, `create_or_adjust_transaction`, `void_transaction`, `resolve_address`, `ping`. Non-2xx or `body['error']` → `SpreeAvalara::RequestError` (status + parsed details). Predicates `duplicate_document_error?` / `already_voided_error?` centralize idempotency matching (exact AvaTax error codes confirmed at cassette recording).

### estimate

```ruby
def estimate(owner, items = nil, tax_date: nil, tax_identifier: nil, exemptions: [], context: {})
  integration = Integration.active_for(owner.store)          # nil = no opinion (see the 2026-09-02 amendment)
  taxable = owner.taxable_items                              # ALWAYS the whole owner; `items` subset ignored
  return sweep!(owner) if taxable.empty? || owner.tax_address.nil?   # no opinion, not a failure

  body = Rails.cache.fetch(EstimateCacheKey.new(owner, taxable, integration, tax_identifier, exemptions).key,
                           expires_in: 5.minutes) do
    integration.client.create_transaction(
      TransactionPresenter.new(owner: owner, integration: integration, items: taxable,
                               type: 'SalesOrder', tax_date: tax_date,
                               tax_identifier: tax_identifier, exemptions: exemptions).call
    )                                                        # raises SpreeAvalara::RequestError → fails closed
  end

  lines = TransactionLine.from_response(body)
  ApplicationRecord.transaction do
    sweep!(owner)                                            # owner-wide, provider-scoped
    lines.each { |line| Spree::TaxLine.create!(line.to_tax_line_attributes(item: ..., owner: owner)) }
    write_pre_tax_amounts!(taxable, lines)
  end
end

def sweep!(owner)
  owner.tax_lines.where(provider_id: 'avalara').delete_all   # never another provider's rows
end
```

The destination-derived inclusiveness helper (see Key Decisions), a single overridable module function:

```ruby
# lib/spree_avalara.rb
def self.tax_inclusive?(owner)
  country = owner.tax_address&.country_code
  return owner.market&.tax_inclusive || false if country.blank?

  market = owner.market if owner.market&.country_codes&.include?(country)
  market ||= owner.store.markets.detect { |candidate| candidate.country_codes.include?(country) }
  (market || owner.market)&.tax_inclusive || false
end
```

- `Rails.cache` (5 min) keyed on `EstimateCacheKey`: integration (id, updated_at, company_code), tax_address, market id + **resolved tax inclusiveness** (`SpreeAvalara.tax_inclusive?(owner)` — destination-derived, see Key Decisions), currency, tax_identifier (kind, value), exemptions digest, per-item `(prefixed_id, quantity, taxable_basis, tax_code, ship-from)`. Success bodies only. Estimate runs **inside the cart transaction/lock** in `Carts::RecalculateTotals` — the cache plus tight timeouts is what keeps that tolerable.
- Request type `SalesOrder` (never persisted by Avalara — no checkout-time Adjust dance). `businessIdentificationNo: tax_identifier&.value`; `customerCode` from owner email; `discount: 0`.
- Lines: `number: item.prefixed_id` (kills legacy `avatax_uuid`/`HasUuid`), `amount: taxable_basis` (`fee.amount` for fees), `taxIncluded` from `SpreeAvalara.tax_inclusive?(owner)` (destination-derived — see Key Decisions). `taxCode`: line item → `tax_category&.tax_code` → store default category's `tax_code` → `'P0000000'`; fulfillment → its selected delivery rate's delivery method's category `tax_code` → `'FR'` (a fulfillment carries no `tax_category` of its own — corrected 2026-09-01); fee → store default category's `tax_code`, else omit (parity with Internal, which taxes category-less items with the default category). Per-line `ShipFrom` = fulfillment's stock location (line item through `line_item.fulfillments`, the `fulfillment_items` association — **not** `inventory_units`, which is a deprecated alias; fallback first fulfillment); `ShipTo` = `owner.tax_address` (already encapsulates the `tax_using_ship_address` store preference — never re-derive).
- Exemption inputs: one entry with no `item_overrides` covering the destination → document-level `entityUseCode`/`exemptionNo`; otherwise per line via `covers_item?`/`covers_jurisdiction?`/`reason_code_for` through `EntityUseCodes` (17 Avalara codes pass through; a label resolves through the derived `BY_NAME` inverse; anything else → `'L'` with the raw reason in row `data`).
- After writing rows: maintain `item.pre_tax_amount` via `update_column` (`taxable_basis - (included ? line_tax : 0)`) — `Returns::Refund#received_total` reads it; mirrors `Internal#store_pre_tax_amount`.
- `context:` accepted, unused in v1 (reserved for `set_tax_line_context` extras).

### TransactionLine → Spree::TaxLine

`SpreeAvalara::TransactionLine` is an `ActiveModel::Model` + `Attributes` value object, one per Avalara response line (the `SpreeEasyPost::TrackerEvent` pattern; named `TransactionLine` so a bare `TaxLine` in the gem's namespace still resolves to `Spree::TaxLine`). Matched by `lineNumber == prefixed_id` (unknown lineNumber raises — protocol violation). One row per sent line, zero-amount treatments included:

```ruby
{ cart|order (XOR), line_item_id|fulfillment_id|fee_id (from prefix li_/ful_/fee_),
  tax_rate_id: nil, amount: line['taxCalculated'], rate: details.sum('rate'),
  label:, included:, provider_id: 'avalara', taxability_reason:,
  country_code:, state_code:, data: { 'avalara' => { details, exemptAmount, … } } }
```

`taxability_reason` mapping (first match wins; all values in `TaxLine.taxability_reasons`' shipped vocabulary; each row pinned by a cassette-backed spec in Phase 7). Rows 1, 2, 6 and 7 were corrected 2026-09-01 against live sandbox responses — see the amendment under Treatment mapping. **Row order matters:** row 6 must not claim a no-nexus line, which also reports `isItemTaxable: false`, so it tests the detail's rate rather than that flag:

| # | Signal | reason |
|---|---|---|
| 1 | `exemptAmount > 0` **and** we sent `entityUseCode`/`exemptionNo` | `customer_exempt` |
| 2 | `exemptAmount > 0` **and** Avalara returned its own certificate (`exemptCertId.to_i.positive?` or `exemptNo.present?`, not sent) | `customer_exempt` |
| 3 | zero VAT (`rateTypeCode 'Z'`/`vatCode`) + identifier sent + cross-border goods line (line_item/fulfillment, EU ship-from ≠ ship-to) | `intra_community_supply` |
| 4 | zero VAT + identifier sent, service/domestic reverse-charge case | `reverse_charge` |
| 5 | zero tax, destination outside the ship-from tax regime (export detail marker) | `export` |
| 6 | `nonTaxableAmount == lineAmount` on a `taxType: 'Sales'` detail whose `rate > 0` — tax applies here, this line does not | `product_exempt` |
| 7 | detail `taxType: 'Use'` **with zero rate and zero tax**, or no details at all (`nonTaxableType: "NexusRule"` when sent) | `not_collecting` |
| 8 | details present, all rates 0 via jurisdiction `RateRule` where the jurisdiction levies no such tax | `not_subject_to_tax` (else `zero_rated`) |
| 9 | rate > 0, `rateTypeCode 'R'` (reduced) | `reduced_rated` |
| 10 | rate > 0 | `standard_rated` |
| 11 | rate == 0 fallback | `zero_rated` |

### commit / void / refund

- **commit** (idempotent — completion is replayable): `create_or_adjust_transaction`, type `SalesInvoice`, `code: order.number`, `commit:` from `preferred_commit_transaction_enabled` (false = file uncommitted, legacy behavior), `tax_date: order.completed_at`, identifier from the order's frozen snapshot. Store `body['id']` in `order.metadata['avalara_transaction_id']` via `update_column`. Rescue `duplicate_document_error?` as success; otherwise raise (loud failure in the finalize `external_step` is correct).
- **void**: `void_transaction(order.number, code: 'DocVoided')`; nil integration → return (nothing filed); already-voided/not-found → success.
- **refund**: line-level `ReturnInvoice` via `create_transaction` (NOT the percentage `RefundTransactionModel` — the contract credits only the returned lines). Negative amounts from `per_unit_pre_tax × received_quantity`, scaled by `min(amount / lines_worth, 1)` when `amount:` is short (restocking fee → proportional). `taxOverride: {type: 'TaxDate', reason: 'Refund', taxDate: tax_date || order.completed_at}`. Code `"#{order.number}-#{return.number}"` → idempotent; duplicate = success.
- **service_tax_rate**: stays the base `nil` default in v1 (documented).

```ruby
def commit(order)
  integration = Integration.active_for(order.store)
  return report_disconnected(order) if integration.nil?      # never refuse a paid order
  body = integration.client.create_or_adjust_transaction(
    createTransactionModel: TransactionPresenter.new(
      owner: order, integration: integration, items: order.taxable_items,
      type: 'SalesInvoice', code: order.number,
      commit: integration.preferred_commit_transaction_enabled,
      tax_date: order.completed_at,
      tax_identifier: order.resolved_tax_identifier,          # frozen order snapshot
      exemptions: order.usable_exemptions                      # made public in core, 2026-09-01
    ).call
  )
  order.metadata['avalara_transaction_id'] = body['id'].to_s
  order.update_column(:metadata, order.metadata)              # replay-safe, no validation churn
rescue SpreeAvalara::RequestError => error
  raise unless integration.client.duplicate_document_error?(error)  # replayed completion = success
end

def refund(order, return_items, amount: nil, tax_date: nil)
  integration = Integration.active_for(order.store)
  return report_disconnected(order) if integration.nil?
  lines_worth = return_items.sum { |item| per_unit_pre_tax(item) * item.received_quantity }
  return if lines_worth <= 0

  scale = amount.nil? ? 1 : [amount.to_d / lines_worth, 1].min      # restocking fee → proportional
  integration.client.create_transaction(
    RefundPresenter.new(
      order: order, integration: integration, return_items: return_items, scale: scale,
      code: "#{order.number}-#{return_items.first.return.number}",  # idempotency key
      tax_override: { type: 'TaxDate', reason: 'Refund',
                      taxDate: (tax_date || order.completed_at).strftime('%Y-%m-%d') }
    ).call
  )
rescue SpreeAvalara::RequestError => error
  raise unless integration.client.duplicate_document_error?(error)  # replayed Returns::Refund = success
end
```

### Exemption translation

`Spree::Purchase::Taxation#usable_exemptions` moves above `private` for this (2026-09-01): a provider needs the same exemption evidence at commit time that core hands it as an argument at estimate time, and reaching past the boundary with `send` from a gem breaks quietly on a refactor. It is the only core change the gem requires.

The gem stores nothing and swaps nothing: `estimate`/`commit` receive the `exemptions:` array core resolved (`Spree::Tax::ResolveExemptions` → the order's company's active certificates for the tax address, filtered by `usable_exemptions`). `EntityUseCodes::ALL` — the legacy Seeder's 17 Avalara codes as a frozen constant — turns each entry's `reason_code` into an `entityUseCode`: a code passes through, a label resolves through the derived `BY_NAME` inverse (`RESALE`→`G`, `FEDERAL_GOV`→`A`, … one normalization reconciles case and underscores), and anything else takes `'L'` with the raw reason kept in row `data`. **Nothing is hand-aliased** — a name the inverse does not hold is a name nobody can show Avalara meant, and the fallback files a claim Avalara will look at rather than the wrong code. Customer-level (no-Company) exemptions are an Open Question — see there.

**Where the merchant's reason code comes from (amended 2026-09-02).** The dashboard offered six values of its own (`resale`, `government`, …) while telling the merchant the selection becomes the tax engine's entity use code — so on Avalara four of the six mapped to the `'L'` fallback, and the merchant had no way to say "federal government" at all. The vocabulary belongs to whichever engine has to understand it, so core grows `Spree.tax_exemption_reason_codes` — declared **empty**, keyed by the name a merchant sees — and a provider registers its own. The gem registers `EntityUseCodes::ALL` under `SpreeAvalara::TaxProvider.display_name` from its engine, merging rather than assigning so a second engine's vocabulary survives. `GET /admin/companies/:id/tax_exemption_certificates/reason_codes` answers a group per provider (and the six neutral values when nothing is registered, so a store with no provider installed still has something to pick from); the dashboard select groups by provider. `REASON_CODE_MAP` and the `'L'` fallback stay exactly as described above — they now catch a legacy row or a hand-written API call rather than every certificate a merchant records.

### Address validation

`SpreeAvalara::Address::Validate` (salvaged; `SUPPORTED_COUNTRIES = %w[US CA]`, `resolve_address`; signature `call(address:, store:)`). `SpreeAvalara::CheckoutAddressValidation` on `carts.complete.validate`: guards — active integration, `preferred_address_validation_enabled`, tax address present + US/CA. Unresolvable address → `workflow.errors.add(:base, …)` + `workflow.reject!`. Transport failure → return silently (fail open).

```ruby
module SpreeAvalara
  class CheckoutAddressValidation
    def call(workflow)
      cart = workflow.cart
      integration = Integration.active_for(cart.store)
      return unless integration&.preferred_address_validation_enabled

      address = cart.tax_address
      return if address.nil? || !Address::Validate::SUPPORTED_COUNTRIES.include?(address.country_code)

      result = Address::Validate.new.call(address: address, store: cart.store)
      return if result.success?
      return if result.error.transport?     # Avalara down ≠ bad address — advisory validation fails open

      workflow.errors.add(:base, :avalara_address_invalid, message: result.error.summary)
      workflow.reject!
    end
  end
end
```

## Migration Path

Phased PR slices; each phase is independently green. Testing runs on Ruby 4.0, `rake test_app` + rspec per easypost. Phases 1–6 ship only specs that make no claims about Avalara response shapes — payload-builder assertions (requests we author) and provider mechanics with the Client stubbed. Everything that depends on what Avalara actually returns is cassette-backed and lands in Phase 7, when the cassettes are re-recorded against a sandbox account.

### Phase 1: gem skeleton + Integration + Client

- gemspec/Gemfile/Rakefile, engine registrations, `lib/spree_avalara.rb`, `SpreeAvalara::Integration`, `SpreeAvalara::Client`, locale, factories, spec infrastructure, CI job (mirror easypost's), monorepo CLAUDE.md providers-table row.
- The Avalara card renders in the dashboard integrations gallery from the preference schema alone; `can_connect?` is checked manually against a sandbox account.

### Phase 2: estimate + TaxLine mapping

- `TaxProvider#estimate`, `TransactionPresenter`/`ItemPresenter`/`AddressPresenter`, `EstimateCacheKey`, `SpreeAvalara.tax_inclusive?`, `TransactionLine` (attributes + mapping-table code paths), `pre_tax_amount` maintenance, the provider-scoped sweep.
- Specs: presenter hash assertions (lineNumbers = prefixed ids, destination-derived `taxIncluded`, `discount: 0`, tax codes); provider mechanics with the Client stubbed — sweep/replace-all across two estimates, foreign-provider rows survive the sweep, `pre_tax_amount` writes, cache hit skips the client, no-address/empty-items paths, failure raises. The mapping table's row-by-row verification is deliberately deferred to Phase 7 (it asserts response shapes).

### Phase 3: commit / void / refund

- The three lifecycle methods, `RefundPresenter`, the idempotency predicates (`duplicate_document_error?` / `already_voided_error?` — carrying `# verify against cassette` comments until Phase 7).
- Specs (stubbed client): commit replay + metadata write, void already-voided, refund scaling math + document code.

### Phase 4: exemption translation

- `EntityUseCodes` constant + `BY_NAME` inverse, presenter exemption placement (document-level when one entry with no `item_overrides` covers the destination, otherwise per-line via `covers_item?`/`covers_jurisdiction?`/`reason_code_for`), `tax_identifier` → `businessIdentificationNo` already wired in Phase 2.
- Specs: reason-code mapping, placement (document vs line), company-certificate entries flowing end to end with the Client stubbed.

### Phase 5: address validation

- `SpreeAvalara::Address::Validate`, `CheckoutAddressValidation` + hook registration.
- Specs: handler reject vs fail-open-on-transport paths (workflow double); `Spree.hooks.validate!` passes on dummy-app boot.

### Phase 6: upgrade task + README

`rake spree_avalara:upgrade` — idempotent, every step guarded by `table_exists?`/`column_exists?` so fresh installs no-op; gem-owned, since core knows nothing of the legacy gem:

1. Integration STI retype — preference payloads carry over untouched because the preference names are identical:

   ```ruby
   Spree::Integration.where(type: 'Spree::Integrations::Avalara')
                     .update_all(type: 'SpreeAvalara::Integration')
   ```

2. `spree_users.vat_id` → customer-owned `Spree::TaxIdentifier` (skip customers that already have one of the derived kind). Kind derivation: leading ISO prefix (`GB` → `gb_vat`, `CHE` → `ch_vat`, EU members incl. `EL`/`XI` → `eu_vat`); else from the customer's default address country; final fallback `eu_vat` with a log line. `validation_status` left nil.
3. `avatax_entity_use_code_id` + `exemption_number` on `spree_users` are **left untouched** — they are the migration source for whichever answer the customer-exemptions Open Question gets (core extension preferred); the task prints a count of users carrying them so the merchant knows the data exists.
4. Delete synthesized `Spree::TaxRate` rows (`name = ENV.fetch('AVATAX_TAX_RATE_NAME', 'AvaTax Official Tax Rate')`) — otherwise the Internal provider reads them.
5. ~~Legacy `spree_avatax_official_transactions` SalesInvoice ids → `order.metadata['avalara_transaction_id']`.~~ **Withdrawn 2026-09-01:** that table is `(order_id, transaction_type, code)` — a document *code*, which is the order number — while `commit` stores Avalara's numeric `body['id']`. Writing a code under a key named `..._transaction_id` invites a caller to send it to Avalara as an id, and buys nothing: void and refund key on the document code, derivable from the order number for every migrated order. The README states the absence instead.
6. Point markets at the provider — only where nothing is set (see Key Decisions), logged per market:

   ```ruby
   store.markets.where(tax_provider: [nil, ''])
        .update_all(tax_provider: 'SpreeAvalara::TaxProvider')
   ```

7. Separate destructive task `spree_avalara:upgrade:drop_legacy_schema`: drops the legacy transactions table, the `avatax_uuid` columns, `spree_users.vat_id` (migrated to `TaxIdentifier`) and `spree_stores.avatax_company_code`. It deliberately does **not** drop `spree_users.exemption_number`/`avatax_entity_use_code_id` or the entity-use-code table while the customer-exemptions Open Question is unresolved — they are its migration source. The main task only prints guidance.

Also in this phase:

- Gem README: install, connect, point markets, preferences, how exemptions flow (company certificates via core; individuals via Avalara's certificate store), upgrade path; caveats — (a) no `VatPriceCalculation` restatement on non-Internal markets (state destination prices via geo-scoped price lists); (b) a market pointing at a deactivated integration computes no Avalara tax at all until it is reconnected — the misconfiguration is reported, never raised, so nothing in the storefront breaks; (c) standalone refunds (no return) are not filed with Avalara in v1.
- `spec/integration/` shells carrying the Phase 7 cassette list; upgrade-task specs run against ad-hoc legacy tables created in the dummy DB.

### Phase 7: cassette recording + response-shape verification (maintainer)

VCR cassettes are **re-recorded by the maintainer** against an AvaTax sandbox account — never hand-authored, never auto-recorded (VCR config: `record: :none` by default, credential filtering; cassette-backed specs skip cleanly while their cassette is absent, so CI stays green through Phases 1–6).

- Cassettes to record: ping ×2 (authenticated/unauthorized), estimate SalesOrder ×3 (US multi-line incl. fulfillment, exempt via entityUseCode/exemptionNo, no-nexus destination), a tax-inclusive EU estimate, commit + commit replay (same code twice), void + already-voided, refund ReturnInvoice + duplicate, resolve_address valid/invalid.
- What this phase closes out: the `TransactionLine` mapping table verified row by row against real responses (including the export and reverse-charge detail markers rows 3–5 rest on), the idempotency error-code predicates confirmed and their `# verify against cassette` comments removed, and the cassette-backed `spec/integration/` layer turned on.
- **`businessIdentificationNo`: sent and covered, but not confirmed honoured (2026-09-02).** Two
  separate claims, and only the second is open. That a registration on the sale reaches the request is
  tested at both levels — a recorded estimate carries the key, and `commit` is covered reading the
  order's own frozen registration. Whether Avalara *acts* on it cannot be shown here: the response is
  identical with and without it, on both EU and US destinations, down to everything but the generated
  document code and timestamp. Since AvaTax ignores keys it does not recognise without erroring —
  proven while confirming the per-line `exemptionCode` — a wrong name would charge EU business buyers
  consumer VAT in silence, and no test available would notice. It matches AvaTax's documented field on
  CreateTransactionModel, and that plus the payload coverage is the evidence there is. Confirming the
  behaviour needs an EU-registered account.
- **Not covered by a cassette (2026-09-02).** Collected seller's use tax — a `taxType: 'Use'` line with a positive rate, which row 7 must not claim as `not_collecting` — needs an account holding a remote-seller registration. No available account has one, and an example written against an account that collects nothing passes on an empty set rather than testing the predicate, so none is kept. That predicate rests on the reasoning under Treatment mapping alone, alongside rows 3–5, which need an EU-registered account for the same reason. The recorded EU estimate pins the inclusiveness flag round-tripping, not VAT arithmetic: the recording account has no EU registration, so the rate comes back 0%.

### Deferred (post-v1, listed not built)

- Standalone-refund subscriber on `refund.created` (percentage refund; skip refunds originated by the returns flow — avoids double-filing with `Returns::Refund`'s provider call).
- Tax-identifier validator registration, if the avatax SDK exposes a usable registration-validation endpoint (unverified against SDK ≥ 19.3).

## Constraints on Current Work

- **Integration state never decides whether a store can sell:** a disconnected provider has no opinion, in every entry point. Nothing may raise out of `estimate`, `commit`, `refund` or address validation because an integration is inactive — a merchant toggles those, and checkout must survive it. Fail closed on a connected service that refuses, not on configuration.
- **Provider row hygiene:** any code writing or sweeping `Spree::TaxLine` rows must scope by its own `provider_id` — never delete another provider's rows (the duty/import-VAT seam depends on this).
- **Never re-derive the tax address:** always `owner.tax_address`; the ship-vs-bill choice is a store preference already encapsulated there.
- **No new columns on core tables for provider state:** external document ids go in `order.metadata`; the gem ships no schema of its own in v1.
- **`Market#tax_inclusive` is now read by an external provider** — the Phase 9 "decide or drop" question in `6.0-tax-provider.md` is answered: it stays and must not be dropped. It is read destination-derived (via the market covering the tax country), which is also the live argument for any future market-resolution work (`6.0-channel-markets.md`'s `set_market_from_country`) and for Phase 9 considering a destination-aware replacement.
- **A taxability reason is never inferred from an amount alone:** `exemptAmount > 0` says nothing about why, and both a no-nexus sale and an exempt tax code report the whole line exempt with `isItemTaxable: false`. A reason claiming a customer exemption requires certificate evidence; one claiming the merchant does not collect reads `taxType`.
- **Estimate call sites must stay tolerant of whole-owner rewrites:** a provider may legitimately rewrite rows beyond the `items` subset it was handed, provided it rewrites everything it deletes.

## Open Questions

- **Do we need customer-level exemption handling?** Core's `TaxExemptionCertificate` is Company-owned, so an individual exempt buyer (US government/nonprofit purchaser with no Company) has no first-class home; the legacy gem covered this with columns on `spree_users`. If the answer is yes, the preferred shape is **extending spree core** — certificates resolvable for a customer as well as a company (a second optional owner, or customer-owned certificates feeding the same `ResolveExemptions`) — rather than gem-owned storage, so every provider gem benefits and the vocabulary stays in one place. Until resolved: the gem forwards company-certificate exemptions only, individual exemptions work through Avalara's own certificate store, and the upgrade tasks preserve the legacy user columns as the future migration's source.

Resolved (previously open):

- **The US zero-tax reason fields (2026-09-01)** — verified live against a sandbox company rather than deferred to Phase 7: `nonTaxableType` is absent, `exemptAmount` is not certificate evidence, and `taxType` (`Sales` vs `Use`) is what separates "exempt here" from "not registered here". Table rows 1, 2, 6 and 7 were corrected accordingly. The EU rows (3, 4, 5, 9, 11) and the idempotency error codes remain Phase 7's.
- **Exact AvaTax enum values (2026-08-19)** — for the idempotency predicates (duplicate document / already voided error codes) and the export / reverse-charge detail markers (mapping rows 4–5). Not a design question: the design is settled and Phase 7's cassette re-recording against the sandbox owns confirming the values; the code carries `# verify against cassette` comments until then.
- **Deferred follow-up scope (2026-08-19)** — standalone-refund subscriber, tax-identifier validator registration, per-fee-kind tax codes, multi-location ShipFrom. Decided-deferred to post-v1, each unblocked by real merchant demand; recorded under Deferred in the Migration Path (the standalone-refund deferral is also a Key Decision, confirmed with the author).
