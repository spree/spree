# Storefront Connection and Multi-Channel Publishable Keys

**Status:** Draft — designed, nothing built
**Target:** Spree 6.1
**Depends on:** `5.6-store-channel-context-and-key-binding.md` (channel-bound publishable keys, shipped), `6.0-store-context-and-first-run-setup.md` (the key selects the store, shipped)
**Author:** Damian Legawiec + Claude
**Last updated:** 2026-11-23
**Tracking:** Linear — · GitHub —

## Summary

This plan settles how a storefront is represented in open-source Spree and makes one change to support it. The representation stays what it is today: a storefront is whatever client holds a publishable key, and the store keeps one `storefront_url`. Core gets no storefront record. The change is that a publishable key can be bound to several channels instead of one, so a single deployment that serves the consumer and wholesale channels can use one key without that key reaching every channel. Hosting, domains, repositories and deployments belong to a hosted product's own control panel, which works through the stock Admin API. A storefront record with its own identity settings was drafted between 2026-11-21 and 2026-11-23 and dropped after comparing with three other open-source commerce platforms, none of which has one.

## Key Decisions (do not deviate without discussion)

- **Core has no storefront record.** (2026-11-23) A storefront is identified by its publishable key. The store keeps the single `storefront_url` preference with its existing fallback chain. A `Spree::Storefront` model (URL, default flag, keys, a link to where it is managed) was drafted and dropped: it only earns its place when one store has several storefronts on different domains, and no merchant has asked for that. The three open-source platforms compared all do without one, and the one whose cloud hosts storefronts assumes one storefront per environment. What would reopen it is in Open Questions.
- **A publishable key can be bound to several channels, through `spree_api_key_channels`.** (2026-11-21) This replaces the single `ApiKey#channel_id` from `5.6-store-channel-context-and-key-binding.md`. No rows means every channel (today's unbound key), one row is today's bound key, and several rows let one key serve, say, the consumer and wholesale channels but not point of sale. The 5.6 plan chose a single binding because one key per storefront surface was the only case; the Next.js storefront has since served two channels from one deployment with one key, which a single binding can only express as "all channels". One of the platforms compared binds its publishable keys to sales channels through the same kind of join table.
- **No rows keeps meaning every channel.** (2026-11-23) The platform with the same join table refuses a key with no channels. Spree does not, because every key that exists today and is unbound must keep working unchanged.
- **Channels can be added to a key, never removed.** (2026-11-21) The 5.6 plan made the binding immutable so that a live credential could not be repointed under a running storefront. Adding a channel does not change any request the storefront already makes; removing one would. To narrow a key, mint a new one and revoke the old. A key with no rows cannot gain its first row, since that would narrow it from every channel to one.
- **Data parity comes first; the open-source UI can be small.** (2026-11-23) What open source must provide is the data and the API. A layer above a store must be able to do everything with a stock installation's Admin API and webhooks, because it cannot change the code underneath it: on Spree Cloud a merchant may run their own Docker image with their own dashboard and API customisations. Nothing here may depend on patching or overriding the dashboard, the API or core in a hosted environment. For storefronts the parity already exists: the Admin API can set `storefront_url`, manage allowed origins and create publishable keys.
- **Hosting details stay out of core.** (2026-11-21) Repository, hosting project, domains, template look and features, and deployment status live in the hosted product's own database. Core has no columns for them and no dashboard slot.
- **Per-storefront name, SEO and branding are not built.** (2026-11-23) Overrides of the store's public identity on a storefront were drafted and dropped with the record. None of the three platforms compared stores identity per storefront or per channel. The store's name, translations and SEO fields stay the only source.
- **No hostname-based resolution.** (2026-11-21) A storefront is identified by its key, never by the request's `Origin` or host. This restates the constraint in `6.0-store-context-and-first-run-setup.md`.

## Design Details

### Key channels

```ruby
# spree_api_key_channels
#   api_key_id, channel_id; unique: (api_key_id, channel_id)
class Spree::ApiKeyChannel < Spree.base_class
  belongs_to :api_key
  belongs_to :channel
end

class Spree::ApiKey
  has_many :api_key_channels, dependent: :destroy
  has_many :channels, through: :api_key_channels
end
```

Only publishable keys may have channels, and every channel must belong to the key's store, as today. `Spree::Channel`'s guard against deleting a channel with active bound keys reads the join table.

### Channel resolution

`Spree::Api::V3::ChannelResolution` keeps its order (key, then header, then store default). Only the key step changes, from one channel to a set:

| The key's channels | `X-Spree-Channel` | Result |
|---|---|---|
| None (unbound) | any | Header, then store default (unchanged) |
| One | absent or matching | That channel (unchanged) |
| One | different | 422 `channel_mismatch` (unchanged) |
| Several | names one of them | That channel |
| Several | names another | 422 `channel_mismatch` |
| Several | absent | The store's default channel if it is in the set, else 422 `channel_required` |

That platform answers a catalogue request that names no channel with products from all of the key's channels. Spree does not, because the channel decides prices, access and the catalogue, so a request always resolves to exactly one.

### Admin API and SDK

`POST /api/v3/admin/api_keys` accepts `channel_ids`. `PATCH` accepts a `channel_ids` that is a superset of the current one and refuses anything else. `channel_id` keeps working through 6.1 as a one-item `channel_ids`, with a deprecation warning, and is returned alongside `channel_ids` while it exists. `@spree/admin-sdk` follows.

### Dashboard

- Minting a publishable key offers a channel picker when the store has more than one channel.
- The "Connect storefront" sheet keeps writing the store's `storefront_url`. It can show two paths side by side (see Where the storefront's code lives); this is copy and layout, not data.

### Self-hosted and hosted management

The data is the same everywhere: a publishable key, an allowed origin and the store's `storefront_url`. What differs is who deploys the code and who writes those three.

| Step | Self-hosted (core only) | Hosted product |
|---|---|---|
| Choose look and features | In the CLI, or by picking a prebuilt variant | In the control panel |
| Get the code | The developer's project or repository | The project's own repository, with a storefront directory beside the server (primary); or a generated repository |
| Deploy | The developer, on any host | The control panel creates the hosting project |
| Key | The seeded key, or one minted in the dashboard | Minted through the Admin API and injected as an env var |
| URL and allowed origin | Typed into the connect sheet | Written through the Admin API when the deployment is live |
| Domains, deployment status, previews, redeploy | Not in Spree | In the control panel |

### Where the storefront's code lives

**1. In the project `create-spree-app` made (the default).** The storefront is `apps/storefront/` in the same repository as `server/`. Nothing needs cloning, so the Vercel clone button is the wrong tool here: it would make a second copy of the code in a new repository.

- Local development: the CLI writes the seeded publishable key into `apps/storefront/.env.local`, as today.
- Going live: the developer deploys `apps/storefront` from their own repository on the host they choose. On Vercel that is an import of the existing repository with the root directory set to `apps/storefront`. They set `SPREE_API_URL` and `SPREE_PUBLISHABLE_KEY` from the connect sheet of the production store's dashboard and paste the deployed URL back into it.
- There is no callback in this case, so the URL is typed in.

**2. A new copy in its own repository, through the Vercel button.** This is today's flow and stays for installations with no project around the server, such as a multi-tenant installation or a store set up from the Docker image. The button clones the storefront template with the two values filled in, and the developer pastes the deployed URL unless Vercel redirects back.

**3. A separate repository the developer made themselves**, with the CLI in an empty directory or by hand. Same as case 1 from the dashboard's side: copy the two values, paste the URL.

The connect sheet can therefore offer two paths and does not guess which applies:

| Path | Shows | Ends with |
|---|---|---|
| "Deploy the storefront in my project" | The API URL, the publishable key, and short steps for a host with a root directory setting | The developer pasting the URL |
| "Deploy a new copy" | The Vercel button | The developer pasting the URL, unless the redirect is available |

### Vercel's documented limits (checked 2026-11-23)

- **No deep link for an existing repository.** The only documented parameterised link is the Deploy Button, `https://vercel.com/new/clone`, which always copies the source into a new repository. Importing a repository the user already has goes through the New Project page, where the root directory and environment variables are set by hand. Path 1 therefore stays as written steps.
- **The button can target a folder.** `repository-url` may include a subdirectory, and `root-directory` sets the project's root. The button can clone one folder of a repository that holds several prebuilt storefront variants.
- **Values can be prefilled, with a caveat.** `env` names the required variables and `envDefaults` gives their defaults. Vercel says not to pass secrets this way because the link is kept in browser history. A publishable key is not a secret, so today's use is within that.
- **The redirect needs a Vercel Integration.** Vercel's docs say to set `developer-id` with `redirect-url`, and that the redirect is offered only when the URL is HTTPS and its hostname matches the Integration's website field or is a subdomain of it. The dashboard sends `redirect-url` without `developer-id` today, from whatever host the installation runs on. By the docs, a self-hosted installation on its own domain cannot get the redirect; a hosted product on one registered domain can. What Vercel does with a `redirect-url` and no `developer-id` is not documented and has not been tested here.

### What a hosted product does, outside core

Spree Cloud is planned as a central control panel, separate from each store's dashboard, which knows every store's dashboard address and opens it. For storefronts it holds, in its own database, the repository and installation, hosting project, domains, template look, features and version, and deployment status. Towards a store it does three things through the stock Admin API with a secret key: mints a publishable key (with `channel_ids`), adds the storefront's origin to the allowed origins, and sets `storefront_url`.

Its primary path is the one the compared platform's cloud uses: the project's own repository holds the server and the storefront in two directories (`server/` and `apps/storefront/` in a `create-spree-app` project), and the control panel deploys both, injects the API URL and key into the storefront, and can pair a storefront preview with each server preview. Generating a separate storefront repository is the alternative for a store with no project repository.

Three consequences of sitting above a store it does not control:

- **It uses only the stock Admin API and webhooks.** No dashboard plugin, no patched serializer, no code in the merchant's image.
- **It reconciles.** `storefront_url`, origins and keys can be changed behind its back by a customised dashboard or an API call, so it re-reads them and decides per value whether to accept the change or write its own back.
- **It checks the version.** A merchant's image may run a Spree release without `channel_ids` on keys. The control panel reads the store's version first and falls back to `channel_id` or an unbound key.

Because it runs on one registered domain, the control panel can be the Vercel Integration that the redirect after a deploy requires, which a self-hosted dashboard cannot.

### How others do it (checked 2026-11-23)

Three open-source commerce platforms with a hosted offering were compared.

| | Platform A | Platform B | Platform C |
|---|---|---|---|
| Storefront record in core | No | No | No |
| What identifies a storefront | Publishable key | Channel token | A channel slug per query |
| Credential to channels | Many-to-many join table | One token per channel | No credential |
| Storefront URL | Server config, one per backend | Server code config | Sent by the client per call, checked against an allowlist |
| Shop name and SEO | Store name only | None in core | Global shop settings |
| Cloud hosts the storefront | Yes, from the same monorepo | Not found | Beta |
| Cloud console separate from store admin | Yes | Yes | Yes |

## Migration Path

1. **Join table.** Add `spree_api_key_channels`, copy each key's `channel_id` into it, move the validations and the channel-deletion guard.
2. **Channel resolution.** Change the key step from one channel to a set.
3. **Admin API and SDK.** Add `channel_ids`, keep `channel_id` as a deprecated alias.
4. **Seeds.** No change is required: the seeded `Default` key stays unbound and `Storefront (Wholesale)` stays bound to one channel.
5. **Dashboard.** Channel picker when minting a key.
6. **Removal, in 6.2.** Drop `spree_api_keys.channel_id` and the `channel_id` API parameter.

The Next.js storefront needs no change. It can move its wholesale surface from an unbound key plus a channel header to a key bound to both channels whenever a project wants the tighter binding.

## Constraints on Current Work

- Do not add new readers of `ApiKey#channel_id` or code that assumes a key has at most one channel. The column becomes a join table.
- Do not add a storefront model, or hosting, repository, domain or deployment columns, to core. See the first Key Decision before proposing one.
- Features meant for a hosted product must work through the stock Admin API and webhooks. Do not design one that needs a patched dashboard or serializer.
- No Store API endpoint may list channels or keys.

## Open Questions

- **A second storefront on another domain for one store.** For example a wholesale portal at its own address, whose order emails should link there and not to the consumer shop. This is what a storefront record was drafted for. If it comes up, the smaller answer is a nullable storefront URL on the channel that falls back to the store's, following the fallback `Spree::Channel::Gating` already uses. Unblocked by a merchant who needs it.
- **Whether the Vercel redirect works today for self-hosted installations.** The docs say it should not (see Vercel's documented limits). Unblocked by one test deploy from a self-hosted dashboard; if it does not redirect, remove the `redirect-url` parameter and the callback handling from the open-source sheet.
- **Email paths.** Emails build paths such as `/products/:slug` and `/checkout/:token/payment` in core, so a storefront with different routes cannot change them. Out of scope here.
