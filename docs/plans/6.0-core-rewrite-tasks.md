# 6.0 Core Rewrite — Implementation Task List

**This is a working task tracker, not a plan.** Plans of record: `6.0-cart-order-split.md`, `6.0-fulfillment-and-delivery.md`, `6.0-6.1-split-adjustments.md`. Where this file and a plan disagree, the plan wins.

**Branch:** `6-0-dev` (verified against HEAD `ee39a89`, 2026-07-28)
**UI rule:** all admin UI work targets `packages/dashboard` via Admin API v3 + `@spree/admin-sdk`. `spree/admin` is legacy and is not touched — and per Decision 2 it stops loading in the dev server (T0.3).
**Ordering rule:** data-transformation rake tasks are the **last** wave (user constraint). Schema migrations (renames/additive) are not data migrations and land with their wave.

## Scope

**In scope** — the three plans end-to-end, plus the *minimum viable slices* of prerequisite plans they hard-depend on:

| Prerequisite slice | Why it's unavoidable |
|---|---|
| `6.0-product-types.md` Phase 1 only | Hard blocker: `ProductType#fulfillment_types` replaces ShippingCategory; `Spree::ProductType` doesn't exist yet |
| `6.0-delivery-zones.md` Phase A + shipping-side Phase C | `spree_delivery_method_zones` must be **born** joining `DeliveryZone` (never re-migrated); Estimator address check needs a matcher |
| `6.0-tax-provider.md` minimal `Base` + `Internal` | Split-adjustments forbids reimplementing `TaxRate.adjust`; the provider is the *only* sanctioned TaxLine writer |

**Out of scope** (seams left ready, ride separately): rest of product-types (custom-field-definition join, live-template propagation, its API/dashboard), full tax-provider (per-Market column, real commit/void wiring, exemption certificates, TaxRate country/state decoupling), `6.0-delivery-rate-provider.md` (store_id + rate provider seam), `6.0-typed-stock-movements.md` (unblocked by Wave 2), multi-vendor (F3 split hook ships as a no-op single partition), returns/exchanges/claims, normalize leftovers (Payment/ReturnAuthorization/GiftCard `state`→`status`), the `spree_zones` table drop (blocked on tax decoupling).

## Decisions (settled interactively 2026-07-28 — recorded in `decisions.md` + the plans' Resolved Questions)

1. **Product-types: minimal Phase 1 only** — rename + store ownership + `fulfillment_types` + `product_type_id`. Rest of that plan is its own effort.
2. **`spree_admin` is dropped from the starter Gemfile on the 6.0 line** (→ T0.3). The gem stays in the monorepo untouched (already out of CI); one-release constant aliases still ship for extensions + emails.
3. **`checkout_flow`: hard removal**, migration guide to `Checkout::Registry`, no shim.
4. **DeliveryRate gets no owner columns** — owner derives through `fulfillment.owner`.
5. **Reaper defaults: guest 30d / customer 90d / empty 48h**, config preferences; money-safety exclusion unconditional.
6. **Webhook dual-emit: exactly one release** (`shipment.*` dropped in 6.1).
7. **`ready_for_pickup`: first-class Store API status** (rollup still reports `ready`).
8. **`partially_canceled`: derived predicate**, not a stored status value.

## Why this order (the four load-bearing choices)

1. **Fulfillment renames before split-adjustments tables** — the typed tables are *born* with `fulfillment_id` (both plans mandate born-correct, never-migrated columns).
2. **Split-adjustments + fulfillment providers before the Cart flip** — `Carts::Complete`'s copy contract (line items, addresses, fulfillments + selected rates, typed money lines) is written **once**, against final vocabulary. Flipping first would mean writing throwaway copy code for legacy shipments/polymorphic adjustments.
3. **Machine removal is its own wave after the flip** — requirements-driven checkout must be live and `UpdateStatuses` in place before `spree_orders.state` and `Order::Checkout` are deleted.
4. **Data rake tasks last** — every task reads legacy structures that deliberately stay in place: `spree_adjustments` (read-only through 6.0 as audit/rollback), `spree_zones` (until tax decouples), ShippingCategory tables (drop in 6.1), incomplete orders (converted to carts by `completed_at`, not `state`).

Each wave must land with its engine suites green (`parallel_rspec` core + api + emails, plus dashboard tests where touched) before the next starts.

### Wave 2 outcome notes (2026-07-29)

- **Deprecation bridges are the standing convention** (Damian): legacy associations are Rails 8.1 `deprecated: true` twins (core gemspec floor bumped to `>= 8.1` for rails/rails#55285); legacy methods/scopes warn via `Spree::Deprecation` then delegate; `alias_attribute` for columns; constant-assignment aliases for classes. Internal Spree code uses **real names only** — twin associations carry separate AR caches, and mixing names inside one flow caused real stale-object bugs (auto-capture, `set_shipments_cost`, `Prioritizer#hash_item`, `Exchange#perform!`, unsaved `to_shipment` graphs).
- Rails 8.1's strict association resolution rejects alias constants in `class_name:` **and** inference — every `class_name:` now names the real class.
- `Calculator#compute` dispatches by class name, so Fulfillment objects route through a new `compute_fulfillment` → `compute_shipment` bridge preserving the historical calculator extension point.
- Retired with no bridge (plan-sanctioned): `ShipmentHandler` (inlined into `after_fulfill` until Wave 4 providers), `Stock::Splitter::ShippingCategory` + `Splitter::Digital` (classes + specs deleted; `Splitter::FulfillmentType` registered), `ShippingCategory#includes_digital_shipping_method?` (zero callers), `Zone`↔shipping-method associations, the market factory's zone scaffolding.

### Wave 3 outcome notes (2026-07-29)

- **Adjuster is order-scoped, not adjustable-scoped.** `Spree::Adjusters::Base#initialize(order)`; `Adjusters::Promotion` recomputes candidates from connected promotions (plus `extra_promotions:` during activation), competes per group (line / fulfillment / order-wide), and cleans everything it didn't write this pass. Winner-only policy lives solely in `#select_applicable` (the 6.1 stacking seam). Actions share `PromotionAction#apply_via_adjuster`: perform = "does this action yield a candidate?" — losing promotions still connect to the order so they keep competing on later recalculations (reinstatement without stored losers).
- **Cross-order negative-total guard dropped from `CreateItemDiscounts#compute_amount`** — it double-counted the very rows being recomputed; per-line clamping over the remaining discounted base owns the floor now (order net = Σ line nets ≥ 0 since every discount is line-attached).
- **Behavior change (spec'd):** an order-level discount distributes nothing when line bases are exhausted (`Order#cart_promo_total` spec updated -110 → -100 with rationale). Legacy let order-level rows ride on top of fully-discounted lines with shipping absorbing the difference.
- **`Order#discounts` now means typed rows.** The 5.4 `alias discounts order_promotions` is gone; the three API serializers keep the wire shape via `many :order_promotions, key: :discounts`.
- **Recalculation reentrancy rules:** `LineItem` after_save no longer runs the updater (services own it — running it mid-mutation cached `order.line_items` and hid later items); `Fulfillment#update_adjustments` skips creation (`previously_new_record?` — recursing mid-`fulfillments=` dropped records) and completed orders; `OrderUpdater#update` resets `line_items`/`fulfillments` association caches at entry.
- **Internal provider details:** fees without a tax category tax against the default TaxCategory; `store_pre_tax_amount` moved into the provider; `TaxRate#adjustment_label` is the public label snapshot; `TaxRate.tax_lines` is `dependent: :nullify` (rows outlive rates; next estimate drops them). `Cart` gained dormant `tax_address`/`tax_zone`. `DeliveryRate#tax_amount` computes inline from rate config (no calculator).
- **api engine (ahead of Wave 6):** read-only `/admin/orders/:id/adjustments` endpoints + serializer removed; `?expand=adjustments` dropped from admin order/line_item/fulfillment serializers. Typed replacements (tax_lines/discounts/fees CRUD) ship in Wave 6 as planned.
