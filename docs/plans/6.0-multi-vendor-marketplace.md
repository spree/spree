## Summary

Open-source the core of Spree's multi-vendor marketplace into Spree 6.0, per [spree/spree#13323](https://github.com/spree/spree/issues/13323). Today multi-vendor lives in the paid Enterprise module as a **decorator-heavy monkey-patch** of core (dozens of prepended core classes, a parent order mutated into a line-item-less "splitted" state). 6.0 brings the **Seller identity, per-seller order splitting, the commission engine, and the payout ledger** into core as first-class models — built natively on the 6.0 Cart/Order split rather than retrofitted onto the legacy `Order`-only model.

What stays paid (Enterprise — boundary amended 2026-07-15, see `decisions.md`): refund **clawbacks** (automatic Stripe transfer reversals + negative-balance netting), ledger⇄provider **reconciliation**, KYC/account-health operations, payout reports (incl. DAC7), marketplace-facilitator taxes, Shopify/WooCommerce sales-channel apps, the category mapper. **Basic Stripe Connect execution — Express onboarding + on-fulfillment transfers — ships open-source in the monorepo**, alongside the Stripe core gateway being pulled in from the standalone `spree_stripe` repo (the payment-sessions-API classes only; the legacy v2-API/storefront code stays behind — likely home: `spree/core`). **Core runs the happy path end-to-end (onboard, sell, get paid); Enterprise operates the unhappy paths and compliance at scale.**

This plan covers the four subsystems: **(A) seller identity & teams**, **(B) order splitting**, **(C) the commission engine**, and **(D) the payout/fund-transfer ledger**. It is informed by a source-level port review of the current Enterprise multi-vendor module (private source — internals deliberately not cited here), the Enterprise behavior documented in the public user docs, and a survey of modern open-source marketplace implementations — see References (competitor names and the detailed comparison are likewise kept out of this public file).

## Key Decisions (do not deviate without discussion)

### Scope split (OSS 6.0 vs Enterprise) — per #13323, amended 2026-07-15 (basic Stripe execution → OSS; see `decisions.md`)

| OSS core (this plan) | Enterprise (stays paid) |
|---|---|
| `Spree::Seller` identity + invitation **and self-serve application** onboarding state machine + seller teams (reusing `Role`/`RoleUser`/`Invitation`) | KYC/account-health **operations** (requirements monitoring, restricted-account workflows) |
| Seller admin dashboard (composed from `@spree/dashboard-*`) + operator marketplace screens | Refund **clawbacks** — automatic Stripe transfer reversals + negative-balance netting |
| **Basic Stripe Connect payouts** (Express onboarding link + on-fulfillment transfers — ships with the monorepo Stripe gateway) | Ledger⇄Stripe **reconciliation** |
| Commission engine (seller- + product- + category-level rules, **commission taxation**) | Payout reports (incl. EU **DAC7** seller-income reporting) |
| Order splitting + payment split | Shopify white-label Sales Channel app |
| **Fund ledger** — `SellerTransfer` (on-fulfillment earnings) + `SellerPayout` (scheduled settlement) + balance, lifecycle, reversals | WooCommerce integration |
| Seller CSV import/export (rides the `Spree::Import`/`Spree::Export` pipeline) | Category mapper (external category → Spree taxon) |
| Sellers API endpoints (Admin + Store) + lifecycle webhooks/events + onboarding task registry (core tasks) | Enterprise onboarding **tasks** registered into the core checklist (Stripe KYC, Shopify/Woo store connection) |
| Merchandising + permissions (via code) | "Automatic taxes" (marketplace-facilitator remittance) |

The boundary is **operational depth**: you can run a marketplace for free end-to-end — sellers onboard to Stripe Express through a hosted link and get paid automatically on fulfillment — and core records what each seller is owed (the payout ledger). The moment you need the money *operations* — automatic refund clawbacks, negative-balance netting, ledger⇄Stripe reconciliation, KYC workflows, regulatory reporting, tax remittance — that's Enterprise (Decision 9).

**The OSS payout story is execution-capable, not just record-keeping (amended 2026-07-15):** the monorepo's Stripe gateway ships a basic `PayoutProvider::StripeConnect` — Express onboarding + on-fulfillment transfers — so the free tier demos money movement end-to-end, at parity with the surveyed OSS competition. `PayoutProvider` stays a public interface, so community providers (PayPal Payouts, Wise, SEPA batch files) are first-class. Enterprise differentiates on the operations *around* the money, not on whether money moves.

### `Spree::Seller` name ownership (RESOLVED 2026-07-14; renamed 2026-08-17)

`Spree::Seller` (prefix `sel_`, table `spree_sellers`) is **the marketplace seller — this plan's model**. The purchase-order procurement source is **`Spree::Supplier`** (`sup_`, `spree_suppliers`, `/api/v3/admin/suppliers`). They are different lifecycles: a supplier is an address-book entry the merchant buys stock from; a seller is an onboarded selling party with users, commission, and payouts.

Both models were originally called `Spree::Vendor` — a hard collision resolved on 2026-07-14 by giving the marketplace the `Vendor` name and renaming the procurement source. The split stood; the naming was reversed on 2026-08-17 once the two reasons for it expired (the user docs are being rewritten for 6.0 stable, and there is no Enterprise production data to keep `ven_` continuity with). **`vendor` was the wrong word for the marketplace side precisely because this schema also holds the supplier**: Amazon's Vendor Central buys from suppliers while Seller Central hosts third parties, so `vendor_id` reads as the procurement relationship to anyone with Amazon experience. `Seller` is also what Gartner, Forrester, VTEX, Marketplacer, Amazon and Mercur all use for this entity. Full rationale in `decisions.md` 2026-08-17.

### 1. Split happens at cart completion, into N child Orders under one parent — never seller-tagged flat line items

The legacy module and current industry implementations agree on the shape, and it maps cleanly onto `6.0-cart-order-split.md`:

- One mixed **`Spree::Cart`** through the entire shopping + checkout flow (a customer adds items from many sellers to one cart — no per-seller cart fragmentation).
- At `cart.complete!` (the `Spree::Carts::Complete` service from the cart/order-split plan), partition cart line items **by the denormalized `line_item.seller_id` snapshot** (set from `product.seller` at add-to-cart; revalidated at completion — see Order splitting) and, **when the cart spans more than one partition** (first-party items, `seller_id: nil`, count as their own partition), fan out into **N child `Spree::Order`s, one per partition**, all owned by **one `Spree::OrderGroup`** that holds customer/payment/address context. Single-partition carts complete as a bare order — no group (see the Trigger & gate bullet).
- The parent↔child relationship is an explicit FK via a dedicated `Spree::OrderGroup`, **not** the legacy `state == 'splitted'` string hack and **not** a join-table indirection. See Design Details and Decision 8.

This is the single most important integration point with the rest of 6.0: **the split is a consumer of the Cart/Order split, implemented inside the completion service**, not a state-machine `after_transition` callback bolted onto a monolithic `Order` (which is how the legacy module did it). The 6.0 cart/order plan removes the order-level state machine entirely, so the legacy trigger cannot survive — splitting must be invoked explicitly from `Carts::Complete`.

### 2. Commission is a frozen snapshot line attached to the order line item, computed once at placement

Mirror the core insight from both the legacy module and the industry references: commission is **denormalized and frozen at sale time**, never recomputed on read. This matches Spree's existing EU Omnibus "frozen at sale" precedent (`5.4-6.0-eu-legal-compliance.md` PriceHistory).

- New model **`Spree::CommissionLine`** (NOT a revival of the legacy commission table, NOT a polymorphic `Adjustment`). One row per commissioned line item — plus one per fulfillment when the rate commissions delivery revenue (`include_shipping`, Decision 4) — storing a **snapshot** of `rate`, `amount`, and the resolved rule's identity.
- Written by a service during/after `cart.complete!`, once. A later rate change does not touch existing lines.
- **Frozen, not re-derived (corroborated 2026-08-17).** A source review of the leading surveyed OSS engine found it re-resolves commission from *current* rate configuration on every refresh (order edit, return received, claim created), deleting and reinserting the lines — so editing a rate there retroactively changes what a seller was already charged on past orders. Its own documentation claims the opposite, which is worth knowing if it is ever used as a reference. Ours are a snapshot written once, the same rule the duties work settled ("never re-derive from the live catalog on an existing order").
- **Commission is NOT a `Spree::Fee`.** `6.0-6.1-split-adjustments.md`'s `Fee` is a *buyer-facing* charge — it rolls into `order.fee_total` and the order total the customer pays. Commission is a *platform ↔ seller* settlement line the customer never sees; it must never touch order totals. `CommissionLine` is therefore its own off-order ledger table that merely follows the same typed-line design (concrete FKs, no polymorphic source, no state machine) as the split-adjustments family. The only real split-adjustments dependency is that tax lines / discounts / fees are line-item-attached, so they re-home cleanly to the child order during the split. (A *buyer-facing* marketplace service fee — StockX-style — would be a `Spree::Fee` with a `kind`; possible later, out of scope here.)

### 3. Commission taxation is a first-class field — this is the OSS differentiator

This is the one place where the **legacy Enterprise module is ahead of the surveyed industry implementations** and the reason #13323 calls out "commission taxation which is essential for European marketplaces." The common industry pattern uses an `include_tax` toggle that only decides whether the *seller's item tax* inflates the commission base; it charges **no tax on the marketplace fee itself**. The legacy module already charges VAT *on the commission* at a configurable per-seller rate (`fee_total = fee_amount + fee_amount × tax_rate`, half-up rounding). The marketplace's commission is itself a **taxable B2B service** the platform renders to the seller. 6.0 must model:
- `amount` — the commission (the fee the platform charges the seller),
- `tax_amount` — VAT/tax **on that commission**, at a configurable commission tax rate,
- `tax_rate` — the rate that produced it, so the row explains its own figure,
- `taxability_reason` + `country_code`/`state_code` — how the fee was treated and where, in `Spree::TaxLine`'s vocabulary (see below),
- `total` — `amount + tax_amount`.

**One tax or several? → one, on the line (RESOLVED 2026-08-17).** The fee's tax stays a scalar on `CommissionLine` — `tax_amount` plus the `tax_rate` it was charged at — rather than becoming child rows. A marketplace fee is a single supply to a single business, which is the EU case this plan exists for.

Reusing `Spree::TaxLine` was considered and rejected, and the reason is worth recording because the model genuinely fits: it already carries rate, amount, treatment, jurisdiction and provider. What does not fit is its **scope**. A tax line's owner is the cart or order because it is the buyer's tax: `Carts::RecalculateTotals` sums `order.tax_lines` straight into `additional_tax_total`, so a commission row stored there would inflate what the shopper pays — the one thing Decision 2 forbids — and `/orders/:id/tax_lines` returns them wholesale, so seller fee arrangements would become visible to any holder of `read_orders`. Both are fixable with a `WHERE commission_line_id IS NULL`, and that is exactly the cost: every future reader of `tax_lines` would have to remember, with an overcharged customer or leaked settlement data as the failure. Same shape, opposite side of the ledger.

What is borrowed instead is the **vocabulary**. The line carries `taxability_reason` validated against `Spree::TaxLine.taxability_reasons` — one list, so a provider registering a treatment registers it once — plus `country_code`/`state_code` through `has_iso_geography`, holding the **seller's** jurisdiction rather than the shopper's. `Spree::CommissionTax` is the ephemeral value object the resolver returns, carrying rate and treatment together; only the tax engine sets a jurisdiction, since an operator override or a store default is a number somebody typed and knows no country. Should a fee ever attract two levies at once, these are the columns that move to child rows, and they will already be named as `TaxLine` names them.

**EU base (RESOLVED 2026-06-25):** commission is computed on the seller's **net (ex-VAT)** item price, and `tax_amount` is applied **on top of the commission** — the marketplace fee is a separate taxable supply from the consumer's item sale, so the two VATs never mix. That base toggle stays available for non-EU/edge merchants who want a gross base (shipped as `tax_inclusive`), but the EU default is net-base + fee-VAT. The **tax-on-the-fee** field is mandatory and is the headline EU feature. The commission tax *rate* is resolved through `6.0-tax-provider.md` (per-Market TaxProvider) rather than a bare `platform_fee_tax_rate` column on the seller (RESOLVED — see Resolved Decisions).

### 4. Commission rate resolution: layered rules, first match wins in operator order — generalize the legacy flat rate

The legacy module resolves a **single flat percentage** with a two-level fallback: the product's platform-fee override if set, else the seller's default rate. That is "very simplified" — percentage only; no categories, no caps, no currency scoping. The industry pattern generalizes this into a proper `CommissionRate` + `CommissionRule` engine (operator-ordered, first-match-wins, dimension-grouped targeting rules, `percentage | fixed`, `min_amount` floor, currency gate, no-rules = global default).

**6.0 adopts the rule-engine shape but keeps the legacy fallback as the default ladder.** New models `Spree::CommissionRate` (position, kind, value, currency, commission tax handling) + `Spree::CommissionRule` (polymorphic `subject` → Product / Category / Seller / global). Resolution walks enabled rates in list order, first match wins. Seed a marketplace-wide rate at the bottom of the list so narrower rates an operator adds resolve ahead of it.

**Rule matching: every rule must hold, and a rule naming several records means any of them.** A rate carries typed rules (Product / Category / Seller / value band / …); the rate matches a line item when every one of them says yes, and a rule holding several ids is satisfied by any of them. A category rule naming Electronics and Cameras beside a seller rule naming X reads "(Electronics OR Cameras) AND seller X" — which expresses plain lists *and* the **seller × category pairing** today's Enterprise sells (user docs: "per seller, per category-seller pairing, or per individual product") with no `match_policy` knob at all. The leading surveyed OSS engine uses the same semantics, so the model is proven; where we differ deliberately is precedence — an explicit operator-ordered list instead of implicit most-specific-wins, which is more predictable (already RESOLVED below).

**Rule shape evidence (survey 2026-08-17).** Read against the enterprise platform's own published API contract, our `(subject_type, subject_id)` rule is the weakest of the three models surveyed. There, a rule carries a typed configuration block — seller ids, channel codes, brands, condition codes — plus a validity `period` and an applicability ceiling, and its rate is a list of tiered thresholds rather than one number. Every dimension we currently cannot express without a migration (price band, channel, validity window, product attribute) is a field there. The other OSS engine shares our shape and is equally stuck: five hardcoded dimensions behind a `switch` with no extension point, and it removed its own minimum-amount cap rather than generalising it. The conclusion is that a commission rule needs **its own configuration**, not merely a pointer to a record — which is what the STI rule pattern already used by `Spree::PriceRule` and `Spree::DeliveryMethodRule` provides (see Resolved Decisions).

Two specifics worth copying rather than inventing. Tiering is expressed as thresholds carrying only a lower bound, so bands are contiguous by construction and can neither overlap nor leave a gap — safer than storing min/max pairs and validating the relationship. And precedence there is likewise an explicit operator-declared ranking (a per-category ordered list), not inferred specificity: both surveyed platforms independently concluded the merchant must be able to state which rule wins.

**Precedence evidence (source review 2026-08-17).** That engine is worth reading on this point because it has now tried *both* of the alternatives we rejected. It shipped a `priority` integer, then dropped it in a later migration in favour of most-specific-wins — scoring a rate by how many distinct dimensions it names, tie-broken by creation date. Two failure modes follow from that scoring and are visible in its current source: dimensions are unranked, so a product-specific rate and a seller-wide rate both score 1 and the *older* one wins; and creation order therefore becomes load-bearing configuration a merchant can neither see nor change. Our ordered list is the third option and answers both — the ladder is explicit, visible, and reorderable. The same review found that engine also removed its `min_amount` cap, and has no notion of tax on the commission at all, so our floor/cap and the EU fee-VAT have no prior art there to copy.

**`include_shipping` on the rate** (default `false`): when the resolved rate has it, the same calculation also runs against the seller order's delivery amounts, persisting a fulfillment-scoped `CommissionLine`. The surveyed OSS competitor commissions shipping via a global-rate-only flag, and Amazon-style referral fees include it; the legacy module was items-only (its order-level "reverse fee" only prorates *item* commission on whole-order refunds — shipping is excluded from its base). Ours is per-rate — strictly more flexible than a global-only flag, and off by default so legacy behavior is preserved.

**Percentage only (RESOLVED 2026-08-17, shipped).** A flat fee cannot charge delivery. A percentage answers "what share of this money is ours?", and postage is money; a flat fee answers "what do we charge for handling this?", and the parcel is part of the sale already being charged for — so a £5 rate on a three-item order was billing £20. The flag is refused on a `fixed` rate and the toggle is hidden for one, matching the surveyed OSS engine, which reads its shipping flag off the percentage default only. A marketplace wanting a flat charge on delivery states it as its own rate, which composes correctly because rates resolve independently.

**Flat fees multiply by quantity (RESOLVED 2026-08-17, shipped).** A flat fee is charged per unit sold, not once per line — three cameras in one line earn the same as three bought one at a time. Charging per line would have let the shopper set the fee through cart grouping alone, and would have made quantity matter under a percentage but not under a flat fee, so switching a rate between the two kinds silently changed more than the number. **No per-line/per-order toggle**, for two reasons. Per-unit is what merchants assume — the large marketplaces state their flat charges as "per unit" and "per item", and that is the industry vocabulary. And a per-*order* mode has no coherent answer in this engine, because rates resolve per line: a basket with a camera at 8% and a book at £2 has no single rate to charge the order with. The enterprise platform reviewed for this reaches the same conclusion structurally — its per-order charges are a separate seller-fee concept in its ledger, never a mode of its commission engine, whose order-level total is documented only as the sum of its lines. A per-order platform charge, if wanted later, is its own entity rather than a flag here. The floor and cap still apply per line, to the multiplied total — which is the first time they do useful work on a flat rate, since one could not previously exceed itself.

**Per-currency amounts (RESOLVED 2026-08-17, shipped).** **Every amount a rate states is per currency**, held in `spree_commission_rate_values` one row per currency: a flat fee's `amount`, and a percentage's `min_amount` floor and `max_amount` cap. The rate itself carries no `currency` column at all. This replaced a single `currency` on the rate, which had meant a dollar-priced rate silently not applying to a euro sale — a seller's fee depended on how the buyer paid — and then, briefly, left the floor and cap on that one column while the flat fee had moved on, so one form asked the same question two different ways. Nothing is ever converted: a converted figure would drift daily against a fee the seller agreed to, and a cap that moves is not a cap. Follows `Spree::Price` and the delivery calculators' `amounts` hash, and the repo's standing "one explicit amount per currency, no FX" decision.

The two kinds differ in what an unstated currency means, and the difference is deliberate. A **flat fee** is skipped entirely for a currency it names no amount in, and the sale falls to the next rate — a fee with no number is not a fee. A **percentage** always applies, since a ratio needs no currency; only its bounds stay behind, so a euro sale under a dollar-capped rate is charged **unbounded** rather than skipped. Skipping would read "we capped our dollar fees" as "we want no commission on euro sales", which no marketplace means. Amounts and bounds share a row but are written by separate fields (`amounts=` / `bounds=`), and neither write may erase the other — a row carrying bounds survives being dropped from the flat fee, and clearing a bound retires the row only if no amount is left on it. Four specs pin those crossings, since sharing a row is exactly where a wholesale-replace writer silently deletes someone else's data.

**Precedence (RESOLVED 2026-06-25; reshaped 2026-08-17 — `acts_as_list`, shipped): an ordered list, not a fixed ladder.** Rates carry `position` via `acts_as_list scope: :store_id` and are walked top-down, first match wins — so the order an operator sees in the table *is* the precedence, and reordering is dragging a row rather than reasoning about an integer. **New rates are created at the top** (`add_new_at: :top`): a rate exists to say something more specific than what is already there, and appending would file it behind the catch-all that matches everything. Seeds put a disabled marketplace-wide rate at the bottom, which makes the product-then-category-then-seller order merchants asked for fall out for free without hardcoding it. Ordering is deliberately **not** derived from how specific a rate's rules look: a rate may name a product, a category and a seller at once, so there is no single dimension to sort on, and "narrowest wins" guesses at an intent the operator can simply state.

**The failure mode this model has, and which every change near it must be checked against:** a rate that matches everything makes every rate below it unreachable, and the mistakes that produce one are all silent widenings — a rate charging *more* sales than anybody asked it to, with a 200 saying it worked. Three separate instances surfaced while building this, each needing a deliberate refusal rather than a sensible default: a rules payload naming an unreachable record used to drop that rule (leaving a narrow rate global), an unregistered rule kind used to be skipped by `assign_typed_association` (same result), and the seeded catch-all was created at the top of the list by `add_new_at: :top` (shadowing every targeted rate on a store that already had some, once enabled). `CommissionRate#global?` exists so the condition is at least visible — the admin marks such a rate — and any future work on rules, ordering or seeding should ask what happens when its input is wrong in the widening direction.

### 5. One payment, recorded as a per-seller split — adopt the explicit split-payment record

The customer makes **one payment** (one gateway charge against the order group). Do **not** create N gateway charges. The split is bookkeeping:

Two patterns exist in the wild: (a) link one payment collection to all child orders and split captures *proportionally* into per-order transaction rows computed on read; or (b) an explicit **split-payment record** per child order (`authorized_amount`, `captured_amount`, `refunded_amount`).

**6.0 adopts the explicit per-seller payment record** (pattern b) rather than proportion-on-read, because a marketplace needs a durable per-seller audit trail for partial captures, partial refunds, and payouts. This is also what the legacy module effectively did by creating real `Spree::Payment` rows on each seller sub-order — but 6.0 does **not** clone `Payment` rows: the gateway object stays singular.

Concretely: `Spree::Payment` gains a nullable `order_group_id` — a grouped checkout's payment attaches to the **group** (its `order_id` is nil); a plain ungrouped order keeps `payment.order` as today. The per-seller bookkeeping is a new **`Spree::PaymentSplit`** row per child order (`payment_id`, `order_id`, `authorized_amount` / `captured_amount` / `refunded_amount`, `currency`) — sketched in Design Details. A partial refund on one seller's order updates that child's split, never the siblings'.

### 6. Per-seller totals are computed independently, not prorated

Confirmed by the references and the legacy module (its split moves line items, adjustments, inventory units, and shipments wholesale to the child order, then recomputes). Taxes/discounts/shipping travel with whichever line item or shipment they were attached to, into exactly one seller's order; each child order recomputes its own totals. **No cart-level total proration** (the one exception is the single payment capture, Decision 5, and store-credit allocation, which the references and the legacy module prorate per item).

### 7. Native models, not decorators

The legacy module is a large decorator layer prepending ~35 core classes. 6.0 brings this into core as **real models, associations, and services** — `Spree::Seller`, `Spree::OrderGroup`, `Spree::PaymentSplit`, `Spree::CommissionLine`, `Spree::CommissionRate`, `Spree::CommissionRule`, `Spree::SellerTransfer`, `Spree::SellerPayout`, and a `Spree::Carts::SplitBySeller` (or folded into `Carts::Complete`) service. No `prepend`. Follow `CLAUDE.md` model conventions (`Spree.base_class`, prefixed IDs, `class_name`/`dependent` on every association, string status columns, paranoia where needed).

Deliberately **not** new models: seller team membership and invitations reuse the existing polymorphic rails — `Spree::RoleUser` (`resource: seller`) and `Spree::Invitation` (`resource: seller`; its `resource` docstring already names Seller as an intended type). The legacy admin's `current_seller` hooks (`spree/admin` `base_controller.rb:155`, `resource_controller.rb:249`) exist only for the Enterprise module's legacy-admin panel and die with the legacy admin; the 6.0 equivalent is `current_seller` scope-fetching on a dedicated Seller API branch (Decision 10 — not ability-level scoping, which the RBAC catalog cannot express).

### 8. The parent is a dedicated `Spree::OrderGroup`, not `Order#parent_id` (RESOLVED 2026-06-16)

The container is a **separate `Spree::OrderGroup` model**, not the legacy "an Order that is secretly a parent" (`Order#parent_id` + `state == 'splitted'`).

**Crucially, `OrderGroup` is a domain-neutral primitive, not a marketplace concept.** It means "N orders placed together as one customer transaction" — multi-vendor is merely its *first* consumer. The same primitive is reused, without a second container model, for: split-by-fulfillment-location (one checkout → per-warehouse orders), split-by-availability (in-stock + pre-order/backorder in one cart), and B2B split-by-company-location (`6.0-channels-catalogs-b2b.md` → 6.1). Naming it `OrderGroup` (not `SellerOrderSet`) keeps it reusable across all of these. The seller relationship lives on the **child `Order`** (`order.seller`), never on the group — the group stays seller-agnostic.

Why a dedicated model beats `parent_id`:
- No ambiguity / no empty parent orders. A parent `Order` with `parent_id: nil` and zero line items (the legacy shape) breaks every "an order has line items" assumption and forces a family of union-association and "is this really a parent?" workarounds. `OrderGroup` simply *has many* orders.
- Clean composition with the Cart/Order split: `Cart` (one, mixed) → on completion → one `OrderGroup` owning N child `Order`s. The group is the natural home for the single payment, the customer, and the shared addresses; children own their own line items, shipments, totals.
- Future-proof: when split-by-location or B2B needs the same fan-out, they reuse `OrderGroup` rather than overloading `Order` again.

**This requires an Enterprise-side data backfill** (not core — existing OSS stores have no sellers). The Enterprise module must ship a one-time migration that, for every legacy `splitted` parent order, creates an `OrderGroup`, attaches its `parent_id`-children as the group's orders, and migrates the legacy commission rows into `spree_commission_lines`. The backfill lives in Enterprise because only Enterprise customers have legacy marketplace data; core ships clean. Tracked as a hard dependency for the Enterprise 6.0 upgrade. See Migration Path.

### 9. Two-level fund ledger — `SellerTransfer` (on-fulfillment) + `SellerPayout` (on-interval), generic in core + a pluggable provider that executes it (RESOLVED 2026-06-25)

**Transfer and payout are two distinct events** — the legacy module conflated them, and an earlier draft of this plan repeated the mistake. They must be separate models:

- **`Spree::SellerTransfer`** — the **per-order** fund movement, triggered **on-fulfillment**. When a seller's order is fully fulfilled (shipped; digital fulfills instantly after payment), the seller *earns* `sale − commission`; that credits their balance. One transfer per fulfilled seller order. This is what the legacy Stripe transfer ledger actually modeled (it fires when the seller sub-order's shipments are all shipped).
- **`Spree::SellerPayout`** — the **scheduled settlement**, triggered **on-interval** (daily/weekly/biweekly/monthly). It sweeps the seller's accumulated unpaid transfers, batches them into one bank settlement, and debits the balance. One payout per interval per seller (per currency).

The legacy module only models the transfer and **outsources payouts to Stripe** (it just configures Stripe's native connected-account payout schedule — there is no `Payout` record; its "payouts" screens are *reports* aggregating transfers, not a ledger). That's fine for Stripe-only Enterprise but **wrong for OSS core**: a `system`-provider marketplace has no Stripe to schedule settlements, so it needs its own payout records.

```text
Spree::SellerTransfer   (one per fulfilled seller order, on-fulfillment) → credits seller balance
      ↓ accumulate                                                   (sale − commission)
Spree::SellerPayout     (one per interval per seller, scheduled)  → debits balance, settles to bank
      ↑ has_many transfers (each SellerTransfer.payout_id)           (batches N transfers; amount = Σ them)

seller.balance = Σ(completed transfers) − Σ(completed payouts)   # derived bridge between the two levels
```

**Payout ⇄ Transfer link (RESOLVED): transfers `belong_to` a payout.** Each `SellerTransfer` carries a nullable `payout_id`. The scheduled job sweeps all unpaid completed transfers for a seller, creates one `SellerPayout`, and stamps them with its id; `payout.amount = SUM(its transfers)`. Every payout itemizes *exactly* which order-transfers it settled — auditable, and robust to mid-period reversals (a refund after a transfer was already paid out becomes the **next** period's negative transfer rather than corrupting a closed payout). This is the seller-balance ledger the surveyed industry references *documented but never implemented* — Spree ships it properly.

Both levels are **generic in core + provider-executed**, mirroring `6.0-tax-provider.md` / `6.0-delivery-rate-provider.md`:

- **Core ships both ledger models** + a **`Spree::PayoutProvider::Base`** strategy with a **`system`** default: it records transfers (on-fulfillment) and payouts (on-interval) but moves no money — the OSS operator sees the per-seller balance and the itemized payout records, and settles offline (marking the payout complete). This is what #13323 means by core knowing "what's owed."
- **The monorepo ships the basic `Spree::PayoutProvider::StripeConnect`** (boundary amendment 2026-07-15), alongside the Stripe core gateway being pulled in from the standalone `spree_stripe` repo — only the payment-sessions-API gateway classes come over (likely into `spree/core`); the legacy v2-API/storefront code stays behind. The provider: Express-account creation + hosted onboarding link surfaced in the seller dashboard + `account.updated` webhook → payout-account status on the seller. `transfer!` executes an on-fulfillment `Stripe::Transfer` tied to the charge via `source_transaction` (gated on the account being payouts-enabled); `pay!` maps `payouts_schedule_interval` onto Stripe's native connected-account payout schedule and records `SellerPayout` rows from payout webhooks.
- **Enterprise extends that provider with the money operations**: `reverse!` executing prorated Stripe transfer reversals on refund (ports the legacy reversal logic), negative-balance netting against future transfers, KYC/account-health workflows beyond the hosted flow, and ledger⇄Stripe reconciliation + payout reports. The paid tier operates the unhappy paths.

**OSS funds flow — two modes.** (a) **`system`** (no gateway objects): the customer's single charge settles in full to the operator's own gateway account as a plain payment; the split is pure bookkeeping (`PaymentSplit` + this ledger); disbursement happens outside the gateway — on the payout schedule the operator pays each seller by bank (SEPA/ACH/wire), guided by the itemized `SellerPayout`, and marks it complete, or automates it (`seller_payout.due` webhook → banking API → `POST /seller_payouts/:id/complete`). The platform is merchant of record for the full transaction and carries seller payables on its own books. (b) **`stripe_connect` basic** (the monorepo Stripe gateway): sellers onboard as Express accounts through Stripe's hosted link; on fulfillment the provider executes a real transfer — money moves automatically. What OSS mode (b) does **not** do is pull money back: a refund always writes the ledger reversal (the books stay correct in every tier), but the Stripe transfer reversal, netting against future transfers, and reconciliation are Enterprise — the first production refund is where the upgrade conversation starts. Note the hard coupling that shapes this seam: a `Stripe::Transfer` requires a connected account, so basic Connect onboarding necessarily ships together with OSS transfer execution; what Enterprise keeps is not onboarding itself but the KYC *operations* around it.

**Transfer amount basis** (ports the legacy allowed-transfer-amount rule, generalized per the resolved store-credit decision): the seller's sale value minus commission, **payment-source-agnostic** (store credit / gift card is the platform's funding concern, not the seller's):

```text
transfer.amount = seller_order.total − seller_order.commission_lines.sum(:total)
```

`seller_order.total` is the child order's grand total — items + its delivery + its taxes − its discounts. The deduction is `CommissionLine#total`, i.e. commission **including the VAT on the commission** (the platform invoices the seller commission + VAT; the seller reclaims that VAT as input tax). The seller is **merchant of record** for their child order in v1: consumer tax and shipping revenue are theirs. A *marketplace-facilitator / deemed-supplier* mode — where the platform withholds consumer tax and the basis becomes `total − tax_total − commission` — is selected per seller by `spree_sellers.tax_remittance` (`seller` | `platform`, default `seller`; RESOLVED 2026-08-15): core owns both branches of the math so the ledger stays provider-independent, while *deciding* that a seller is platform-remitted (nexus, deemed-supplier rules) is Enterprise "automatic taxes" territory (see the scope table).

**Reversals** (ports the legacy reversal chain): a refund on a shipped order writes a negative `SellerTransfer` linked to the original via `reversed_from`, so the seller's net earned is always `Σ(seller_transfers)`. If the original was already settled in a closed payout, the reversal lands as a negative transfer in the next payout period. Ties into `6.0-returns-exchanges-claims.md`. The reversible-amount rule — original minus already-reversed, floored at zero — carries over as a model method on `SellerTransfer`.

**Triggers (RESOLVED):** `seller_transfer.due` fires **on-fulfillment** (all the seller order's fulfillments fulfilled); `seller_payout.due` fires **on the seller's `payouts_schedule_interval`** (daily/weekly/biweekly/monthly/manual, `nil` ⇒ store default — the "Use marketplace default interval" semantics in today's Enterprise settings, carried over). Core honors `manual` natively (operator triggers settlement by hand); Enterprise implements the scheduled intervals.

**Naming & scope (RESOLVED 2026-06-25):** the models keep the `Seller` prefix and `belongs_to :seller` — they are deliberately *not* generalized to bare `Transfer`/`Payout`. Rationale: (1) "transfer" and "payout" are heavily overloaded payment terms (gateway ACH/wire transfers, Stripe payout objects) — the `Seller` prefix is what keeps these ledger records unambiguous and avoids re-introducing the very namespace confusion that made the legacy gateway-namespaced transfer model unclear; (2) the reusability that a dealership / B2B revenue-share scenario would want comes from an **abstract payee** (`belongs_to :payee, polymorphic`), *not* from a generic model name — and we have no second consumer yet, so per YAGNI we bind to `Seller` now. If a concrete non-seller payee requirement lands later, the migration path is to make `payee` polymorphic (Seller + e.g. CompanyLocation) — a localized schema change — rather than a rename. This mirrors `OrderGroup`'s seller-agnostic structure, but the inverse conclusion is correct here: the container is generic because the seller lives on its children, whereas these ledger rows are *intrinsically* a payment to one specific payee.

### 10. Seller users are `Spree::AdminUser`, on a dedicated `/api/v3/seller` API branch with its own JWT audience and login registry (RESOLVED 2026-08-15)

Two questions were re-examined against the shipped auth (PR #14380) and RBAC (PR #14412) work — should seller staff be a separate user model, and should they use the Admin API with narrower permissions or their own routes. Both settled the same way: **reuse the principal, separate the surface.**

**Principal — `Spree.admin_user_class`, no `SellerUser` model.** The platform is two-principal after #14380: `Customer` buys, `AdminUser` operates a back office — and a seller's team operates a back office. That one class now carries the entire auth stack (`has_secure_password`, lockout, password policy, `generates_token_for :password_reset`, `UserIdentity` SSO linking, invitation acceptance, refresh-token cookie flow); a third principal would duplicate every one of those (and every future MFA/passkey improvement) as a second security surface. The RBAC rails already assume it: `RoleUser` (`user: Spree.admin_user_class`, `resource: seller`, store binding derived from the seller), `Invitation` (`resource: seller`), and `Spree::Ability#staff_roles` deliberately excluding seller-resourced assignments as belonging to "their own panel's ability". One human, one login, several hats: an `AdminUser` may hold a store role and a seller role at once (the operator's own first-party seller; a merchant selling on two marketplaces run on two stores). A seller member is **not** store staff — membership is by *resource type*, never by `store_id`.

**Surface — a third v3 branch, `/api/v3/seller/…`, beside `store` and `admin`.** The plan's earlier line ("seller users hit the same admin API with seller-scoped abilities — no separate seller routes") is superseded: it relied on `PermissionSets::SellerUser` with `seller_id: user.seller_ids` hash conditions, and #14412 removed permission sets with no bridge — the catalog is flat `read_*`/`write_*` keys with no conditions, and the RBAC plan already re-decided on 2026-08-08 that "seller-panel endpoints scope-fetch through `current_seller` exactly as admin endpoints scope through `current_store`". Reusing the ~300 admin endpoints would mean per-principal forks in every `scope`/`find_resource`/incidental lookup (`stock_location_id`, `reason_id`, `variant_id` on line-item writes) — each miss a cross-seller read or write inside the same store — plus per-principal field masking in serializers. A seller branch is ~20 controllers, each written scope-first (`current_seller.products`, `current_seller.orders`, …): **IDOR by construction**, the same way store isolation works on the admin branch today (controller scoping only — the ability layer has no tenancy conditions). What a seller may not do (publish to channels, edit orders, refund, approve itself, create stock locations) is an endpoint that does not exist, not an ability rule. Do **not** subclass admin controllers into the seller namespace — inherited `current_store.*` lookups are precisely the leak; share workflows and permitted-param lists, never controllers.

**Isolation is enforced at the token layer, not only at membership.** Three requirements, all mandatory (they answer the two concrete objections to a shared model — "staff must be SSO-only while sellers use passwords" and "what happens when a seller token hits the Admin API"):

1. **Own JWT audience** — `JWT_AUDIENCE_VENDOR = 'seller_api'` beside `store_api`/`admin_api`. The admin branch rejects a seller token at `decode_jwt` (`verify_aud`) with 401 before any store resolution, membership check, or ability is built, and the seller branch rejects admin tokens symmetrically. Fail-closed at the outermost layer; the `resource_type` filters below remain defense in depth.
2. **Own login surface** — `Spree.seller_authentication_strategies` (default: `:email` only) + `/api/v3/seller/auth/{login,refresh,logout,password_reset}`. Login policy is per surface, not per class: an SSO-only store keeps `Spree.admin_authentication_strategies.remove(:email)` while sellers sign in with passwords, against the same `AdminUser` table. The seller login **refuses anyone with no seller membership** (`role_users` on `resource: seller`), the same "unprovisioned subject is rejected" rule the admin SSO callback applies — so a staff-only account cannot mint a token here, and a token it *could* mint carries the seller audience anyway.
3. **Refresh tokens carry the audience** — `spree_refresh_tokens.audience` (string), written at mint and enforced on refresh, with a separate cookie name/path for the seller panel. Today's `RefreshToken` has no audience, so without this a seller-minted refresh token could be presented to the admin refresh endpoint and exchanged for an `admin_api` JWT.

**Accepted trade-offs:** password policy and lockout stay model-level and therefore shared between staff and sellers (desired — a seller account locks out too; a stricter *staff-only* policy is a per-surface login concern, like MFA later). Thin controllers are duplicated across the admin and seller branches; that duplication is the price of an auditable tenancy boundary.

**Cross-plan obligation (admin branch, ship ahead of Phase 1):** `AdminAuthentication#current_user_member_of_store?` matches `role_users.exists?(store: current_store)`, which a seller-resourced assignment passes (its store is the seller's store) — the Ability then yields no keys so scoped endpoints 403, but the scope-exempt ones (`/admin/tags`, `/admin/store` show, exports/imports index, translation batches) are reachable. Tighten to `resource_type: 'Spree::Store'`, mirroring `Ability#staff_roles` and `RoleGrantGuard`, with a regression spec.

### 11. Several sellers may sell the same item: the seller lives on the **variant**, not on a separate offer record (RESOLVED 2026-08-16, **shipped**)

Until now this plan assumed one product belongs to one seller (`products.seller_id`), so two sellers of the same physical item produced two unrelated products and two storefront listings. That is the right shape for unique goods and the wrong one for commodities — the same book, phone or part sold by several sellers. **Supporting both is the single most requested capability the legacy module could not deliver**, so 6.0 must get the grain right; retrofitting it after the split and commission engine are built on one-owner assumptions is the expensive path.

**The seller is an attribute of the variant.** `spree_variants.seller_id` (nullable) alongside the existing `spree_products.seller_id`. The column is the variant's *override*: blank defers to the product, so a seller who owns a whole listing is named once on the product and every variant inherits them, and only a variant blank on **both** is first-party. Every consumer — the split's partition key, SKU uniqueness, the buy box — reads that one resolved answer rather than the raw column. One product may therefore hold variants from several sellers: a new unit from the marketplace's own warehouse and a refurbished one from a seller, on one product page. **Condition (new / used / refurbished) is an `OptionType`,** so it splits the variant like any other axis and inherits the option machinery already there — presentation kinds, positions, storefront pickers and facets.

**Why not a separate `Offer` record.** The surveyed implementations that model this all introduce one, but they share a constraint Spree does not have: each is built *on top of* a commerce engine or a merchant's existing catalog, so they cannot put a seller on the variant and cannot re-key inventory. Their offer row is a variant they were not allowed to write. Spree owns the variant, and an offer would duplicate almost all of it — seller, sku, price, stock, condition, delivery config. Modelling it separately would mean a second pricing pipeline, a stock anchor migration (`spree_stock_items` is uniquely keyed on `(variant, stock_location)`), a new `line_items.offer_id` with the cart's variant-keyed deduplication reworked around it, and offer-relative rewrites of ~67 purchasability call sites. On the variant, all of that is already true by construction: two sellers are two variant rows, so two stock rows, prices resolve unchanged, and `line_item.variant.seller_id` gives per-line seller attribution — which is precisely what the split in Decision 1 partitions on.

*"Offer" remains the right word for the storefront* ("3 offers from 2 sellers"). Presentation vocabulary need not be a table.

**Consequences that must ship with it:**

- **Buy box.** Product-level answers (`purchasable?`, `in_stock?`, headline price, `default_variant`) become **buy-box-relative**: a selection service groups a product's sibling variants and picks a featured one, and the existing rollups then answer about the winner. Selection is **computed, never a stored winner column** — it depends on price, stock and delivery, all of which move constantly — and pluggable from the start, since ranking is marketplace policy. Real implementations weight landed price and delivery speed, gate on seller performance, and rotate among near-equals rather than crowning one; losing sellers stay visible. Because condition is an option, the buy box is keyed on **(product, option combination)**, which gives the industry's "a new buy box and a used buy box" behaviour for free.
- **`default_variant` prefers first-party.** The product's public identity — headline price, SKU, and the EU Omnibus `prior_price`, which is a compliance claim — should be the operator's own listing where one exists, not whichever seller sorts first.
- **Delivery profile gains a variant-level override.** It is product-level today, and `Stock::Splitter::DeliveryProfile` memoises one profile per `product_id`, so sellers sharing a product would share whichever profile resolved first — packing and pricing one seller's goods with another's shipping config. A nullable `delivery_profile_id` on the variant falling back to the product follows `Variant#tax_category` exactly. This is worth having regardless of marketplaces: a merchant selling a poster and its framed print under one listing cannot express that today.
- **Writes never destroy another seller's variants — enforced at the seller branch, not the model.** `Product#variants=` is full-replacement — variants absent from the payload are destroyed — and the dashboard round-trips the whole array on every save. That is correct for the **operator's** write path, and it is deliberately not narrowed by seller there: marketplace staff see and write every seller's variants on a master product (that is what running a marketplace means), and on an owned product all variants are one seller's anyway. The danger is only a **seller's** write path handed a full-replacement setter with a narrowed read. So the obligation sits where Decision 10 already puts every seller-branch concern: the seller products controller (Phase 3) scope-fetches through `current_seller` and must never pass a whole-product `variants:` payload through — it writes its own rows through the nested variants endpoint, where a row belonging to another seller is a 404 by scope. No model-level bound (an earlier `writing_seller` was cut as over-engineered — it solved Phase 3's problem in the wrong layer).
- **Option filtering must match within one variant.** `with_option_value_ids` issues a separate subquery per option type against `product_id`, so "Blue AND XL" matches a product with a Blue variant and a *different* XL variant. This is a pre-existing storefront bug that sharing a product across sellers makes worse; the fix is to require one variant to satisfy every value.
- **Search documents are per-product** with a single scalar price and a single boolean stock. They describe the buy-box winner, and a seller's write must not silently rewrite a rival's listing facts.

**Operators see everything; sellers see their own.** Marketplace staff manage every variant on a product, including other sellers' — they run the marketplace. Seller isolation is the `/api/v3/seller` branch scope-fetching through `current_seller` (Decision 10), not a narrowing of the admin surface.

**Both shapes coexist with no mode switch.** A store selling only its own goods has `seller_id: nil` everywhere and notices none of this. Unique goods keep one seller per product. A commodity gets sibling variants from several sellers. Promoting an exclusive listing to a shared one is a data change, not a migration. What this deliberately does **not** solve in 6.0 is *catalog matching* — deciding that two sellers' submissions are the same item. Every surveyed platform treats that as hard and several sell it separately; core should ship exact matching on a typed identifier (the identifier's namespace stored explicitly, never inferred from its shape) and leave fuzzy matching to an extension.

**Supersedes:** the "SKU uniqueness relaxes to per-seller scope" line under Product ownership & approval, which assumed duplicate product rows per seller.

## Design Details

### Seller identity & teams

The headline model. Ports the Enterprise module's seller model — renamed to `Spree::Seller` with prefix `sel_` (2026-08-17), so the Enterprise backfill re-stamps ids rather than carrying `ven_` over — and adopts the lifecycle already shipped in the Enterprise admin (user docs: Invited → Onboarding → Ready for Review → Approved / Rejected / Suspended). **The external-store subsystem is not ported — none of it, ever**: the external store/product/order/category resource family, the per-platform Shopify/WooCommerce connections and sync workers, the category mapper, and the seller-side hooks that reach into them (external-store shipping-method pulls, external-store-derived settings) all remain Enterprise. Core's `Seller` carries no external-store associations, columns, or callbacks — the Enterprise module layers its connection models onto core's Seller from the outside:

```ruby
class Spree::Seller < Spree.base_class
  has_prefix_id :ven
  include Spree::SingleStoreResource
  include Spree::UserManagement   # roles, role_users, users, invitations — the team
  include Spree::HasCustomFields  # Metafields is a 6.1-removed shell
  include Spree::Metadata
  include Spree::TranslatableResource   # about/description translate like Product
  acts_as_paranoid
  publishes_lifecycle_events

  belongs_to :store, class_name: 'Spree::Store'
  belongs_to :billing_address, class_name: 'Spree::Address', optional: true  # on the commission invoice (EU)
  belongs_to :returns_address, class_name: 'Spree::Address', optional: true  # where customer returns route

  has_many :products,        class_name: 'Spree::Product',       dependent: :nullify
  has_many :stock_locations, class_name: 'Spree::StockLocation', dependent: :nullify
  has_many :orders,          class_name: 'Spree::Order'           # child (seller) orders
  has_many :commission_lines, class_name: 'Spree::CommissionLine'
  has_many :seller_transfers, class_name: 'Spree::SellerTransfer'
  has_many :seller_payouts,   class_name: 'Spree::SellerPayout'
  # Teams come from Spree::UserManagement above, not hand-rolled: after the
  # RBAC refactor a RoleUser has no resource of its own, so a seller's team is
  # whoever holds a role the seller owns (`roles` → `role_users` → `users`).

  # name, slug (unique per store), contact_email, billing_email
  # about          : rich text (sanitized HTML column per 6.0-rich-text-descriptions.md)
  # NO denormalized sales_total/commission_total counters (legacy has them) — lifetime
  # revenue & commission derive from commission_lines / seller_transfers (we have a ledger now)
  # NO encrypted name/contact columns (legacy encrypts for its multi-tenant SaaS; core stays plain)
  # logo / square_logo / cover_photo : ActiveStorage attachments (storefront-facing branding)
  # terms_accepted_at : datetime — seller ToS acceptance (store-configured rich-text ToS)
  # holiday_mode_until : datetime, nullable — paused storefront presence ("holiday mode")
  # payouts_schedule_interval : string, nullable — 'daily'|'weekly'|'biweekly'|'monthly'|'manual';
  #                             nil ⇒ store default (store preference), matching today's
  #                             "Use marketplace default interval" semantics
  # minimum_payout_amount : decimal, nullable — sub-threshold balances carry to the next period;
  #                         nil ⇒ store preference default_minimum_payout_amount (RESOLVED 2026-08-15)
  # tax_remittance : string — 'seller' (default) | 'platform'; selects the transfer basis (Decision 9;
  #                  RESOLVED 2026-08-15). Enterprise 'automatic taxes' sets it; core only reads it

  # Ports the legacy lifecycle (status column renamed from `state` per
  # 6.0-normalize-state-to-status.md), but NOT its state machine: approving
  # sends mail and provisions payouts, which is exactly the work
  # 6.0-service-workflows.md keeps out of save callbacks. Transitions are
  # workflows (Spree::Sellers::Invite, ::Approve, ::Suspend, …); the model
  # only declares the values.
  #
  #   pending → invited → onboarding → ready_for_review → approved
  #
  # `approve` also lifts a suspension and revives a rejected seller, so the
  # reachable set is wider than that line — which is the permissiveness the
  # legacy machine had, now expressed as workflow guards rather than a graph.
  include Spree::HasStatus
  has_status :pending, :invited, :canceled, :onboarding, :ready_for_review,
             :approved, :rejected, :suspended, default: :pending

  validates :name, presence: true
  # Scoped to the store: spree_base_uniqueness_scope is empty, so naming it
  # explicitly is what makes two marketplaces able to share a slug.
  validates :slug, presence: true, uniqueness: { scope: [*spree_base_uniqueness_scope, :store_id] }
end
```

- **Two entry paths, one lifecycle.** (a) *Invitation*: operator creates a `pending` seller and invites → `Spree::Invitation` (`resource: seller`, seller-role) → acceptance creates the `RoleUser` and fires `start_onboarding`. (b) *Self-serve application* — a public "become a seller" flow: a Store API endpoint creates a `pending` seller + application; the operator admits into onboarding or rejects. Same state machine, no second flow.
- **Teams** = `Spree::RoleUser` rows with `resource: seller` and `user: Spree.admin_user_class`. Seller admins invite teammates through the same `Invitation` rail the store admin uses. No new membership model.
- **Authorization** (rewritten 2026-08-15 for the shipped RBAC — Decision 10): seller users are `Spree.admin_user_class` and sign in through the seller login surface (own strategy registry, own `seller_api` JWT audience). Authorization on the Seller API branch is the same two-axis model the admin branch uses:
  - *Tenancy* is controller scoping — every seller endpoint scope-fetches through `current_seller` (resolved from `X-Spree-Seller-Id` + a `role_users` membership check on `resource: seller`; `current_store` is **derived** from `current_seller.store`, never taken from a header). Writes are force-stamped `seller_id`. Nothing tenancy-related lives in the ability.
  - *Capability* is the permission catalog — the same `read_*`/`write_*` vocabulary, through the same `ScopedAuthorization` key gate. Adopts the RBAC plan's settled direction: `Role#audience` (`staff` | `seller`); a **seller-grantable catalog subset** marked at `register_resource` (products, orders, fulfillments, stock, returns, exports/imports, analytics — never `settings`, `staff`, `api_keys`, commissions); the roles editor filters its grid by audience; assignment and invitation guards pair audience with resource type. Seller roles are defined by the operator (role names are globally unique — sellers assign their people to tiers, they do not define roles). Two seller-only catalog resources: `seller_profile` (own profile, branding, addresses, onboarding tasks) and read-only `payouts` (the seller's ledger view). `Spree::Ability` gains a `resource:` option (default the store) so the seller branch builds its ability from `role_users` where `resource: current_seller` — the "seller-side ability" the RBAC plan deferred here.
  - The legacy `PermissionSets::SellerUser` baseline survives only as the **seeded default seller role's key set** (`write_products`, `write_orders`, `write_fulfillments`, `write_stock`, `write_returns`, `write_exports`, `write_seller_profile`, `read_payouts`). "No commission management / no channel publication / no self-approve / no stock-location create" are endpoints that do not exist on the seller branch, not ability rules. `#13323`'s "manage permissions (via code)" = seeds or the roles API, per the RBAC plan.
  - `Spree::UserRoles` gains `has_many :sellers, through: :role_users, source: :resource, source_type: 'Spree::Seller'` beside `stores`; the seller branch's `/me` returns the seller memberships so a panel can pick its context. `AdminUserMethods#can_be_deleted?` reasons about `Store.current.users` — the seller branch needs its own "last owner of this seller" rule.
- **Onboarding checklist — superseded 2026-08-18 by `6.0-seller-onboarding-requirements.md`.** The "lightweight task registry" below became an operator-configured model (`Spree::SellerRequirement` rows over registered kinds, persisted `SellerRequirementSubmission` for attested/verified checks, `Sellers::SubmitForReview` + `Approve` as the only gates); the paragraph is kept for the intent it records. Original text: **Onboarding checklist — the registry is core, Enterprise contributes tasks.** Core ships a lightweight task registry (task key + completion check + required flag) and the core tasks: accept ToS, complete profile/branding, billing + returns addresses, at least one delivery method, at least one product. `submit_for_review` requires all required tasks complete (ports the legacy `onboarding_completed?` guard — without a checklist the guard has nothing to check, and sellers can't see what's missing). Extensions **register additional tasks** into the same registry: the monorepo Stripe gateway adds "connect your Stripe account" (Express onboarding); Enterprise adds KYC verification follow-through and Shopify/Woo store connection — the paid value is in *those tasks*, not in the tracker. The seller dashboard and the operator's onboarding-progress view (the n/m column in today's Enterprise) both render from the registry.
- **Storefront visibility**: only `approved` sellers (and their products) are exposed; `holiday_mode_until` in the future hides the seller's products from sale (purchasability gate, not catalog deletion).

### Order splitting

```text
Spree::Cart (one, mixed)
  └─ line_items (owner: cart_id set, order_id nil)   ← 6.0-cart-order-split.md

   cart.complete!  →  Spree::Carts::Complete  →  splits by seller
        │
        ▼
Spree::OrderGroup (the transaction container — customer, single payment, shared addresses)
  ├─ Spree::Order (seller A)  belongs_to :order_group, belongs_to :seller
  │     ├─ line_items (owner = this order)   — seller A's items
  │     ├─ fulfillments                       — seller A's fulfillment (Shipment pre-rename)
  │     ├─ commission_lines                   — frozen at split
  │     ├─ seller_transfer                    — seller A's earning, on-fulfillment (level-1 ledger)
  │     └─ payment_split                      — seller A's share of the single payment
  ├─ Spree::Order (seller B)  …
  └─ …
```

The `OrderGroup` owns the customer + single payment + shared addresses; each child `Order` owns its own line items, fulfillments, and totals. The group carries no seller reference — `seller` lives on the child order (Decision 8). Vocabulary follows `6.0-fulfillment-and-delivery.md` throughout: Fulfillment (né Shipment), DeliveryMethod (né ShippingMethod), and the ledger trigger is **on-fulfillment** — which also covers digital/instant fulfillment types (a digital seller order fulfills, and therefore earns, immediately after payment).

- **Trigger & gate:** explicit call inside `Spree::Carts::Complete`, after payment authorization. The gate is **more than one fulfillment partition** — line items partition by the `seller_id` snapshot, with `nil` (the operator's own first-party items) forming its own partition, and the split + `OrderGroup` happen **only when ≥ 2 partitions exist**. A mixed cart of seller A + first-party items splits into two child orders (one with `seller_id: nil`). A single-partition cart — all first-party, or all one seller — completes as a **bare order exactly as today**: no group, no `PaymentSplit`; when that partition is a seller's, the order still carries `seller_id` and commission + ledger apply unchanged (Phase 2's compute-only mode is exactly this). Not a state-machine callback — and not the legacy shape either: the legacy module splits **~30 seconds after checkout** in a background job, leaving a window where the parent order exists un-split. 6.0 splits synchronously inside completion, so the checkout response already returns the finished `OrderGroup` and no `splitted`-pending state ever exists.
- **Partition key:** `line_item.seller_id`, denormalized from `variant.seller` — the variant the customer actually chose, falling back to `variant.product.seller` for a product whose seller owns the whole listing (Decision 11). Denormalization is load-bearing, not an optimization: the split, seller ability scoping, and seller order lists all key on it, and on a shared product the *product* cannot answer which seller was bought from. Because ownership *can* change while an item sits in a cart, `Carts::Complete` revalidates each line's `seller_id` before partitioning and refreshes stale lines (re-running package/delivery validation) — the same cart-revalidation class as price or availability drift.
- **Per-seller delivery selection happens at checkout, before the split.** Today's Enterprise checkout already groups packages by seller and lets the customer pick a delivery method per seller package (user docs: multi-vendor-checkout); 6.0 keeps that UX. The cart's packages come from `6.0-order-routing.md` (`for_allocation` — seller items allocate from that seller's stock location), delivery options per package come from `6.0-delivery-rate-provider.md` filtered to the package's seller: a `DeliveryMethod` with `seller_id` is offered only on that seller's packages; `seller_id: nil` methods are marketplace-wide. The chosen method + rate travel with the package into that seller's child order at split. **This is a hard requirement on the cart/order-split checkout design** (see Constraints).
- **Move semantics:** line items, their tax lines / discounts / fees (`6.0-6.1-split-adjustments.md`), fulfillment items, and fulfillments are assigned to the correct child `Order` (created from the cart partition); the owner FK on every typed line is rewritten to the child order. **Order-level `Fee` rows** (both adjustable FKs nil — e.g. a payment surcharge; allowed per split-adjustments 2026-07-27) prorate across child orders by item totals using the same largest-remainder rule as order-level discount distribution, their tax lines following the fee. Stock location per child comes from the routing strategy, not a bare `detect`.
- **Group status:** derived, not a column. The `OrderGroup` is "fully fulfilled" when all its orders are, "partially canceled" when some are, etc. — computed across `order_group.orders`, replacing the legacy `all_shipments`/`splitted?`/`cancel_parent_order` workarounds (which existed only because the legacy parent was itself an `Order`).

**Resolution** (`Spree::Commissions::ResolveRate` service): load enabled `CommissionRate`s for the store in list order (`position ASC`) — the currency gate applies **only to `fixed` rates** (a flat fee must state an amount in the order's currency; a `percentage` is a ratio and always passes, its floor and cap simply not applying outside the currencies they were written in) — and return the first whose rules match the line item: rules grouped by `subject_type`, every present group needs ≥1 match (Decision 4). A rate with no rules is the global default (`CommissionRate#global?`) — and because resolution stops at the first match, one placed above a targeted rate makes it unreachable, which is why the seeded default sits at the bottom and the admin surfaces the flag. `Spree::Seeds::CommissionRates` seeds exactly one such rate, **disabled and at zero**: a marketplace that has not set its terms should charge nothing rather than a number core invented. This also untangles the three legacy meanings of `platform_fee` (store preference / seller column / product override) into one model.

**Calculation** (`Spree::Commissions::CalculateLine` service) — ports the legacy per-item fee calculation, generalized:

```text
item_net   = discounted item amount, ex-VAT     # price − discounts, tax excluded (EU default base)
item_gross = discounted item amount, incl. VAT  # price − discounts, tax included
base       = tax_inclusive ? item_gross_per_unit : item_net_per_unit
per_unit   = kind == 'percentage' ? (base * rate / 100) : amount_for(currency)
amount     = per_unit * quantity                                     # both kinds scale with quantity
amount     = clamp(amount, min_amount_for(currency),
                           max_amount_for(currency))                 # NEW: max cap, per currency
tax_amount = amount * commission_tax_rate / 100                      # Decision 3 — the EU piece
total      = amount + tax_amount
```

The base is **payment-source-agnostic**: store credit / gift cards are how the customer *paid*, not a price component — they never reduce the commission base (consistent with the resolved transfer-basis decision; the legacy implementation subtracted a store-credit share from the base, and that behavior is deliberately dropped). "Net" here means *net of VAT*; discounts are always subtracted first in both bases (the seller's commission is charged on what the customer actually paid for the item — promotions are seller-funded in v1, see Open Questions).

**Commission tax rate source (the contract `CalculateLine` consumes):** precedence is (1) an explicit `commission_tax_rate` override on the `CommissionRate`, else (2) the store's `TaxProvider` asked for the platform-service rate against the **seller's billing address** (commission is a B2B supply to the seller — not the consumer's ship address), else (3) a store-preference default, else 0. Missing/erroring provider lookups fall through to (3) — commission lines are written inside the split transaction and must never block checkout on a tax-service outage.

**Rounding:** every persisted money field rounds **half-up to the currency's minor unit** (2 dp for most currencies, using the currency exponent — matching legacy behavior): `per_unit` after the percentage step, `amount` after quantity × clamp, `tax_amount` after the tax step; `total` is the sum of the two rounded parts, so `Σ CommissionLine` amounts always reconcile with balances and payouts to the cent.

Persist one `CommissionLine` per line item on the child order, inside the split transaction. When the resolved rate has `include_shipping`, run the same calculation against the seller order's delivery amount and persist a fulfillment-scoped `CommissionLine` alongside.

**Settlement sweep (level 2):** the scheduled job runs **per `(seller, currency)` pair** on the seller's `payouts_schedule_interval`: it collects that pair's unsettled transfers, creates one `SellerPayout` with `amount = Σ`, stamps each transfer's `payout_id`, and invokes `provider.pay!`. `system` leaves it `pending` for manual completion; `stripe_connect` settles and a webhook completes it.

**Claim & idempotency contract:** creating the payout and stamping its transfers' `payout_id` happen in **one transaction — that stamp is the claim**; a re-run sweep only ever sees `payout_id IS NULL` transfers, so a batch can never be swept twice. `provider.pay!` must be idempotent, keyed on the payout's prefixed ID (Stripe idempotency key), so a crashed/retried invocation cannot double-pay. Failure paths: `pay!` raising → `payout.fail!` with its transfers **still stamped** — retry means re-invoking `pay!` on the *same* payout (never re-sweeping into a new one); a payout stuck in `processing` past a timeout is surfaced in the operator payouts queue for manual resolution (webhook lost vs. provider-side failure), never auto-recreated.

**The same contract applies to level 1.** One `earning` transfer per seller order — enforced by a partial unique index on `(order_id) WHERE kind = 'earning'` — so a re-fired fulfillment event finds the existing row instead of double-crediting. `provider.transfer!` is idempotent keyed on the transfer's prefixed ID, and the provider `reference` (Stripe transfer id) is unique when present: if `transfer!` succeeded externally but the record never reached `completed` (crash between API call and commit), the retry's idempotency key returns the same external transfer and the recovery path re-syncs `reference` + status rather than creating a second money movement. Ambiguous/timed-out attempts park the record in `processing` for the operator queue, same as payouts.

**OSS settlement statements come free.** The ledger is exportable through the standard `Spree::Export` pipeline — a per-seller CSV of transfers/payouts (sales − commission − commission VAT = net, plus reversals) is just an export of these tables, replacing the legacy `Spree::Reports::SellersPayout` report. What stays Enterprise under "payout reports" is provider *reconciliation* (ledger ⇄ Stripe) and regulatory reporting (DAC7) — not the raw statement.

### Reversals (refunds)

The legacy module writes **reverse commission rows** when items are refunded (per returned item, plus an order-scoped prorated row for whole-order refunds) **and** reverse transfers. 6.0 keeps both, symmetric — but reversals are always **per line** (a whole-order refund reverses each line's commission exactly; the legacy order-level proration and its rounding fuzz are not carried over):
- A refund writes a negative/`reversed` `CommissionLine` (net commission = `sum(commission_lines)`).
- A refund writes a `refund_reversal` `SellerTransfer` linked via `reversed_from` (net earned = `sum(seller_transfers)`). If the original transfer was already settled in a completed payout, the reversal lands in the next payout period (Decision 9).

**The hook point is `Spree::Refund`.** `6.0-returns-exchanges-claims.md` funnels Return, Exchange, and Claim money movement through `Spree::Refund` — so a single subscriber on the refund event covers all three flows: it updates the child order's `PaymentSplit.refunded_amount`, writes the reverse `CommissionLine`s for the refunded items, and writes the reversal `SellerTransfer`.

### Product ownership & approval

- Products carry `seller_id` (nullable — the operator's own first-party products have none). Seller users only see/manage their own (ability tenancy condition).
- **Approval reuses the product status workflow — no new approval model.** Seller-created products default to `draft`; a store preference `seller_products_require_approval` (default `true`) controls whether sellers may activate their own products or an operator must. This covers the seller product-approval workflow competing marketplaces ship, with zero new machinery, and `#13323`'s "merchandise Seller's products" stays intact — the operator retains full edit rights over seller products (naming, taxons, publication to channels).
- Seller bulk product CSV import/export rides the existing `Spree::Import` / `Spree::Export` pipeline (see `5.6-admin-spa-csv-import.md`) with the seller context stamped on created records — no marketplace-specific importer.
- **SKU uniqueness relaxes to per-seller scope.** Two sellers legitimately sell the same manufacturer SKU (the legacy module disables SKU validation outright); 6.0 scopes the uniqueness check by the **variant's** `seller_id` instead of dropping it (Decision 11 — sellers share a product, so scoping by the product's owner would not separate them). Note today's scope is `spree_base_uniqueness_scope`, which is empty: SKUs are unique across the whole installation, not even per store.
- "Shop by seller" curated pages come from a seller-subject `CollectionRule` kind (`6.0-replace-taxons-with-categories.md`), replacing the legacy `Spree::TaxonRules::Seller`.

### Seller notifications

Seller notifications are **event-driven, with OSS mailers included** — split along the existing mailer boundary:

- **Back-office emails to sellers and admins live in core**, next to the existing back-office mailers (`Spree::ExportMailer`, `Spree::ImportMailer`, `Spree::InvitationMailer`, `Spree::ReportMailer`): a `Spree::SellerMailer` ports the legacy set — seller approved/rejected/suspended (to the seller's team), onboarding started/submitted-for-review (to store admins), new seller order, payout completed — wired as subscribers to the lifecycle events below. Seller *invitations* need nothing new: they already ride core's `InvitationMailer` via the `Invitation` rail. Core-resident means seller email works in every installation, regardless of gems.
- **Consumer-facing emails** (e.g. the per-seller shipment tracking emails customers receive) belong to `spree/emails` (rebuilt + modernized in 5.6, optional) — or to the storefront's own email stack via webhooks, for headless setups that own transactional email.

Either way the events are the seam — subscribers/webhooks feed n8n/Slack/custom stacks, including OSS payout automation: `seller_payout.due` → webhook → operator's banking flow → `POST /seller_payouts/:id/complete`.

Events (via `publishes_lifecycle_events` + explicit publishes): `seller.created/updated/approved/rejected/suspended`, `order_group.completed`, per-child `order.placed` (existing), `commission_line.created`, `seller_transfer.completed/reversed`, `seller_payout.due/completed/failed`.

### Store API surface

Mirrors what the legacy v2 storefront already exposed for Enterprise (`/api/v2/storefront/sellers`), rebuilt on v3:

- `GET /api/v3/store/sellers` + `GET /api/v3/store/sellers/:slug` — public profile: `name`, `slug`, `about`, `logo`, `square_logo`, `cover_photo`. Only `approved`, non-holiday sellers. No timestamps, no contact email, no financials (store-serializer rules).
- Product serializers gain a `seller { id, name, slug }` object (nil for first-party products); product listing accepts `q[seller_id_eq]` — that plus the seller profile endpoint is a complete seller storefront page. Seller becomes a search facet through the existing SearchProvider filter registry.
- `POST /api/v3/store/seller_applications` — the self-serve "become a seller" application (name, contact email, message) creating a pending seller + owner invitation for operator review. Rate-limited, no auth required.
- Checkout completion of a cart that split returns the **order group**: `{ order_group: { id, number, orders: [...] } }`; carts that don't split (a single partition — all one seller, or all first-party) keep returning the bare order. Customer account history lists groups with nested per-seller orders + per-order fulfillment tracking (today's "separate tracking per seller" UX).

### Admin API surface

Endpoint list lives in `6.0-admin-api.md` → "Marketplace (new in 6.0)": sellers CRUD + `invite`/`approve`/`reject`/`suspend` (approve also un-suspends, matching the legacy machine), commission rates CRUD (nested `rules: []`, PriceList-style), read-only `commission_lines` + `seller_transfers`, `seller_payouts` + `POST :id/complete` (manual settlement), read-only `order_groups`. API key scopes: `read_sellers`/`write_sellers`, `read_commissions`/`write_commissions`, `read_payouts`/`write_payouts`. This is the **operator's** surface only — seller *users* never call it (Decision 10; the 2026-07-14 "collapse into ability scoping" wording is superseded).

### Seller API surface (new 2026-08-15 — Decision 10)

A third v3 branch, `/api/v3/seller/…`, anchored by `Spree::Api::V3::Seller::BaseController` / `Seller::ResourceController` (mirroring the admin pair; concerns added to one must be added to the other):

- **Auth & context:** `POST /seller/auth/login|refresh|logout`, password reset — `Spree.seller_authentication_strategies`, `seller_api` JWT audience, audience-stamped refresh token + own cookie. `X-Spree-Seller-Id` selects the seller; membership = `role_users` on `resource: seller`; a header naming a seller the caller does not belong to is 403; `Spree::Current.store` is set from `current_seller.store`. `GET /seller/me` — user + seller memberships + `permission_keys` for the selected seller. Invitation acceptance stays on the existing `/admin/invitation_acceptances` (it is store-agnostic and already handles `resource: seller`).
- **Own resources:** `GET/PATCH /seller/profile` (name, about, branding uploads, billing/returns addresses, `payouts_schedule_interval`, ToS acceptance, holiday mode), `GET /seller/onboarding_tasks` + `POST /seller/onboarding/submit_for_review`, `GET /seller/team` + team invitations (`RoleGrantGuard`-bounded to seller-audience roles), `GET /seller/balance`, `GET /seller/transfers`, `GET /seller/payouts` (read-only ledger).
- **Catalog:** products (+ nested variants, prices, media, stock items) — every lookup through `current_seller.products`; create force-stamps `seller_id`; approval state per the store's seller-product preference. No channel publication, no categories/collections/tags management (read-only pickers where a product form needs them, store-scoped read).
- **Orders:** the seller's child orders (`current_seller.orders`), fulfillments with `Fulfillments::Fulfill`/`Cancel`/`UpdateTracking`, returns/claims on those orders. **No** refunds, order edits, approvals, payments — the seller sees its `payment_split`, never the group's `Payment`.
- **Delivery:** the seller's own delivery methods (`seller_id` = self); store-wide methods read-only.
- **Exports/imports:** the seller's own runs on the `Spree::Export`/`Import` pipeline, scoped by `seller_id`.
- **Serializers:** `Spree::Api::V3::Seller::*Serializer < V3::*Serializer` (the store serializer) plus an explicit list of operational fields — never a subclass of the admin serializer, so nothing leaks by inheritance. Own typelizer output and a generated `docs/api-reference/seller.yaml` from `spree/api/spec/integration/spree/api/v3/seller/`.
- **Tripwires:** the branch enters `Spree::StoreScopeGuard`'s coverage, and Phase 1 adds a seller-scope guard on the same pattern (flag store-scoped-but-not-seller-scoped scans on seller-owned tables under `/seller`).
- **Later, not 6.0:** seller-bound secret API keys (Enterprise Shopify/Woo apps acting as the seller) — safe only on this branch, because its base scope is `current_seller`; a store-bound admin key is `can :manage, :all`.
- SDK packaging (a `@spree/seller-sdk` vs a `seller` namespace in the admin SDK) is decided with Phase 4; the API decision does not depend on it.

## Migration Path

This is **new OSS code**, not a rename of existing core — there is no in-place data migration for existing Spree stores (they have no sellers). The "migration" is twofold:

1. **From the Enterprise module to core**, for existing marketplace customers. A one-time backfill rake task (shipped in Enterprise — only Enterprise has legacy data) must:
   - For each legacy `splitted` parent order, create a `Spree::OrderGroup` and attach its `parent_id` children as the group's orders.
   - Migrate the legacy per-item commission rows → `spree_commission_lines`. **Sign convention flips**: the legacy module stores order-level fee totals negative (load-bearing in its payout math); `CommissionLine` amounts are positive, reversals are their own negative/`reversed` rows.
   - Decrypt the legacy encrypted seller contact columns (ActiveRecord encryption — a multi-tenant SaaS choice) into core's plain columns.
   - Migrate the legacy Stripe transfer ledger → `spree_seller_transfers` (the per-order, on-fulfillment level) with `provider: 'stripe_connect'` and the Stripe transfer id in `reference`. The legacy module has no payout *records* (it delegated scheduling to Stripe), so there is nothing to backfill into `spree_seller_payouts` — historical Stripe payouts can optionally be reconstructed from Stripe's API, or simply start fresh from the cutover.
   The Enterprise module then becomes a thin layer on top of core's new models, deleting its splitting + commission + transfer decorators. The basic `Spree::PayoutProvider::StripeConnect` ships in the monorepo with the pulled-in Stripe gateway (2026-07-15 amendment); Enterprise extends it (clawbacks, netting, KYC ops, reconciliation) and keeps Shopify/WooCommerce.

## Constraints on Current Work

Even before this lands, work touching adjacent areas should:

- **Cart/Order split (`6.0-cart-order-split.md`)**: keep `cart.complete!`/`Spree::Carts::Complete` as the single completion entry point — the seller split hooks in there. Do not reintroduce an order-level `after_transition` extension surface; multi-vendor must not depend on one. When fleshing out the checkout flow on Cart, design delivery selection **per package** (packages come from order routing) — the multi-vendor checkout needs one delivery choice per seller package before completion, and payments must be attachable to an `OrderGroup`, not only to an `Order`.
- **Rich text sanitization (`6.0-rich-text-descriptions.md`)**: sellers are the marketplace's lower-trust writers, and today they are protected by the 5.x-only Enterprise gem's `Spree::SanitizeConcern` (`sanitize :description, :meta_description, if: -> { seller_id.present? }`). That gem does not carry into 6.0 — this plan rewrites its functionality as core models — so **core must own the sanitization before seller-authored content lands here**. Core's `SanitizableRichText` (shipped 5.6.2) sanitizes on write rather than deriving `sanitized_*` on read, which is the stronger form. Three obligations for this plan: (1) apply it to every seller-writable rich text field (`Seller#about`, seller-authored product descriptions); (2) keep seller-facing write paths — the seller dashboard, seller CSV/feed imports, bulk maintenance jobs — on save-backed writers, since the concern is a `before_save` and does not cover `update_columns`/`update_all`/raw SQL (anything that must bypass callbacks calls `Spree::RichTextSanitizer.sanitize` explicitly); (3) do **not** ship a 6.0 allowlist weaker than the Enterprise scrubber sellers have on 5.x — that one prunes `script`/`style` element bodies entirely.

Do **not** add a commission/marketplace `Fee` kind — commission is `Spree::CommissionLine`, off-order (Decision 2); `Fee` stays buyer-facing.
- **Inventory operations (`6.0-inventory-operations.md`)**: the procurement model is `Spree::Supplier` — never reuse `Spree::Seller` (reserved for marketplace sellers) for purchase-order sources. See `decisions.md` 2026-07-14.

Seller-branch controllers scope-fetch through `current_seller` and never subclass admin controllers.

Do **not** put the fund ledger in a payment-gateway namespace (the legacy gateway-namespaced-transfer mistake) nor collapse transfer and payout into one model — `Spree::SellerTransfer` (on-fulfillment) and `Spree::SellerPayout` (scheduled) are both core and provider-agnostic.

## Resolved Decisions

- **The split adopts the paid order rather than replacing it, and moves rows rather than copying them** (RESOLVED 2026-08-20, shipped). Completion builds one draft order holding the whole basket so it can be paid as one; the split then makes that order the group's first child and hands the other partitions' rows to new siblings. The alternative — build N fresh orders and destroy the original — was written first and rejected on two counts: the original is the record the payment was taken against and the row carrying the unique `cart_id` that makes completion replayable, so destroying it orphans money and breaks resumption. Rows **move** (`update_all` on the owner FK) rather than being re-copied from the cart, because everything was costed once inside the completion lock and re-deriving would ask the pricing and tax engines a question already answered — possibly getting a different one. The group takes the order's number so the customer keeps the reference they saw at checkout, and children suffix off it (`R1001-1`), following the same reads-its-parent shape as fulfillment and payment numbers.
- **Splitting a parcel between sellers divides everything hanging off it** (RESOLVED 2026-08-20, shipped). A fulfillment holding two sellers' goods becomes two, and the cost the customer was quoted is apportioned between them by the value each half carries (largest-remainder), never copied onto both. The first implementation cloned the fulfillment wholesale and charged delivery twice — the group totalled more than the customer paid, caught by a totals spec rather than by review. The honest reading is that one quote for one parcel no longer describes two; a marketplace wanting each seller quoted separately gets that by giving sellers their own delivery methods, which packs their goods separately from the start and leaves nothing to divide. **Three things divide with it**, each missed on the first pass because a divided parcel is the only case where a row's owner keeps its id while its contents change: the parcel's own tax lines, discounts and fees (re-pointing by `fulfillment_id` finds nothing for the clone, so the source kept tax on a charge it no longer bore and the sibling shipped untaxed), the **selected delivery rate** (a fulfillment restates its cost from its rate whenever amounts refresh, so leaving the rate whole quietly restored the full charge on both halves the next time anything touched them), and the **stock reservations** on the moving line items (scoped by `order_id` at release, so one child would have released everyone's and each sibling none).
- **Per-seller commission needed no commission-engine change** (RESOLVED 2026-08-20, verified). Each child order publishes its own `order.placed`, which `OrderCommissionSubscriber` already answers, and `Commissions::CommissionOrder` already partitions by `line_item.seller_id` and skips nil-seller lines — so the seller children are commissioned and the first-party child correctly is not, with no marketplace branch anywhere in the engine. This is the payoff of the Phase 2 decision to key commission on the line item's own seller snapshot rather than on the order.
- **A promotion is redeemed by a checkout, not by an order** (RESOLVED 2026-08-21, shipped). `Promotion#credits_count` counted distinct `order_id`s carrying its discount rows, so a split checkout — which leaves a row on every child — spent a `usage_limit` two or three times over on one customer's single redemption, and a promotion capped at 100 uses ran out early for everyone. Counting now collapses on `COALESCE(orders.order_group_id, orders.id)`, so a group's children are one use between them and an ungrouped order is itself; `adjusted_credits_count` and `used_by?` exclude the asking order's **whole group** rather than just the order, via `Order#sibling_order_ids` (`[id]` when ungrouped). Coupon codes and the one-use-per-customer rule were checked and need nothing — a code's `used` flag lives on the code, and `used_by?` answers a boolean. The adjacent lesson: anything counting "how many times has this been used" must ask what a *use* is, because the split turned one of them into several without changing any of those call sites.
- **A single-seller checkout stamps its order with the seller** (RESOLVED 2026-08-21, shipped). The split gate returns early on one partition, which was right about not making a group and wrong about doing nothing: the line items carried `seller_id` (so commission worked) while `orders.seller_id` stayed null — and that column is what `Seller#orders` and the seller branch's `current_seller.orders` read, so a seller's own order list would have been empty for every basket bought only from them. The single-partition path now stamps the order before returning.
- **The seller is asked about through a concern, so the container stays neutral** (RESOLVED 2026-08-20, shipped). `OrderGroup#sellers`, `#seller_count` and `#includes_first_party?` live in `Spree::Marketplace::OrderGroup`, included into the model rather than written on it, and `PaymentSplit` carries no seller reader at all (its order answers). Decision 8 says the group is a domain-neutral primitive whose other three planned consumers — split-by-location, split-by-availability, B2B split-by-company-location — have no seller, and "first party" means nothing to any of them. The readers are genuinely useful to a marketplace operator and the admin serializer renders them; keeping them in a concern is what lets both be true. Worth doing on the boundary rather than later, since the moment those fields ship they are client-visible API.
- **The split must say "re-sum, don't regenerate" explicitly** (RESOLVED 2026-08-20, shipped). `Carts::RecalculateTotals` takes `resum_only:`, and the split passes it. The freeze was previously inferred from `completed?`, which is `completed_at.present?` — and the children are still **drafts** when they are re-summed, so the guard did not fire: the promotion adjuster deleted the discounts just moved onto each child and re-tested one seller's subset against a threshold the whole basket met, and the tax provider deleted the moved tax lines and re-derived them from today's rates. The service's own docstring claimed it was avoiding exactly this. A lifecycle predicate was the wrong instrument for an intent the caller knows and the record does not; the parameter states it. Pinned by a spec asserting an order-level £6 promotion survives the split intact (£3 per child, group total equal to what was charged) — the failure was silent and money-visible, and only a totals assertion catches it.
- **A shared payment is bounded, re-allocated and refunded per child — never voided wholesale** (RESOLVED 2026-08-20, shipped). Four consequences of one payment covering several orders, each of which fails silently in a different direction: a partial capture forks the payment (`split_uncaptured_amount`), so the remainder must **carry the uncaptured shares with it** or the sellers who have not shipped point at an authorization that no longer holds their money; `Orders::Cancel` on a grouped child **refunds that child's captured share** instead of voiding the payment, since voiding would release the siblings' authorization and un-pay sellers still shipping; `Payment#owner` being an `OrderGroup` means `gateway_options` asks it for `ship_total`/`additional_tax_total`/`discount_total`/`last_ip_address`, so the group answers all of them by roll-up (without which **every** post-placement gateway call on a split checkout raised); and every refund now carries `order_id` (stamped from the payment when it can answer, named by the caller when it cannot), which is what lets `Order#refunds` stay one plain association and the admin refunds endpoint keep working.
- **Every post-placement money path needs its own grouped case, and each one fails silently without it** (RESOLVED 2026-08-21, shipped). The split itself was well covered while the paths that run *after* it were not, and that is where the defects clustered — six of them, none raising at checkout. Dispatch capture claims the share **before** the gateway, inside its lock (claiming after meant a partial capture forked the payment while the share still read uncaptured, carried the full amount onto the remainder, and let the same order capture twice); `Carts::Complete`'s pre-payment compensation refuses to run once a group exists (its guards read `order.payments`, which a split has moved to the group, so it would have destroyed a paid order); `Orders::Cancel` honours `refund_payments` on the grouped path exactly as on the plain one (it had refunded unconditionally, so an operator cancelling with the default got a live gateway refund they never asked for) and reads what the order was paid from its shares; `Refunds::Create` bounds a refund by the named order's share, so refunding one seller cannot spend a sibling's captured money; `payment.paid` publishes `order.paid` per settled child, since a grouped payment has no single order and the event is public webhook API (**this one did not actually work until 2026-08-21** — see the shared-payment entry above: it read a captured figure that the subscriber had not yet written); `split_uncaptured_amount` uses a bang, since a silent failure would leave the group holding more money than was charged; and `Refund#update_order` re-sums the order the refund names rather than the payment's (nil on a shared payment, so every refund on a split checkout raised). Two of these were found only by *writing the specs* — the grouped dispatch and grouped refund batteries each failed on their first run against code that had already passed review. **The lesson for Phase 3a:** a ledger built on captured shares must be specced against dispatch, refund and cancellation of a *grouped* order, not only against the split, and the bound on what one order may take must count the rows rather than trust a figure a subscriber updates after the fact.
- **A share records what it reserved separately from what the gateway took** (RESOLVED 2026-08-21, shipped). `spree_payment_splits.claimed_amount` beside `captured_amount`: a parcel reserves what it is about to draw *before* charging, so two parcels cannot reach for the same money, and that reservation becomes captured only once the charge lands. `undrawn_amount` (authorized − captured − claimed) is what a parcel may take, and `capture_in_flight?` is a plain read of the row. Cancellation refuses to settle a share mid-charge, reporting it for manual resolution rather than releasing an authorization about to be drawn or refunding money nobody took. **Two earlier attempts got this wrong, and both are the reason the column exists.** Overloading `captured_amount` for the claim meant `carry_splits_to` — which runs *during* the capture — saw the claim as taken and carried the full share onto the remainder payment, paying that order twice. Inferring the in-flight state from the payment failed twice over: `payment.captured_amount` sums capture *events*, which a checkout-captured payment never writes (so every ordinary order looked mid-capture), and `payment.completed?` is set by whichever sibling captured first, so a second seller's genuine in-flight claim looked settled and was refunded. **The rule for Phase 3a:** the split row is the only thing that knows the difference between reserved and confirmed — a transfer or payout sweep must read `captured_amount`, never `authorized_amount` minus arithmetic, and never ask the shared payment.
- **A shared payment breaks every reader that assumed one payment means one order** (RESOLVED 2026-08-21, shipped). A review pass over the split found thirteen such readers, each verified against the code before being believed, and every one real. The instructive ones: **`order.paid` never fired for a split checkout** — it publishes from the payment's own `after_commit`, which runs *before* `payment.completed` reaches the subscriber that marks the shares captured, so the figure it read was always zero (an earlier note in this plan asserted the opposite ordering and was wrong; the trace is what settled it). Public webhook API, silently dead for marketplace orders. **Several payments each re-divided the whole basket and each rounded**, so three children owed 33.33/33.33/33.34 were credited 33.34/33.32/33.34 — the group's sum correct and two children's wrong; payments now draw down what is left. **A parcel whose halves are both worth nothing kept the full delivery charge on each**, the same double-charge fixed earlier surviving in the zero-weight path. And a grouped child's `payment_total` was summed from payments it does not own, persisting nothing paid. The pattern worth carrying into Phase 3a: **anything that reaches an order through `payment.order`, or a total through `order.payments`, is wrong on a grouped order** — and none of these failed loudly.
- **A grouped child order's money is read from its payment splits, not its payments** (RESOLVED 2026-08-20, shipped). Such an order owns no payments — the customer paid once, against the group — so `Orders::UpdateStatuses` reads captured/authorised/refunded from `payment_splits`, capture-on-dispatch draws from the group's payments **bounded by that child's remaining share** (without the bound the first seller to ship captures the whole basket), and `spree_refunds.order_id` names which child a refund puts right so `PaymentSplitRefundSubscriber` can recompute that share alone. `Refund#order` falls back to the payment and `Order#refunds` resolves either shape, so nothing outside a split checkout changes. This is the concrete argument for storing shares rather than computing proportions on read: once one seller has shipped and been captured while another has not, no proportion of the group's totals describes either.
- **The shared catalog ships as variant attributes plus one selection service** (RESOLVED 2026-08-16, shipped — Decision 11's Phase 1b). `spree_variants.seller_id` and `spree_variants.delivery_profile_id`, both nullable, and **two modes that never mix**: on an *owned* product (`products.seller_id` set) every variant is that seller's and ships as the product does — no other seller can create a variant there, so the variant's own columns carry no meaning and are kept blank by a normalizer; on a *master* product (`products.seller_id` nil, the shared catalog) each seller's row names its own seller and how it ships, falling back to the master's profile. The resolved answer is a plain read on the model (`resolved_seller`, `resolved_delivery_profile` — product's if owned, else the row's; no memo, no inheritance chain), and the API carries **one field each** (`seller_id`, `delivery_profile_id`), read resolved and written to the column, so a storefront never learns which mode it is in and a read-then-write round trip on an owned product changes nothing (the write is a no-op there). This deliberately departs from `Variant#tax_category`'s override-the-reader shape, and supersedes an earlier cut that modelled the seller as an inheritance-with-override and grew a second `own_*` name on the API to keep the round-trip safe — the domain has no override to model, so it needed neither. `Variant#digital?` moved onto the variant's own profile with it, which is what lets a download and its printed edition sit on one product. Condition is an `OptionType` shipped as **sample data, not a seed** (`db/sample_data/options.rb`, beside color; values new/refurbished/used): nothing in core keys on the word — the buy box groups by whatever option values it is given — so it is a merchant's choice, not an install prerequisite, and a store that sells only new goods never finds it on a fresh install, so it splits a product the way any axis does and the buy box keys on the option combination — a new buy box and a used one, at no extra cost. **The buy box is `Spree::Products::SelectBuyBox`** behind `Spree.product_buy_box_service`: computed on every read and never stored (it turns on price, stock and who is selling today, none of which hold still), ranking first-party ahead of sellers then cheapest, refusing to feature a seller who is suspended, onboarding or away, and still naming a variant when nothing is buyable so the page has a price to render. `purchasable?`/`in_stock?`/`backorderable?` now answer through the winner rather than `variants.any?` — a product is not purchasable because a suspended seller happens to hold stock — and `default_variant` prefers a first-party listing, since the headline price, SKU and the Omnibus `prior_price` are compliance claims about the operator's own pricing. **SKU uniqueness is scoped to the resolved seller** via a hand-written validation rather than a `scope:` option, because Rails' uniqueness validator reads the raw column and would have merged two sellers who each own a whole product into the nil scope. Cross-store binding is refused on the model (`seller`/`delivery_profile` must belong to the product's store), matching the pair already on Product. **Three pre-existing faults were fixed with it, each with a regression spec proven against the old code:** `Product#variants=`'s full-replacement delete was left as-is on the operator's path — the operator writes every seller's variants on a master — and the guard against a seller wiping a rival's rows lives at the seller branch, not the model (see "Writes never destroy another seller's variants" above), `Stock::Splitter::DeliveryProfile` and `Stock::Coordinator` re-keyed their memoisation off `product_id`, and `with_option_value_ids` now requires **one variant** to satisfy every axis (a `HAVING COUNT(DISTINCT option_type_id)` over one grouped subquery) instead of asking the product about each axis separately — "Blue AND XL" had matched a product selling a blue small beside a red XL, a live storefront bug independent of marketplaces. **Both search providers were fixed together**, since a filter's meaning is part of the provider contract and fixing one would have made results change when an operator installs the search gem: the Meilisearch document is per product, so its option values are a union across variants that cannot answer a per-variant question — the presenter now also emits `option_value_combination_ids` (one token per *combination* of values seen on the same variant) and a multi-axis filter asks for a whole combination, with single-axis filters and the disjunctive-facet queries unchanged. Whole combinations rather than pairs, because every pair holding on *some* variant is not the same as one variant holding them all — three variants (blue, XL, used), (blue, S, new) and (red, XL, new) satisfy each pair of "blue AND XL AND new" while none carries all three. Token count is exponential in the axis count, so it is capped (`MAX_COMBINATION_AXES`) and filters naming more axes fall back to the pairwise approximation. **The upgrade needs a reindex** — existing documents lack the field, so a multi-axis filter matches nothing until then; `search_reindex` is in the 5.6→6.0 manifest for exactly this and is a no-op on the database provider.

The admin surface follows the delivery-method rules editor: `GET /commission_rates/rule_types` for discovery, one row per condition, a picker where the kind names records and its preference schema otherwise.
- **Commission rule matching → every rule must hold (AND), a rule naming several records means any of them (OR)** (RESOLVED 2026-07-14, restated 2026-08-17 for the typed shape). Expresses plain lists and the seller × category pairings today's Enterprise sells, with no `match_policy` knob; same semantics as the leading surveyed OSS engine, but precedence stays the operator's own ordering rather than implicit specificity. See Decision 4.
- **Commission on delivery revenue → `include_shipping` on the rate** (RESOLVED 2026-07-14). Per-rate flag, default off (legacy was items-only); a fulfillment-scoped `CommissionLine` (nullable `fulfillment_id`, exactly-one-of with `line_item_id`). Matches the surveyed OSS competitor (global-only there) and Amazon referral-fee behavior. See Decision 4.
- **Split payment record → `Spree::PaymentSplit` + `payments.order_group_id`** (RESOLVED 2026-07-14). One gateway payment on the group, one split row per child order; no cloned `Payment` rows. See Decision 5 + Design Details.
- **Seller teams → reuse `Role`/`RoleUser`/`Invitation` with `resource: seller`** (RESOLVED 2026-07-14). The polymorphic rails already exist in core (Invitation's docstring names Seller); no `SellerUser` model. See Seller identity & teams.
- **Parent representation → dedicated `Spree::OrderGroup`** (RESOLVED 2026-06-16). See Decision 8 + Design Details. Diverges from the legacy `parent_id`/`splitted` shape; requires the Enterprise backfill.
- **Commission tax rate source → per-`CommissionRate` field, resolved through the `TaxProvider`** (RESOLVED 2026-06-16). Not a per-seller `platform_fee_tax_rate` column (legacy) and not a bare per-market lookup. The rate carries its own commission-tax configuration with a sensible store default; the actual rate is resolved via `6.0-tax-provider.md` so it stays jurisdiction-correct. See Decision 3.
- **Fund ledger → two levels: `Spree::SellerTransfer` (per-order, on-fulfillment) + `Spree::SellerPayout` (per-interval settlement), both generic in core + pluggable `PayoutProvider` (system no-op in core; basic StripeConnect with the monorepo Stripe gateway per the 2026-07-15 amendment, extended by Enterprise with the money operations)** (RESOLVED 2026-06-25). See Decision 9. Transfer credits the seller balance on fulfillment; payout sweeps unsettled transfers into a scheduled bank settlement (transfers `belong_to` their payout — auditable). `seller.balance(currency) = Σ completed transfers − Σ completed payouts` per currency. Splits the legacy gateway-namespaced transfer ledger (which conflated the two and outsourced settlement to Stripe) into core ledger + provider execution along the OSS/Enterprise seam.
- **Commission tax → one scalar on the line, in TaxLine's vocabulary** (RESOLVED 2026-08-17). `tax_amount` + `tax_rate` + `taxability_reason` + the seller's `country_code`/`state_code` on `Spree::CommissionLine`, with `Spree::CommissionTax` as the value object the resolver returns. Reusing `Spree::TaxLine` itself was rejected: its rows sum into the order total and are exposed on the buyer-facing `/orders/:id/tax_lines`, so a commission row there would overcharge the shopper and leak settlement data. Same shape, opposite side of the ledger — so the words are shared and the rows are not. See Decision 3.
- **Commission VAT base → net item price, VAT added on top of the fee** (RESOLVED 2026-06-25). For EU, commission is computed on the seller's **net (ex-VAT)** item price; the commission `tax_amount` (Decision 3) is then applied **on top of the commission** as a separate B2B service supply — the marketplace fee is a distinct taxable event from the consumer's item sale, so the two VATs never mix. The base toggle stays available for non-EU/edge merchants who genuinely want a gross base, but the EU default is net-base + fee-VAT. Shipped as **`tax_inclusive`** (2026-08-17), matching `Spree::Market#tax_inclusive` rather than the surveyed industry's `include_tax` — the flag says the commission base is tax-inclusive, which is the same adjective the rest of Spree already uses for a price that carries its tax. This makes the marketplace's commission invoice to the seller stand on its own (correct for EU invoicing + remittance).
- **Store-credit/gift-card payout → payment-source-agnostic** (RESOLVED 2026-06-25). The `SellerTransfer` amount (which rolls up into the payout) is `(seller's sale value) − (commission owed)`, **independent of how the customer paid**. Store credit / gift cards are the platform's funding concern, not the seller's — the seller is owed their full cut of the sale regardless. This **drops the legacy store-credit dual-basis** from the amount calculation; that branch existed only to reconcile the old store-credit funding model and does not belong in the payout basis. (The platform still tracks its own store-credit liability separately — that's orthogonal to what the seller receives.)
- **Commission precedence → an operator-ordered list** (RESOLVED 2026-06-25 as integer priority; **reshaped 2026-08-17 to `acts_as_list`, shipped**). `CommissionRate` carries `position` (`acts_as_list scope: :store_id, add_new_at: :top`) and resolution walks it top-down, first match wins (Decision 4). The list on screen is the precedence, so reordering is dragging rather than assigning numbers; new rates land at the top so they take effect on creation instead of behind the catch-all. `Spree::Seeds::CommissionRates` puts one disabled marketplace-wide rate at the bottom, which yields the product > category > seller order merchants asked for without hardcoding a ladder. No specificity inference — a rate can name all three dimensions at once, so there is nothing to infer from.
- **Commission rate currency → required for fixed, ignored for percentage** (RESOLVED 2026-06-25). A `kind: 'fixed'` rate **must** carry a `currency` (a flat "2" is meaningless without one); a `kind: 'percentage'` rate ignores currency (10% applies in any currency). Enforced by a model validation: `validates :currency, presence: true, if: -> { kind == 'fixed' }`. See the `CommissionRate` model.
- **Payout vs transfer trigger → transfer on-fulfillment, payout on-interval** (RESOLVED 2026-06-25). These are the two distinct events of Decision 9: a `SellerTransfer` becomes due **on-fulfillment** (the seller earned it); a `SellerPayout` settles on the seller's **scheduled interval** (`payouts_schedule_interval`). The earlier "on-ship vs on-deliver vs scheduled" framing was a category error — it conflated the two. Core's `system` provider honors `manual` settlement natively; Enterprise implements daily/weekly/biweekly/monthly.

## Open Questions

1. **Seller-funded vs platform-funded promotions.** v1: discounts reduce the seller's sale value (seller-funded). Platform-funded promos ("we run a 10% site-wide sale and make sellers whole") need a funding flag on Promotion and a compensating ledger line — **post-6.0**. Unblocked by: a merchant asking for platform-funded campaigns once the ledger is live; the shape is a `funded_by` on Promotion + a positive `SellerTransfer` compensating row.
2. **Seller-scoped promotions** (a seller creates promotions limited to its own products) — **post-6.0** (resolved 2026-08-15 as deferred). Shape when it lands: `spree_promotions.seller_id` (nullable), a `/api/v3/seller/promotions` endpoint on the seller branch, and a rule guard that a seller promotion only matches line items with the same `seller_id`. Cheap on the single-store Promotion model; unblocked by the 6.0 headline scope shipping first.
