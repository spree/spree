# Order timeline

**Status:** In Progress — the activity log, the actor on events, the Admin API and SDK, the dashboard Timeline and docs are built on `feature/v-3855-order-timeline`; awaiting review
**Target:** Spree 6.1
**Depends on:** 6.1-order-change-substrate.md (order changes, including `confirmed_by`, `canceled_by`, `previous_total` and `new_total`), 6.0-action-actors.md (`acted_by`, `current_actor`, the actor serializer), 6.0-typed-webhook-events.md (the event catalog the timeline listens to)

**Tracking:** Linear V-3855 · GitHub spree/spree#15345

## Summary

A merchant opening a placed order cannot see what happened to it. The order
page shows the order as it is now, and an Order changes card lists edits, but
nothing says when the payment was authorized and captured, who refunded what,
when a fulfillment shipped, or which return restocked an item. Shopify and
Medusa both answer this with a timeline: every step of the order, newest
first, each naming who did it, with staff comments in between. Spree publishes
an event for almost every one of those steps but keeps none of them. This plan
records them: an append-only activity log per order, written from the events
the order's records already publish, an Admin API resource to read it and post
comments, and a Timeline section on the order page that replaces the Order
changes card. Only orders placed after release get a timeline; nothing is
backfilled.

## Key Decisions (do not deviate without discussion)

- **Recorded as it happens, never rebuilt from the order's records
  (2026-11-27).** The records an order keeps cannot rebuild its history:
  events are not stored, a payment keeps only its current status and
  `updated_at`, and there is no table for comments. A row is written when the
  step happens and never changed afterwards.
- **No backfill (2026-11-27).** Only orders placed after the release have a
  timeline. An older order shows one line saying history is recorded from the
  release date. A backfill could only guess from timestamps, and a guessed
  history is worse than none.
- **Entries point to order changes; they never copy their actions
  (2026-11-27).** An order change stays the full record of an edit. Its entry
  holds the order change id, and the timeline expands the change's actions
  when it reads them. A confirmed change cannot be edited, so what the entry
  shows never drifts.
- **One step, one entry (2026-11-27).** Where two events describe the same
  step, the timeline records one:
  - A change requested and confirmed in the same call (the dashboard's Save,
    a discount on a placed order) is one "changed the order" entry. A change
    that waits for confirmation gets a requested entry and, later, a
    confirmed or canceled one.
  - A change made by a return, exchange or claim is not an entry of its own.
    It is nested under that record's entry ("Return RET1002 received", with
    the restock under it).
  - A manual discount on a placed order comes only from its order change. No
    separate discount entry.
  - A refund comes from `payment.refunded`, `refund.requested` or
    `refund.failed`, never `refund.created`, which fires before the gateway
    answers and would record refunds it declined.
- **Personal data is referenced, never copied (2026-11-27).** An entry names
  its actor through `acted_by` columns and the customer through the order. It
  never stores an email, a name or an address, so anonymizing a customer
  leaves nothing behind in the timeline.
- **The actor travels on the event (2026-11-27).** The Admin and Seller APIs set
  `Spree::Current.actor` to `current_actor` for each request, and
  every event copies it into its metadata when it is published, as `actor_id` (the
  prefixed id) and `actor_type` (the actor kind, `admin_user` or `api_key`).
  The subscriber reads it from there, and webhook consumers, who receive the
  metadata, learn who acted too. This covers every step,
  including payment captures and fulfillments, which have no actor column.
  Reading `acted_by` columns from each record was rejected because thirteen
  of the records the timeline covers have none yet, and writing entries from
  each workflow because it would touch every workflow and every extension's
  step. Accepted trade-off: work done in a background job has no actor unless
  the job sets `Spree::Current.actor` itself, so such entries name no one
  until it does.
- **Entries are written inline after commit (2026-11-27).** The subscriber is
  registered with `async: false`, so an entry exists by the time the request
  that made it returns and the dashboard's refetch shows it. A background job
  would often leave the entry missing until the next refresh. Accepted
  trade-off: one insert is added to each recorded step's request.
- **Comments can be deleted by their author, never edited (2026-11-27).** The
  timeline stays a faithful record, and a comment posted on the wrong order
  can still be removed. Fixing a typo means deleting and posting again.
- **An order-only table (2026-11-27).** `spree_order_activities` has a concrete
  `order_id`, so scoping and permissions follow the order, and the codebase's
  rule against polymorphic subjects holds. A customer or product timeline
  later gets its own table; a general activity log was rejected as design
  work for timelines nobody has asked for.

## Design Details

### Model

```ruby
create_table :spree_order_activities do |t|
  t.references :order, null: false, index: false
  t.string :kind, null: false                # 'payment.completed', 'comment', …
  t.string :category, null: false            # what the timeline groups and filters by
  t.references :actor, polymorphic: true     # acted_by — staff, API key, nil
  t.references :order_change                 # set for order change entries
  t.text :body                               # comments only
  t.jsonb :details                           # small snapshot, see below
  t.datetime :created_at, null: false
end
add_index :spree_order_activities, [:order_id, :created_at]
```

```ruby
module Spree
  class OrderActivity < Spree.base_class
    has_prefix_id :ordact
    include Spree::ActedBy

    belongs_to :order, class_name: 'Spree::Order', inverse_of: :activities
    belongs_to :order_change, class_name: 'Spree::OrderChange', optional: true
    acted_by :actor

    validates :kind, presence: true
    validates :body, presence: true, if: -> { kind == 'comment' }
  end
end
```

- There is no `updated_at`: rows are never changed. A comment can be deleted
  by the staff member who wrote it; that is the only write after insert.
- `details` holds what the entry shows and could not read later: the amount
  and currency, the payment method's brand and last four digits, the
  transaction id, the fulfillment or return number, the tracking number, and
  the prefixed id of the record it describes. Amounts are strings in the
  order's currency, never floats.
- `Spree::Order has_many :activities, dependent: :destroy`. Rows live as long
  as their order.

### What is recorded

A registry maps an event name to a builder that turns the event into an
entry, or into nothing. The built-in entries:

| Event | Entry |
| --- | --- |
| `order.placed` | Order placed, with the total |
| `payment.completed`, `payment.capture_failed` | Captured, or the capture failed, with the method, amount and transaction id. `payment.captured` always accompanies `payment.completed`, so only the completion is recorded; a payment authorized at checkout has no entry of its own until it is captured |
| `payment.voided`, `payment.void_failed` | Voided, or the void failed |
| `payment.refunded`, `refund.requested`, `refund.failed` | Refunded once the gateway answers (`payment.refunded` names the refund in its metadata), waiting on the gateway, or declined; with the amount, reason and the refund's own transaction id. `refund.created` fires before the gateway is asked, so it is not recorded |
| `fulfillment.fulfilled`, `fulfillment.delivered`, `fulfillment.canceled` | Shipped with the carrier and tracking number, delivered, canceled |
| `order_change.requested`, `order_change.confirmed`, `order_change.canceled` | The change, under the one-step rule above |
| `return.requested`, `return.received`, `return.refunded`, `return.canceled` | The return, with a received return's restock nested |
| `exchange.requested`, `exchange.received`, `exchange.fulfilled`, `exchange.canceled` | The exchange, with its restock or replacements nested |
| `claim.opened`, `claim.resolved`, `claim.denied`, `claim.canceled` | The claim, with its replacements nested |
| `order.approved`, `order.canceled` | Approved or canceled |

Store credit is not recorded on its own: credit issued for an order comes from a refund, return or claim, which already has an entry. It gets a kind when a consumer needs one.

An extension adds its own events to the registry:

```ruby
Spree.order_activity_kinds.register('loyalty.points_awarded') do |event|
  order = Spree::Order.find_by_prefix_id(event.payload['order_id'])
  next unless order

  { order: order, details: { points: event.payload['points'] } }
end
```

### Writing entries

One subscriber listens to every registered event name, with `async: false`,
and writes the row its builder returns. Events are published after the step's
transaction commits, so a step that rolls back leaves no entry. A failure to
write an entry is rescued, reported to the error handler, and never fails the
step.

The actor comes from the event's metadata:

```ruby
# Spree::Api::V3::Admin::BaseController
around_action { |_, action| Spree::Current.set(actor: current_actor) { action.call } }

# Spree::Events::Adapters::Base#build_event
metadata: Spree::Event.actor_metadata.merge(metadata)   # actor_id, actor_type

# Spree::OrderActivitySubscriber — resolves through Spree.actor_classes
actor = event.actor   # nil when none, or the row is gone
```

Webhook deliveries send the event's metadata, so both values are the public
forms the API already uses for actors: a prefixed id and an actor kind, never
a class name or a raw id.

The one-step rules are applied when the row is written:

- On `order_change.requested`, nothing is written when the change has already
  been confirmed by the time the subscriber runs: Save requests and confirms
  in one transaction, and both events are published after it commits.
- On any `order_change.*` event, nothing is written when the change belongs
  to a return, exchange or claim. That record's `received`, `fulfilled` or
  `resolved` event names the change it made in its metadata
  (`order_change_id`), and the record's entry links to it.
- `order_change.canceled` for a set that was never submitted writes nothing.

### Admin API

```
GET    /api/v3/admin/orders/{order_id}/activities        list, newest first
POST   /api/v3/admin/orders/{order_id}/activities        { body } adds a comment
DELETE /api/v3/admin/orders/{order_id}/activities/{id}   the author removes their comment
```

- Filters: `kind` and `category` (order, payments, fulfillment, changes,
  returns, comments; an extension adds its own). Paginated like every list.
- `expand=actor` and `expand=order_change.actions.variant`.
- Reading needs the `read` permission on orders; commenting needs `update`.
  No new permission subject.
- Serialized as `{ id, kind, actor_id, actor_type, actor?, order_change_id,
  order_change?, body, details, created_at }`.

### Dashboard

- A **Timeline** section at the bottom of the order page replaces the Order
  changes card.
- A comment box sits at the top. Entries are grouped by day on a vertical line,
  each with an icon for its group, one sentence, the actor and the time.
- An entry with more to show opens up: an order change lists its actions with
  the wording the Order changes card uses today, a payment shows its
  transaction id.
- An order change that is still requested is shown as a notice at the top of
  the section with Apply and Discard. Its requested entry stays in the history
  below, since someone did request it.
- How each kind is shown comes from a registry in `dashboard-core`, so a
  plugin can show its own kinds. An unknown kind still gets a plain entry.
- An order placed before the release shows "History is recorded from
  <date>".

## Migration Path

1. Migration, model, `Spree::Order has_many :activities`, factory.
2. The kind registry, the built-in builders and the subscriber, with the
   one-step rules. Specs per built-in kind, including a rolled-back step and a
   preview leaving no entry.
3. The Admin API resource, comments, OpenAPI from the integration specs, SDK
   types and the `orders.activities` client.
4. The dashboard Timeline section and the kind registry in `dashboard-core`.
   The Order changes card and its hook are removed. Translations in every
   locale, a Playwright spec for placing, paying, editing, commenting and a
   return.
5. Docs: the merchant guide's order page, the developer page on events, and
   an extension example registering a kind.

## Constraints on Current Work

- A new step a merchant should see on an order publishes an event, and the
  event's record carries its actor through `acted_by`. A step that only
  writes a row cannot reach the timeline.
- An event that reaches the timeline must not carry personal data the
  timeline would copy. Builders read names through the order and the actor.
- Order change workflows keep publishing their events after commit. The
  one-step rule for Save depends on it.
- A background job that performs a step on behalf of a staff member or an API
  key wraps its work in `Spree::Current.set(actor: …)`. Without it the
  timeline entry names no one.
- Event metadata keys `actor_id` and `actor_type` are reserved for the actor.
  They hold its prefixed id and actor kind, because webhook deliveries send
  the metadata.

## Open Questions

None. Emails sent for an order are not recorded: no event says an email was
sent. Recording them waits on `spree_emails` publishing one.
