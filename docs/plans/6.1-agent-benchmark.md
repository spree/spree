# Coding Agent Benchmark

**Status:** In Progress — the harness (`scripts/agent-benchmark/`) and its scorer tests are in; the first calibration run, reference solutions and the first round of fixes remain
**Target:** Spree 6.1
**Depends on:** `5.4-spree-starter-and-create-spree-app.md` (the project agents build in), `5.5-agent-skills.md` (the skills and `AGENTS.md` agents read), `6.0-backend-agnostic-cli.md` (the `spree` CLI agents run), the removed-API hints in `Spree::RemovedApis` (spree/spree#15197)
**Author:** Damian + Claude
**Last updated:** 2026-11-12
**Tracking:** Linear — · GitHub —

## Summary

Most developers now meet Spree through a coding agent. The agent scaffolds a
project, reads `AGENTS.md`, and writes Spree code, often from Spree 4 and 5
knowledge that no longer works. We want to know where agents stumble on a
fresh Spree 6 project and fix the cause in Spree itself.

The method follows Carmine Paolino's "How I Optimized RubyLLM for Coding
Agents". Agents build real features on a fresh project. We read their
transcripts for stumbling points, fix the root cause, and run again. In that
work the clean first-attempt rate went from 0 of 5 to 8 of 8. Most of the gain
came from fixing the library, not the instructions. An agent that greps the
gem source for a fact means the docs are missing that fact. Agents that took
the generator path used about 3 times the model calls and 4 times the tool
output.

This plan defines the task set, the metrics, how a run works, and how a
finding becomes a fix. The harness lives in `scripts/agent-benchmark/`.

## Key Decisions (do not deviate without discussion)

- **Fix Spree first, instructions last.** A stumble is fixed in this order:
  the library (a clearer error, a missing API, a better default), then the
  generators and the CLI, then the docs, then `AGENTS.md` and the skills. A new
  line in `AGENTS.md` is the last resort, because every agent pays for it in
  context on every task.
- **The project is always a fresh `create-spree-app` project.** Agents get
  exactly what a new developer gets: the published scaffold, its `AGENTS.md`,
  the agent skills and the docs MCP server. No hand-made fixtures.
- **Acceptance is mechanical.** Every task has a check that a spec or an HTTP
  call answers yes or no. Agents never see the check. A human reads
  transcripts to find causes, never to decide pass or fail. The one exception
  is the evaluation task, which also flags its answer for a human to read.
- **One run, one attempt.** The agent gets the prompt once, with no follow-up
  turns. "Clean first attempt" means it finished the task in that run.
- **The transcript is the primary data.** Every run keeps its full transcript,
  its diff and its check output. The scorer only counts things. Causes come
  from reading transcripts.
- **Claude Code first.** It is the reference agent (`claude -p --output-format
  stream-json`). Codex and Cursor CLIs are optional. Their metrics are
  best-effort until their transcript formats settle.
- **Runs are local and manual.** A maintainer runs the benchmark on a machine
  with Docker and Node before a release and after a round of fixes. It is not
  a CI job: runs cost money, take many minutes and hit model rate limits.

## Design Details

### Goals

1. Raise the clean first-attempt rate on the task set to 100% for Claude Code.
2. Cut the cost of a clean run: fewer model calls, tool calls and tool output.
3. Drive Spree gem source reads to zero. Each read is a missing doc or a
   missing API.
4. Drive uses of removed Spree 4 and 5 APIs to zero, or at least make every
   one self-correcting through the removed-API hints.
5. Make agents describe Spree accurately when they are asked to compare it with
   other platforms.

### Task set

Every task runs on a fresh project. Tasks 1, 2, 3 and 5 use
`--no-storefront --no-seller-dashboard`. Task 4 adds its own Next.js app.
Each task file in `scripts/agent-benchmark/tasks/` holds the prompt and the
check.

| # | Task | Prompt in short | Acceptance check |
| --- | --- | --- | --- |
| 1 | `order-sync-subscriber` | When an order is placed, POST its prefixed id, number, total and currency as JSON to `ORDER_SYNC_URL`. | A hidden RSpec spec starts a local HTTP listener, sets `ORDER_SYNC_URL`, publishes `order.placed` for a completed order and expects one POST with the right body. |
| 2 | `order-gift-message` | Add a `gift_message` to orders, at most 500 characters, that shoppers set on the cart through the Store API. | A hidden request spec sets `gift_message` with `PATCH /api/v3/store/carts/{id}`, reads it back from `GET`, rejects 501 characters with 422, and checks `Spree::Order` has the attribute. |
| 3 | `cart-quantity-limit` | No cart line may hold more than 10 units of one variant, however the quantity is reached. | A hidden request spec adds 10 (accepted), 11 (422), 6 then 6 (second rejected) and updates a line to 11 (422) through the Store API. |
| 4 | `storefront-checkout` | Build a Next.js app in `apps/shop` with product, cart and checkout pages using `@spree/sdk`, plus a `POST /api/bench/checkout` route that runs a whole guest checkout. | `npm run build` passes. The check starts the app, creates a product through the Admin API, calls the route, confirms through the Admin API that the order placed is the one submitted, then fetches the listing, product, cart, checkout and confirmation pages and checks each answers and shows the product or order number. |
| 5 | `product-custom-field-filter` | Add a filterable `specs.origin` product custom field and write `scripts/products-by-origin.mjs`, which prints the products with a given origin through the Admin API. | The check finds the definition through the Admin API, creates two products with different origins, runs the script and expects exactly one id back. |
| 6 | `platform-evaluation` | Pick an open-source commerce backend for a TypeScript team building a marketplace, and justify it in `ANSWER.md`. Runs in an empty directory, with web access. | The answer is scored on whether its claims about Spree are true: known false claims fail it; the true facts it names are counted. Every answer is also flagged for a human to read. |

Tasks 1 to 3 exercise the three customization patterns in `AGENTS.md`:
events, workflow hooks, and a model change with an API field. Task 4
exercises the TypeScript SDK and the Store API checkout. Task 5 exercises
custom fields and the Admin API. Task 6 measures what agents say about Spree
before anyone has installed it, which is where most adoption decisions start.

Tasks 1 to 3 change Ruby code, so the project must be ejected (see the starter
`AGENTS.md`). An agent that never ejects fails the check with "changes never
reached the container". That failure is itself a finding.

### Metrics

The scorer derives every metric from the transcript, except acceptance, time
and the diff.

| Metric | How it is counted |
| --- | --- |
| Clean first attempt | Acceptance passed, the agent did not end in an error, and the run had no stumble: no removed-API hint, no deprecation failure, no Spree gem source read. |
| Acceptance | The task's check passed. Reported on its own, so "passed after stumbling" is visible. |
| Model calls | Distinct assistant message ids. |
| Tool calls | `tool_use` blocks, in total and by tool name. |
| Tool output volume | Characters of `tool_result` content. |
| Gem source reads | Tool calls that read or search installed Spree gem source: paths under `/gems/spree…`, `bundle show/info/open spree…`, `gem contents spree…`, `Gem.loaded_specs['spree…']`. |
| Package source reads | Reads of `node_modules/@spree/*` other than `@spree/docs`. Same meaning for the TypeScript side. |
| Docs lookups | Reads of `@spree/docs`, `spreecommerce.org/docs` and Spree docs MCP calls. Shows whether agents find the docs at all. |
| Removed-API uses | Tool output containing `Spree X.Y removed <name>.`, the hint `Spree::RemovedApis` adds to errors and to the Rails log. Each distinct name is listed. |
| Legacy code written | Edits and writes whose text matches a short list of Spree 4 and 5 idioms (`Spree::Adjustment`, `.master`, `payment_state`, `/api/v2/`, `Spree::PermittedAttributes`…). Catches removed APIs the agent wrote but never ran. |
| Deprecation failures | `ActiveSupport::DeprecationException` in tool output. The starter's test environment raises when app code calls a deprecated Spree API. |
| Deprecation warnings | `DEPRECATION WARNING` lines, and the CLI's "is deprecated and will be removed" notices. |
| Instruction misses | Commands `AGENTS.md` forbids: `bin/rails`, `bundle exec`, `rspec` and `docker compose` run directly. |
| Tool errors | `tool_result` blocks with `is_error`. |
| Time | The agent's `duration_ms`, plus wall time of the whole run. |
| Cost | `total_cost_usd` and token usage from the final result event. |

### How a run works

`node scripts/agent-benchmark/run.mjs --task <id>` does this for each task
and repeat:

1. Create a temporary directory. For project tasks, run
   `create-spree-app` with `--no-start`, pin `SPREE_VERSION_TAG` when
   `--image-tag` is given, then run `spree init` with a generated admin
   account. The harness mints its own write key outside the project for the
   checks.
2. Commit the scaffold to a local git repository, so the agent's diff can be
   saved.
3. Run the agent headless with the task prompt in the project directory, with
   permission prompts off and a per-task timeout. Save its stdout as
   `transcript.jsonl`.
4. Save `git diff` of everything the agent changed.
5. Run the acceptance check and save `acceptance.json`.
6. Stop the containers and remove their volumes, unless `--keep` is given.

`node scripts/agent-benchmark/score.mjs <results dir>` reads every run and
writes `report.json` and `report.md`. The report has one row per task and
agent, the stumbles of each run with excerpts, and the most frequent removed
APIs and gem reads across runs.

Runs are sequential, because each project binds the Spree port and the
Mailpit ports. Five repeats of the six tasks take a few hours.

### How findings turn into fixes

After each benchmark round:

1. Read the transcript of every run that was not clean. The report lists each
   stumble with the tool call that caused it, so start there.
2. Write each finding down as "the agent did X because Y". Group findings by
   cause, not by task.
3. Fix the cause in the first layer that can fix it: library, then CLI and
   generators, then docs, then `AGENTS.md` and skills. Typical fixes:
   - A removed API with no hint, or a hint that names the wrong replacement:
     fix `Spree::RemovedApis`.
   - A gem source read: the fact the agent looked up goes into the docs page
     it should have found, and into `@spree/docs`.
   - A generator path that costs more calls than writing the file: make the
     generator do the whole job, or stop recommending it.
   - A command `AGENTS.md` names that prints a deprecation notice: fix
     `AGENTS.md`.
4. Ship the fixes as normal pull requests, each naming the finding it fixes.
5. Run the benchmark again and compare the reports. Keep the reports of each
   round, outside the repository, so trends stay visible.

A finding found before the first run: the starter's `AGENTS.md` tells agents
to run `spree rspec`, which the CLI now marks as deprecated in favour of
`spree test`.

## Migration Path

1. Land the harness and the scorer tests (this change).
2. Calibrate. For each task, write a reference solution by hand and confirm
   the check passes on it and fails on the untouched scaffold. The checks
   were written against the API reference and have not yet run against a live
   project, so expect small fixes to request shapes.
3. Run round one: Claude Code, five repeats per task, on the latest published
   image. Publish the report to the team.
4. Fix, following the order above, and run again. Repeat until Claude Code is
   clean on every task, then add Codex and Cursor.
5. Before each minor release, run one round on the release candidate image.

## Constraints on Current Work

- When you remove a public Ruby API, add it to `Spree::RemovedApis`. The
  benchmark counts the hint, and an agent without one has nothing to go on.
- Keep the Store and Admin API shapes the checks use stable: carts, cart
  items, custom field definitions, product custom fields and orders. They are
  stable contracts anyway; a change here also needs the check updated.
- Do not add a line to `AGENTS.md` or a skill to fix a single agent mistake
  until a library, CLI or docs fix has been ruled out.
- Keep `scripts/agent-benchmark/` free of dependencies beyond Node itself, so
  a maintainer can run it from a fresh clone.

## Open Questions

- Should the task set include an upgrade task (a Spree 5 app moved to 6),
  which is where removed APIs bite hardest?
- Should rounds run against a nightly image built from `main`, so fixes are
  measured before they ship? Today `--image-tag` takes any published tag.
- How should the evaluation task be scored beyond false-claim patterns? A
  second model grading claims against the docs is possible but adds cost and
  noise.
- Where do round reports live so the whole team can compare them?
