# TypeScript Subscribers

**Status:** Draft — design finalized, nothing built
**Target:** Spree 6.1 (developer preview); stable in 6.2
**Depends on:** `6.1-spree-base-image.md` (Node in the production image, the build script), `6.0-typed-webhook-events.md` (the typed event envelope), `5.6-solid-queue-single-container.md` (one app container)
**Author:** Damian Legawiec (design driven with Claude)
**Last updated:** 2026-11-13
**Tracking:** Linear — · GitHub spree/spree#15213

## Summary

A project created with `create-spree-app` can react to Spree events only by writing Ruby. This plan adds `apps/subscribers`: a folder of TypeScript files, one per subscriber, that run when an event is published — sync an order to an ERP, post to a chat channel, tag a customer — without touching the Rails app. Spree writes each event to a small queue table; a Node worker in the same container reads the table, runs the matching handlers, and writes back through the Admin API. It is deliberately a bridge: a limited, after-the-fact way to react in TypeScript until a later Spree major runs subscribers inside the server. The subscriber files a developer writes are the part meant to survive that change.

## Key Decisions (do not deviate without discussion)

- **A bridge, not a platform (2026-11-13).** In 6.x, TypeScript subscribers only react to events. None of the following is added: synchronous calls that let TypeScript block or change an action, several apps with their own keys and permissions, apps hosted outside the container with an install step, dashboard extensions loaded from apps. Each is a reasonable next step and together they are the app-platform complexity this plan exists to avoid. Blocking logic in TypeScript waits for the major where it is an in-process function.
- **Handlers run in a separate Node process (2026-11-13).** A Ruby server cannot run TypeScript in-process. Accepted cost: a handler reaches Spree only through the Admin API, one network call per read or write.
- **The transport is a dedicated queue table read directly from Postgres (2026-11-13).** Pulling over the Admin API was rejected: its claim and acknowledge operations would become public API that a later major must carry, and a long-poll would hold one of Puma's three default threads. Reusing `spree_webhook_deliveries` was rejected: that table is shaped for HTTP, and its rule that disables an endpoint after consecutive failures would switch off every TypeScript subscriber when one has a bug. Accepted costs: TypeScript subscribers need Postgres (MySQL installations use Ruby subscribers), and failed events have no dashboard view at first.
- **This is a queue for one consumer, not an event log.** No cursors, no replay, no history. A row is deleted when its handlers succeed.
- **Rows cannot pile up.** Three rules together: the worker deletes a row on success; a recurring sweeper deletes rows older than the retention period, whatever their state; and Spree writes rows only when TypeScript subscribers are switched on.
- **The Ruby subscriber that writes the queue runs as a background job**, like the existing webhook subscriber. Its job row commits with the data change and a failed insert is retried. Accepted cost: one extra hop before a handler runs.
- **A worker handles one row at a time, and exits when a handler overruns (2026-11-13).** Claiming a batch was rejected: rows waiting behind slow handlers would outlive their claim and be run twice. Stopping only the slow handler was rejected: JavaScript has no way to stop a running function from outside, and a handler that merely stops being awaited keeps running while its row is retried. Exiting the worker ends the overrunning handler for certain, and the supervisor starts a new one. The worker exits still holding its claim, so the row is retried only after the claim expires. Accepted cost: throughput is one event at a time per worker, and an overrunning handler costs a worker restart. A handler that blocks the worker completely is not covered: the worker cannot exit, so it is not restarted (see Open Questions). More workers, not batches, are the way to go faster.
- **The whole event is retried, not each handler (2026-11-13).** Tracking which handlers already succeeded was considered and left out. Handlers must be safe to run twice, including twice at the same time.
- **A loop guard is part of the first version (2026-11-13).** Events caused by the worker's own Admin API calls are not queued. Without it a handler on `order.updated` that updates the order fills the table in seconds. Accepted cost: one TypeScript subscriber can never react to another's write.
- **Events that carry credentials, and events declared `webhook: false`, never reach TypeScript.** The same rule that keeps them out of the webhook delivery log. Password-reset emails therefore stay in Ruby.
- **A handler receives the event and an `admin` client, and nothing else (2026-11-13).** No database handle. Exposing one would turn the Rails table layout into a public contract.
- **New package `@spree/subscribers`; `@spree/core` stays browser-safe (2026-11-13).** `@spree/core` is the vocabulary both sides share (enums, money, filters, event names) and never gains server code or runtime dependencies. Server code gets its own package. No general server package is created in 6.x to hold one table; that would fix its name and shape before the next major is designed.
- **Drizzle is used, privately.** The runner declares the queue table with Drizzle so the layout is written once in TypeScript. It is not exported and not passed to handlers.
- **The worker uses the database settings Rails uses (2026-11-13).** `DATABASE_URL` in production; `DATABASE_HOST`, `DATABASE_USERNAME`, `DATABASE_PORT` and `DATABASE_NAME` in development, with the defaults of the starter's `database.yml`. No override variable.
- **Production ships one JavaScript file (2026-11-13).** No `node_modules` and no package manager in the image. A dependency that cannot be bundled (native code, runtime asset files) fails the build with a clear message; shipping a pruned `node_modules` is a later addition if people hit it.
- **Puma starts and supervises the worker**, the same way it runs Solid Queue, with a `bin/subscribers` command to run it as its own service.
- **The folder is `apps/subscribers`.** It matches the Ruby term and promises only what the feature does.
- **Ships in 6.1 as a developer preview, stable in 6.2 (2026-11-13).** Chosen over waiting for 6.2 so the announcement lands with 6.1. What the preview promises: the subscriber file shape — `defineSubscriber`, the event envelope, the `admin` field. What may change before 6.2: defaults, the `spree-subscribers` command, the queue table. Accepted cost: a preview label on the feature the announcement is about, and it cannot be finished until the base image is published in the same release.
- **Subscribers are found by folder (2026-11-13).** Every file in `src/subscribers/` is loaded; adding a subscriber is adding a file. It is the convention the dashboard already uses for routes. An explicit list was rejected because a subscriber someone forgets to list never runs and gives no error. Accepted cost: a little hidden behaviour — the build generates the list of files.
- **The scaffolder creates the worker's secret key (2026-11-13).** `create-spree-app` and `spree add subscribers` create a key marked as the subscribers key and write it to `.env`, so the example works on first run and the loop guard is set up correctly. Accepted cost: a full-access secret key sits in `.env` by default. A key scoped during setup was rejected for the first version: one more prompt, and handlers fail later on a scope nobody granted.
- **Commitments carried into the next major (2026-11-13).** A subscriber file written for 6.x runs unchanged when subscribers move inside the server:
  1. An in-process subscriber receives the same full event envelope, not a bare id. Accepted cost: the server serializes the record for every subscriber, even one that needs only the id.
  2. `defineSubscriber` and the `admin` context field keep working, and new context fields are only added.
  3. Subscribers stay asynchronous and after-commit. Blocking logic gets its own API rather than changing what a subscriber is.

## Design Details

### What a developer writes

```ts
// apps/subscribers/src/subscribers/order-placed.ts
import { defineSubscriber } from '@spree/subscribers'

export default defineSubscriber('order.placed', async (event, { admin }) => {
  await notifyErp(event.data)
  await admin.orders.update(event.data.id, { metadata: { erp_synced: true } })
})
```

- `event` is the typed envelope `@spree/sdk/webhooks` ships: `id`, `name`, `created_at`, `data`, `metadata`. `data` is the record in its Store API shape.
- `admin` is an `@spree/admin-sdk` client signed in with a secret key.
- A subscriber is a plain object with a `handler` function, so a test calls it with a fake event and a fake client — no database, no running Spree.

### The scaffolded app

```
apps/subscribers/
├── package.json        # scripts: dev, build, typecheck, test; one dependency
├── tsconfig.json
├── AGENTS.md
├── src/subscribers/order-placed.ts
└── tests/order-placed.test.ts
```

No entry file, no database code, no configuration file. The runner loads every file in `src/subscribers/` whose default export is a subscriber; the build generates that list, and a file without one fails the build rather than being skipped. Settings come from the project's `.env`.

The template's source is a thin `packages/subscribers-starter` in this monorepo, shipped inside `@spree/cli` like the dashboard starter. `create-spree-app` offers it during setup and `spree add subscribers` adds it later.

### Packages

| Part | Contents | Promise |
| --- | --- | --- |
| `@spree/subscribers` (main entry) | `defineSubscriber` and its types | Stable — the part meant to survive |
| Runner (internal to the package) | Database connection, Drizzle table definition, claim and retry loop, shutdown handling | Private — removed when subscribers run in-process |
| `spree-subscribers` command | `dev`, `build`, `start` | Used by `spree dev`, the image build and Puma |

The package versions together with the Spree gems, because the runner must match the queue table's layout. On start the runner checks a schema version and stops with a clear message when it does not match.

The Ruby half lives in `spree_core`: the migration, the model, the subscriber that writes rows, the sweeper job and the Puma plugin.

### The queue table

`spree_subscriber_events`:

| Column | Purpose |
| --- | --- |
| `id` | Primary key |
| `event_id` | The event's id, unique — an event is queued once |
| `event_name` | For matching handlers |
| `store_id` | The store the event belongs to |
| `payload` | The envelope a webhook would carry |
| `attempts` | How many attempts have started, counted when a worker claims the row |
| `locked_at` | When a worker claimed it |
| `lock_token` | A random id for that claim, so only the worker that holds it can finish or release the row |
| `next_attempt_at` | When a failed row may be tried again |
| `last_error` | The last failure, for diagnosis |
| `created_at` | For the sweeper |

### From event to handler

1. Rails publishes an event, as today. Every existing Ruby subscriber runs unchanged.
2. `Spree::SubscriberEventWriter` (a Ruby subscriber on `*`, run as a job) inserts a row, unless:
   - TypeScript subscribers are switched off (`SPREE_SUBSCRIBERS_ENABLED`, which the scaffolder sets);
   - the event carries a credential or is declared `webhook: false`;
   - the event was caused by the worker's own Admin API call (the loop guard).
3. The worker polls about once a second. It claims one row that is due — `next_attempt_at` is empty or past, `attempts` is below the limit, and `locked_at` is empty or older than the claim timeout — with `FOR UPDATE SKIP LOCKED`, so several workers never take the same row. Claiming stamps `locked_at` and a fresh `lock_token`, and adds one to `attempts`. The attempt is counted here, when it starts, so an attempt that crashes the worker still counts. The worker claims the next row only when this one is finished, so a claim never waits behind another row's handlers.
4. It runs every handler registered for the event name. A row with no handler is deleted.
5. On success it deletes the row. On failure it records the error, sets `next_attempt_at` to a growing delay from now and releases the row by clearing `locked_at`. The delay is stored on the row, so every worker honours it and it survives a restart. Both writes apply only while the row's `lock_token` is still this worker's: a worker that lost its claim changes nothing.
6. After the last attempt the row is never claimed again: the claim in step 3 skips it. It stays, with its last error, until the sweeper removes it.

A claim expires: a row whose `locked_at` is older than the claim timeout is offered again, under a new `lock_token`. This covers a worker that crashed mid-handler, and is why a handler can run twice. The handler timeout covers all the handlers of one row and is shorter than the claim timeout. JavaScript cannot stop a running handler from outside, so when the timeout passes the worker records the error on the row, keeps its claim and exits; Puma starts a fresh worker. The error write gets a few seconds: the worker exits whether or not it has finished, so a slow database cannot keep the worker alive past its claim. The row is not released: it becomes due only when its claim expires, which is later than the handler timeout, so by then the process that ran the old handler is gone — unless the handler has blocked the worker, which the next paragraph covers. Because a worker handles one row at a time, nothing else is lost by the restart. Claims are not renewed.

This is not a hard guarantee. The timeout is checked inside the worker, so a handler that blocks the worker completely — a long synchronous loop — keeps the check from running, and the worker can outlive its claim. Another worker then retries the row while the first handler is still running. Handlers must therefore be safe to run twice at the same time, not only one after the other. The guide says so.

A blocked worker also stops working. It cannot exit, and Puma restarts a worker only when it exits, so it stays blocked until the handler returns or the container restarts. With one replica, no TypeScript subscriber runs in that time: rows wait in the queue, and the sweeper deletes the ones that pass the retention period. With several replicas, the retries of that row can block one worker each, up to the attempt limit of five. Ruby subscribers, webhooks and the store itself are not affected. Closing both gaps needs something outside the handler's thread to end it; see Open Questions.

### The loop guard

The scaffolder creates the worker's secret key, marked as the subscribers key, and writes it to `.env` as `SPREE_SUBSCRIBERS_API_KEY`. An event published while handling a request signed in with that key carries the mark in its metadata, and the writer skips it. The mark comes from the key, never from a header a client could send.

It covers events published during the request. An event published later by a job that the request enqueued is not marked; that is accepted for the first version.

### Relation to Ruby subscribers

- TypeScript subscribers add behaviour. They cannot replace, reorder or stop a Ruby subscriber.
- Ruby subscribers that run inline during the publish (for `order.placed`: `OrderPlacedSubscriber`, `OrderCommissionSubscriber`) have always finished before a TypeScript handler starts. Those that run as jobs (product metrics, emails) run in parallel with it, in no fixed order.
- The payload is a snapshot from publish time. A handler that needs current state reads it through `admin`.
- When Ruby code turns event publishing off for a bulk operation, no rows are written.
- An event declared by a Ruby extension reaches a handler, but its payload type is unknown; generated types cover Spree's own events.

### Where the worker runs

- **Development:** `spree dev` starts it on the host with file watching, as it starts the dashboard dev server, and passes it the database address. The quick-start compose file publishes Postgres on loopback, as the development compose file already does.
- **Production:** `spree-image-build app` type-checks `apps/subscribers`, bundles it with the runner into `/rails/subscribers/index.mjs` plus a source map, and writes nothing when the project has no `apps/subscribers`. Puma starts `node /rails/subscribers/index.mjs` when the file exists, restarts it if it exits and stops it on shutdown. `bin/subscribers` runs it as its own service.
- On a stop signal the worker finishes the handler in flight and releases its claims.
- Several replicas each run a worker.

### Defaults

| Setting | Default |
| --- | --- |
| Attempts before giving up | 5 |
| Claim timeout | 5 minutes |
| Handler timeout | 4 minutes |
| Sweeper retention | 7 days |
| Poll interval | 1 second |

The sweeper is a recurring job. Recurring jobs are listed in each project's own `config/recurring.yml`, so new projects get the entry from the scaffold and existing projects need it added.

## Migration Path

1. **Ruby side in `spree_core`:** the migration and model for `spree_subscriber_events`, the writer subscriber with its three skip rules, the sweeper job, the mark on the subscribers key. RSpec for each.
2. **`@spree/subscribers`:** the authoring entry, the runner (connection, claim, retry, shutdown, schema-version check) and the `spree-subscribers` command. Vitest for the runner against a real Postgres.
3. **`packages/subscribers-starter`** with the example subscriber and its test, shipped in `@spree/cli`.
4. **CLI and scaffolder:** `spree add subscribers`, the `create-spree-app` prompt, `spree dev` co-running the worker, the sweeper entry in the scaffolded `config/recurring.yml`, `SPREE_SUBSCRIBERS_ENABLED` and the key in `.env`.
5. **Image:** the bundling step in `spree-image-build`, the Puma plugin, `bin/subscribers`. Depends on the base image being published.
6. **Existing projects:** `spree upgrade` adds the sweeper entry to `config/recurring.yml`; the upgrade guide says the same.
7. **One end-to-end check** in the starter pipeline: place an order, see the example subscriber's write land.
8. **Docs:** a "TypeScript subscribers" guide, including what they cannot do and that handlers must be safe to repeat. The guide and the scaffolded `AGENTS.md` mark the feature as a developer preview and say which parts are promised.
9. **6.2:** remove the preview label once defaults, the command and the table layout have held through 6.1.

## Constraints on Current Work

- `@spree/core` stays browser-safe: no server code, no HTTP, no runtime dependencies. Server-side TypeScript goes in its own package.
- Do not add Admin API operations for the subscribers worker. Anything in the Admin API must be carried into the next major; the worker talks to the queue table directly.
- Do not export Drizzle, the table definition or a database handle from `@spree/subscribers`, and do not add one to the handler context.
- Do not add a way for TypeScript to block or change an in-flight action in 6.x.
- A new event that carries a credential must be declared as one in the event catalog, or it will be queued for TypeScript.
- A change to `spree_subscriber_events` is a change to a contract shared with the npm package: bump the schema version and release both together.

## Open Questions

None block the work. Three items are deferred:

- **A dashboard view of failed events.** Until it exists, failures show in the worker's log and in the queue table. It is worth building once the preview shows how often handlers fail; it does not change the design.
- **Ending a handler that blocks the worker.** The worker's own timeout cannot end a handler that never gives control back, so that handler can overlap with its own retry and leaves its worker stalled; with one replica, TypeScript subscribers stop until the container restarts. Two ways to end it from outside:
  - *A heartbeat to the supervisor.* The worker signals every few seconds, and the Puma plugin (and `bin/subscribers`) kills and restarts a worker that has been silent for longer than the gap between the handler timeout and the claim timeout. A blocked worker is then gone before its claim expires, which closes both gaps. Cost: a handler that computes for longer than that without a pause is killed too.
  - *A separate thread for handlers.* The worker's main thread stops the handler thread at the timeout. Cost: every handler call crosses a thread boundary, and the `admin` client has to be created inside that thread.

  The choice is left for when the runner is built, where both costs can be measured. One of them must be in place before the stable release in 6.2; the 6.1 preview may ship without, with the limit stated in the guide.
- **Scoped keys for the worker.** Left out of the first version. It becomes worth doing if projects ask to limit what subscribers may write; the key is already a separate, marked key, so scoping it later changes nothing else.
