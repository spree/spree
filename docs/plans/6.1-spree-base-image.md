# Spree Base Image

**Status:** In Progress — the image definition, build script, publishing workflow, CLI changes and docs are built; the `spree/spree-starter` switch is its own pull request and waits for the first published base image
**Target:** Spree 6.1
**Depends on:** `5.6-project-layout-and-dashboard.md` (the project layout and the Dockerfile this replaces), `5.6-solid-queue-single-container.md` (one app container)
**Author:** Damian Legawiec (design driven with Claude)
**Last updated:** 2026-11-13
**Tracking:** Linear V-3818 · GitHub spree/spree#15211

## Summary

Every Spree project builds its production image from a 200-line Dockerfile copied from `spree/spree-starter`. Each project owns that copy, so it drifts from upstream, and every operating system, Ruby or Node security fix has to be applied by each project by hand. This plan publishes a Spree base image — one runtime image and one build variant, both holding Ruby, Node and the system libraries Spree needs, and no gems — and moves the build logic out of the Dockerfile into a script shipped inside the build variant. A project's Dockerfile shrinks to about ten lines that start `FROM` the base. Spree then patches the runtime once and projects pick it up by rebuilding. The definition lives in this monorepo and is the single source for the stock `ghcr.io/spree/spree` image, self-built project images, and images built by a hosted Spree cloud, so a project moves between self-hosting and the cloud without changing how it is built.

## Key Decisions (do not deviate without discussion)

- **No gems in the base image (2026-11-13).** The base holds the runtime only. Pre-installed Spree gems would tie the base to an exact Spree patch release and force a rebuild on every gem release. Accepted cost: every project build compiles its native gems, as it does today.
- **The definition lives in the monorepo and replaces the spree-starter Dockerfile (2026-11-13).** `spree/spree-starter` keeps only the thin project Dockerfile. The base image, the build script and the workflows that publish them are in `spree/spree`.
- **Two images from one definition.** A runtime image, and a build variant that adds compilers, pnpm and the build script. Compilers never reach production.
- **Node is always in the runtime image.** It removes any "is there TypeScript in this project" branching from the image, and gives `apps/subscribers` (planned separately) and later TypeScript pieces a runtime without another image change. Accepted cost: projects with no TypeScript code carry an unused Node binary.
- **Build logic is image content, not Dockerfile content.** Layout detection, the stock-or-custom dashboard choice and the gem and asset steps move into a script in the build variant. A fix to the build then reaches projects through the image.
- **The image contract is small and is meant to outlive the Ruby runtime.** It is: where the built app lives, the build script's commands, the port, the health check, and the entrypoint's behaviour. A project's Dockerfile depends on nothing else, so a later Spree major can change what is inside the base without changing that Dockerfile.
- **The stock image is built from the base, and is still published from `spree/spree-starter` (2026-11-13).** `ghcr.io/spree/spree` becomes "the base plus the stock server and stock dashboards". The starter keeps publishing it on its version tags, now from the thin Dockerfile, and gains a weekly rebuild. The monorepo workflow builds a stock image only to health-check a new base and never pushes it. Publishing both images from the monorepo was rejected: it needs the monorepo to hold write access to the `ghcr.io/spree/spree` package, and it changes the release order. Accepted cost: two workflows in two repositories.
- **The 6.1 base carries Node 24 (2026-11-13).** It is supported until April 2028, so it outlives the line. Node 22, which the repository builds with today, reaches end of life in April 2027 and would force a Node major bump under a floating tag. Accepted cost: the image build is the first place the dashboards are built with Node 24.
- **The switch in `spree/spree-starter` is a second pull request (2026-11-13).** It cannot pass until the base image is published from `main`, so it merges after this one.
- **Target is Spree 6.1 (2026-11-13).** Chosen over 6.2 so the TypeScript subscribers plan, which depends on this image, can follow without waiting a release. Accepted cost: little time to prove the image before 6.1 ships, so the runtime check (Migration Path step 1) comes first and the contract stays as small as listed here.
- **Scaffolded Dockerfiles use the floating line tag (2026-11-13).** `ghcr.io/spree/spree-base:6.1`, so a rebuild picks up security fixes with no action from the project. A pinned tag bumped by Dependabot was rejected: projects that ignore Dependabot would never get fixes, which is the problem this plan exists to solve. Accepted cost: two builds of the same commit can differ, and a bad base rebuild reaches every project at once — so a rebuild is published only after the stock image built on it boots and passes its health check. Dated tags stay available for projects that want to pin.
- **The build is two steps: gems, then app (2026-11-13).** Gems install in their own layer, so a code change does not reinstall and recompile them. A single step was rejected because it only caches with BuildKit cache mounts, which hosted build platforms do not reliably offer. The Dockerfile copies the `Gemfile` from whichever layout is present (`Gemfile*`, `server/Gemfile*`, `backend/Gemfile*`), so one file still serves every layout.
- **An ejected project runs in development on the build variant directly (2026-11-13).** `docker-compose.dev.yml` uses the published build image and mounts the source; the image's entrypoint installs missing gems into a volume before any command runs. There is no local image build and no `dev` stage in the project Dockerfile. Accepted cost: the first start installs gems at run time, and the build variant carries `psql`.
- **Images are published to GHCR only, named in full, and signed (2026-11-13).** Spree does not control the `spree` or `spreecommerce` namespaces on Docker Hub, so there is no Docker Hub mirror. A new third namespace was rejected: nobody guessing an image name would guess it, so it adds a place to look without fixing wrong guesses. Every scaffolded file and doc writes the registry host (`ghcr.io/spree/...`), never a bare image name, because a bare name resolves to Docker Hub. Each published image carries a build provenance attestation, so a project can verify it came from the `spree/spree` publishing workflow. Accepted cost: Spree images do not appear in Docker Hub search, and an image name guessed from memory still resolves to a Docker Hub namespace Spree does not own — today that includes `spreecommerce/spree`, last updated in 2019.
- **The current and the previous Spree minor lines are rebuilt (2026-11-13).** Once 6.2 ships, `6.2` and `6.1` are rebuilt weekly; when 6.3 ships, `6.1` is frozen and its last dated tag stays available. A project gets one full release cycle to upgrade before its base stops being patched. "Current only" was rejected because every project would have to upgrade Spree the day a minor ships to stay patched. Accepted cost: two lines to rebuild, scan and health-check on every run.
- **The base definition is the reference for custom bases.** A project that needs a different base (another distribution, a hardened vendor image) copies `docker/base/` — the Dockerfile and the build script — and owns it. Keeping the old 200-line Dockerfile published alongside was dropped: it would be a second definition to keep correct.

## Design Details

### Images

| Image | Contents | Used for |
| --- | --- | --- |
| `ghcr.io/spree/spree-base:<line>` | Debian slim, Ruby, Node, libvips, jemalloc, curl, the `rails` user (uid 1000), the entrypoint, the production environment variables | Final stage of every production image |
| `ghcr.io/spree/spree-base:<line>-build` | The runtime image plus build-essential, git, libpq-dev, libyaml-dev, pkg-config, zlib1g-dev, npm, pnpm (through corepack), `psql` and `spree-image-build` | Build stage; development container |
| `ghcr.io/spree/spree:<version>` | The base plus the stock server and stock dashboards | Quick start, as today |

`<line>` is the Spree minor line, for example `6.1`. Because the base holds no gems it is not tied to a Spree patch release.

Both architectures published today (`linux/amd64`, `linux/arm64`) stay.

### What the base fixes

The runtime image sets everything the current Dockerfile's final stage sets, so a project's Dockerfile does not repeat it:

- `WORKDIR /rails`, `USER 1000:1000`, `EXPOSE 3000`
- `RAILS_ENV=production`, the Bundler deployment variables, the jemalloc preload
- `SPREE_DASHBOARD_DIST_PATH=/rails/dashboard`, `SPREE_SELLER_PANEL_DIST_PATH=/rails/seller-dashboard`
- `ENTRYPOINT` and the default `CMD`. In production the entrypoint prepares the database when the command is the Rails server. Outside production it installs missing gems first, which is what makes the build variant usable as a development container.

### The build script

`spree-image-build` ships in the build variant. It takes over what the Dockerfile's `ctx`, `dashboard`, `seller-dashboard` and `build` stages do today, in two commands:

- `spree-image-build gems` installs the gems from the `Gemfile` and `Gemfile.lock` in the working directory and precompiles bootsnap for them.
- `spree-image-build app <context>` does the rest:
  - finds the Rails app in the build context (`server/`, the older `backend/`, or the context root);
  - builds `apps/dashboard` and `apps/seller-dashboard` when present, and the stock templates from `@spree/cli` otherwise;
  - precompiles bootsnap for the app and precompiles assets;
  - writes the result to fixed paths: `/rails`, `/rails/dashboard`, `/rails/seller-dashboard`.

It also checks that the project fits the base and fails with a plain message when it does not:

- the Spree version in `Gemfile.lock` is not newer than the base's line (an older project on a newer base builds; a newer project on an older base does not);
- the project's Ruby requirement accepts the base's Ruby.

### A project's Dockerfile

```dockerfile
# syntax=docker/dockerfile:1
ARG SPREE_BASE=ghcr.io/spree/spree-base:6.1

FROM ${SPREE_BASE}-build AS build
COPY --chown=rails:rails Gemfile* .ruby-version* server/Gemfile* server/.ruby-version* backend/Gemfile* backend/.ruby-version* ./
RUN spree-image-build gems
COPY . /src
RUN spree-image-build app /src

FROM ${SPREE_BASE}
COPY --chown=rails:rails --from=build /usr/local/bundle /usr/local/bundle
COPY --chown=rails:rails --from=build /rails /rails
```

One file serves a `create-spree-app` project (build context is the project root) and a bare clone of the starter (context is the Rails app). The canonical copy is `docker/project/Dockerfile` in this repository; the starter's copy and the one the CLI writes are checked against it.

### Development container

An ejected project runs on the build variant, with no local image build:

```yaml
web:
  image: ghcr.io/spree/spree-base:6.1-build
  environment:
    RAILS_ENV: development
    BUNDLE_DEPLOYMENT: "0"
    BUNDLE_WITHOUT: ""
  volumes:
    - ./server:/rails
    - bundle_cache:/usr/local/bundle
  command: ["bin/rails", "server", "-b", "0.0.0.0", "-p", "3000"]
```

The entrypoint installs missing gems into the volume (development and test groups included) before the command, so the server and every one-off command (`spree migrate`, `spree console`) find them. Consequences for the CLI:

- A project counts as ejected when its compose file mounts the source into `/rails`, not only when it has a `build:` section.
- `spree build` (without `--production`) is no longer needed for development. It stays as a command that pulls the newer build image, so existing habits and docs keep working.
- After a `Gemfile` change, a restart is enough; the gems install on start.

### Ruby version

The starter's `Gemfile` reads `ruby file: '.ruby-version'`, which pins an exact patch (`4.0.9`). With a base image the Ruby patch version belongs to the base, so a base rebuild that moves Ruby to the next patch must not break a project build. The starter's `Gemfile` changes to accept any patch of the base's Ruby minor; `.ruby-version` stays for local tooling.

### Publishing and patching

- The base is rebuilt weekly and whenever its definition changes, for the current and the previous Spree minor line. The lines, with the Ruby and Node version and the git ref each is built from, are listed in `docker/base/lines.json`. An older line is frozen: its floating tag stops moving and its last dated tag stays available.
- Each rebuild publishes the floating line tag and an immutable tag stamped with the date and time (for example `6.1-202611160323`), for both variants.
- The stock image is rebuilt in `spree/spree-starter` on every Spree release (as today) and weekly, after the base, so `ghcr.io/spree/spree` also receives security fixes between Spree releases. Today it is built only when a version tag is pushed.
- A rebuild moves the floating tag only after the stock image built on it boots and passes its health check. A failed rebuild leaves the previous image in place.
- Base images are scanned for known vulnerabilities in the publishing workflow.
- Each workflow attaches a build provenance attestation to every image it pushes — both base variants here, the stock image in the starter. The image contract docs show how to verify one.

### CLI and scaffolder

- `spree build --production` recognises the new Dockerfile. It detects the current one by a marker string (`.spree-custom-app`); the check gains the base image reference.
- `create-spree-app` needs no change for the Dockerfile or the compose file: it copies both from the starter. The generated Dependabot configuration keeps leaving Docker out: the floating tag needs no bumping.
- `spree eject` and the commands that prepare the database work with a development compose file that has no `build:` section.
- The `AGENTS.md` files scaffolded into a project (`packages/create-spree-app/src/templates/agents-md.ts` and the one in `spree/spree-starter`) state that Spree images are published only at `ghcr.io/spree` and that nothing on Docker Hub is official.
- `spree upgrade` gains a step that moves an ejected project onto the base image: it replaces a stock Dockerfile with the thin one, swaps the stock `build:` block in the compose files for the build image, and loosens the Ruby pin in the `Gemfile`. A Dockerfile or compose file the project has changed is left alone, with a message.

## Migration Path

1. **Prove the runtime.** Build the base from the official Ruby slim image with Node copied from the official Node image of the same Debian release. Confirm Node runs without extra libraries and measure the size added.
2. **Add the definition, the build script and the publishing workflow** to the monorepo. Publish the base for the 6.1 line, both variants, both architectures.
3. **Rebuild the stock image from the base.** Its tags, contents and behaviour do not change for users. Compare the resulting image with the current one (size, boot, health check, dashboards served).
4. **Replace the Dockerfile in `spree/spree-starter`** with the thin one, switch its development compose file to the build image, loosen the Ruby requirement in its `Gemfile`, and add the weekly rebuild to its release workflow. A separate pull request there, merged after the first base image is published.
5. **Update the CLI and the scaffolder** (`spree build --production` detection, `spree build` and `spree eject` for the development container, the `spree upgrade` step).
6. **Turn on scheduled rebuilds, the health-check gate, scanning and provenance attestations**, and add the base image to `/release` so a new Spree minor publishes its line.
7. **Document it**: deployment guides, the upgrade guide, and the image contract.

Existing projects keep working throughout: their Dockerfile is self-contained and does not reference the base.

## Constraints on Current Work

- Do not add build steps to the spree-starter Dockerfile that could not move into a script. New build logic should be written so it can run as one command.
- A new system package that Spree itself needs at runtime belongs to the base image, not to project Dockerfiles or docs that tell users to `apt-get install`.
- Do not put gems, or anything tied to a Spree patch version, in the base.
- Do not widen the image contract (paths, port, health check, entrypoint behaviour, the two dashboard path variables) without updating this plan. Each addition is something a later Spree major must keep.
- Do not add a `dev` stage or other development-only steps to project Dockerfiles; development tooling goes into the build variant.
- Write Spree image references with the registry host (`ghcr.io/spree/...`) in code, scaffolded files and docs. Never write a bare `spree/...` or `spreecommerce/...` image name, and never point users at Docker Hub for a Spree image.
- Code must not assume Node is absent from the production image, and must not assume it is present before this plan ships.

## Open Questions

None block the work. Two items are deferred:

- **A Docker Hub mirror.** Blocked until Spree controls the `spree` or `spreecommerce` namespace there. A namespace claim with Docker would unblock it; if it succeeds, the publishing workflow pushes the same tags to Docker Hub and the stale `spreecommerce/spree` image is replaced or pointed at the new name.
- **How a hosted Spree cloud consumes the base** (rebuilding customer images when the base changes). It depends on the cloud's build pipeline and is out of scope here; the image contract is what it will rely on.
