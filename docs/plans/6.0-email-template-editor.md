# Email Template Editor

**Status:** Design finalized — nothing built
**Target:** Spree 6.0
**Depends on:** `6.0-liquid-mjml-emails.md` (Liquid and MJML templates, the template lookup, email serializers), `6.0-admin-rbac.md` (permission catalog), `6.0-admin-spa.md` (dashboard)
**Author:** Damian Legawiec
**Last updated:** 2026-09-30
**Tracking:** Linear V-3729 · GitHub spree/spree#14775

## Summary

Every transactional email Spree sends renders from a Liquid template written in MJML, and today only a developer can change one, by adding a file to the app. This plan lets merchants edit the emails their customers receive in the dashboard: each customer email, and the layout and shared blocks those emails are built from. Staff, store-owner and seller emails stay as Spree ships them. Edits are saved as a draft and go live when published; Spree finds the published version before the file, so an edited email goes out on the next send with no deploy. The editor shows the template's code next to a preview rendered on the server by the same renderer customers' emails go through, lists the variables the email receives, sends a test email, and keeps a history the merchant can revert to. Store branding settings (colors, fonts) style every customer email without touching its code, and survive a revert. When a Spree upgrade changes a default the merchant has customized, the dashboard says so and shows what changed.

## Key Decisions (do not deviate without discussion)

- **Preview renders on the server** (2026-09-30). The dashboard sends the draft template to an Admin API endpoint; the Ruby renderer fills it with sample data and returns the HTML and text parts. What the merchant sees is exactly what customers receive, there is one renderer and one set of filters to maintain, and sending a test email is the same call with a recipient. Rendering in the browser stays an option for later if typing responsiveness demands it.
- **The database is one more step in the existing lookup, in front of the files.** A store's saved template for a key wins; without one, the app's file, then Spree's own file, answer as today. No mailer changes: the key (`spree/order_mailer/confirm_email`) is the same name the file lookup uses. A developer's file override and a merchant's saved template can coexist; the merchant's wins for their store.
- **Templates are store-scoped records** (`belongs_to :store` through `Spree::SingleStoreResource`), following the rule for store-owned data. A template never leaks between stores.
- **Only customer emails are editable** (2026-09-30). Merchants edit what their customers receive: order confirmation, cancellation and payment link, the multi-seller purchase confirmation, shipping, refund, downloads, customer password reset and data export, newsletter confirmation and company invitation. Staff emails in core (admin and seller password resets, staff invitations, import and export results, disabled webhooks), the store-owner notifications and the seller emails stay as Spree's files. The line is who reads the email, not which gem ships it.
  - **Accepted trade-off:** a merchant cannot reword the new-order notification their own staff receives, or the emails sent to sellers, from the dashboard; a developer still can, with a file.
- **Customer emails can use an edited layout and edited shared partials** (2026-09-30). A merchant can edit `layouts/spree/base_mailer` and the `spree/shared/*` partials, so the footer or the item row changes once for every customer email.
  - **Accepted trade-off:** one bad edit to the layout or a partial affects every customer email. Publishing a layout or partial therefore validates every customer email of the store, not just one.
- **Emails that are not editable never read store templates** (2026-09-30). Staff, store-owner and seller emails render with Spree's own layout and partials (or the app's files), even when the store has published edited versions. A template edit can never break or rebrand a password reset for staff.
  - **Accepted trade-off:** the lookup must know which emails are editable, and a merchant's footer change does not appear on staff emails.
- **Edits are drafts until published** (2026-09-30). Saving stores a draft; a separate Publish step makes it live and records a revision. Teams can stage and review a change before customers see it.
  - **Accepted trade-off:** a draft state per template, a publish endpoint and UI, and every screen must make clear whether it shows the draft or the published version.
- **A published template must render.** Publishing validates by rendering with sample data under strict variables: a Liquid syntax error, an unknown variable, an unknown filter or invalid MJML is refused with the line and message, so a merchant can never break an email that is already being sent. Drafts may be saved in any state, since they are work in progress. Production sends stay lenient (an unknown variable prints nothing), as today.
- **One template serves every language, with optional per-language versions** (2026-09-30). A saved template applies to every language, using translation keys (`{{ 'key' | t }}`) or plain text; a merchant can add a version for one language when its copy must differ. The lookup tries the email's language first, then the every-language version, then the files.
  - **`locale` is never NULL:** the every-language version stores `locale = 'any'`, because a unique index treats NULLs as distinct and would let two every-language rows exist for one key.
- **History is the live row plus an append-only revisions table** (2026-09-30). `spree_email_templates` holds what is published, so the lookup on every send is one indexed read; `spree_email_template_revisions` records each publish. Rejected: one versions table with a current flag, which makes every send query the latest version and needs the flag kept consistent under concurrent publishes.
- **Preview uses the latest matching record, and the merchant can pick another** (2026-09-30). Each email builds its sample from the store's most recent matching record (last completed order, fulfillment, return), falls back to an in-memory sample for a new store, and accepts a record id so a merchant can check a specific case (a discount, a multi-parcel order).
- **Test emails go only to the signed-in admin** (2026-09-30). The endpoint cannot be used to send store-branded mail, a phishing risk, to arbitrary addresses. To check another inbox, the admin forwards it.
- **The editor is CodeMirror 6** (2026-09-30), as a headless `CodeEditor` component in `@spree/dashboard-ui` so the seller panel and plugins can reuse it. It is modular and small, and custom completions for Liquid variables and MJML tags are straightforward. Liquid highlighting inside HTML needs a small custom mode. Rejected: Monaco (a multi-megabyte bundle with web workers, poor on mobile) and a plain textarea (no highlighting or autocomplete).
- **The subject is a field of its own.** Files carry the subject as front matter; a saved template stores `subject` and `body` separately, which is the shape the front matter was chosen to map onto. The editor shows the subject as a text field above the code.
- **Email templates are their own permission resource** (`email_templates`), not part of `settings`. A template writes content every customer receives, including links, so the RBAC plan's rule for sensitive resources applies: a role can manage store settings without being able to change what customers are emailed.
- **Branding lives in store preferences** and reaches templates as `store.branding` variables that the layout's `<mj-attributes>` read. It is independent of any template's code, so reverting a template never loses the store's colors and fonts.
- **Variables come from the generated reference.** The same data that writes `email-variables.mdx` is served by the Admin API, so the editor's autocomplete, the docs and the serializers cannot disagree.

## Design Details

### Data model

```
spree_email_templates                spree_email_template_drafts          spree_email_template_revisions
─────────────────────                ───────────────────────────          ──────────────────────────────
id                                   id                                   id
store_id      → spree_stores         store_id      → spree_stores         email_template_id → spree_email_templates
key           string, not null       key           string, not null       subject           text
locale        string, not null       locale        string, not null       body              text, not null
subject       text                   subject       text                   base_digest       string, not null
body          text, not null         body          text, not null         published_by (acted_by)
base_digest   string, not null       base_digest   string, not null       created_at
published_at  datetime, not null     updated_by (acted_by)                index (email_template_id, created_at)
created_at, updated_at               created_at, updated_at
unique (store_id, key, locale)       unique (store_id, key, locale)
```

- **`key`** is the name the lookup uses: an editable email's view path (`spree/order_mailer/confirm_email`), the layout (`layouts/spree/base_mailer`) or a partial's render name (`spree/shared/line_item`). It is validated against the editable set and what Spree and the app ship, so a store cannot create a template nothing renders or a staff email it may not edit.
- **`locale`** is a language code, or `'any'` for the version every language uses.
- **`subject`** is set for emails and empty for the layout and partials.
- **`base_digest`** is the SHA-256 of the default file's source when the merchant started from it. Comparing it with the current default's digest is how the dashboard knows an upgrade changed the default underneath the merchant's version.
- **Drafts** hold work in progress, one per store, key and language. Publishing validates the draft, copies it into `spree_email_templates` (creating the row on first publish), appends a revision and deletes the draft.
- **Reverting to a revision** copies it into the draft; the merchant publishes it like any other change. **Reverting to the default** deletes the store's published template and draft, so the file answers again. History is never rewritten.
- The published model publishes lifecycle events (`email_template.published`, `.deleted`), so integrations and audit tooling see what customers will now receive.

### Lookup

An editable-email registry names the customer emails, `Spree::Emails.editable_templates` in `spree_emails`, which an extension appends to for its own customer emails. When a mailer renders one of them, `Spree::Emails::TemplateResolver#find(key)` gains a store:

1. the store's published template for the key in the email's language
2. the store's published template for the key with `locale = 'any'`
3. the app's `app/views/<key>.liquid`
4. the first gem's `app/views/<key>.liquid`

Partials and the layout resolve the same way through the renderer's file system, so a published `layouts/spree/base_mailer` or `spree/shared/line_item` applies to every customer email that uses it. For any other email the resolver is built without the store, so steps 1 and 2 never run and the layout and partials come from files. A preview renders the draft being edited in place of its published version, and the published versions of everything else.

### Branding

Store preferences, all optional, defaulting to today's design:

- `preferred_email_accent_color` (buttons, links)
- `preferred_email_background_color`, `preferred_email_card_color`
- `preferred_email_text_color`, `preferred_email_heading_color`
- `preferred_email_font` (from a fixed list of email-safe and web fonts, each with its fallback stack)

`Spree::Emails::StoreSerializer` exposes them as `store.branding`. The default layout reads them in `<mj-attributes>` and `<mj-style>`, so every default email follows them. A merchant's edited layout can read them too, or ignore them.

### Admin API

Under `/api/v3/admin/email_templates`, keyed by the template key (URL-encoded), scoped to the current store:

| Endpoint | What it does |
| --- | --- |
| `GET /email_templates` | Every editable template: key, name, kind (email, layout, partial), languages customized, whether a draft exists, whether the default changed since |
| `GET /email_templates/:key?locale=` | The published version (the store's, else the default), the draft if any, the default, and the variables it receives |
| `PUT /email_templates/:key/draft` | Save the draft's subject and body, in any state |
| `DELETE /email_templates/:key/draft` | Discard the draft |
| `POST /email_templates/:key/publication` | Publish the draft; renders it (and, for the layout or a partial, every customer email) with sample data; 422 with line-level errors when anything does not render |
| `DELETE /email_templates/:key?locale=` | Revert to the default |
| `POST /email_templates/:key/preview` | Render an unsaved subject and body with sample data (`record_id` optional); returns subject, HTML and text |
| `POST /email_templates/:key/test_email` | Send the draft or the published version to the signed-in admin |
| `GET /email_templates/:key/revisions` | History, newest first |
| `POST /email_templates/:key/revisions/:id/restoration` | Copy a revision into the draft |
| `GET /email_templates/:key/default_diff` | The default as it was when customized, and as it is now |

Publish, preview, test send and restore are not CRUD on the template itself, so each is its own nested resource with `create`, per the API conventions.

### Sample data

Each email declares how to build its sample: the store's most recent matching record (the last completed order, fulfillment, return), a record the merchant picks by its id, or an unsaved sample built in memory so a brand-new store can still preview. Every lookup is scoped to the current store. The same samples feed validation on publish. Token-carrying values (reset links, invitation links) get placeholder URLs, never a real token.

### Dashboard

A new **Settings → Emails → Templates** area (next to the existing sender settings):

- A list of the customer emails, the layout and the shared blocks, showing which are customized and which have an updated default.
- The editor: language switcher, subject field, CodeMirror editor with MJML and Liquid highlighting and variable autocomplete, preview pane (desktop and mobile widths, HTML and plain-text tabs, a record picker) refreshed on pause, "Send test email", "Save draft", "Publish", "Discard draft", "Revert to default", and a history drawer. The screen always says whether it shows the draft or the published version.
- An "Updated by Spree" banner with a side-by-side diff of the old and new default, and the option to keep the customized version or start again from the new default.
- A **Branding** card for the colors and fonts, with the preview reflecting them.

All copy goes through i18next in every locale file, per the dashboard rules.

## Migration Path

1. **Models and lookup**: `Spree::EmailTemplate`, `Spree::EmailTemplateDraft`, `Spree::EmailTemplateRevision`, one migration, the store and language steps in `TemplateResolver`, publish workflow with validation, lifecycle events, permission catalog entry `email_templates`.
2. **Sample data and preview**: per-email sample builders, the preview and test email endpoints.
3. **Admin API**: the remaining endpoints, serializers, integration specs, OpenAPI regeneration, Admin SDK methods.
4. **Branding**: store preferences, `store.branding` in the store serializer, the default layout reading them, the branding card.
5. **Dashboard editor**: `CodeEditor` in `@spree/dashboard-ui`, the list, editor, preview, drafts and publishing, history, revert, update banner with diff.
6. **Docs**: merchant guide in `docs/user/settings/emails`, developer notes on how saved templates interact with file overrides, and the Admin API reference.

## Constraints on Current Work

- **Keep every email's data in its serializer and every token in its mailer.** The editor shows the serialized variables and nothing else; a value a mailer computes in Ruby without passing it to the template cannot be offered to merchants.
- **Don't add Ruby-only template features.** Anything a template needs must be a Liquid filter or a serialized field, so a saved template renders exactly like a file.
- **Renaming an email key is now a data migration.** Saved templates reference keys; renaming a mailer method needs a rake task moving stored templates to the new key.
- **Changing a default template triggers the "updated by Spree" banner** for every store that customized it. Change defaults deliberately, and describe the change in release notes.
- **Keep partial arguments stable.** Merchants can edit partials and the emails that call them independently, so renaming or removing a partial's argument breaks stores that customized either side. Add arguments; don't rename them.
- **Any new way to send an email must go through the lookup.** A mailer that renders a template itself would skip the store's published version.
- **A new customer email must be registered as editable** in `Spree::Emails.editable_templates` (with a sample builder), or merchants cannot edit it. A new staff, store-owner or seller email must not be registered.
