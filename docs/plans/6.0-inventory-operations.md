# Inventory Operations (Transfers + Purchase Orders + Lots + Variant History)

**Status:** In Progress — the 6.0 half (transfers, purchase orders, suppliers, history screens) implemented 2026-09-07; lot capture stays 6.1
**Target:** Spree 6.0 (transfers, purchase orders, history) / 6.1 (simple lot capture). **Tier split 2026-09-07:** the lot LIBRARY — received-lot inventory, quantities, expiry, FIFO/FEFO auto-allocation — moved to Enterprise (`ee/docs/plans/inventory-lots.md`); OSS keeps the traceability capture below.
**Depends on:** Typed Stock Movements (6.0-typed-stock-movements.md), Fulfillment & Delivery (6.0-fulfillment-and-delivery.md), Stock Reservations (6.0-stock-reservations.md)
**Author:** Damian + Claude
**Last updated:** 2026-09-07 (grooming: open questions 1-3 settled, implementation decisions recorded below)

> **Naming note (2026-07-14):** the procurement-source model this plan introduces is **`Spree::Supplier`** (`spree_suppliers`, prefix `sup_`, `/api/v3/admin/suppliers`). An earlier draft called it `Spree::Seller`, which collided with the marketplace seller model of `6.0-multi-vendor-marketplace.md` — `Spree::Seller` is reserved for marketplace sellers (see `decisions.md` 2026-07-14). "Supplier" also matches Shopify's purchase-order vocabulary.

## Summary

Lift inventory operations from "atomic decrement + log" to a first-class workflow on par with Shopify. Three coordinated changes:

1. **`Spree::StockTransfer` gains a lifecycle.** Today a transfer is one-shot — source decrements and destination increments in the same transaction. After this plan: `draft → ready_to_ship → in_transit → received` (with `cancelled` as a terminal escape hatch), plus line items, partial receive support, and a discrepancy column. Source units leave on `mark_in_transit`, destination units land on `receive` — not at the same instant.
2. **New `Spree::PurchaseOrder` model** for supplier receives. Today's "external receive" hack (a `StockTransfer` with `source_location_id: nil`) is replaced by a proper `PurchaseOrder` with `supplier`, `expected_at`, `line_items[]` with `unit_cost`, and the same receive flow as transfers.
3. **Variant + Location stock history.** Surfaces the audit feed introduced by `6.0-typed-stock-movements.md` as inline timelines in the admin SPA — answering "why is on-hand 47?" in the place users always ask: on a SKU or a warehouse.
4. **Simple lot capture** (reshaped 2026-09-07 — the tier split): OSS records **which lot/batch a fulfillment actually shipped** — entered at fulfillment time, split across batches when needed — and makes the lot number searchable in both directions (customer → order → lot; lot → every order/customer that received it — the recall question). The full lot **library** (received-lot inventory with quantities, expiry, FIFO/FEFO auto-allocation) is the Enterprise layer that fills these same capture rows automatically.

This plan is the **UX surface** for inventory ops. The data primitives (typed `StockMovement`, `kind`, concrete FKs to Order/Fulfillment/Return/Exchange/StockTransfer/PurchaseOrder) come from `6.0-typed-stock-movements.md` and the Fulfillment rename. Those two plans must land first.

## Problem

### 1. Stock transfers don't model reality

A box moves from warehouse A to warehouse B over multiple days. Today's `StockTransfer` collapses the entire trip into one transaction:

```ruby
source.unstock(variant, qty, self)
destination.restock(variant, qty, self)
```

This means:
- A merchant cannot record "5 units left warehouse A today, arriving tomorrow" — the destination's `count_on_hand` jumps the moment the source decrements, so availability is wrong for the intervening period.
- There is no partial-receive workflow. If 10 went out and 8 arrived (2 damaged in transit), there's no model for the discrepancy.
- There is no "draft" state — a transfer can't be planned and edited before it ships.
- There is no per-line-item record. A transfer of 5 SKUs becomes 5 independent rows whose only link is `stock_movements.originator_id = transfer.id`.

### 2. "External receive" is a hack

Today, receiving stock from a supplier is implemented as `StockTransfer.transfer(nil, destination, variants)` — passing a `nil` source. There is no supplier identity, no PO number, no unit cost, no expected-arrival date, no audit of who placed the order. The legacy admin's "Receive" screen is a `StockTransfer` form with the source dropdown hidden.

Suppliers and merchant warehouses are different things. A PO has unit cost (drives COGS / margin reporting), an expected date (drives replenishment scheduling), and a supplier (drives accounts payable). A transfer has none of those — it's internal logistics. Folding them together costs us margin reporting and replenishment UX forever.

### 3. Movement history has no UI surface

Once `6.0-typed-stock-movements.md` lands, every change to `count_on_hand` carries a typed reason (`received | allocated | shipped | released | adjusted`) and a concrete FK to its cause. That data is invisible without screens. The legacy admin had a "Stock Movements" page that listed `+5 from T-123`, but it was an undifferentiated firehose across all SKUs and all locations — the question merchants actually ask is per-SKU ("why is this on-hand 47?") or per-location ("what changed in the Brooklyn warehouse this week?"). The destination is the question, not the dataset.

## Current State

| What | How it works (5.5) |
|---|---|
| `Spree::StockTransfer` | One-shot atomic transfer. Columns: `source_location_id` (nullable for receives), `destination_location_id`, `number`, `reference`, `type` (STI column, unused), `created_at`. No status, no expected/received-at, no line items. |
| External receive | `StockTransfer.transfer(nil, destination, variants)` — no supplier, no cost. |
| Movement audit | `Spree::StockMovement` with polymorphic `originator` — a `Fulfillment` (stock leaves at order placement, not at dispatch), a `StockTransfer`, a `Return`/`Exchange`, or nothing. Manual corrections and backordered restocks write no movement at all. |
| Admin SPA | `Products → Transfers` (single page) with create-transfer sheet. No history view, no PO concept. |

## Key Decisions (do not deviate without discussion)

### Transfers

- **`Spree::StockTransfer` gets a `status` column** with values `draft | ready_to_ship | in_transit | partially_received | received | canceled`, declared with `Spree::HasStatus` and moved by workflows (see the 2026-09-07 decisions below). No state machine.
- **Two-phase stock movement**, mirroring Shopify. Source's `count_on_hand` decrements on `mark_in_transit`. Destination's `count_on_hand` increments on `receive` (potentially partial). Between those two events, the units are in flight — physically gone from the source, not yet at the destination.
- **First-class line items.** New table `spree_stock_transfer_items` with `(stock_transfer_id, variant_id, quantity_shipped, quantity_received, condition)`. Replaces today's "implicit line item via stock_movement.stock_item.variant".
- **Partial receive is the default model.** The receive screen edits `quantity_received` per item. If `SUM(quantity_received) < SUM(quantity_shipped)`, status becomes `partially_received`; when equal, `received`. A `discrepancy_reason` column on the line item captures "damaged in transit / lost / undercount" for the gap.
- **Cancelled is terminal.** Cancelling a `draft` is a no-op for stock. Cancelling an `in_transit` transfer requires the merchant to choose: write the source back to its `count_on_hand` (treat as if it never shipped), or write off the units (shrinkage; `adjusted` movement with reason). No silent reversal.
- **`receive` writes typed `received` stock movements with `stock_transfer_id`.** `mark_in_transit` writes typed `shipped` movements with `stock_transfer_id`. Two-way reconciliation through the `kind` + `stock_transfer_id` columns of `6.0-typed-stock-movements.md`.

### Purchase Orders

- **New model `Spree::PurchaseOrder`**, not an STI subclass of `StockTransfer`. The two share a UX rhythm (line items → receive flow) but their domains are distinct (supplier vs warehouse, unit cost vs no cost, AP vs internal logistics). STI would force one table to carry both vocabularies. Better to have parallel models with a shared `Receivable` concern that owns the line-items + receive-flow + status machine.
- **`Spree::Supplier` is the supplier identity.** Minimal: `name`, `contact_name`, `email`, `phone`, `address`, `notes`, `metadata`. Stores manage their own supplier list — suppliers are not shared across stores in 6.0.
- **Statuses**: `draft | ordered | partially_received | received | canceled`. No `in_transit` — a PO doesn't track in-flight stock from the supplier; the merchant only knows about it when units land. (Future enhancement: optional `shipped` state if the supplier provides tracking, but not in 6.0.)
- **`PurchaseOrderItem` has `unit_cost` (Money) and `quantity_ordered` / `quantity_received`.** Currency comes from the PO's `currency` column (defaults to the store's). Receiving units writes typed `received` stock movements with `purchase_order_id`.
- **PO does not affect `count_on_hand` until receive.** Ordered units are visible to the merchant as "on order" (computed: `SUM(quantity_ordered - quantity_received)` per variant), but never count toward availability.

### Simple lot capture (reshaped 2026-09-07 · 6.1)

- **`Spree::FulfillmentLot`** — the capture row: `fulfillment_item_id`,
  `lot_number` (string, required), `quantity` (nullable — nil = the whole
  line; multiple rows express a split batch, e.g. 80 × LOT-001 + 20 ×
  LOT-002). Entered in the fulfill dialog or added/corrected afterwards on
  the fulfillment card; `lot_number` is ransackable, and the dashboard's
  order search gains a lot-number mode so an accountant or QA manager can
  paste a batch number and see every affected fulfillment, order and
  customer.
- **`lot_tracked` boolean on the variant** is an advisory prompt: the
  fulfill dialog requires lot entry for flagged variants (dashboard-level,
  the advisory-required precedent from product types); the server accepts
  lot rows on any item, flagged or not.
- **No quantities, no expiry, no allocation in OSS** — the capture answers
  traceability, not inventory. The Enterprise lot library (received-lot
  rows per variant + location, `expires_at`/`manufactured_on`/supplier
  reference, `manual | fifo | fefo` allocation) **writes these same
  capture rows automatically at dispatch**, so the recall search reads one
  surface regardless of tier.
- Store API: nothing — lots are back-office data.

### Implementation decisions (2026-09-07)

Settled interactively before implementation; they replace the parts of this
plan written against 5.x idioms that 6.0 has since retired.

- **No state machines — `Spree::HasStatus` plus workflows.** `state_machines-activerecord` is not a
  dependency of 6.0 (`6.0-normalize-state-to-status.md`, `6.0-service-workflows.md` decision 11), so
  the `state_machine :status do … end` blocks below are read as intent, not as code. Both models
  `include Spree::HasStatus` and declare `has_status …, default: :draft`; every transition is a
  workflow in `app/workflows/spree/stock_transfers/` and `app/workflows/spree/purchase_orders/`,
  registered on `Spree::Dependencies` as `stock_transfer_*_workflow` /
  `purchase_order_*_workflow`. This is what makes a receive able to carry the quantities the
  warehouse counted and a cancellation able to carry the merchant's restock-or-write-off choice —
  arguments a transition callback could not take. The guards the state machine expressed
  (`from: :in_transit`) become the workflows' own status checks.
- **The one-shot `StockTransfer.transfer` / `.receive` class methods are removed outright.** 6.0 is
  the breaking window (`decisions.md` 2026-08-30 left the choice to this grooming), and a
  deprecation shim would keep a second write path into `count_on_hand` alive for a release —
  precisely the thing typed movements exist to prevent. `Spree::StockTransfers::Create` +
  `MarkInTransit` + `Receive` replace them, and the admin `POST /stock_transfers` now persists a
  draft instead of moving stock. The unused `type` STI column and the dead `persist: false`
  movement path go with them.
- **Legacy source-less transfers are soft-deleted after migration, with a purge task for a later
  release.** `spree:upgrade:migrate_external_receives_to_purchase_orders` mints the `PO-…`, points
  the existing movements at it and stamps the `T-…` transfer `deleted_at`, so the old number stays
  findable for historical reporting without the same receive appearing twice in the admin.
  `spree:upgrade:purge_migrated_external_receives` removes them when a merchant is ready.
- **Suppliers and purchase orders are one new permission-catalog resource, `:purchasing`.**
  `read_purchasing` / `write_purchasing`, registered in
  `PermissionConfiguration#register_default_resources` alongside `:stock`. The plan's earlier
  `read_inventory` / `write_inventory` would have put "Stock" and "Inventory" side by side on the
  roles screen with nothing to tell a merchant which is which. Transfers stay under `stock`, whose
  subject list gains `Spree::StockTransferItem`.
- **`spree_stock_transfers` gains its own `store_id`.** Today the table has none, `Spree::Store` has
  no `stock_transfers` association, and so `Spree::Base.for_store` falls through to `self` — the
  admin transfers endpoint is not store-scoped at all. The column, `Spree::SingleStoreResource` and
  a `Store#stock_transfers` association close that, and make transfers obey the same tenancy rule as
  purchase orders rather than a second one derived from `destination_location`. `#number_store`
  keeps working and now simply reads `store`.
- **`source_location_id` stays nullable in the database**, with presence enforced on the model. A
  `change_column_null … false` would fail on any install still holding external-receive rows, and
  data transformations belong in rake tasks (CLAUDE.md), so the upgrade task is what empties the
  column of nulls.
- **Money is a `decimal(10, 2)` column, not `_cents` + `monetize`.** Spree has no money-rails
  dependency; `PurchaseOrderItem#unit_cost` follows `Spree::Variant#cost_price`, and the currency
  comes from the purchase order rather than being repeated per line.
- **A supplier's address is inline columns**, mirroring `Spree::StockLocation` — the closest
  precedent for a non-customer entity with a postal address, and the shape a flat v3 payload and a
  flat dashboard form both want. No `belongs_to :address`.
- **Suppliers are per store** (`spree_suppliers.store_id`, `Spree::SingleStoreResource`, unique on
  `(store_id, name)`), settling open question 2. Promoting them to installation-wide later means
  adding a join table, backfilling one row per existing supplier and keeping `store_id` as the
  owner — worth knowing, not worth building against.
- **A receive stamps what the units cost onto the movement.** `spree_stock_movements.unit_cost`
  (nullable `decimal(10, 2)`) records the price each unit actually landed at, so the rolling
  average-cost feature of open question 3 has a ledger to read instead of a reconstruction to
  attempt — including across two partial receives at different prices. `StockLocation#restock` and
  `#move` take an optional `unit_cost:`; transfers and returns leave it null, because moving stock a
  merchant already owns is not a purchase.
- **Status transitions are `PATCH` member routes**, matching `orders/:id/cancel`,
  `returns/:id/receive` and every other transition already in the Admin API. The plan's claim that
  these are POSTs describes no existing endpoint.

### Typed Stock Movements wiring

These additions live in `6.0-typed-stock-movements.md`; this plan only consumes them.

- Add `purchase_order_id` FK to `Spree::StockMovement` (typed-movements plan lists `order_id`, `fulfillment_id`, `return_id`, `exchange_id`, `stock_transfer_id` — extend with `purchase_order_id`).
- Add `Spree::StockMovement::KINDS += ['purchase_order_received']` — **actually no**, reuse `received` with `purchase_order_id` set. Same shape as a return receive. The `kind` is *what happened to stock*; the FK is *why*.

### Admin SPA UX

- **Top-level Products subnav**: `Transfers`, `Purchase Orders`. Each is a list page with status filters (Draft / Ready / In transit / Received / All).
- **Transfer detail page** has three modes by status:
  - `draft` → editable line items, "Mark as ready to ship" / "Cancel" actions.
  - `ready_to_ship` → frozen line items, "Mark in transit" (writes source `shipped` movements) / "Back to draft" / "Cancel".
  - `in_transit` / `partially_received` → receive screen: per-item `quantity_received` input with running totals, optional `discrepancy_reason` per item, "Receive" submit (writes destination `received` movements for the deltas).
  - `received` / `cancelled` → read-only summary + activity log.
- **Purchase Order detail** mirrors transfer detail. `draft` → editable line items + costs. `ordered` → frozen line items, "Receive" enabled. Same partial-receive screen.
- **Variant Inventory tab (on Product detail) gains a History panel.** Reads `GET /api/v3/admin/stock_movements?q[stock_level_variant_id_eq]=…` (the typed-movements admin endpoint), renders `date · location · qty before → after · kind · cause` with the cause linking to the underlying entity (Transfer T-…, PO PO-…, RMA RA-…, Order #…, "Manual adjustment").
- **Stock Location detail page (settings) gains an Activity tab.** Same data shape, scoped via `q[stock_level_stock_location_id_eq]`. Useful for warehouse reconciliation.
- **No standalone "Stock Movements" page.** Movements are always read in the context of a variant or a location. The legacy admin's firehose list is gone.

## Design Details

### StockTransfer (updated)

```ruby
class Spree::StockTransfer < Spree.base_class
  has_prefix_id :st
  # Transfers have no store column; #number_store resolves through
  # destination_location.store — see 6.0-document-numbers.md
  has_spree_number prefix: 'T'
  include Spree::NumberIdentifier
  include Spree::Metafields
  include Spree::Metadata

  publishes_lifecycle_events

  belongs_to :source_location, class_name: 'Spree::StockLocation'
  belongs_to :destination_location, class_name: 'Spree::StockLocation'

  has_many :items, class_name: 'Spree::StockTransferItem',
           inverse_of: :stock_transfer, dependent: :destroy
  has_many :stock_movements, class_name: 'Spree::StockMovement',
           inverse_of: :stock_transfer
  accepts_nested_attributes_for :items, allow_destroy: true

  validates :source_location, :destination_location, presence: true
  validate :source_differs_from_destination
  validate :has_items, on: :submit

  state_machine :status, initial: :draft do
    event :mark_ready do
      transition from: :draft, to: :ready_to_ship
    end
    event :mark_in_transit do
      transition from: %i[draft ready_to_ship], to: :in_transit
    end
    event :receive_partial do
      transition from: :in_transit, to: :partially_received,
                 if: ->(t) { t.items.any?(&:short?) }
    end
    event :receive do
      transition from: %i[in_transit partially_received], to: :received,
                 unless: ->(t) { t.items.any?(&:short?) }
    end
    event :cancel do
      transition from: %i[draft ready_to_ship in_transit], to: :cancelled
    end

    after_transition to: :in_transit,     do: :write_shipped_movements
    after_transition to: :partially_received, do: :write_received_deltas
    after_transition to: :received,       do: :write_received_deltas
  end

  scope :open,   -> { where(status: %w[draft ready_to_ship in_transit partially_received]) }
  scope :closed, -> { where(status: %w[received cancelled]) }
end
```

### StockTransferItem (new)

```ruby
class Spree::StockTransferItem < Spree.base_class
  has_prefix_id :sti

  belongs_to :stock_transfer, class_name: 'Spree::StockTransfer', inverse_of: :items
  belongs_to :variant, -> { with_deleted }, class_name: 'Spree::Variant'

  validates :quantity_shipped, numericality: { greater_than: 0, only_integer: true }
  validates :quantity_received, numericality: { greater_than_or_equal_to: 0, only_integer: true }
  validate :received_does_not_exceed_shipped

  attribute :discrepancy_reason, :string

  def short?
    quantity_received < quantity_shipped
  end

  def outstanding
    quantity_shipped - quantity_received
  end
end
```

### PurchaseOrder (new)

```ruby
class Spree::PurchaseOrder < Spree.base_class
  has_prefix_id :po
  has_spree_number prefix: 'PO'   # see 6.0-document-numbers.md
  include Spree::NumberIdentifier
  include Spree::SingleStoreResource
  include Spree::Metafields
  include Spree::Metadata

  publishes_lifecycle_events

  belongs_to :supplier, class_name: 'Spree::Supplier'
  belongs_to :destination_location, class_name: 'Spree::StockLocation'
  belongs_to :store, class_name: 'Spree::Store'

  has_many :items, class_name: 'Spree::PurchaseOrderItem',
           inverse_of: :purchase_order, dependent: :destroy
  has_many :stock_movements, class_name: 'Spree::StockMovement',
           inverse_of: :purchase_order
  accepts_nested_attributes_for :items, allow_destroy: true

  attribute :currency,    :string
  attribute :expected_at, :date
  attribute :notes,       :text

  # Currency defaults from the store before validation — creation paths never
  # need to pass it explicitly, but may override for foreign-currency POs.
  before_validation { self.currency ||= store&.default_currency }

  validates :supplier, :destination_location, :currency, presence: true
  validate  :has_items, on: :submit

  state_machine :status, initial: :draft do
    event :mark_ordered do
      transition from: :draft, to: :ordered
    end
    event :receive_partial do
      transition from: :ordered, to: :partially_received,
                 if: ->(po) { po.items.any?(&:short?) }
    end
    event :receive do
      transition from: %i[ordered partially_received], to: :received,
                 unless: ->(po) { po.items.any?(&:short?) }
    end
    event :cancel do
      transition from: %i[draft ordered partially_received], to: :cancelled
    end

    after_transition to: :partially_received, do: :write_received_deltas
    after_transition to: :received,           do: :write_received_deltas
  end
end
```

### PurchaseOrderItem (new)

```ruby
class Spree::PurchaseOrderItem < Spree.base_class
  has_prefix_id :poi

  belongs_to :purchase_order, class_name: 'Spree::PurchaseOrder', inverse_of: :items
  belongs_to :variant, -> { with_deleted }, class_name: 'Spree::Variant'

  attribute :quantity_ordered,  :integer
  attribute :quantity_received, :integer, default: 0
  attribute :unit_cost_cents,   :integer
  attribute :unit_cost_currency, :string

  monetize :unit_cost_cents

  validates :quantity_ordered, numericality: { greater_than: 0, only_integer: true }
  validates :quantity_received, numericality: { greater_than_or_equal_to: 0, only_integer: true }
  validate :received_does_not_exceed_ordered
  validate :unit_cost_present_when_required

  def short?
    quantity_received < quantity_ordered
  end

  def outstanding
    quantity_ordered - quantity_received
  end

  def total_cost
    unit_cost * quantity_ordered
  end
end
```

### Admin API

New endpoints; all CRUD-shaped, all under `/api/v3/admin/`:

```text
GET    /stock_transfers
POST   /stock_transfers
GET    /stock_transfers/:id
PATCH  /stock_transfers/:id
DELETE /stock_transfers/:id                          # only when status == draft

POST   /stock_transfers/:id/mark_ready
POST   /stock_transfers/:id/mark_in_transit
POST   /stock_transfers/:id/receive                  # body: { items: [{ id, quantity_received, discrepancy_reason }] }
POST   /stock_transfers/:id/cancel                   # body: { on_in_transit: 'restock' | 'write_off' } when needed

GET    /suppliers
POST   /suppliers
GET    /suppliers/:id
PATCH  /suppliers/:id
DELETE /suppliers/:id

GET    /purchase_orders
POST   /purchase_orders
GET    /purchase_orders/:id
PATCH  /purchase_orders/:id
DELETE /purchase_orders/:id                          # only when status == draft

POST   /purchase_orders/:id/mark_ordered
POST   /purchase_orders/:id/receive                  # body: { items: [{ id, quantity_received }] }
POST   /purchase_orders/:id/cancel
```

Each status change is its own member action rather than a `PATCH` that mass-assigns `status`, because each one is a workflow with its own arguments. The verb is `PATCH`, matching `orders/:id/cancel`, `returns/:id/receive` and every other transition already in the Admin API.

`GET /stock_movements` (the audit feed introduced by `6.0-typed-stock-movements.md`) gains support for `q[purchase_order_id_eq]` automatically once the FK is in the ransackable list.

## Migration Path

### Phase 0 (prerequisite)

`6.0-typed-stock-movements.md` lands first — the `kind` column, concrete FKs, allocated_count column on StockLevel, and StockMovement model rewrite. Without this, transfers and POs can't write typed audit rows.

### Phase 2: Data migration (rake task `spree:migrate_external_receives_to_purchase_orders`)

For each existing `StockTransfer` with `source_location_id IS NULL`:

1. Find-or-create a `Spree::Supplier` named `"Migrated receives"` for the relevant store.
2. Create a `Spree::PurchaseOrder` with `status: 'received'`, `received_at: transfer.created_at`, `currency` from store default, `ordered_at: nil`.
3. Migrate the transfer's `stock_movements` into the PO via `purchase_order_id` (set, leave `stock_transfer_id` for historical lineage if desired, or null it). The migration leaves `count_on_hand` untouched — the movements already affected stock at the time.
4. Create `PurchaseOrderItem` rows from the underlying movements with `unit_cost_cents: 0` (historical cost is unknown).
5. Mark the original `StockTransfer` as `deleted_at`-stamped + `status: 'received'` for audit, or hard-delete it after a release of soft-deprecation. Open question — see below.

All other existing transfers (with a real source location) become `status: 'received'` with `received_at = created_at`. They retroactively look like instantaneous transfers, which matches today's reality.

### Phase 3: Model & service code

- New models: `Supplier`, `PurchaseOrder`, `PurchaseOrderItem`, `StockTransferItem`.
- `StockTransfer` gains a declared status + line items; the old atomic `transfer`/`receive` class methods are removed.
- New services under `Spree::Inventory::`:
  - `Spree::Inventory::SubmitTransfer` (draft → ready_to_ship → in_transit, writes `shipped` movements)
  - `Spree::Inventory::ReceiveTransfer` (params: `{ items: [{ id, quantity_received, discrepancy_reason }] }`, writes `received` movements for deltas)
  - `Spree::Inventory::CancelTransfer`
  - Parallel `Spree::Inventory::SubmitPurchaseOrder` / `Spree::Inventory::ReceivePurchaseOrder` / `Spree::Inventory::CancelPurchaseOrder`
- Each service returns a `ServiceModule::Result` (success/error) — same pattern as existing checkout services.
- Permissions: `Supplier`, `PurchaseOrder` and `PurchaseOrderItem` register as the `:purchasing`
  catalog resource (`read_purchasing` / `write_purchasing`); `Spree::StockTransferItem` joins the
  existing `:stock` resource's subject list.

### Phase 4: Admin API + serializers

- Register dependencies (`admin_supplier_serializer`, `admin_purchase_order_serializer`, `admin_purchase_order_item_serializer`, `admin_stock_transfer_item_serializer`).
- Register API scopes: `read_inventory` / `write_inventory` for POs and suppliers. Transfers stay under `read_stock` / `write_stock` (existing).
- Controllers under `Spree::Api::V3::Admin::`:
  - `SuppliersController` (standard CRUD)
  - `PurchaseOrdersController` (standard CRUD + transition actions)
  - `StockTransfersController` rewritten — no more `create` doing source/dest decrement; create persists a draft. Transitions are explicit actions.
- New integration specs in `spree/api/spec/integration/spree/api/v3/admin/`.

### Phase 5: SDK + admin SPA

- Run typelizer + rswag + admin-client generators.
- `useTransfers`, `useTransfer`, `useTransition<Transfer>` hooks (consolidate the action endpoints behind a single hook with `action: 'mark_ready' | 'receive' | 'cancel'`).
- Same shape for purchase orders.
- `useSuppliers`.

## Constraints on Current Work

- **Don't call `StockTransfer.transfer` or `.receive`.** Both are gone. Moving stock between
  warehouses is `Spree::StockTransfers::Create` → `MarkInTransit` → `Receive`; receiving from a
  supplier is a `Spree::PurchaseOrder`.
- **Don't transition a transfer or a purchase order by writing `status`.** `update(status: …)`
  passes the inclusion validation and writes no stock movement, which silently desynchronizes the
  ledger from the shelf. Call the workflow.
- **Don't reach `Spree::StockTransfer` unscoped.** It carries `store_id` now, so
  `current_store.stock_transfers` is the lookup — including for the incidental resolution of a
  `source_location_id` or a `variant_id` out of a payload.
- **Don't add receive flows to `StockTransfer` without `source_location_id`.** Supplier receives move to `PurchaseOrder`. If a 5.5 feature needs to record a supplier receive, scope it minimally and flag it for migration.
- **Don't create a separate "Stock Movements" admin SPA page.** Movement history is always inline on variant + stock location.
- **Don't fold cost data onto `StockTransfer`.** Transfers don't have a unit cost — they move existing inventory between owned locations. Cost lives on `PurchaseOrderItem.unit_cost`.
- **Lot capture lives only on `Spree::FulfillmentLot` rows** — no `lot_number` strings on line items, orders, or movements. The Enterprise library layers on these rows (its allocation fills them); OSS never grows lot quantities, expiry, or allocation of its own.

## Open Questions

1. ~~Historical "external receive" transfers — keep or hard-delete after migration?~~ **Settled
   2026-09-07: soft-delete plus a purge task** — see Implementation decisions.
2. ~~Suppliers shared across stores?~~ **Settled 2026-09-07: per store.** Promotion path recorded
   in Implementation decisions if a multi-storefront merchant ever asks.
3. ~~Average / weighted-average cost on Variant?~~ **Partly settled 2026-09-07.** The feature itself
   is still a separate plan — `Variant#average_cost`, and what returns, write-offs and
   foreign-currency receives do to it, are not scoped here. What this plan now ships is the ledger
   it will read: every `received` movement carries the `unit_cost` the units landed at.
4. **Pickup transfers (ship-to-store).** `6.0-fulfillment-and-delivery.md` mentions `pickup_stock_policy: 'any'` as enabling ship-to-store. The natural implementation is auto-creating a `StockTransfer` when a pickup order's items aren't local at the chosen pickup location. Reviewed 2026-09-07 and deliberately left open: the mechanism is straightforward, but it hangs on a storefront promise ("ready in 3 days" instead of "ready in 2 hours") that belongs to the fulfillment plan, and nothing in the 6.0 transfer lifecycle either enables or forbids it. Unblocked by: a decision on what the pickup date range says when stock has to travel.
5. **Server-side enforcement of `lot_tracked`** — should the fulfill workflow refuse (not just prompt) when a flagged variant ships without lot rows? Advisory in v1 (dashboard requires, server accepts); revisit if merchants report gaps. The library-tier questions (expired lots, flag flips over existing stock) moved to the Enterprise plan.
