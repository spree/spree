# Klaviyo Marketing Integration

**Status:** In Progress — building Migration Path steps 1–6 (core email takeover and erasure hook, the `spree_klaviyo` gem, storefront events, docs); step 7, the release, is done by hand
**Target:** Spree 6.0 (next patch release)
**Depends on:** `6.0-integrations-admin.md` (the `Spree::Integration` model, verify-before-activate, the dashboard gallery), `6.0-typed-webhook-events.md` (the event catalog and Store-shaped payloads), `6.0-json-preferences.md` (secret preferences and their upgrade steps), `6.0-email-template-editor.md` (template keys name the customer emails), `5.4-6.0-eu-legal-compliance.md` (newsletter verification, consent records, erasure), `6.0-paypal-payment-provider.md` (the provider-gem port this one follows)
**Author:** Łukasz Adamczyk
**Last updated:** 2026-11-12
**Tracking:** Linear V-3765 · GitHub spree/spree#15096

## Summary

Bring Klaviyo to Spree 6 as an optional gem at `spree/providers/klaviyo`,
publishing the existing gem name `spree_klaviyo` and released with Spree. The
standalone [`spree/spree_klaviyo`](https://github.com/spree/spree_klaviyo)
gem (1.1.2, built for 5.3–5.6) does not run on 6.0: it depends on
`spree_admin`, takes its browsing events from the Rails storefront's analytics
handler (removed in 6.0), decorates `Spree::BaseController`, the user class
and `Spree::Publishable`, and reads taxons, reimbursements, shipments,
`private_metadata` and metafields, which 6.0 replaced. This is a rewrite on
6.0's seams, not a copy. The integration keeps its stored class and
preference names, so an upgrading store keeps its connection. The server
sends Klaviyo what only the server knows: customer profiles, newsletter
sign-ups, the order lifecycle under Klaviyo's standard metric names, and
refunded returns. The Next.js storefront sends browsing events and Started
Checkout through Klaviyo's own script. Klaviyo can take over the newsletter
confirmation and, at the merchant's choice, the order emails, through a small
generic addition to core that lets an active integration stop Spree sending a
given customer email; `spree_emails` only asks whether to send.

## Key Decisions (do not deviate without discussion)

1. **An integration in the provider-gem shape, not a provider.** Directory
   `spree/providers/klaviyo` (the home of third-party integration gems,
   payment gateways included), gem `spree_klaviyo`,
   `s.version = Spree.version`, exact pin on `spree_core`, a Rails engine that
   registers the integration, its subscribers and its hook in
   `after_initialize`. Klaviyo implements no core provider seam: core never
   calls it to compute anything, it listens to events and a workflow hook. No
   "marketing provider" abstraction is added, because core has nothing to ask
   a marketing system; the one thing core needs, which emails Spree still
   sends, is a generic capability of `Spree::Integration` (Key Decision 9).
   The `spree` meta gem does not depend on it; the `spree_admin` dependency
   is dropped (the dashboard form is generated from the preference schema).
   No tables, no migrations; the install generator stays as a no-op, as
   Stripe's and PayPal's do, so `rake test_app` and existing
   `rails g spree_klaviyo:install` calls keep working (`spree add` does not
   need one).
2. **Ships in the next 6.0 patch release**, following PayPal (2026-10-27). A
   store syncing Klaviyo on 5.x loses that sync the day it upgrades until the
   gem exists. Core gains five small additive pieces (Key Decisions 9 and
   18): `Spree::Integration#replaced_customer_emails`,
   `Spree::Store#sends_customer_email?`, `Spree::Store#active_integrations`
   (moved from `Spree::IntegrationBackedProvider`, which then calls it), the
   `spree_emails` subscribers asking `sends_customer_email?`, and a public
   `original_email` reader on `Spree::Customers::Anonymize`. With no
   integration installed every email is sent exactly as today, so they can
   ride a patch.
3. **Every stored name is kept.** The integration stays
   `Spree::Integrations::Klaviyo` (it lives in `spree_integrations.type`;
   the wire type is `klaviyo`), and `klaviyo_private_api_key` (`:password`)
   and `default_newsletter_list_id` keep their names, so an upgraded store's
   row works the moment the gem is installed, with no data step. New classes
   live under `SpreeKlaviyo::`. `klaviyo_public_api_key` is no longer
   declared: nothing on the server uses it, and the public key goes in the
   storefront's Google Tag Manager tag (Key Decision 16). Old rows keep the
   value harmlessly.
4. **The integration is the only server-side credential home**
   (`6.0-integrations-admin.md`, "One credential home"). Saving credentials
   makes no network call. Activating runs `can_connect?`, which reads the
   configured list with the private key and blocks going live, with
   Klaviyo's own message, on a missing or wrong key, a key without the Lists
   read scope, or a missing or wrong list id. That is all it proves: a key
   missing a write scope (events, profiles, subscriptions, data privacy)
   activates, and the first job that needs the scope fails with 403 and is
   reported (Key Decision 13). The list's opt-in setting is not checked (Key
   Decision 7).
5. **Klaviyo's official Ruby SDK, `klaviyo-api-sdk ~> 19.0`** (decided
   2026-11-03), the same choice as every other provider gem (`stripe`,
   `paypal-server-sdk`, `easypost`, `meilisearch`). Version 19 sends API
   revision `2026-10-15`, the latest; 5.x's `2025-04-15` is already
   deprecated (Klaviyo keeps a revision stable for a year, deprecated for a
   second, then retires it, falling forward rather than failing). Moving to
   a newer revision is a new SDK major version and a deliberate change that
   re-records the cassettes. How the SDK is used:
   - **One API client per integration.** Each call builds
     `KlaviyoAPI::ApiClient.new(configuration)` with that store's key and
     passes it to the API class (`KlaviyoAPI::ProfilesApi.new(client)`). The
     SDK's global `KlaviyoAPI.configure` and its convenience wrappers
     (`KlaviyoAPI::Profiles…`) are never used: they hold one process-wide
     key, and two stores would send each other's data.
   - **Explicit timeout.** The SDK's default is none at all; the gem sets
     10 seconds.
   - **Retries belong to the jobs** (Key Decision 13). The SDK only retries
     through its global wrappers, which sleep in the worker thread for up to
     60 seconds; the per-integration calls do not retry, and the jobs
     reschedule instead.
   - **`debugging` stays off** (Key Decision 15).

   **Accepted trade-off:** `typhoeus` (with `ethon` and `ffi`, which load
   libcurl at runtime) and `retriable` come with the SDK, only for an app
   whose Gemfile lists `spree_klaviyo` (Key Decision 1; `server/Gemfile`
   does not). Spree's server image already has libcurl (it installs `curl`);
   other hosts that add the gem must provide it.
6. **Profiles are upserted, never looked up.** Every profile write is one
   `POST /api/profile-import` (create or update; 75/s and 750/m per Klaviyo
   account). A customer's profile carries the email and an `external_id`
   (Klaviyo's field for "the id the person has in an external system"), so
   Klaviyo keeps one profile when the customer changes their email: the
   import finds the profile by `external_id` and updates the email. The
   `external_id` is the customer's prefixed id (`cus_…`) by default (decided
   2026-11-05), which a merchant can take from Klaviyo straight to the
   dashboard or the API. The integration's
   `use_database_ids_as_external_ids` switch, off by default, sends the
   customer's database id instead, the value 1.x sent
   (`migrate_users_to_customers` keeps the ids), so a store whose profiles
   1.x created can keep matching them; it is the one place Spree sends a raw
   database id out, and only when the merchant turns it on. Stores sharing a
   Klaviyo account should use the same setting. Klaviyo matches by
   `external_id` before email: an import whose email matches a profile
   holding a different `external_id` creates a second profile with the same
   email (confirmed in the test account, 2026-11-05). With the switch off,
   every customer 1.x synced therefore gets a second profile, which the
   switch's help text and the upgrade guide state (the merchant decides; no
   automatic switch for upgraded stores, decided 2026-11-05). A guest's
   profile carries the email alone, and when the guest registers Klaviyo adds
   the `external_id` to that profile rather than creating a second one
   (confirmed in the test account, 2026-11-05). Rejected: the database id for everyone
   (a number nobody can look up in Spree, and a permanent exception to
   prefixed ids), email only (an email change would split the person into
   two profiles and leave the consent on the old one), and storing
   Klaviyo's profile id in `Spree::ExternalReference` (a profile import
   finds the profile in one call without it, and `Customer` has no external
   references because customers belong to every store). Events identify the profile by
   email only: Klaviyo accepts events asynchronously (202) and could never
   report an identifier conflict. An event for an email that two profiles
   share is recorded on the older profile only (confirmed in the test
   account, 2026-11-05). A deletion request for that email deletes both
   profiles (same check). An import whose email and external id
   belong to two profiles is no conflict either: Klaviyo answers 200 and
   moves the email onto the profile holding the external id (confirmed in
   the test account, 2026-11-05). Any other 4xx on import is reported, not
   retried. The 5.x fetch-by-email → create → store
   `klaviyo_id` → patch sequence, the `klaviyo_id` key on the user and
   `FetchAndStoreUserKlaviyoId` are gone: Spree stores nothing about Klaviyo
   on its own records. An anonymized customer is never synced (Key Decision
   18).
7. **Klaviyo owns the newsletter opt-in** (decided 2026-11-03), so the
   merchant designs the confirmation email in Klaviyo, and the list's own
   opt-in setting, chosen by the merchant in Klaviyo, decides whether there
   is one. Every sign-up goes to Klaviyo at once as a bulk subscribe with
   `consent: SUBSCRIBED` against `default_newsletter_list_id`: an unconfirmed
   sign-up on `newsletter_subscriber.subscription_requested` (published for
   each request), and a signed-in customer, whom Spree confirms on the spot,
   on `newsletter_subscriber.verified`. On a double opt-in list Klaviyo
   emails its confirmation and adds the address once the link is clicked; on
   a single opt-in list Klaviyo adds the address at once and nobody sends a
   confirmation. While the integration is active, Spree's own confirmation is
   not sent either way (Key Decision 9). Removal
   (`newsletter_subscriber.deleted`: the customer opting out, staff deleting
   the subscriber, or an erasure) is a bulk unsubscribe, which revokes
   email-marketing consent in Klaviyo, not only list membership. Consent in
   Klaviyo belongs to the account, not the list, so stores sharing one
   Klaviyo account share it: an unsubscribe sent for one store stops
   marketing email from all of them.
   **Accepted trade-offs:** a single opt-in list subscribes addresses nobody
   has confirmed. That is the merchant's choice, not Spree's (decided
   2026-11-03): activation does not check the setting, and the docs explain
   both settings and say which markets expect double opt-in. A store
   upgrading from 1.x with a single opt-in list gets exactly that from the
   upgrade on, since Spree's confirmation stops. A guest's subscriber row in
   Spree stays unverified, and a confirmation made in Klaviyo sets neither
   the customer's `accepts_email_marketing` nor a Spree consent record.
   Klaviyo is the record of marketing consent for these stores (Key Decision
   20 explains why nothing flows back). On a double opt-in list, a signed-in
   customer who ticks "email me" also confirms through Klaviyo's email, since
   the list's setting covers every source. If Klaviyo cannot be reached,
   nobody gets a confirmation until the job succeeds; after its last attempt
   it is reported. Klaviyo resends its confirmation when an address that is
   still waiting for one signs up again: two sign-ups seconds apart got two
   emails (test account, 2026-11-05).
   Rejected: refusing a single opt-in list at activation, or checking the
   list before each subscribe (a merchant may want single opt-in, and an
   upgraded store's integration is already active, so an activation check
   would never run for it); Spree confirming and Klaviyo recording the
   result, either as a plain subscribe (a double opt-in list then sends a
   second confirmation, and the merchant cannot design the email in Klaviyo)
   or as a historical import with `consented_at` (no second email, but
   Klaviyo then skips the list's "Added to list" flows, the usual
   welcome-series trigger, silently). The `klaviyo.subscribed` metafield is
   not ported.
8. **Klaviyo's standard ecommerce metric names** (decided 2026-11-03), with
   the property names its guide recommends (`OrderId`, `Items[]` with
   `ProductID`, `SKU`, `ProductName`, `Quantity`, `ItemPrice`, `RowTotal`,
   `ProductURL`, `ImageURL`, `Categories`; `ItemNames`, `DiscountCode`,
   `DiscountValue`, `BillingAddress`, `ShippingAddress`), so Klaviyo's flow
   templates, metric mapping and lifetime-value reports recognise the data:

   | 1.x | 6.0 |
   |---|---|
   | Order Completed | Placed Order |
   | (none) | Ordered Product, one per line |
   | Package Shipped | Fulfilled Order, one per package |
   | Order Cancelled | Canceled Order |
   | Reimbursement Paid | Return Refunded, Spree's own name (Key Decision 12) |
   | Checkout Started | Started Checkout, from the storefront (Key Decision 16) |

   Refunded Order, Klaviyo's standard refund metric, is not sent (Key
   Decision 12).
   **Accepted trade-off:** a store upgrading from 1.x re-points the flows,
   segments and templates built on the old metrics, which keep their history
   in Klaviyo but stop receiving. The upgrade guide gives the table above.
   Keeping the 1.x names was rejected because their properties were built on
   5.x models (taxons, reimbursements) and change shape anyway; a switch for
   legacy names was rejected because every event would then be built twice
   for as long as it existed. Fulfilled Order is sent per package, not per
   order, with that package's lines as its `value`, because a shipping email
   names one package's tracking; Klaviyo's guide defines it only as "when an
   order is sent to the customer".
9. **An active integration can take over customer emails; `spree_emails`
   only asks whether to send** (decided 2026-11-03).
   - `Spree::Integration#replaced_customer_emails` returns the template keys
     (`Spree.editable_email_templates`, e.g.
     `spree/order_mailer/confirm_email`) of the customer emails the
     integration sends in Spree's place. The base returns `[]`.
   - `Spree::Store#sends_customer_email?(template_key)` is true when the
     store's `send_consumer_transactional_emails` is on and no active
     integration of the store lists the key.
   - Every customer email subscriber in `spree_emails` asks
     `store.sends_customer_email?('<its template key>')` instead of reading
     the store preference; it knows nothing about integrations or Klaviyo.
     Staff, store-owner and seller emails are not affected.

   Klaviyo always lists the newsletter confirmation
   (`spree/newsletter_mailer/email_confirmation`) while active (Key
   Decision 7), and four integration switches, all off by default, list the
   order emails. Each switch's flow is triggered by an event Klaviyo
   receives exactly when Spree would have sent the email it replaces, so
   turning a switch on neither adds nor loses an email:

   | Switch | Spree emails replaced | Klaviyo event, sent on |
   |---|---|---|
   | Order confirmation | `spree/order_mailer/confirm_email`, `spree/order_group_mailer/confirm_email` | Placed Order, on `order.placed` (not grouped) or `order_group.completed` |
   | Cancellation | `spree/order_mailer/cancel_email` | Canceled Order, on `order.canceled` |
   | Shipping | `spree/fulfillment_mailer/fulfilled_email` | Fulfilled Order, on `fulfillment.fulfilled` |
   | Refund | `spree/return_mailer/refunded_email` | Return Refunded, on `return.refunded` |

   Staff can choose not to notify the customer when placing an order for
   them, canceling it or marking a package shipped, and Spree then skips its
   email. Placed Order, Canceled Order and Fulfilled Order carry that choice
   as `NotifyCustomer`, and the docs tell merchants to filter each flow that
   replaces a Spree email on it, since a flow cannot know otherwise.

   An email whose link carries a token Spree must later redeem is never
   taken over: password reset, data export and data request confirmation,
   digital downloads, the payment link (which nothing in Spree sends today)
   and company invitations stay Spree's, because Klaviyo cannot redeem the
   token. The newsletter confirmation is the one exception, because Klaviyo
   runs the whole confirmation itself and Spree's token is never sent.
   **Accepted trade-offs:** a switch turned on before the matching Klaviyo
   flow is live leaves customers with no email, so each switch's help text
   says to build the flow first; "Resend confirmation" in the dashboard sends
   nothing for an email Klaviyo has taken over; and a storefront that sends
   its own emails from webhooks (the reference storefront's Resend option)
   is not governed by this and is turned off in the storefront.
   Rejected: per-email switches in the store's own email settings (more
   general, but a core and dashboard feature deserving its own plan, which
   would push this one to 6.1), and taking over the newsletter confirmation
   only (merchants moving order emails to Klaviyo could still only turn off
   every Spree customer email, password resets included).
10. **Every event carries a `unique_id` from Spree**, so a retried job never
    records an event twice (Klaviyo keeps the first event per profile,
    metric and `unique_id`; it has no idempotency header). Placed Order uses
    the purchase's prefixed id: the order's, or the order group's for a
    split checkout (Key Decision 11). Canceled Order uses the canceled
    order's id, which for an ordinary order is the Placed Order's, so Klaviyo
    subtracts the cancellation from lifetime value (it does so only when the
    `unique_id`s match). Ordered Product uses the line item's id, Fulfilled
    Order the fulfillment's, and Return Refunded the id of the
    `return.refunded` event, one per refund of a return (Key Decision 12).
    **Accepted trade-off** (decided 2026-11-03): in a split checkout each
    seller's order carries its own id, so every seller's cancellation
    reaches Klaviyo and its flow, but it does not match the group's Placed
    Order, so lifetime value in Klaviyo is not reliable for marketplace
    stores; the docs say so. Rejected: the group's id for every seller's
    cancellation (Klaviyo would drop the second seller's cancellation, and
    its email with it), and the group's id for the first cancellation only
    (ordering logic for a figure that stays wrong after the second). 5.x
    sent no `unique_id`, so every retried job duplicated revenue in Klaviyo.
11. **Placed Order is sent once per purchase.** An ordinary order sends it
    from `order.placed`. A split checkout (marketplace) sends one from
    `order_group.completed` with the group's number, total and every line,
    timed at the cart's `completed_at` (an order group has no completion time
    of its own), and its child orders send none, so a buyer's one purchase
    starts one post-purchase flow, as Spree's own group confirmation does.
    Fulfilled Order and Canceled Order stay per order, as the sellers' own
    emails do.
12. **Refunds reach Klaviyo only as Return Refunded, Spree's own metric**
    (decided 2026-11-03). It is sent on `return.refunded`, the event Spree's
    refund email is sent on, which the return refund workflow publishes once
    the money has moved; like the email, it is skipped when the return's
    refunded total is zero. One refund of a return is one event, however
    many payments the money went back to, and a return refunded twice sends
    two. It carries the return's number, the order's `OrderId`, the returned
    lines (`Items[]`) and the refunded total as properties, not as `value`:
    it triggers the refund email of Key Decision 9 and is not revenue. 5.x
    did the same with Reimbursement Paid, sent on the event that sent Spree
    5's refund email, with no `value`.
    **Accepted trade-offs:** refunds never reduce lifetime value in Klaviyo,
    as in 5.x; refunds made outside a return (a cancellation's, or one staff
    make by hand) are not sent, as in 5.x and as Spree sends no refund email
    for them. Rejected: Klaviyo's standard Refunded Order. Klaviyo counts it
    against lifetime value only when its `unique_id` is the Placed Order's,
    and then keeps only the first, so a second partial refund, or a second
    seller's refund in a split checkout, would be dropped and lifetime value
    would stay wrong anyway; and it cannot replace Spree's refund email,
    because Spree records one refund per payment and also for cancellations
    and manual refunds.
13. **Subscribers are thin and the work runs in the gem's jobs.** A
    subscriber checks that the store has an active Klaviyo integration and
    enqueues a job with the integration and the record (GlobalID, never a
    class name from a string; 5.x `constantize`d one). Subscription jobs take
    the email address instead of the subscriber row: after
    `newsletter_subscriber.deleted` the row is gone, and `Spree::BaseJob`
    discards a job whose record cannot be loaded without a word. A 429 is
    rescheduled after Klaviyo's `Retry-After` with jitter and no attempt
    limit, since the limit always lifts and rescheduling holds no worker; an
    unsubscribe is the exception and gives up 20 minutes after it was
    enqueued, so it always reaches Klaviyo before an erasure's deletion (Key
    Decision 18). A 5xx, a timeout or a failed connection (the SDK raises
    `KlaviyoAPI::ApiError` with no status for a timeout and 0 for a failed
    connection) is retried with polynomial backoff, five attempts, then
    reported through `Rails.error`; any other 4xx is reported once and not
    retried, because the same body cannot succeed. A report carries the
    status and Klaviyo's error codes and titles, never
    `ApiError#message`, which appends the response headers and body (Key
    Decision 15). Nothing in checkout, sign-up or newsletter requests calls
    Klaviyo.
14. **No circuit breaker, the same as Stripe and PayPal.** Timeouts and job
    retries only; outage handling, if wanted, goes into core.
15. **No request or response bodies in logs or error reports.** Bodies carry
    names, emails and addresses. The SDK's `debugging` (which logs them)
    stays off; the gem logs method, path, status and duration.
16. **Browsing events and Started Checkout come from the storefront's
    Klaviyo script** (decided 2026-11-03; Started Checkout moved there the
    same day). The Next.js storefront (`spree/storefront`) does not load
    Klaviyo's onsite script itself: the merchant loads it from a Google Tag
    Manager tag, with the account's six-character public key, so the
    shopper's cookie consent gates it (decided 2026-11-12; an earlier
    `KLAVIYO_COMPANY_ID` variable that loaded it unconditionally was
    dropped). Calls made before the tag loads do nothing and are not queued,
    so nothing from before consent is sent once the shopper accepts; the cost
    is an event fired in the moment before the tag loads, typically the
    landing page's Viewed Product. The merchant must not add Klaviyo's own
    Viewed Product tag, which would record each view twice. The storefront
    sends Viewed Product and Added to Cart (Active on
    Site is automatic), and Started Checkout where Klaviyo's integration
    guide places it: when the checkout page opens for a shopper Klaviyo
    already knows (where the storefront fires GTM's `begin_checkout`), or
    when the shopper enters their email at checkout. It identifies the
    shopper by email on sign-in, sign-up and checkout email entry, which
    joins the browser's anonymous history to the profile the server writes;
    only the browser holds Klaviyo's visitor cookie. The reference
    storefront has no newsletter sign-up form, so a storefront that adds one
    makes the same call when the form is submitted (decided 2026-11-05).
    Started Checkout cannot come from the server: a 6.0 cart has no
    state that changes when checkout opens (its step is computed from what is
    still missing), opening checkout only reads the cart, and signing in
    copies the customer's email and saved addresses onto the cart, so no
    server-side event tells "in checkout" from "has a cart".
    **Accepted trade-offs:** Klaviyo is configured in two places (keys in the
    dashboard, public key in the GTM tag); onsite tracking needs GTM; ad
    blockers and declined cookie consent drop browsing events and some Started
    Checkout events, and with them some abandoned-checkout emails; a custom
    storefront sends
    these events itself. Rejected: server only (no Viewed Product or browse
    abandonment, which 5.x had); server-side Added to Cart (anonymous carts,
    the majority, have no identity Klaviyo can use); Started Checkout on
    `cart.updated` (adding a line only touches the cart, which publishes
    nothing, and a signed-in shopper's cart has an email and addresses before
    checkout); and a new Store API call marking checkout as started (a core
    endpoint, event and SDK method in a patch release, which every storefront
    would still have to call).
17. **Payloads are value objects** (`SpreeKlaviyo::Profile`,
    `SpreeKlaviyo::MetricEvent`), one instance per Klaviyo object with
    `from_*` constructors, in the `SpreeEasyPost::TrackerEvent` style; they
    build the bodies the SDK takes. The 5.x presenters, which included
    storefront and image helpers, are gone. Amounts are `BigDecimal` until a
    payload is built; Klaviyo takes JSON numbers, so each amount is rounded
    to the currency once and converted there, with `value_currency` set,
    which 5.x never sent.
18. **Erasure deletes the profile in Klaviyo** (decided 2026-11-03). The gem
    registers on the `customers.anonymize.after_anonymize` hook and requests
    a profile deletion by the person's original email
    (`POST /api/data-privacy-deletion-jobs`) through every active Klaviyo
    integration, because customers belong to every store and an erasure need
    not name one. Core gives the workflow a public `original_email` reader,
    documented as the hook contract for releasing third-party data: by the
    time the hook runs, the customer record holds the tombstone address. The
    same erasure deletes the person's newsletter subscriptions, whose
    unsubscribe jobs carry the original email; the deletion job is enqueued
    30 minutes later and an unsubscribe gives up after 20 (Key Decision 13),
    so the unsubscribes reach Klaviyo first, because Klaviyo's docs do not say
    whether an unsubscribe for an address it has deleted creates a profile
    again. Profile sync checks at run time whether the customer is
    anonymized, so neither the `user.updated` an erasure publishes nor an
    older one still queued can write the tombstone over the real profile
    (`external_id` would match it). A job whose email is at the tombstone
    domain (`Spree::Customers::Anonymize::REDACTED_DOMAIN`) sends nothing, so
    a later event on an erased person's retained order (a cancellation, a
    shipment) cannot create a profile for the tombstone. **Accepted
    trade-offs:** the key needs Klaviyo's `data-privacy:write` scope, which
    1.x keys lack; until the merchant adds it, deletions fail with 403 and
    are only reported through `Rails.error`, so the docs and the upgrade
    guide say so plainly. Deletion removes the profile's whole Klaviyo
    history and cannot be undone, which is what erasure asks for. Stores
    sharing one Klaviyo account each send the request.
19. **Providers never decorate core models.** No `BaseController`,
    user-class or `Publishable` decorators; everything hangs off events, the
    workflow hook and the integration. The 5.x visitor-id decorators and
    `SpreeKlaviyo::Current` go with the Rails storefront.
20. **Spree does not learn about consent changes made in Klaviyo.** A person
    who unsubscribes from a Klaviyo email, or confirms a sign-up there, is
    not reflected in Spree. Klaviyo sends the marketing email and its
    consent governs sending; its consent webhooks are open only to Advanced
    KDP accounts and app partners. Syncing back is a later release, through
    a Klaviyo flow's webhook action or polling Klaviyo's events, if
    merchants need Spree's subscriber list to match.
21. **Back in stock is not ported.** Klaviyo answers a back-in-stock
    subscription for a variant it has no catalog entry for with 404, and
    5.x never synced a catalog, so its call could not work; nothing in 6.0
    calls it. A catalog sync (Klaviyo's Catalogs API, items and variants
    with stock) is its own plan when merchants ask for product feeds or
    back-in-stock flows.
22. **Not in this release:** SMS consent and phone numbers on profiles
    (Klaviyo rejects the whole import for a number that is not E.164), more
    than one list per store (per market or locale), and a Started Checkout
    link that restores the cart on another device (it needs a storefront
    route that sets the cart token; `CheckoutURL` opens the storefront's cart
    page).

### Integration

`Spree::Integrations::Klaviyo < Spree::Integration`:

- Preferences: `klaviyo_private_api_key` (`:password`, stored in the
  encrypted `secret_preferences` column) and `default_newsletter_list_id`
  (`:string`), both needed to activate (not to save), then the four booleans
  of Key Decision 9: `sends_order_confirmation`, `sends_order_cancellation`,
  `sends_shipping_confirmation`, `sends_refund_confirmation`, default false,
  and `use_database_ids_as_external_ids` (Key Decision 6), default false.
- The switches' labels and help text are dashboard translations,
  `admin.preferences.<key>` and `admin.preferences.<key>_description`, in
  every locale under `packages/dashboard/src/locales/`: the generated form
  reads its strings from there, not from the gem. Each description names the
  Klaviyo event to build the flow on, says to build it before turning the
  switch on, and mentions the `NotifyCustomer` filter.
- `replaced_customer_emails` returns the newsletter confirmation's key plus
  the keys of the switches that are on (Key Decision 9's table).
- `integration_group` `marketing`; `logo_url`
  `https://spreecommerce.org/docs/images/integrations/logos/klaviyo.png`;
  `docs_url` the marketing guide; a `description` fallback and its
  `spree.integrations.klaviyo.description` translation.
- `can_connect?` reads the list (`GET /api/lists/:id`, scope `lists:read`)
  and puts the reason in `connection_error_message`: which setting is
  missing, or Klaviyo's own detail for a bad key, a missing scope or an
  unknown list.
- API verbs the jobs call: `import_profile(profile)`, `subscribe(email)`,
  `unsubscribe(email)`, `create_event(metric_event)`,
  `request_profile_deletion(email)`. Each builds its per-integration SDK
  client (Key Decision 5) and lets `KlaviyoAPI::ApiError` (status,
  headers, body) reach the job, which decides about retrying from its status
  and `Retry-After` and reports without the body (Key Decision 13).

### Core: integrations taking over customer emails

```ruby
# spree_core
class Spree::Integration
  # Template keys (Spree.editable_email_templates) of the customer emails this
  # integration sends in Spree's place while it is active.
  def replaced_customer_emails = []
end

class Spree::Store
  def sends_customer_email?(template_key)
    prefers_send_consumer_transactional_emails? &&
      active_integrations.none? { |integration| integration.replaced_customer_emails.include?(template_key) }
  end
end

# spree_emails, e.g. Spree::OrderEmailSubscriber#send_customer_confirmation
return unless order.store.sends_customer_email?('spree/order_mailer/confirm_email')
```

`Spree::Store#active_integrations` reads the request-cached
`Spree::Current.integrations` when the store is the current one and the
store's active integrations otherwise, the rule
`Spree::IntegrationBackedProvider.active_integrations` implements today; it
moves to the store and the provider concern calls it. Email subscribers run
in jobs, where no store is current. Every customer email subscriber in
`spree_emails` switches to `sends_customer_email?` with its own template key;
a spec walks the registered customer email templates and asserts each one's
subscriber asks for its key, so a new customer email cannot skip it. The
payment link's template is left out of that spec, because nothing in Spree
sends it.

### What syncs

| Spree trigger | Klaviyo call |
|---|---|
| `user.created`, `user.updated` (customers publish under the `user` prefix) | profile import (skipped for an anonymized customer) |
| `newsletter_subscriber.subscription_requested`, `newsletter_subscriber.verified` | bulk subscribe to the configured list, by email |
| `newsletter_subscriber.deleted` | bulk unsubscribe (consent revoked), by email |
| `order.placed` (not grouped) / `order_group.completed` | profile import from the order, Placed Order, one Ordered Product per line |
| `fulfillment.fulfilled` | Fulfilled Order (that package) |
| `order.canceled` | Canceled Order |
| `return.refunded` | Return Refunded (skipped when nothing was refunded) |
| `customers.anonymize.after_anonymize` hook | profile deletion request through every active Klaviyo integration, 30 minutes later |

No job sends anything for an email at the tombstone domain (Key Decision
18). Started Checkout and the browsing events come from the storefront (Key
Decision 16). Address changes have no event in 6.0; a customer's location is
refreshed from the bill address on their next order.

### Profiles

`SpreeKlaviyo::Profile.from_customer(customer)` and `.from_order(order)`:
email, first and last name, `external_id` for a customer (the prefixed id,
or the database id when the integration's switch is on; Key Decision 6),
and `location` from the bill address (address lines, city, region, postcode,
country).

### Events

`SpreeKlaviyo::MetricEvent` has one constructor per metric (`.placed_order`,
`.ordered_product`, `.fulfilled_order`, `.canceled_order`,
`.return_refunded`) and builds the `POST /api/events` body: the metric name,
the profile inline by email, `time` from the record (`completed_at`, the
cart's for a split checkout; `canceled_at`; the fulfillment's
`fulfilled_at`; for Return Refunded, when the event was published),
`unique_id` (Key Decision 10) and the properties of Key Decision 8. Placed
Order, Ordered Product, Fulfilled Order (the package's lines) and Canceled
Order carry `value` and `value_currency`; Return Refunded carries its amount
as a property (Key Decision 12). Placed Order, Canceled Order and Fulfilled
Order carry `NotifyCustomer` from the Spree event (Key Decision 9).
Properties carry what a Klaviyo email needs without calling back: lines with
images and product URLs, totals, discount codes, addresses, for a
fulfillment its tracking number and URL, and for a refunded return its
number, lines and refunded total, so the emails of Key Decision 9 can be
built entirely in Klaviyo. Product URLs follow the convention the Google feed
and the emails already use, `#{store.storefront_url}/products/#{product.slug}`;
images use `spree_image_url`; categories come from the product's
categories.

### Storefront (`spree/storefront`)

- No Klaviyo variable: the script comes from the store's GTM container
  (`GTM_ID`), and `.env.example` says so (Key Decision 16).
- `src/lib/analytics/klaviyo.ts` beside `gtm.ts`, called from the same
  places: Viewed Product where `trackViewItem` is called, Added to Cart where
  `trackAddToCart` is, and Started Checkout where `trackBeginCheckout` is
  when the cart already has an email, otherwise once the checkout email is
  saved. Item properties use the names of Key Decision 8. Started Checkout
  follows Klaviyo's guide: `$event_id` is the cart's id with the Unix time,
  `$value` the cart total, plus `ItemNames`, `Items[]` and `CheckoutURL`,
  the storefront's cart page (Key Decision 22).
- `identify({ email })` after sign-in and sign-up, and when checkout takes
  an email (before Started Checkout). There is no newsletter sign-up form to
  call it from (Key Decision 16).
- Every call does nothing until GTM has loaded the script.

## Constraints on Current Work

- A customer email in `spree_emails` (or any gem adding one) decides whether
  to send with `store.sends_customer_email?(template_key)`, never by reading
  `send_consumer_transactional_emails` directly; once step 1 lands, the spec
  over registered templates enforces it.
- An email whose link carries a token Spree must later redeem must never
  appear in any integration's `replaced_customer_emails`.
- No new feature work in the standalone `spree/spree_klaviyo` repository;
  critical 5.x fixes only.
- Don't rename `Spree::Integrations::Klaviyo` or its preferences; they are
  stored data.
- Every Klaviyo event carries a `unique_id` derived from a Spree record or
  the Spree event that triggered it. A new event without one is a bug.
- Never call the SDK through `KlaviyoAPI.configure` or its convenience
  wrappers; they hold one key for the whole process.
- Don't set `KLAVIYO_API_REVISION` or `API_REVISION` in a host app: the SDK
  reads either one in place of the revision its version pins, and a generic
  `API_REVISION` meant for something else would change it silently.
- Don't give this gem network protection the other provider gems lack, such
  as a circuit breaker.
- Nothing in a request path (checkout, sign-up, newsletter) calls Klaviyo
  synchronously.
- A change to when `order.placed`, `order_group.completed`, `order.canceled`,
  `fulfillment.fulfilled`, `return.refunded` or the newsletter events are
  published, to their `notify_customer` metadata, or to the
  `customers.anonymize.after_anonymize` hook, is checked against this gem:
  the switches of Key Decision 9 rely on Klaviyo's events firing exactly when
  Spree's emails would.
