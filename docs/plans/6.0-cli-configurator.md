## Summary

Add a command group to `@spree/cli` that treats a YAML file as the desired configuration of a store and reconciles a live instance against it through the Admin API: `diff` shows what would change, `deploy` applies it, `introspect` writes the live configuration back out as YAML. Records are matched on natural keys (slug, code, SKU, name), never on prefixed IDs, so the same file provisions a fresh local project, a staging environment and a hosted production store. Today the only way to shape an environment is Ruby: `db:seed`, `spree:load_sample_data`, the first-run provisioning service, and sixty lines of Ruby embedded as strings in the dashboard's Playwright global setup. A declarative file is reviewable in a pull request, runs from CI against any instance, and needs no Ruby on the caller's machine, which matters because the default install is an API-only Docker app and headless teams often never open the Rails side. Every project scaffolded by `create-spree-app` ships a skeleton `spree.config.yml`, and `spree init` deploys it during setup. The dashboard e2e suite is the first consumer, so the tool is exercised on every CI run before a single spec starts.

The longer goal is that store setup stops being Ruby at all. Ruby keeps only what has no API by design (the store row, the admin role, the first admin and the first API key). The per-store defaults the seeds create today, and the country-shaped defaults first-run setup builds, become configuration files deployed by the same engine. The format and the engine are TypeScript over the Admin API, so they carry over unchanged when the server side moves away from Rails.

## Key Decisions (do not deviate without discussion)

- **Built on the Admin API, run from the CLI, never in-process Ruby.** An in-process `rake spree:config:apply` would be faster and could call workflows directly, but it only works where you can run Rails, cannot target a hosted instance, and would not exercise the API. The whole point is a file that works from outside the app. The existing `spree api` transport (credential layers, `@spree/admin-sdk`, retries, idempotency keys, `X-Spree-Store-Id`) is reused unchanged.
- **YAML is the canonical format; JSON is accepted for free.** YAML carries comments and block text and diffs cleanly, which a hand-edited, reviewed file needs. YAML is a superset of JSON, so a generated file may be JSON with no second code path. The CLI already depends on the `yaml` package. No `spree.config.ts` with a `defineConfig()` helper: that reintroduces configuration as code that needs a runtime, which is what this removes. Teams that want loops generate YAML and commit the output.
- **A published JSON Schema makes the file self-describing.** Every section is validated with Zod before any network call, and the same schemas emit a JSON Schema shipped with the CLI. `introspect` writes a `# yaml-language-server: $schema=` header so editors autocomplete and flag mistakes inline.
- **Records match on natural keys, never prefixed IDs.** IDs differ per environment; a slug or code does not. References between records (a product's category, a delivery method's zone) are written as the target's natural key and resolved by the CLI. The key table below is part of the contract; a resource without a stable, unique, human-readable key cannot be managed until it gets one.
- **Only bootstrap stays in Ruby seeds; per-store defaults become a file (decided 2026-09-14, revised 2026-10-01).** The store row, the immutable admin role, the first admin user and the first API key have no API by design (`6.0-store-context-and-first-run-setup.md`) and stay in `Spree::Seeds`. Everything `Spree::Seeds::StoreResources` creates (tax categories, channels, roles, digital delivery, payment methods, product types, customer groups, the reason lists, commission rates, seller requirements, saved reports, allowed origins) becomes a defaults file in the configurator format, shipped with `@spree/config` and deployed by the engine. The 2026-09-14 version kept `Spree::Seeds::All` whole because "a Rails app must seed without Node"; that promise is dropped for 6.0. Accepted trade-off: a Rails-only install that never runs the CLI or the dashboard setup screen starts with an empty store until something deploys the defaults file. The file lives with the engine, not in `spree_core`, because no Ruby code reads it.
- **Country-shaped defaults are a template the engine deploys (decided 2026-10-01).** The default market, warehouse, delivery zones and pickup that `Spree::Stores::ProvisionDefaults` builds from the merchant's country, currency and locale become a template filled with those three answers and deployed through the engine, by the setup screen, `spree init` and hosted signup alike. `ProvisionDefaults` is deleted once every caller has moved. Accepted trade-off: setup runs the engine in the browser and makes several Admin API calls where one Ruby transaction ran before, so a setup interrupted midway leaves a partly provisioned store; a rerun of the same deploy finishes it, since the engine only creates what is missing.
- **Reconciliation is client-side in the first release.** For each section the CLI lists live records filtered on the natural key, then creates, updates or skips. This needs no new endpoints beyond gaps the key audit finds (a missing Ransack allowlist entry, a missing key attribute). Server-side bulk upserts by natural key are a later optimisation for hot sections, added to the API only once the client-side path shows where they pay off. `prices/bulk_upsert` and `stock_levels/bulk_upsert` are used where they already exist.
- **Transaction data is out of scope permanently.** Orders, payments, fulfillments, returns, seller payouts and transfers are history, not configuration. They stay in Ruby sample data and in the e2e Ruby bootstrap. Customers are the one exception (see Design Details): they are reference data for promotions and groups, the CSV import already upserts them on email, and the e2e suite needs one.
- **The store's own country, currency, locale and default market stay with first-run setup (decided 2026-10-02).** Markets match on `name`, and the bootstrap market is created before anyone has said where the shop is, so a template could not move it to another country: it would add a second market and leave the first behind. Setting the store's country is part of the store row, which is bootstrap, so the setup endpoint (and, on scripted installs, the seed reading `STORE_COUNTRY`, `STORE_CURRENCY` and `STORE_LOCALE`) relocates the store and its default market in Ruby, as `Spree::Store#relocate`. The country template builds everything else: warehouse, delivery profile, zones, methods, pickup and the default package type.
- **Sample data stays on the setup request and waits for provisioning (decided 2026-10-02).** The setup endpoint still accepts `sample_data` and queues the loader, but the loader runs only once the store is provisioned (`Spree::Store#provisioned?`: a first-party default warehouse exists) and retries until then, so it never starts before the browser has deployed the template. A separate sample-data endpoint and a resume-on-sign-in check were weighed and rejected as more surface than the flow needs. Accepted trade-off: a setup whose deploy never finished leaves an unprovisioned store with nothing to resume it; `spree config provision` or redeploying from the setup screen finishes it.
- **Built-in saved reports are created by the store itself (decided 2026-10-02).** The twenty preset reports are product definitions with translated names and a read-only `seeded` flag, not merchant configuration, so they leave the seeds for a store callback, the way the store already creates its default channel. They are not a configurator section. Accepted trade-off: about sixty lines stay in Ruby.
- **Sample data requires a provisioned store (decided 2026-10-02).** `spree:load_sample_data` refuses on an unprovisioned store with a message naming `spree config provision`; it no longer runs the seeds itself. Every Node caller (setup screen, `spree init`, the e2e and SDK integration setups, the worktree template) provisions first, and Ruby specs that need seeded rows use factories. Accepted trade-off: loading sample data on a bare Rails app now needs the CLI.
- **The engine is a library first and a command second, in its own `@spree/config` package (decided 2026-09-14, revised 2026-10-01).** The first release put the engine under `packages/cli/src/config/`, exported as `@spree/cli/config`, with a rule to split it out when a third consumer appeared. The setup screen (country template) and a future TypeScript server are that consumer, so the engine, its schema and its sections move to `packages/config` as `@spree/config`, and the CLI, the dashboard setup screen and the e2e global setup import it. Putting it in `@spree/admin-sdk` stays rejected: the SDK is a thin client and must not pull `yaml` and `zod` into every consumer's bundle. Accepted trade-off: one more package to version and release.
- **Deletes are opt-in per section (decided 2026-09-14).** `deploy` only creates and updates; live records missing from the file are deleted only in sections named in `--prune <sections>`, and `--fail-on-delete` refuses any plan containing a delete. Full sync with a guard flag was rejected because a file that declares only delivery zones would then wipe every other section unless the operator remembered the flag. Accepted trade-off: a stale record can linger in staging unnoticed; `diff` reports live records absent from the file as "not managed" so they are visible.
- **Some sections can never be pruned (decided 2026-10-01).** `--prune` refuses `store` (never deleted), `customers` (customer accounts belong to the installation, not one store, so the Admin API's customer list is not store-scoped and a prune would delete other stores' customers) and `sellers` (a seller carries orders, payouts and transfers). The refusal lives in the engine, so code calling it directly is held to it too.
- **Stock in the file is opening stock (decided 2026-10-01).** Quantities are written when a variant is created and never compared or rewritten afterwards: counts move with sales and receipts, and a deploy that reset them would overwrite real inventory. Ongoing stock belongs to the dashboard and the Admin API.
- **The file manages only what it can name (decided 2026-10-01).** Where a live list mixes records the file can express with records it cannot (a channel's or pickup method's seller warehouses, a delivery zone's postal-code members), the comparison sees only the first kind and every write carries the second through unchanged, so `introspect` followed by `deploy` never removes data.
- **Keys are written in the form the store saves (decided 2026-10-01).** Slugs and permalinks must already be lowercase and hyphenated, because the API normalises them on save and a key written any other way would never match its own record. Customer emails are lower-cased on load. Rich text (`description`) is HTML, compared against the stored markup with whitespace and entity escaping ignored, and `introspect` writes the HTML, never the plain-text rendering.
- **A deploy checks read scopes as well as write scopes (decided 2026-10-01).** Each section declares the scope its listing needs; a deploy needs the write scope of every present section and the read scope of every section it lists, including the targets of its references. Stock locations are the case that forced it: written with `write_settings`, listed with `read_stock`.
- **The first release covers configuration, catalog and customers (decided 2026-09-14).** Products with variants, prices and stock, and customers, are in scope from the start, because the dashboard e2e bootstrap needs them and dogfooding without them is theatre. Configuration-only was rejected as leaving most of the Ruby bootstrap in place. Accepted trade-off: products are the largest section and most of the implementation effort.
- **Every new project ships with a config file, and project setup deploys it (decided 2026-09-14, revised the same day).** `create-spree-app` writes `spree.config.yml` at the project root and `spree init` runs `spree config deploy` against it right after seeding, non-interactively, so a fresh project's shape is in a file from day one and the same file is what CI later deploys to staging. The file ships as a **skeleton**: the version, the schema pointer and commented examples of every section, with nothing pre-filled that first-run setup owns. The store name, country, currency, locale and the default market are answered on the setup screen (or through `ADMIN_EMAIL` / `STORE_COUNTRY` on scripted installs), and a pre-filled `store` or `markets` section would fight that screen: deployed before the merchant opens it, and reverting their answers on the next deploy. The docs teach `spree config introspect` as the way to capture the store into the file once setup has run. Deploy needs write scopes, and the project's auto-minted key is `read_all` by design (`5.5-admin-api-cli.md`), so `spree init` mints a short-lived secret key, deploys, and revokes it. Accepted trade-off: project setup now has an HTTP step against the freshly booted container and fails loudly if the API is not up.
- **Project setup asks nothing the setup screen already asks (decided 2026-09-14).** `create-spree-app` gains no store prompts and `spree init` stops prompting for an admin email and password; the one-time setup link the seed prints is the default path, and `--admin-email` / `--admin-password` stay for scripted installs. Sample data needs an admin to own its imports, so the setup screen gains a "Load sample data" checkbox: the setup request accepts `sample_data` and enqueues a background job that runs the loader once the admin exists. `create-spree-app` and `spree init` stop asking about sample data; `SPREE_SAMPLE_DATA` and `spree sample-data` stay for scripted installs and for loading it later.
- **The `store` section carries the store's name, contact addresses and preferences; markets carry currency, locale and country (decided 2026-09-14).** The Admin API's store endpoint permits none of `default_currency`, `default_locale`, `default_country` or `supported_currencies`, and `6.0-store-context-and-first-run-setup.md` rules that a store's country changes through its market. Markets keep `name` as their key: adding a `code` column was weighed in the audit and rejected as a schema change with one consumer.
- **Key hardening: validations now, unique indexes later (decided 2026-09-14).** The audit found six keys with no uniqueness guard (tax rate, delivery method, payment method and price list names, webhook endpoint URL, API key name), five guarded by validation only, and the four reason lists guarded by a database index only, where a duplicate 500s instead of 422. Store-scoped uniqueness validations (`validates_store_uniqueness`) are on main for them, so duplicates fail with a usable error, and the engine refuses to reconcile any entry whose key matches more than one live record. Unique indexes need a dedupe task for installations that already hold duplicates, so they ship as their own follow-up.
- **First release ships the sections the e2e suite and the scaffold need (decided 2026-09-14).** store, channels, markets, customer groups, tax categories, delivery zones, delivery methods, stock locations, suppliers, categories, products (with variants, prices and stock), customers and sellers. The remaining sections of the key table plug into the same engine next. Since 2026-10-01 they are ordered by what the defaults file needs: roles, payment methods, product types, the reason lists, commission rates, seller requirements and allowed origins first (they replace `StoreResources`), then tax rates, delivery profiles, option types, collections, price lists, custom field definitions, webhook endpoints, api keys and integrations. The audit's per-section notes are recorded in the natural-key table so nothing has to be rediscovered.
- **Section attributes are derived from the Admin OpenAPI spec (decided 2026-10-01).** Each section's writable attributes come from the request body the generated `admin.yaml` documents for its endpoint, which the CLI already bundles; only the file-shaped parts (references by key, prices by currency, stock by warehouse, preferences without the `preferred_` prefix) stay hand-written. The first release's hand-written Zod and field lists cost about 100 lines per section and need a drift test per preference list, which does not scale to thirty sections. Accepted trade-off: request-body specs must be complete before a section can derive from them (the store endpoint documents 5 of its ~40 permitted attributes today), so completing them comes first.
- **The command noun is `config` (decided 2026-09-14).** `spree config validate | diff | deploy | introspect`, beside `spree api` and `spree auth`. Top-level verbs were rejected because `spree deploy` next to `spree dev`, `spree build` and `spree init` reads as deploying the application; `spree store` was rejected because it names one section of the file.

## Design Details

### Command surface

```bash
spree config diff       --config store.yml                      # dry run, exit 0 when nothing would change
spree config deploy     --config store.yml                      # diff, confirm, apply; non-TTY skips the prompt
spree config deploy     --config store.yml --prune products,categories   # allow deletes in these sections
spree config deploy     --config store.yml --fail-on-delete     # CI guard: refuse if the plan contains any delete
spree config introspect --out store.yml --include channels,delivery       # live instance to YAML
spree config validate   --config store.yml                      # schema check only, no network
```

Credentials resolve exactly as for `spree api` (flags, then env, then project auto-mint, then profiles). A deploy needs write scopes for every section present in the file; the plan step checks the key's scopes first and names the missing ones with the `spree api-key create --scopes ...` remediation, before touching anything.

### File format

```yaml
# yaml-language-server: $schema=https://spreecommerce.org/schemas/config/6.0.json
version: 1

store:
  name: Acme Wholesale
  preferences: { guest_checkout: false }

markets:
  - name: United States
    currency: USD
    countries: [US]
    default: true
  - name: Europe
    currency: EUR
    countries: [DE, FR, NL, PL]

channels:
  - code: retail
    name: Retail
  - code: wholesale
    name: Wholesale
    customer_groups: [wholesale]

customer_groups:
  - name: Wholesale

tax_categories:
  - name: Default
    default: true
  - name: Non-taxable

delivery_zones:
  - name: Europe
    countries: [DE, FR, NL, PL]

delivery_methods:
  - name: Standard EU
    delivery_zone: Europe
    calculator:
      type: flat_rate
      preferences: { amount: 9.90, currency: EUR }

product_types:
  - name: Apparel
    option_types: [size, color]

option_types:
  - name: size
    label: Size
    values: [S, M, L, XL]
  - name: color
    label: Color
    values: [Red, Blue, Black]

categories:
  - permalink: clothing
    name: Clothing
    children:
      - permalink: clothing/t-shirts
        name: T-Shirts

products:
  - slug: classic-tee
    name: Classic Tee
    product_type: Apparel
    categories: [clothing/t-shirts]
    channels: [retail, wholesale]
    status: active
    variants:
      - sku: TEE-S-RED
        options: { size: S, color: Red }
        prices: { USD: 29.99, EUR: 27.90 }
        stock: { Warehouse: 100 }
```

Only sections present in the file are reconciled. A file with just `delivery_zones` and `delivery_methods` touches nothing else. Inside a present section, records absent from the file are left alone unless that section is listed in `--prune`.

### Natural keys

| Section | Key | Notes |
|---|---|---|
| `store` | singleton | update only; the row is bootstrap |
| `channels` | `code` | unique per store today |
| `markets` | `name` | unique per store; a `code` column was weighed and rejected (see Key Decisions) |
| `customer_groups` | `name` | unique per store (soft-delete aware) |
| `tax_categories`, `tax_rates` | `name` | |
| `delivery_zones`, `delivery_profiles`, `delivery_methods` | `name` | |
| `payment_methods` | `name` | credentials are never written from the file; see Secrets below |
| `stock_locations` | `name` | |
| `product_types` | `name` | unique per store, case-insensitive |
| `option_types` | `name` | values keyed on `name` within the type |
| `categories` | `permalink` | full path, so nesting is implied |
| `collections` | `permalink` | |
| `products` | `slug` | same key the CSV import uses |
| `variants` | `sku` | nested under the product; same key the CSV import uses |
| `prices` | `(sku, currency)` | via `prices/bulk_upsert` |
| `stock_levels` | `(sku, stock location)` | via `stock_levels/bulk_upsert` |
| `price_lists` | `name` | rows keyed on `sku` |
| `custom_field_definitions` | `(resource_type, namespace, key)` | |
| `roles` | `name` | the immutable admin role is skipped |
| `customers` | `email` | same key the CSV import uses |
| `allowed_origins` | `origin` | |
| `webhook_endpoints` | `url` | |
| `api_keys` | `name` | create only; the token is printed once and never written back |
| `integrations` | `type` | one per store per type by validation |
| `commission_rates` | `code` | |
| `seller_requirements` | `type` (or `name` for multi types) | |
| `return_reasons`, `claim_reasons`, `refund_reasons`, `order_cancellation_reasons` | `name` | |
| `sellers` | `slug` | |

Where a key is not yet unique in the database, a store-scoped validation guards it now and a unique index follows with its dedupe task; the engine never picks the first of several matches. Every key column must also be on the model's Ransack allowlist, since the client-side plan step filters on it.

### Reconciliation

1. **Load and validate.** Parse YAML, validate against the section schemas, resolve every reference to a key that exists either in the file or on the live instance. A dangling reference fails here, with the YAML path, before any write.
2. **Plan.** For each present section, in dependency order, list live records filtered on the natural key and classify every file entry as create, update or unchanged. Update compares only the attributes the file sets. Live records not in the file become deletes only when the section is in `--prune`.
3. **Show the diff.** Grouped by section, one line per record, attribute-level detail for updates. Machine-readable with `--format json` so CI can post it.
4. **Confirm and apply.** Interactive TTY asks once; non-TTY proceeds unless `--fail-on-delete` trips. Writes go through the Admin SDK with idempotency keys, sequentially across sections and in small parallel batches within a section. A 422 is reported against the YAML path of the offending entry with the API's own messages, and the run continues with the remaining entries so one bad row does not hide the rest.
5. **Report.** Counts per section and per outcome; non-zero exit if anything failed.

Section order follows the reference graph: store, channels, customer groups, tax, delivery zones and profiles, delivery methods, payment methods, stock locations, option types, product types, categories, collections, products (with variants, prices, stock), price lists, custom field definitions, roles, customers, origins, webhooks, integrations, marketplace sections, api keys. Prune runs in reverse order.

### Introspect

Reads every list endpoint of the requested sections, strips IDs, timestamps and computed fields, writes references as natural keys, and emits the file with the `$schema` header. Secrets never come back: payment method credentials, integration credentials and API key tokens are written as `# managed outside this file`. `--include` limits sections; the default is everything but products, since a large catalog belongs in the CSV import and export pipeline, not a hand-edited file.

### Secrets

The file is meant to be committed. Provider credentials (payment gateway keys, integration tokens) are set by the file only through `${ENV_VAR}` placeholders, which the CLI substitutes at deploy time and `introspect` never emits. `$${ENV_VAR}` is a literal `${ENV_VAR}`, and a value that is nothing but a placeholder is typed as a number or a flag where the schema expects one. A literal value in a credential attribute is rejected by validation.

### Schemas

The first release's section schemas are hand-written Zod in the engine, typed against the Admin SDK's generated record types, and Zod emits the published JSON Schema at build time. Section attributes move to the Admin OpenAPI spec (see Key Decisions); the file-shaped parts stay Zod. `@spree/admin-sdk` now ships generated Zod schemas for API responses (`@spree/admin-sdk/zod`); those describe what the API returns, not what a file writes, so the engine may use them to validate live records but not as file schemas.

### Dashboard e2e as the first consumer

`packages/dashboard/e2e/global-setup.ts` keeps two Ruby statements: `Spree::Seeds::All.call` and the admin user. Everything else in `BOOTSTRAP_RUBY` moves to `packages/dashboard/e2e/fixtures/*.yml`, applied through the library entry against the test server once it is up, with prune on. Products, the second channel, categories, the promo customer and group, stock locations and levels, and the supplier all fit the sections above. The ledger seller's payouts and transfers are transaction data and stay Ruby, in a much smaller block, as do the seller-panel sign-in accounts (admin users have no configurator section). The sellers themselves are declared in the file. Spec-level helpers that already seed through the Admin API (`seedCatalogPickerProducts`) are unchanged. The gain is twofold: the fixtures become readable, and every CI run exercises the Admin API write paths before the suite starts.

Core seeds, the worktree template and `spree:load_sample_data` did not change in the first release; the seeds shrink in the defaults phase (see Migration Path).

### The project config file

`create-spree-app` writes `spree.config.yml` next to `docker-compose.yml`. It is a skeleton: the `version`, the `$schema` header and commented examples of each section, with nothing that first-run setup owns. The store name, country, currency, locale and default market come from the setup screen, and a file that pre-filled them would be deployed before the merchant answers and would revert their answers on the next deploy. `spree config introspect` captures the store into the file once setup has run.

`spree init` runs, in order: `db:seed`, `spree:cli:ensure_api_key`, then `spree config deploy --config spree.config.yml` with a secret key minted for that run and revoked afterwards. `spree config deploy` with no `--config` defaults to `spree.config.yml` in the project directory, so day-to-day use is `spree config diff` and `spree config deploy` with nothing else. The `store` section updates the seeded store rather than creating one; sections are additive unless pruned, so records the seeds or setup created are left alone. The file is committed with the project, and the CLI quickstart teaches deploying it to a remote instance with a profile.

### Recipes

`spree config recipe <name>` (a starter file for a wholesale store, a marketplace, an EU multi-currency setup) is a follow-up once the format has settled. The first release ships an `examples/` directory in the CLI package and the e2e fixtures as living examples.

### Documentation

A new `docs/developer/cli/configurator.mdx` covers the file format, the commands, the natural-key table, secrets, and CI usage, linked from the CLI quickstart and the Admin API page. The JSON Schema is published with the docs.

## Migration Path

1. **Natural key audit.** Done 2026-09-14. Validations are on main; unique indexes and their dedupe task are a follow-up (see Key Decisions).
2. **Engine and schemas.** Done (V-3633): section schemas, reference resolution, plan and apply, diff rendering, unit tests against an in-memory Admin API.
3. **Commands.** Done: `validate`, `diff`, `deploy`, `introspect` in `@spree/cli`, sharing credential resolution with `spree api`.
4. **Dashboard e2e.** Done: the bootstrap fixtures are `e2e/fixtures/store.yml`, deployed before the first spec.
5. **Project scaffold.** Done: `create-spree-app` writes the skeleton `spree.config.yml`; `spree init` deploys it with a per-run secret key.
6. **Docs and schema publication.** Done: `docs/developer/cli/configurator.mdx` and `docs/schemas/spree-config/1.json`.
7. **Package split.** Move `packages/cli/src/config/` to `packages/config` (`@spree/config`); the CLI re-exports nothing and imports it like the dashboard does.
8. **Complete the request-body specs and derive section attributes from them.** Starting with the endpoints the defaults file needs.
9. **Defaults file.** Add the sections `StoreResources` seeds, ship the defaults file in `@spree/config`, deploy it from `spree init`, the setup screen and hosted signup, then delete `Spree::Seeds::StoreResources` and the per-resource seed services.
10. **Country template.** Replace `Spree::Stores::ProvisionDefaults` with a template the same callers deploy, then delete it.
11. **Later, outside this plan:** server-side bulk upserts by natural key for products and categories, `recipe`, an MCP wrapper.

## Constraints on Current Work

- A new admin-manageable resource must have a stable, unique, human-readable key (code, slug or name, unique per store, enforced by an index) and that key must be on its Ransack allowlist. Without it the resource cannot be declared in a config file.
- New dashboard e2e fixtures go into the YAML fixtures once step 4 lands; until then, keep additions to `BOOTSTRAP_RUBY` to what has no Admin API, so they move cleanly.
- Do not add a Ruby-side YAML loader to core or the CLI's rake tasks; the configurator's contract is the Admin API.
- Credential attributes on payment methods and integrations must never be readable back through the Admin API in plain text; `introspect` relies on that.
- A `store` section never carries currency, locale or country; those are market attributes. A scaffolded `spree.config.yml` never pre-fills anything first-run setup owns.
- A new per-store default goes into the defaults file in `@spree/config`, never into a `Spree::Seeds` service; a new country-shaped default goes into the country template, never into `Spree::Stores::ProvisionDefaults`. Both Ruby services only shrink from here.
- A new section declares its `readScope` when its listing needs a scope other than its write scope's `read_` twin, and a `pruneRefusal` when a file must never delete its records.
- A new section whose live lists can hold records the file cannot name (sellers' rows, member types the file does not express) must carry them through every write; a deploy never removes what the file could not have listed.
- A new admin endpoint documents its full request body in its rswag spec, since section attributes are derived from it.
- A key the configurator matches on is kept unique with `validates_store_uniqueness` on the model (case-insensitive, ignoring soft-deleted and revoked rows). The six keys this run added get their unique indexes in the follow-up that also renames existing duplicates; a key added after that follow-up ships its index in the same change.

## Open Questions

- **Sample data as a recipe.** Most of `spree/core/db/sample_data` (channels, options, product types, collections, payment methods, wholesale setup) is configuration, and its products and customers are already CSV imports; orders are transaction data. Turning it into a config file plus the existing CSVs would remove most of the remaining Ruby. Deferred until the defaults file (step 9) lands, because it needs the same phase-2 sections; decide then whether orders stay a small Ruby task or are dropped from sample data.

The design questions settled on 2026-09-14 (deletion policy, first-release scope, package placement, command noun, key hardening, the store section's shape, project setup) and on 2026-10-01 (defaults out of Ruby, the country template, the package split, spec-derived attributes) are recorded under Key Decisions.
