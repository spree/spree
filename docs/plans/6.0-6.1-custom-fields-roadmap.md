# Custom Fields Roadmap

**Status:** Draft — design finalized 2026-10-06, nothing built
**Target:** Spree 6.0 (visibility and immutability fixes), Spree 6.1 (checkout capture, new types, validation, wider exposure, translations)
**Depends on:** `5.4-6.0-custom-fields-rename.md` (implemented), `6.0-store-scoped-custom-field-definitions.md` (implemented), `5.4-metafield-translations.md` (folded in, see below), `6.0-extendable-validations.md` (checkout requirements)
**Author:** Damian Legawiec
**Last updated:** 2026-10-06
**Tracking:** Linear V-3731 · GitHub spree/spree#14821

## Summary

Custom fields let a merchant add a typed, labelled value to a record (a product's "Care instructions", an order's "Delivery date") from the dashboard, without a developer or a deploy. This plan settles what the feature is for, and therefore what it will and will not grow into. Custom fields are a **merchant-facing** feature. They are **not** a data modelling system: developers who need relations, reusable content types or structured objects add real tables. Within that scope there are real gaps. Admin-only fields leak through storefront search. A definition's type can be changed under existing values. Shoppers cannot fill a field in at checkout, the one request merchants keep raising, so a delivery date ends up in untyped cart metadata the merchant cannot see properly. There is no date or choice type and no validation, and values never reach order responses, emails, webhooks or translations. This plan fixes the two defects in 6.0 and closes the rest in 6.1.

## Key Decisions (do not deviate without discussion)

- **Custom fields stay a merchant-facing feature, not a data modelling system** (2026-10-06). The feature serves merchants and their staff who cannot change code. Developers extending Spree add columns and tables. Coding agents make that cheap, and every model already accepts extension attributes (`additional_permitted_attributes`). So none of the following will be built:
  - reusable structured content types (a merchant-defined schema with its own entries);
  - references from a custom field to other records (product, variant, collection, customer, file);
  - file or asset fields;
  - measurement-unit types (weight, dimension, volume) and money;
  - general "list of any type" fields;
  - per-field permissions beyond storefront read and write;
  - custom-field facets (value lists with counts) in the storefront filters endpoint. Filtering by `cf_` keys is unaffected.

  Each of these drags in referential integrity, permissions, cache invalidation and admin pickers, and each is better served by a real table.
- **Custom fields are not where extensions store their data** (2026-10-06). An extension that needs data ships its own columns or tables. `Spree::Metadata` stays the untyped place for integration bookkeeping. Custom fields belong to the merchant: an extension may read them, and it never creates definitions behind the merchant's back.
- **Custom-field filtering stays as shipped in 5.6; facet lists are not added** (2026-10-06). Storefront and admin product filtering and sorting by `cf_` keys (searchable and sortable definitions, on both search providers) stay supported, and the 6.0 fix below makes them respect visibility. What this plan does not add is custom-field *facets*: listing a field's values with product counts in `/store/products/filters`, the way option types appear there today. Faceted navigation stays with option types (as `6.0-product-types.md` already says). This replaces the pending "6.0 metafield faceting" item in `5.4-search-provider.md`.
- **Admin-only values never reach a storefront surface** (6.0, 2026-10-06). That covers reading, filtering, sorting, text search, sort-option labels and search-engine documents. `storefront_visible: false` means the value must not affect what a shopper sees, and that includes the order of results.
- **A definition's `field_type` and `resource_type` are fixed once it is created** (6.0, 2026-10-06). This is enforced in the model (`attr_readonly`) and the Admin API stops permitting both on update. The dashboard already disables both pickers when editing. Changing type means creating a new definition and moving the values deliberately.
- **Storage stays one `text` value per field** (2026-10-06). New types serialize into the same `value` column, so no new value columns are added. Date and date-time types store ISO 8601 strings, which sort correctly as text. A choice holding several values is stored as a JSON array.
- **Validation lives on the definition and is enforced in `Spree::CustomField`** (6.1, 2026-10-06). This is where the Admin API, nested-attribute and `set_custom_field` write paths all meet. It checks **new writes only**: a value that was valid before a rule changed stays readable, and only fails when someone writes it again. This carries forward the direction in `6.0-extendable-validations.md`.

## Design Details

### Part 1 (6.0): stop admin-only fields leaking to the storefront

**What leaks today.** `Spree::SearchProvider::CustomFieldSchema#product_definitions` picks every searchable or sortable product definition, whoever is asking. As a result, a field marked "not visible on storefront" leaks in five ways:

- `/store/products` accepts its `cf_` filter, so a shopper can probe its values by filtering;
- it can be used as a sort, which reveals the order of its values;
- `Product.search` matches its text;
- `/store/products/filters` lists its label among the sort options;
- the Meilisearch presenter indexes it into the same document the storefront queries.

**The fix:**

- `CustomFieldSchema` takes the audience the database provider already carries (`SearchProvider::Database.new(store, audience: :store)`). For `:store` it narrows to `storefront_visible: true`; for `nil` (admin) it keeps every definition.
- The `Product.search` text match gets the same narrowing whenever it runs on behalf of the storefront.
- The Meilisearch provider stops filtering, sorting or searching by admin-only `cf_` attributes in storefront requests. Admin-only fields stay in the index only when the provider serves admin search too; if it does not, they are left out of the document.
- **Spec:** an admin-only searchable and sortable field is ignored as a storefront filter, rejected or ignored as a storefront sort, absent from storefront sort options, and not matched by storefront text search. All four still work through the Admin API.

### Part 2 (6.0): fixed type and owning record type

- `attr_readonly :field_type, :resource_type` on `Spree::CustomFieldDefinition`.
- `Admin::CustomFieldDefinitionsController#permitted_params` permits `field_type` and `resource_type` on create only.
- Sending a different value on update returns 422 with a message naming the field. It is not silently ignored, so a client that thinks it changed the type learns that it did not.

### Part 3 (6.1): shoppers fill in fields at checkout

**The definition gets a storefront write setting.** In full:

- `storefront_writable` (boolean, default false). Only `Spree::Order` definitions can set it. Line-item fields are deferred (see Key Decisions).
- A field writable by shoppers must also be visible on the storefront, so a shopper can always read back what they entered.

**The cart holds the values until checkout completes.**

- `Spree::Cart` includes `Spree::HasCustomFields` and accepts definitions whose `resource_type` is `Spree::Order`. The cart is the order before completion, so merchants define one field, not two.
- The type-match validation on `CustomField` gets this single, explicit exception.
- `Carts::Complete` copies the cart's custom-field rows to the new order in the same step that copies `metadata`.

**The Store API.**

- `PATCH /api/v3/store/carts/:id` and `POST /api/v3/store/carts` accept `custom_fields`. The write shape mirrors the read shape:

  ```json
  { "custom_fields": [ { "key": "checkout.delivery_date", "value": "2026-10-12" } ] }
  ```

- **Keys are looked up, never auto-created.** A key is resolved only among the store's order definitions that are writable by shoppers. An unknown key, or one that is not writable, returns 422.
- A blank value removes the field. Fields the request does not name are left as they are, which matches how cart metadata merges.
- The cart and order Store serializers support `expand=custom_fields` (storefront-visible fields only).
- `@spree/sdk` gets the typed parameter, and the storefront checkout can render these fields from the definitions.
- **Shoppers need the list of fields to render.** `GET /api/v3/store/custom_field_definitions?q[resource_type_eq]=order` returns the definitions writable by shoppers, with their type, label and validation rules. Nothing admin-only is ever returned.

**Required checkout fields.**

- A required field that shoppers can write blocks checkout completion until it has a value.
- This goes through the checkout requirements mechanism from `6.0-extendable-validations.md`, not a save-time model validation. The cart is written many times before it is complete, so "required" can only mean "required to complete".

### Part 4 (6.1): new types

| Token | Class | Stored as | Validation options | Searchable / sortable | Dashboard widget |
|---|---|---|---|---|---|
| `date` | `Spree::CustomFields::Date` | `YYYY-MM-DD` | min, max | yes / yes | `<StoreDatePicker>` (date-only) |
| `date_time` | `Spree::CustomFields::DateTime` | ISO 8601 UTC | min, max | yes / yes | `<StoreDatePicker includeTime>` |
| `choice` | `Spree::CustomFields::Choice` | string, or JSON array when several values are allowed | allowed choices (required), allow several values | yes / single value only | `<Select>`, or a multi-select |

- **Date and date-time input.** Values are parsed with `iso8601`, never `Time.zone.parse`. A date entered without a zone means the store's time zone. This follows the time-zone rules in the root `CLAUDE.md`.
- **Filters.** The `cf_` predicates gain `eq gt gteq lt lteq present blank` for date and date-time, and `eq not_eq in present blank` for choice. A choice holding several values matches if any of its values matches.
- **Everywhere else.** CSV export and import, the Google feed and the GDPR export handle all three types through the existing per-type `csv_value` and `serialize_value` overrides.

### Part 5 (6.1): validation

**Definitions get a `validations` JSON column.** Its keys depend on the type:

| Key | Applies to | Meaning |
|---|---|---|
| `required` | all types | The value cannot be blank. Enforced only at checkout completion, for order fields that shoppers can write (Part 3). Everywhere else it is a dashboard marker and a client-side check; the server accepts a blank value (see Key Decisions). |
| `min` / `max` | short_text, long_text (characters); number, date, date_time (value) | Inclusive bounds |
| `choices` | choice | Allowed values, in display order; at least one |
| `multiple` | choice | Several values allowed |

- **Two validation layers.**
  - `Spree::CustomFieldDefinition` validates the rules themselves: only keys that apply to the type, `min` no greater than `max`, choices not blank and unique.
  - `Spree::CustomField` validates each value against its definition's rules when the value is written.
- **Errors.** They come back as normal field errors on `value`, so the dashboard's `mapSpreeErrorsToForm` displays them inline.
- **Exposure.** Rules are exposed on the Admin definition serializer and, for fields writable by shoppers, on the Store definition endpoint. The storefront and dashboard validate on the client with the same rules.
- **Regular expressions are left out on purpose.** Each pattern is a denial-of-service risk on every write (catastrophic backtracking) and gives poor error messages. Choices, length and range cover the merchant cases we have seen.

### Part 6 (6.1): values reach orders, customers, emails and webhooks

- **Admin API:** the order and customer serializers support `expand=custom_fields`, matching products. Today those values can only be read through the nested `/custom_fields` endpoint.
- **Store API:** the cart and order serializers (Part 3), and the customer's own account serializer, support `expand=custom_fields` with storefront-visible fields.
- **Emails:** the email order serializer (`spree/emails/app/serializers/spree/emails/`) includes storefront-visible custom fields as a list of `key`, `label`, `field_type` and `value`, so templates can render them:

  ```liquid
  {% for field in order.custom_fields %}{{ field.label }}: {{ field.value }}{% endfor %}
  ```

  - The staff new-order email (core serializer) includes **all** of an order's fields, including admin-only ones.
  - The order confirmation template renders custom fields when present.
  - `docs/developer/customization/email-variables.mdx` is updated.
- **Webhooks:** order and customer event payloads include storefront-visible custom fields. Payloads stay on Store serializers (decisions.md 2026-09-29), so admin-only fields stay out of webhooks; an integration that needs them reads the Admin API.
- **No events per value change.** `Spree::CustomField` does not publish its own lifecycle events. A value change already `touch`es the owning record.

### Part 7 (6.1): translations

This folds in `5.4-metafield-translations.md` unchanged in scope:

- definition labels are translatable;
- values of `short_text`, `long_text` and `rich_text` are translatable;
- `number`, `boolean`, `json`, `date`, `date_time` and `choice` values are not.

Choice **labels** are not translated either, because a choice value is the label. A merchant selling in several languages who needs translated options uses a short-text field instead. That plan's design is used as written, including Mobility and per-entity translation tables, and exposure through the resource translations API in `5.5-6.0-resource-translations-api.md`. Its target moves to 6.1.

### Part 8 (6.1): smaller gaps to close

- **Dashboard:** value editors for variants, option types and sellers, which have API routes but no UI.
- **Seller onboarding** renders each requirement field with its proper widget instead of a plain text input.
- **Customer CSV import** processes `custom_field.*` columns, which the template already offers but the importer ignores.
- **Registry:** models that include `HasCustomFields` but are missing from `Spree.custom_fields.enabled_resources` either get registered or lose the include. Today no definition can be created for them, so the include promises a feature that does not exist.
- **Dashboard default:** the definition form defaults `storefront_visible` to false while the server defaults to true. Both should default to **false**, so a new field never reaches the storefront unless the merchant asks.
- **Docs:**
  - fix the "dropdown" custom field mentioned in the 5.6→6.0 upgrade guide (true once `choice` ships, wrong until then);
  - move `docs/developer/core-concepts/metafields.mdx` to a `custom-fields.mdx` path, with a redirect.

## Migration Path

**6.0**

1. Make the search providers aware of the audience, and add the leak specs (Part 1).
2. Add `attr_readonly`, create-only permitted params and the 422 on change (Part 2).
3. Align the dashboard and server defaults for `storefront_visible` (Part 8). Existing definitions keep their stored value.

**6.1**

4. Migration: add `storefront_writable` (boolean, default false, not null) and `validations` (JSON) to `spree_custom_field_definitions`.
5. Add the `date`, `date_time` and `choice` type classes, register them, extend `CustomFieldSchema` predicates, and add dashboard widgets (Part 4).
6. Validation rules on the definition, enforcement on the value, Admin API and dashboard editor (Part 5).
7. Custom fields on the cart, copying on completion, Store API write and expand, the Store definitions endpoint, the checkout requirement, and the SDK (Part 3).
8. Serializer expansion for orders and customers, email serializers and templates, webhook payloads (Part 6). Regenerate types, Zod and OpenAPI.
9. Translations (Part 7), following `5.4-metafield-translations.md`.
10. Smaller gaps (Part 8).

No data migration is needed. Existing values of existing types are unaffected. Existing definitions get `storefront_writable: false` and no validation rules, which is exactly how they behave today.

## Constraints on Current Work

- **Do not add a custom field type for:**
  - a reference to another record;
  - a file;
  - a measurement unit or money;
  - a reusable content schema.

  Add a column or a table instead, and point the requester to this plan.
- **Do not suggest custom fields to an extension author as storage.** Extensions own their tables. Metadata is for integration bookkeeping.
- **Any new code path that reads custom fields on behalf of a shopper filters `storefront_visible: true`.** This covers serializers, search, feeds, webhooks and emails sent to customers. Search code takes an audience and never assumes admin.
- **Never call `set_custom_field` with a `"ns.key"` string from a Store API path.** That form auto-creates a definition. Store writes resolve existing definitions that are writable by shoppers, or fail.
- **Do not add `field_type` or `resource_type` to an update path anywhere** (API, import, seeds).
- **New value storage stays in the single `value` text column.** A new type serializes into it.
- **Custom-field rules do not use regular expressions.**

## Open Questions

All design questions were settled on 2026-10-06. Deferred, not open:

- **Shopper-writable line-item fields.** Unblocked by real demand for typed per-line input (engraving, per-item gift notes) that line item metadata does not serve, plus a design for limiting a definition to certain products and for merging fields when cart lines are rebuilt.
- **Server-side `required` outside checkout.** Unblocked only if products and their custom fields become a single atomic write on every path (Admin API, CSV import, `set_custom_field`). Until then, see decisions.md 2026-08-06.
