# Liquid and MJML Email Templates

**Status:** In Progress — building the whole plan (Alba into core, renderer, layout, all 16 mailers, docs) on `feat/emails-liquid`
**Target:** Spree 6.0 (moved from 6.1 on 2026-09-29)
**Depends on:** v3 serializers (`spree_api`), `spree_emails` (5.6 rebuild)
**Author:** Damian Legawiec
**Last updated:** 2026-09-29
**Tracking:** Linear V-3720 · GitHub spree/spree#14755

## Summary

Transactional emails are the last HTML Spree renders through Rails views. This plan replaces all 61 ActionMailer ERB templates (16 mailers across `spree_core` and `spree_emails`) with **Liquid** templates written in **MJML**. Liquid fills in the data first, then MJML turns the result into email-safe HTML, using the `mrml` gem (a Rust port of MJML) with no Node involved. Templates read plain JSON produced by serializers, never models. This makes the templates:

- **Portable.** Liquid also runs in Node through `liquidjs`.
- **Safe to hand to merchants.** Liquid is built for untrusted templates.
- **Much shorter** than the hand-written HTML tables they replace.

Three things are out of scope and come later on this foundation: merchant editing in the dashboard, templates stored in the database, and live previews. Action Mailer still delivers every email.

## Key Decisions (do not deviate without discussion)

- **Liquid for data, MJML for layout** (2026-09-24).
  - **Why Liquid:** it's the only template language with maintained, first-class engines in both Ruby (`liquid`, maintained by Shopify) and TypeScript (`liquidjs`). That matches the long-term direction of shrinking Rails in the stack. It was also designed for untrusted, merchant-written templates. Handlebars, which Vendure and Saleor use, has only a weak Ruby port and a history of code-execution vulnerabilities when compiling templates from outside sources.
  - **Why MJML:** it's what Vendure and Saleor use. A dozen layout tags (`mj-section`, `mj-column`, `mj-button`) compile to the nested tables, inline styles and Outlook workarounds that email clients need, and mobile stacking comes built in.
  - **Rejected: React Email, Maizzle (now Vue with Tailwind) and other Tailwind-for-email tools.** They are build-time tools on Node, so the file an author writes is not the file that runs. Merchant editing would need Node on the server, or would expose unreadable compiled output.
  - **Rejected: React Email's visual editor.** Templates must be managed as code.
  - **Rejected: plain HTML tables with Liquid, like Shopify.** Nothing new to learn, but Spree would keep maintaining the fragile table markup by hand.
- **Liquid renders first, then MJML, on every email** (2026-09-24). This is the order Vendure uses (`Handlebars.compile`, then `mjml2html`). Loops and conditions can then sit anywhere between MJML tags without `<mj-raw>` wrappers, and partials pulled in by `{% render %}` compile together with the template. Measured with `mrml`, MJML takes about 0.6 milliseconds per email and Liquid about 1.4 milliseconds, so there's nothing to cache.
- **Every output is escaped unless marked safe** (2026-09-24). Liquid doesn't escape HTML by default. A customer named `<a href="https://evil.test">Click to verify</a>` renders a live link, including into the store owner's new-order notification. Rendering always passes `global_filter` with HTML escaping, which was verified to neutralize that input. Values known to be safe HTML opt out explicitly with a `raw` filter. Escaping before MJML also stops customer data from forming MJML tags.
- **Templates keep Rails view paths** (2026-09-25). A template sits where its ERB sat, with the extension changed: `app/views/spree/order_mailer/confirm_email.liquid`. That path is also the template's **key**, so a later database row or Node renderer addresses it as `spree/order_mailer/confirm_email`. The upgrade note is a list of renames, and Rails developers already know where to look.
  - **Accepted trade-off:** template names are tied to Ruby mailer classes and methods for good. A future Node renderer keeps these paths rather than getting cleaner names, and renaming a mailer or one of its methods becomes a breaking change for every app that overrides that email.
- **Templates read serializer output, never models** (2026-09-25). Liquid "drops" that wrap models aren't used.
  - **Customer emails** receive hashes from a new family of **email serializers**, each inheriting from the public v3 Store serializer, for example `Spree::Emails::OrderSerializer < Spree::Api::V3::OrderSerializer`. They add only what emails need. The audit found real gaps in the Store serializers: SKU, product link, per-line amount before discounts, the promotion/manual discount split, the order-group purchase breakdown, and fulfillment items as more than ids. Filling those gaps here keeps the public Store API, SDK types and webhook payloads unchanged.
  - **Accepted trade-off:** a third serializer family to maintain. Email data is a superset of the webhook payload for the same record, not identical to it.
- **Alba moves into `spree_core`** (2026-09-25). Core's back-office emails (admin and seller password resets, invitations, import and export finished, webhook disabled) must work in every installation, including those without `spree_api`, as the marketplace plan requires. With Alba in core, they use email serializers too, so every email takes its data one way.
  - **What moves:** `spree_core` gains the `alba` dependency. The Alba setup in `spree/api/config/initializers/alba.rb` (backend, inflector, the `iso8601` type) moves into core, so both gems configure Alba once and identically.
  - **Where serializers live:** core's email serializers are in `spree/core/app/serializers/spree/emails/` and stand alone, because the v3 Admin serializers live in `spree_api`. That makes each field explicit. The Admin webhook-endpoint serializer, for example, carries `secret_key`, which an email must never render.
- **Tokens never come from a serializer.** Password-reset, invitation, newsletter, download and payment-link URLs carry secrets. The mailer builds them and passes them as email-specific values. Email serializers never expose a token.
- **Action Mailer stays the delivery layer.** Mailers keep choosing the recipient, locale, `from` and `reply_to`, keep their guards (for example `CompanyMailer` cancels delivery for a non-pending invitation, and `SellerMailer` cancels when there are no recipients), and keep delivering through the job queue with retries. Only rendering changes.
- **The template lookup is a chain, with room for a database step.** The renderer asks a resolver for a key. In this plan the resolver checks the host app's Liquid file, then the host app's ERB override (deprecated), then the gem's Liquid default. The later editing work adds a store-scoped database step in front without changing any mailer.
- **The plain-text part is generated from the HTML** (2026-09-25). Spree converts the final HTML to text, keeping links as `label (url)`. A `confirm_email.text.liquid` next to the template overrides it. This halves the file count, and the text can never drift from the HTML.
  - **Accepted trade-off:** generated text is a little less tidy than hand-written text. Seven emails that have no text part today gain one.
- **Copy keeps its translation keys through a `t` filter** (2026-09-25). Default templates read the existing `Spree.t` keys, for example `{{ 'order_mailer.confirm_email.instructions' | t }}`. One template serves every language, and no locale files move. A merchant editing later can still type plain text for a single-language store.
  - **Accepted trade-off:** default templates read less naturally than plain copy.
- **Filters are a small, deliberate public interface, with Shopify's names where the meaning matches.** Agents and developers know Liquid mostly through Shopify themes and reach for Shopify names first. Matching names where the behavior matches (`money`, `money_with_currency`, `date`, `t`) turns that habit into correct code. Nothing is added just because a Rails helper existed.
- **The subject lives in the template.** Each template carries its subject line as Liquid, so one email is one self-contained unit. That's the shape a database row takes later.
- **All 16 mailers migrate in 6.0** (2026-09-25, moved from 6.1 on 2026-09-29). The plan was pulled into 6.0 so the release ships one email stack rather than changing it again one release later, and so merchant editing can start on 6.x without a template migration in between.
- **ERB overrides keep rendering through 6.0, unchanged, with a deprecation warning** (2026-09-29). When a host app or extension still has an ERB file at an email's path, the mailer renders it the way it does today: the old ERB layout, the shared partials and the mailer helpers stay in the gems for that purpose, moved under `app/views/spree/legacy_mailer/` and flagged for removal. 6.1 removes the ERB step and those files.
  - **Why:** the deprecation-bridge rule. An app that customised its order confirmation must not silently start sending the default design after an upgrade.
  - **Accepted trade-off:** two email designs live in the gems for one release. Overriding only a shared ERB partial (the footer, the header) no longer has any effect, because Liquid emails don't read it; Spree logs each such file at boot with the Liquid file that replaces it.
- **The subject is front matter** (2026-09-29). A template opens with a small YAML block holding its subject as Liquid, the Jekyll convention:

  ```liquid
  ---
  subject: "{{ store.name }} {{ 'order_mailer.confirm_email.subject' | t }} #{{ order.number }}"
  ---
  ```

  The block maps one-to-one onto a subject column when templates move to the database. Rejected: a `{% subject %}` tag in the body, which would have to be dug back out of the body for that move.

## Design Details

### Rendering pipeline

```
mailer ── key + data ──▶ Spree::Emails::Renderer            (spree_core)
                           │
                           ├─ 1. resolve key                 host .liquid → host ERB (deprecated) → gem .liquid
                           ├─ 2. Liquid: subject + body      escaping global_filter, strict variables, render limits
                           │      body = layout wrapping the template through {{ content_for_layout }}
                           ├─ 3. MJML → HTML                 mrml
                           └─ 4. text part                   .text.liquid override, or generated from the HTML
                           ▼
mail(subject:, html:, text:)  ── Action Mailer delivery (unchanged)
```

- **Dependencies in `spree_core`:**
  - `liquid`: pure Ruby.
  - `mrml`: MIT licensed, with precompiled binaries for Linux (glibc and musl, x86_64 and arm64), macOS and Windows, so Docker builds need no Rust toolchain. `mrml` is a single-maintainer binding; if it's abandoned, the fallback is compiling MJML through `mjml` on Node in a separate step, with no change to templates.
  - `alba`.
- **The layout** is `app/views/layouts/spree/base_mailer.liquid`: `<mjml>`, `<mj-head>` (fonts and default attributes through `<mj-attributes>`), the header with the store logo, the footer, and `{{ content_for_layout }}` where the body goes. `content_for_layout` is Shopify's name for the same idea. MJML's default Google Fonts import is replaced with the stack the current ERB stylesheet uses.
- **Partials** are loaded with `{% render 'spree/shared/button', url: ..., label: ... %}` and resolve to `app/views/spree/shared/_button.liquid`, the Rails partial naming. `render` gives each partial its own isolated variables. The ERB layout tricks that don't exist in Liquid are replaced:
  - `_mailer_hero` used as a layout with `yield` becomes a partial that takes its heading and text as arguments.
  - `content_for :head` styles move into the layout's `<mj-head>`.
- **Resource limits.** Liquid's render limits are set so a runaway loop fails one email instead of stalling the job queue. Strict variables make an unknown variable raise in development and test, so a typo like `order.nubmer` fails a spec rather than rendering blank.

### Data each template receives

| Variable | Source |
| --- | --- |
| The record (`order`, `order_group`, `fulfillment`, `return`, `customer`, `seller`, `company`, …) | Its email serializer as a hash. Customer emails: `spree_emails` serializers inheriting the v3 Store ones. Back-office emails: core serializers. |
| `store` | Name, storefront URL, absolute logo URL (mailer logo, falling back to the store logo), support email, address, default currency and locale. One core serializer; no Store API serializer exists for stores today. |
| Email-specific values | Built by the mailer: reset, invitation, confirmation, download and payment-link URLs with their tokens; the `resend` flag. |

Line item: `sku`, `display_amount` (price × quantity before discounts, not `display_total`), product storefront URL, image URL. |

Helpers replaced by filters or serializer fields:

- `name_for`, `spree_storefront_resource_url`, `fulfillment_tracking_link_to` and `digital_link_download_url` become serializer fields or mailer-built values.
- `Spree::Money` and the `display_*` methods become `money` or preformatted `display_*` fields.
- `I18n.l` and `strftime` become `date`.
- The image helpers become `image_url`.
- `Spree.t` becomes `t`.

### Filters

| Filter | Example | Notes |
| --- | --- | --- |
| `money` / `money_with_currency` | `{{ line_item.amount \| money }}` | Shopify-compatible names; formatted through `Spree::Money` in the email's currency |
| `date` | `{{ order.completed_at \| date: 'long' }}` | In the store's time zone, never the server's |
| `t` | `{{ 'order_mailer.confirm_email.dear_customer' \| t: name: order.customer_name }}` | Existing `Spree.t` keys with interpolation |
| `image_url` | `{{ line_item.image_url \| image_url: width: 96 }}` | Resized variant URL |
| `raw` | `{{ product.description_html \| raw }}` | Opts out of escaping; only for HTML sanitized on write |

### Previews and tests

- The bundled Action Mailer previews (`/rails/mailers`) keep working, because they call the mailers.
- A shared spec renders every shipped template with factory data under strict variables, so a missing or misspelled variable fails CI.
- Every rendered email is checked for leftover `{{`, `{%` and `<mj-`, which catches both an unrendered Liquid tag and an MJML tag that didn't compile.
- An escaping spec renders each customer-facing email with an HTML payload in every free-text field (names, addresses, notes, company names).

### Documentation

- A developer guide in `docs/developer/` on overriding an email: where files go, the layout and partials, filters, escaping, and the plain-text override.
- **A reference of every email's variables**, generated from the email serializers and published through `llms.txt` too. Agents otherwise assume Shopify's objects (`shop.name`, `order.name`), and this reference corrects that.
- A 6.0 upgrade note listing every ERB path with its Liquid replacement.

## Migration Path

1. **Alba into core.** Add the dependency, and move the Alba setup from `spree_api` into core.
2. **Renderer and resolver in `spree_core`:** `liquid` and `mrml`, the lookup chain with the deprecated ERB step, escaping, limits, filters, and text generation.
3. **Layout and partials** in MJML, matching the current ERB design visually.
4. **Core mailers** (admin user, seller user, invitation, import, export, webhook), each with its core email serializer and render spec. One mailer per commit.
5. **`spree_emails` mailers** (order, order group, fulfillment and shipment, return, digital asset, customer, newsletter, company, seller), each with its email serializer and render spec. One mailer per commit.
6. **Docs:** the override guide, the generated variable reference, and the upgrade note.
7. **6.1:** remove the ERB step from the resolver and delete the old views.

## Constraints on Current Work

- **Keep email views dumb.** New emails and changes to existing ones compute values in the mailer, or expose them from a serializer, rather than calling model methods or new helpers from the view. Every model call in a view today is migration work for this plan, and the order-group views that query the database are the worst case.
- **Don't add new mailer view helpers.**
- **Don't widen the public Store serializers for an email's sake.** A field only an email needs goes on the email serializer once this plan lands.
- **Renaming a mailer class or method is a breaking change** once templates are Liquid, because the view path is the template key that apps override (and, later, that database rows reference).
- **Never put a token in a serializer.** URLs carrying secrets are built by the mailer.
- **New mailers** (message relay, gift cards) may still ship in ERB before this plan lands, but should follow these rules so their conversion is mechanical.

## Open Questions

None block 6.0. Deferred to a later plan on merchant editing:

- Editing in the dashboard, database-stored templates as a store-scoped step in front of the resolver, and revision history.
- Live preview in the browser through `liquidjs` and MJML's browser build.
- Store branding settings (colors, fonts) feeding the layout's `<mj-attributes>`. Today the only branding is the logo and mailer logo.
- Warning merchants when a default they customized has changed, with a diff.

Each is unblocked by this plan shipping: the resolver chain, the email keys and the data contract are what the editor builds on.
