# Dashboard Chat Assistant

**Status:** In Progress — design finalized 2026-08-20; **Phase 0 spike complete (GO)**; **Phase 1 complete 2026-08-20** — every promise audited against the code, with chat history, markdown replies, named-scope filters and a 17-example spec suite closing the gaps a review found. Phase 2 (import/export) complete; Phase 3 (merchandising writes) next
**Target:** Spree 6.0 (Developer Preview, alongside the React dashboard)
**Depends on:** `6.0-admin-spa.md` (the dashboard is the surface), `6.0-admin-rbac.md` (the permission catalog gates the tool list), `5.6-admin-spa-csv-import.md` (import pipeline the assistant drives), `6.0-integrations-admin.md` (future per-store credential surface), `6.0-service-workflows.md` (tools execute through workflows)
**Author:** Damian Legawiec (design driven with Claude)
**Last updated:** 2026-08-20

## Summary

An AI chat assistant embedded in the React dashboard: a merchant opens a chat
panel, asks in plain language, and the assistant answers from live store data
or performs work on their behalf — searching and explaining catalog/order
data, driving CSV imports and exports (including proposing column mappings
for messy files), and merchandising tasks (promotions, pricing, markets,
channels). Reporting tools follow once aggregate endpoints exist.

The architecture is three layers:

1. **A new optional top-level gem `spree/assistant` (`spree_assistant`)**
   runs the agent loop server-side on [RubyLLM](https://rubyllm.com)
   (provider-agnostic; **Claude is the default model, always**), persists
   conversations, and streams each turn to the dashboard.
2. **A first-class tool registry owned by Spree, not by the LLM library.**
   Tools are `{name, description, params schema, required permission,
   mutating flag, executor}` objects that execute against the same scoped
   services and workflows the Admin API uses, under the signed-in admin's
   own CanCanCan ability. RubyLLM tool classes are generated from the
   registry; a future MCP server is a second thin adapter over the same
   registry.
3. **A chat panel in `@spree/dashboard`** that renders streamed text,
   activity cards for tool calls, and approve/reject cards for proposed
   mutations.

The assistant can never do anything the logged-in admin could not do by
clicking, and every mutation requires explicit human approval in the UI.

## Key Decisions (do not deviate without discussion)

- **Ships in the 6.0 line as part of the dashboard Developer Preview
  (2026-08-20).** Additive and optional — an extra gem plus a panel that
  only renders when a store has an active assistant integration — so it
  rides the preview rather than waiting for 6.1. The phase 0 spike is the
  scope valve: if RubyLLM fights the approval gate, the fallback is decided
  here (see Migration Path), not by slipping the release.
- **Packaging (2026-08-20): new top-level optional engine `spree/assistant`,
  gem name `spree_assistant`**, beside core/api/emails — the
  `spree_opentelemetry` precedent. Core and api take no LLM dependency. Not
  under `spree/providers/` (that shelf means commerce providers with an
  `Integration` credential surface).
- **LLM client (2026-08-20): RubyLLM, not the official `anthropic` gem.**
  Spree is a bring-your-own-infrastructure platform — pluggable providers is
  the house architecture (tax, delivery rates, search), and merchants are
  standardized on different LLM vendors. RubyLLM gives one interface over
  Anthropic/OpenAI/Gemini/Bedrock/Ollama plus Rails-native chat persistence
  (`acts_as_chat`). **Claude stays the default model in every configuration
  path.** Accepted trade-offs: provider-specific features (fine-grained
  prompt caching placement, newest betas) lag behind official SDKs — the
  raw-params passthrough is the escape hatch — and it is a
  single-maintainer project, so versions are pinned deliberately. Mitigation:
  the tool registry and prompts are Spree-owned, so a client-library swap
  stays cheap.
- **Pin `ruby_llm ~> 2.0.0.rc2`, and keep the library behind the adapter
  (2026-09-11; supersedes the 1.16.0 pin from the phase 0 spike).** The gate
  now rests on the library's own `requires_approval` rather than the
  `Tool::Halt` return 2.0 removed, and the prediction the pin was taken on
  held: the upgrade touched the adapter, the test harness and a comment,
  because no library type had been allowed to travel past `RunTurn`'s Spree
  value object. Two things improved in the move. A held change no longer
  needs a sentinel return threaded through the tool result, since the
  resolver answers "pending" and the loop simply stops; and sibling reads in
  the same response now still run, where the halt exception used to abandon
  them. Keep the discipline that made this cheap: no RubyLLM type outside the
  adapter, and the approval decision stays server-side — nothing in the
  outbound payload tells the vendor a tool is privileged.
- **The tool registry is Spree's, the LLM library only consumes it
  (2026-08-20).** `Spree::Assistant.tools` is an explicit registry (same
  pattern as `Spree.integrations`). Each tool declares its JSON params
  schema, the RBAC permission key that gates it, and whether it mutates.
  RubyLLM tool classes are generated adapters. This keeps the registry
  reusable for the MCP server later and independent of the client library.
- **No MCP in 6.0; MCP is a later adapter, never the assistant's internal
  transport (2026-08-20). — Superseded 2026-09-15 by `6.0-mcp-server.md`:
  MCP ships in 6.0 first, over a registry extracted into `spree_core` as
  `Spree.agent_tools`; this plan rebases onto it. The "never the internal
  transport" half still holds.** Routing the embedded assistant's own tools
  through an MCP connector would require every install to expose a public
  MCP endpoint just to power its own chat, and breaks local development.
  When an MCP server ships (own plan), it is a protocol adapter mounted over
  the same registry, authenticating with secret API keys + scopes.
- **Tools execute as the signed-in admin — never as a privileged service
  account (2026-08-20).** Every executor receives `{user, ability, store}`
  and goes through the same scope-fetched lookups (`current_store.…`),
  services and workflows the Admin API controllers use. The tool list handed
  to the model is filtered to the user's permission keys, so a user without
  `write_promotions` never even sees `create_promotion`. There is no
  separate assistant permission model.
- **Every mutating tool call requires explicit human approval
  (2026-08-20).** When the model calls a tool marked `mutating`, the loop
  halts, the proposal (tool, human-readable summary, exact arguments) is
  persisted and streamed to the panel, and nothing executes until the user
  approves. Rejection feeds "the user declined" back to the model. Reads
  auto-execute. This is the prompt-injection defense: untrusted text in
  product descriptions or order notes can never silently mutate the store.
  No risk-tiering in v1 — revisit only with usage data.
- **JWT-only surface (2026-08-20).** Assistant endpoints authenticate with
  admin JWT exclusively — it is a human surface. Secret API keys get no
  access (machine integrations should call the Admin API directly, or the
  future MCP server).
- **Curated tools, not generated endpoint wrappers (2026-08-20).** No
  1:1 tool per Admin API endpoint. A small generic read layer
  (`search_resources` / `get_resource` / `describe_resource` over an
  allowlisted resource map, reusing the models' Ransack allowlists) plus
  task-shaped write tools per domain (~10–15 total at 6.0). The generic-verb
  + schema-introspection vocabulary is deliberately shared with
  `5.5-admin-api-cli.md`.
- **Credentials via `Spree::Integration` from day one — one Integration
  class per AI provider (2026-08-20).** Each provider is its own subclass
  (`SpreeAssistant::Integrations::Anthropic`, `::OpenAI`, `::Gemini`, …)
  registered in `Spree.integrations` under a new `ai` integration group, so
  every provider gets its own card in the `/settings/integrations` gallery —
  visible, advertisable, configured independently (`:password` API key +
  provider-appropriate `model` preference; the Anthropic card defaults to
  the latest Claude model and is the flagship). This follows the
  `6.0-integrations-admin.md` rule that per-store providers never ship
  env-var credential contracts, and buys masking, the settings UI and
  verify-before-activate (`can_connect?` = a cheap model ping) from the
  existing machinery. Accepted trade-off: no zero-UI env-var setup path —
  installs provision through the integrations UI or Admin API.
- **AI providers follow the established provider-registry pattern
  (2026-08-20).** `Spree.assistant_providers` is a keyed registry copied
  from `Spree.tax_providers` / `Spree.delivery_rate_providers`:
  `Spree::Assistant::Providers::Base` subclasses (`Anthropic`, `OpenAI`,
  `Gemini`, …), each declaring its Integration class (credentials), its
  RubyLLM provider mapping, and its default model (Claude on the Anthropic
  provider). Extensions register additional providers the same way they
  register tax or delivery-rate providers. The store preference selects a
  registry key; the provider resolves credentials from its store
  Integration.
- **Which provider the assistant uses is a Store preference (2026-08-20).**
  `assistant_provider` on `Spree::Store` (default `'anthropic'` — Claude is
  the default, always), rendered as a picker in the dashboard's store
  settings listing the registered AI providers and deep-linking to each
  provider's integration card for credentials (no per-provider credential
  UI outside the integrations page). Assistant availability = the selected
  provider has an active integration on the current store; the status
  endpoint reports this and the panel hides otherwise. Born on Store per
  `6.0-store-scoped-configuration.md` — never a `Spree::Config` global.
- **Streaming (2026-08-20): server-sent events from an
  `ActionController::Live` endpoint**, consumed with `fetch` + readable
  stream in the SPA (native `EventSource` cannot send the JWT
  `Authorization` header). Accepted trade-off: each in-flight turn holds a
  Puma thread for its duration; acceptable for a low-concurrency back-office
  feature, revisit with a job-backed design only if real deployments show
  thread starvation. The imports "polling, no ActionCable" rule is about
  progress counters; token-streaming chat genuinely needs a stream.
- **Conversations are store-scoped, user-owned data (2026-08-20).**
  `Spree::AssistantChat` (via `Spree::SingleStoreResource`) belongs to the
  admin user; users see only their own chats. Chats are deletable, and
  conversation content (which can embed customer PII from tool results) is
  covered by the same GDPR erasure expectations as the rest of the store —
  chat bodies never feed telemetry or logs.

## Design Details

### Gem layout

```
spree/assistant/
  app/models/spree/assistant_chat.rb        # acts_as_chat (RubyLLM), SingleStoreResource, belongs_to admin user
  app/models/spree/assistant_message.rb     # acts_as_message
  app/models/spree/assistant_tool_call.rb   # acts_as_tool_call + status: proposed|approved|rejected|executed
  app/services/spree/assistant/run_turn.rb  # drives one turn: build context → RubyLLM chat → stream events
  app/tools/spree/assistant/tools/base.rb   # registry DSL: tool_name, description, param, permission, mutating!
  app/tools/spree/assistant/tools/…         # concrete tools
  app/controllers/spree/api/v3/admin/assistant/…  # chats, messages (SSE), tool call approve/reject, status
  app/models/spree_assistant/integrations/anthropic.rb  # one Spree::Integration subclass per provider (`ai` group):
  app/models/spree_assistant/integrations/…             #   :password api_key + provider-appropriate model preference
  app/services/spree/assistant/providers/base.rb        # provider classes (tax/delivery-rate provider pattern):
  app/services/spree/assistant/providers/anthropic.rb   #   integration_class, RubyLLM mapping, default model
  lib/spree/assistant.rb                    # Spree::Assistant.tools + Spree.assistant_providers registries, configuration
```

Three tables: `spree_assistant_chats`, `spree_assistant_messages`,
`spree_assistant_tool_calls`. Approval state lives on the tool-call row —
no separate proposal model. All models inherit `Spree.base_class`; the
assistant user association uses `Spree.admin_user_class`.

### Endpoints (JWT only)

- `GET  /api/v3/admin/assistant` — availability (does the store's selected
  `assistant_provider` have an active integration?) + provider and model;
  drives panel visibility
- `GET/POST /api/v3/admin/assistant/chats`, `GET/DELETE /chats/:id` — own chats only
- `POST /chats/:id/messages` — sends a user message, responds as an SSE
  stream of turn events
- `POST /chats/:id/tool_calls/:id/approve` / `…/reject` — resolves a
  proposed mutation; approve executes and responds with the SSE continuation

SSE event vocabulary (public API, additive-only): `tool_call.started`,
`tool_call.result` (the records a read found, ready to render),
`tool_call.proposed`, `tool_call.resolved`, `message.completed`,
`turn.finished`, `turn.failed`. A `text.delta` event is reserved for
token-level streaming, which the panel does not yet consume — replies
arrive whole at `message.completed`.

### The turn loop

`Spree::Assistant::RunTurn` builds the system prompt (store name, currencies,
markets/channels summary, admin user's name and locale, today's date, and
dashboard deep-link conventions so answers can link to `/orders/$orderId`
etc.), instantiates the RubyLLM chat with the permission-filtered tool set,
and streams. Tool execution:

- **Read tool** → executes inline, result returned to the model, activity
  card streamed to the panel.
- **Mutating tool** → persists the tool call as `proposed`, streams
  `tool_call.proposed`, halts the turn. Approval executes the tool inside
  the same registry executor (re-checking `ability` at execution time — the
  proposal may be approved minutes later), appends the result, and resumes
  the conversation. Rejection appends a declined result.

Executors never write models directly — they call the same workflows and
services the Admin API uses (`Spree.promotion_…`, `Spree::Import`,
price-list services), so validation hooks, events and webhooks fire exactly
as if the API had been called.

### Tool set

**Generic reads (phase 1):**

| Tool | Behavior |
|---|---|
| `search_resources` | Ransack-filtered, paginated search over an allowlisted resource map (products, orders, customers, promotions, price lists, markets, channels, stock levels). Reuses each model's `whitelisted_ransackable_*` allowlists. |
| `get_resource` | Fetch one record by prefixed ID, serialized with the admin serializer. |
| `describe_resource` | Schema introspection: filterable/sortable fields per resource, so the model discovers vocabulary instead of hallucinating it. |

**Import / export (phase 2):** `start_import` (create a `Spree::Import`
from an uploaded file), `propose_import_mapping` (the LLM's best use: map
messy CSV headers onto Spree fields, returned for user confirmation before
`complete_mapping`), `get_import_status`, `create_export` (resource +
Ransack filters through the existing exports machinery).

**Merchandising (phase 3, all mutating):** `create_promotion`,
`update_promotion`, `update_prices` (bulk over a price list / market),
`assign_products_to_channel`, `update_market`. Exact list finalized during
the phase against what the workflows support.

**Reporting (post-6.0):** read tools over aggregate endpoints
(`sales_summary`, `top_products`) once those endpoints exist — additive,
no architecture change.

### Dashboard panel

Part of `@spree/dashboard` proper (not a plugin): a slide-over chat panel
available on every authenticated route, rendered only when the status
endpoint reports the assistant available. Streamed markdown rendering,
activity cards per tool call, approve/reject cards for proposals showing the
human-readable summary (the raw arguments were dropped in review — the
summary is the sentence a merchant decides on, and printing the arguments
underneath restated the same change as JSON). All strings through
i18next in every locale file. Chat history list + delete with confirm.

### Phase 0 spike results (2026-08-20) — GO

The approval gate was proven end to end against ruby_llm 1.16.0 before any
gem code was written. The spike stubs the provider endpoint, so it asserts
control flow rather than model behaviour and runs without an API key.

**Mechanism in 1.16.0.** A tool returns `RubyLLM::Tool::Halt` (via the
protected `halt` helper) from `execute`. The loop then skips its recursive
`complete`, and — the load-bearing detail — the halt content is first
persisted as a normal `role: :tool` message. History is therefore left
valid and resumable: the tool call has a matching result, so no provider
rejects a dangling call, and that placeholder row is the slot approval
later overwrites with the real result. Resuming replays the persisted rows
through `to_llm`.

**Two traps the spike surfaced, both binding on phase 1:**

1. The messages table needs a **`tool_call_id`** reference column (the
   parent tool call), not `parent_tool_call_id` — the persistence layer
   assigns `message.tool_call_id` directly.
2. **Resuming must reload the chat record**, not merely rebuild the
   in-memory chat. The replay reads a cached association, so without the
   reload the model is re-sent the stale awaiting-approval placeholder and
   confirms work it never saw performed — a silent, plausible-looking wrong
   answer. It is invisible unless a test asserts on the outbound request
   body, so **phase 1 keeps an assertion on what the provider actually
   receives after a resume.**

**Mechanism from 2.0.0.rc2 (upgraded 2026-09-11).** `Tool::Halt` is gone. A
mutating tool now declares `requires_approval` with a resolver that answers
`nil` — "still pending" — so the library stops the loop *before* calling
`execute`, and the adapter records the proposal from the resolver instead of
from a tool return. Two consequences worth keeping in mind:

- **The library writes no tool-result row for a held call**, so
  `PersistProposal` still writes the placeholder itself. Trap 2 above did
  **not** go away: approval happens in a different request with a different
  chat object, so the resume still replays persisted rows explicitly and
  still needs the assertion on the outbound payload.
- **Sibling reads still run.** The old halt aborted the whole response; a
  pending approval only parks the calls that need one. "How many products do
  I have, and set this one to draft" now answers the question and holds only
  the change.

The upgrade cost what the pin predicted: the adapter, the test harness
(`sync_response` moved from `Provider` to `Protocol` and lost its connection
argument, and `param`/`desc:` became `parameter`/`description:`), and a
comment. `config.use_new_acts_as` is removed — 2.0 warns if it is still set,
so the initializer that once silenced a 1.x warning was deleted.

### Prompt hygiene and caching

System prompt and tool list are byte-stable within a conversation
(store/user context first, volatile data never in the prefix) so provider
prompt caching can engage; verify RubyLLM's per-provider caching support
during phase 1 and use raw-params passthrough if needed. Tool results
carry prefixed IDs, never raw IDs.

## Migration Path

Greenfield — no data migration. Phases:

- **Phase 0 — spike: DONE, GO (2026-08-20).** Proven against ruby_llm
  1.16.0 with a stubbed provider endpoint (21 checks, no API key needed):
  a mutating tool halts the loop with nothing written, the call and its
  arguments persist for the approval card, approval executes and the
  conversation resumes with the model receiving the real result, rejection
  reports back as declined, and the tool list is filtered by permissions.
  See "Phase 0 spike results" above for the mechanism and the two traps it
  surfaced.
- **Phase 1 — SHIPPED (2026-08-20).** `spree/assistant` gem (models,
  migration, registry, provider classes, per-provider Integration cards under
  a new `ai` group, `assistant_provider` store preference, JWT-only Admin API
  with SSE turn + approve/reject endpoints, `search_resources` /
  `get_resource` / `describe_resource` reads, plus `update_product_status` as
  the first mutating tool), the `client.assistant` SDK resource +
  `streamAssistantTurn`, and the dashboard panel. Verified by a 30-check
  backend smoke run against a real database and by driving the panel in a
  browser end to end: ask → read tool runs → mutation halts → approve →
  the product actually changes → conversation resumes.
  **Deviations from the sketch, all deliberate:** persistence is Spree's own
  rather than the library's `acts_as_chat` (which would put a table of LLM
  model metadata in Spree's schema and hide the replay the approval flow
  depends on); customers are absent from the read map (they are global, with
  no store association to scope through — a surface returning personal data
  gets its own reviewed scoping path); and the panel is an inline column of
  the page, not an overlay, since an answer usually names a record the
  merchant then acts on.

  **Closed after audit (2026-08-20).** A completeness pass against this plan
  found five gaps, all now fixed: chat history had no UI at all (a list,
  switcher and delete-with-confirm now sit in the panel header, and reopening
  a chat replays reads as their clickable record lists); assistant replies
  rendered as plain text, so a link or a bold phrase came through raw
  (`AssistantMarkdown` renders the light markdown a short reply contains and
  turns dashboard paths into real links); two user-visible error strings were
  hardcoded English; the panel could not answer stock questions because the
  search tool exposed only column attributes and never the models' named
  scopes; and **the gem had no tests**, including the one this plan made
  binding. `spree/assistant/spec` now covers the approval gate, the argument
  and budget guards, store scoping, permission filtering and filter
  validation — and asserts on the payload the provider actually receives
  after a resume, which is the only way the stale-replay failure is visible.
- **Phase 2 — SHIPPED (2026-08-20).** `describe_import_mapping` (the file's
  own headings plus the schema's fields and which are required),
  `propose_import_mapping` (mutating — applies the pairing and starts the
  import once every required field is satisfied), `get_import_status` (state,
  row counts, and failures grouped by reason rather than recited row by row),
  and `create_export` (mutating — the file leaves the building, so a merchant
  decides). Verified end to end against a deliberately messy CSV: mapping
  applied, import auto-started, one row imported.

  **Deviations from the sketch:** there is no `start_import` tool. Uploading
  needs a signed blob the chat has no way to produce, and the dashboard's
  import wizard already does it well — so the merchant uploads, and the
  assistant does the part that is actually hard, which is reading
  "Retail Price (inc VAT)" and knowing it means `price`. Permissions mirror
  the controllers rather than the resource map: an import is gated on the
  **write** scope of what is being imported (`write_products`), an export on
  the **read** scope, both resolved per record — a customer import needs
  `write_customers`, not a settings key.
- **Phase 3:** merchandising write tools behind the approval gate.
- **Post-6.0:** reporting tools; MCP server adapter (own plan).

## Constraints on Current Work

- **New admin capabilities are born in the Admin API first.** If an
  assistant tool needs data or an action the API lacks, add the endpoint /
  attribute to `spree/api` and consume it — tools never grow private access
  paths into core.
- **Tool executors follow the same rules as controllers:** scope-fetched
  lookups through the store, writes through workflows/services, never raw
  model writes — **and both layers of authorization, not one.** Permission
  keys answer whether an admin may touch a resource at all; they never answer
  *which records*. Reads go through `ResourceMap#scope_for`, which applies
  `accessible_by` on top of the store scope; anything that changes or deletes
  a record must additionally call `unauthorized(action, record)` before
  acting. A host app's record-level rule (`can :read, Spree::Order,
  seller_id: ...`) is honoured by the Admin API, so it must be honoured here
  — otherwise a seller asks the assistant and is shown the whole store.
  Covered by `spec/authorization_spec.rb`.
- **Core and `spree/api` take no LLM dependency** — anything
  assistant-specific lives in `spree/assistant`.
- **The SSE event names and tool names are public API once shipped** —
  additive-only, same discipline as event payloads.
- No LLM vendor lock-in in interfaces: nothing outside `spree/assistant`'s
  configuration may assume Anthropic specifically.
- **No RubyLLM type may cross the adapter boundary** — not a `ToolCall`, not
  a `Message`, not whatever the next release renames. Controllers,
  serializers and the registry see Spree value objects only. This is what
  kept the 2.0 upgrade to the adapter plus the test harness, after 2.0
  deleted the halt mechanism the gate was first built on.
- **A mutating tool is gated by declaring it, never by what it returns** —
  the adapter marks it `requires_approval` and its resolver answers
  "pending"; the library then never calls `execute`. A tool that enforces
  its own gate inside `execute` has already been handed the arguments and is
  one early return away from running.
- **A resume must reload the chat record before replaying** — rebuilding
  only the in-memory chat re-sends the stale placeholder and produces a
  confident wrong answer. Any test covering approve/resume asserts on the
  outbound provider payload, not just on the visible reply.

## Open Questions

All 2026-08-20 design questions (target release, approval gate scope,
credential surface, turn transport) are resolved into Key Decisions above.
Genuinely deferred, non-blocking:

- **Exact phase-3 merchandising tool list** — finalized during that phase
  against what the promotion/pricing workflows support by then.
- **Reporting tools** — blocked on aggregate Admin API endpoints existing;
  purely additive read tools once they do.
- **MCP server** — gets its own plan when scheduled; the registry contract
  here is what it will consume.
- **Risk-tiered approvals / undo** — revisit only with usage data showing
  the all-gated model is too chatty.
