# Seller Offers on Master Catalog Products

**Status:** Implemented (2026-09-05) — all seven phases of the migration path
are in: the variant review lifecycle and `open_to_sellers`, the admin and
seller API surfaces, the seller panel's Offers section, the operator's
marketplace card and review actions, sample data and docs. **Remaining:** the
follow-ups named under Not in this plan (offer media, CSV import/export of
offers, review emails), each deliberately deferred
**Target:** Spree 6.0
**Depends on:** `6.0-multi-vendor-marketplace.md` (Decision 11 — the shared catalog, shipped 2026-08-16), `6.0-seller-product-submission.md` (the review pattern and the shared form cards this plan extends), `6.0-admin-rbac.md`
**Author:** Damian Legawiec
**Last updated:** 2026-09-05

## Summary

The data model for several sellers selling the same item shipped on
2026-08-16: a variant carries its own `seller_id` and `delivery_profile_id`
when it sits on a *master* product (a product with no seller of its own), the
buy box picks the offer a product leads with, and the Store API already shows
shoppers every seller's row. What did not ship is any way for a seller to
**create** one of those rows. The seller products endpoint is deliberately
rooted in `current_seller.products`, which a master product never is, and its
comment defers the shared catalog to "a separate surface" that was never
built. Today only an operator, through the Admin API, can list a seller
against a master product.

This plan builds that surface: an operator opens a product to sellers, a
seller searches the opened catalog and lists an offer against an item, the
marketplace reviews the offer exactly as it reviews a seller's own product,
and the seller panel and the operator's dashboard both show what is going on.
It reuses the variant workflows, the review row and the product form pieces
that exist rather than adding a model — the marketplace plan settled that an
offer *is* a variant, and nothing here changes that.

Vocabulary: a **master product** is a product with `seller_id` nil (the
marketplace's shared catalog, as the marketplace plan and the model comments
already call it — the deprecated `Product#master` bridge from the
master-variant removal is unrelated and leaves in 6.1). A seller's variant on
one is an **offer**, the word the marketplace plan reserved for the storefront
("3 offers from 2 sellers"); in the API it stays a variant.

## What exists today

| Layer | State |
| --- | --- |
| Core model | Complete for the data. `variants.seller_id`/`delivery_profile_id`, the two-mode rule (owned product blanks both columns; master product keeps them), `resolved_seller`, `Variant.for_seller`, SKU uniqueness per resolved seller, cross-store binding refused, `Seller has_many :variants` — which, because of the normalizer, is *exactly* the seller's rows on master products. `Products::SelectBuyBox` ranks offers; `Product#sellable_variants` drops a suspended, onboarding or away seller. **No status on a variant**, and no way to say which products are open to sellers. |
| Review | Products only. `Spree::ProductSubmission` rows, `Products::Propose/Approve/Reject`, the `auto_approve_seller_products` preference, seller submit actions and operator approve/reject. |
| Admin API | Complete for writes. `/admin/products/:id/variants` permits `seller_id` and `delivery_profile_id`; the admin variant serializer reads both resolved; the product-level `variants:` payload permits `seller_id` too. |
| Store API | Complete. `seller_id` on every variant, `buy_box_variant_id` and the price of the winner on the product. |
| Seller API | **Missing.** No read of the marketplace catalog, no variants endpoint. `Seller::ProductsController` writes variants only inside an owned product's payload and strips `seller_id`/`delivery_profile_id` from them on purpose. |
| Seller SDK | **Missing** the same two resources; its `products` doc comment says so. |
| Seller panel | **Missing.** Products list and the shared product form only (`pages/products.tsx`, `pages/product.tsx`); nav has no entry. |
| Operator dashboard | **Partial.** `ProductSellerCard` names the seller of an *owned* product. The variants section (`dashboard-core/src/products/variants-section.tsx`) has no seller column and the variant sheet no seller field, so on a master product an operator cannot see whose row is whose, nor assign one — although the API permits it. |
| Sample data | `spree:sellers:sample_data` creates no offer, so a fresh seller panel has nothing to show for this. |
| Docs | Nothing under `docs/developer` describes the shared catalog. |

Three properties of the existing write path shape the design, all verified
in code:

- `Variant#set_option_value` creates an option type when the name is unknown
  (looked up **globally**, not per store), attaches it to the product, and
  creates option values on demand. Handed to a seller unfiltered, an offer
  payload could add an axis to the operator's product or a value to the
  marketplace's vocabulary.
- `Products::NestedAttributes#apply_variants` is full replacement — rows
  absent from a product payload are destroyed. The marketplace plan already
  places the guard against a seller wiping a rival's rows on the seller
  branch: a seller must never reach a master product through a
  whole-product write.
- `Variants::NestedAttributes#stock_location_for` resolves a location against
  the product's **store**, which on a marketplace is every seller's
  warehouse. `Seller::ProductsController#own_stock_levels` already narrows
  that to the seller's own locations; the offer endpoint needs the same
  narrowing and must not re-implement it.

## Key Decisions (do not deviate without discussion)

1. **An offer is a variant; there is no new model and no new permission
   resource.** `Spree::Variant` is already a `products` subject for the seller
   audience, so `write_products` gates offers exactly as it gates the seller's
   own listings. A seller who may edit their catalog may list against the
   marketplace's — the two are one capability.

2. **A product is closed to sellers until the operator opens it** (decided
   2026-09-05). `spree_products.open_to_sellers`, boolean, default false, on
   the product rather than a store switch, because a curated marketplace
   opens the commodities and keeps its exclusives — a switch cannot say which
   is which, and "every first-party product" would have meant every item in a
   store's own catalog the day it admitted its first seller. Accepted cost:
   a migration, a form field, a filter and a bulk pair on the operator side,
   and every existing product starts closed, so an operator opens the catalog
   deliberately. Closing a product later stops **new** offers; the ones
   already on it stay — withdrawing them is a review decision on each, not a
   side effect of a checkbox.

3. **An offer is reviewed like a product** (decided 2026-09-05). The master
   product was reviewed once, but an offer names a price, a condition and a
   seller, and that is what a shopper buys — a wrong condition on a vetted
   item is exactly the case review exists for. `Spree::Variant` gains a
   status through `has_status` and its own `Propose`/`Approve`/`Reject`
   /`Draft`/`Archive` workflows on the products' template; the review trail
   goes on `Spree::ProductSubmission`, which gains an optional `variant_id`,
   rather than on a second table that would copy it column for column. The
   `auto_approve_seller_offers` store preference chains `Propose` into
   `Approve` the way `auto_approve_seller_products` does, so a marketplace
   that trusts its sellers on price sets it once. Accepted cost: a status
   column on every variant (backfilled `active` by an upgrade step), a
   review surface on the operator's product page, and every shopper-facing
   read of a product's variants learning to exclude rows that are not
   `active`. **Every variant gets the status, not only offers.** A nullable
   "no status means first-party" column would have avoided the backfill, but
   `has_status` validates inclusion and every scope it generates would then
   have two meanings; and a status on a first-party row is not waste — it is
   the per-variant draft/archive the catalog has wanted instead of
   `discontinue_on`.

4. **The seller reads the marketplace catalog through the public serializer.**
   `GET /seller/master_products` serializes with the *store* product
   serializer (plus the option types and their values, which the offer form
   needs), and its `variants` expand uses the *store* variant serializer. A
   seller sees rival offers exactly as a shopper does — price, seller, stock
   state — and never a rival's cost price, customs data or warehouse. No
   seller-branch master-product serializer is written; the public one is the
   contract.

5. **The seller writes offers through a variants resource rooted in
   `current_seller.variants`.** Shallow-nested: create and list under the
   master product (`/seller/master_products/:id/variants`), read, update,
   delete and the status moves by id (`/seller/variants/:id`), plus a
   top-level index of every offer the seller holds. A rival's row is a 404 by
   scope. This is the "nested variants endpoint" the marketplace plan's
   Decision 11 asked for, and the reason a seller is never handed a
   whole-product `variants:` payload on a master.

6. **`seller_id` and `status` are never parameters on the seller branch.**
   The row is built through `current_seller.variants` and carries the seller
   from where it was built, the way `build_resource` on the products endpoint
   carries ownership; status moves through the member actions, as the
   submission plan requires. `tax_category_id` and `position` are not
   permitted either: tax is marketplace configuration, and the order of a
   shared product's rows is the operator's.

7. **Options are picked, never created** (decided 2026-09-05). A seller names
   a value for every option type the master product carries, from the values
   that type already has. An unknown axis, an unknown value, or a missing
   axis is a 422 naming it — never a silent drop, because a row missing the
   condition axis would land in the wrong buy box. This is the same line the
   submission plan drew for tags and categories: a seller files into the
   marketplace's vocabularies and does not extend them, and it keeps the
   size and colour lists every storefront filter shows free of a seller's
   spelling of "X-Large". Accepted cost: a seller holding an XL the master
   lacks asks the operator to add it. It also closes the global `OptionType`
   creation in `set_option_value` for this caller without touching the
   model.

8. **One offer per seller per option combination on a product.** A second row
   by the same seller with the same values is refused (422) on the seller
   branch. It is not a model validation: first-party catalogs may carry
   duplicate combinations today and a model rule would break them.

9. **Prices are the seller's, stock is in the seller's warehouses, shipping is
   the seller's pick from the marketplace's profiles.** Prices follow the
   variant workflow's full-replacement rule and default to the store currency
   as the products endpoint already does; submitting requires at least one
   price, since an offer without a price is not an offer. Stock levels are
   narrowed to `current_seller.stock_locations` by the helper the products
   endpoint already has, which moves into a shared concern. `delivery_profile_id`
   is resolved through `current_store.delivery_profiles` the same way and,
   left blank, the row ships as the master does (model behaviour, unchanged).

10. **The seller variant serializer gains `delivery_profile_id`, `product_id`,
    `status` and the `submission` expand.** It withheld the profile because
    on an owned product the write is a no-op; on a master it is the whole
    point. Read/write symmetry then requires the owned-product nested payload
    to permit the profile too, which is safe: the model blanks it there.
    `product_id` is what lets the offers index say which product each row is
    on; `status` and the latest submission's `review_note` are what the panel
    shows a seller whose offer was sent back — never the reviewer's identity,
    exactly as on the product.

11. **The seller panel gets an Offers section and reuses the product form's
    variant pieces** (decided 2026-09-05). Its own rail entry rather than a
    tab or rows mixed into the products table: offers and owned products are
    two resources with different bulk moves, and one table cannot honestly
    serve both. The variant field groups (identity, shipping and customs,
    purchase rules, price, inventory) are lifted out of
    `variant-edit-sheet.tsx` into headless sections in `@spree/dashboard-core`
    that take a form and a field prefix, so the sheet and the new offer page
    render one definition — the same move the submission plan made for the
    product cards. Picking the master product uses `ResourcePickerSheet` over
    the master products search.

12. **The operator's dashboard shows whose row is whose, opens products to
    sellers, and reviews offers where they live.** On a master product the
    variants section gains a seller column, a status badge and approve/reject
    on a proposed row; the variant sheet gains a seller picker. All of it
    renders nothing on an owned product or a store without sellers. There is
    no offers page of its own: an offer is a row on a product, and the
    products table's "offers awaiting review" filter is how an operator finds
    the queue — the same shape the marketplace plan chose for order groups.

## Design Details

### Core

**Opening a product.** `spree_products.open_to_sellers` (boolean, `null:
false`, default `false`). On the Ransack allowlist, permitted on the admin
products endpoint, on the admin product serializer only — a shopper has no
use for it. `Product.open_to_sellers` scope.

**Variant status.**

```ruby
class Spree::Variant < Spree.base_class
  has_status :draft, :proposed, :active, :rejected, :archived, default: :active
end
```

The same list as a product's so the two vocabularies never diverge. The
default is `active` because the attribute default is what a first-party
variant and an owned product's variant get — they are not reviewed, their
product is. The seller branch creates offers as `draft`. The column is added
nullable and backfilled to `active` by
`spree:upgrade:backfill_variant_statuses`, a new
step in the 5.6→6.0 manifest; the `has_status` validation then holds every
row written after the upgrade. No database default, per the migration rules.

**What "active" gates.** `Variant#available?` gains `active?`, which reaches
the cart, the buy box (`buyable?` reads `purchasable?`) and every
purchasability rollup at once. Showing is separate from buying, and a
proposed offer must not be *seen* either, so the shopper-facing reads of a
product's variants narrow to `.active`: the Store API `variants` expand and
`GET /store/variants`, `Product#sellable_variants` and the buy box
candidates, and the search documents on both providers (the Meilisearch
presenter builds its option-combination tokens from `product.variants`).
`Product#variants` itself stays raw — the operator writes every row.

**Workflows.** `Spree::Variants::Propose`, `Approve`, `Reject`, `Draft`,
`Archive`, registered as `Spree.variant_propose_workflow` and friends, each
the products' template with `variant:` in place of `product:` — the same
`validate` hook, the same guards (`Propose` only from `draft` or `rejected`),
the same events (`variant.proposed`, `variant.approved`, `variant.rejected`),
the same submission-row writes. `Approve` and `Reject` persist the
`reviewer:` they are given; `Reject` takes a `reason:`. `Propose` chains into
`Approve` when `preferred_auto_approve_seller_offers` is set and records
`metadata: { auto_approved: true }` on the row. `Variants::Update` refuses a
direct `status` write on a `proposed` or `rejected` row, as
`Products::Update` does, so leaving review is always a decision.

**The review row.** `spree_product_submissions.variant_id` (nullable) with an
index on `(variant_id, created_at)`. `belongs_to :variant, optional: true`;
`Product#submissions` and `#latest_submission` narrow to `variant_id: nil`
so a product's own trail never shows an offer's; `Variant#submissions` and
`#latest_submission` read the rows that name it. `ProductSubmissions::Close`
is unchanged — it settles a row, whichever subject the row is about. The
event serializer carries `variant_id` beside `product_id`.

### Seller API

```text
GET    /api/v3/seller/master_products                     search the opened catalog
GET    /api/v3/seller/master_products/:id                 one product, expand=variants,option_types,media
GET    /api/v3/seller/master_products/:id/variants        this seller's offers on it
POST   /api/v3/seller/master_products/:id/variants        list an offer (draft)
GET    /api/v3/seller/variants                            every offer this seller holds, expand=product,submission
GET    /api/v3/seller/variants/:id
PATCH  /api/v3/seller/variants/:id
DELETE /api/v3/seller/variants/:id                        withdraw for good (paranoid delete)
PATCH  /api/v3/seller/variants/:id/submit                 Variants::Propose
PATCH  /api/v3/seller/variants/:id/draft                  Variants::Draft — take down
PATCH  /api/v3/seller/variants/:id/archive                Variants::Archive
```

**`Seller::MasterProductsController`** — read only. Scope:
`current_store.products.active.for_seller(nil).open_to_sellers`. Ransack over
the product allowlist, which already includes `variants`, so a seller can
search by name, SKU or barcode to find the item they hold. Rooted in
`current_store` rather than `current_seller` on purpose — this is the one
seller-branch collection that is the marketplace's, not the seller's — so it
overrides `scope` rather than naming a `seller_association`, and the override
is commented as the deliberate exception to the branch rule.

**`Seller::VariantsController`** — `seller_association :variants`. With a
parent (the nested routes) the scope is `current_seller.variants.where(product:
@parent)`, the parent resolved through the master products scope so a seller
cannot list against an owned product, a closed one, an inactive one, or one
another store holds. `create_workflow` is `Spree.variant_create_workflow`,
`update_workflow` `Spree.variant_update_workflow`, with
`create_workflow_arguments` handing the parent as `product:` and a record
built through `current_seller.variants` so `seller_id` is set before the
workflow sees it, and `status: 'draft'` in the attributes. The status member
actions mirror the products controller's `set_status_resource` /
`run_status_workflow` pair, which move into the shared concern below.
Permitted:

```ruby
:sku, :barcode, :cost_price, :cost_currency,
:weight, :height, :width, :depth, :weight_unit, :dimensions_unit,
:hs_code, :country_of_origin, :customs_description,
:minimum_order_quantity, :order_multiple, :purchase_unit, :units_per_carton,
:track_inventory, :preorderable, :preorder_ships_at, :backorder_limit,
:delivery_profile_id,
options: [:name, :value],
prices: [:amount, :compare_at_amount, :currency],
stock_levels: [:id, :stock_location_id, :count_on_hand, :backorderable]
```

Before the workflow runs, the controller resolves `options` against
`@parent.option_types` and their values (Decision 7), refuses a duplicate
combination (Decision 8), fills price currencies, narrows stock levels and
resolves the profile (Decision 9). The helpers that already do the last three
on `Seller::ProductsController`, and the status-action pair, move into a
`Spree::Api::V3::Seller::CatalogParams` concern both controllers include. The
`submit` action refuses a row with no price (422), since the workflow cannot
know the seller meant to price it later.

The validate hook of the variant workflows is where a host adds its own
rule (a minimum margin, a banned category); nothing here bypasses it.

### Admin API

- `open_to_sellers` on the products endpoint and serializer, with
  `POST /admin/products/bulk_open_to_sellers` and
  `POST /admin/products/bulk_close_to_sellers` on the existing bulk pattern.
- `PATCH /admin/products/:product_id/variants/:id/approve` and `/reject`
  (takes `reason`), the products' pair moved down a level. `write_products`
  gates both, as it does for products.
- `status` permitted on the admin variants payload for first-party rows, and
  refused by `Variants::Update` on a row in review — the same rule as
  products.
- `with_proposed_offers` joins the product Ransack scopes so the products
  table can filter to the queue; `status` joins the variant allowlist.
- The admin variant serializer gains `status` and the `submission` expand.

### Serializers

- `Seller::VariantSerializer` adds `status`, `delivery_profile_id`
  (resolved), `product_id`, a `product` expand using the *store* product
  serializer (the offers index shows the product's name and thumbnail;
  nothing more is needed) and the `submission` expand through the existing
  seller submission serializer.
- Master products serialize with `Spree.api.product_serializer` and
  `Spree.api.variant_serializer`. The option types expand carries each type's
  values, since the offer form renders one picker per axis.

### Seller SDK

`sellerClient().masterProducts.{list,get}` and
`sellerClient().variants.{list,listFor,create,get,update,delete,submit,draft,archive}`,
typed from the regenerated serializers. The `products` doc comment that
points at "a separate surface" now names it.

### Seller panel

- **Nav:** `offers` at position 115, between Products and Orders, subject
  `Spree::Variant`.
- **`/offers`** — `ResourceTable` over `variants.list` with `expand=product`:
  thumbnail and product name, option values, SKU, price, stock, status badge
  with the same quick filter the products table has. Row click opens the
  offer; a "New offer" button opens the master product picker. Bulk actions:
  submit, take down, archive — each a loop over the member action, the way
  the products page does it, with the count in the confirm.
- **Master product picker** — `ResourcePickerSheet` over `masterProducts.list`
  searching name, SKU and barcode; confirming one navigates to
  `/offers/new?product=<id>`.
- **`/offers/new` and `/offers/:variantId`** — one page, two modes, the shape
  `pages/product.tsx` has. Sidebar: a status card on the products' pattern
  (Submit / Take down / Archive, the rejection note shown against a rejected
  offer), a read-only card for the master product (image, name, the
  marketplace's own price if it sells one) and the delivery profile picker.
  Main: an Options card (one `Select` per axis, items from the master's
  option types), then the lifted variant sections — identity (SKU, barcode),
  price (`InputGroup` with the currency, per supported currency, currencies
  from the profile as the product page does), inventory (the seller's own
  locations, from `/seller/stock_locations`), shipping and customs, purchase
  rules. Save runs create or update; delete is behind `useConfirm` with the
  destructive variant and names the product.
- **Entry from Products:** the "Add" control on the products page becomes a
  menu — "New product" and "Sell an existing marketplace product" — so a
  seller who has not found the Offers entry still lands on the picker.
- Every string through i18next; the seller panel ships `en.json` only.

### Operator dashboard

- Product page: a Marketplace card on first-party products with the
  "Open to sellers" switch, shown only on a store that has sellers (the
  sellers list the marketplace pages already read). It stays inside the
  product form, so it saves with the rest of the page.
- Products table: an `open_to_sellers` filter, an "Offers awaiting review"
  quick filter over `with_proposed_offers`, and the bulk pair
  Open to sellers / Close to sellers.
- Variants section: on master products, a Seller column labelled from the
  store's sellers (a first-party row shows the store's name), a status badge
  and Approve / Reject on a proposed row — Reject opening the same reason
  dialog the product page uses. Hidden when the product has a seller of its
  own or the store has none.
- Variant sheet: a seller `Combobox` on master products only, writing
  `seller_id` through the existing nested payload (already permitted). Empty
  means first-party. The product form schema gains `seller_id` and `status`
  on a variant row; the mapping round-trips both unchanged.

### Sample data

`spree:sellers:sample_data` opens the first active first-party product to
sellers and adds one offer from the sample seller: priced slightly under the
marketplace's own row, stock in the seller's location, submitted and left
`proposed` so both the seller's Offers page and the operator's review filter
have something to show. Skipped when the store has no first-party product yet
(the task runs before `spree:load_sample_data` on a fresh install) and
idempotent on re-run.

### Not in this plan

- **Offer media.** The master's images serve every offer, which is how
  shared catalogs work; a per-offer photo (a used copy's actual condition)
  is a nested media route on the seller variant and waits for a request.
- **CSV import and export of offers.** The seller import creates owned
  products; the seller export narrows products by `for_seller`. Both need a
  variant-level dataset to carry offers — later.
- **Catalog matching.** Deciding a seller's new product *is* an existing
  master stays out of core (marketplace plan, Decision 11). Here the seller
  searches and picks.
- **Review emails.** The seller's product review sends none today; offers
  follow suit until the product side gets them.
- **Storefront.** Nothing changes for the customer: offers were already
  public, and now only approved ones are.

## Migration Path

1. **Core.** The two migrations (`open_to_sellers`, `variants.status` +
   `product_submissions.variant_id`), `has_status` on Variant with the
   `active?` gate in `available?`, the five workflows and their dependency
   keys, the store preference, the submission model changes, the narrowed
   shopper-facing reads, the upgrade step and its manifest entry. Model and
   workflow specs; a regression spec proving a proposed offer is neither
   listed nor purchasable, on both search providers.
2. **Admin API.** `open_to_sellers` and its bulk pair, approve/reject on
   nested variants, the new Ransack entries, serializer attributes.
   Controller specs; OpenAPI regenerated.
3. **Seller API, read.** `Seller::MasterProductsController`, routes,
   controller spec (active-only, first-party-only, opened-only, cross-store
   404, Ransack by SKU).
4. **Seller API, write.** The `CatalogParams` concern extracted from the
   products controller (its spec unchanged, proving the move); the variants
   controller with the option, duplicate, price, stock and profile rules and
   the three status actions; the seller variant serializer additions and the
   owned-product payload permitting the profile. Controller spec covers every
   refusal, and a rival's row on the same product returning 404 from show,
   update, destroy and submit. Integration specs for the happy paths;
   regenerate OpenAPI and the SDK types; SDK tests.
5. **Seller panel.** Lift the variant sections into `@spree/dashboard-core`
   and repoint the sheet (no visual change); offers table, picker, offer
   page with its status card, nav, locale keys, the products page "Add" menu.
6. **Operator dashboard.** Marketplace card, table filters and bulk pair,
   seller column, review actions, seller picker, schema and mapping.
7. **Sample data and docs.** The sample offer; a short page under
   `docs/developer` on the shared catalog from both sides; the upgrade doc
   naming the new step; the marketplace plan's Phase 4 note pointing here.

Data: the `backfill_variant_statuses` upgrade step backfills `active` onto every
existing variant. Nothing else moves.

## Constraints on Current Work

- **A seller must never reach a master product through a whole-product
  write.** `Seller::ProductsController` stays rooted in
  `current_seller.products`; do not widen it, and do not add a seller-branch
  route that passes `variants:` for a product the seller does not own.
- **Never permit `seller_id` or `status` on the seller branch.** The row
  carries the seller from the scope it was built in, and status moves
  through the workflows.
- **A seller-branch write of `options` must resolve against the product's own
  option types and existing values before it reaches `set_option_value`**,
  which creates types globally and values on demand.
- **Stock levels on the seller branch go through the shared narrowing
  helper**, never straight to the workflow — the workflow resolves against
  the whole store.
- **A new shopper-facing read of a product's variants goes through
  `listed_variants` (in SQL) or `visible_variants` (in memory), never
  `variants`.** The status scope is `listed`, not `active` — `Variant.active`
  is the older "sellable in a currency" scope and means something else.
  `Product#variants` is the operator's view; anything a customer sees or buys
  from goes through the narrowed reads, and the rollups a customer reads
  (`prices`, `option_values`) hang off the narrowed association rather than
  being filtered again by each caller.
- **Nothing writes `variants.status` around the workflows**, and a path that
  moves a variant out of review runs `Approve`/`Reject` or refuses — the
  submission plan's rule, now for both subjects.
- **New variant form fields go into the lifted sections in
  `@spree/dashboard-core`**, not into the sheet or the offer page, or the two
  drift.
- **`Product#submissions` means the product's own trail.** A reader wanting
  an offer's goes through the variant.

## What implementation changed

Three things the design did not foresee, each caught by a spec or a review and
worth carrying into the next plan that touches this area:

- **The narrowing had to be an association, not a convention.** The plan said
  "a new shopper-facing read of a product's variants narrows to `active`" and
  listed the readers to patch. That list was incomplete: the Google shopping
  feed published offers awaiting review to an external surface, and the facet
  counts disagreed with the results they linked to. `Product#listed_variants`
  is now a scoped `has_many` with the option-value rollups routed through it,
  and `visible_variants` is the in-memory reader for preloaded records.
- **`Variant.active` was already taken.** `has_status` generates a scope per
  status, but Variant had a pre-existing `active` scope meaning "sellable in a
  currency", and `define_status_methods` skips a name that already answers. The
  status filter is `listed`; the collision is commented at both definitions.
- **`purchasable?` measured only stock.** It reaches `preorder?` through
  `oversellable_now?`, neither of which consulted availability, so a
  preorderable offer stayed buyable while in review. It now requires
  `available?`, which is what every caller already meant.

## Open Questions

None open. Two things were settled by choosing, not by discovering, and are
worth watching once the feature is in use: whether operators want a
"withdraw every offer" action when closing a product (today closing stops
new ones only), and whether a seller needs to add a value to an existing
axis often enough to justify a request-a-value flow. Both are additive.
