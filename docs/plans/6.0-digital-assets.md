# Digital Assets: Rename, Admin Management, Delivery

**Status:** In Progress — wave 1 (rename) shipped 2026-08-10; waves 2–4 pending
**Target:** Spree 6.0
**Depends on:** `6.0-fulfillment-and-delivery.md` (Digital fulfillment provider, shipped), `6.0-admin-api.md` (endpoint conventions), `6.0-admin-spa.md` (dashboard architecture), `6.0-admin-rbac.md` (permission catalog), `6.0-store-scoped-configuration.md` (preference conventions)
**Author:** Damian Legawiec
**Last updated:** 2026-08-10

## Summary

Spree ships a complete digital products engine in core: `Spree::Digital` (a file on a variant, private storage, many per variant) and `Spree::DigitalLink` (a per-purchase token with click and day limits), auto-fulfilled at order completion — including digital files riding on physically shipped items. But the engine is invisible: there is no Admin API, no dashboard page (the legacy Rails admin UI was deleted with that engine), no email ever delivers a download link, and downloads publish no events, so a merchant needs a console to sell an ebook and a customer never receives a file unless the storefront wires it up. This plan renames the model to `Spree::DigitalAsset` (the name the docs, the store preferences, and the legacy admin already use), builds the Admin API v3 + dashboard management surface, adds a delivery mailer, a customer downloads endpoint, download events, per-asset limit overrides, and signed-URL download transport — closing the gap between what the engine does and what merchants and customers can see.

## Key Decisions (do not deviate without discussion)

- **Rename `Spree::Digital` → `Spree::DigitalAsset`** (2026-08-10). The model name finally matches the docs, the store preferences (`digital_asset_*`), and the legacy admin's vocabulary. `Spree::DigitalLink` keeps its name — it reads correctly next to `DigitalAsset`. Prefixed ID stays `dig_`.
- **Full table rename** (2026-08-10): `spree_digitals` → `spree_digital_assets`, `spree_digital_links.digital_id` → `digital_asset_id`. 6.0 is the breaking window and the categories rename set the precedent; class, table, and FK all match with no pinning. Accepted cost: one schema migration every host runs, one more upgrade-guide step.
- **Deprecation bridges everywhere, per the standard convention**: `Spree::Digital = Spree::DigitalAsset` constant alias with a warning for one release; `variant.digitals` / `product.digitals` / `digital_link.digital` kept as deprecated twin associations (`deprecated: true`); internal code uses the new names only.
- **Lifecycle events dual-emit for one release**: new canonical `digital_asset.*` events, legacy `digital.*` twins emitted alongside (same pattern as the fulfillment rename).
- **Store download route**: canonical becomes `GET /api/v3/store/digital_links/:token` (the resource being fetched IS the link); the legacy `GET /api/v3/store/digitals/:token` path keeps working for one release because emailed/bookmarked URLs live in the wild.
- **Dedicated delivery mailer** (2026-08-10): `Spree::DigitalAssetMailer` with `files_ready_email` (sent on order completion when digital links exist) and `file_updated_email` (opt-in, on attachment replacement), rather than a section in the order confirmation. Rationale: works for mixed orders, resendable from admin as a standalone action, and survives headless shops replacing the confirmation email. Accepted cost: a second email in the inbox for digital orders.
- **Per-asset limit overrides** (2026-08-10): nullable `authorized_clicks` / `authorized_days` on `spree_digital_assets`; null falls back to the store setting. Lets one catalog mix re-download-forever items with time-limited ones. **This is an explicit, documented exception to the "store preference is authoritative, no runtime fallback" rule** in `6.0-store-scoped-configuration.md` — the fallback here is record-level (asset → its store's setting), never a chain through global config, and the store setting remains the single authoritative default.
- **Signed-URL download transport** (2026-08-10): the store download action calls `authorize!` then redirects to a short-lived signed storage URL instead of proxying bytes through `send_data`, freeing Puma workers for large files. The previously dead `digital_asset_link_expire_time` store preference (default 300) becomes the signed-URL TTL — kept and documented instead of deleted. Accepted cost: clients that expected file bytes on the token URL must follow the redirect (one-release note in the changelog).
- **Permission catalog placement**: `Spree::DigitalAsset` joins the `:products` catalog resource (rides `read_products` / `write_products` — catalog data managed from the product page); `Spree::DigitalLink` management (reset) joins `:orders` (`write_orders` — a per-purchase order artifact). No new catalog resource; digital assets are not `settings`-sensitive.
- **Admin API shape**: nested index + create under products (`/admin/products/:product_id/digital_assets`), shallow show/update/destroy (`/admin/digital_assets/:id`), matching existing nested-resource conventions. File upload via direct-upload signed blob (same mechanism as CSV import), never multipart through the API request.
- **Download visibility ships as an event, not a log table**: successful downloads publish a `digital_link.downloaded` domain event (webhook-visible). The dashboard surfaces `access_counter` and last-download time (already tracked — `authorize!` increments with `touch: true`). A persisted per-download log table is deferred until someone needs per-download rows (IP, user agent).
- **Replacing an asset's file must never break past purchases.** Tokens resolve through the link to the current attachment, so replacement transparently updates for every past buyer — this existing behavior becomes a tested guarantee.
- **Phantom `:digital` param removed** from the admin products controller `permitted_params` — `spree_products` has no such column; `digital?` is derived from the product type.

## Design Details

### Model rename

`spree/core/app/models/spree/digital.rb` → `digital_asset.rb`, class `Spree::DigitalAsset`. One migration renames the table and the FK column. Associations gain explicit `class_name`. `Spree::DigitalLink` gets `belongs_to :digital_asset` plus deprecated `digital` reader/writer delegates. `Variant#digital_assets`, `Product#digital_assets` (through variants), scope `with_digital_assets` unchanged in behavior. The optional `Spree::Security::DigitalLinks` include point is untouched.

New nullable override columns on `spree_digital_assets`: `authorized_clicks`, `authorized_days` (integers, no defaults — null means "use the store setting"). `DigitalLink#expired?` / `#access_limit_exceeded?` read the effective value through the asset.

Serializers: `DigitalSerializer` → `DigitalAssetSerializer` (store, stays minimal and unmounted), new `Admin::DigitalAssetSerializer` extending it with `variant_id` (prefixed), `filename`, `content_type`, `byte_size`, the override fields, timestamps. Dependencies registration renamed with the legacy key readable one release.

### Admin API v3

- `GET /api/v3/admin/products/:product_id/digital_assets` — list, includes variant info for the picker.
- `POST /api/v3/admin/products/:product_id/digital_assets` — params: `variant_id` (prefixed; defaults to the product's default variant when absent, mirroring the legacy admin's auto-assign), `attachment` (signed blob id), `authorized_clicks`, `authorized_days`.
- `GET/PATCH/DELETE /api/v3/admin/digital_assets/:id` — PATCH accepts `variant_id`, the override fields, and a replacement `attachment` blob (which may trigger `file_updated_email`, opt-in per request).
- `POST /api/v3/admin/digital_links/:id/reset` — zeroes the counter and restarts the expiry clock (`DigitalLink#reset!`, which has existed since 2021 without a caller).
- `POST /api/v3/admin/orders/:id/resend_digital_links` — re-sends `files_ready_email`.

All lookups scoped through `current_store` (assets via the product association chain, links via `current_store.digital_links`).

### Dashboard

- **Product page — "Digital files" card**: listed for products whose type includes the `digital` fulfillment type (and any product that already has assets, so legacy data stays reachable). Upload with progress (direct upload), variant picker, filename + human file size + variant columns, per-file "Custom limits" toggle exposing the two override fields, replace, delete behind `useConfirm({ variant: 'destructive' })`.
- **Order page — links on digital line items**: per-link status (clicks used / effective limit, expires-at or expired badge), reset action behind a confirm explaining that it re-opens access, resend-email action.
- **Store settings — Downloads section**: fields for `limit_digital_download_count`, `digital_asset_authorized_clicks`, `limit_digital_download_days`, `digital_asset_authorized_days`, `digital_asset_link_expire_time`.
- `@spree/admin-sdk`: `digitalAssets` resource, `digitalLinks.reset`, order resend; translations in all locale files.

### Delivery email

`Spree::DigitalAssetMailer` in `spree/emails`, triggered by a subscriber on order completion when the order has digital links (after the auto-fulfill steps in `Orders::Complete` have created them). `files_ready_email` lists each purchased file with its download URL; `file_updated_email` notifies past buyers when an asset's attachment is replaced — opt-in at replacement time, never automatic. Both resendable from the admin order page.

### Customer downloads

`GET /api/v3/store/account/digital_links` — authenticated customer, lists links across their completed orders with product/variant/filename context and authorizability state. Store SDK gains a `digitalLinks` resource (list + a download-URL helper); today the SDK ships generated types but no methods, so storefronts hand-build URLs.

### Download transport and events

The store download action (`GET /api/v3/store/digital_links/:token`) calls `authorize!` and redirects (302, `allow_other_host: true`) to a signed storage URL with `expires_in: store.preferred_digital_asset_link_expire_time.seconds` and attachment disposition. On success it publishes `digital_link.downloaded` (payload: prefixed link id, asset id, order id, access counter) — the first domain event in this area, making downloads webhook-visible. Failure keeps the existing 403 with code `digital_link_expired`.

## Migration Path

1. **Rename wave (core)** — **shipped 2026-08-10**: migration (table + FK rename, override columns), model/file/serializer rename, constant alias + deprecated twin associations, dual-emit events, dependencies key bridge, effective-limit readers. Also landed opportunistically because they touched the same files: the canonical `digital_links/:token` route with the legacy path bridged, signed-URL download transport (resurrecting `digital_asset_link_expire_time` as the TTL), the `digital_link.downloaded` event, removal of the phantom `:digital` product param, and the use-case doc correction. Core (7406 examples) and API (2714 examples) suites green; types, Zod schemas and OpenAPI regenerated.
2. **Admin API wave**: catalog entries (`DigitalAsset` → `:products`, link reset → `:orders`), controllers + routes + serializers, remove the phantom `:digital` product param, integration specs, typelizer + OpenAPI regeneration.
3. **Dashboard wave**: admin-sdk resources, product card, order-page links + reset + resend, settings section, e2e specs.
4. **Delivery wave**: mailer + subscriber, customer downloads endpoint + store SDK resource, signed-URL transport + `digital_link.downloaded` event, canonical route + legacy route bridge.
5. **Docs correction** (can land first, independently): `docs/use-case/digital-products/admin-capabilities.mdx` currently describes management screens, release triggers, resendable emails, and download logs that do not exist — trim to reality now, re-expand as waves ship.

## Constraints on Current Work

- New code (including the admin API and dashboard work on this branch) uses `Spree::DigitalAsset` and `digital_assets` association names only; the legacy names are for the bridge layer.
- Any new admin controller touching these models must land with its permission catalog entry (RBAC plan constraint applies).
- The per-asset fallback is the only sanctioned fallback: never add a chain through global `Spree::Config`, and new digital behavior settings are born on Store (or the asset), never global.
- Do not build a per-download log table, PDF stamping, or streaming features ad hoc — the `digital_link.downloaded` event is the extension point until a real need arrives.
- Do not preclude future asset kinds: nothing outside the model should assume an attachment is always present (deferred external/provider-backed assets and license-key pools, see Open Questions).
- Emailed download URLs are long-lived customer-facing artifacts: any route change must keep old URLs working for at least one release.

## Open Questions

Only deferred items remain; nothing blocks implementation.

1. **Asset kinds** (`external_url`, provider-backed for third-party repositories/licensing) and **license key pools** (pre-generated keys per variant, one consumed per purchase) — groom for 6.1 once this plan ships. Unblocked by: this plan's waves landing, plus a concrete integration target to design the provider contract against.
2. **Per-download log rows** (IP, user agent, per-download timestamps) — revisit if merchants ask for more than the counter + event; the event payload is designed so a subscriber can build this externally today.
