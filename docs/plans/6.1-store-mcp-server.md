# Store MCP Server (UCP)

**Status:** In Progress — the guest surface is built: catalog, cart and checkout handoff tools named per UCP 2026-08-25, the endpoint, the discovery profile and the storefront handoff route. Remaining for 6.1: in-agent checkout completion, signed-in customers (OAuth), order webhooks.
**Target:** Spree 6.1
**Depends on:** `6.0-mcp-server.md`, `6.0-mcp-oauth.md`
**Author:** Damian Legawiec
**Last updated:** 2026-10-20
**Tracking:** Linear — · GitHub —

## Summary

A second MCP endpoint that serves a shopper rather than a merchant: browse the
catalog, build a cart, check out, track an order — from an agent the shopper
already uses. The admin server answers "how is my store doing"; this answers
"find me a birthday present under £50 and ship it by Friday".

The October 2026 landscape review settled what shape it takes. Storefront MCP
is table stakes, and the market has split it into a guest shopping surface and
an authenticated operator surface. The guest surface has converged on the
Universal Commerce Protocol (UCP): MCP is the transport, UCP names the tools and
the objects. The major hosted platforms moved their catalog and cart tools to
UCP, platforms with their own tool names renamed them after spec-following
agents failed to find them, and the agent surfaces that actually buy speak
UCP. No open-source platform has a UCP mapping yet.

## Key Decisions (do not deviate without discussion)

- **UCP names and shapes, not a Spree vocabulary.** The tools are the spec's
  (`search_catalog`, `lookup_catalog`, `get_product`, `create_cart`,
  `get_cart`, `update_cart`, `cancel_cart`, `create_checkout`,
  `get_checkout`, `update_checkout`, `cancel_checkout`, `get_order`) and
  answer with the spec's objects: prices in minor units, `totals` as typed
  rows, a `ucp` envelope on every response, `not_found` as an error message
  rather than a protocol error. Pinned to one UCP version (`2026-08-25`).
- **Exposed directly.** No discover/execute meta-tools: platforms that tried
  them found shopping agents then see no commerce tools.
- **A second endpoint, not a mode.** `POST /api/v3/store/mcp`, in the same
  `spree_mcp` gem, building a server over `Spree.store_agent_tools` only. One
  endpoint deciding at runtime whether its caller is a shopper or a merchant
  is the shape that produces a confused-deputy bug.
- **The Store API is the only data source.** Tools dispatch into it exactly as
  the admin tools dispatch into the Admin API, so storefront gating, prices
  hidden from guests, channel scoping and merchandising (the search provider's
  boosts and sort) apply to agents unchanged. No tool reads a model for data.
- **The cart token is the cart id.** A UCP cart or checkout id is the only key
  a guest agent holds, so it has to be unguessable. Spree's prefixed cart ids
  encode a sequential key; the cart's `has_secure_token` token does not. The
  tools resolve a cart by token within the store and hand the Store API the
  same token in `X-Spree-Token`, which is what already authorizes a guest's
  cart. Checkout and cart are one record in Spree, so they share the id.
- **Guest-first, with the publishable key as the whole credential.** The key
  identifies the store, not a person, and ships in every storefront already.
  It may ride in the URL (`?key=pk_…`) because consumer MCP clients take a URL
  and nothing else.
- **Checkout hands off; payment never passes through the server.** Every
  checkout answers `requires_escalation` with a `continue_url` that opens the
  same cart in the store's own checkout. In-agent
  completion with tokenised credentials, then AP2 mandates, come later.
- **`update_cart` and `update_checkout` replace the whole item list**, as the
  spec requires: a variant missing from the request is removed.
- **Purchasable variants, never products, go in a cart.** A product id in a
  line item is refused with a recoverable message naming the fix — the most
  common field bug the landscape review found.

## Design Details

### What is reused unchanged

| Component | Why it carries over |
| --- | --- |
| `Spree::AgentTool` | The tool contract names no surface |
| `Spree::AgentTools::Registry` | Already audience-aware; refuses an admin tool on the store registry |
| `Spree::AgentTools::ApiDispatch` | Dispatches to any Rails path; gained a per-call `headers:` limited to `X-Spree-Token` |
| `Spree::AgentTools::Context` | A publishable key is an `api_key` principal; store tools declare no permission |
| `Spree::Mcp::ToolAdapter` | Speaks MCP, not Spree; already returns `structuredContent` plus text, as UCP requires |
| `Spree::Mcp::Server` | Now takes a `surface:` naming its registry and instructions |

### Request flow

```text
agent ──POST /api/v3/store/mcp?key=pk_…──▶ Store::McpController
          (JSON-RPC tools/call)                 │ publishable key → store, channel
                                                ▼
                                     Mcp::Server (surface: :store)
                                                │ Spree.store_agent_tools
                                                ▼
                               AgentTools::Shopping::<tool>
                                 │ cart id (token) → cart, in this store
                                 ▼
                       ApiDispatch ─▶ /api/v3/store/... (X-Spree-API-Key, X-Spree-Token)
                                 │
                                 ▼
                         Shopping::Ucp (Store API JSON → UCP objects)
```

### Tools

| Tool | Store API it reaches | Kind |
| --- | --- | --- |
| `search_catalog` | `GET /products` (search provider; an empty query lists the catalog) | read |
| `lookup_catalog` | `GET /products` filtered by product or variant ids | read |
| `get_product` | `GET /products/:id` with variants | read |
| `create_cart` | `POST /carts` with `items` | write |
| `get_cart` | `GET /carts/:id` | read |
| `update_cart` | `PATCH /carts/:id` with the full item list (absent lines set to 0) | write |
| `cancel_cart` | `DELETE /carts/:id` | write |
| `create_checkout` | the cart named by `cart_id`, or a new one from `line_items`; `PATCH` for `buyer.email` | write |
| `get_checkout` | `GET /carts/:id` | read |
| `update_checkout` | as `update_cart`, plus `buyer.email` | write |
| `cancel_checkout` | `DELETE /carts/:id` | write |
| `get_order` | `GET /orders/:id` with the token | read |

`complete_checkout` is deliberately not offered until in-agent payment exists:
a tool that can only ever escalate is noise in the model's tool list.

### Discovery

`GET /api/v3/store/ucp` answers the store's UCP business profile: the MCP
service binding (endpoint carrying the publishable key), the capabilities the
tools implement (`catalog.search`, `catalog.lookup`, `cart`, `checkout`,
`order`) and an empty `payment_handlers`. The storefront serves it at its own
`/.well-known/ucp`, so an agent that knows the merchant's domain finds the
endpoint.

### Handoff

`Spree::Cart#storefront_checkout_url` is the `continue_url`:
`<storefront_url>/cart/resume?id=<cart id>&token=<cart token>`. The storefront
route replaces the cart's token through the Store API (which also checks the
pair), adopts the cart into the browser's cart cookies with the new token and
redirects to its checkout. The link therefore works once: whoever built the
cart or sent the link loses it, along with the buyer's details and the order.

A store with no web storefront configured (no storefront URL setting and no
non-local allowed origin) gets no link: its checkout answers `incomplete`
with `checkout_unavailable`, rather than a link to the API's own address.

The profile's endpoint uses `Spree::Config[:public_api_url]`
(`SPREE_PUBLIC_API_URL`) when set, since a storefront fetching the profile on a
private network would otherwise advertise its private address.

### What must never be reachable

- **Another shopper's anything.** Every lookup goes through the cart token or
  the order token, never through an id alone.
- **Prices a customer should not see.** The Store serializers already exclude
  cost price, margin and supplier; the tools only reshape what they return.
- **The back office.** The store registry refuses an admin-audience tool.

## Migration Path

1. **Guest surface (built).** Tools, endpoint, profile, handoff.
2. **Customer OAuth.** Customer-owned grants, a consent screen, a signed-in
   shopper's saved addresses and order history (`get_order` without a token).
3. **In-agent completion.** `complete_checkout` with tokenised PSP credentials
   from a registered payment handler, confirmation required; then AP2 mandates.
4. **Fulfillment extension.** Delivery options chosen in the agent, mapped onto
   cart fulfillments.
5. **Order webhooks** to the agent's profile.
6. **B2B and marketplace.** Company-scoped buyers (contract catalog, price
   list, PO number), approval as `requires_escalation`, multi-seller checkout,
   MOQ and order-multiple errors, reorder-to-cart. Track UCP proposals #929
   (quotes) and #947 (procurement) and comment rather than ship a vendor
   extension ahead of the spec.

## Constraints on Current Work

- **Do not widen `Spree.admin_agent_tools`** to cover storefront cases.
- **A new agent tool declares its `audience`.** The registry refuses a
  mismatch, so an undeclared tool silently defaults to admin.
- **Keep `ApiDispatch` surface-neutral.** Per-call headers are limited to
  `CALL_HEADERS`; a tool never chooses the caller's credential.
- **Never expose a prefixed cart id as a UCP id.** It is guessable; the token
  is the handle.
- **A Store API controller that gains a write** should expect to be reachable
  by an agent. Scope every lookup through the cart or the customer.

## Open Questions

- **Rate limiting.** Tool calls carry the shopper's address into the Store
  API, so its per-key-and-address limit applies to each agent separately. One
  MCP call still costs one or more Store API requests against that limit.
- **Order status for the agent after handoff.** The storefront replaces the
  cart token when it adopts the cart (`PATCH /store/carts/:id/token`), so
  the link works once and its sender loses the buyer's details. The agent
  loses the checkout with it. Reporting completion back needs a narrower,
  status-only view, or order webhooks to the agent's profile.
- **Agent profile negotiation.** `meta.ucp-agent.profile` is accepted but not
  fetched or validated; capability negotiation is fixed to what the server
  implements.
- **`idempotency-key`.** Accepted and ignored until a tool completes or pays.
- **Reading a cart does not re-price it.** `get_cart` shows the prices lines
  were added at; an update re-prices every line (it re-sends them all), and
  completion re-prices inside its lock, so nobody is charged a stale price.
  Whether a read should re-price is open — it would make a read a write.
