# Service Workflows — one step DSL for services, sagas, hooks and events

**Status:** In Progress — Phase 1 shipped to 6-0-dev as a two-tier split (2026-07-30): `Spree::Workflow` (the DSL) powers the curated flows in `app/workflows/`; every other service stays a plain ServiceModule class
**Target:** Spree 6.0
**Depends on:** `6.0-cart-order-split.md` (Carts::Complete is the reference implementation and stress test). Coordinates with: `6.0-multi-vendor-marketplace.md` (payout runs are the first durable-flow consumer), the Rails 8.1 floor decision (decisions.md 2026-07-29 — ActiveJob Continuations are the durability primitive).
**Author:** Damian Legawiec + Claude (design session 2026-07-30)
**Last updated:** 2026-07-30

## Summary

Services, sagas, extension points and events are today four unrelated idioms:
`ServiceModule` run-pipelines threading raw kwarg hashes between steps,
`Carts::Complete` hand-rolling phases/compensation/resumability, extensions
choosing between replacing a whole service (`Spree::Dependencies`) or reacting
after commit (subscribers), and `publish_event` calls buried inside bodies.
This plan evolves `ServiceModule` — in place, additively — into a declared
step DSL (`argument` / `step` / `on_flow_failure:` / `run_hooks` / `emit` /
transaction grouping) so one mental model covers a two-step item service and the
completion saga alike. Medusa's workflows are the DX benchmark; the runtime
stays plain Ruby inside Rails transactions — no execution-state tables, no
engine. **`Carts::Complete` is the stress test:** the DSL is done when the
completion pipeline expresses its lock scopes, out-of-transaction payment
I/O, compensation and structural resumability with its entire spec battery
green and its observable semantics byte-identical.

## Problem

- **Step contracts are implicit.** Pipeline steps receive whatever kwargs the
  caller passed (`@_passed_input` seeds from the raw hash); renames and new
  keys fail at runtime as `IncompatibleParamsPassed`, or worse, silently
  (the 2026-07-30 `cart:` kwarg sweep broke exactly this way; `rewrite_input!`
  exists only to patch the seed mid-flight).
- **Sagas are bespoke.** Compensation, resumability and TTL sweeping live as
  one-off code in `Carts::Complete`; the next saga (marketplace payouts,
  claims) would reinvent all three.
- **Extensions have an axe and a megaphone, no scalpel.** They can swap an
  entire service class or subscribe after commit — there is no supported way
  to inject logic *inside* a flow, in-transaction, at a named point.
- **Events are invisible side effects.** What a service announces is
  discoverable only by reading its body; subscribers form a second, parallel
  system with its own discovery problem (the never-built status subscriber
  hid for months).

## Key Decisions (do not deviate without discussion)

1. **Two tiers, one caller contract (2026-07-30 — supersedes the earlier
   "evolve ServiceModule in place" framing).** `app/services/` holds plain
   `ServiceModule` classes — hand-written `def call(cart:, ...)`, standard
   Ruby, zero DSL vocabulary; this is the permanent default, not a legacy
   tier. `app/workflows/` holds `Spree::Workflow` (the DSL below), earned
   only by flows needing an extension hook, compensation/external I/O,
   replay/halt semantics, or a durable future. Initial set:
   `Carts::Complete`, `Carts::AddItem`, `Carts::Recalculate`,
   `Carts::RecalculateTotals` (+ order twins); a service graduates to the
   workflow tier the moment it earns a hook — never speculatively.
   `Callable.call`, `Result`, `success`/`failure` stay the shared caller
   contract across both tiers — callers cannot tell them apart.
2. **No engine.** No execution-state tables, no visualizer, no parallel
   executor, no cross-process orchestration in this plan. Medusa needs those
   because its modules cross process boundaries; inside one Rails process
   they are ceremony. Durable flows get state from ActiveJob Continuations
   (Phase 2), not from us.
3. **Declared contracts.** `argument :cart` / `argument :quantity, default: 1` declare presence-validated
   per-line arguments (ActiveJob/GraphQL vocabulary); `step :name, provides: [:line_item]`
   declares what a step adds to the context. Unknown keys raise in test/dev, log in
   production. Context is an object (`flow.cart`), not a threaded hash.
4. **Transaction boundaries are explicit DSL, not ambiance.** A bare `step`
   runs in the flow's ambient transaction started by `transaction do ... end`
   grouping blocks; `external_step` is forbidden inside one. This is the lesson
   `Carts::Complete` teaches: PREPARE is in-lock transactional, payment I/O
   must never be, FINALIZE is its own transaction. The DSL must express all
   three or it has failed the stress test.
5. **`on_flow_failure:` pairs a step with its undo method,** run in reverse
   order for completed steps when a later step fails outside a shared
   transaction (inside one, rollback is the compensation — the undo arms
   only after the enclosing transaction commits). Formalizes
   `Carts::Complete#compensate!`; the name says when it runs and why (the
   plain-English rename from the saga literature's "compensation" was
   deliberate — see the naming discussion 2026-07-30).
6. **`run_hooks :name` declares the extension point (ActiveSupport's run_callbacks verb — all registered handlers run there)**, registered through `Spree.hooks`
   with dotted keys and class handlers (decided 2026-07-30):

   ```ruby
   Spree.hooks.register('carts.add_item.after_item_added', MyApp::UpdateExternalWMS)
   Spree.hooks.carts                                  # introspection: flows → points → handlers
   Spree.hooks.for('carts.add_item.after_item_added') # resolved handler list
   ```

   Handlers are classes responding to `call(context)`, where the context at
   a hook point is exactly the declared arguments ∪ the `provides:` keys of
   every preceding step — a computed contract, not a documented one. Discovery, cheapest to
   strictest: `Spree.hooks.contract('carts.add_item.after_item_added')`
   returns the key list; unknown-key reads raise listing the available
   keys; the context supports `deconstruct_keys` for self-documenting
   pattern-matching destructure (`context => { cart:, line_item: }`); and
   an opt-in `uses :cart, :line_item` declaration (Spree::Flows::Handler)
   validates the handler against the contract at boot-finalize. The hook
   reference page is generated from these contracts (Typelizer
   philosophy — code is the source of truth). The registry stores
   class *names* and constantizes at dispatch (the Spree::Dependencies
   trick) — dev-reload safe, initializer safe, and re-registration dedupes
   by string identity. Blocks are accepted for one-line glue but class
   handlers are the documented norm. Hooks run in-transaction; exceptions
   abort the flow (that is the point — consistency-tier one). At
   boot-finalize every registered key is validated against hooks actually
   declared by flow classes (their `run_hooks` declarations), so typos fail loudly at boot instead of
   silently never firing. Hook keys are public API, versioned like
   dependency keys.
7. **`emit 'name', payload: ->(ctx) { ... }`** declares an after-commit
   event with an explicit plain-Ruby payload lambda. The documented
   convention — enforced by review, visible at the declaration — is
   serializing through the record's `event_payload` (the V3 serializer
   path lifecycle events use), so flow events stay shape-identical to
   webhook payloads: `payload: ->(ctx) { ctx.order.event_payload.merge(notify_customer: ctx.order.notify_customer) }`. Same bus, same subscribers, same webhooks — the
   only change is that announcements are declarations, greppable at the top
   of the file. Inline `publish_event` remains valid for conditional edges.
8. **The consistency doctrine ships as documentation** in the same PR:
   *step* — must be true in the same transaction; *sync subscriber* — must be
   true in the same request (statuses); *async subscriber* — eventually
   (emails, webhooks, metrics). One table, linked from CLAUDE.md.
9. **`Carts::Complete` is the acceptance test, not a rewrite target.** The
   retrofit must preserve, observably unchanged: P1 replay idempotency,
   in-lock `expected_total` verification, `completing_at` TTL + sweeper
   resume, pre-capture-only compensation, after-commit-only event emission,
   and the `complete_order` draft branch. The existing spec battery runs
   unmodified — if a spec has to change, the DSL is wrong, not the spec.
10. **Dependency swapping gains step granularity, keeps service granularity.**
    `Spree.cart_add_item_service` continues to resolve the class; inside a
    flow, `step :reserve_stock, with: -> { Spree.stock_reserve_service }`
    keeps step implementations swappable without subclassing the whole flow.

## Design Details

```ruby
class Spree::Carts::AddItem < Spree::Service
  argument :cart
  argument :variant
  argument :quantity, default: 1
  argument :options, default: {}

  transaction do
    step :add_to_line_item,  provides: [:line_item, :line_item_created]
    step :reserve_stock,     if: ->(ctx) { ctx.cart.in_checkout? },
                             undo: :release_reservation
    step :recalculate,       with: -> { Spree.cart_recalculate_service }
    run_hooks :after_item_added
  end

  emit 'cart.item_added', payload: ->(ctx) { ctx.cart.event_payload.merge(line_item_id: ctx.line_item.prefixed_id) }

  private

  def add_to_line_item(ctx)
    # returns a hash merged into the context, validated against out:
  end
end
```

The completion saga shape (the stress test — abbreviated):

```ruby
class Spree::Carts::Complete < Spree::Service
  argument :cart
  argument :expected_total, default: nil
  argument :payment_pending, default: false

  step :replay_completed, halt_with: :existing_order   # P1 idempotency

  transaction lock: :cart do                            # PREPARE
    step :recalculate_in_lock
    step :verify_expected_total
    step :validate_cart
    step :stamp_completing
    step :copy_draft_order, provides: [:order]
  end

  external_step :process_payments, undo: :destroy_draft_and_repoint  # Y — never in a txn

  transaction do                                        # FINALIZE
    step :finalize_order
    step :stamp_cart_completed
  end

  step :release_reservations
  step :recompute_statuses
  emit 'order.placed', payload: ->(ctx) { ctx.order.event_payload.merge(notify_customer: ctx.order.notify_customer) }
end
```

- **Context object**: thin struct over the accumulated hash; `ctx.cart`,
  `ctx[:line_item]`; writes only through step `provides:` merges. `Result.value`
  remains whatever `success(...)` returns, for caller compatibility.
- **`halt_with:`** — early successful exit (replay paths) without treating it
  as failure.
- **Compensation registry**: completed `on_flow_failure:`-bearing steps push
  their undo methods; a failure in a *later* non-shared-transaction step pops them in
  reverse. Inside a `transaction` block no compensation runs — rollback is it.
- **`emit` timing**: collected during the flow, published after the outermost
  commit via `after_commit` on the flow's final transaction (or immediately
  when no transaction is open). Mirrors today's `finalize!` guarantee that a
  rolled-back completion never leaks `order.placed`.
- **Durable flows (Phase 2 — resolved 2026-07-30): plain ActiveJob
  Continuations IS the durability tool.** Rails 8.1's
  `ActiveJob::Continuable` already provides checkpointed steps, cursors
  and interruption-resume; long-running background work uses it directly
  as a plain job — no workflow involvement. Reference implementation:
  `Spree::Imports::ProcessJob` (the CSV import spine — row creation
  resumes from a row-number cursor, then group dispatch; the parallel
  per-group fan-out keeps its own row-status crash-safety). Inline
  callers use `perform_now`; permanent errors are rescued inside the
  step (Continuable resumes errors raised after progress, so
  `discard_on` handlers never run for them); checkpoints are forbidden
  inside open transactions, so transition-callback callers defer the
  inline run to `ActiveRecord.after_all_transactions_commit`.

  A full Workflow-level durable layer (`durable!`, a Continuations-backed
  `Spree::WorkflowJob` walking `flow_items` as checkpoint segments,
  context carried in job data as GlobalIDs) was built, validated
  end-to-end — including interruption/resume with context intact — and
  then deliberately removed as unconsumed framework: every capability it
  added over plain Continuable went unused by the import, and the
  workflows that would use it don't exist yet. It returns only if a flow
  genuinely needs DSL semantics (cross-checkpoint provides, re-armed
  compensation, hooks) *and* durability together — the marketplace
  payout run is the candidate, and it additionally needs the two pieces
  never built: parking (`FlowExecution` rows + resume tokens for KYC
  webhooks) and per-(execution, step) idempotency keys. Design against
  those real requirements then, not before.

## Editor & Typing Story

The contracts are declared data — typing artifacts are generated from them,
never hand-written (Typelizer philosophy, applied to Ruby):

1. **Contexts are real classes** (Phase 1a requirement, not optional):
   per-flow `Context` classes metaprogrammed at load with defined reader
   methods + generated YARD. Solargraph and Ruby LSP then complete and
   navigate `ctx.line_item` with no extra toolchain — method_missing
   dispatch would forfeit the entire editor story and is forbidden.
2. **Opt-in argument types, GraphQL-Ruby style** — the per-line `argument`
   freed the second positional for a type: `argument :cart, Spree::Cart`,
   `argument :quantity, Integer, default: 1`, `:boolean` for `[true,
   false]`, arrays as unions (`[Spree::Cart, Spree::Order]`, `nil` for
   nilable). Validated once at the `call` boundary against supplied
   arguments: ContractError in dev/test, log-warn in production
   (consistent with the other contract checks). **No coercion** — silent
   `"2"` → `2` hides caller bugs; controllers already cast. (RBS/sig
   generation was considered and dropped — 2026-07-30: the runtime
   contracts plus real reader methods carry the editor story on their
   own; no generated signature artifacts.)
3. **`ruby-lsp-spree` addon (tooling backlog, separate from this plan):**
   ruby-lsp-rails-style addon giving in-string completion for hook keys in
   `Spree.hooks.register`, go-to-definition from key to `run_hooks` declaration,
   hover contracts, unknown-key diagnostics — generalizing to the wider
   string-registry family (`subscribes_to` event names, dependency keys).

## Migration Path

1. **Phase 1a — the DSL** (`Spree::Service`, context, `argument`/`step`/
   `transaction`/`external_step`/`on_flow_failure:`/`run_hooks`/`emit`/
   `halt_with:`) — **shipped**, with typed arguments and the
   provides:-as-write-schema rule; specs
   for every construct, consistency-tier doc. No production service changes.
2. **Phase 1b — reference retrofit — shipped.** Every Cart/Order service
   was migrated as a stress exercise, then deliberately folded back
   (2026-07-30): the DSL stays only on the four curated workflows;
   everything else returned to plain bodies keeping the semantics gained
   along the way (`OrderUpdater#update` dissolved into
   `RecalculateTotals`, single status writer, `use_shipping` fix).
   Acceptance held throughout: batteries green unmodified.
3. **Phase 1c — first hooks — shipped:** `after_item_added` (AddItem) and
   `before_finalize` (Complete) registered-hook seams. These two only; more
   hooks are added by demand, not speculation. Extension-facing docs pending.
4. **Rolling adoption:** services migrate when meaningfully touched — never a
   big-bang sweep. `ServiceModule::Base` is not deprecated in 6.0.
5. **Phase 2 — resolved:** plain `ActiveJob::Continuable` jobs are the
   durability tool (`Spree::Imports::ProcessJob` is the reference); the
   upgrade data migrations adopt the same pattern. Workflow-level durable
   execution is deliberately not shipped — revisit with the payout run
   per the note above.

## Constraints on Current Work

- New services are plain sequential `ServiceModule` bodies (like
  `Orders::UpdateItem`) — no new `run`-pipelines, and no DSL outside
  `app/workflows/`.
- Do not hand-roll compensation/saga logic in a plain service; a flow that
  needs it belongs in `app/workflows/` on `Spree::Workflow`.
- Adding an extension hook to a plain service means graduating it to the
  workflow tier first — hooks exist only as `run_hooks` declarations.

## Open Questions

- Should `with:` step swapping be exposed to extensions or reserved for core
  seams initially?
- Context object mutability rules for hooks (read-write vs read-plus-merge).
- Whether the sweeper that resumes stuck completions generalizes into flow
  infrastructure in Phase 2 or stays completion-specific.
