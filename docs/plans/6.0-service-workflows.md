# Service Workflows — one step DSL for services, sagas, hooks and events

**Status:** In Progress — Phase 1 shipped to 6-0-dev as a two-tier split (2026-07-30): `Spree::Workflow` (the DSL) powers the curated flows in `app/workflows/`; every other service stays a plain ServiceModule class. Phase 3 (extension surface: `run_hooks` returning a merged hash, `reject!`, validate/context hooks, four service graduations) shipped 2026-08-02. See **Workflow and hook inventory** below for the 31 shipped workflows and their extension points, **To deliver** for what is still planned, and **Known gaps** for what is wrong in what shipped
**Target:** Spree 6.0
**Depends on:** `6.0-cart-order-split.md` (Carts::Complete is the reference implementation and stress test). Coordinates with: `6.0-multi-vendor-marketplace.md` (payout runs are the first durable-flow consumer), the Rails 8.1 floor decision (decisions.md 2026-07-29 — ActiveJob Continuations are the durability primitive).
**Author:** Damian Legawiec + Claude (design session 2026-07-30)
**Last updated:** 2026-08-05

## Summary

Services, sagas, extension points and events are today four unrelated idioms:
`ServiceModule` run-pipelines threading raw kwarg hashes between steps,
`Carts::Complete` hand-rolling phases/compensation/resumability, extensions
choosing between replacing a whole service (`Spree::Dependencies`) or reacting
after commit (subscribers), and `publish_event` calls buried inside bodies.
This plan evolves `ServiceModule` — in place, additively — into a declared
step DSL (`argument` / `step` / `on_flow_failure:` / `run_hooks` / `emit` /
transaction grouping) so one mental model covers a two-step item service and the
completion saga alike. Medusa's workflows are the DX benchmark; the runtime
stays plain Ruby inside Rails transactions — no execution-state tables, no
engine. **`Carts::Complete` is the stress test:** the DSL is done when the
completion pipeline expresses its lock scopes, out-of-transaction payment
I/O, compensation and structural resumability with its entire spec battery
green and its observable semantics byte-identical.

## Problem

- **Step contracts are implicit.** Pipeline steps receive whatever kwargs the
  caller passed (`@_passed_input` seeds from the raw hash); renames and new
  keys fail at runtime as `IncompatibleParamsPassed`, or worse, silently
  (the 2026-07-30 `cart:` kwarg sweep broke exactly this way; `rewrite_input!`
  exists only to patch the seed mid-flight).
- **Sagas are bespoke.** Compensation, resumability and TTL sweeping live as
  one-off code in `Carts::Complete`; the next saga (marketplace payouts,
  claims) would reinvent all three.
- **Extensions have an axe and a megaphone, no scalpel.** They can swap an
  entire service class or subscribe after commit — there is no supported way
  to inject logic *inside* a flow, in-transaction, at a named point.
- **Events are invisible side effects.** What a service announces is
  discoverable only by reading its body; subscribers form a second, parallel
  system with its own discovery problem (the never-built status subscriber
  hid for months).

## Key Decisions (do not deviate without discussion)

1. **Two tiers, one caller contract (2026-07-30 — supersedes the earlier
   "evolve ServiceModule in place" framing).** `app/services/` holds plain
   `ServiceModule` classes — hand-written `def call(cart:, ...)`, standard
   Ruby, zero DSL vocabulary; this is the permanent default, not a legacy
   tier. `app/workflows/` holds `Spree::Workflow` (the DSL below), earned
   only by flows needing an extension hook, compensation/external I/O,
   replay/halt semantics, or a durable future. Initial set:
   `Carts::Complete`, `Carts::AddItem`, `Carts::Recalculate`,
   `Carts::RecalculateTotals` (+ order twins); a service graduates to the
   workflow tier the moment it earns a hook — never speculatively. First
   graduation (2026-07-31): `Orders::Cancel`, absorbing the orchestration
   buried in `Order#after_cancel` — the cancellation record, status flip
   and fulfillment cancellation commit atomically with the `after_cancel`
   hook inside the transaction, while payment settlement (gateway voids
   and refunds, previously running inside the DB transaction) moved to an
   `external_step` after commit. Workflow-backed `Spree::Dependencies`
   seams are named `*_workflow` (`order_cancel_workflow`,
   `cart_add_item_workflow`, `cart_recalculate_workflow`,
   `carts_complete_workflow`, `cart/order_recalculate_totals_workflow`);
   the legacy `*_service` names stay settable and readable one release
   (reads, writes and top-level `Spree.*` resolution — no boot crashes),
   but a legacy write is stashed, NOT applied: a class written against
   the old service contract is not interchangeable with the workflow the
   new call sites consume, so the warning says the override was not
   applied and names the `*_workflow` seam to port to. Legacy reads fall
   back to the workflow class, which accepts the old keyword vocabulary
   through its `alias_argument` bridges. Removed in 6.1.
   `Callable.call`, `Result`, `success`/`failure` stay the shared caller
   contract across both tiers — callers cannot tell them apart.
2. **No engine.** No execution-state tables, no visualizer, no parallel
   executor, no cross-process orchestration in this plan. Medusa needs those
   because its modules cross process boundaries; inside one Rails process
   they are ceremony. Durable flows get state from ActiveJob Continuations
   (Phase 2), not from us.
3. **The #perform signature is the argument contract (2026-07-31 — the
   perform-composed shape, superseding the class-declared `argument`/
   context/`provides:` design).** A workflow defines a plain
   `def perform(order:, canceler: nil, reason: 'other')`: Ruby itself
   raises on missing/unknown keywords, YARD documents it, and a bare
   `super` first line assigns every parameter — defaults applied — to an
   ivar with a public reader. Data between steps flows through locals and
   instance variables, the before_action idiom every Rails developer
   already knows. The earlier shape's typed/union argument checks, alias
   macros, Context classes and write-schema validation are gone; twin
   vocabularies are plain overrides
   (`def perform(order:, **rest) = super(cart: order, **rest)`), and
   deprecated keywords are guard clauses in perform.

4. **Transactions and locks are plain Rails.** `ApplicationRecord.transaction do`
   and `cart.with_lock do` inside perform — no grouping DSL. What makes
   that sound: `failure(...)` RAISES an internal control-flow signal
   (Exception, not StandardError — the ActiveJob Continuation::Interrupt
   precedent, so a plain `rescue` in perform can't swallow it), which
   unwinds an open transaction into a natural rollback before the runner
   converts it to the failure Result; `halt!(value)` is its successful
   twin, forbidden inside workflow-opened transactions. `external_step`
   refuses to run inside a transaction the workflow itself opened —
   guarded by transaction-depth delta, so a caller-level wrapping
   transaction (the admin API's order lock) stays the caller's business.

5. **`on_flow_failure:` names a step's undo,** armed via
   `ApplicationRecord.current_transaction.after_commit` when the
   workflow-opened transaction around the step commits (immediately when
   there is none), and popped in reverse when a later step fails —
   rollback remains the compensation inside an uncommitted transaction.

6. **Hooks: `hooks :after_cancel` declares the extension points**
   (class-level, one line, so `Spree.hooks.validate!` still fails boot on
   registrations against hooks that don't exist); `run_hooks :after_cancel`
   inside perform dispatches every registered handler **with the workflow
   instance** — argument readers plus whatever the workflow exposes via
   plain `attr_reader` are the handler contract, visible in the file
   instead of computed. Registry unchanged otherwise: dotted keys, class
   name handlers constantized at dispatch, `Spree.hooks.register`,
   introspection facade. Hook keys are public API.

7. **Events are `publish_event`, not workflow syntax (2026-07-31).** The
   established Publishable vocabulary is used inline in perform —
   `order.publish_event('order.canceled', ...)` — positioned after the
   transaction block and before `success(...)`, which gives
   after-commit-only-on-success ordering for free. The earlier `emit`
   declaration is gone.

8. **The consistency doctrine ships as documentation** in the same PR:
   *step* — must be true in the same transaction; *sync subscriber* — must be
   true in the same request (statuses); *async subscriber* — eventually
   (emails, webhooks, metrics). One table, linked from CLAUDE.md.
9. **`Carts::Complete` is the acceptance test, not a rewrite target.** The
   retrofit must preserve, observably unchanged: P1 replay idempotency,
   in-lock `expected_total` verification, `completing_at` TTL + sweeper
   resume, pre-capture-only compensation, after-commit-only event emission,
   and the `complete_order` draft branch. The existing spec battery runs
   unmodified — if a spec has to change, the DSL is wrong, not the spec.
10. **Dependency swapping gains step granularity, keeps service granularity.**
    `Spree.cart_add_item_service` continues to resolve the class; inside a
    flow, `step :reserve_stock, with: -> { Spree.stock_reserve_service }`
    keeps step implementations swappable without subclassing the whole flow.

11. **Workflows replace state machines for new models (2026-08-02).** A new
    model gets a plain `status` string column with an inclusion validation and
    generated predicates — never a `state_machine :status` block. Transitions
    are workflows: `Spree::Returns::Receive.call(...)`, not `return.receive!`.
    See "State machines" below for the full rule and the narrow exceptions.

12. **Hook keys are public API and ship on the 6.0 boundary (2026-08-02 —
    amends decision 6 and the "never speculatively" clause in decision 1).**
    The original rule — a service graduates the moment it earns a hook, and
    hooks are added by demand — was written to prevent speculative
    abstraction, and it still governs *workflows*. It does not govern *hooks*
    on flows already in the workflow tier. A hook is a published extension
    point: adding one later is cheap, but *moving* one means restructuring a
    flow extension authors have already registered against, which is a
    breaking change. 6.0 is the breaking-change window. A documented,
    coherent extension surface is itself the demand — so hooks are placed
    deliberately across the existing workflows now, at the points a
    third-party integration would need them, rather than one at a time as
    individual merchants ask. The bar remains real: a hook must name a point
    where an extension would plausibly inject behaviour, and every hook ships
    documented. Speculative *workflows* are still forbidden.

13. **Customer registration is a workflow; the welcome email leaves core
    (2026-08-05).** `Spree::Customers::Create` graduates on real demand, not
    speculation: registration is the canonical veto point (bot and
    disposable-email screening, fraud checks, B2B "registration requires
    approval" — all need to *reject* a signup, which the `user.created`
    lifecycle event cannot do), and creation today carries multi-record side
    effects scattered inconsistently across three paths (newsletter-subscriber
    linking and consent propagation on self-registration only, address
    adoption and welcome email on the checkout path only, neither on admin
    create). The workflow absorbs `Orders::CreateUserAccount` via an optional
    `order:` argument — one flow, one workflow — so store self-registration,
    the checkout "create an account" box, and (later) storefront OIDC
    auto-provisioning all flow through one seam
    (`customer_create_workflow`); the old service class stays as a deprecated
    one-release shell. Deliberately **not** routed through it: the Admin API
    create action (plain CRUD, and staff creation must not be blockable by
    registration-policy hooks) and JWT/refresh-token issuance (an HTTP
    session concern that stays in the controller — the workflow returns the
    customer, the controller mints tokens). **The welcome email is dropped
    from core entirely**: no `send_welcome_email` call anywhere; signup email
    is host-app implementation via a `user.created` subscriber or the
    `customers.create.after_create` hook, consistent with headless
    storefronts owning consumer email. The host-app migration step is
    written up in decisions.md 2026-08-05 ("Upgrade step (host
    applications)") and belongs in the 6.0 upgrade manifest.

## Hooks

Three families, because they solve different problems:

**Lifecycle hooks** — past tense, fired after something happened, for
extensions that react: `after_item_added`, `after_cancel`, `after_confirm`.
Handlers read the workflow instance and cannot change the outcome. This is
what we ship today.

**Validation hooks** — `validate`, fired before the work, for extensions that
*reject*. A handler calls `reject!(message)` on the workflow to abort the flow
(contract below). This is the seam merchants ask for most (return windows, B2B
purchase limits, per-group eligibility) and today they have to replace the
whole workflow class to get it.

**Context hooks** — imperative (`set_pricing_context`, `set_tax_line_context`,
`set_promotion_context`, `get_provider_data`), fired before a calculation so
extensions can feed data *into* it.

### Hook contracts (resolved 2026-08-02)

**Context hooks collect and deep-merge handler return values.** A handler
returns a hash; `run_hooks` merges every handler's hash in registration order
and returns the result. No shared mutable state — handlers stay pure and
independently testable, and a handler that returns `nil` contributes nothing
rather than corrupting the context.

```ruby
# Handler
class MyApp::PricingContext
  def call(workflow)
    { customer_tier: workflow.cart.customer&.tier }
  end
end

# Workflow
context = run_hooks(:set_pricing_context)   # => { customer_tier: 'gold' }
Spree.price_selector.call(cart, **context)
```

`run_hooks` returning a value is additive — lifecycle hooks ignore the return
and are unaffected. On a key collision the last registered handler wins, and
the collision is logged via `Rails.error.report` in development so two
extensions fighting over the same key is visible rather than mysterious.

**`validate` handlers reject with `reject!(message)`.** A purpose-named method
on the workflow that wraps the existing failure path — it raises
`FailureSignal`, so the undo stack unwinds and an open transaction rolls back
exactly as a failed step would. The distinct name keeps "an extension vetoed
this" legible against "this step failed" at the call site.

```ruby
class MyApp::LimitReturnWindow
  def call(workflow)
    return if workflow.order.completed_at > 30.days.ago

    workflow.reject!(Spree.t('returns.errors.outside_window'))
  end
end
```

### What is public API (resolved 2026-08-02)

The 6.0 extension surface is deliberately narrow, because everything in it is
frozen for the release:

**Public** — hook keys and their contracts, `reject!`, `Spree::Dependencies`
class swapping, `has_status`/`add_status`, workflow `#perform` keyword
signatures.

**Internal** — `with:` step targets, step names, step boundaries and ordering.
`step :reserve_stock, with: -> { Spree.stock_reserve_service }` stays a core
seam: documenting it would freeze every step name and its collaborator kwarg
contract as public API, locking internal structure we still expect to refactor
during the 6.0 finishing work. Extensions get hooks (finer-grained than class
swapping, and safe) and Dependencies (coarser, already public). Revisit in 6.1
once real hook usage shows what is genuinely missing.

### Configurable statuses

`Spree::HasStatus` (see "State machines" below) holds its values in a
`class_attribute`, not a frozen constant, so extensions can add statuses
without reopening core. The API is deliberately **additive only**:

```ruby
# Core
class Spree::Return < Spree.base_class
  has_status :requested, :approved, :received, :refunded, :canceled,
             default: :requested
end

# Extension decorator
Spree::Return.add_status(:inspecting, after: :received)
Spree::Return.statuses
# => %w[requested approved received inspecting refunded canceled]
```

Adding is safe; wholesale replacement is not offered. Core workflows guard on
core statuses (`Returns::Refund` requires `received?`), so allowing an
extension to remove one would silently break core flows with no error at the
point of removal — the guard would simply never pass.

A custom status needs a custom workflow to move records into it. That is the
intended shape, not a gap: `add_status` deliberately takes no `from:`/`to:`
transition graph, because validating transitions centrally is a state machine
by another name — the exact thing decision 11 removes. Extensions write a
workflow the same way core does.

### State machines

`state_machines-activerecord` stays a dependency through 6.0 for the models
that still carry machines (Payment, Fulfillment, InventoryUnit,
ReturnAuthorization, GiftCard — see `6.0-normalize-state-to-status.md`).
**New models do not get state machines.** The reasoning, argued at length in
`6.0-returns-exchanges-claims.md` → "Why workflows, not state machines":

- Transition callbacks run inside the save transaction, which puts gateway I/O
  in a database transaction — the exact failure `Carts::Complete`'s three-phase
  design exists to prevent.
- Transitions take no arguments, so partial and contextual operations
  (receive two of three items, one not resellable) have nowhere to put their
  inputs.
- There is no compensation story; `on_flow_failure:` is.
- Guards raise `StateMachines::InvalidTransition` instead of returning an
  inspectable `Result`.

The precedent is already shipped: the Order state machine is gone in 6.0
(`6.0-cart-order-split.md`), and `Orders::Cancel`/`Orders::Resume` absorbed
`Order#after_cancel`/`#after_resume`.

The narrow exception: a model whose status genuinely has no side effects at
all — a pure label with no restocking, no money, no fulfillment — may keep a
machine if the transition graph is doing real validation work. In practice
this has not come up.

## Design Details

- **The whole workflow vocabulary is five words**: `step :name` (runs the
  method of that name, instrumented), `external_step`, `run_hooks`,
  `failure(...)`, `halt!(value)` — plus the class-level `hooks`
  declaration and `with:`/`on_flow_failure:` step options. Everything
  else in a workflow file is the Ruby a Rails developer already writes.
- **`step :name, with: -> { Spree.cart_recalculate_totals_workflow }`**
  delegates to a collaborator resolved from the lambda (the Dependencies
  seam does the swapping); its keyword arguments are sliced from the
  workflow's readers — a Workflow collaborator declares its contract on
  #perform, a ServiceModule collaborator on its author-written #call.
- **Observability**: every step run emits the `step.spree_workflow`
  ActiveSupport::Notifications event with `{ workflow:, step: }` — APMs
  and log subscribers consume it with zero new concepts. Workflow-backed
  Dependencies seams are named `*_workflow` (legacy `*_service` names
  stay settable/readable one release; writes are stashed, never applied —
  an old service class is not workflow-contract compatible).
- **Why not Medusa's function-composition shape** (analyzed 2026-07-31):
  Medusa's `createWorkflow` body is a symbolic graph builder — their own
  docs forbid if/else, loops, await, try/catch and direct variable use
  inside it ("variables in the workflow don't have any values"),
  replacing them with `when().then()` and `transform()`. That is a
  heavier DSL than ours wearing function syntax; the honest Ruby
  equivalent of what it actually does is the perform-composed shape:
  runtime named steps with real Ruby control flow, the
  ActiveJob::Continuable idiom — which also makes durable jobs and
  workflows read identically across Spree.

## Editor & Typing Story

The contract is a plain method signature: editors, YARD and Solargraph
understand `def perform(order:, canceler: nil)` natively — completion,
go-to-definition and documented params with no toolchain. Argument
readers are real methods defined from the signature; derived state
exposed to hooks is plain `attr_reader`. (RBS/sig generation considered
and dropped 2026-07-30; the generated-Context editor story retired with
the perform-composed shape 2026-07-31.) The `ruby-lsp-spree` addon idea
(in-string completion for hook keys, go-to-definition from key to the
`hooks` declaration) stays on the tooling backlog, separate from this
plan.

## Migration Path

1. **Phase 1a — the DSL — shipped, then reshaped (2026-07-31)** into the
   perform-composed form described above after the Medusa analysis; the
   class-declared form (typed arguments, Context classes, provides:,
   transaction grouping, emit) lives in branch history. Specs cover every
   construct of the final surface.
2. **Phase 1b — reference retrofit — shipped.** Every Cart/Order service
   was migrated as a stress exercise, then deliberately folded back
   (2026-07-30): the DSL stays only on the four curated workflows;
   everything else returned to plain bodies keeping the semantics gained
   along the way (`OrderUpdater#update` dissolved into
   `RecalculateTotals`, single status writer, `use_shipping` fix).
   Acceptance held throughout: batteries green unmodified.
3. **Phase 1c — hooks — shipped:** `after_item_added` (AddItem),
   `before_finalize` (Complete), `after_cancel` (Orders::Cancel,
   in-transaction) and `after_resume` (Orders::Resume) registered-hook
   seams. The original "more hooks are added by demand, not speculation"
   stance is amended by decision 12 — Phase 3 below places the remaining
   hooks deliberately on the 6.0 boundary. Extension-facing docs pending.
4. **Rolling adoption:** services migrate when meaningfully touched — never a
   big-bang sweep. `ServiceModule::Base` is not deprecated in 6.0.
5. **Phase 2 — resolved:** plain `ActiveJob::Continuable` jobs are the
   durability tool (`Spree::Imports::ProcessJob` is the reference); the
   upgrade data migrations adopt the same pattern. Workflow-level durable
   execution is deliberately not shipped — revisit with the payout run
   per the note above.

### Phase 3 — extension surface (2026-08-02, targets 6.0) — **shipped**

Two waves finished the extension surface on the 6.0 boundary, per decision 12.
Wave A added the runtime contracts (`run_hooks` returning a merged hash,
`reject!`) plus hooks on the existing workflows; Wave B graduated four services
that had already earned the tier (`Fulfillments::Create`, `Payments::Capture`,
`Payments::Refund`, `Payments::HandleWebhook`, `Carts::Merge`). Returns,
exchanges and claims then arrived with hooks from the start.

`Spree::Returns::EligibilityValidator` on `returns.create.validate` and
`exchanges.create.validate` — a per-market return window that staff bypass
(decisions.md 2026-08-03). Everything else is unregistered seam.

## Known gaps

Not new workflows — things wrong or missing in what already shipped.

- ⬜ **Extension-facing docs list only the pre-returns hooks.**
  `docs/developer/customization/workflows.mdx` documents the pre-returns hook
  points (plus `customers.create`, added 2026-08-05); the fifteen
  returns/exchanges/claims workflows added since are missing from the
  reference table. (Earlier revisions claimed the table is spec-asserted in
  core — no such spec exists, which is part of this gap.)
- ⬜ **`Spree.hooks.clear!` wipes core registrations permanently.** The
  boot-time initializer runs once, so any spec or extension calling it
  silently disables `EligibilityValidator` for the rest of the process. Either
  narrow those call sites to `unregister`, or make core registrations
  restorable — deliberately not done yet, since the alternative adds a
  two-tier concept to a public registry.
- ⬜ **No UI-state coverage.** Workflow specs are thorough; the dashboard
  surfaces they drive have none. Four bugs shipped in the post-sale UI that
  spec batteries could not catch (empty dropdowns on terminal records, a stale
  sidebar count, a menu firing without a dialog, a disabled button with no
  explanation). A Playwright walk through open → approve → resolve asserting
  menu contents at each step would cover most of them.
- ⬜ **Wave B leftovers.** `Payments::Capture` and `Refund` own the transaction
  boundary and guards, but the money movement still lives in the model
  (`Payment#capture!`, `Refund#perform!` in an `after_create`). Moving it into
  the workflows is a larger change than the boundary fix and has not been
  scheduled.
- ⬜ **`get_provider_data` has no consumer.** Declared on
  `Fulfillments::Create`, but no fulfillment provider reads the merged hash
  yet. It is a published contract with no proof it fits the providers' needs.
- ⬜ **No post-sale subscribers or mailers.** `return.requested`,
  `return.approved`, `claim.resolved` and the rest are published and nothing
  listens, so a self-service return notifies nobody. The dashboard sidebar
  counter is the only signal a merchant gets.

**Explicitly out of scope.** No workflows for CRUD. Creating, updating and
deleting a region, tax rate, API key or product is a controller plus a model
save; wrapping those in workflow classes would add hundreds of pass-through
classes with no hook, no compensation and no external I/O to justify them.
Workflows are earned by orchestration, not by being a write.

## Constraints on Current Work

- New services are plain sequential `ServiceModule` bodies (like
  `Orders::UpdateItem`) — no new `run`-pipelines, and no DSL outside
  `app/workflows/`.
- Do not hand-roll compensation/saga logic in a plain service; a flow that
  needs it belongs in `app/workflows/` on `Spree::Workflow`.
- Adding an extension hook to a plain service means graduating it to the
  workflow tier first — hooks exist only as `run_hooks` declarations.
- **No `state_machine` on a new model.** Plain `status` string, inclusion
  validation, transitions through workflows (decision 11).
- **No new business logic in model callbacks or transition callbacks** —
  especially not gateway I/O. If a save has a side effect that touches money,
  stock or an external system, it belongs in a workflow step.
- **New `set_*_context` hooks follow the collect-and-merge contract** ("Hook
  contracts" above) — handlers return a hash, never mutate shared state.
