## Overview

An upgrade between Spree releases changes data as well as code: values move to new columns, records gain the store they belong to, old formats are converted. Each of those data steps runs as a **maintenance task**.

A maintenance task gives an upgrade step what a bare rake task lacks. It runs in batches with a cursor that survives a deploy, it can be cancelled, and every run is recorded: who started it, from where, what it reported and, if it stopped, why. A half-finished upgrade therefore tells you exactly which step stopped and what already ran.

The steps of each upgrade are listed in its manifest, in the order they must run. See the [5.6 to 6.0 upgrade guide](/developer/upgrades/5.6-to-6.0) for what each one does.

## Running the upgrade

**From the command line**, the whole upgrade runs in order:

<Tabs>
  <Tab title="Spree CLI">
    ```bash
    spree upgrade
    ```
  </Tab>
  <Tab title="Without CLI">
    ```bash
    bin/rails spree:install:migrations db:migrate
    bin/rake spree:upgrade
    ```
  </Tab>
</Tabs>

The walk stops at the first step that fails or does not finish, and records nothing as complete until every step has succeeded. Re-running is safe: each step only changes data that still needs it.

To re-run one step after fixing the data that stopped it, name the step:

<Tabs>
  <Tab title="Spree CLI">
    ```bash
    spree upgrade --step migrate_returns
    ```
  </Tab>
  <Tab title="Without CLI">
    ```bash
    STEP=migrate_returns bin/rake spree:upgrade
    ```
  </Tab>
</Tabs>

A step that walks rows can preview what it would change, and a step that takes parameters reads them from `ARGS`:

```bash
DRY_RUN=1 bin/rake "spree:maintenance_tasks:perform[capture_methods]"
ARGS='batch_size=200' bin/rake "spree:maintenance_tasks:perform[deliveries]"
```

**From the dashboard**, under Settings → Maintenance tasks, the Upgrade tab lists the steps the store still needs as a checklist, each with its notes and a Run button. This is how an operator without a shell runs an upgrade. The History tab lists every run, whether it started in the dashboard, through the Admin API or on the command line.

## While a step is running

The run page shows progress and what the step has reported so far. **Cancel** stops the run at its next checkpoint, for good. Work already committed stays committed — cancelling is not an undo.

A step that fails or is cancelled is started again rather than resumed. Every step only changes data that still needs it, so a new run skips what the last one finished. Only one run of a step can be in flight at a time, so a second start is refused.

## Permissions

An upgrade step can rewrite any data in the installation, so the grant sits with the other sensitive permissions:

- `read_maintenance_tasks` — see the upgrade steps and run history.
- `write_maintenance_tasks` — start and cancel runs.

Only the admin role holds these by default. Error backtraces are shown only to callers who may act on a run, since they name internal paths.

## What a store is shown

A store installed fresh at this release sees no Upgrade tab — it has no historical data to convert. For a store that was upgraded, the tab shows the release it is moving to, with the releases it has already crossed below as completed history that cannot be re-run from the dashboard.

Which those are comes from `Spree::UpgradeRecord`, a stamp written when an upgrade walk completes and when a store is first installed. Without a stamp — a store upgraded before this record existed — the tab assumes the release immediately below the installed one and says so, pointing at the command line for the earlier steps.

Stamp a boundary by hand when you know a store already ran those steps:

```ruby
Spree::UpgradeRecord.stamp!('5.6', source: 'manual')
```

## Adding an upgrade step

A step is declared once, in the upgrade's `manifest.yml`, and names exactly one of:

- **`task`** — a rake task, for a step that is a single pass of updates. It runs through a shared runner that records it like any other run.
- **`task_class`** — a `Spree::MaintenanceTask` subclass, for a step that walks rows and benefits from progress, checkpoints and a dry run, or that takes parameters.

```ruby
# app/maintenance_tasks/spree/maintenance_tasks/upgrade/capture_methods.rb
module Spree
  module MaintenanceTasks
    module Upgrade
      class CaptureMethods < Spree::MaintenanceTask
        supports_dry_run
        collection_batch_size 5_000

        def collection
          Spree::PaymentMethod.where(capture_method: nil, auto_capture: true).order(:id)
        end

        def process(payment_method)
          return tally(:would_convert) if dry_run?

          payment_method.update_columns(capture_method: 'checkout')
          tally(:converted)
        end
      end
    end
  end
end
```

The collection must have an explicit, stable order, since the cursor is a value from that ordering. Each batch must be safe to run again: an interruption between applying a batch and recording its cursor repeats that batch. A task class named by a manifest is registered from it, so it needs no other wiring.
