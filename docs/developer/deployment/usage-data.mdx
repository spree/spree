---
title: Update Checks and Usage Data
description: How Spree tells you a newer release exists, the usage data the update check and the command line tools report, and how to turn either off.
---

When an admin opens the [Dashboard](/developer/dashboard/deployment), Spree asks `spreecloud.io` whether a newer Spree release exists, at most once a day. When one does, the dashboard tells admins who can manage the store, and shows that release's notes.

The same request carries a small amount of usage data. It tells the Spree team which versions, gems and databases are in use, so they can decide what to support and fix first. It never identifies a person. It does include your storefront's address, so it identifies the store; you can turn it off with one environment variable.

## What admins see

A dot appears on the notifications bell beside the account menu when a newer release exists. Opening the bell shows which release is available, which version you are running, and that release's notes from GitHub. The dot clears once the notifications are opened, and comes back when the next release is published.

Only admins who can manage the store see the update. The running Spree version is not shown to anyone else, and an integration using a secret API key cannot read it.

The release notes are fetched from GitHub by the admin's browser and kept there for that release. If GitHub refuses the request, for example because an office has used up GitHub's hourly limit for its address, the dialog links to the notes on GitHub instead.

The update check's answer is [cached](/developer/deployment/caching) on the server for a day, so only the first dashboard visit of the day waits on it, and never for more than two seconds. A failed check is retried after an hour, and that retry waits on spreecloud.io again. An installation without a dashboard only runs the check when a signed-in admin calls the updates endpoint of the Admin API directly.

## What is sent

| Field | Example | Notes |
| --- | --- | --- |
| `version` | `6.0.1` | The running Spree version. Always sent, even with usage data turned off. |
| `environment` | `production` | The Rails environment. |
| `url` | `https://shop.example.com` | The default store's storefront URL. This identifies the store. |
| `install_id` | `2f1f2f60-9114-4b3a-…` | A random identifier generated once per installation. It is not derived from anything about you. |
| `ruby`, `rails` | `3.4.7`, `8.1.4` | Ruby and Rails versions. |
| `database` | `postgresql` | The database adapter. |
| `gems` | `spree_api,spree_emails,spree_stripe` | Installed Spree gems. |
| `dashboard` | `true` | Whether the dashboard is configured. |
| `stores`, `products`, `orders`, `sellers` | `1-9`, `1k-9k`, `10k-99k` | Counts as ranges (`0`, `1-9`, `10-99`, `100-999`, `1k-9k`, `10k-99k`, `100k+`), never exact numbers. Sellers are sent only when there are any. |

### What is never sent

- Names, email addresses or any other customer, admin or seller data
- Order contents, prices, revenue or exact counts
- Store names, settings, credentials or API keys

The IP address a request comes from is not saved with the data.

## Turning it off

Two switches, both environment variables. See [Environment Variables](/developer/deployment/environment_variables) for where to set them.

| Variable | Effect |
| --- | --- |
| `SPREE_TELEMETRY_DISABLED=1` | Stops the usage data. The daily check still runs, but sends only `version`, so the update notice keeps working. `DO_NOT_TRACK=1` does the same. |
| `SPREE_UPDATE_CHECK_DISABLED=1` | Stops the daily request entirely. Nothing is sent and the update notice never appears. |

You can set the same switches from Ruby instead:

```ruby server/config/initializers/spree.rb
Spree.config do |config|
  config.telemetry_enabled = false     # send the version only
  config.update_check_enabled = false  # send nothing at all
end
```

Either way, turning a switch off wins over the other method: an environment variable cannot turn back on what the initializer turned off, and the reverse.

The check never runs in the `test` environment or on a CI server (any machine with the `CI` environment variable set, which GitHub Actions, GitLab CI, CircleCI and most other services do), so test runs send nothing.

## Command line tools

The [Spree CLI](/developer/cli/quickstart) and `create-spree-app` report how setup goes, so the Spree team can see where new projects get stuck. They send one event each time you run one of these commands yourself: `create-spree-app`, and `spree init`, `add`, `dev`, `upgrade`, `eject`, `build`, `plugin` and `generate`.

Nothing is sent for any other command, such as `spree api` or `spree exec`, when the command runs in a script, a pipe or CI, or for the `spree init` and `spree add` that `create-spree-app` runs for you. The event is sent in the background after the command finishes, so it never slows a command down or makes it fail. The first time, the CLI prints a notice saying so.

| Field | Example | Notes |
| --- | --- | --- |
| `command` | `dev` | Which command ran. Never its arguments. |
| `status`, `exit_code` | `ok`, `0` | Whether it succeeded, failed, or you cancelled it. Never the error message. |
| `duration_ms` | `8421` | How long it took. |
| `cli`, `cli_version` | `@spree/cli`, `1.4.0` | Which tool and version. |
| `node_version`, `package_manager` | `24.4.0`, `pnpm` | The Node.js version and package manager. |
| `os`, `arch`, `docker` | `darwin`, `arm64`, `false` | The operating system, processor type, and whether it ran inside Docker. |
| `machine_id` | `2f1f2f60-9114-4b3a-…` | A random identifier created once on your machine. It is not derived from anything about you. |
| `project_id` | `3f1c…` | A one-way hash of the project's git remote, keyed with your machine ID, so runs of one project on one machine can be grouped. The remote is never sent, and the hash cannot be matched against a list of public repositories. |
| `options` | `storefront: true` | For `create-spree-app` only: the choices you made, such as including a storefront. |

To turn it off on your machine:

<Tabs>
  <Tab title="Spree CLI">
    ```bash
    spree telemetry disable
    ```
  </Tab>
  <Tab title="Environment variable">
    ```bash
    export SPREE_TELEMETRY_DISABLED=1
    ```
  </Tab>
</Tabs>

`DO_NOT_TRACK=1` works too. `spree telemetry status` shows whether reporting is on and why.
