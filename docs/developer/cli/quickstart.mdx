The Spree CLI (`@spree/cli`) does two things from your terminal:

1. **Manages your Spree project** — boot the Docker stack, run generators and migrations, tail logs, open a console, upgrade versions.
2. **Calls the Admin API** — generic `get`/`post`/`patch`/`delete` commands to read, write, and explore your store's data, with zero-config credentials in local dev. See [Admin API from the CLI](/developer/cli/admin-api).

```bash
spree dev                                                  # boot the project
spree api get /orders -q status_eq=placed --limit 10     # query the Admin API
spree api post /products -d '{"name":"Classic Tee","prices":[{"currency":"USD","amount":"29.99"}]}'  # create a resource
spree api endpoints --search refund                        # discover endpoints, offline
```

The `spree api` commands work against any Spree 5.5+ instance and are built for both humans and AI agents — see the dedicated [Admin API from the CLI](/developer/cli/admin-api) guide. The rest of this page covers project management.

## Installation

The CLI is included automatically when you scaffold a project with `create-spree-app`. You can also install it globally:

```bash
npm install -g @spree/cli
```

Then run commands from your project directory:

```bash
spree dev
```

Or use `npx` without installing:

```bash
npx @spree/cli dev
```

## Commands

### `spree init`

First-run setup. Starts Docker services, seeds the database, generates an API key, and optionally loads sample data.

```bash
spree init
spree init --no-sample-data   # Skip sample data
spree init --no-open           # Skip opening browser
```

### `spree dev`

Run the app in the foreground — streams web + worker logs; `Ctrl+C` stops them. The databases keep running for a fast next boot (`spree stop` shuts everything down).

```bash
spree dev
```

### `spree stop`

Stop all services.

```bash
spree stop
```

### `spree restart`

Restart `web` and `worker` in place — same image, same volumes, fresh backend process. Good for configuration changes the backend doesn't reload on its own.

```bash
spree restart
```

Not appropriate for dependency changes (Ctrl+C and re-run `spree dev`), Dockerfile or runtime version changes (use `spree build`), or compose file changes (Ctrl+C and re-run `spree dev`).

### `spree update`

Pull the latest Spree Docker image and recreate containers. Migrations run automatically on startup.

```bash
spree update
```

### `spree build`

Rebuild the dev image after Dockerfile or runtime version changes. Only relevant after `spree eject`.

```bash
spree build
spree build --reset-deps     # Also drop the cached backend dependencies so they re-install
spree build --yes            # Skip confirmation prompts (for CI)
```

`spree add <extension>` does NOT require a rebuild — dependencies land in a cache volume which survives image rebuilds.

`--reset-deps` only drops that cache. Postgres, Redis, Meilisearch, and storage volumes are preserved.

### `spree upgrade`

Walk a Spree version upgrade end-to-end inside the dev stack. Updates the Spree packages, applies pending migrations, then walks the version-specific data backfills from the upgrade manifest.

```bash
spree upgrade                  # Detect target, run the full sequence interactively
spree upgrade --plan           # Print the plan without executing
spree upgrade --to 5.5         # Cap the walk at a specific target version
spree upgrade --step <id>      # Re-run a single step idempotently (skips the update + migrate)
spree upgrade --yes            # Skip the per-step prompts
```

Production upgrades only need the third stage — installing dependencies and migrating happen in your deploy pipeline. The CLI runs all three for local development. See [Upgrades](/developer/upgrades) for the manual production path.

### `spree eject`

Switch from the prebuilt Docker image to building from your local `server/` directory. This lets you customize the backend — add extensions, override models, add migrations, etc.

```bash
spree eject
```

After ejecting, the Docker image is built from `server/Dockerfile`. Edit files in `server/` and run `spree dev` to rebuild and restart with your changes.

See [Customizing the Backend](/developer/create-spree-app/quickstart#customizing-the-backend) for details on what you can customize.

### `spree add`

Add an app or an extension to your project.

```bash
spree add dashboard           # React Admin Dashboard in apps/dashboard
spree add seller-dashboard    # Seller Panel in apps/seller-dashboard
spree add spree_stripe        # An extension, by its package name
```

For an extension, `spree add` installs the package, runs the extension's installer when it ships one, and restarts a running stack so the server loads it.

### `spree logs`

Stream service logs.

```bash
spree logs         # Web service (default)
spree logs worker  # Worker service
```

### `spree console`

Open an interactive backend console.

```bash
spree console
```

### `spree shell`

Open an interactive bash shell inside the web container — the system-shell sibling of `spree console` and `spree db:console` (psql). If the web container is down, it starts a one-off container against the same volumes instead. For one-off non-interactive commands, use `spree exec`.

```bash
spree shell
spree bash    # alias
```

### `spree open`

Open the admin dashboard in the browser.

```bash
spree open
```

### `spree seed`

Seed the database.

```bash
spree seed
```

### `spree sample-data`

Load sample products, categories, and images.

```bash
spree sample-data
```

### `spree user create`

Create an admin user. Prompts for email and password interactively, or pass them as flags:

```bash
spree user create
spree user create --email admin@example.com --password secret123
```

### `spree api-key`

Manage Store and Admin API keys. Secret keys carry [scopes](/api-reference/admin-api/authentication) and require at least one.

```bash
spree api-key list                                     # List all keys
spree api-key create                                   # Interactive
spree api-key create --name "Storefront" --type publishable             # Store API key
spree api-key create --name "Admin" --type secret --scopes read_all     # Admin API key
spree api-key revoke <id>                              # Revoke a key
```

### `spree encryption init`

Generate [Active Record encryption](/developer/deployment/environment_variables#active-record-encryption) keys — Spree encrypts webhook signing secrets, payment gateway customer IDs and OAuth tokens with them. New projects already have keys; use this for projects created before they were generated at setup.

```bash
spree encryption init            # Add ACTIVE_RECORD_ENCRYPTION_* keys to the project's .env
spree encryption init --print    # Print a fresh set without writing anything (e.g. for your hosting provider)
```

It never overwrites keys `.env` already sets, and there is no `--force`: changing the keys makes data encrypted with them unreadable. Afterwards, recreate the containers so they load the new `.env` (`spree update`, or `spree dev` for an ejected project — `spree restart` keeps the old environment), and back the keys up in your secret manager.

### `spree api`

Call the Admin API with generic `get`/`post`/`patch`/`delete` commands — zero-config inside a project (a read-only key is minted on first use), env vars or profiles for remote stores. See [Admin API from the CLI](/developer/cli/admin-api) for the full guide.

```bash
spree api get /products -q status_eq=active --limit 10
spree api post /products -d '{"name":"Classic Tee","prices":[{"currency":"USD","amount":"29.99"}]}'
spree api endpoints --resource orders    # endpoints + required scopes, offline
spree api schema "POST /orders"          # request/response schema, offline
spree api status
```

### `spree auth`

Save Admin API credentials for remote stores as named profiles.

```bash
spree auth login --profile prod --base-url https://store.example.com
spree api get /orders --profile prod
spree auth status
spree auth logout --profile prod
```

## Dev workflow commands

Each command runs inside the project's containers against the running stack.

### `spree generate`

Scaffold a new API resource.

```bash
spree generate api_resource Brand name:string slug:string:uniq
```

`api_resource` scaffolds the full v3 surface: model, migration, Store + Admin controllers and serializers, factory, controller specs, routes, and the `read_<resources>` / `write_<resources>` permissions that let staff roles and secret API keys reach the Admin API.

### `spree migrate`

Install pending Spree migrations, then run them — the canonical post-update sequence.

```bash
spree migrate
spree migrate:status               # show which migrations have run
spree migrate:rollback             # roll back the last migration
spree migrate:rollback --steps 2   # roll back the last two
```

### `spree db:reset`

Drop, recreate, migrate, and seed the database. **Destructive** — wipes everything. Asks for confirmation.

```bash
spree db:reset
spree db:reset --yes   # Skip confirmation (for CI)
```

### `spree db:console`

Open a `psql` session against the dev Postgres database (runs inside the `postgres` container).

```bash
spree db:console
```

### `spree test`

Run the backend test suite inside the web container against the test database — never your development data. Everything after `test` passes through, so file paths, line numbers, and flags work as usual.

```bash
spree test                                      # full suite
spree test spec/models/spree/brand_spec.rb      # one file
spree test spec/models/spree/brand_spec.rb:15   # one example
spree test --format documentation
```

Before the first run, create the test database with `spree exec bin/rails db:test:prepare`. See the [Testing tutorial](/developer/tutorial/testing) for writing specs.

## Running things inside the container

### `spree task`

Run a Spree maintenance task. Anything after the task name passes through.

```bash
spree task load_sample_data
spree task search:reindex
spree task price_history:seed
spree task price_history:prune
```

### `spree exec`

Run an arbitrary command inside the `web` container. Use it for anything without a dedicated command.

```bash
spree exec ls -la
spree exec env
spree exec bin/rails runner "puts Spree::Product.count"
spree exec bundle outdated
```

### Deprecated commands

These commands still work in Spree 6 and print a notice naming their replacement. They are removed in Spree 7, when the backend moves from Rails to Node.

| Deprecated | Use instead |
| --- | --- |
| `spree exec bin/rails …` | `spree exec bin/rails …` |
| `spree exec bin/rake spree:<task>` | `spree task <task>` |
| `spree exec bin/rake <other task>` | `spree exec bin/rake <other task>` |
| `spree bundle add <extension>` | `spree add <extension>` |
| `spree bundle …` | `spree exec bundle …` |
| `spree test …` | `spree test …` |
| `spree routes` | `spree api endpoints` |
| `spree generate <anything but api_resource>` | `spree exec bin/rails generate …` |
| `spree generate <extension>:install` | `spree add <extension>` |
| `spree migrate:rollback STEP=n` | `spree migrate:rollback --steps n` |
| `spree build --reset-bundle` | `spree build --reset-deps` |
| `spree plugin new --ruby-name`, `--no-engine` | `--backend-name`, `--no-backend` |

## Pair with AI agents

The CLI's predictable command surface is what AI coding agents drive when working on Spree projects. The [Spree agent skills](/developer/agentic/agent-skills) teach agents these commands and conventions, and the Claude Code plugin adds `/spree:doctor` (stack diagnosis) and `/spree:audit-upgrade` (upgrade-readiness audit) on top. See [Agentic Development](/developer/agentic/overview).
