The client exposes a `request` method — the same function that powers all built-in resources. Use it to call any Store API endpoint, including ones you've added yourself.

```typescript
import { createClient } from '@spree/sdk'
import type { PaginatedResponse } from '@spree/sdk'

const client = createClient({
  baseUrl: 'https://api.mystore.com',
  publishableKey: 'pk_YOUR_KEY',
})

interface Brand {
  id: string
  name: string
  slug: string | null
  description: string | null
  logo_url: string | null
}

// Paths are relative to /api/v3/store
const brands = await client.request<PaginatedResponse<Brand>>('GET', '/brands')
const nike = await client.request<Brand>('GET', '/brands/nike')
```

`client.request` uses the same auth headers, retry logic, and locale/currency defaults as `client.products.list()` or any other built-in resource.

For a complete walkthrough — creating the API endpoints on the backend, defining TypeScript types, filtering, and expanding associations — see the [API](/developer/tutorial/model-and-api) and [SDK](/developer/tutorial/storefront) tutorials.

## Shipping a client for an extension

An extension that adds Store API endpoints can ship a typed client for them as an npm package. The package defines an extension with `defineStoreExtension`, and an app adds it to its client with `extend`:

```typescript
// in the extension's package
import { defineStoreExtension } from '@spree/sdk'
import type { Quote } from './types'

export const storeQuotes = defineStoreExtension('quotes', ({ request }) => ({
  get: (id: string) => request<Quote>('GET', `/quotes/${id}`),
  accept: (id: string) => request<Quote>('PATCH', `/quotes/${id}/accept`),
}))
```

```typescript
// in the app
import { createClient } from '@spree/sdk'
import { storeQuotes } from 'my-quotes-extension'

const client = createClient({ baseUrl, publishableKey }).extend(storeQuotes)

const quote = await client.quotes.get('quote_1') // typed as Quote
```

- `request` is the client's own: paths are relative to `/api/v3/store`, and the extension's calls carry the same auth, headers, retries and defaults as the built-in resources.
- `extend` returns a new client and leaves the original as it was. Both share their settings, so a token or locale set on either one applies to the other.
- Extensions chain: `client.extend(quotes).extend(loyalty)`.
- An extension adds a new namespace only. `extend` throws a `TypeError` for a name the client already has (`products`, or the same extension twice) and for an extension of another API.
- The package lists `@spree/sdk` as a peer dependency, so the app's own client is the one extended.

### Generating the extension's types

The extension documents its endpoints in its own `openapi/*.yaml` with rswag (see [documenting your extension's endpoints](/developer/mcp/custom-tools#documenting-your-extensions-endpoints)). The package generates its request body and list filter types from those documents, the same way the SDKs generate theirs:

```bash
spree sdk types --spec ../my_extension/openapi/admin.yaml --spec ../my_extension/openapi/store.yaml
```

This writes `src/types/<api>/params/` and `src/types/<api>/filters.ts`, which the extension's methods use for their arguments:

```typescript
import type { QuoteCreateParams } from './types/store/params'
```

Response types come from the extension's serializers, with [Typelizer](https://github.com/skryukov/typelizer), as Spree's own do. Add the task to the extension's Rakefile:

```ruby Rakefile
require 'spree/api/sdk_types_task'
Spree::Api::SdkTypesTask.new(engine: 'MyExtension::Engine', out: '../my-extension-sdk/src/types')
```

and run it from the extension's root, against its test app:

```bash
cd ../my_extension
bundle exec rake test_app                  # once, and after changing the install generator
bundle exec rake spree:sdk:serializer_types
```

It writes `src/types/<api>/generated/` for the serializers under the engine's `app/serializers`, by namespace (`Admin::` for the Admin API, `Seller::` for the Seller API, the rest Store), and a `src/types/<api>/spree.ts` they import from. That file re-exports the SDK's types beside the package's own, so a `Quote` that nests an order uses the SDK's `Order` rather than a copy. A named value list (`enum_type_name:`) is defined in the package and stays open to values a store adds.

Give the extension's serializers names the SDK does not use: a `QuoteSerializer` is fine, but an `OrderSerializer` would generate an `Order` that clashes with the SDK's in `spree.ts`, which TypeScript reports as an error. Two serializers of one API that end in the same name (`Orders::ItemSerializer` and `Returns::ItemSerializer`) are refused for the same reason.
