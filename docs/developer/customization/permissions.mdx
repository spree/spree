title: Permissions
---

Spree authorizes staff through **roles** that hold flat **permission keys** from a single catalog. Merchants manage everything in the dashboard — no Ruby required — and the same vocabulary powers secret API key scopes, so a role grant and a key scope always mean the same thing.

## The permission catalog

Every grantable capability is a key of the form `read_<resource>` or `write_<resource>` — `read_orders`, `write_products`, `write_staff`, and so on. Each resource covers a slice of the Admin API and the models behind it; `write_*` implies the matching `read_*`.

Discover the catalog at runtime:

```bash
GET /api/v3/admin/permissions
```

Each entry describes the key, its resource, its `read`/`write` kind, a UI group, and localized labels — the role editor and the API-key scope picker are both rendered from this endpoint.

The important granularity choice: keys are **per resource, not per action**. There is no `cancel_orders` — `write_orders` covers all order writes. The money-adjacent areas are separate resources (`payments`, `refunds`, `gift_cards`, `store_credits`), so "customer service can view orders but cannot refund" is simply `read_orders` without `write_refunds`.

## Managing roles

Roles are data. Create and edit them in the dashboard under **Settings → Roles**: each role has a name, a description, and a permission grid; staff are assigned roles per store from **Settings → Staff**.

The same surface exists on the Admin API:

```bash
GET    /api/v3/admin/roles
POST   /api/v3/admin/roles      # { name, description, permissions: ["read_orders", ...] }
PATCH  /api/v3/admin/roles/:id
DELETE /api/v3/admin/roles/:id
```

For reproducible environments, seed roles with plain ActiveRecord:

```ruby
# db/seeds.rb
Spree::Role.find_or_create_by!(name: 'support')
  .update!(permissions: %w[read_orders read_customers], description: 'Read-only support')
```

A few rules the server enforces everywhere:

- **The `admin` role is protected.** It always grants everything and cannot be renamed, re-permissioned, or deleted.
- **Locked roles.** A role with `mutable: false` (set from seeds or the console) renders read-only in the dashboard — for roles a host application does not want store staff to edit.
- **A role in use cannot be deleted.** Reassign staff and revoke pending invitations first.
- **No privilege escalation.** A caller can only grant permissions they effectively hold — when creating or editing roles, assigning roles to staff, inviting staff, or minting API keys. Only admins can grant the `admin` role.

## How enforcement works

Every Admin API controller declares the resource it belongs to. On each request the principal's keys — a staff member's role permissions, or a secret key's scopes — are checked against `read_<resource>` or `write_<resource>` depending on the action. A missing key produces a 403 that names it:

```json
{
  "error": {
    "code": "access_denied",
    "message": "Missing permission: write_orders",
    "details": { "required_permission": "write_orders" }
  }
}
```

Behind that gate, keys compile to [CanCanCan](https://github.com/CanCanCommunity/cancancan) rules (a read key grants `can [:read, :admin]` on the resource's models; a write key grants `can :manage`), which handle record-level concerns. `GET /api/v3/admin/me` returns both views — the rule dump the dashboard mirrors for UI gating, and `permission_keys`, the flat list of keys the user holds on the current store.

Storefront customers are **not** part of this system. Customer authorization is ownership — carts and orders by token or account, addresses by `user_id` — enforced by a fixed internal baseline and the Store API's scoped lookups. There is nothing to configure.

## Extensions: registering permissions

An extension registers its resources into the catalog once. The keys appear in the role editor, become mintable API-key scopes, and gate the extension's admin endpoints — no further wiring:

```ruby
# in your engine's initializer
Spree.permissions.register_resource(:reviews, group: :catalog, subjects: -> {
  [SpreeReviews::Review]
})
```

- `group` places the row in the permission pickers (`:orders`, `:catalog`, `:marketing`, `:customers`, `:settings`, `:access`, `:analytics` — or your own).
- `subjects` is a lambda returning the CanCanCan subjects the keys grant; it resolves lazily, so load order does not matter.
- Pass `write: false` for read-only resources (like the analytics dashboard).

Localize the labels in your engine's locale file:

```yaml
en:
  spree:
    permissions_catalog:
      resources:
        reviews:
          label: Reviews
          description: Moderate and reply to product reviews
```

Your admin controllers then declare the same resource:

```ruby
class SpreeReviews::Admin::ReviewsController < Spree::Api::V3::Admin::ResourceController
  scoped_resource :reviews
end
```

## Advanced: record-level custom rules

The catalog is deliberately flat. When a host application needs rules the catalog cannot express — regional restrictions, ownership conditions — register a plain `CanCan::Ability` class; its rules merge into every ability:

```ruby
# app/models/regional_support_ability.rb
class RegionalSupportAbility
  include CanCan::Ability

  def initialize(user)
    return unless user.respond_to?(:market_id) && user.market_id

    cannot :manage, Spree::Order
    can [:read, :admin], Spree::Order, market_id: user.market_id
  end
end

# config/initializers/spree.rb
Spree::Ability.register_ability(RegionalSupportAbility)
```

Keep record-state rules ("a completed order cannot be deleted") out of abilities entirely — they belong on models and workflows, where every caller hits them, including secret API keys that never consult CanCanCan.
