## Sentry

`@spree/dashboard-sentry` reports errors from the admin dashboard and the seller panel. Install it in each app you deploy:

```bash
pnpm add @spree/dashboard-sentry
```

Then start it from the app's entry module, `src/main.tsx`, before the app renders:

```tsx
import { initDashboardSentry } from '@spree/dashboard-sentry'

initDashboardSentry({
  dsn: import.meta.env.VITE_SENTRY_DSN,
  release: import.meta.env.VITE_SENTRY_RELEASE,
})
```

Use the DSN of a browser (React) Sentry project. It is public by design, and with no DSN the call does nothing, so the same build runs with Sentry on or off. `initDashboardSentry` takes any [Sentry browser option](https://docs.sentry.io/platforms/javascript/guides/react/configuration/options/), plus:

| Option | Default | Purpose |
|---|---|---|
| `environment` | The Vite mode, such as `production` | Environment name on each event |
| `enableInDevelopment` | `false` | Report from the dev server too. Development builds stay quiet otherwise |

`VITE_` values are compiled into the browser bundle, so set them when you build, not only when you run the server. Call it the same way in the seller panel's `src/main.tsx`.

What gets reported:

- Uncaught errors and unhandled promise rejections.
- Errors a page throws while rendering or loading data, including the ones the panel's error screen catches and shows.
- The signed-in user's ID and email, cleared on sign-out.
- A `panel` tag, `admin` or `seller`, so both apps can share one Sentry project. Events raised while the app starts are tagged too.

Not-found pages and redirects are not errors and are skipped. Single-use tokens in password reset, email confirmation and invitation links are replaced with `redacted` in error events and breadcrumbs before they leave the browser, after your own `beforeSend` and `beforeBreadcrumb` run.

The plugin turns on error reporting only. Tracing, Session Replay and other Sentry features stay off unless you pass their options. Token redaction does not cover them: replays and trace spans can record the page URL, including a reset or invitation token.

## Another service

An error-tracking plugin needs two things from the dashboard:

- `errorReporters` in `defineDashboardPlugin`, keyed by a unique id. Each one is called with every error the panel's error screens catch. These errors never reach `window.onerror`, where most error trackers listen.
- The [`app.root` slot](/developer/dashboard/slots-catalog#app-root), rendered once inside the signed-in session, to attach the user to reports.

```tsx
import { APP_ROOT_SLOT, type AppRootSlotContext, defineDashboardPlugin, useAuth } from '@spree/dashboard-core'
import { useEffect } from 'react'
import { tracker } from './tracker'

function TrackerUser({ panel }: AppRootSlotContext) {
  const { user, isInitializing } = useAuth()
  useEffect(() => {
    if (isInitializing) return
    tracker.setUser(user ? { id: user.id, panel } : null)
  }, [user, panel, isInitializing])
  return null
}

defineDashboardPlugin({
  errorReporters: { tracker: (error) => tracker.capture(error) },
  slots: { [APP_ROOT_SLOT]: [{ id: 'tracker-user', component: TrackerUser as never }] },
})
```

An error boundary of your own reports the same way: pass `reportCaughtError` from `@spree/dashboard-core` as the `onCatch` of `RouteErrorBoundary` or TanStack Router's `CatchBoundary`.

Call `defineDashboardPlugin` from a function the host calls in its entry module, as `initDashboardSentry` does, or mark the package as a dashboard plugin so both panels load it on install — see [Distributing plugins](/developer/dashboard/plugins/distributing).
