## Check it is installed

A new Spree store has the server already — `spree_mcp` is in the starter's
`Gemfile`, so the endpoint is live the first time you boot:

```text
https://your-store.com/api/v3/admin/mcp
```

<Note>
  Nothing to configure, and no migration for the server itself. The OAuth
  tables ship with `spree_core` and arrive with Spree's other migrations.
</Note>

Upgrading an older store, or deliberately removed it? Add the gem back:

<Tabs>
  <Tab title="Spree CLI">
    ```bash
    spree add mcp
    ```
  </Tab>
  <Tab title="Without CLI">
    ```ruby server/Gemfile
    gem 'spree_mcp'
    ```

    ```bash
    bundle install
    ```
  </Tab>
</Tabs>

## Connect a client

Paste the URL into your MCP client. It sends you to Spree, you sign in, and you approve what the agent may do.

<Tabs>
  <Tab title="Claude Code">
    ```bash
    claude mcp add --transport http spree https://your-store.com/api/v3/admin/mcp
    ```
  </Tab>
  <Tab title="Claude Desktop / claude.ai">
    **Settings → Connectors → Add custom connector**, then paste the URL.

    This client asks for a **Client ID** as well. Copy it from
    **Settings → OAuth clients** in your Spree dashboard, where each
    registered client shows one — it is public, and is what identifies the
    connector to your store.
  </Tab>
  <Tab title="Cursor">
    ```json .cursor/mcp.json
    {
      "mcpServers": {
        "spree": {
          "url": "https://your-store.com/api/v3/admin/mcp"
        }
      }
    }
    ```
  </Tab>
  <Tab title="VS Code">
    ```json .vscode/mcp.json
    {
      "servers": {
        "spree": {
          "type": "http",
          "url": "https://your-store.com/api/v3/admin/mcp"
        }
      }
    }
    ```
  </Tab>
</Tabs>

That is the whole setup. There is no key to mint, paste or rotate — the client discovers how to authorize itself from the endpoint, and you approve it in a browser.

<Note>
  A Spree API key is **not** accepted here, deliberately: an agent acts for a person, so it carries that person's own permissions rather than a standing credential with nobody behind it. For access that cannot sign in — a CI job, a server-side integration — use the [`spree api` CLI](/developer/cli/admin-api).
</Note>

## Approve what it may do

Signing in brings up a consent screen listing the permissions the client asked for. Tick the ones you want it to have.

What you approve matters more than it looks:

- **An agent never gets more than you have.** The grant narrows your own permissions, so a staff member who cannot issue refunds cannot approve an agent that can.
- **Only what you approved.** Approving product access does not quietly include orders — the tools for anything else are not even offered to the model.
- **It is yours, not the store's.** Each person connects for themselves, so an agent's actions are recorded against whoever approved it.

[Permissions and consent](/developer/mcp/permissions) covers this in full.

## The first conversation

The agent picks tools from what you ask; there is no command to learn.

> **You:** Which products are out of stock, and what did we sell in Germany last month?

It calls `describe_resource` to learn that products can be filtered by an `out_of_stock` scope, `search_resources` to list them, then `describe_reporting` and `query_report` for the German figures — and answers in one reply.

> **You:** Create a product called Expensive Bag with two variants, size S and M, 100 in stock each, priced 199 USD.

It calls `create_resource` once, with the variants, their prices and their stock levels nested in the same write.

> **You:** Cancel order R123456789 and tell the customer why.

It finds the order, then calls `orders_cancel`. Your client asks you to confirm before the call runs, because the tool declares that it changes data. Spree then runs the same cancellation the dashboard runs, and the order's timeline records who cancelled it.

## Check what it can see

Ask the agent directly — `describe_resource` with no arguments lists every resource the connection reaches, and the client's own tool list shows what it was offered. A connection approved for products alone sees roughly a dozen tools rather than all 58.

## Troubleshooting

<AccordionGroup>
  <Accordion title="The client says the server needs authorization and nothing happens">
    The endpoint advertises its authorization server at `/api/v3/oauth/protected-resource/mcp`. If your store sits behind a proxy that rewrites the host, the advertised URL has to be one the browser can reach — check that `Spree::Store#url` and the incoming `Host` header agree.
  </Accordion>

  <Accordion title="Connected, but the agent says it cannot do something">
    It was not granted that permission. **Settings → Connected apps** shows what each connection holds; revoke and reconnect to approve more. Tools outside the grant are not offered at all, so the agent will say it has no way to do it rather than failing mid-call.
  </Accordion>

  <Accordion title="A tool exists but refuses with a permission error">
    Tool visibility is per permission, but the data behind it is checked per record and per resource. A connection granted `read_reports` can run a report, and will still be refused a dimension that exposes customers unless it also holds `read_customers`.
  </Accordion>

  <Accordion title="Nothing is listed under Connected apps">
    Connections are per person. You are looking at your own; another staff member's connection appears under theirs.
  </Accordion>
</AccordionGroup>
