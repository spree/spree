58 tools ship with the server. An agent is only ever shown the ones its grant permits, so a connection approved for products alone sees roughly a dozen.

The catalog is deliberately not a mirror of the API's 500-odd operations — a tool list that size makes a model worse at choosing, not better. Tools cover the operations a merchant asks for by name; everything else is reached through the three generic ones under [store setup](#store-setup).

<Note>
  The **Permission** column is what a grant must hold for the tool to be offered. A dash means the tool carries no permission of its own and is gated per resource instead: `search_resources` is offered to everyone, but only lists resources the grant can read.

  The last column says whether the tool reads or writes. A write asks your client to confirm before it runs.
</Note>

## Resources

Beyond tools, the server offers MCP **resources** — files a client can fetch rather than operations it can run.

| Resource | What it is |
| --- | --- |
| `spree+export://<id>` | A finished export, as CSV. Reading one costs the same permission as reading the records in it. |

A product's media, an order's purchase order and an import's own file are things an agent *puts* there rather than reads back, so they are uploads rather than resources.

## What no tool will do

Some things are out of reach whatever a grant holds.

- **Credentials.** API keys, integrations, webhook endpoints and gift card codes are never returned by any tool. A gift card code is the money itself, and an integration's settings are where provider credentials live.
- **Minting another credential.** A grant cannot create API keys, roles, staff accounts or another OAuth client — so an agent can never widen its own reach.
- **Erasing a customer.** GDPR erasure is irreversible and is not something to put behind a single confirmation prompt. Do it in the dashboard.
- **Order editing.** Adding line items, discounts and fees to an existing order runs through paths that are not yet workflows. Cancelling, refunding and fulfilling all work today.

25 further workflows are excluded for reasons a contract spec enforces, so one cannot be exposed by accident.

## Writing records

Three tools cover every resource the Admin API can write, rather than one tool per resource:

- `create_resource`, `update_resource`, `delete_resource`

They dispatch to the real endpoint, so a resource whose controller runs a workflow gets that workflow. Two things worth knowing:

**Nested records travel with their parent.** A product's variants carry their own options, prices and stock levels in the same write, so creating a product with two sized variants is one call rather than four. `describe_resource` reports what fits inside each list.

**A list replaces rather than appends.** Sending one variant leaves a product with one variant. Send every row you want to keep.
