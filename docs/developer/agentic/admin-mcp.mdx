Your store can host a [Model Context Protocol](https://modelcontextprotocol.io) server of its own. Where the [docs MCP server](/developer/agentic/mcp) lets an agent read Spree's documentation, this one lets an agent operate *your* store: find products, answer "what did we sell in Germany last month", cancel an order, mark a shipment delivered, add a market.

It runs inside your Spree application — there is no separate service to deploy — and a request goes through the same tenancy, permission and validation rules as the Admin API. An agent can do exactly what the credential you give it allows, and nothing else.

```text
https://your-store.com/api/v3/admin/mcp
```

<Note>
  The server is an optional gem. Add `spree_mcp` to your `Gemfile` and restart; there is nothing else to configure.

  ```ruby server/Gemfile
  gem 'spree_mcp'
  ```
</Note>

## Two ways to connect

| | Who it is for | What the agent may do |
| --- | --- | --- |
| **Sign in** (OAuth) | A merchant connecting a consumer client — claude.ai, Claude Desktop, ChatGPT | What the signed-in person approves, never more than their own role allows |
| **A secret API key** | A developer configuring an agent they run themselves — Claude Code, Cursor, VS Code, your own code | Exactly the scopes on the key |

Signing in needs nothing created first: paste your store's MCP URL into the client, and it will walk you through approving access. Everything below the next section is the key-based path.

## Signing in

A consumer client asks for your store URL, then opens a Spree page listing what it wants to do. Approve it and the client is connected; nothing is copied or pasted.

```text
https://your-store.com/api/v3/admin/mcp
```

What you approve matters more than it looks:

- **An agent never gets more than you have.** The grant narrows your own permissions, so a staff member who cannot issue refunds cannot approve an agent that can.
- **Only what you approved.** Approving product access does not quietly include orders — the tools for anything else are not even offered.
- **Revoke whenever you like.** **Settings → Connected apps** lists everything connected, with the last time each was used. Revoking stops it on its next call.

Each person connects for themselves, so an agent's actions are recorded against the person who approved it.

## Mint a key first

For an agent you run yourself, the credential is an ordinary Spree secret API key, and its scopes decide what the agent is even told exists. A key that can read orders is never shown a refund tool.

1. In the dashboard, go to **Settings → API keys** and create a **secret** key.
2. Name it after the agent that will hold it — "Claude Code, orders" — so you know what you are revoking later.
3. Grant only the scopes that agent needs. `read_products` for a merchandising assistant; add `write_orders` only if it should genuinely be able to cancel and refund.
4. Copy the key. It is shown once.

Revoking the key in the dashboard is the off switch, and it takes effect on the agent's next call.

<Warning>
  Give an agent the narrowest scopes that let it do its job. A tool that moves money — refunds, payment capture — is offered to any key holding `write_orders`, and the only thing standing between the model and the action is your client's confirmation prompt.
</Warning>

## Setup with a key

The key travels as a header on every request. Spree accepts it as `X-Spree-API-Key` — the Admin API's own header — or as `Authorization: Bearer`, for clients that only offer a bearer-token field.

<Tabs>
  <Tab title="Claude Code">
    ```bash
    claude mcp add --transport http spree-admin https://your-store.com/api/v3/admin/mcp \
      --header "X-Spree-API-Key: sk_your_key"
    ```

    To share the connection with your team without putting the key in git, commit a project `.mcp.json` that reads it from the environment and let each developer export their own:

    ```json .mcp.json
    {
      "mcpServers": {
        "spree-admin": {
          "type": "http",
          "url": "https://your-store.com/api/v3/admin/mcp",
          "headers": { "X-Spree-API-Key": "${SPREE_API_KEY}" }
        }
      }
    }
    ```
  </Tab>
  <Tab title="Cursor">
    Add to `~/.cursor/mcp.json` for yourself, or `.cursor/mcp.json` in the project to share it with your team:

    ```json
    {
      "mcpServers": {
        "spree-admin": {
          "url": "https://your-store.com/api/v3/admin/mcp",
          "headers": { "X-Spree-API-Key": "sk_your_key" }
        }
      }
    }
    ```

    Cursor reads the key from the file, so a project config puts a live credential in your repository. Either keep it in `~/.cursor/mcp.json`, which is outside the project, or add `.cursor/mcp.json` to `.gitignore` and have each developer mint their own key.
  </Tab>
  <Tab title="VS Code (Copilot)">
    Add to `.vscode/mcp.json`. The `inputs` block prompts for the key instead of storing it in the file:

    ```json
    {
      "inputs": [
        { "id": "spree-key", "type": "promptString", "description": "Spree secret API key", "password": true }
      ],
      "servers": {
        "spree-admin": {
          "type": "http",
          "url": "https://your-store.com/api/v3/admin/mcp",
          "headers": { "X-Spree-API-Key": "${input:spree-key}" }
        }
      }
    }
    ```
  </Tab>
  <Tab title="Your own agent">
    Any HTTP client works. Post one JSON-RPC message per request:

    ```bash
    curl https://your-store.com/api/v3/admin/mcp \
      -H "Content-Type: application/json" \
      -H "X-Spree-API-Key: sk_your_key" \
      -d '{"jsonrpc":"2.0","id":1,"method":"tools/list"}'
    ```
  </Tab>
</Tabs>

<Note>
  Every client above carries the key in its own configuration. A consumer connector — claude.ai, Claude Desktop's connector UI, ChatGPT — has nowhere to put one: it connects from the vendor's servers rather than your machine. Those sign in instead, as described above.
</Note>

## What the agent can do

The tools are not a mirror of the API's endpoints — there would be hundreds, and a catalog that size makes a model worse at choosing. They come in four groups instead.

| Group | Tools | What they are for |
| --- | --- | --- |
| Finding things | `describe_resource`, `search_resources`, `get_resource` | Discovering which resources exist and what they can be filtered by, then finding and reading records |
| Answering with numbers | `describe_reporting`, `query_report` | Revenue, orders and units, sliced by time, product, channel or country — the same figures the dashboard charts show |
| Doing things | One tool per operation: `orders_cancel`, `fulfillments_mark_delivered`, `products_activate`, `refunds_create`, `price_lists_activate` and around fifty more | Each runs the same workflow the dashboard runs, so validations, emails and webhooks behave identically |
| Store setup | `create_resource`, `update_resource`, `delete_resource` | Markets, channels, delivery and payment methods, tax rates and the rest of the settings screens |

An agent is only ever shown the tools its key permits, so the list stays small and relevant: a key minted for order operations sees around twenty.

### How a conversation goes

The agent picks tools from what you ask; there is no command to learn.

> **You:** Which products are out of stock, and what did we sell in Germany last month?

The agent calls `describe_resource` to learn that products can be filtered by an `out_of_stock` scope, `search_resources` to list them, then `describe_reporting` and `query_report` for the German figures — and answers in one reply.

> **You:** Cancel order R123456789, refund the customer, and tell them why.

The agent finds the order, then calls `orders_cancel`. Your client asks you to confirm before the call runs; Spree then runs the same cancellation the dashboard runs, and the order's timeline records the API key as the canceller, so an audit later shows which agent did it.

## What it will not do

Some things are deliberately out of reach, whatever scopes the key holds.

- **Credentials.** API keys, integrations, webhook endpoints and gift card codes are never returned by any tool. A gift card code is the money itself, and an integration's settings are where provider credentials live.
- **Erasing a customer.** GDPR erasure is irreversible and is not something to put behind a single confirmation prompt. Do it in the dashboard.
- **Files.** Media uploads, import files and label downloads. The protocol carries text and structured data.
- **Order editing.** Adding line items, discounts and fees to an existing order still runs through paths that are not yet workflows. Cancelling, refunding and fulfilling all work today.

## Adding your own tools

The catalog is a registry in `spree_core`, so an extension or a host application adds to it without depending on the MCP gem. Two kinds of thing to add.

**A back-office operation you already have as a workflow.** Name its `Spree::Dependencies` key and the permission that should gate it:

```ruby server/config/initializers/spree.rb
Spree.agent_tools.expose_workflows(supplier_sync_workflow: 'write_purchasing')
```

That is the whole change. The tool's name comes from the workflow's own key (`suppliers.sync` becomes `suppliers_sync`), its description from the class's leading comment, and its parameters from `perform`'s signature and the YARD `@param` lines above it — so the tool and the workflow cannot drift apart. Two rules the derivation relies on: every parameter needs an `@param` with a type, and a parameter naming a record must be typed as a model the agent can already read.

**Something that is not a workflow** — a lookup against another system, a report of your own. Subclass `Spree::AgentTool` and register the class by name:

```ruby app/tools/my_shop/agent_tools/supplier_stock.rb
module MyShop
  module AgentTools
    # Asks the supplier's API what they hold, so a merchant can ask before
    # committing to a purchase order.
    class SupplierStock < Spree::AgentTool
      tool_name 'supplier_stock'
      description 'Current stock at a supplier, by SKU.'
      permission 'read_purchasing'

      param :sku, description: 'The SKU to look up', required: true

      def call(sku:)
        stock = MyShop::SupplierApi.stock_for(sku, store: context.store)
        return { error: "No supplier carries #{sku}." } if stock.nil?

        { summary: "#{sku}: #{stock} available", sku: sku, available: stock }
      end
    end
  end
end
```

```ruby server/config/initializers/spree.rb
Spree.agent_tools << 'MyShop::AgentTools::SupplierStock'
```

Four things worth knowing when you write one:

- **Registration is by name, not by class**, so your edits to a description or a parameter take effect on the next request rather than needing a restart.
- **`context` is who is asking**: `context.store` is always the caller's store, and `context.principal` is the admin or the API key — pass it to anything that records who acted.
- **A refusal is `{ error: '…' }`**, not an exception. The model reads that text and corrects itself, so write it as an instruction rather than a stack trace.
- **Keep the result small.** It lands in the model's context. Return a `summary` line plus the few fields that answer the question, and let the caller ask for more.

A tool is offered only to a credential holding its `permission`, so a key that cannot read purchasing never learns `supplier_stock` exists.

## Choosing between this and the CLI

The [`spree api` CLI](/developer/cli/admin-api) reaches every endpoint, handles bulk work, and its output pipes into other commands, so an agent with a shell should generally use it. Reach for this server when the shell is not available, or when the work is conversational — a tool shaped like "cancel this order" gives a model far less room to go wrong than composing the HTTP call itself, and each one runs the same workflow the dashboard runs.
